# design-gate — 화면 작업 관문 (사용자 결정 2026-09-28)

계기: 스킨 리프레시(2026-09-27)에서 브리프·원칙을 확인하지 않고 목업부터 만들었다. 목업은 실제 CSS가 아니어서 실물과 달랐고, 안내 문구·행동 유도 원칙도 점검하지 않았다. 원칙이 글로만 있으면 지켜지지 않는다 — 이 스킬과 훅이 확인을 건너뛸 수 없게 한다.

## 1. 읽기 (이 순서, 필요한 절만 범위 Read)
1. `.claude/skills/design-gate/CHECKLIST.md` 전체 — **사용자 디자인 결정 목록**과 점검표 틀. 짧다.
2. `.claude/rules/frontend.md`의 「화면 사용성 원칙」 — 안내 문구 최소 · 결정 최소 · 행동으로 유도.
3. `docs/design/BRIEF.md`의 「가장 잦은 작업」「성공 기준」 — 빠름·규율, 견적은 엑셀식 표.
4. `docs/design/SYSTEM.md`에서 이번 화면의 템플릿 절(목차 → Grep → 범위 Read). 새 색·서체·radius는 만들지 않는다(토큰은 `tokens.css`).

## 2. 점검표 만들기 — 코드를 쓰기 전에
- `.claude/skills/design-gate/CHECKLIST.md`의 「점검표 틀」을 `docs/design/checks/<YYYY-MM-DD>-<작업>.md`로 복사한다.
- 화면마다 항목을 **지금 화면 기준으로** 먼저 채운다(무엇이 어긋나 있나). 고칠 계획이 그 답이다.

## 3. 만들기
- 사용자 디자인 결정(CHECKLIST.md §1)을 바꾸지 않는다. 바꿔야 하면 멈추고 사용자에게 묻는다.
- 디자인 **비교·시안은 실제 앱 화면으로만** 보여 준다 — 목업 HTML은 실제 CSS 모듈과 달라 판단을 그르친다. 도구: `docs/DESIGN.md` §2-4.

## 4. 커밋 전
- 점검표의 모든 항목을 `- [x]`로 바꾸고 항목마다 근거 한 줄(무엇을 보고 확인했나)을 적는다. 지킬 수 없는 항목은 사용자 승인을 받고 이유를 적는다.
- 화면 코드(app/·ui/의 .tsx·.css) 커밋에는 점검표를 함께 스테이징한다 — 없거나 `- [ ]`가 남으면 훅이 커밋을 막는다.
- 완료 판정은 여전히 독립 DOM 감사 → `/design-review` → `/qa`(CLAUDE.md §6). 점검표는 그 대신이 아니라 그 앞이다.
