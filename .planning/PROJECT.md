# PLANT8 ERP — 프로젝트·지출·손익 관리 시스템

## What This Is

BTL 광고·마케팅 대행사 PLANT8(현재 10명, 30명까지 성장 예정)의 전 직원이 매일 쓰는 프로젝트 관리 시스템이다. 지금 쓰는 PHP 인트라넷의 4기능(프로젝트·견적 줄·지출결의+결재·법인카드)을 그대로 이어받고, 그 위에 프로젝트·팀 손익, 증빙 필수 규칙, 마감 알림, 기타소득 확인증 현장 수집, 연차, 연간 팀 목표를 더한다. 만들고 운영하는 사람은 전문 개발자가 아닌 사용자 1인 + Claude Code이므로, 완성 뒤에는 사람·계급·권한·정보 노출·결재선·규칙·알림·코드표·화면 입력 항목까지 코드 수정 없이 관리 화면에서 조정한다. 이전 시도(260907)의 코드는 가져오지 않고 작고 단순하게 새로 짓는다.

## Core Value

기획본부와 경영관리본부가 프로젝트마다 같은 숫자(견적·예상 비용·확정 비용·손익)를 본다. 기획본부는 계산식이나 근거 줄을 보지 않고도 계산된 숫자를 납득할 수 있어야 하고, 경영관리·대표는 근거 줄까지 내려가 볼 수 있으며 계산식은 설정 화면에 드러나 있다.

- [ ] 법인카드 사용 등록, 견적 줄과 연결, 이중 계산 없음 (`CARD_USED` 433건 이전)
- [ ] 거래처·클라이언트·직원·법인카드·분류 코드표 마스터 이전 (거래처 278곳 중 미사용 표시, 자동완성)
- [ ] 이전 스크립트는 멱등·재실행 가능. 표별 행수 일치 검증, 불일치는 고치지 않고 표시
- [ ] 전환: 이전 완료 뒤 새 시스템이 입력, 인트라넷은 조회만. 직원에게 같은 것을 두 번 입력시키지 않는다

**기획본부 편의성 — 업무가 늘어나는 만큼 더 단순하게**
- [ ] 인트라넷의 자잘한 오류 제거: 견적가·차익은 서버가 계산, 승인·삭제 GET 금지, 저장 실패·중복 저장·입력값 유실 없음
- [ ] 입력 편의: 거래처·클라이언트·프로젝트 자동완성, 기본값 자동 채움, 이전 건 복사. 견적 줄 → 지출결의 → 증빙이 한 흐름으로 이어져 같은 값을 다시 적지 않는다
- [ ] 늘어나는 업무(증빙 첨부·규칙 준수)는 클릭 수·화면 이동을 인트라넷보다 줄여 상쇄. 기준: 지출결의 한 건 = 화면 하나에서 첨부까지 완료
- [ ] 화면 기준은 `docs/design/SYSTEM.md` 하나. 처음 보는 직원이 설명 없이 자기 일을 찾는다. 역할별 첫 화면. 폰에서도 쓸 수 있는 반응형

**손익 — 납득 가능한 세 층**
- [ ] 프로젝트 손익: 매출 − 비용. 비용은 줄마다 가장 굳은 값 하나 — 증빙액 > 지출결의 승인액 > 견적 실행가(예상). 진행 중에는 예상값이 든다
- [ ] 매출 기준(세금계산서 발행액 / 계약 금액 / 입금액)과 연도 귀속 날짜(발행일 / 종료일 / 입금일)를 설정에서 선택
- [ ] 팀 손익 = 팀 프로젝트 손익 합 − 수주 실패 비용(제안·PT 등, 수주되면 프로젝트 비용) − 팀이 직접 쓴 관리비(프로젝트 없이 팀 이름으로 올린 지출). 공통비 배부·인건비 없음
- [ ] 경영관리·대표는 모든 손익 숫자에서 근거 줄(견적 줄·지출결의·증빙)까지 드릴다운. 계산식은 설정 화면에 노출
- [ ] 기획본부는 드릴다운·계산식 없이 결과 숫자만 본다. 자기가 입력한 견적·지출과 그 숫자가 어긋나지 않아 설명 없이 납득할 수 있어야 한다(같은 용어, 같은 단위, 입력 즉시 반영)
- [ ] 열람 범위: 대표·경영관리는 전체, 팀장은 자기 팀, 기획본부(staff)는 기본 비노출

**연간 목표·인센티브**
- [ ] 팀별 한 해 목표(매출·이익 등) 입력, 진행률·달성 여부 표시. 팀장까지 열람
- [ ] 달성 시 인센티브 금액을 설정된 규칙으로 계산. 대표·경영관리만 열람
- [ ] 프로젝트가 어느 해 성과에 들어가는지의 기준은 위 연도 귀속 설정과 같고 화면에 명시

**규칙 강제 + 마감 알림 (지출 습관 구축)**
- [ ] 결재 통과 없이 지급 진행 불가. 증빙 없으면 마감(정산) 불가 — 규칙별 on/off는 설정
- [ ] 마감·기한 알림: 지출결의 누락, 지급일 임박, 결재 대기, 증빙 미첨부. 시점·대상은 설정
- [ ] 알림 채널: 앱 안 알림함 + 이메일. 중복 발송 방지

**증빙·확인증·연차**
- [ ] 증빙(세금계산서·영수증·카드 전표) 첨부, 지출결의·법인카드 건에 연결. 첨부 파일 저장
- [ ] 기타소득 확인증: 외부 인력이 폰에서 서명·주민등록번호 제출(외부 열람 링크). 개인정보 암호화·보존 기간·열람 권한은 보안 감사 뒤 확정
- [ ] 연차 신청·승인·잔여 일수

**코드 수정 없는 운영 (비개발자 유지보수)**
- [ ] 사람 등록 + 계급 + 팀 선택으로 입사자 추가. 계급 종류는 데이터(기본 5: 대표·본부 책임자·팀장·기획 PM·시스템 관리자)
- [ ] 권한표: 계급 × 메뉴 × 동작(보기/쓰기/승인) 체크박스
- [ ] 정보 노출표: 계급 × 정보 항목(손익 숫자·팀 비용·목표·인센티브·거래처 금액 등) 보기 여부. 기획본부 기본값 = 옛 인트라넷 수준만, 새 기능 정보는 기본 숨김
- [ ] 결재 단계·담당 계급, 규칙 on/off, 알림 시점·대상, 세율·수식을 설정 화면에서 변경
- [ ] 분류·코드표·선택지(견적 대분류·소분류, 지급 방식, 프로젝트 상태 등) 관리 화면
- [ ] 화면 입력 항목 추가: 관리자가 프로젝트·견적 줄·거래처 등에 칸(텍스트·숫자·날짜·선택)을 추가하면 입력·목록·검색에 반영
- [ ] 화면에 있는 설정 키는 서버가 반드시 읽는다(테스트로 강제). 설정 JSON 내보내기·가져오기

## Context

**현재 인트라넷 (대체 대상)**: PHP CodeIgniter 3 + MySQL(AWS RDS ap-northeast-2), 15,650줄. 실제 쓰는 기능 4개, 표 10개 2,849행. 2026년 1~9월 프로젝트 125건, 견적 줄 1,379행, 지급요청 464건(요청자 11명), 법인카드 433건(작성자 10명), 7월 로그인 세션 1,453회 — 오류가 많아도 매일 쓴다. 돈이 나가려면 견적 줄 → 지급요청 → 3단 결재를 거쳐야 하기 때문이다. 결함: 서버 검증 없음(차익 불일치 66줄), 승인·삭제 GET, 비밀번호 평문, CSRF 꺼짐, 첨부 미사용, 고아 견적 줄 5. 손익·증빙·확인증·알림 화면 없음. 자세한 감사는 `docs/research/repo-audit-260917.md`.

**왜 다시 만드나**: 기획본부와 경영관리가 프로젝트 하나의 돈을 같은 숫자로 보지 못한다. 기획본부 PM은 발주 뒤 몰아서 입력하고, 경영관리는 그때 처음 금액을 본다. "기획본부에서 본인들이 입력하는 만큼만 프로젝트 비용이라고 인식한다." 인트라넷은 기능이 너무 없고, 경영관리가 기획본부 업무를 파악할 동선이 없다. 부차 목적: 직원들이 사내 지출 규칙과 체계를 습관으로 익히게 한다.

**세 번의 실패한 재구현**: `plant8-erp-rebuild`("20명이 쓸 것에 비해 너무 크다"로 폐기), `260807`, `260907`(41일간 1,845커밋, 63만 줄, 1만 3천 테스트, 사용자 0). 실패 원인은 수요가 아니라 범위와 "다 만든 뒤 옮긴다". 이번 위험은 못 만드는 게 아니라 **또 너무 많이 만드는 것**이다. 260907의 용어·업무 규칙 조사는 `docs/research/erp260907-*.md`에 있다(참고용, 코드는 가져오지 않음).

**손익이 왜 어려운가**: 기획본부와 경영관리가 보는 손익이 다르다. 새 시스템의 손익이 인트라넷 숫자와 달라져도 기획본부가 그 계산을 납득해야 한다. 프로젝트 손익만이 아니라 수주 단계 비용과 팀 관리비를 포함한 최종 손익을 팀장이 확인해야 하고, 팀 연간 목표 달성이 인센티브로 이어지므로 "어느 프로젝트가 어느 해 성과인가"의 기준도 납득 가능해야 한다. 따라서 계산식·귀속 기준은 코드에 박지 않고 설정으로 두며, 모든 숫자에서 근거 줄로 내려갈 수 있어야 한다.

**정보 노출 원칙**: 기획본부는 기본적으로 옛 인트라넷과 비슷한 정보만 본다. 새로 추가되는 기능의 정보(손익·팀 비용·목표·인센티브)는 극도로 제한하고, 무엇을 누구에게 보일지는 전부 설정과 권한에서 조정한다. 계산식과 근거 줄 드릴다운도 기획본부에는 노출하지 않는다. 납득은 투명성이 아니라 **일관성**에서 온다: 기획본부가 입력한 값과 화면의 결과 숫자가 어긋나지 않고, 용어·단위가 같고, 입력하면 즉시 반영된다.

**기획본부의 기준**: 기획본부 입장에서 인트라넷의 문제는 자잘한 오류, 데이터 입력의 불편함, 디자인이다. 새 시스템의 기획본부 편의는 이 셋으로 판단한다. 새 시스템에서 기획본부의 업무(증빙 첨부·규칙 준수)는 인트라넷보다 늘어나므로, 워크플로는 그만큼 더 단순하고 편리해야 한다.

**사용자**: 대표(전체 손익·인센티브), 경영관리 담당(나갈 돈·증빙·결재·인센티브), 본부 책임자·팀장(자기 팀 손익·목표), 기획 PM(프로젝트·견적·지출결의·법인카드 입력), 시스템 관리자(= 사용자 본인, 설정·권한). 외부 인력(확인증 제출, 로그인 없음).

**이 문서의 출처**: `/gsd-new-project` 문답(2026-09-17). 이전 `/office-hours` 설계 문서(`docs/designs/plant8-erp-phase1-intranet-replacement.md`)는 사용자가 260907 재사용과 9/30 일정 때문에 폐기했다. 그 문서에서 유지한 것은 핵심 가치, 인트라넷 4기능 대체, 지출 규칙·체계 습관 구축 세 가지뿐이다.

## Constraints

- **인력**: 사용자 1인(비개발자) + Claude Code. 검토자 없음. 운영은 코드 수정 없이. 코드는 한 사람이 Claude Code로 고칠 수 있을 만큼 단순
- **일정**: 정해진 기한 없음. 제대로 만드는 게 우선
- **비용**: 구독·라이선스 도구 없음. 월 운영 비용 최소화. 인프라 선택은 비용·유지 관리·단순함 기준
- **호스팅**: 개인 Google 계정 GCP에서 먼저 → 회사 GCP로 이식. Cloud Run + Cloud SQL(둘 다 서울 리전) 확정. 프로젝트 ID 미고정, 스크립트 한 번으로 재현
- **전환**: 인트라넷 데이터 전부 이전. 이전 뒤 새 시스템이 입력, 인트라넷은 조회만
- **개인정보**: 기타소득 확인증(주민등록번호), 계좌번호. `/cso` 보안 감사 필수. 인트라넷 평문 비밀번호는 이전하지 않음
- **디자인**: `docs/DESIGN.md` 절차 우선. `docs/design/SYSTEM.md` 없으면 화면을 만들지 않고 §1→§3 먼저. 새 색·서체·radius 생성 금지, 토큰은 `tokens.css`에서만
- **규모**: 10명 → 30명, 동시 사용자 수십 명. 성능보다 이식성과 단순함
- **코딩 규칙 (CLAUDE.md)**: TDD, `any` 금지, 새 의존성은 이유 + 승인, 시크릿 코드 금지, 요청받지 않은 리팩터 금지, 한 커밋 한 의도
- **워크플로**: 계획은 `/plan-ceo-review` → `/plan-eng-review` 게이트 통과 뒤 실행. 실행 상태의 단일 출처는 `.planning/`
