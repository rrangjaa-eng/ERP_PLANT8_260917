# Requirements: PLANT8 ERP — 프로젝트·지출·손익 관리 시스템

**Defined:** 2026-09-17
**Core Value:** 기획본부와 경영관리본부가 프로젝트마다 같은 숫자를 본다. 기획본부는 계산식·근거 없이 결과 숫자로 납득하고, 경영관리·대표는 근거 줄까지 본다.

## v1 Requirements

Requirements for initial release. Each maps to roadmap phases.

### 인증·계정 (AUTH)

- [ ] **AUTH-01**: 관리자가 직원 계정을 만들고 초기 비밀번호를 발급하면, 직원은 이메일+비밀번호로 로그인한다. 로그인 실패 N회(기본 5, 설정) 시 15분 잠금과 IP 속도 제한이 걸리고, 잠금·해제는 행동 로그에 남으며 관리자가 풀 수 있다
- [x] **AUTH-02**: 로그인 세션은 브라우저를 다시 열어도 유지되고, 어느 화면에서든 로그아웃할 수 있다
- [ ] **AUTH-03**: 직원은 비밀번호를 바꿀 수 있고, 관리자는 비밀번호를 재발급할 수 있다
- [ ] **AUTH-04**: 로그인 방식은 환경 변수로 선택된다(기본 이메일). Google 로그인 추가가 코드 구조를 바꾸지 않는다

### 마스터·코드표 (MAST)

- [ ] **MAST-01**: 거래처·클라이언트를 등록·수정하고, 미사용은 삭제 대신 숨김 표시한다. 입력 시 자동완성된다. 거래처 계좌번호는 앱 단에서 암호화 저장하고 기본은 뒤 4자리만 보이며, 마스킹 해제는 정보 노출표 항목이다. 거래처마다 기본 증빙 종류(세금계산서·계산서·카드 전표·기타소득·사업소득 등)를 두어 지출결의·카드 사용 등록 때 자동으로 채워진다
- [ ] **MAST-02**: 직원 등록 = 사람 + 계급 + 팀 선택. 입사자 추가에 코드 수정이 없다. 팀은 본부에 속한다(팀 ⊂ 본부). 팀 소속은 발령일 이력으로 남고, 비용 귀속·팀 손익은 사용일 시점의 소속 팀을 따른다
- [ ] **MAST-03**: 법인카드 마스터: 직원별 개인 지급 카드와 팀 전용 카드를 등록하고, 카드마다 소지자(직원) 또는 소속 팀을 지정한다
- [ ] **MAST-04**: 견적 대분류·소분류, 지급 방식, 프로젝트 상태 같은 코드표를 관리 화면에서 추가·수정·비활성화한다

### 프로젝트·견적 (PROJ)

- [ ] **PROJ-01**: 프로젝트를 등록·목록·상세로 다룬다(클라이언트, 담당 PM, 팀, 기간, 상태)
- [ ] **PROJ-02**: 견적 줄 원장에 견적가·실행가(예상 원가)를 입력하면 차익은 서버가 계산한다. 브라우저 계산값은 저장하지 않는다. 지출결의·구매 요청 등 연결 문서가 있는 견적 줄은 보관(삭제)하지 않고 '취소' 상태(견적가 0, 이력 유지)로만 바꾼다
- [ ] **PROJ-03**: 프로젝트에 매출 최소 칸(계약 금액, 세금계산서 발행일·발행액, 입금일·입금액)을 기록한다. 계약 금액·발행액은 공급가액으로 적고 부가세·합계는 자동 계산된다. 입금액은 통장에 들어온 금액(합계)으로 적고 시스템이 공급가액으로 역산한다. 별도 매출 모듈은 없다
- [ ] **PROJ-04**: 프로젝트 상태를 진행 → 완료(정산)로 바꿀 수 있고, 완료된 프로젝트에는 새 지출결의를 올릴 수 없다
- [ ] **PROJ-05**: 이전 프로젝트·견적 줄을 복사해 새로 만들 수 있고, 반복 입력 칸은 기본값이 채워진다
- [ ] **PROJ-06**: 완료(정산) 처리 시 시스템이 미결 지출결의·미매칭 견적 줄·매출 미입력을 점검해 이유와 함께 막는다. 강행 허용 여부는 설정
- [ ] **PROJ-07**: 견적은 사전 견적 → 상세 견적 차수(1차·2차…)로 관리되고, 차수마다 "고객 승인" 표시를 둔다. 승인 전에는 그 차수의 줄에서 지출결의·구매 요청을 올릴 수 없다(설정으로 끌 수 있음)

### 지출결의·결재·법인카드 (EXP)

- [ ] **EXP-01**: 견적 줄에서 "지출결의 올리기"를 누르면 거래처·금액·프로젝트가 자동으로 채워진다. 같은 값을 다시 적지 않는다. 지출결의는 기본 견적 줄 1개당 문서 1개다(여러 줄을 골라도 문서는 줄마다 하나). 분할 지급을 계획한 줄만 회차별 문서를 두며 회차 합계는 실행가를 넘을 수 없다. 같은 줄에서 두 번 눌러도 문서가 겹치지 않는다(idempotency key)
- [ ] **EXP-02**: 지출결의 한 건을 화면 하나에서 작성·증빙 첨부·제출까지 끝낸다
- [ ] **EXP-03**: 결재는 기본 4단(기안자 팀의 팀장 → 기안자 본부의 책임자 → 경영관리본부 담당 → 대표). 단계는 계급 × 조직 범위(기안자의 팀/본부/전사/특정 부서)로 정의되고 빈 자리는 건너뛴다. 기안자가 단계 담당 본인이면 그 단계를 건너뛴다(설정). 승인·반려(기안자에게 복귀)·회수가 된다. 상태 문서는 version 컬럼 낙관적 잠금으로 승인↔회수·승인↔반려 동시 조작을 막는다
- [ ] **EXP-04**: 결재선은 제출 시점에 문서에 고정된다. 이후 설정 변경이 진행 중 문서에 영향을 주지 않는다. 고정되는 것은 단계별 계급 × 조직 범위이며, 사람은 표시 시점의 현재 담당으로 해석하고 이미 승인한 사람은 그대로 보존된다
- [ ] **EXP-05**: 결재자는 결재 대기함에서 폰으로도 승인·반려한다
- [ ] **EXP-06**: 결재를 통과하지 않은 지출결의는 지급 완료 처리가 되지 않는다. 지급 완료된 견적 줄은 잠겨 새 지출결의를 올릴 수 없다(이중 지급 방지)
- [ ] **EXP-07**: 직원은 자기 카드·자기 팀 카드의 사용을 등록하고 견적 줄, 프로젝트 '견적 외 비용', 팀 비용 중 하나에 연결한다. 팀 비용을 고르면 소속 팀이 자동으로 정해진다. 연결 없는 카드 사용은 서버가 막는다(이중 계산 방지)
- [ ] **EXP-08**: 프로젝트 없이 팀 이름으로 지출(수주 실패 비용, 팀 관리비)을 올릴 수 있고 종류를 구분한다. 직원 개인이 쓴 비용(개인 카드 사용·개인 지출결의)이 프로젝트에 연결되지 않으면 사용일 기준 그 직원의 소속 팀 비용으로 귀속되고, 팀장 화면에 '프로젝트 미연결'로 표시된다
- [ ] **EXP-09**: 경영관리가 지급 예정일을 정하고 지급 완료 처리한다. 지급 완료액은 실제 이체 금액(부가세 포함·원천징수 차감 후)으로 적고, 시스템이 공급가액으로 역산해 계산값과 다르면 차이를 표시한다
- [ ] **EXP-10**: 온라인 구매 요청: 직원이 품목·링크·금액·연결할 견적 줄(또는 팀 비용)을 적어 경영관리에 신청하면, 경영관리가 법인카드로 구매하고 구매 완료 처리한다. 완료된 요청은 법인카드 사용 건으로 연결된다(신청/구매 완료/취소, 결재 없음). 어느 문이 열리는지는 사람이 고르지 않는다: 견적 줄의 협력사가 설정에 지정된 '온라인구매' 협력사면 구매 요청만, 그 외 협력사면 지출결의만 열린다
- [ ] **EXP-11**: 지급 예정일을 적지 않아도 시스템이 거래처별 지급 기한(기본 작성일+60일, 거래처별 조정)과 "기한 전 마지막 금요일" 규칙으로 자동 계산해 보여 준다. 규칙은 설정
- [ ] **EXP-12**: 결재 마감은 지급일 전 영업일 14시(설정). 마감이 지나면 그 주 지급 대상에서 빠지고, 공휴일이 끼면 마감일과 알림이 함께 앞당겨진다
- [ ] **EXP-13**: 증빙 없이 먼저 결제한 지출결의는 "선결제" 표시와 사유가 필수이고, 14일(설정) 안에 증빙이 없으면 독촉 알림이 가되 처리는 막지 않는다
- [ ] **EXP-14**: 지출결의는 제출 시 금액이 0보다 커야 하며 음수를 입력할 수 없다. 매출·조정 항목은 환불·할인을 위해 음수를 허용한다
- [ ] **EXP-15**: 사람은 공급가액만 적는다. 지출결의·카드 사용·구매 요청에 증빙 종류(세금계산서·계산서·카드 전표·현금영수증·기타소득·사업소득·해외 인보이스 등, 코드표)를 고르면 종류별 세금 규칙(없음 / 부가세 가산율 / 원천징수율+면제 기준(수령자 부담) / 원천징수 회사 대납(경품 등: 세율·계산 방식 단순 비율 또는 gross-up))에 따라 부가세 또는 원천징수액과 지급 총액을 서버가 계산해 보인다. 종류를 바꾸면 즉시 다시 계산된다. 규칙·세율은 이력형 설정이고 손익 비용은 공급가액 기준 그대로되, 회사 대납 세금은 그 줄의 프로젝트(또는 팀) 비용에 더해진다. 규칙 종류마다 적용 기준일(기본: 원천징수·회사 대납 = 지급일, 미지급이면 지급 예정일; 부가세 = 증빙일, 없으면 작성일)과 절사 단위(1원/10원)·방식(절사/반올림/올림)·최소 징수액을 갖고, 문서에는 계산 시점의 세율 버전이 저장되어 재계산 시 차이가 표시된다
- [ ] **EXP-16**: 경영관리는 자동 결제·정기 결제처럼 PM이 모르는 법인카드 사용을 대신 등록해 프로젝트(견적 줄 또는 견적가 0인 '견적 외 비용' 줄)나 카드 소지자의 팀 비용에 연결한다. 연결되면 담당 PM에게 알림이 가고 PM의 프로젝트 비용에 '경영관리 등록' 표시로 보인다. 결재는 없다

### 증빙 (EVID)

- [ ] **EVID-01**: 세금계산서·영수증·카드 전표 파일을 지출결의·법인카드 건에 첨부한다(폰 사진 포함). 업로드는 크기 한도(기본 10MB, 설정)·형식(이미지·PDF)을 검사하고 SHA-256으로 중복을 감지하며 폰 사진은 축소한다
- [ ] **EVID-02**: 증빙 필수 규칙이 켜져 있으면 증빙 없는 건은 지급 완료가 되지 않는다. 규칙은 설정에서 on/off
- [ ] **EVID-03**: 증빙 금액(공급가액)을 기록하면 그 줄의 확정 비용이 된다. 증빙의 부가세·원천징수는 종류별 규칙(EXP-15)으로 다시 계산되어 지급 총액에만 반영된다
- [ ] **EVID-04**: 증빙을 떼면 그 줄의 비용은 다시 예상(견적 실행가 또는 지출결의 승인액) 상태로 돌아간다

### 손익 (PNL)

- [ ] **PNL-01**: 프로젝트 상세 상단에 네 숫자(견적 / 예상 비용 / 확정 비용 / 수익금액·수익률)가 보인다. 계산할 수 없는 줄(예: 환율 없음, 매출 기준 미입력)은 숫자와 별도로 '계산 불가(이유)'로 표시되어 합계에 들어가지 않고 건수 배지로 보인다
- [ ] **PNL-02**: 줄마다 가장 굳은 값 하나만 비용으로 든다: 증빙액 > 지출결의 승인액 > 견적 실행가. 진행 중에는 예상값이 든다. 회사 대납 세금(EXP-15)과 견적 외 비용(EXP-16)도 그 프로젝트의 비용에 든다. 목록·Excel·팀 합계와 상세(trace)는 하나의 effectiveCost SQL 식(우선순위 CASE + 근거 id)을 공유해 읽기 시점에 계산하고, 저장은 정산 스냅샷뿐이다. '목록 합계 = 상세 합계' 테스트가 있다
- [ ] **PNL-03**: 매출 기준(계산서 발행액 / 계약 금액 / 입금액)과 연도 귀속 날짜(발행일 / 종료일 / 입금일)를 설정에서 고르고, 화면에 현재 기준이 표시된다. 완료 전(매출 미확정)에는 상세 견적 합(없으면 사전 견적)을 분모로 쓰고, 완료 뒤에는 설정된 매출 기준을 쓴다
- [ ] **PNL-04**: 경영관리·대표는 손익 숫자에서 근거 줄(견적 줄·지출결의·증빙·리저브 출금·'계산 불가' 이유)까지 내려가 보고, 계산식은 설정 화면에 보인다
- [ ] **PNL-05**: 기획본부는 결과 숫자만 본다. 자기가 입력한 견적·지출과 숫자가 어긋나지 않고, 같은 용어·단위로 즉시 반영된다
- [ ] **PNL-06**: 완료(정산) 처리된 프로젝트의 손익은 스냅샷으로 고정되고, 이후 설정 변경에 소급되지 않는다. 완료 뒤 계약 금액·매출이 정정되면 스냅샷은 재계산하지 않고 차이만 표시한다. 완료(정산)는 정산 결재 문서(경영관리 기안 → 대표 승인)로 처리되며 대표 승인 순간 스냅샷이 찍힌다
- [ ] **PNL-07**: 팀 손익 = 팀 프로젝트 손익 합 − 수주 실패 비용 − 팀 직접 관리비(팀 이름 지출 + 프로젝트 미연결 직원 개인 비용, 사용일 시점 소속 기준). 팀장은 자기 팀, 대표·경영관리는 전체를 본다
- [ ] **PNL-08**: 프로젝트·팀 손익 목록을 Excel로 내보낸다. 정보 노출표가 내보내기에도 적용된다
- [ ] **PNL-09**: 모든 금액 입력·계산·표시는 공급가액(부가세 제외) 기준이며 화면에 명시된다. 예외는 통장에 실제 오간 돈 칸(입금액·지급 완료액)뿐이며 합계로 적고 공급가액으로 역산한다. 부가세율(기본 10%)·원천징수율·면제 기준은 적용 시작일이 있는 이력형 설정이다

### 리저브·외화 (RSV, FX)

- [ ] **RSV-01**: 클라이언트별 리저브 대장: 입금·출금·잔액을 날짜순으로 기록하고 본다. 각 줄은 프로젝트에 연결할 수 있고, 통화·환율·원화 환산액을 함께 적는다
- [ ] **RSV-02**: 프로젝트 매출을 리저브에서 충당하면 대장에 출금으로 남고, 그 금액이 손익의 매출(설정된 매출 기준)에 반영된다. 잔액이 부족하면 이유와 함께 막힌다
- [ ] **FX-01**: 매출·지출결의·증빙·법인카드·리저브 금액에 통화·외화 금액·환율·원화 환산액을 함께 기록한다. 환율은 입력할 때 사람이 적고 기본값은 설정(통화별 최근 환율)에서 온다. 손익·목표·내보내기는 원화 환산액 기준이며 원래 통화·금액이 함께 표시된다. 원화는 정수 원, 외화 금액은 소수 2자리, 환율은 소수 4자리이고 반올림은 서버의 단일 함수에서만 한다. 분할 시 합계가 원금과 같도록 마지막 회차에서 보정한다

### 알림 (NOTI)

- [ ] **NOTI-01**: 앱 안 알림함과 미읽음 배지가 있다
- [ ] **NOTI-02**: 같은 알림이 이메일로도 간다. 발송은 회사 Google 계정 SMTP(환경 변수 host·user·password·from; Workspace 릴레이 설정은 TODOS.md)이며, 발송 실패는 알림함과 관리자 배너에 남는다
- [ ] **NOTI-03**: 관리자가 설정에서 알림 규칙을 새로 만든다. 조건 종류(상태 + 기준일로부터 N일 전/후, '프로젝트 종료 후 지출결의 없음' 같은 교차 문서 조건 등)는 코드에 등록되고, 규칙 = 조건 종류 × 파라미터(대상 문서(지출결의·구매 요청·결재·증빙·프로젝트·연차), N일, 받는 사람(계급·담당자·팀장), 채널)의 인스턴스다. 기본 규칙 4개(종료 후 지출결의 없음, 지급 예정일 임박, 결재 대기 초과, 증빙 미첨부)는 시드로 제공
- [ ] **NOTI-04**: 같은 건이 두 번 발송되지 않는다. 스케줄러가 하루 몇 번 호출하는 단일 엔드포인트로 동작한다(큐 없음). tick은 advisory lock으로 동시 실행을 막고 notification_log 유니크 제약으로 중복 발송을 막는다

### 기타소득 확인증 (CERT)

- [ ] **CERT-01**: 외부 인력(수령자)이 직원 화면·인쇄물의 QR(1회성 링크)을 폰으로 찍고 들어와 본인 정보(이름·주민등록번호·주소·연락처·계좌)를 직접 입력하고 터치 서명을 제출한다(로그인 없음). 지급 금액·소득 종류·원천징수액은 지출결의에서 미리 채워져 수령자는 고칠 수 없다. 링크는 1회 제출 후 만료된다
- [ ] **CERT-02**: 주민등록번호는 앱 단에서 암호화 저장되고, 열람은 권한자로 제한되며 열람 기록이 남고, 보존 기간 뒤 파기된다
- [ ] **CERT-03**: 제출된 확인증을 해당 지출결의 건에 연결한다
- [ ] **CERT-04**: 개인 지급(기타소득·사업소득) 건에는 원천징수 제안 금액이 자동 계산되어 뜨고(EXP-15의 증빙 종류별 세금 규칙 중 원천징수 종류. 세율·면제 기준은 이력형 설정, 기본 기타소득 8.8%·사업소득 3.3%, 기타소득 면제 기준 = 기타소득금액 5만원 이하 = 지급액 125,000원 이하), 경영관리가 확정하면 지급액에 반영된다
- 활성화 조건: `/cso` 보안 감사 통과

### 코드 없는 운영 (ADMN)

- [ ] **ADMN-01**: 권한표: 계급 × 메뉴 × 동작(보기/쓰기/승인) 체크박스

- [ ] **ADMN-12**: "지우지 않는다": 사용자가 무엇을 삭제해도 보관함으로 이동하며, 관리자만 보관함에서 보고 복원할 수 있다. 삭제·복원은 행동 로그에 남는다

### 데이터 이전·전환 (MIG)

- [ ] **MIG-01**: 인트라넷 데이터를 옛 표 구조 그대로 가져오지 않고, 새 시스템의 표·코드표·상태·번호 서식에 맞게 변환해 입력한다. 원본 행마다 새 시스템의 대응 행이 있음을 검증한다(멱등·재실행). 적재와 검증은 단일 트랜잭션이며 검증 실패 시 ROLLBACK하고 migration_runs에 기록한다. 이전 행은 source='intranet'으로 표시된다. 적재는 (source, source_id) 키 upsert라 재실행·리허설이 안전하고, 이전 문서 번호는 옛 id에서 결정적으로 파생된다(예약 범위). 델타 이전 시 새 시스템에 이미 있는 유사 프로젝트(클라이언트·이름·기간)는 중복 후보로 표시된다. 추출·변환은 Phase 4부터 시작해 실제 데이터를 픽스처로 쓰며, 옛 금액의 공급가/합계 판정(표본 대조 + 행별 amount_basis, 불명은 '계산 불가')과 외화 건수 보고를 Phase 4 변환에서 한다
- [ ] **MIG-02**: 차익 불일치(66줄)·고아 견적 줄(5)은 고치지 않고 표시만 한다
- [ ] **MIG-03**: 결재 상태를 인트라넷 3단 → 새 4단으로 매핑하고, 법인카드 433건의 견적 줄 연결을 유지한다. 이전 행은 편집되기 전까지 새 규칙(고객 승인 게이트, 증빙 필수, 결재 마감, 알림)에서 면제되고 연도 귀속일은 종료일로 둔다. 완료된 옛 프로젝트는 일괄 '이전 완료' 처리한다
- [ ] **MIG-04**: 평문 비밀번호는 이전하지 않고 계정을 새로 발급한다
- [ ] **MIG-05**: 리허설을 반복한 뒤 전환일에 인트라넷을 조회 전용으로 바꾸고 새 시스템만 입력한다. 리허설은 source='intranet' 행을 upsert로 재적재하고(삭제 없음) 설정·권한은 보존하며, 전환 전 새 시스템 입력은 source='demo'뿐이고(실제 업무 입력 없음) demo 행은 전환일에 삭제한다. 전환 착수 조건은 회사 GCP에서 배포 스크립트 1회 성공이고, 전환일에는 그 사이 인트라넷에 쌓인 델타만 이전한다

### 배포·운영 (OPS)

- [ ] **OPS-01**: 배포 스크립트 한 번으로 새 GCP 프로젝트에 기동한다. 프로젝트 ID·리전·DB 접속은 환경 변수. Cloud SQL은 공인 IP 없이 커넥터+IAM 인증(로컬은 Auth Proxy). 배포 스크립트는 max-instances × 풀 ≤ DB max_connections − 5 를 검사해 초과 시 거부하고, 확장-축소 마이그레이션 → 0% → 스모크 → 100% 순으로 배포하며 rollback.sh가 있다. Cloud Monitoring 경보 3개(5xx>5%·tick 24h 미성공·백업 실패)가 관리자 메일로 간다
- [ ] **OPS-02**: 사용 없을 때 비용이 0에 가깝고(스케일-투-제로), 월 비용 목표가 문서화된다
- [ ] **OPS-03**: DB가 자동 백업되고 복원 절차가 문서화되며 복원 리허설을 1회 한다
- [ ] **OPS-04**: 린트(`any` 금지)·타입체크·핵심 흐름(로그인→지출결의→결재→손익) 통합 테스트가 CI에서 돈다. ESLint import 경계(app↛repositories/db, domain↛app, repository는 viewer 필수)와 Server Action zod 검증 필수 린트가 포함된다
- [ ] **OPS-05**: 직원 계정별 핵심 행동만 로그로 남긴다: 로그인, 문서 생성·제출·승인·반려·회수·삭제, 지급·구매 처리, 설정·권한 변경, 민감 정보(손익·인센티브·주민등록번호) 열람. 단순 조회·화면 이동 같은 잡음은 남기지 않는다. 관리자는 로그를 정리(수정·삭제)할 수 있다. Excel 내보내기와 마스킹 해제는 설정으로 끌 수 없는 핵심 로그다
- [ ] **OPS-06**: 관리자 시스템 상태 화면: 마지막 알림 tick·백업·이전 실행·계산 불가 건수·DB 커넥션·배포 버전을 보이고 한도 초과 시 배너가 뜬다. 서버 로그는 JSON 형식이다
- [ ] **OPS-07**: `docs/ARCHITECTURE.md`·`docs/OPERATIONS.md`(런북 포함)를 Phase 1 산출물로 만들고 페이즈마다 갱신한다(각 300줄 상한)
