# Roadmap: PLANT8 ERP

## Overview

배포부터 시작한다. Phase 1은 기능이 아니라 "서울 리전 Cloud Run + Cloud SQL에 스크립트 한 번으로 올라가고 로그인이 된다"를 증명하고, Phase 2에서 모든 화면의 기준인 `docs/design/SYSTEM.md`를 확정한다. Phase 3에서 권한·정보 노출·설정 레지스트리·마스터를 관리자 화면으로 세워 이후 어떤 화면도 권한 없이 만들어질 수 없게 한 뒤, Phase 4~6에서 인트라넷 4기능(프로젝트·견적 줄·지출결의+결재·법인카드)을 기획 PM → 결재자 → 경영관리 순서의 세 수직 슬라이스로 대체한다. Phase 7에서 인트라넷 데이터 전부를 리허설 반복으로 이전해 전환하고, 그 실데이터 위에 Phase 8 프로젝트 손익, Phase 9 팀 손익·연간 목표·인센티브를 얹는다. 개인정보를 다루는 기타소득 확인증(Phase 10)은 `/cso` 보안 감사 통과를 조건으로 마지막에 둔다.

세 번의 실패("다 만든 뒤 옮긴다")를 피하기 위해 페이즈마다 실제 사용자가 배포된 앱에 로그인해 실제 업무 하나를 끝낼 수 있어야 한다(`**Mode:** mvp`). 다듬기·정리 페이즈는 없다.

**페이즈 수 근거:** 표준 granularity(5~8)를 넘겨 10개로 둔 이유 — 배포 스켈레톤과 디자인 시스템이 각각 독립 게이트(하드 제약 1·2)이고, 지출결의 흐름 21개 요구사항은 PM/결재자 슬라이스와 경영관리 슬라이스로 나눠야 한 페이즈가 3~5플랜에 들어가며, 데이터 이전·프로젝트 손익·팀 손익·확인증(`/cso` 게이트)은 각각 별도 검증 단위이기 때문이다.

**디자인 시스템 순서(하드 제약 2) 선택:** Phase 1 = 배포 스켈레톤(임시 로그인·내 계정 화면만, 업무 화면 없음) → Phase 2 = 디자인 시스템. Phase 1의 임시 화면은 무스타일이며 Phase 2에서 SYSTEM.md 기준으로 교체된다. 첫 업무 화면은 Phase 3부터다.

**리저브·외화 배치:** 통화·환율·원화 환산 금액 모델(FX-01)과 클라이언트별 리저브 대장(RSV-01)은 Phase 4에 둔다 — Phase 5·6이 지출결의·증빙·법인카드 금액을 넣기 전에 금액 모델이 먼저 있어야 하고, 리저브 대장은 매출 칸과 같은 자리(프로젝트·클라이언트)에 붙기 때문이다. 리저브 충당 → 매출 반영(RSV-02)은 매출 기준(PNL-03)이 생기는 Phase 8이다. 그 결과 Phase 4가 11개 요구사항으로 원장 페이즈 중 가장 크고 5플랜(상한)에 닿을 것으로 본다. 계획 단계에서 5플랜을 넘기면 리저브 대장(RSV-01)을 별도 페이즈로 뗀다(`/gsd-phase`).

**CEO 리뷰 반영(260917, HOLD SCOPE):** `docs/designs/plant8-erp-roadmap-ceo-review-260917.md`의 결정 23건(1A~23A), 시점 결정 D3(완료=정산 결재 문서)·D4(원화 정수·서버 단일 반올림)·D5(이메일=회사 Google SMTP), OUTSIDE VOICE OV-1~8이 각 페이즈의 성공 기준에 접혀 있다. 새 기능은 없고 OPS-06(관리자 시스템 상태 화면)·OPS-07(`docs/ARCHITECTURE.md`·`docs/OPERATIONS.md`)만 Phase 1에 더해져 v1은 87개다. 구조 변화 세 가지 — Phase 3은 메커니즘+마스터로 좁히고 전 메뉴 검수는 Phase 6 끝으로(OV-5), 인트라넷 추출·변환 스크립트는 Phase 4부터 시작해 Phase 7은 델타 이전+전환만(OV-1), Phase 7 착수 게이트는 회사 GCP에서 deploy.sh 1회 성공(OV-6)이고 Phase 8 착수 조건은 Phase 4~6 실사용 지표다.

## Phase Details

### Phase 1: 배포 스켈레톤·로그인
**Goal**: 관리자(사용자 본인)가 배포 스크립트 한 번으로 띄운 서울 리전 Cloud Run 앱에 직원 계정으로 로그인해 비밀번호를 바꾸고 로그아웃한다 — 기능보다 "배포된다"를 먼저 증명한다. 배포 순서·롤백·경보·운영 문서·시스템 상태 화면 뼈대가 이 페이즈의 산출물이며 이후 페이즈는 여기에 항목만 더한다
**Mode:** mvp
**Depends on**: Nothing (first phase)
**Requirements**: AUTH-01, AUTH-02, AUTH-03, AUTH-04, OPS-01, OPS-02, OPS-04, OPS-06, OPS-07
**Success Criteria** (what must be TRUE):
  1. `scripts/deploy.sh` 한 번으로 빈 GCP 프로젝트에 Cloud Run(서울) + Cloud SQL(서울, 최소 사양) + Secret Manager가 만들어지고 앱이 뜬다. Cloud SQL은 공인 IP 없이 Cloud SQL 커넥터 + IAM 인증으로만 붙고 로컬 개발은 Auth Proxy를 쓴다. 프로젝트 ID·리전·DB 접속과 이메일 SMTP 4개(host·user·password·from — 이 페이즈는 정의만, 발송은 Phase 6)는 환경 변수뿐이며 코드·커밋에 시크릿이 없다. 같은 스크립트로 개인 GCP → 회사 GCP 이식이 재현된다
  2. 관리자가 시드/CLI 명령으로 직원 계정과 초기 비밀번호를 발급하면, 직원이 배포된 URL에서 이메일+비밀번호로 로그인하고, 브라우저를 닫았다 열어도 세션이 유지되며, 어느 화면에서든 로그아웃할 수 있다. 로그인 실패 N회(기본 5, 설정)면 15분 잠금과 IP 속도 제한이 걸리고, 잠금·해제는 행동 로그에 남으며 관리자가 풀 수 있다
  3. 직원이 자기 비밀번호를 바꾸고 관리자가 재발급할 수 있다. 로그인 방식은 환경 변수 하나(예: `AUTH_PROVIDER=email`)로 선택되고 Google 로그인은 어댑터 자리만 있어 코드 구조 변경 없이 켤 수 있다
  4. CI가 린트(`any` 금지)·타입체크·실 DB 통합 테스트(로그인 흐름)를 돌리고 실패하면 배포가 막힌다. 린트에는 ESLint import 경계(app↛repositories/db, domain↛app, repository는 viewer 필수)와 Server Action zod 검증 필수 규칙이 들어 있다. 이 통합 테스트는 이후 페이즈가 지출결의→결재→손익 단계를 덧붙여 가는 뼈대다
  5. `docs/ARCHITECTURE.md`와 `docs/OPERATIONS.md`(런북 포함)가 이 페이즈의 산출물로 존재하고 각 300줄 상한이며 이후 페이즈마다 갱신된다. OPERATIONS.md에는 월 운영 비용 목표(Cloud Run 스케일-투-제로 + Cloud SQL 최소 사양, 유휴 시에도 DB는 과금)와 실제 과금 항목, 배포·롤백·경보 대응 절차가 적혀 있다
  6. 배포는 확장-축소(expand-contract) 마이그레이션 린트를 통과한 뒤 migrate → 트래픽 0% 리비전 → 스모크 → 100% 순서로 진행되고 `scripts/rollback.sh`로 직전 리비전에 돌아간다. deploy.sh는 max-instances × 커넥션 풀 ≤ DB max_connections − 5 를 검사해 초과 시 배포를 거부한다. Cloud Monitoring 경보 3개(5xx > 5%·알림 tick 24시간 미성공·백업 실패)가 관리자 메일로 가고 deploy.sh로 재현된다
  7. 관리자 시스템 상태 화면 뼈대가 있어 배포 버전·DB 커넥션·마지막 백업을 보이고 한도 초과 시 배너가 뜬다. 서버 로그는 JSON 형식이다. 이후 페이즈가 항목을 더한다(Phase 6 마지막 알림 tick, Phase 7 이전 실행·백업, Phase 8 계산 불가 건수)

### Phase 2: 디자인 시스템·앱 셸
**Goal**: 직원이 폰과 PC에서 `docs/design/SYSTEM.md` 기준으로 만들어진 앱 셸(로그인·내 계정·내비게이션)을 쓰고, 이후 모든 화면은 이 토큰·컴포넌트만 쓴다
**Mode:** mvp
**Depends on**: Phase 1
**Requirements**: UX-01
**Success Criteria** (what must be TRUE):
  1. `docs/design/SYSTEM.md`와 `docs/design/tokens.css`가 존재하고, `docs/DESIGN.md` §1 브리프(`docs/design/BRIEF.md`) → §2 발산(후보 방향 비교, `docs/design/EXPLORE.md`) → §3 수렴 절차의 산출물이며 `/plan-design-review`를 통과했다. 260907의 화면·정보구조·UI 흐름은 참고하지 않았다
  2. 배포된 앱의 로그인·내 계정·앱 셸(내비게이션·레이아웃·빈 상태)이 SYSTEM.md 컴포넌트와 tokens.css 토큰만 쓴다. 새 색·서체·radius가 없고 Phase 1의 임시 화면은 남아 있지 않다
  3. 폰(375px)과 PC에서 같은 셸이 깨지지 않고, 키보드만으로 로그인·내비게이션·비밀번호 변경이 된다
  4. 이후 페이즈가 그대로 가져다 쓰는 핵심 컴포넌트 계약이 SYSTEM.md에 있다: 서버 검증 오류를 보여주는 폼, 엑셀식 표 입력(grid), 선행 단계 전 비활성 + 이유를 보이는 행동 유도 버튼, 알림함·배지, 폰용 목록·시트. 모든 컴포넌트 계약은 LOADING/EMPTY/ERROR/SUCCESS/PARTIAL 다섯 상태를 필수로 정의하고 EMPTY·ERROR는 다음 행동을 유도한다(안내 문구 없음)
  5. 엑셀식 표(grid)는 이 페이즈에서 동작 계약만 확정한다: Tab/Enter·방향키 이동, 여러 칸 복사·붙여넣기, Esc 취소, 저장·새 줄 단축키, 일괄 저장은 전부 저장 또는 전부 거부이며 충돌·오류 칸을 표시한다. 자체 구현/라이브러리 선택은 Phase 4 계획에서 한다

### Phase 3: 권한·설정·마스터 (관리자 운영 콘솔)

### Phase 4: 프로젝트·견적 원장
**Goal**: 기획 PM이 프로젝트를 등록하고 엑셀처럼 견적 줄을 입력하면 차익이 서버에서 계산되며, 사전→상세 차수와 고객 승인, 매출 칸, 진행→완료 상태까지 프로젝트의 돈 뼈대가 선다. 모든 돈 칸은 통화·환율·원화 환산액을 갖는 하나의 금액 모델을 쓰고, 경영관리는 클라이언트별 리저브 대장을 기록한다
**Mode:** mvp
**Depends on**: Phase 3
**Requirements**: PROJ-01, PROJ-02, PROJ-03, PROJ-04, PROJ-05, PROJ-07, ADMN-09, UX-04, UX-05, RSV-01, FX-01
**Success Criteria** (what must be TRUE):
  1. PM이 프로젝트(클라이언트·담당 PM·팀·기간·상태)를 등록·목록·상세로 다루고, 번호는 설정된 서식(접두어·연도·자릿수·구분자·순번 범위, 예: 26001)으로 자동 부여된다. 클라이언트·거래처는 자동완성되고, 이전 프로젝트·견적 줄 복사와 기본값 채움으로 반복 입력이 없다. 목록 합계(견적·실행가·차익)는 집계 쿼리 1회로 계산되고(Phase 8의 비용 우선순위 CASE 집계가 같은 자리에 얹힌다), 목록·검색이 쓰는 인덱스 목록이 `docs/ARCHITECTURE.md`에 있으며, 요청 본문은 1MB 한도, 목록 응답은 p99 500ms 이내다
  2. 견적 줄 표에서 Tab/Enter·방향키 이동, 여러 칸 복사·붙여넣기, Esc 취소, 저장·새 줄 단축키로 키보드만으로 입력이 끝나고, 견적가·실행가를 넣으면 차익은 서버가 계산해 저장한다. 브라우저 계산값은 저장되지 않아 인트라넷의 차익 불일치(66줄) 같은 오류가 구조적으로 불가능하다. 잘못된 입력은 서버 검증으로 즉시 안내되고, 저장 실패·중복 저장·입력값 유실이 없으며, 승인·삭제·상태 변경은 GET으로 되지 않는다
  3. 견적은 사전 견적 → 상세 견적 차수(1차·2차…)로 관리되고 차수마다 "고객 승인" 표시가 있다. 승인 전 차수의 줄에서는 지출결의·구매 요청 동작이 비활성이며(설정으로 끌 수 있음) 이 상태가 Phase 5·6의 게이트로 그대로 쓰인다
  4. 프로젝트에 계약 금액·세금계산서 발행일/발행액·입금일/입금액을 적을 수 있고, 진행 → 완료(정산) 전환이 되며 완료된 프로젝트는 견적 줄이 잠기고 새 지출을 받지 않는 상태로 표시된다(전환을 정산 결재 문서로 처리하는 것은 Phase 5 D3, 미결 점검은 Phase 6, 스냅샷은 Phase 8). 지출결의·구매 요청은 음수 없이 양수만, 매출·조정 항목은 환불·할인을 위해 음수를 허용하는 규칙이 스키마에 있다. 지출결의·구매 요청 등 연결 문서가 있는 견적 줄은 보관(삭제)되지 않고 '취소' 상태(견적가 0, 이력 유지)로만 바뀌며 FK는 RESTRICT다
  5. 매출 칸을 비롯한 돈 칸은 하나의 금액 모델(통화·외화 금액·환율·원화 환산액)을 쓴다: 통화를 고르면 환율 기본값이 설정의 통화별 최근 환율에서 채워지고 입력하는 사람이 고쳐 적을 수 있으며, 원화 환산액은 서버가 계산해 저장한다(KRW는 환율 1). 원화는 정수 원, 외화 금액은 소수 2자리, 환율은 소수 4자리이고 반올림은 서버의 단일 함수에서만 하며, 분할 시 합계가 원금과 같도록 마지막 회차에서 보정한다. 목록·상세·합계는 원화 환산액 기준이고 외화 건은 원래 통화·금액이 병기된다. Phase 5·6의 지출결의·증빙·법인카드 금액은 이 모델을 그대로 쓴다
  6. 경영관리가 클라이언트별 리저브 대장에 입금·출금을 날짜순으로 기록하면 잔액이 서버 계산으로 보이고, 각 줄은 프로젝트에 연결할 수 있으며 5의 금액 모델(통화·환율·원화 환산액)로 적힌다. 리저브는 정보 노출표의 새 항목이라 기획본부에게는 기본 숨김이다. 프로젝트 매출을 리저브에서 충당하는 동작은 매출 기준이 생기는 Phase 8(RSV-02)에서 붙는다
  7. 인트라넷 추출·변환 스크립트(`scripts/migrate/`의 extract·transform)가 이 페이즈에서 시작되어, 실제 인트라넷 데이터(프로젝트·견적 줄)를 새 표 구조로 변환한 결과가 개발·테스트 픽스처로 쓰인다. 적재(load)·검증·전환은 Phase 7이다

### Phase 5: 지출결의·결재·연차
**Goal**: 기획 PM이 견적 줄에서 지출결의를 한 화면에서 증빙 첨부까지 끝내 제출하면 결재자가 폰에서 승인·반려하고, 같은 결재 모듈로 연차도 승인된다
**Mode:** mvp
**Depends on**: Phase 4
**Requirements**: EXP-01, EXP-02, EXP-03, EXP-04, EXP-05, EXP-08, EXP-14, EVID-01, ADMN-04, LEAV-01, UX-03, UX-06
**Success Criteria** (what must be TRUE):
  1. 견적 줄에서 "지출결의 올리기"를 누르면 거래처·금액·프로젝트가 채워진 문서가 줄마다 하나 생성되고(여러 줄을 골라도 문서는 줄마다 — 기본 1줄 1문서), 분할 지급을 계획한 줄만 회차별 문서를 두며 회차 합계는 실행가를 넘을 수 없고, 같은 줄에서 두 번 눌러도 문서가 겹치지 않는다(idempotency key). 작성·증빙 첨부(세금계산서·영수증·카드 전표, 폰 사진 포함)·제출이 한 화면에서 끝난다. 제출 시 문서 번호(예: 26001-0001)가 부여되고 금액은 0보다 커야 하며 음수는 입력되지 않는다. 금액 칸은 Phase 4의 금액 모델(통화·외화 금액·환율·원화 환산액)이며 결재 대기함·목록에는 원화 환산액과 원래 통화가 함께 보인다
  2. 제출된 문서의 결재선(기본 4단: 팀장→본부 책임자→경영관리→대표, 빈 자리 건너뜀)은 제출 시점에 문서에 고정된다. 고정되는 것은 단계별 계급이며, 사람은 표시 시점의 현재 담당으로 해석하고 이미 승인한 사람은 그대로 보존된다. 설정 화면에서 결재 단계·담당 계급·규칙 on/off를 바꾸면 새 문서만 따르고 진행 중 문서는 바뀌지 않는다
  3. 결재자는 결재 대기함에서 폰으로 승인·반려(기안자에게 복귀)하고 기안자는 회수할 수 있다. 상태 문서는 version 컬럼 낙관적 잠금으로 승인↔회수·승인↔반려 동시 조작을 막고 두 순서 모두 테스트로 증명된다. 화면에 안내 문구가 없고, 선행 단계(고객 승인·필수 항목·증빙) 전에는 제출 버튼이 이유와 함께 비활성이며, 다음 할 일이 한 곳에 보인다
  4. 프로젝트 없이 팀 이름으로 지출(수주 실패 비용 / 팀 관리비 구분)을 올릴 수 있다
  5. 직원이 종일·반차·반반차·재택 중 하나로 연차를 신청하면 같은 결재 모듈로 승인되고 잔여 일수(1 / 0.5 / 0.25, 재택은 차감 없이 기록)가 차감된다. 연차 일수는 관리자가 연 1회 설정한다
  6. 결재 모듈은 문서 종류 3개 — 지출결의·연차·정산 결재 — 를 하드코딩 없이 다룬다. 정산 결재는 경영관리가 기안하고 대표가 승인하는 문서로 프로젝트 완료(정산) 전환을 처리하며, 대표 승인 순간의 손익 스냅샷은 Phase 8에서 붙는다

**Requirements**: EXP-06, EXP-07, EXP-09, EXP-10, EXP-11, EXP-12, EXP-13, EVID-02, EVID-03, EVID-04, ADMN-11, NOTI-01, NOTI-02, NOTI-03, NOTI-04, PROJ-06
**Success Criteria** (what must be TRUE):

  6. 프로젝트 완료(정산) 처리 시 미결 지출결의·미매칭 견적 줄·매출 미입력을 점검해 이유와 함께 막고, 강행 허용 여부는 설정이다

### Phase 8: 프로젝트 손익
**Goal**: 기획본부와 경영관리·대표가 프로젝트마다 같은 네 숫자(견적/예상 비용/확정 비용/수익)를 보고, 경영관리·대표는 근거 줄까지 내려가며, 기획본부는 결과 숫자만 보되 자기 입력과 어긋나지 않아 납득한다. 숫자는 원화 환산액 기준이고, 경영관리가 리저브에서 충당한 매출도 같은 숫자에 들어간다
**Mode:** mvp
**Depends on**: Phase 7. 착수 조건: Phase 4~6 화면에 직원의 실제 입력이 쌓이고 있다는 실사용 지표(OV-1)
**Requirements**: PNL-01, PNL-02, PNL-03, PNL-04, PNL-05, PNL-06, PNL-08, PNL-09, UX-02, RSV-02
**Success Criteria** (what must be TRUE):

  2. 매출 기준(계산서 발행액 / 계약 금액 / 입금액)과 연도 귀속 날짜(발행일 / 종료일 / 입금일)를 설정에서 고르고 화면에 현재 기준이 표시된다. 완료 전에는 상세 견적 합(없으면 사전 견적)이 분모, 완료 뒤에는 설정된 매출 기준이 분모다. 부가세율(기본 10%)은 적용 시작일이 있는 이력형 설정이다
  3. 경영관리가 프로젝트 매출을 클라이언트 리저브에서 충당하면 그 클라이언트의 리저브 대장에 프로젝트 연결 출금 줄이 남고, 그 원화 환산액이 설정된 매출 기준의 매출에 포함되어 네 숫자가 바뀐다. 잔액이 부족하면 잔액·부족액과 함께 막힌다. 완료(정산) 뒤의 충당은 스냅샷을 바꾸지 않고 차이로 표시된다(5와 같은 규칙)
  4. 경영관리·대표는 손익 숫자를 눌러 근거 줄(견적 줄·지출결의·증빙·리저브 출금)로 내려가고 계산식을 설정 화면에서 본다. 기획본부(staff)에게는 드릴다운·계산식이 화면·API·Excel 어디에도 나오지 않는다(정보 노출표 기본값). 계산은 SQL 뷰가 아니라 결과와 근거(trace)를 함께 돌려주는 서비스 함수다. 목록·Excel·팀 합계는 우선순위 CASE 집계 1회로 계산하고 상세는 trace를 만들며, '목록 합계 = 상세 합계' 테스트가 있다
  5. 완료(정산)는 정산 결재 문서(경영관리 기안 → 대표 승인, Phase 5 결재 모듈)로 처리되며 대표 승인 순간 손익 스냅샷이 찍힌다. 스냅샷은 이후 설정 변경에 소급되지 않고, 완료 뒤 계약 금액·매출이 정정되면 재계산하지 않고 차이만 표시된다

**Depends on**: Phase 9 (순서상 마지막 기능 페이즈), 기능적으로 Phase 3(권한·행동 로그)·Phase 6(지급 흐름)

**Success Criteria** (what must be TRUE):
  1. `/cso` 보안 감사가 이 페이즈의 설계(앱 단 암호화·키 관리·열람 권한·보존 기간·외부 링크·세션)에 대해 통과했고, 감사 결과가 반영되기 전에는 확인증 기능이 프로덕션에서 꺼져 있다(설정 플래그). 감사에서 나온 조정은 이 페이즈 안에서 반영한다
  2. 외부 인력이 로그인 없이 1회성 링크(만료 시간 있음)를 폰에서 열어 서명·주민등록번호·계좌를 제출하면, 링크는 다시 쓸 수 없다
  3. 주민등록번호는 앱 단에서 암호화되어 저장되고, 전체 보기는 권한자로 제한되며 열람마다 행동 로그에 남고, 보존 기간(설정) 뒤 파기된다
  4. 제출된 확인증이 해당 지출결의에 연결되고, 개인 지급(기타소득·사업소득) 건에는 원천징수 제안 금액(기본 기타소득 8.8%·사업소득 3.3%·5만원 이하 면제, 적용 시작일이 있는 이력형 설정)이 자동으로 떠서 경영관리가 확정하면 지급액에 반영된다
