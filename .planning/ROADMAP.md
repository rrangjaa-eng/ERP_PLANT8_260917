# Roadmap: PLANT8 ERP

## Overview

배포부터 시작한다. Phase 1은 기능이 아니라 "서울 리전 Cloud Run + Cloud SQL에 스크립트 한 번으로 올라가고 로그인이 된다"를 증명하고, Phase 2에서 모든 화면의 기준인 `docs/design/SYSTEM.md`를 확정한다. Phase 3에서 권한·정보 노출·설정 레지스트리·마스터를 관리자 화면으로 세워 이후 어떤 화면도 권한 없이 만들어질 수 없게 한 뒤, Phase 4~6에서 인트라넷 4기능(프로젝트·견적 줄·지출결의+결재·법인카드)을 기획 PM → 결재자 → 경영관리 순서의 세 수직 슬라이스로 대체한다. Phase 7에서 인트라넷 데이터 전부를 리허설 반복으로 이전해 전환하고, 그 실데이터 위에 Phase 8 프로젝트 손익, Phase 9 팀 손익·연간 목표·인센티브를 얹는다. 개인정보를 다루는 기타소득 확인증(Phase 10)은 `/cso` 보안 감사 통과를 조건으로 마지막에 둔다.

세 번의 실패("다 만든 뒤 옮긴다")를 피하기 위해 페이즈마다 실제 사용자가 배포된 앱에 로그인해 실제 업무 하나를 끝낼 수 있어야 한다(`**Mode:** mvp`). 다듬기·정리 페이즈는 없다.

**페이즈 수 근거:** 표준 granularity(5~8)를 넘겨 10개로 둔 이유 — 배포 스켈레톤과 디자인 시스템이 각각 독립 게이트(하드 제약 1·2)이고, 지출결의 흐름 21개 요구사항은 PM/결재자 슬라이스와 경영관리 슬라이스로 나눠야 한 페이즈가 3~5플랜에 들어가며, 데이터 이전·프로젝트 손익·팀 손익·확인증(`/cso` 게이트)은 각각 별도 검증 단위이기 때문이다.

**디자인 시스템 순서(하드 제약 2) 선택:** Phase 1 = 배포 스켈레톤(임시 로그인·내 계정 화면만, 업무 화면 없음) → Phase 2 = 디자인 시스템. Phase 1의 임시 화면은 무스타일이며 Phase 2에서 SYSTEM.md 기준으로 교체된다. 첫 업무 화면은 Phase 3부터다.

**리저브·외화 배치:** 통화·환율·원화 환산 금액 모델(FX-01)과 클라이언트별 리저브 대장(RSV-01)은 Phase 4에 둔다 — Phase 5·6이 지출결의·증빙·법인카드 금액을 넣기 전에 금액 모델이 먼저 있어야 하고, 리저브 대장은 매출 칸과 같은 자리(프로젝트·클라이언트)에 붙기 때문이다. 리저브 충당 → 매출 반영(RSV-02)은 매출 기준(PNL-03)이 생기는 Phase 8이다. 그 결과 Phase 4가 11개 요구사항으로 원장 페이즈 중 가장 크고 5플랜(상한)에 닿을 것으로 본다. 계획 단계에서 5플랜을 넘기면 리저브 대장(RSV-01)을 별도 페이즈로 뗀다(`/gsd-phase`).

## Phases

**Phase Numbering:**
- Integer phases (1, 2, 3): Planned milestone work
- Decimal phases (2.1, 2.2): Urgent insertions (marked with INSERTED)

Decimal phases appear between their surrounding integers in numeric order.

- [ ] **Phase 1: 배포 스켈레톤·로그인** - 스크립트 한 번으로 Cloud Run + Cloud SQL(서울)에 올라가고 이메일+비밀번호 로그인이 되는 앱, CI에서 린트·타입체크·통합 테스트
- [ ] **Phase 2: 디자인 시스템·앱 셸** - `docs/design/SYSTEM.md` + `tokens.css` 확정, 앱 셸(내비게이션·레이아웃)과 핵심 컴포넌트 계약, Phase 1 임시 화면 교체
- [ ] **Phase 3: 권한·설정·마스터 (관리자 운영 콘솔)** - 사람·계급·팀, 권한표·정보 노출표, 설정 레지스트리 자동 화면, 거래처·법인카드·코드표, 행동 로그·보관함
- [ ] **Phase 4: 프로젝트·견적 원장** - 프로젝트 등록·목록·상세, 엑셀식 견적 줄 표(차익 서버 계산), 차수·고객 승인, 매출 칸, 문서 번호 서식, 통화·환율·원화 환산 금액 모델, 클라이언트별 리저브 대장
- [ ] **Phase 5: 지출결의·결재·연차** - 견적 줄에서 한 화면 지출결의(증빙 첨부 포함) 제출, 4단 결재(제출 시 고정, 폰 승인), 팀 비용, 같은 결재 모듈로 연차
- [ ] **Phase 6: 지급·증빙·법인카드·마감 알림 (경영관리)** - 지급일 자동 계산·마감 14시·공휴일, 결재·증빙 게이트로 지급 완료, 법인카드·구매 요청·이중 계산 차단, 알림함+이메일
- [ ] **Phase 7: 데이터 이전·전환** - 인트라넷 전 데이터를 새 구조로 변환·검증(멱등), 리허설 반복 뒤 전환, 백업·복원 리허설
- [ ] **Phase 8: 프로젝트 손익** - 네 숫자(견적/예상/확정/수익), 비용 우선순위(증빙>승인액>실행가), 매출 기준·연도 귀속 설정, 리저브 충당 → 매출 반영, 드릴다운·계산식(경영관리·대표만), 완료 스냅샷, 역할별 첫 화면
- [ ] **Phase 9: 팀 손익·연간 목표·인센티브·화면 항목 추가** - 팀 손익(프로젝트 합 − 수주 실패 비용 − 관리비), 연간 목표 진행률, 인센티브 계산(대표·경영관리만), 커스텀 필드 관리 화면
- [ ] **Phase 10: 기타소득 확인증** - 외부 인력 1회성 링크 제출(서명·주민등록번호·계좌), 암호화·열람 기록·파기, 지출결의 연결, 원천징수 제안 — `/cso` 통과가 활성화 조건

## Phase Details

### Phase 1: 배포 스켈레톤·로그인
**Goal**: 관리자(사용자 본인)가 배포 스크립트 한 번으로 띄운 서울 리전 Cloud Run 앱에 직원 계정으로 로그인해 비밀번호를 바꾸고 로그아웃한다 — 기능보다 "배포된다"를 먼저 증명한다
**Mode:** mvp
**Depends on**: Nothing (first phase)
**Requirements**: AUTH-01, AUTH-02, AUTH-03, AUTH-04, OPS-01, OPS-02, OPS-04
**Success Criteria** (what must be TRUE):
  1. `scripts/deploy.sh` 한 번으로 빈 GCP 프로젝트에 Cloud Run(서울) + Cloud SQL(서울, 최소 사양) + Secret Manager가 만들어지고 앱이 뜬다. 프로젝트 ID·리전·DB 접속은 환경 변수뿐이며 코드·커밋에 시크릿이 없다. 같은 스크립트로 개인 GCP → 회사 GCP 이식이 재현된다
  2. 관리자가 시드/CLI 명령으로 직원 계정과 초기 비밀번호를 발급하면, 직원이 배포된 URL에서 이메일+비밀번호로 로그인하고, 브라우저를 닫았다 열어도 세션이 유지되며, 어느 화면에서든 로그아웃할 수 있다
  3. 직원이 자기 비밀번호를 바꾸고 관리자가 재발급할 수 있다. 로그인 방식은 환경 변수 하나(예: `AUTH_PROVIDER=email`)로 선택되고 Google 로그인은 어댑터 자리만 있어 코드 구조 변경 없이 켤 수 있다
  4. CI가 린트(`any` 금지)·타입체크·실 DB 통합 테스트(로그인 흐름)를 돌리고 실패하면 배포가 막힌다. 이 통합 테스트는 이후 페이즈가 지출결의→결재→손익 단계를 덧붙여 가는 뼈대다
  5. 월 운영 비용 목표(Cloud Run 스케일-투-제로 + Cloud SQL 최소 사양, 유휴 시에도 DB는 과금)와 실제 과금 항목이 `docs/OPERATIONS.md`에 적혀 있다

### Phase 2: 디자인 시스템·앱 셸
**Goal**: 직원이 폰과 PC에서 `docs/design/SYSTEM.md` 기준으로 만들어진 앱 셸(로그인·내 계정·내비게이션)을 쓰고, 이후 모든 화면은 이 토큰·컴포넌트만 쓴다
**Mode:** mvp
**Depends on**: Phase 1
**Requirements**: UX-01
**Success Criteria** (what must be TRUE):
  1. `docs/design/SYSTEM.md`와 `docs/design/tokens.css`가 존재하고, `docs/DESIGN.md` §1 브리프(`docs/design/BRIEF.md`) → §2 발산(후보 방향 비교, `docs/design/EXPLORE.md`) → §3 수렴 절차의 산출물이며 `/plan-design-review`를 통과했다. 260907의 화면·정보구조·UI 흐름은 참고하지 않았다
  2. 배포된 앱의 로그인·내 계정·앱 셸(내비게이션·레이아웃·빈 상태)이 SYSTEM.md 컴포넌트와 tokens.css 토큰만 쓴다. 새 색·서체·radius가 없고 Phase 1의 임시 화면은 남아 있지 않다
  3. 폰(375px)과 PC에서 같은 셸이 깨지지 않고, 키보드만으로 로그인·내비게이션·비밀번호 변경이 된다
  4. 이후 페이즈가 그대로 가져다 쓰는 핵심 컴포넌트 계약이 SYSTEM.md에 있다: 서버 검증 오류를 보여주는 폼, 엑셀식 표 입력(grid), 선행 단계 전 비활성 + 이유를 보이는 행동 유도 버튼, 알림함·배지, 폰용 목록·시트

### Phase 3: 권한·설정·마스터 (관리자 운영 콘솔)
**Goal**: 관리자가 코드 수정 없이 사람·계급·팀·권한표·정보 노출표·설정·코드표·거래처·법인카드를 화면에서 등록하고, 이후 모든 화면·API가 이 권한·설정 위에 얹힌다
**Mode:** mvp
**Depends on**: Phase 2
**Requirements**: ADMN-01, ADMN-02, ADMN-03, ADMN-05, ADMN-06, ADMN-08, ADMN-10, ADMN-12, OPS-05, MAST-01, MAST-02, MAST-03, MAST-04
**Success Criteria** (what must be TRUE):
  1. 관리자가 사람 등록 + 계급 + 팀 선택으로 입사자를 추가하고 계정·초기 비밀번호를 같은 화면에서 발급한다. 계급 종류(기본 5: 대표·본부 책임자·팀장·기획 PM·시스템 관리자)는 추가·이름 변경이 되는 데이터다
  2. 권한표(계급 × 메뉴 × 동작)와 정보 노출표(계급 × 정보 항목) 체크박스를 바꾸면 즉시 메뉴·동작·응답 필드가 바뀐다. 판정은 `can()` / `visible()`(응답 직렬화 한 곳) / `scopeFor()`(repository WHERE) 세 함수에서만 이루어져 화면·API·자동완성·검색·Excel이 같은 결과를 내고(우회 경로 없음, 테스트로 증명), 기획본부(staff) 기본값은 인트라넷 수준이며 새 기능 정보는 기본 숨김이다
  3. 설정 키는 코드의 typed registry 한 곳에 등록되고 설정 화면이 자동 생성된다. 등록됐지만 서버가 읽지 않는 키가 있으면 테스트가 실패한다. 설정을 JSON으로 내보내 빈 환경에 가져오면 같은 동작을 한다
  4. 거래처·클라이언트(미사용은 삭제 대신 숨김, 입력 시 자동완성), 법인카드(개인/팀, 소지자 또는 소속 팀), 코드표(견적 대·소분류, 지급 방식, 프로젝트 상태 등)를 관리 화면에서 등록·수정·비활성화한다
  5. 로그인·설정 변경·권한 변경·삭제·복원 같은 핵심 행동만 행동 로그에 남고(단순 조회·화면 이동은 안 남음), 대표·경영관리·관리자가 사람·기간·행동 종류·문서로 걸러 Excel로 내보내며 관리자가 정리할 수 있다. 무엇을 "삭제"해도 보관함으로 가고 관리자만 보고 복원한다

### Phase 4: 프로젝트·견적 원장
**Goal**: 기획 PM이 프로젝트를 등록하고 엑셀처럼 견적 줄을 입력하면 차익이 서버에서 계산되며, 사전→상세 차수와 고객 승인, 매출 칸, 진행→완료 상태까지 프로젝트의 돈 뼈대가 선다. 모든 돈 칸은 통화·환율·원화 환산액을 갖는 하나의 금액 모델을 쓰고, 경영관리는 클라이언트별 리저브 대장을 기록한다
**Mode:** mvp
**Depends on**: Phase 3
**Requirements**: PROJ-01, PROJ-02, PROJ-03, PROJ-04, PROJ-05, PROJ-07, ADMN-09, UX-04, UX-05, RSV-01, FX-01
**Success Criteria** (what must be TRUE):
  1. PM이 프로젝트(클라이언트·담당 PM·팀·기간·상태)를 등록·목록·상세로 다루고, 번호는 설정된 서식(접두어·연도·자릿수·구분자·순번 범위, 예: 26001)으로 자동 부여된다. 클라이언트·거래처는 자동완성되고, 이전 프로젝트·견적 줄 복사와 기본값 채움으로 반복 입력이 없다

  6. 경영관리가 클라이언트별 리저브 대장에 입금·출금을 날짜순으로 기록하면 잔액이 서버 계산으로 보이고, 각 줄은 프로젝트에 연결할 수 있으며 5의 금액 모델(통화·환율·원화 환산액)로 적힌다. 리저브는 정보 노출표의 새 항목이라 기획본부에게는 기본 숨김이다. 프로젝트 매출을 리저브에서 충당하는 동작은 매출 기준이 생기는 Phase 8(RSV-02)에서 붙는다

### Phase 6: 지급·증빙·법인카드·마감 알림 (경영관리)
**Goal**: 경영관리가 결재 통과 건의 지급일을 자동 계산으로 받고 증빙을 확인해 지급 완료하며, 법인카드·구매 요청·팀 비용까지 모든 나가는 돈이 견적 줄에 한 번만 연결되고, 마감 알림이 앱과 이메일로 온다
**Mode:** mvp
**Depends on**: Phase 5
**Requirements**: EXP-06, EXP-07, EXP-09, EXP-10, EXP-11, EXP-12, EXP-13, EVID-02, EVID-03, EVID-04, ADMN-11, NOTI-01, NOTI-02, NOTI-03, NOTI-04, PROJ-06
**Success Criteria** (what must be TRUE):
  1. 지급 예정일을 비워 두면 거래처별 지급 기한(기본 작성일+60일, 거래처별 조정)과 "기한 전 마지막 금요일" 규칙으로 자동 계산되어 보이고, 결재 마감(지급일 전 영업일 14시, 설정)이 지나면 그 주 지급 대상에서 빠진다. 공휴일 표는 법정 공휴일 규칙으로 매년 후보가 생성되고 관리자가 검토·확정·수동 추가하며, 공휴일이 끼면 지급일·마감·알림이 같은 표를 써서 함께 앞당겨진다
  2. 결재를 통과하지 않은 건은 지급 완료 처리가 되지 않고, 증빙 필수 규칙(설정 on/off)이 켜져 있으면 증빙 없는 건도 되지 않는다. 증빙 금액을 적으면(통화·환율·원화 환산액 포함) 그 줄의 확정 비용(원화 환산액)이 되고, 증빙을 떼면 예상(승인액 또는 견적 실행가)으로 돌아간다. 선결제 건은 표시·사유가 필수이고 14일(설정) 안에 증빙이 없으면 독촉 알림이 가되 처리는 막지 않는다
  3. 직원이 자기 카드·자기 팀 카드 사용을 등록하면 견적 줄(또는 팀 비용)에 연결해야만 저장되고, 사용액은 같은 금액 모델(통화·환율·원화 환산액)로 적힌다. 견적 줄의 협력사가 설정된 '온라인구매' 협력사면 구매 요청만, 그 외면 지출결의만 열리고(사람이 고르지 않음), 경영관리가 구매 완료하면 카드 사용 건으로 연결된다(신청/구매 완료/취소, 결재 없음). 한 견적 줄이 지출결의와 카드 사용에 이중으로 잡히지 않는다
  4. 앱 안 알림함과 미읽음 배지가 있고 같은 알림이 이메일로도 간다. 기본 규칙 4개(종료 후 지출결의 없음·지급 예정일 임박·결재 대기 초과·증빙 미첨부)가 시드로 있고, 관리자가 대상 문서·조건(상태 + 기준일 N일 전/후)·받는 사람·채널로 새 규칙을 만든다. Cloud Scheduler가 하루 몇 번 부르는 단일 엔드포인트로 동작하고 같은 건은 두 번 발송되지 않는다
  5. 프로젝트 완료(정산) 처리 시 미결 지출결의·미매칭 견적 줄·매출 미입력을 점검해 이유와 함께 막고, 강행 허용 여부는 설정이다

### Phase 8: 프로젝트 손익
**Goal**: 기획본부와 경영관리·대표가 프로젝트마다 같은 네 숫자(견적/예상 비용/확정 비용/수익)를 보고, 경영관리·대표는 근거 줄까지 내려가며, 기획본부는 결과 숫자만 보되 자기 입력과 어긋나지 않아 납득한다. 숫자는 원화 환산액 기준이고, 경영관리가 리저브에서 충당한 매출도 같은 숫자에 들어간다
**Mode:** mvp
**Depends on**: Phase 7
**Requirements**: PNL-01, PNL-02, PNL-03, PNL-04, PNL-05, PNL-06, PNL-08, PNL-09, UX-02, RSV-02
**Success Criteria** (what must be TRUE):
  1. 프로젝트 상세 상단에 견적 / 예상 비용 / 확정 비용 / 수익금액·수익률이 보이고, 줄마다 증빙액 > 지출결의 승인액 > 견적 실행가 순으로 가장 굳은 값 하나만 비용으로 든다(진행 중에는 예상값). PM이 견적·지출을 입력하면 즉시 반영되고 같은 용어·같은 단위(공급가액, 화면에 명시)로 표시된다. 네 숫자는 원화 환산액 기준이며 외화 건은 원래 통화·금액이 병기된다
  2. 매출 기준(계산서 발행액 / 계약 금액 / 입금액)과 연도 귀속 날짜(발행일 / 종료일 / 입금일)를 설정에서 고르고 화면에 현재 기준이 표시된다. 완료 전에는 상세 견적 합(없으면 사전 견적)이 분모, 완료 뒤에는 설정된 매출 기준이 분모다. 부가세율(기본 10%)은 적용 시작일이 있는 이력형 설정이다
  3. 경영관리가 프로젝트 매출을 클라이언트 리저브에서 충당하면 그 클라이언트의 리저브 대장에 프로젝트 연결 출금 줄이 남고, 그 원화 환산액이 설정된 매출 기준의 매출에 포함되어 네 숫자가 바뀐다. 잔액이 부족하면 잔액·부족액과 함께 막힌다. 완료(정산) 뒤의 충당은 스냅샷을 바꾸지 않고 차이로 표시된다(5와 같은 규칙)
  4. 경영관리·대표는 손익 숫자를 눌러 근거 줄(견적 줄·지출결의·증빙·리저브 출금)로 내려가고 계산식을 설정 화면에서 본다. 기획본부(staff)에게는 드릴다운·계산식이 화면·API·Excel 어디에도 나오지 않는다(정보 노출표 기본값). 계산은 SQL 뷰가 아니라 결과와 근거(trace)를 함께 돌려주는 서비스 함수다
  5. 완료(정산) 처리된 프로젝트의 손익은 스냅샷으로 고정되어 이후 설정 변경에 소급되지 않고, 완료 뒤 계약 금액·매출이 정정되면 재계산하지 않고 차이만 표시된다
  6. 역할별 첫 화면이 있다: PM(내 프로젝트·내 지출결의), 경영관리(나갈 돈·결재·미증빙), 대표·팀장(손익). 프로젝트 손익 목록을 Excel로 내보내면 정보 노출표가 그대로 적용되고 원화 환산액 옆에 원래 통화·금액 열이 함께 나간다. CI 핵심 흐름 통합 테스트가 로그인 → 지출결의 → 결재 → 손익까지 통과한다

### Phase 9: 팀 손익·연간 목표·인센티브·화면 항목 추가
**Goal**: 팀장이 자기 팀의 손익(프로젝트 합 − 수주 실패 비용 − 관리비)과 연간 목표 진행률을 보고, 대표·경영관리가 인센티브 계산을 확인하며, 관리자가 코드 없이 화면 입력 칸을 추가한다
**Mode:** mvp
**Depends on**: Phase 8
**Requirements**: PNL-07, GOAL-01, GOAL-02, GOAL-03, ADMN-07
**Success Criteria** (what must be TRUE):
  1. 팀 손익 = 팀 프로젝트 손익 합 − 수주 실패 비용 − 팀 직접 관리비(공통비 배부·인건비 없음)로 계산되어 팀장은 자기 팀만, 대표·경영관리는 전체를 본다. 팀 손익 목록도 Excel로 내보내며 정보 노출표가 적용되고 원화 환산액 기준에 원래 통화가 병기된다
  2. 팀별 연간 목표(매출·이익)를 표에서 입력하면 달성률·진행률이 원화 환산액 기준으로 보이고 팀장까지 열람한다. 어느 프로젝트가 어느 해 성과인지는 손익과 같은 연도 귀속 설정을 쓰며 화면에 기준이 표시된다
  3. 인센티브 계산 규칙은 설정에 있고 달성 시 금액이 계산되며 대표·경영관리만 본다. 기획본부·팀장에게는 화면·API·Excel 어디에도 없다
  4. 관리자가 프로젝트·견적 줄·거래처에 텍스트/숫자/날짜/선택 4종 칸을 추가하면 입력·목록·검색·Excel 내보내기에 즉시 반영되고 서버가 칸마다 타입을 검증한다

### Phase 10: 기타소득 확인증
**Goal**: 경영관리가 외부 인력에게 1회성 링크를 보내면 그 사람이 폰에서 서명·주민등록번호·계좌를 제출하고, 확인증이 지출결의에 연결되며 원천징수가 자동 제안된다 — `/cso` 보안 감사 통과가 활성화 조건
**Mode:** mvp
**Depends on**: Phase 9 (순서상 마지막 기능 페이즈), 기능적으로 Phase 3(권한·행동 로그)·Phase 6(지급 흐름)
**Requirements**: CERT-01, CERT-02, CERT-03, CERT-04
**Success Criteria** (what must be TRUE):
  1. `/cso` 보안 감사가 이 페이즈의 설계(앱 단 암호화·키 관리·열람 권한·보존 기간·외부 링크·세션)에 대해 통과했고, 감사 결과가 반영되기 전에는 확인증 기능이 프로덕션에서 꺼져 있다(설정 플래그). 감사에서 나온 조정은 이 페이즈 안에서 반영한다
  2. 외부 인력이 로그인 없이 1회성 링크(만료 시간 있음)를 폰에서 열어 서명·주민등록번호·계좌를 제출하면, 링크는 다시 쓸 수 없다
  3. 주민등록번호는 앱 단에서 암호화되어 저장되고, 전체 보기는 권한자로 제한되며 열람마다 행동 로그에 남고, 보존 기간(설정) 뒤 파기된다
  4. 제출된 확인증이 해당 지출결의에 연결되고, 개인 지급(기타소득·사업소득) 건에는 원천징수 제안 금액(기본 기타소득 8.8%·사업소득 3.3%·5만원 이하 면제, 적용 시작일이 있는 이력형 설정)이 자동으로 떠서 경영관리가 확정하면 지급액에 반영된다
