# Roadmap: PLANT8 ERP

## Overview

배포부터 시작한다. Phase 1은 기능이 아니라 "회사 GCP 프로젝트의 서울 리전 Cloud Run + Cloud SQL에 스크립트 한 번으로 올라가고 로그인이 된다"를 증명하고, Phase 2에서 모든 화면의 기준인 `docs/design/SYSTEM.md`를 확정한다. Phase 3에서 권한·정보 노출·설정 레지스트리·마스터를 관리자 화면으로 세워 이후 어떤 화면도 권한 없이 만들어질 수 없게 한 뒤, Phase 4~7에서 인트라넷 4기능(프로젝트·견적 줄·지출결의+결재·법인카드)을 기획 PM(4·5) → 결재자(5) → 경영관리 지급(6) → 마감·알림(7) 순서의 네 수직 슬라이스로 대체한다. Phase 8에서 데이터 이전 없이 전환한다 — 관리자가 마스터를 관리 화면에서 손으로 넣고 계정을 발급한 뒤, 시스템이 완성되는 대로 연중에 전환일을 잡아 그날부터 새 시스템만 입력하고 인트라넷은 과거 조회 전용이 된다(2026-09-23 사용자 결정). 전환 뒤 쌓인 실입력 위에 Phase 9 프로젝트 손익, Phase 10 팀 손익·연간 목표·인센티브를 얹는다. 개인정보를 다루는 기타소득 확인증(Phase 11)은 `/cso` 보안 감사 통과를 조건으로 마지막에 둔다.

세 번의 실패("다 만든 뒤 옮긴다")를 피하기 위해 페이즈마다 실제 사용자가 배포된 앱에 로그인해 실제 업무 하나를 끝낼 수 있어야 한다(`**Mode:** mvp`). 다듬기·정리 페이즈는 없다.

**페이즈 수 근거:** 표준 granularity를 넘겨 11개로 둔 이유 — 배포 스켈레톤과 디자인 시스템이 각각 독립 게이트(하드 제약 1·2)이고, 지출결의·증빙·법인카드 흐름 21개 요구사항(EXP 16·EVID 4·PROJ-06)은 PM/결재자 슬라이스(Phase 5)와 경영관리 지급 슬라이스(Phase 6)로, 공휴일·지급일·마감·알림(EXP-11/12·ADMN-11·NOTI 4개)은 별도 슬라이스(Phase 7)로 나눠야 한 페이즈가 3~5플랜에 들어가며(엔지니어링 리뷰 OV-6: 옛 Phase 6의 17개 요구사항을 10 + 7로 분할), 전환·프로젝트 손익·팀 손익·확인증(`/cso` 게이트)은 각각 별도 검증 단위이기 때문이다.

**디자인 시스템 순서(하드 제약 2) 선택:** Phase 1 = 배포 스켈레톤(임시 로그인·내 계정 화면만, 업무 화면 없음) → Phase 2 = 디자인 시스템. Phase 1의 임시 화면은 무스타일이며 Phase 2에서 SYSTEM.md 기준으로 교체된다. 첫 업무 화면은 Phase 3부터다.

**리저브·외화 배치:** 통화·환율·원화 환산 금액 모델(FX-01)과 클라이언트별 리저브 대장(RSV-01)은 Phase 4에 둔다 — Phase 5·6이 지출결의·증빙·법인카드 금액을 넣기 전에 금액 모델이 먼저 있어야 하고, 리저브 대장은 매출 칸과 같은 자리(프로젝트·클라이언트)에 붙기 때문이다. 리저브 충당 → 매출 반영(RSV-02)은 매출 기준(PNL-03)이 생기는 Phase 9다. 그 결과 Phase 4가 11개 요구사항으로 원장 페이즈 중 가장 크고 5플랜(상한)에 닿을 것으로 본다. 계획 단계에서 5플랜을 넘기면 리저브 대장(RSV-01)을 별도 페이즈로 뗀다(`/gsd-phase`).

**CEO 리뷰 반영(260917, HOLD SCOPE):** `docs/designs/plant8-erp-roadmap-ceo-review-260917.md`의 결정 23건(1A~23A), 시점 결정 D3(완료=정산 결재 문서)·D4(원화 정수·서버 단일 반올림)·D5(이메일=회사 Google SMTP), OUTSIDE VOICE OV-1~8이 각 페이즈의 성공 기준에 접혀 있다. 새 기능은 없고 OPS-06(관리자 시스템 상태 화면)·OPS-07(`docs/ARCHITECTURE.md`·`docs/OPERATIONS.md`)만 Phase 1에 더해졌다(87개). 구조 변화 세 가지 — Phase 3은 메커니즘+마스터로 좁히고 전 메뉴 검수는 패리티 마지막 페이즈 끝으로(CEO OV-5; 분할 뒤 Phase 7 끝), ~~인트라넷 추출·변환 스크립트는 Phase 4부터 시작해 이전 페이즈(Phase 8)는 적재·검증·델타 이전+전환만(CEO OV-1)~~(2026-09-23 대체: 데이터 이전 없음 — 추출·변환과 04-03은 철회, Phase 8은 수기 입력 전환), 이전 착수 게이트(회사 GCP deploy.sh 1회 성공, CEO OV-6)와 손익 착수 조건(Phase 4~6 실사용 지표)은 엔지니어링 리뷰(Eng OV-3·OV-1, 아래)로 대체됐다. 리뷰 뒤 사용자가 OV-3을 재정의했다 — 사람은 공급가액만 적고, 증빙 종류(코드표)별 세금 규칙으로 부가세·원천징수액·지급 총액을 서버가 계산하며, 통장에 실제 오간 돈 칸(입금액·지급 완료액)만 합계로 적고 공급가로 역산한다(EXP-15 → Phase 5, 코드표·설정 키는 Phase 3, 매출 칸은 Phase 4, 지급·증빙은 Phase 6). CERT-01은 수령자가 QR(1회성 링크)로 들어와 본인 정보를 직접 입력하고 터치 서명하는 방식이 됐다. 비용이 새는 곳 셋도 규칙으로 막았다 — 경품 등 회사 대납 세금은 그 줄의 프로젝트 비용(EXP-15 4번째 규칙·PNL-02), 자동 결제·정기 결제는 경영관리가 법인카드 사용을 대리 등록(EXP-16 → Phase 6, '견적 외 비용' 줄은 Phase 4 원장), 프로젝트 미연결 직원 개인 비용은 사용일 시점 소속 팀 비용(EXP-08·MAST-02·PNL-07). v1은 89개다(2026-09-23 데이터 이전 제외로 86개 — MIG-01~03 Out of Scope).

**엔지니어링 리뷰 반영(260917):** `docs/designs/plant8-erp-roadmap-eng-review-260917.md`의 결정 15건(Issue 1~15, 전부 A안)과 OUTSIDE VOICE OV-1~8이 각 페이즈 성공 기준에 접혀 있다. 앱 구조는 Next.js 단일 앱 + Drizzle 4계층 `app/ → domain/ → repositories/(viewer 필수) → db/`이고 `research/ARCHITECTURE.md`의 Hono·REST·raw pg는 참고용이다(Issue 1; `docs/ARCHITECTURE.md`가 이 구조를 기록). 단일 지점 셋 — 금액 산술은 `domain/money`(Phase 4), 게이트 판정은 `domain/rules.gate`(Phase 4), 읽기는 `scopeFor(viewer)` 행 필터 + `project(viewer, dto)` DTO 출구(Phase 3) — 를 세우고 이후 페이즈는 참조만 한다(Issue 3·8·9). 테스트는 3계층이다(Issue 14): 단위(Vitest, `domain/*`), 통합(Vitest + GitHub Actions Postgres 서비스 컨테이너: repositories·액션·동시성·누수 생성·설정 읽힘·tick 멱등성), E2E(Playwright, 역할 4종 핵심 흐름 + 계급별 노출 스모크). 페이즈 완료 조건은 새 도메인 모듈 = 단위 테스트, 새 액션·DTO = 통합 테스트 + 누수 생성, 새 화면 흐름 = E2E 1개다. 구조 변화 셋 — (1) Phase 6을 둘로 나눴다(Eng OV-6): Phase 6 = 지급·증빙·법인카드·구매 요청·미결 점검(10개), Phase 7 = 공휴일·지급일·마감·알림·SMTP·tick + 전 메뉴 권한 검수(7개). 옛 Phase 7~10은 8~11로 밀렸다. (2) Phase 1부터 회사 GCP 프로젝트에 배포한다(Eng OV-3; 회사 GCP 확보 2026-09 넷째 주). 개인 GCP 단계는 없고 개인 환경은 로컬 개발만이라 CEO OV-6의 이전 착수 게이트는 Phase 1에서 충족되며 D5의 "개인 Gmail SMTP" 단계도 사라진다. (3) 전환 전 새 시스템 입력은 source='demo'뿐이고 실제 업무 입력은 없다(Eng OV-1; CEO OV-1의 "Phase 4~6 실사용 지표"를 교체). Phase 9(프로젝트 손익) 착수 조건은 전환 후 N주(설정, 기본 2주) 실입력이다. OV-4(쓰기 시점 파생 컬럼)는 기각하고 읽기 시점 계산을 유지하되 effectiveCost SQL 식 하나를 목록·합계·상세가 공유한다(Phase 9). OV-8(FX-01 v2 이관)은 사용자 요구로 유지한다.

## Phase Details

### Phase 1: 배포 스켈레톤·로그인

**Goal**: 관리자(사용자 본인)가 배포 스크립트 한 번으로 회사 GCP 프로젝트에 띄운 서울 리전 Cloud Run 앱에 직원 계정으로 로그인해 비밀번호를 바꾸고 로그아웃한다 — 기능보다 "배포된다"를 먼저 증명한다. 4계층 앱 구조·배포 파이프라인·롤백·경보·3계층 테스트 골격·운영 문서·시스템 상태 화면 뼈대가 이 페이즈의 산출물이며 이후 페이즈는 여기에 항목만 더한다
**Mode:** mvp
**Depends on**: Nothing (first phase). 착수 조건: 회사 GCP 프로젝트 확보(2026-09 넷째 주 예정, Eng OV-3) — 확보 전에는 로컬 개발만

### Phase 4: 프로젝트·견적 원장

**Goal**: 기획 PM이 프로젝트를 등록하고 엑셀처럼 견적 줄을 입력하면 차익이 서버에서 계산되며, 사전→상세 차수와 고객 승인, 매출 칸, 수주중→진행→완료(정산) + 미수주 상태 전환까지 프로젝트의 돈 뼈대가 선다. 모든 돈 칸은 `domain/money` 하나의 금액 모델(통화·환율·원화 환산액)을 쓰고 게이트 판정은 `domain/rules.gate` 하나를 지나며, 경영관리는 클라이언트별 리저브 대장을 기록한다
**Mode:** mvp
**Depends on**: Phase 3
**Requirements**: PROJ-01, PROJ-02, PROJ-03, PROJ-04, PROJ-05, PROJ-07, ADMN-09, UX-04, UX-05, RSV-01, FX-01
**Success Criteria** (what must be TRUE):

  1. PM이 프로젝트(클라이언트·담당 PM·팀·기간·상태)를 등록·목록·상세로 다루고, 번호는 설정된 서식(접두어·연도·자릿수·구분자·순번 범위, 예: 26001)으로 자동 부여된다. 번호 부여는 `document_counters(format_key, scope_key, next_no)` 행을 같은 트랜잭션에서 `UPDATE … RETURNING`으로 잠그고 증가시키며, 문서 표의 `UNIQUE(format_key, number)`가 중복을 막고, 실패한 트랜잭션의 결번은 허용된다. 동시 제출(트랜잭션 2개) 통합 테스트가 있다(Issue 10; Phase 5의 지출결의 번호도 같은 카운터). 클라이언트·거래처는 자동완성되고, 이전 프로젝트·견적 줄 복사와 기본값 채움으로 반복 입력이 없다. 목록 합계(견적·실행가·차익)는 집계 쿼리 1회로 계산되고(Phase 9의 effectiveCost 식이 같은 자리에 얹힌다), 목록·검색이 쓰는 인덱스 목록이 `docs/ARCHITECTURE.md`에 있으며, 요청 본문은 1MB 한도, 목록 응답은 p99 500ms 이내다
  2. 견적 줄 표에서 Tab/Enter·방향키 이동, 여러 칸 복사·붙여넣기, Esc 취소, 저장·새 줄 단축키로 키보드만으로 입력이 끝나고, 견적가·실행가를 넣으면 차익은 서버가 계산해 저장한다. 견적가 0인 '견적 외 비용' 줄은 견적 줄 원장의 한 종류로, 견적에 없던 비용(Phase 6의 경영관리 대리 등록 등)을 프로젝트에 붙이는 자리다. 브라우저 계산값은 저장되지 않아 인트라넷의 차익 불일치(66줄) 같은 오류가 구조적으로 불가능하다. 잘못된 입력은 서버 검증으로 즉시 안내되고, 저장 실패·중복 저장·입력값 유실이 없으며, 승인·삭제·상태 변경은 GET으로 되지 않는다

  2. 증빙 업로드는 브라우저가 이미지를 축소(최대 변 2000px JPEG)하고 SHA-256을 계산해 보내면 서버가 크기 한도(기본 10MB, 설정)·형식(이미지·PDF)·중복(SHA-256)을 검사한 뒤 GCS 서명 PUT URL(크기 상한 조건)을 내주고, 브라우저가 GCS에 직접 올린 뒤 완료를 통보하면 서버가 GCS 메타데이터를 재확인하고서야 files 행을 만든다. 서버 이미지 라이브러리는 없고 PDF는 원본이다(Issue 15). 완료 통보가 없는 고아 객체의 청소 절차는 `docs/OPERATIONS.md`에 적는다(F8). 증빙 금액은 공급가액으로 적으며(금액 모델) 그 줄의 확정 비용(원화 환산액)이 되고, 증빙의 부가세·원천징수는 종류별 규칙(`applyTaxRule()`)으로 다시 계산되어 지급 총액에만 반영된다. 증빙을 떼면 예상(승인액 또는 견적 실행가)으로 돌아간다. 선결제 건은 표시·사유가 필수이고 처리는 막지 않으며, 14일(설정) 안에 증빙이 없을 때의 독촉 알림은 Phase 7의 알림 규칙으로 붙는다
  3. 직원이 자기 카드·자기 팀 카드 사용을 등록하면 견적 줄 / 프로젝트 '견적 외 비용' / 팀 비용 중 하나에 연결해야만 저장되고(팀 비용은 소속 팀 자동), 사용액은 같은 금액 모델(통화·환율·원화 환산액)로 적힌다. 카드 사용 등록 때도 거래처 기본 증빙 종류가 채워지고 종류별 세금 규칙(`applyTaxRule()`)이 같이 적용된다. 견적 줄의 협력사가 설정된 '온라인구매' 협력사면 구매 요청만, 그 외면 지출결의만 열리고(사람이 고르지 않음), 경영관리가 구매 완료하면 카드 사용 건으로 연결된다(신청/구매 완료/취소, 결재 없음; 번호는 생성 시 카운터 부여). 한 견적 줄이 지출결의와 카드 사용에 이중으로 잡히지 않는다. 경영관리는 자동 결제·정기 결제처럼 PM이 모르는 법인카드 사용을 대신 등록해 프로젝트(견적 줄 또는 견적가 0인 '견적 외 비용' 줄)나 카드 소지자의 팀 비용에 연결하며, 연결되면 PM의 프로젝트 비용에 '경영관리 등록' 표시로 보인다(결재 없음). 담당 PM에게 가는 알림은 Phase 7 알림함에서 붙는다
  4. 프로젝트 완료(정산) 처리 시 미결 지출결의·미매칭 견적 줄·매출 미입력을 `domain/rules.gate`로 점검해 이유와 함께 막고, 강행 허용 여부는 설정이다. 정산 결재 문서(Phase 5)의 기안 전에 이 점검이 돈다
  5. 경영관리 흐름(결재 통과 건 → 증빙 확인 → 지급 완료; 이미지·PDF 두 업로드 경로)이 Playwright E2E로 CI에 있고, 지급 게이트·이중 연결 차단·업로드 의도만 있고 완료 없는 경우가 통합 테스트로 덮인다(Issue 14·F8). 새 액션·DTO(지급·카드·구매 요청·증빙)는 누수 스캔 생성기에 등록되어 계급별 검사가 따라온다

### Phase 9: 프로젝트 손익

**Goal**: 기획본부와 경영관리·대표가 프로젝트마다 같은 네 숫자(견적/예상 비용/확정 비용/수익)를 보고, 경영관리·대표는 근거 줄까지 내려가며, 기획본부는 결과 숫자만 보되 자기 입력과 어긋나지 않아 납득한다. 숫자는 원화 환산액 기준이고, 경영관리가 리저브에서 충당한 매출도 같은 숫자에 들어간다
**Mode:** mvp
**Depends on**: Phase 8. 착수 조건: 전환 후 N주(설정, 기본 2주) 동안 직원의 실제 입력(source가 'demo'가 아닌 행)이 쌓였다(Eng OV-1)
**Requirements**: PNL-01, PNL-02, PNL-03, PNL-04, PNL-05, PNL-06, PNL-08, PNL-09, UX-02, RSV-02
**Success Criteria** (what must be TRUE):

  1. 프로젝트 상세 상단에 견적 / 예상 비용 / 확정 비용 / 수익금액·수익률이 보이고, 줄마다 증빙액 > 지출결의 승인액 > 견적 실행가 순으로 가장 굳은 값 하나만 비용으로 든다(진행 중에는 예상값). 프로젝트 비용 = 줄별 공급가액 + 회사 대납 세금(EXP-15, `domain/money.applyTaxRule()` 결과) + 견적 외 비용 줄(EXP-16)이다. PM이 견적·지출을 입력하면 즉시 반영되고 같은 용어·같은 단위(공급가액, 화면에 명시; 예외는 통장 실제 금액 칸(입금액·지급 완료액)뿐이며 합계로 적고 공급가액으로 역산)로 표시된다. 네 숫자는 원화 환산액 기준이며 외화 건은 원래 통화·금액이 병기된다. 계산할 수 없는 줄(예: 환율 없음, 매출 기준 미입력)은 숫자와 별도의 '계산 불가(이유)' 상태로 반환·표시되어 합계에 들어가지 않고 건수 배지로 보이며, 그 건수는 관리자 시스템 상태 화면에도 더해진다
  2. 매출 기준(계산서 발행액 / 계약 금액 / 입금액)과 연도 귀속 날짜(발행일 / 종료일 / 입금일)를 설정에서 고르고 화면에 현재 기준이 표시된다. 완료 전에는 상세 견적 합(없으면 사전 견적)이 분모, 완료 뒤에는 설정된 매출 기준이 분모다. 부가세율(기본 10%)·원천징수율·면제 기준은 적용 시작일이 있는 이력형 설정이다(Phase 3 레지스트리)
  3. 경영관리가 프로젝트 매출을 클라이언트 리저브에서 충당하면 그 클라이언트의 리저브 대장에 프로젝트 연결 출금 줄이 남고, 그 원화 환산액이 설정된 매출 기준의 매출에 포함되어 네 숫자가 바뀐다. 잔액이 부족하면 잔액·부족액과 함께 막힌다. 완료(정산) 뒤의 충당은 스냅샷을 바꾸지 않고 차이로 표시된다(5와 같은 규칙)
  4. 경영관리·대표는 손익 숫자를 눌러 근거 줄(견적 줄·지출결의·증빙·리저브 출금·'계산 불가' 이유)로 내려가고 계산식을 설정 화면에서 본다. 기획본부(staff)에게는 드릴다운·계산식이 화면·API·Excel 어디에도 나오지 않는다 — 손익 DTO를 `project(viewer, dto)`로 투영하면 기획본부에게는 결과 숫자 필드만 남고 trace·근거 id 필드는 타입 수준에서 빠진다(Issue 3; 누수 스캔이 이 DTO × 계급을 검사). 비용 판정은 effectiveCost SQL 식 하나(우선순위 CASE + 근거 id)이고 목록·Excel·팀 합계·상세(trace)가 전부 이 식을 공유해 읽기 시점에 계산하며, 저장하는 것은 정산 스냅샷뿐이다 — 쓰기 시점 파생 컬럼은 갱신 누락 비정규화라 두지 않는다(Eng OV-4). 계산은 SQL 뷰가 아니라 결과와 근거(trace)를 함께 돌려주는 `domain/pnl` 서비스 함수이고, '목록 합계 = 상세 합계' 테스트가 있다
  5. 완료(정산)는 정산 결재 문서(경영관리 기안 → 대표 승인, Phase 5 결재 모듈)로 처리되며 대표 승인 순간 손익 스냅샷이 찍힌다. 스냅샷은 이후 설정 변경에 소급되지 않고, 완료 뒤 계약 금액·매출이 정정되면 재계산하지 않고 차이만 표시된다
  6. 역할별 첫 화면이 있다: PM(내 프로젝트·내 지출결의), 경영관리(나갈 돈·결재·미증빙), 대표·팀장(손익). 프로젝트 손익 목록을 Excel로 내보내면 정보 노출표가 그대로 적용되고 원화 환산액 옆에 원래 통화·금액 열이 함께 나간다. CI 핵심 흐름 통합 테스트가 로그인 → 지출결의 → 결재 → 손익까지 통과한다. 같은 프로젝트를 PM과 대표가 열었을 때의 노출 차이(PM은 결과 숫자만, 대표는 드릴다운)가 Playwright E2E 스모크로 CI에 있다(Issue 14). 손익 계산 테스트는 합성 데이터 단위 테스트이며 현재 시각(시계)을 주입해 연도 귀속·스냅샷 시점을 결정적으로 검증한다. 골든 표·양 본부 사전 확인은 두지 않는다(15B, 수용된 위험)

### Phase 10: 팀 손익·연간 목표·인센티브·화면 항목 추가

**Goal**: 팀장이 자기 팀의 손익(프로젝트 합 − 수주 실패 비용 − 관리비)과 연간 목표 진행률을 보고, 대표·경영관리가 인센티브 계산을 확인하며, 관리자가 코드 없이 화면 입력 칸을 추가한다
**Mode:** mvp
**Depends on**: Phase 9
**Requirements**: PNL-07, GOAL-01, GOAL-02, GOAL-03, ADMN-07
**Success Criteria** (what must be TRUE):

  1. 팀 손익 = 팀 프로젝트 손익 합 − 수주 실패 비용 − 팀 직접 관리비(팀 이름 지출 + 프로젝트 미연결 직원 개인 비용, 사용일 시점 소속 기준; 공통비 배부·인건비 없음)로 계산되어(Phase 9의 effectiveCost 식 공유) 팀장은 자기 팀만, 대표·경영관리는 전체를 본다. 팀 손익 목록도 Excel로 내보내며 정보 노출표가 적용되고 원화 환산액 기준에 원래 통화가 병기된다

  4. 관리자가 프로젝트·견적 줄·거래처에 텍스트/숫자/날짜/선택 4종 칸을 추가하면 입력·목록·검색·Excel 내보내기에 즉시 반영되고 서버가 칸마다 타입을 검증한다 — 검증은 Phase 3 규약의 `field_definitions` → zod 스키마 조립을 그대로 쓰고(새 검증 코드 없음), 필드 타입 변경은 금지되어 새 필드를 만들어야 하며, 정렬에 쓰는 필드만 실측 후 표현식 인덱스를 더한다(Issue 13)

### Phase 11: 기타소득 확인증

**Goal**: 경품 담당자가 경품 지출결의 화면에서 행사 QR을 만들고, 수령자가 제출한 확인증(Phase 04.3)이 그 지출결의에 자동으로 붙으며, 경품에 대한 회사 대납 세금이 제안되어 경영관리가 확정하면 그 프로젝트 비용에 든다 — Phase 04.3의 `/cso` 두 번과 이 페이즈의 연결이 끝나야 프로덕션에서 켜진다
