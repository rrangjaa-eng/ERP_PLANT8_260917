# BLOCKING CONSTRAINTS — Read Before Anything Else

> These are not suggestions. Each constraint below was discovered through failure.
> Acknowledge each one explicitly before proceeding.

- [ ] CONSTRAINT: worktree-isolation-stale-base — `Agent(subagent_type="gsd-executor", isolation="worktree")` forks its isolated worktree from the repository's default branch (`main`) / the session's original checkout commit — **not** from the orchestrator's current branch HEAD. On this branch (`phase-1-deploy-skeleton-login`, created off `main`), the first attempt to dispatch 01-02 this way halted immediately: the executor's own `worktree_branch_check` guard caught the worktree's actual HEAD (`e81b8ca`, `main`'s commit) not matching the expected base (`ae0bf67`, the orchestrator branch's real tip after wave 1 merged). No commits were lost — the guard did its job — but the dispatch was wasted. Structural mitigation: for the rest of this phase (and any phase run on a side branch with `branching_strategy: none`), dispatch `gsd-executor` WITHOUT `isolation="worktree"` — plain sequential dispatch directly on the shared working tree (pass the current branch/HEAD explicitly in the prompt, tell the executor there's no worktree guard to run, and have it update STATE.md/ROADMAP.md itself per the sequential-mode success criteria). This worked cleanly for 01-02 through 01-06 (6 plans, zero further incidents). Wave 5's two plans (01-05, 01-06) were run sequentially rather than in parallel for the same reason — no safe way to isolate two concurrent worktrees with correct bases was available.

**Do not proceed until this box is checked.**
