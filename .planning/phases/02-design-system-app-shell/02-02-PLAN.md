`pnpm add -D stylelint@17.15.0`으로 설치한다. D-20이 승인한 유일한 신규 devDependency이고, 리서치가 레지스트리에서 버전·라이선스·저장소를 확인했으며 postinstall 스크립트가 없음을 확인했다. **다른 stylelint 플러그인이나 config 패키지를 추가하지 않는다** — D-20이 devDependency를 stylelint 하나로 한정했고 내장 규칙 둘로 필요한 것을 전부 표현할 수 있다.

`stylelint.config.mjs`를 리포 루트에 만든다(ESM 기본 export — `package.json`이 `"type": "module"`).
- `declaration-property-value-allowed-list`: `font-family`는 `--font-sans` 참조만, `font-size`는 `--fs-` 계열 참조만, `border-radius`는 0 또는 `--radius` 참조만.
- `declaration-property-value-disallowed-list`: 색이 들어갈 수 있는 속성 집합(색·배경·테두리 색·외곽선 색·fill·stroke·accent-color·caret-color·box-shadow·border·outline·background-image)에 대해 16진 색 리터럴과 rgb/rgba·hsl/hsla 함수 호출을 금지한다. 값 전체 일치가 아니라 부분 매치이므로 box-shadow의 px 오프셋 숫자는 그대로 통과한다.
- **간격 속성에 대한 규칙 블록을 만들지 않는다.** D-20의 금지 범위는 CLAUDE.md 원문대로 색·서체·radius 셋이다. 실물 HTML의 간격 선언 대부분이 tokens.css의 4px 계열 토큰에 대응하지 않아, 간격까지 금지하면 SYSTEM.md가 이관을 지시한 마크업 자체가 거부된다. 이 제외 사실을 설정 파일 주석으로 남기지 않는다 — 근거는 02-01이 DECISIONS.md에 이미 적었다.
- `docs/design/tokens.css`를 예외 처리하지 않는다. 대신 `lint` 스크립트가 넘기는 glob을 앱 CSS로 한정해 `docs/`가 애초에 스캔 대상에 들지 않게 한다.

`package.json`의 `lint` 스크립트를 eslint 뒤에 stylelint를 이어 붙인 형태로 바꾼다. glob은 `ui/**/*.module.css`, `app/globals.css`, `app/**/*.module.css` 셋. 스크립트 이름과 개수는 그대로 두므로 CLAUDE.md의 명령 문장과 CI `quality` 잡(`pnpm lint`를 이미 부른다)은 손대지 않는다.

`test/unit/stylelint-config.test.ts`를 만든다. stylelint의 standalone API(`stylelint.lint({ code, config })`)에 설정 객체를 직접 넘겨 경고 배열을 받는 헬퍼 하나를 두고, 이름 붙은 케이스로 고정한다:
- 색 리터럴을 쓴 선언은 경고가 1개 이상이다
- 같은 자리에 토큰 참조를 쓰면 경고가 0개다
- box-shadow의 inset px 오프셋 + 토큰 색은 경고가 0개다
- box-shadow 안에 색 리터럴이 있으면 경고가 1개 이상이다
- radius 리터럴은 경고가 1개 이상이고, 0과 토큰 참조는 0개다
- 서체 리터럴은 경고가 1개 이상이고 `--font-sans` 참조는 0개다
- **간격 리터럴은 경고가 0개다** — 범위 한정이 의도임을 테스트로 고정한다
- 실물에서 상시 쓰이는 흰색 리터럴이 걸리고, 같은 계산값의 `--bg` 참조는 통과한다
  </action>

(1) `.dockerignore`에서 `docs` 한 줄을 지운다. `.planning`·`test`·`gha-creds-*.json` 등 나머지 제외는 건드리지 않는다.

**왜 부분 예외(`!docs/design/tokens.css`)가 아니라 통째 제거인가:** 부분 예외의 유일한 장점은 빌드 캐시 보존인데, build 스테이지가 `COPY . .`로 컨텍스트 전체를 한 레이어에 담으므로 어차피 커밋 하나라도 바뀌면 그 레이어는 무효화된다 — 보존할 캐시가 없다. 반대로 부분 예외는 `.dockerignore`의 부정 패턴 의미론에 의존하는데, 이 환경에 Docker 데몬이 없어 실제 `docker build`로 확인할 수 없다(리서치 Environment Availability). 확인할 수 없는 의미론에 프로덕션 빌드를 걸지 않는다. 비용은 빌드 컨텍스트 전송량 약 9.2MB 증가뿐이고 최종 이미지 크기는 불변이다 — runtime 스테이지가 `docs/`를 어디서도 다시 가져오지 않는다.

(2) `.github/workflows/ci.yml`의 `pull_request` 트리거와 `.github/workflows/deploy.yml`의 `push` 트리거를 **`paths-ignore`에서 `paths` + `!` 형태로 바꾼다.** GitHub 문서가 「경로 제외」에 제공하는 필터는 두 가지이고(`paths-ignore`, 그리고 `!`를 쓰는 `paths`) **부정 패턴을 지원한다고 문서가 명시하는 쪽은 `paths`뿐이다.** `paths-ignore` 아래의 `!`는 문서에 없는 동작이므로 거기에 프로덕션 배포 트리거를 걸지 않는다.

필터의 기본값이 뒤집히므로(`paths-ignore`는 「기본 실행 + 나열된 것만 제외」, `paths`는 「기본 미실행 + 나열된 것만 실행」) **오늘의 동작을 그대로 보존하는 순서로 쓴다.** 네 줄이고 순서가 의미를 갖는다 — 뒤의 일치가 앞의 일치를 덮는다:
1. 모든 경로를 포함하는 패턴 — 오늘의 「기본은 실행」을 복원한다
2. `.planning/**` 부정 — 오늘 제외되던 것
3. `docs/**` 부정 — 오늘 제외되던 것
4. `docs/design/tokens.css` 긍정 — 새로 되살리는 예외. **반드시 3번 뒤여야 한다**

두 워크플로 모두 같은 네 줄이고, `workflow_call`·`workflow_dispatch`·`branches: [main]`·`concurrency`는 건드리지 않는다. 이 수정이 없으면 색 하나만 바꾼 커밋이 CI도 배포도 타지 않아 운영에 영원히 도달하지 않는다 — D-21이 tokens.css를 앱의 단일 출처로 만든 이상 그 파일은 소스 코드다.

(3) 두 테스트를 고친다. 기존 단언은 `paths-ignore` 문자열의 존재를 요구하므로 **그대로 두면 이 변경과 함께 실패한다.** `test/unit/ci-guard.test.ts`의 경로 필터 케이스와 `test/unit/deploy/workflows.test.ts`의 트리거 케이스 각각에서(두 파일 모두 YAML 파서 없이 텍스트로 검사하는 기존 방식):
- `paths-ignore` 키가 더는 없음을 단언한다 — 두 형태가 섞이면 GitHub가 같은 이벤트에 둘을 함께 쓰는 것을 허용하지 않는다
- `paths` 키와 네 패턴이 모두 있음을 단언한다
- 네 패턴의 문자열 인덱스가 위 1→2→3→4 순서임을 단언한다. 특히 tokens.css 줄이 `docs/**` 부정 줄보다 뒤다
- 모든 경로를 포함하는 첫 패턴이 있음을 단언한다 — 이것이 빠지면 필터가 뒤집혀 거의 모든 PR에서 CI가 사라진다. 이 한 줄이 가장 위험한 회귀 지점이다

(4) **이 메커니즘의 실제 효과는 로컬에서 판정할 수 없다.** 문서가 지원한다고 적은 형태를 쓰는 것까지가 이 태스크가 자동으로 증명할 수 있는 전부이고, 실제 트리거는 GitHub 서버만 판정한다. 두 가지를 사람 체크로 넘긴다 — tokens.css만 바뀐 PR이 CI를 타는지, 그리고 필터가 뒤집히지 않았는지(문서·계획 밖 파일만 바뀐 PR이 여전히 CI를 타는지). 이 두 가지가 확인되기 전까지 이 수정은 **미검증**이라고 SUMMARY에 적는다.
