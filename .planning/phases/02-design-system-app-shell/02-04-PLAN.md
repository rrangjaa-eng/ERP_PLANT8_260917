<objective>
직원이 어느 화면에 있든 같은 셸에서 같은 자리를 찾는다 — PC의 상단 바, 폰의 하단 탭과 「더보기」 시트. 그리고 이 페이즈에서 처음으로, PC에서도 키보드만으로 내 계정과 로그아웃에 닿을 수 있게 된다.

Purpose: §6-0은 상단 바에 사용자를 그려 놓았지만 그것이 무엇을 여는지 한 번도 말하지 않았다. 「더보기」 시트(설정·내 정보·로그아웃)는 폰 전용이다. 그래서 명세만 따르면 PC에는 내 계정·로그아웃으로 가는 정의된 경로가 없고, 성공 기준 3의 「키보드만으로 비밀번호 변경」과 AUTH-02의 「어느 화면에서든 로그아웃」이 달성 불가다. 02-01이 문서에 그 경로를 적었고 이 플랜이 그것을 만든다.
Output: 역할 매핑 데이터 1개, 셸 컴포넌트 4개, 셸 삽입 레이아웃 1개, 매핑 단위 테스트 1개.

**파일 수에 대하여:** `files_modified`가 15줄이지만 논리 단위는 9개다 — 셸 컴포넌트 넷이 각각 `.tsx` + `.module.css` 쌍이라 여덟 줄을 쓰고, 라우트 이동 둘이 옛 경로·새 경로 네 줄로 세어진다(실제로는 파일 두 개의 이동). 세 태스크가 서로 겹치지 않는 파일 집합을 쓰고(매핑+상단 바 / 폰 하단 탭+시트 / 조립+이동), 셸은 조각으로 나누면 중간 상태에서 화면이 성립하지 않는다. 그래서 나누지 않는다.
</objective>

1차 메뉴 다섯(프로젝트·지출결의·법인카드·결재·손익)의 URL은 각각 `/projects` · `/expenses` · `/cards` · `/approvals` · `/pnl`로 고정한다 — 02-05가 정확히 이 다섯 경로로 화면을 만들고, 02-05의 라우트 대조 검증이 이 파일의 목록과 실제 라우트를 맞춰 본다. 이 파일이 URL의 유일한 출처이므로 다른 곳에 URL 문자열을 복제하지 않는다.

`ui/shell/` 아래에 두는 이유: D-26의 경계 규칙상 `ui`는 `ui`와 `lib`만 import할 수 있고 이 파일은 둘 다 필요로 하지 않는 순수 상수·함수다. `domain/`에 두면 셸이 `domain`을 부르게 되어 경계를 넘는다.

`test/unit/ui/role-menu.test.ts`로 위 behavior 여섯 가지를 고정한다. 02-02가 `test → ui` 경계를 열어 두었으므로 import가 lint에 막히지 않는다.

`ui/shell/TopBar.tsx`와 CSS Module을 만든다. 서버 컴포넌트로 둔다 — 정적 구조뿐이다. §6-0 그대로: 앱에서 유일한 딥그린 면, 흰색 반전 워드마크(잎만 밝은 녹색 토큰), 1차 메뉴, 명령 팔레트 표기(자리만, 동작은 나중 페이즈), 우측 사용자. 높이는 PC 38 · 폰 44 토큰. 현재 메뉴는 진한 바 글자색 + 아래 2px 밑줄(인셋 그림자 — px 오프셋은 리터럴로 두고 색만 토큰). 메뉴가 빠지면 남은 메뉴가 왼쪽으로 붙고 빈 자리를 두지 않는다.

**사용자 진입점(02-01이 §6-0에 새로 적은 것).** 우측 사용자 이름이 내 계정과 로그아웃에 닿는 경로여야 한다. **형태는 §6-0이 적은 것 하나만 쓴다** — 02-01 체크포인트 항목 G가 「열리는 메뉴 / 화면 링크 하나 / 나란한 요소 셋」 중 하나를 골랐고 그 답이 §6-0에 문장으로 있다. 열고 닫는 형태를 골랐다면 마우스 없이 Tab만으로 도달해 열 수 있어야 하고 Esc로 닫히며 포커스가 돌아와야 한다. 링크 하나를 골랐다면 여는 상태를 만들지 않는다 — §6-0에 없는 상호작용을 추가하지 않는다. 소속은 렌더하지 않는다 — 세션에 그 데이터가 없다. 이름만 표시하고, 자리를 임의의 값으로 채우지 않는다.
