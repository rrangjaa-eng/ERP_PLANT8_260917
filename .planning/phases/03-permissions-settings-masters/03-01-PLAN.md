<objective>
**As a** 시스템 관리자, **I want to** 코드표 항목을 화면에서 추가·비활성화·보관하고 다른 계급이 그 화면에 닿을 수 있는지를 권한표 체크박스로 정하고 싶다, **so that** 코드 수정과 재배포 없이 사람·계급·메뉴의 관계를 운영 중에 바꿀 수 있다.

이 플랜은 이 페이즈의 **트레이서**다. 마스터 엔티티 하나(코드표 항목)를 새로 생기는 모든 계층에 한 번에 꿰어 실제로 동작시킨다 — 스키마 → 마이그레이션 → `scopeFor(viewer)`를 쓰는 리포지토리 → `project(viewer, row, spec)`을 거치는 domain → `authedActionClient` Server Action → 관리자 화면 → 행동 로그 → 보관함. 뒤따르는 여섯 플랜은 전부 이 증명된 경로 위의 **확장**이다.

Purpose: 성공 기준 2가 요구하는 것은 "판정이 세 함수에서만 이루어진다"는 구조적 속성이다. 구조적 속성은 층을 따로따로 쌓아 올리면 마지막에야 성립 여부가 드러난다 — 층 여섯 개를 커밋한 뒤 "app이 행 객체를 받고 있었다"를 발견하면 여섯 커밋을 되돌려야 한다. 그래서 가장 얇은 한 경로를 먼저 끝까지 배선해 증명한다.

Output: 새 표 4개 + users 표의 계급 외래키, 판정 4함수, 레지스트리 3개(메뉴·정보 항목·액션), 행동 로그 기록 API, 보관·복원, 멱등 시드, 코드표 관리 화면 1개, 단위 5 · 통합 3 · E2E 1.

- `project.ts`: `export type DtoSpec<Row, Dto> = { readonly fields: ReadonlyArray<{ key: keyof Dto & string; from: keyof Row & string; infoItem: string }> }` + `project(viewer, row, spec, deps?): Promise<Partial<Dto>>`. spec의 `fields`를 **선언 순서대로** 순회하며 각 항목의 정보 항목을 노출 판정으로 확인해 통과한 것만 결과 객체에 싣는다 — 그래서 결과 키 순서는 spec 선언 순서이고 노출표 행 순서와 무관하다. 원본에 `from` 키가 없으면 조용히 건너뛰어 이미 투영된 결과를 다시 투영해도 같은 결과가 나오게 한다(멱등). spec 밖의 키는 결코 결과에 실리지 않는다
