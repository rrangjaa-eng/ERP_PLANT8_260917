설정 레지스트리의 아래 네 가지를 확정한다.

**① 값 저장 표를 둘로 나눈다**
- `settings_simple(key, value jsonb)` — 키당 행 하나, upsert
- `settings_historized(key, effective_from date, value jsonb)` — 키당 여러 행, `(key, effective_from)` 복합 UNIQUE
- 등록 레지스트리는 **하나**이고 각 항목이 이력 여부를 메타로 갖는다(ROADMAP 성공 기준 4가 「이 레지스트리에」를 반복한다)
- Pro: 비이력형 조회가 단일 행 읽기라 단순하고, 이력형 표에 쓸데없는 날짜 컬럼이 비이력형 키에 붙지 않는다
- Con: 키의 이력 여부를 나중에 바꾸려면 두 표 사이 데이터 이동이 필요하다
- 대안(한 표에 nullable 날짜 컬럼): 조회가 단순해 보이지만 "날짜가 null인 행과 있는 행"의 의미가 섞여 유효값 규칙이 모호해진다

**② 조회 함수의 시그니처**
`getSettingValue(def, opts?)` — `def`는 레지스트리 항목(키 문자열이 아니라 **정의 객체**), `opts.asOf`는 선택적 날짜. 반환은 `def`의 zod 스키마가 보장하는 타입.
- 키 문자열이 아니라 정의 객체를 받는 이유: 반환 타입이 호출부에서 추론되고, 오타 난 키 문자열이 런타임까지 살아남지 못한다
- `asOf`는 이력형 키에서만 쓰이고 비이력형 키에서는 무시한다
- **「어느 날짜를 넘길지」는 호출자의 책임이다** — 원천징수·회사 대납은 지급일(미지급이면 지급 예정일), 부가세는 증빙일(없으면 작성일)이라는 규칙(Eng OV-5)은 Phase 4의 금액 모듈이 결정해 `asOf`로 넘긴다. Phase 3의 조회 함수는 결정된 날짜를 받기만 한다
- Pro: Phase 3이 세금 규칙을 몰라도 되고 경계가 선명하다. Con: Phase 4가 날짜 결정 로직을 반드시 만들어야 하며 그 전까지 이력형 키는 오늘 기준으로만 읽힌다

**③ 유효값 규칙: `effective_from <= asOf` 중 최댓값, 경계 포함**
- 적용 시작일이 조회 기준일과 정확히 같으면 그 행이 유효하다
- 해당하는 행이 없으면(모든 행이 미래) 레지스트리 기본값으로 떨어지고, 기본값도 없으면 예외를 던진다(fail-closed)
- Pro: 「2026-01-01부터 10%」가 2026-01-01에 적용된다는 상식적 해석. Con: 없음 — 대안(초과 비교)은 시작일 당일이 비는 반직관적 동작이다

**④ 「등록됐으나 읽히지 않는 키」 검출과 그 예외**

함수 셋:

- `addHistorizedValue(viewer, def, { effectiveFrom, value })` — 이력형 전용. 같은 권한 확인 → 스키마 검증 → insert(복합 UNIQUE가 중복 시작일을 막는다) → 기록. 과거 행 수정·삭제 함수는 만들지 않는다. 미래 예정 행 취소용 `cancelHistorizedValue(viewer, def, effectiveFrom)`만 두고, 적용 시작일이 오늘 이전이면 거부한다
