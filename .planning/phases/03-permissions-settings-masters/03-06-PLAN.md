암호화 저장의 아래 다섯 가지를 확정한다.

**① 직렬화 형식: `v1:<iv>:<tag>:<ciphertext>` — 네 조각, 구분자는 콜론, 뒤 세 조각은 각각 base64**
03-CONTEXT.md는 접두어 `v1:`만 지정했고 정확한 형식은 명시하지 않았다(03-RESEARCH.md 가정 A2가 이 공백을 지목했다).
- Pro: 사람이 읽고 어느 버전인지 즉시 알 수 있고, 한 컬럼에 담기며, 파싱이 문자열 분리 하나다
- Con: base64가 원문보다 길어 컬럼 크기가 늘고, 콜론이 구분자라 base64 알파벳과 충돌하지 않는지에 의존한다(표준 base64에 콜론이 없어 안전하다)
- 대안(JSON 객체를 jsonb 컬럼에): 구조가 명시적이지만 컬럼 타입이 바뀌고 인덱스·비교가 복잡해진다

**② 키 인코딩: `APP_DATA_KEY_v1`은 base64로 인코딩된 32바이트**
03-RESEARCH.md 가정 A1이 "실제 값이 다른 인코딩으로 채워지면 길이가 다른 키가 되어 암호화가 즉시 실패한다"고 경고했다. 코드가 형식을 정하고 Secret Manager 등록이 그 형식을 따른다.
- Pro: 환경 변수에 안전하게 담기는 표준 인코딩. Con: 등록하는 사람이 hex로 넣으면 앱이 뜬 뒤 첫 암호화에서 실패한다 → 그래서 `lib/crypto.ts`가 키 길이를 즉시 검증하고 명확한 오류를 낸다

**③ 키가 없으면 fail-closed**
`lib/env.ts`가 이 키를 선택 문자열로 두어 값 없이도 앱이 뜬다(Phase 1 계약). 암호화·복호화는 키가 없으면 즉시 예외를 던진다 — 평문 저장이나 빈 값 통과로 떨어지지 않는다.
- Pro: 키 없는 환경에서 계좌번호가 평문으로 저장되는 최악이 구조적으로 불가능하다. Con: 키를 안 넣은 환경에서 거래처 계좌번호 입력이 500으로 실패한다(이것이 의도된 동작이고, 배포 전 사람 확인 항목이 그래서 존재한다)

**④ 키 회전: 새 버전 키를 **더하고** 옛 키를 남긴다**
`APP_DATA_KEY_v2`를 `lib/env.ts`에 선택 문자열로 추가한다. 새 암호화는 항상 가장 높은 버전 키를 쓰고, 복호화는 접두어의 버전으로 키를 고른다. `scripts/rotate-key.ts`가 옛 버전 암호문을 읽어 새 버전으로 다시 쓴다. **회전이 끝날 때까지 옛 키를 지우지 않는다.**
