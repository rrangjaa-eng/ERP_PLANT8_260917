**As a** 기획 PM·팀장, **I want to** 행사 종료일 다음 날 프로젝트가 저절로 정산 단계로 넘어가고, 종료일이 지났는데 아직 수주중인 건이 상세에서 눈에 띄기를, **so that** 「끝났는데 안 닫힌 건」을 사람이 기억해서 옮기지 않아도 되고, 정산 규칙(실행가 수정 · 새 줄 추가만)이 날짜에 맞춰 정확히 걸린다.

이 플랜은 04-06 재계획에서 나눈 **날짜로 움직이는 절반**의 서버 쪽이다(D-76 · D-81). 옛 04-11(23파일)은 체커 1차에서 기간 칸(S13) · 정산→진행 되돌리기(D-80) · 진행 이후 기간 저장 규칙(D-82) · 「기간 적기」 연결을 **04-22**로 보냈다. 이 플랜은 자동 정산 · 읽기·쓰기 경로의 선판정 · 종료일 지남 표시와 그 이름 출처를 맡는다. 상태 모델은 04-06, 사람의 전환과 잠금·로그 트랜잭션은 04-20, 상태 화면은 04-21, KST 날짜 모듈은 04-29가 만들었다.

**D-76 실행 방식(계획 재량 — 사용자 D19-8 확정, CEO OV-5 보완):** 읽기 시점 판정. 두 입구를 둔다.
- **읽기용 `applyAutoSettlement`:** 짧은 별도 트랜잭션에서 `UPDATE … WHERE id IN (SELECT … FOR UPDATE SKIP LOCKED) RETURNING`을 한 번 돌리고 같은 트랜잭션에서 돌아온 행마다 시스템 로그를 남긴다. 잠긴 행(누가 저장·전환 중)은 건너뛴다 — 그 쓰기가 자기 잠금 안에서 같은 판정을 한다. 실패하면 로그만 남기고 읽기는 계속된다(fail-open).
- **쓰기용 `loadProjectForGate`:** 프로젝트 행을 `FOR UPDATE`로 잠근 뒤 그 행이 판정 대상이면 같은 트랜잭션에서 정산으로 바꾸고 로그를 남긴 다음 잠근 행을 돌려준다. 실패하면 쓰기도 실패한다(fail-closed). 이 플랜에서는 상태 전환이 쓰고, 04-22가 합성 저장, 04-12가 견적 줄 저장, 04-14가 차수·승인 쪽(그룹 B)에 같은 함수를 건다(CEO A-33 — 손으로 흩어 놓는 선판정 네 곳을 한 함수로).

Cloud Scheduler 예약 작업은 Phase 7이 **같은 `applyAutoSettlement`를 부르는 얇은 배선**으로 얹는다(범위 밖 — CEO 리뷰 「이연」).

Purpose: 04-12(정산의 편집 범위)가 걸리려면 프로젝트가 제때 정산이 되어야 하고, 04-17·04-18(목록)이 정산 태그를 보이려면 목록 읽기도 같은 판정을 거쳐야 한다. 04-22의 기간 칸이 이 플랜의 함수·이름 출처를 그대로 쓴다.

① `domain/projects/status-transitions.ts`에 자동 전환 한 줄 `AUTO_TRANSITIONS = [{ from: "in_progress", to: "settling", trigger: "end_date_passed" }] as const`를 더한다 — 자동 전환이 쓰는 상태 값도 이 데이터 모듈 한 곳에서 온다.

② **리포지토리(`repositories/projects.ts`).** `settleOverdueProjects(viewer, { todayKst, projectIds?, from, to }, tx)`: 대상 선택을 하위 선택 `SELECT id FROM projects WHERE status = $from AND end_date IS NOT NULL AND end_date < $todayKst::date AND archived_at IS NULL [AND id = ANY($projectIds)] FOR UPDATE SKIP LOCKED`로 잠그고, `UPDATE projects SET status = $to, version = version + 1, updated_at = now() WHERE id IN (그 하위 선택) AND status = $from RETURNING id, end_date, (직전 status_change 시각 — `action_log`에서 그 프로젝트의 `status_change` 최대 `occurred_at`을 고르는 스칼라 하위 질의)`. **날짜 비교에 DB의 현재 날짜 함수나 서버 시간대를 쓰지 않는다** — 오늘은 인자로만 들어온다(Pitfall 7). RETURNING 안의 하위 질의가 Drizzle에서 막히면 같은 `tx`에서 돌아온 id 목록으로 두 번째 SELECT 한 번을 돌린다(그 선택을 SUMMARY에 적는다). 테이블·칸 이름은 `db/schema/action-log.ts`에서 확인한다.

③ **`domain/projects/auto-transition.ts`.** 순수 도우미 `effectiveOnFor({ endDate, lastChangeOn })`(A-08, 내보내기) · `applyAutoSettlement(opts: { projectIds?: string[] }, deps?: { now?; recordAction?; settle?; logger? }): Promise<string[]>` — `withTransaction`으로 **짧은 별도 트랜잭션**을 열어(바깥 tx를 받지 않는다 — 읽기 경로 전용) `kstToday(now())` → `settleOverdueProjects(…, tx)` → 돌아온 행마다 `recordAction(SYSTEM_VIEWER, { actionType: "status_change", entity: "project", entityId, detail: { from, to, trigger: "end_date_passed", effectiveOn } }, { tx })` → 커밋. 바뀐 행이 있으면 `log.info("project.auto_settle", { count })`. 트랜잭션 안의 어느 단계든 던지면 롤백되고, 함수는 `log.error("project.auto_settle_failed", { projectIds, reason: 오류 이름·코드 })`를 남긴 뒤 `[]`를 돌려준다 — **읽기를 막지 않는다**(A-15·C-09, 사용자 D19). 단위 테스트는 `deps.settle`·`deps.recordAction`·`deps.logger`를 스텁으로 넣어 `behavior`를 DB 없이 증명한다(RED → GREEN).
