# Phase 04.1: 결재 모듈·연차 — Research

**Researched:** 2026-09-24
**Domain:** 범용 결재 엔진(routes/steps/instances 상태 기계) + 연차 신청·잔고 차감, Next.js 16 App Router + Drizzle 4계층 기존 스택 위
**Confidence:** MEDIUM — 재사용할 building block은 전부 코드를 직접 읽어 HIGH, 결재선의 "특정 부서(경영관리본부)" 담당자 해석 메커니즘은 기존 스키마에 빈 자리가 있어 LOW(아래 Open Questions)

## Summary

Phase 04.1은 새 외부 패키지가 필요 없다 — Next.js 16·Drizzle·next-safe-action·zod 기존 스택과 Phase 3이 이미 세운 권한·설정·조직·행동로그·누수스캔 메커니즘 위에 결재 도메인(`domain/approvals`)과 연차 도메인만 얹는다. 04.1이 만들 3표(routes/steps/instances)는 문서 종류를 `document_kind` 문자열 컬럼으로만 구분해 Phase 5가 지출결의·정산 결재를 "등록"만 하면 되게 하고, 연차 자체는 문서 종류 중 하나로 04.1이 직접 만든다.

가장 중요한 두 가지 리스크는 기능이 아니라 **동시 실행 중인 두 브랜치의 마이그레이션 번호/스냅샷 충돌**과 **결재선의 "특정 부서(경영관리본부)" 조직 범위를 해석할 사람↔조직 매핑이 현재 스키마에 없다**는 것이다. 전자는 이번 조사에서 drizzle-orm의 마이그레이션 실행기가 스냅샷을 런타임에 전혀 읽지 않는다는 사실을 코드로 확인했으므로(아래 Pitfall 1) 번호 충돌은 이번 브랜치에서 안전하게 회피할 수 있다. 후자는 `docs/inputs/phase-05-approval.md` §1 자체가 "경영관리본부에 팀이 없다"고 명시하면서도 그 조직에 "담당"이 항상 존재해야 한다고 요구하는데, 기존 스키마의 조직 소속 조회 경로가 오직 `team_memberships → teams.org_unit_id`뿐이라 팀이 없는 본부는 이 경로로 아무도 찾을 수 없다(Open Question 1). 계획 단계에서 반드시 결정해야 한다.

**Primary recommendation:** `domain/approvals`를 Phase 3 도메인들(`domain/permissions`, `domain/settings/registry`, `domain/org`, `domain/action-log`)과 같은 패턴(순수 함수 + `deps?` 주입 + `registerDto`/`registerAction` 부작용 등록)으로 짓고, 결재선의 "조직 범위" 해석은 팀 경로만으로는 불충분함을 인정한 뒤 이 페이즈에서 "본부 직접 소속" 조회 경로를 하나 추가한다(Open Question 1의 해법 B). 마이그레이션은 지금 0017부터 생성하되 Phase 4 쪽 마이그레이션(0011~0016)이 먼저 main에 머지되면 PR 직전에 `drizzle-kit generate`를 재실행해 번호·스냅샷을 다시 만든다(Pitfall 1).

### Locked Decisions (다시 묻지 않음)

- 결재선 기본 4단(팀장 → 본부 책임자 → 경영관리 → 대표), 단계 = 계급 × 조직 범위, 제출 시 고정, 사람은 표시 시점 현재 담당으로 해석 — `docs/inputs/phase-05-approval.md` §1
- 빈 자리는 건너뛰고, 전부 비면 대표가 받는다. 결재 없이 통과하는 문서는 없다 — 입력 §2
- 자기 승인 기본값은 문서 종류별 설정: 연차 = 건너뜀(지출결의·정산 결재의 "본인이 직접 눌러 통과"는 Phase 5 소관이지만, 04.1은 "문서 종류별로 다른 기본값을 가질 수 있는 설정 키 구조"를 지금 세워야 한다) — 입력 §3
- 반려 사유는 자유 입력 필수, 사유 코드표 없음 — 입력 §4
- 연차: 종일 1 · 반차 0.5 · 반반차 0.25 · 재택 0(기록만, 횟수 제한 없음), 회계연도(1월 시작) 부여, 이월 없음, 일수는 관리자 연 1회 설정, 잔여 초과는 막지 않고 경고(신청 창·결재 옆판에 남은/결재 중/이번 신청 일수) — 입력 §5
- **D-96 (연차 — 입사 첫해):** 입사한 해에는 법정 월차를 자동으로 준다. 입사일부터 1개월을 채울 때마다 1일, 그해 최대 11일, 입사 다음 회계연도 말에 소멸. 회계연도 연차와는 별도 잔고. **Reversibility: costly** — 잔고가 두 종류가 되어 신청·결재 옆판·차감 로직이 함께 바뀐다
- **D-97:** 퇴직 시에는 잔여 일수만 보여 주고 금액 정산은 하지 않는다. 연차 수당 계산은 범위 밖

### Claude's Discretion (04.1이 정한다)

- 월차 "1개월 채움" 판정은 입사일 기준 매월 같은 날 적립으로 하고 결근 차감은 관리자 수동 조정(근태 기록 없음). 신청 시 차감 순서는 소멸이 빠른 월차부터가 기본

## Architecture Patterns

### System Architecture Diagram

```
[직원 브라우저/폰]
      │  연차 신청 폼 제출 (Server Action, authedActionClient)
      ▼
[app/(app)/leave/*]  ── Server Component + Server Action
      │  submitLeaveRequest(viewer, input)
      ▼
[domain/approvals]  ← 문서 종류 등록 레지스트리(document_kind: "leave", 테스트용 2번째 종류)
      │  1. 잔고 확인(domain/leave) — 경고만, 막지 않음
      │  2. resolveRoute(documentKind, drafter) → 계급×조직범위 단계 배열 읽기(설정)
      │  3. 단계별 담당자 후보 해석(팀/본부/전사/특정부서) → 빈 자리 스킵 → 전부 빔이면 대표
      │  4. approval_instances/approval_steps INSERT(고정된 role×scope, status=submitted)
      │  5. recordAction(document_submit)
      ▼
[repositories: approval-routes / approval-steps / approval-instances / leave-requests / leave-adjustments]
      │  scopeFor() 없음 — 후보·처리자·기안자 기준으로 행을 고르고 project(viewer,row,spec,{visible 요청 메모})로 DTO 투영
      ▼
[PostgreSQL: approval_routes, approval_steps, approval_instances, leave_requests, leave_adjustments]

[결재자 폰] ── 결재 대기함(app/(app)/approvals/page.tsx, 이미 자리 있음)
      │  listMyInbox(viewer) — 표시 시점 담당자 재해석(step.roleId × step.scope 를
      │  매 조회 시 teamAtDate/신규 org-unit 조회로 "현재" 사람으로 치환, 저장하지 않음)
      │  approveStep(viewer, instanceId, expectedVersion) / rejectStep(..., reason) / withdraw(...)
      ▼
[domain/approvals.nextStep(current, action)] — 순수 함수: draft→submitted→in_review→approved/rejected/withdrawn
      │  WHERE version = expectedVersion UPDATE ... RETURNING (낙관적 잠금, quote-lines 선례 재사용)
      ▼
[승인 완료 시] 저장된 잔고를 깎지 않는다 — 잔고는 승인된 신청·leave_adjustments에서 파생 계산(domain/leave/balance.ts) + recordAction(document_approve)
```

> CEO-22(2026-09-24) 정정: 위 그림은 확정된 계획(04.1-01·03)에 맞춰 잔고 표 없음(파생 계산) · 결재함 `scopeFor()` 없음으로 고쳤다.

### Pattern 1: 순수 상태 기계 `nextStep()`

**What:** 문서 상태와 액션을 받아 다음 상태를 결정하는 부작용 없는 함수. `domain/rules/gate.ts`의 "등록형 규칙 + 단일 진입점" 정신과 같은 결이지만, gate.ts는 불리언 허용/거부이고 `nextStep()`은 상태 전이 자체를 계산한다는 점이 다르다.

**When to use:** 결재 인스턴스의 모든 상태 변경(제출/승인/반려/회수)이 이 함수를 거친다. 화면·액션 레이어는 이 함수가 돌려준 다음 상태만 UPDATE에 쓴다.

**Example (설계 스케치 — 코드베이스에 아직 없음, 이 페이즈가 만든다):**
```typescript
// domain/approvals/index.ts — 설계 스케치. 정확한 타입은 계획 단계에서 확정.
export type ApprovalStatus =
  | "draft" | "submitted" | "in_review" | "approved" | "rejected" | "withdrawn";

export type ApprovalAction =
  | { type: "submit" }
  | { type: "approve"; stepIndex: number }
  | { type: "reject"; stepIndex: number; reason: string }
  | { type: "withdraw" };

export function nextStep(
  current: { status: ApprovalStatus; stepIndex: number; totalSteps: number },
  action: ApprovalAction,
): { status: ApprovalStatus; stepIndex: number } {
  // draft → submitted → in_review → (approved | rejected | withdrawn)
  // in_review에서 approve가 마지막 단계면 approved, 아니면 stepIndex+1로 in_review 유지.
  // 순수 함수 — DB·시각·권한 판정을 하지 않는다(그건 domain의 다른 함수·repositories의 몫).
  throw new Error("설계 스케치 — 계획 단계에서 구현");
}
```

### Pattern 2: 제출 시점 결재선 고정 + 표시 시점 재해석

**What:** `approval_steps` 행에 role×scope(계급 id + 조직 범위 종류/대상)를 **문자 그대로** 저장한다(정규화된 "담당자 user_id" FK가 아니다). 목록·상세 조회 시마다 그 role×scope를 현재 조직 데이터로 재해석해 "지금 이 사람"을 계산한다.

**When to use:** EXP-04 "고정되는 것은 단계별 계급×조직 범위이며, 사람은 표시 시점의 현재 담당으로 해석" 요구사항 그 자체.

**Example:**
```typescript
// domain/org/index.ts:188 — 이미 존재하는 재사용 가능한 building block
export async function teamAtDate(
  viewer: Viewer,
  userId: string,
  date: string,
  deps?: Partial<TeamAtDateDeps>,
): Promise<TeamDto | null> { /* ... */ }
```
이 함수는 "사람 → 그 시점 팀"을 푼다. 결재선 해석은 반대 방향("팀/본부 → 그 역할을 가진 현재 사람들")이 필요하므로 **새 리포지토리 함수**가 필요하다(Open Question 1 참고) — `teamAtDate`를 그대로 재사용할 수는 없고 같은 패턴(발령일 이력 기준 최신 1건)을 역방향 쿼리로 다시 짜야 한다.

### Pattern 3: 낙관적 잠금 — WHERE version = expected UPDATE

**What:** `version` 정수 컬럼을 두고 UPDATE의 WHERE 절에 기대값을 넣어, 0행이 갱신되면 "충돌"로 판정한다.

**When to use:** EXP-03의 "승인↔회수·승인↔반려 동시 조작을 막는다"는 요구사항 그대로.

// repositories/quote-lines.ts:98-131 — 이미 존재하는 선례, approval_instances에 그대로 적용

`db/schema/quote-lines.ts:34`: `version: integer("version").notNull().default(1),` — approval_instances도 같은 컬럼 정의를 쓴다.

### Anti-Patterns to Avoid

- **결재 상태를 문서 종류별로 하드코딩하는 if/switch:** ROADMAP 성공 기준 1이 명시적으로 "테스트 전용 두 번째 문서 종류로 하드코딩이 없음을 증명"을 요구한다 — `document_kind` 문자열 + 등록 레지스트리 패턴(다른 Phase 3 레지스트리들과 동일)을 쓴다.
- **담당자를 제출 시점에 user_id로 확정해 저장:** EXP-04를 정면으로 위반한다. role×scope만 저장하고 사람은 항상 조회 시점에 계산한다.
- **`scopeFor()`를 결재 대기함 필터로 오용:** `scopeFor`는 메뉴 보기 권한에 따른 "all/none" 이진 판정만 한다(`domain/permissions/scope-for.ts:11`, `Scope = { rows: "all" | "none"; ... }`). "내가 이 인스턴스의 현재 담당자인가"는 이 함수가 풀 수 없는 질문이다 — 결재 대기함 조회는 `scopeFor`와 별개의 도메인 로직(현재 단계의 role×scope를 현재 조직 데이터로 풀어 viewer.id가 그 후보 집합에 있는지)이 필요하다.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| 동시성 제어(승인 레이스) | 커스텀 락 테이블·SELECT FOR UPDATE 직접 구현 | `version` 컬럼 + WHERE-version UPDATE(`repositories/quote-lines.ts:98-131` 패턴) | 이미 Phase 4가 검증한 패턴, 추가 인프라 없음 |
| 문서 번호 부여 | 새 카운터 로직 | `repositories/document-counters.ts`의 `allocateNumber()` + `domain/document-numbering` | 트랜잭션 내 원자적 증가가 이미 동시 제출 통합 테스트로 검증됨(Issue 10) |
| 권한 판정 | 새 role-check 함수 | `domain/permissions/can.ts`의 `can(viewer, menu, action)` | 유일한 판정 지점(D-35), 다른 경로를 만들면 누수 스캔이 못 잡는다 |
| 설정 화면 렌더링 | 결재 단계 전용 커스텀 폼 | `domain/settings/registry.ts`의 typed registry(자동 화면 생성) | ADMN-05가 "등록된 키를 서버가 읽는지 테스트가 강제"를 요구 — 별도 폼을 만들면 이 강제가 깨진다 |
| 행동 로그 기록 | 새 로그 테이블/함수 | `domain/action-log/record.ts`의 `recordAction()` — `document_submit`/`document_approve`/`document_reject`/`document_withdraw`가 **이미 CORE_ACTION_TYPES에 있다**(`domain/action-log/record.ts:14-17`) | 새 액션 타입 등록조차 필요 없다 |

**Key insight:** Phase 3·4가 만든 4개 레지스트리(DTO, Server Action, Export, Setting)와 3개 판정 함수(can/visible/scopeFor)가 이미 "새 문서 종류를 등록만 하면 검사·화면·권한이 따라온다"는 정확히 04.1이 필요로 하는 확장점이다. 04.1의 진짜 신규 작업은 ① 상태 기계 자체, ② 결재선의 역방향 조직 조회(사람→팀이 아니라 팀/본부→현재 사람들), ③ 연차 잔고 계산 셋뿐이다.

## Common Pitfalls

### Pitfall 1: 마이그레이션 번호·스냅샷 충돌 (병렬 브랜치)

**What goes wrong:** main은 현재 `0010_revenue_entries.sql`에서 멈춰 있다(`db/migrations/meta/_journal.json` idx 10까지, [VERIFIED: db/migrations/meta/_journal.json — 직접 확인, entries[10].tag="0010_revenue_entries"]). Phase 4는 별도 브랜치(`origin/claude/gsd-progress-e1nzgu`, 현재 HEAD `1480ffc`, 04-32까지 완료, [VERIFIED: git log 실행 결과])에서 실행 중이며 아직 마이그레이션 0011을 만들지 않았지만(그 브랜치도 여전히 0000~0010뿐 — `git ls-tree origin/claude/gsd-progress-e1nzgu -- db/migrations/`로 직접 확인), ROADMAP.md의 Phase 4 웨이브 4·5·6·14·21·24가 이미 0011~0016 번호를 계획 문서에 못박아 뒀다(`.planning/ROADMAP.md:228,234,240,272,300,313` — "마이그레이션 0011"·"0012"·"0013"·"(0014)"·"0015"·"0016"). 04.1이 지금 `pnpm db:generate`를 돌리면 다음 사용 가능 번호는 로컬에서 0011이 된다 — Phase 4가 실제로 0011을 쓰기 전에 04.1이 선점하면 번호가 겹친다.

**Why it happens:** 두 브랜치가 같은 `main`(0010)에서 갈라져 독립적으로 `drizzle-kit generate`를 실행하기 때문. `drizzle-kit generate`는 로컬 `db/migrations/meta/_journal.json`만 보고 다음 번호를 정하므로 다른 브랜치의 예정된 번호를 알지 못한다.

**How to avoid:** ROADMAP 04.1 절 자체가 이미 "0017부터 쓴다"고 못박았다(`.planning/ROADMAP.md:328,345` — "Phase 4 미완성 코드... 기대지 않아 Phase 4와 나란히 진행", "Phase 4가 마이그레이션 0011~0016을 쓸 예정이라 이 페이즈 마이그레이션 번호와 `_journal.json` 충돌을 푸는 방식"을 계획 단계 결정 사항으로 위임). 04.1의 스키마 파일을 만든 뒤 로컬 `db/migrations/meta/_journal.json`의 idx를 **수동으로 6개 앞당기거나**(비추천 — drizzle-kit이 다음 실행 때 다시 0011로 되돌릴 수 있음), 더 안전하게는:
  1. 04.1 스키마(`db/schema/approvals.ts`, `db/schema/leave.ts`)를 작성하고 `pnpm db:generate`로 **정상적으로 0011 번호를 받게** 생성한 뒤,
  2. 파일명·journal.json의 tag·idx를 0011→0017로 **수동 리네임**한다(SQL 파일 내용·snapshot 파일 내용은 그대로, 파일명과 journal 엔트리만 바꾼다). `meta/0011_snapshot.json` → `meta/0017_snapshot.json`으로 파일명도 함께 바꾼다.
  3. PR을 열기 **직전**(04.1 브랜치를 main에 머지하기 전), main을 확인해 Phase 4의 0011~0016이 이미 merge되어 있으면 `git rebase main` 후 04.1의 0017 스냅샷이 실제로 0016 이후 스키마 상태를 반영하는지 검증한다 — **가장 안전한 방법은 이 시점에 04.1의 마이그레이션을 삭제하고 rebase된 스키마 기준으로 `pnpm db:generate`를 다시 돌리는 것**이다.
  4. drizzle-orm의 런타임 마이그레이터(`node_modules/drizzle-orm/migrator.js`)는 **`meta/_journal.json`과 각 `.sql` 파일만 읽고 `meta/*_snapshot.json`은 전혀 읽지 않는다**([VERIFIED: node_modules/drizzle-orm/migrator.js — `readMigrationFiles()`가 `journalPath`와 `${migrationFolderTo}/${journalEntry.tag}.sql`만 fs.readFileSync하고, 스냅샷 파일 경로를 참조하는 코드가 없음을 직접 읽어 확인]). 즉 **스냅샷이 일시적으로 부정확해도 `pnpm db:migrate`(운영 적용)는 깨지지 않는다** — 스냅샷은 오직 `drizzle-kit generate`가 "다음 diff"를 계산할 때만 쓰는 dev-time 도구다. 그래서 이 문제의 진짜 리스크는 "런타임 마이그레이션 실패"가 아니라 "merge 후 첫 `drizzle-kit generate`가 Phase 4의 스키마 변경을 다시 diff하려 드는 것"이다 — 위 3단계(merge 직전 재생성)가 이를 막는다.

  **권장 옵션: 위 1~4를 그대로 쓴다.** 대안으로 "저장소를 소유한 사람이 두 브랜치의 머지 순서를 먼저 정하고 먼저 머지되는 쪽이 번호를 확정한다"는 조율도 가능하지만, 병렬 진행의 취지(서로 기다리지 않음)에 어긋난다.

**Warning signs:** `pnpm db:generate`가 0011이 아닌 다른 번호를 제안하면 로컬 `meta/_journal.json`이 이미 0011~0016을 포함한 상태(= main에 Phase 4가 이미 머지됨)라는 뜻이니 그대로 다음 번호를 쓰면 된다(수동 리네임 불필요).

### Pitfall 2: 조직 범위 "특정 부서(경영관리본부)" 해석 경로 없음

**What goes wrong:** `docs/inputs/phase-05-approval.md` §1은 "경영관리본부에 팀이 없어 1단도 빔"이라고 명시한다. 그런데 EXP-03의 3단계("경영관리본부 담당")는 항상 채워져야 한다(§2 "아무도 안 남으면 대표가 받는다"는 **모든 단계가 빈** 경우의 예외이지, 특정 단계 하나가 구조적으로 항상 빌 수 있다는 뜻이 아니다). 현재 스키마에서 "어떤 사람이 어느 본부 소속인가"를 조회하는 유일한 경로는 `team_memberships → teams.org_unit_id`뿐이다([VERIFIED: `domain/permissions/scope-for.ts:20-32`의 `ENTITY_MENUS`, `repositories/users.ts` 전체, `db/schema/auth.ts`의 `users` 테이블 정의 — 전부 직접 읽었고 `users` 테이블에 `org_unit_id` 컬럼이 없음을 확인]). 팀이 없는 본부는 이 경로로 아무도 찾을 수 없다.

**Why it happens:** Phase 3(MAST-02)의 조직 모델이 "팀 ⊂ 본부"만 설계했고, "본부 직속 인원(팀 없음)"은 설계 대상이 아니었다.

**How to avoid:** 계획 단계에서 다음 중 하나를 명시적으로 결정해야 한다(연구 결과로는 결정할 수 없다 — Open Question 1 참고):
  - (A) 마스터 데이터 운영으로 해결: 경영관리본부 아래에도 "경영관리팀" 같은 이름뿐인 팀을 만들어 기존 `team_memberships` 경로를 그대로 쓴다. 스키마 변경 없음, MAST-02의 `teamId?: string`가 이미 optional이라 코드 변경도 없다 — 다만 "팀이 없다"는 §1의 전제와 화면상 모순된다(팀 목록에 실체 없는 팀이 보임).
  - (B) 스키마 확장: `users`에 `org_unit_id`(nullable) 직접 소속 컬럼을 추가하거나, `team_memberships`와 평행한 `org_unit_memberships` 발령 이력 표를 04.1이 새로 만든다. 04.1의 Claude's Discretion(결재 3표 스키마 세부)에 포함되는 범위라 이 페이즈가 결정할 수 있지만, Phase 3의 조직 모델(MAST-02)에 손을 대는 것이므로 04.1이 Phase 4가 건드리는 파일과 겹치지 않는다는 전제(ROADMAP "Phase 4 미완성 플랜이 바꾸는 파일... 건드리지 않는다")와는 별개로 **Phase 3가 이미 완성한 파일**(`db/schema/org.ts`, `domain/org/index.ts`)을 확장하게 된다 — Phase 4와는 충돌하지 않지만 Phase 3 산출물의 범위를 넘는다는 점은 사용자 확인이 필요하다.
  - (C) "경영관리본부 담당"을 role×org-scope 해석이 아니라 **역할(계급) 단독 해석**으로 단순화: "본부 책임자" 계급을 가진 사람 전원 중 소속 팀이 없는(=본부 직속) 사람을 후보로 본다. 이는 우연히 지금 조직 구조(경영관리본부만 팀이 없음)에서는 동작하지만 일반 규칙으로는 깨지기 쉽다(팀 없는 다른 본부가 생기면 오해석).

  **본 연구는 (A)를 잠정 권장**한다 — 스키마·코드 변경이 0이고 "회계연도 시작 전 관리자가 마스터를 세팅"하는 이미 확립된 운영 패턴(Phase 8 전환 계획과 동일한 결)과 맞기 때문이다. 그러나 이는 제품 결정(조직도가 실제로 그렇게 보이는지)이라 계획 단계에서 사용자 확인이 필요하다.

**Warning signs:** 결재선 해석 단위 테스트에서 "경영관리본부 담당" 단계가 합성 데이터로도 항상 빈 배열을 반환하면 이 문제다.

### Pitfall 3: `scopeFor()`를 결재 대기함 필터로 오용

**What goes wrong:** 새 리포지토리 함수를 만들 때 습관적으로 `scopeFor(viewer, "approval_instance")`를 호출해 "내 결재함"을 필터링하려 하면, `scopeFor`는 "이 메뉴를 볼 권한이 있는가"의 all/none 이진 판정만 하지(`domain/permissions/scope-for.ts:11` `Scope = { rows: "all" | "none"; includeArchived: boolean }`) "이 특정 인스턴스의 현재 담당자가 나인가"는 답하지 못한다. 그대로 쓰면 전체 결재 인스턴스가 모든 사용자에게 보이거나(approvals 메뉴 view 권한만 있으면 전부 "all") 전혀 안 보이는 이진 결과만 나온다.

**Why it happens:** Phase 3의 `scopeFor` 패턴이 "메뉴 단위 전체 공개/비공개"만 다루도록 설계됐다(마스터 데이터·프로젝트 목록처럼 "역할이 있으면 전체를 본다" 류 엔티티에 맞음). 결재함은 "역할이 있어도 내 차례인 문서만 본다"는 인스턴스별 동적 필터가 필요한 첫 사례다.

**How to avoid:** `scopeFor`는 approvals 메뉴의 view 권한 확인(화면 접근 자체)에만 쓰고, "내 결재함 목록"은 별도 도메인 함수(`listMyPendingApprovals(viewer)`)가 각 진행 중 인스턴스의 현재 단계를 현재 조직 데이터로 재해석해 `viewer.id`가 후보 집합에 있는 것만 반환하도록 만든다. `ENTITY_MENUS`(`domain/permissions/scope-for.ts:20-32`)에 `approval_instance: "approvals"` 한 줄을 추가하는 것은 맞지만, 그것만으로 "내 차례" 필터링이 끝났다고 착각하면 안 된다.

### Pitfall 4: 연차 잔고 이력형 설정과 "연 1회 설정"의 시점 불일치

**What goes wrong:** "연차 일수는 관리자가 연 1회 설정"을 비이력형(simple) 설정 키로 만들면, 회계연도 중간에 관리자가 값을 바꿨을 때 이미 지급된 과거 연도 잔고까지 소급 변경되는 사고가 날 수 있다(예: 15일 → 20일로 바꾸면 작년 잔고도 20일이 되어버림).

**Why it happens:** `domain/settings/registry.ts`는 simple(비이력형)과 historized(이력형) 두 종류를 명확히 구분하는데(`registry.ts:24`), 어느 쪽을 쓸지는 호출자(04.1)의 판단이다.

**How to avoid:** 연간 지급 일수는 **historized**로 등록하고(`effectiveFrom` = 회계연도 시작일, 즉 매년 1월 1일), 연차 잔고 계산 시점의 `asOf`를 신청 연도의 회계연도 시작일로 넘긴다(`getSettingValue(def, { asOf: ... })`). Phase 4의 세율 설정이 이미 이 패턴을 쓰고 있다(`domain/settings/registry.ts:73-82`의 historized 분기).

## Open Questions

1. **"특정 부서(경영관리본부)" 조직 범위를 어떻게 사람으로 풀 것인가?**
   - What we know: 현재 스키마는 `user → team(현재 시점) → org_unit` 한 경로뿐이고, 경영관리본부는 입력 문서 자체가 "팀이 없다"고 말한다.
   - What's unclear: 제품 의도가 "경영관리본부에도 나중에 팀이 생길 수 있다"(그러면 스키마 확장 없이 A안으로 충분)인지 "본부 직속 인원이라는 개념 자체가 필요하다"(그러면 B안 스키마 확장이 맞다)인지.
   - Recommendation: 계획 시작 전 사용자에게 A/B/C(Pitfall 2) 중 선택을 받는다. 이 페이즈의 스키마 설계 전체가 이 답에 의존한다.

2. **연차 신청에도 결재선 4단이 전부 적용되는가, 축약된 결재선을 쓰는가?**
   - What we know: 05-CONTEXT.md·phase-05-approval.md는 결재선 4단을 "지출결의" 맥락에서 서술한다. 연차가 정말 같은 4단(팀장→본부 책임자→경영관리→대표)을 통과해야 하는지, 아니면 연차는 관례상 팀장 승인만으로 끝나는 더 짧은 경로인지 명시된 문장이 없다.
   - What's unclear: ROADMAP 04.1 성공 기준 2는 "결재선(기본 4단...)"을 연차 검증에 그대로 쓴다고 서술하지만, 실무상 연차를 대표까지 올리는 것이 과한지는 불명.
   - Recommendation: 04.1의 설정 레지스트리에 문서 종류별 결재선을 등록 가능하게 만들되(Pattern 4), 기본값은 ROADMAP 문면대로 4단 전체로 시작하고 계획 단계에서 사용자에게 "연차도 4단 전체인가"를 확인한다.

3. **연차 신청·결재 대기함 UI 계약이 없다.**
   - What we know: `docs/design/SYSTEM.md`에 연차 화면 정본이 없다(05-CONTEXT.md canonical_refs가 명시: "연차 화면 정본 없음"). `app/(app)/approvals/page.tsx`는 이미 존재하지만 완전한 placeholder(`ListEmpty` 하나뿐, [VERIFIED: app/(app)/approvals/page.tsx 전체 읽음]).

4. **Phase 3가 실제로 완료됐는가?** (연구 중 발견한 문서-코드 불일치)
   - What we know: `.planning/ROADMAP.md`의 Phase 3 절은 플랜 7개가 전부 `[ ]`(미완료) 표시고 Progress 표도 "0/TBD Not started"라고 적혀 있다. 그러나 `domain/permissions`, `domain/settings`, `domain/org`, `domain/action-log`, `domain/code-tables`, `domain/vendors`, `domain/corp-cards`, `domain/people` 전부가 main에 완성된 코드로 존재하고, Phase 4 코드(`domain/projects`, `domain/quotes`)가 이미 그것들을 정상 참조하며 동작 중이다(leak-scan 테스트가 이 전부를 import, [VERIFIED: test/integration/leak-scan.test.ts:17-31]).
