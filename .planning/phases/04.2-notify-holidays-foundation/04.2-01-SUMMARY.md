# Phase 04.2 Plan 01: notify-tick foundation Summary

**`POST /internal/notify-tick` verifies the Google OIDC token, then runs one advisory-locked tick inside a 25 s client-deadline transaction. The tick writes deduplicated `notification_log` rows (oldest first, strict cap) and one `notify_tick_runs` record that carries the incomplete recipients and an evaluation-failure flag.**

- **Duration:** about 2h 45m (the start time was not captured at spawn. It is approximated from the base commit at 18:15Z; the full integration suite took a large share)
- **Started:** ~2026-09-24T18:12Z
- **Completed:** 2026-09-24T20:58Z

## Accomplishments

- Two tables plus generated migration `0011_notify_log` (lock-timeout header, `created_at timestamp(3)`, CHECK on email_status with `sending`/`unknown`, five-column NOT NULL dedup key)
- A tracer slice from start to finish: OIDC verification, the advisory lock, the ledger insert with ON CONFLICT DO NOTHING, and the run record, returning 200/401/409/500 with the documented bodies
- Batch rules: an oldest-first strict cap, `incompleteRecipientIds` stored in the same transaction, per-kind isolation (log `notify.condition_failed`, `evaluation_failed = true`), and a weekend branch that skips evaluation
- `withDeadlineTransaction`: one connection, with BEGIN through COMMIT/ROLLBACK raced against a timer. On timeout it calls `release(err)`, which destroys the connection, and rejects late (swallowed). No global `query_timeout`.
- The existing-key lookup uses 5 array parameters (`unnest`), independent of the candidate count

## Decisions Made

- The lock key is `420401`. It is the repo's first advisory lock, and 04.2-10 will take the same key in its waiting form.
- The batch cap is read before the lock transaction opens. The plan leaves moving it inside the transaction to 04.2-10.
- If `verifySchedulerToken` can't fetch the certificates, it throws, and the handler returns 500 `tick_failed` rather than 401 `invalid_token`. An outage upstream is not a bad token.
- The test signer's public key works as PEM (spki) in `Certificates`, so the JWK fallback wasn't needed. (The plan asked for this to be confirmed during execution.)
- Tie-break order for the cap is `reference_date`, then `recipient_id`, then `entity_id`, all ascending (D-4202).
