**계획 단계 결정·가정(표면화):**

- **D-4205 후보를 만드는 계기(지연 생성):** 해마다 따로 돌리는 작업을 두지 않는다. (1) 영업일 판정·계산이 어떤 해를 처음 읽을 때(`calendar.ts`가 그 해를 보장) (2) tick이 올해를 보장하고 다음 해를 시도(실패는 경고만) (3) 관리자 공휴일 화면 진입(올해·다음 해 — 04.2-07). 배포 때 만들지 않는다(마이그레이션·시드가 날짜에 기대지 않게). 그래서 해가 바뀌어도 첫 tick이 새 해를 채운다.
- **보장의 기준:** 그 해에 `statutory` 행이 하나라도 있으면 이미 생성된 것으로 보고 건너뛴다. 없으면 `generateHolidayRules(year)`를 `ON CONFLICT (date) DO NOTHING`으로 넣는다 — 같은 날짜에 관리자 수동 행이 먼저 있으면 그 행이 남는다(덮어쓰지 않는다). 이미 생성된 해의 규칙 행은 다시 만들지 않는다 — 음력 표·규칙을 나중에 고쳐 이미 만든 해를 바로잡아야 하면 그때 마이그레이션으로 한다(가정 — SUMMARY에 남긴다).
- **표 모양:** `holidays` — `id` uuid PK(`defaultRandom`) · `date` date NOT NULL 유니크(`holidays_date_key`) · `name` text NOT NULL · `kind` text NOT NULL + CHECK(넷) · `created_by` text NULL FK `users.id`(규칙 행은 null) · `created_at` timestamp NOT NULL 기본 now. 해별 조회는 `date` 범위(`>= YYYY-01-01 AND < (YYYY+1)-01-01`)로 해서 `year` 칸을 따로 두지 않는다(유니크 날짜 색인이 범위 조회를 덮는다). `holiday_year_confirmations` — `year` integer PK · `confirmed_at` timestamp NOT NULL 기본 now · `confirmed_by` text NOT NULL FK `users.id`. 확정 표를 04.2-07이 아니라 여기서 만드는 이유: 마이그레이션 수를 둘(04.2-01 · 이 플랜)로 묶어 병렬 머지 저널 충돌 면을 줄인다.
- **마이그레이션 번호:** `pnpm db:generate --name holidays`가 정한다(손 번호 금지). 병렬 머지 시 drizzle _journal.json 재번호 필요 — 04.2-10이 머지 직전 재생성한다.
- **lookup 범위:** `loadHolidayLookup(years)`는 요청한 해들을 보장하고 한 번에 읽어 `HolidayLookup`을 만든다. 순수 함수가 읽지 않은 해를 요청하면 오류를 던진다(빈 집합으로 삼키지 않는다). `addBusinessDaysKst(date, n)`은 기준 해의 앞뒤 한 해까지 미리 읽는다(|n| ≤ 250을 가정 — 그보다 크면 `RangeError`).
