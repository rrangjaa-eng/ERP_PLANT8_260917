- **D-4217 결과 불명 표시(Codex #4 화면 쪽 — 신규 결정 · 개정 — Codex 2차 #1·#2):** 04.2-10은 모호한 SMTP 끊김·발송 마감을 `unknown` 행으로, 끊긴 실행을 `sending` 행으로 남기고 자동 재발송하지 않는다. 받는 사람이 받았는지 모르므로 실패와 따로 센다. 첫 계획은 결과 불명을 마지막 이메일 실행 하나에서 셌는데, 끊긴 실행 A 뒤에 성공한 실행 B가 오면 A가 한 번도 보이지 않았다(Codex 2차 #1). 그래서 결과 불명은 `findUnresolvedEmail(viewer, { now, unknownAfterMs: EMAIL_UNKNOWN_AFTER_MS, visibleDays: EMAIL_UNKNOWN_VISIBLE_DAYS })` → `{ bundles: U, since }`에서 온다 — 알림 행 기준이라 어떤 실행이 뒤에 와도 선점 뒤 10분부터(`unknown` 행은 바로) 7일 동안 보인다. B2는 0건이 아닌 조각만 쓰고 시각은 조각마다 괄호에 넣는다 — 실패만 `이메일 발송 실패 {F}건 ({failedAt})`, 둘 다 `이메일 발송 실패 {F}건 ({failedAt}) · 결과 불명 {U}건 ({since})`, 결과 불명만 `이메일 결과 불명 {U}건 ({since})`(`since`는 가장 이른 결과 불명 선점 시각). 〔2026-09-25 개정 — /plan-design-review #2(R11, UI-SPEC 62d1392 Copywriting B2): 앞 판은 시각을 끝에 하나만(` · {시각}`) 달아 둘 다일 때 그 시각이 어느 조각의 것인지 읽히지 않았다. 7일 창은 그대로다(#6 — 바꾸지 않음)〕 사용성 원칙(화면 글자는 건수·시각·오류만)에 따라 2차 계획의 설명 꼬리(받는 사람 메일함을 확인하라는 문장)와 `0건` 조각을 뺀다 — 누구의 메일함인지 화면이 알려 주지 못해 행동으로 이어지지 않고, 다음 한 수는 링크 `시스템 상태 보기`가 맡는다. `0건`을 쓰는 S4 zero-one-many 규칙은 시스템 상태 줄의 규칙이라 배너에는 적용하지 않는다. 시스템 상태 `이메일` 줄 꼬리는 항목마다 시각을 단다: 실패가 있으면 ` · 실패 {F}건 ({failedAt})`(`실패 {F}건`만 `--danger`), 결과 불명이 있으면 이어서 ` · 결과 불명 {U}건 ({since})`(본문 색 — `--danger`는 「실패 N건」 하나뿐이라는 S4 partial을 지킨다). 결과 불명이 0이면 기존 꼬리 ` · 실패 N건 (시각)`와 글자 하나 다르지 않다. 문구는 UI-SPEC 62d1392가 정했고, SYSTEM.md에는 DECISIONS.md 한 항목 + §7-11(B2 변형 한 문장)·§6-8(설정/결과 분리와 꼬리 한 문장) 덧붙임이 먼저 들어간다(UI-SPEC 「SYSTEM.md 수정 제안」 #4·#5의 D-4217 부분). 받는 사람 알림함의 결과 불명 행(`unknown`·`sending`)에는 보조 줄을 쓰지 않는다 — 받는 사람이 할 일이 없다(UI-SPEC S1-c · 04.2-09 소유 · 디자인 리뷰 #17).
- **결과 불명 확인 컨트롤을 두지 않는다(Codex 2차 #1 반려분 — 사용성 원칙으로 닫음):** 리뷰는 결과 불명을 「명시적으로 풀 때까지」 남기라고 권했다. 사람이 확인 처리하는 컨트롤(버튼 · 서버 액션 · 행동 로그 종류)은 경고를 치우려고 관리자에게 결정 하나를 더 시키는 요소다 — 사용성 원칙(확인 컨트롤보다 조용한 상태)에 따라 만들지 않는다. 결과 불명은 선점 뒤 7일이 지나면 B2와 `이메일` 줄 꼬리에서 조용히 빠진다(04.2-10 `EMAIL_UNKNOWN_VISIBLE_DAYS`). 2차 계획의 /plan-design-review 열린 질문은 이것으로 닫는다 — SUMMARY 「열린 질문」에 옮기지 않는다.
