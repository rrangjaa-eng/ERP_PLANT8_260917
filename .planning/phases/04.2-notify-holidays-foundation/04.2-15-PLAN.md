**계획 단계 결정(표면화):**

- **D-4216 발송 결과 셋(Codex 2차 #2):** 첫 계획의 `send(): Promise<void>`(실패는 던짐)는 「DATA를 받은 서버의 확답이 끊긴 경우」와 「서버가 거부한 경우」를 같은 예외로 보내 04.2-10이 둘 다 `failed`로 적었다 — 실제로 간 메일이 「알림함으로만 전달됨」으로 보인다. 그래서 포트는 `send(message: EmailMessage, opts: { signal: AbortSignal }): Promise<SendOutcome>`이고 `SendOutcome = { outcome: "sent" } | { outcome: "rejected"; code: string } | { outcome: "indeterminate"; code: string }`다. 판정은 어댑터가 자기 단계 변수(`stage`: `"connect" | "login" | "send"`)로 한다 — nodemailer의 고수준 `createTransport().sendMail()`은 어느 단계에서 끊겼는지 돌려주지 않아 쓰지 않는다. 판정 규칙은 must_haves 두 번째 줄 그대로다. 발송 단계에서 응답 코드 없는 오류를 모두 `indeterminate`로 보는 것은 보수적 선택이다(MAIL FROM·RCPT 중 끊김도 포함) — 실제로 안 간 메일을 「결과 불명」으로 보이는 쪽이 간 메일을 「실패」로 보이는 쪽보다 안전하다(관리자가 받은 사람에게 확인한다).
- **어댑터 모양:** `createSmtpSender(config, deps?: { connectionOptions?: Partial<SMTPConnectionOptions> })` — 호출마다 `new SMTPConnection({ ...smtpConnectionOptions(config), ...deps?.connectionOptions })`(`nodemailer/lib/smtp-connection`), 원문은 `new MailComposer({ from: config.from, to, subject, text }).compile().build()`(`nodemailer/lib/mail-composer`), 순서 `connect` → `login({ user, pass })` → `send({ from, to: [to] }, 원문)` → 성공이면 `quit()`. 결과는 한 번만 정한다(settle-once 가드): `send` 콜백 · 연결의 `error` 이벤트 · `end` 이벤트 · `signal`의 `abort` 중 먼저 온 것. nodemailer는 소켓이 끊기면 `send` 콜백 대신 `error` 이벤트만 낼 수 있다(`_onClose` → `_onError`) — 그래서 이벤트를 반드시 듣는다. `signal`이 이미 중단 상태면 연결하지 않고 `rejected`·`DEADLINE`. 풀 연결(`SMTPPool`)·재시도·재연결을 쓰지 않는다(한 tick에 받는 사람 수만큼 짧은 연결 — 10~30명 규모).
- **기본 연결 옵션:** `smtpConnectionOptions(config)` = `{ host: config.host, port: 587, secure: false, requireTLS: true, connectionTimeout: 10000, greetingTimeout: 10000, socketTimeout: 20000 }`. 포트는 환경 변수가 넷뿐이라 587(STARTTLS 필수)로 고정한다 — Workspace SMTP 릴레이·`smtp.gmail.com` 둘 다 587을 받는다(값 확인은 사용자 몫, D-711 · OPERATIONS 「이메일(SMTP) 확인 경로」는 04.2-04). 세 시간 제한은 남기되 한 통의 상한은 `signal` 마감이다(유휴 한도만으로는 끝이 없다 — Codex 2차 #6).
- **마감 값은 호출자 몫:** 한 통의 마감(`EMAIL_SEND_DEADLINE_MS` 30초)과 요청 전체 예산은 04.2-10의 이메일 단계가 정하고 `AbortSignal`로 넘긴다. 어댑터는 값을 모른다.
