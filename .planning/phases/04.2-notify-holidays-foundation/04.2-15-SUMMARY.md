### Auto-fixed Issues

**1. [Rule 1 - 계획 가정 오류] 연결 거부 코드는 ECONNECTION이 아니라 ESOCKET**
- **Found during:** Task 3 GREEN
- **Issue:** behavior 첫 줄은 「아무도 듣지 않는 포트 → rejected·ECONNECTION」이지만 nodemailer 10.0.10은 TCP 연결 오류를 `_onConnectionSocketError = err => this._onConnectionError(err, 'ESOCKET')`로 적고 `_formatError`가 node의 `ECONNREFUSED`를 덮어쓴다(systematic-debugging으로 원인 확인).
- **Fix:** 어댑터에서 코드를 바꿔 적지 않고 테스트 기대값을 실측 `ESOCKET`으로 고쳤다(허용 목록 안 · 결과 `rejected`는 계획과 같다). 테스트에 이유 주석.
- **Files modified:** test/unit/lib/email-sender.test.ts
- **Commit:** 19977a1

**2. [Rule 3 - Blocking] `emailErrorCode`를 smtp-sender.ts에 두고 sender.ts가 다시 내보냄**
- **Found during:** Task 3 RED 준비
- **Issue:** 계획대로면 sender.ts(emailSenderFromEnv → createSmtpSender)와 smtp-sender.ts(→ emailErrorCode)가 서로 값을 가져와 런타임 순환이 된다 — `test/unit/import-cycles.test.ts`가 막는다(CLI 번들 top-level await 교착).
- **Fix:** 허용 목록·`emailErrorCode`는 smtp-sender.ts에 두고 `export { emailErrorCode } from "@/lib/email/smtp-sender"`. sender.ts 공개 이름은 계획과 같다. smtp-sender.ts는 sender.ts에서 타입만 가져온다.
- **Files modified:** lib/email/sender.ts, lib/email/smtp-sender.ts
- **Commit:** dc3f192, 19977a1

**3. [Rule 3 - 테스트 가능성] `emailSenderFromEnv(source = env)` 선택 인자**
- **Issue:** 계획은 `smtpConfigFromEnv(source?)` · `emailSenderFromEnv()`. 「그때 null」을 모듈 재적재 없이 단위로 보려면 같은 선택 인자가 필요하다.
- **Fix:** 두 함수 모두 `source`(기본값 `env`)를 받는다. 연결 옵션 덮어쓰기(deps)는 여전히 넘기지 않는다(T-4.2-151).
- **Commit:** e33d7c6

**4. [Rule 1 - 정확성] 발송 단계는 원문을 만든 뒤부터**
- **Issue:** 「login 콜백 뒤 `stage = "send"`」 그대로면 MailComposer 원문 만들기 실패나 그 사이 마감이 `indeterminate`가 된다 — 서버에 아무것도 보내지 않았는데 「결과 불명」.
- **Fix:** `stage = "send"`를 `build()` 성공 뒤 `connection.send` 직전으로 옮겼다. 원문 만들기 실패는 login 단계 → `rejected`.
- **Commit:** 19977a1

**5. [가정 명시] 테스트의 `SMTP_FROM`은 주소만**
- UI-SPEC(`사용 중 · {SMTP_FROM 주소}`)이 SMTP_FROM을 주소로 다루고, nodemailer 봉투는 `<`·`>`가 든 발신자를 EENVELOPE로 거부한다 — 표시 이름 해석은 넣지 않았다. 04.2-04 OPERATIONS 「이메일(SMTP) 확인 경로」에서 값 모양이 주소임을 확인하면 된다.
