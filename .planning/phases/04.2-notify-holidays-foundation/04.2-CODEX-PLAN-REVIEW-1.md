# Phase 04.2 — Codex(GPT) 계획 적대적 검토 원문 1차 (2026-09-24, codex exec -s read-only)

1. **high — 04.2-02-PLAN.md, Tasks 1–2: The holiday fixtures are already wrong.** They omit 노동절 and 제헌절, added in 2026. Consequently, 2027 also lacks their substitutes on May 3 and July 19. The asserted 19/20-row counts would enforce incorrect calendars. **Fix:** version rules by effective date, update all dependent fixtures, and require authoritative calendar comparison before acceptance. ICU checks only validate lunar conversion; they cannot validate statutory holidays. [Official amendment](https://www.law.go.kr/lsInfoP.do?lsiSeq=285779&viewCls=lsRvsDocInfoR), [official 2027 calendar announcement](https://www.kasa.go.kr/prog/plcyBrf/brief/kor/sub01_01_04/view.do?plcyBrfNo=431).

2. **high — 04.2-02-PLAN.md, Task 2; 04.2-05-PLAN.md, Tasks 1–2: Substitute generation ignores manually registered holidays.** A temporary holiday occupying the proposed substitute date must be considered when finding the next non-holiday. `generateHolidayRules(year)` cannot see it, and `ON CONFLICT DO NOTHING` merely discards the substitute row. Adding a temporary holiday afterward never recalculates anything either. **Fix:** distinguish holidays that *trigger* substitution from holidays that *block* a substitute date; derive future substitutes using both statutory and manual dates. Test both insertion orders. [Article 3](https://www.law.go.kr/LSW/lsLawLinkInfo.do?ancYnChk=0&chrClsCd=010202&lsJoLnkSeq=1012317597).

3. **high — 04.2-01-PLAN.md, Tasks 1–2; 04.2-05-PLAN.md, Task 1: “Next tick continues” is not guaranteed.** Overflow exists only in memory, evaluators receive only `today`, and holidays skip evaluation entirely. A condition returning candidates only on their due date loses weekend notifications and yesterday’s overflow. Repeating identical fixtures with identical `now` cannot prove D-709. **Fix:** require evaluators to return all eligible, previously unlogged occurrences through today, with stable occurrence identities. Test Friday overflow → Monday and holiday-due → next-business-day delivery.

4. **high — 04.2-08-PLAN.md, Tasks 2–3; 04.2-09-PLAN.md, Task 1: A crash permanently loses email without the promised administrator warning.** Claims commit as `failed`, but run counters remain zero until every send finishes. Killing the process after commit leaves permanently suppressed messages; `findLastEmailTickRun`, filtering on positive counters, excludes that run. Conversely, SMTP acceptance followed by a crash produces “failed/inbox only” despite possible delivery. **Fix:** persist claimed bundle counts and an explicit incomplete/unknown outcome before sending; expose interrupted attempts without retrying them. Test crashes before send, after SMTP acceptance, and before counter update, plus a concurrent tick during blocked SMTP.

5. **high — 04.2-08-PLAN.md, Tasks 2–3: Raw exception messages defeat the SMTP secrecy claim.** SMTP errors can contain recipient addresses, server responses, hostnames, or authentication details. Logging only a field named `message` does not sanitize its contents; the fake error `"fake smtp failure"` cannot detect leakage. **Fix:** log an allowlisted error category/code and counts, not raw exception text. Inject errors containing every forbidden value and assert their absence from captured logs.

6. **high — 04.2-10-PLAN.md, Task 1: Migration cleanup can delete main’s snapshot.** After resolving a snapshot collision by taking main’s version, step ② deletes “the same-number snapshot” belonging to the draft migration. That path now contains main’s snapshot. This is precisely the parallel-number collision the plan anticipates. **Fix:** retain an artifact manifest from before merging, restore the entire migration tree to the selected main commit, then generate only the schema delta. Test a same-number snapshot collision.

7. **high — 04.2-10-PLAN.md, Task 1: The “empty DB” gate does not create an empty DB.** `scripts/dev-db.sh` preserves existing databases, and integration setup also migrates the existing database. Earlier tasks already applied the two draft migrations, so the consolidated migration can fail with existing tables. A fresh-only test also does not prove upgrade safety against main’s applied journal. **Fix:** use separate disposable databases for fresh installation and main → regenerated migration upgrade; verify migration records and resulting constraints in both. Explicitly prohibit consolidating migrations already deployed to shared environments.

8. **medium — 04.2-10-PLAN.md, Task 1: Its acceptance criterion is impossible, and regeneration is not repeatable as written.** `*_holidays.sql` also matches the required `*_notify_holidays.sql`, so that glob cannot produce empty output. A second execution removes only the original two draft names, leaving the previously consolidated migration behind. **Fix:** identify exact obsolete tags instead of suffix globs, and make cleanup handle either draft or previously consolidated artifacts. Exercise the procedure twice.

9. **medium — 04.2-01-PLAN.md, Task 2; 04.2-08-PLAN.md, Task 2: The batch setting does not bound work.** The first recipient’s bundle may exceed the cap arbitrarily; evaluation materializes every candidate; email claiming separately takes all pending rows. Sequential SMTP operations can exceed the request deadline after every recipient has already been irreversibly claimed. **Fix:** define separate bounds for candidate evaluation, inbox insertion, and email attempts. Split inbox processing across ticks while retaining one digest per recipient/day, and claim only work that fits the configured execution budget.

10. **medium — 04.2-01-PLAN.md, Tasks 1 and 3: Missing audience is not explicitly rejected.** `BETTER_AUTH_URL` is optional locally, while the planned verifier only checks whether the expected email exists. The installed Google verifier skips audience checking when its audience argument is undefined. **Fix:** return `not_configured` unless both expected audience and scheduler email are present whenever verification is enabled. Test the actual default handler configuration, including missing audience and missing `email_verified`.

11. **medium — 04.2-01-PLAN.md, Task 3: The replay-security acceptance claim is false.** A valid bearer token remains replayable during its validity window. Deduplication suppresses existing keys, but replay can process overflow or newly eligible candidates—the plans intentionally support repeated ticks. **Fix:** state the guarantee as authenticated invocation plus occurrence idempotency, not replay rejection. Test replay with unchanged candidates and then new candidates; add separate request-level replay protection only if that stronger requirement is intended.

12. **medium — 04.2-03-PLAN.md, Tasks 1–2; 04.2-07-PLAN.md, Tasks 1–2: Audit writes are not atomic with the recorded changes.** A committed lockout followed by failed `recordAction` leaves zero lock records; subsequent attempts are rejected before repairing it. Confirmation has the same permanent gap because retry encounters an existing confirmation and skips logging. Holiday `document_*` logs can additionally be disabled by existing settings. **Fix:** perform state changes and required audit insertion in one transaction using the tx-aware API, and make mandatory holiday audit events non-disableable. Test audit-write failure and concurrent duplicate deletion.

13. **medium — 04.2-03-PLAN.md, Task 2: The administrator-actor test proves a path users cannot execute.** The plan acknowledges that the only real unlock caller is the CLI using `SYSTEM_VIEWER`, yet claims D-712’s administrator attribution using a directly injected administrator viewer. **Fix:** provide an authenticated administrator unlock action, or preserve a verified operator identity through the CLI execution path. Test that real entry point.

14. **medium — 04.2-07-PLAN.md, Task 1: Confirmation accepts arbitrary or incomplete years.** The action validates only integer shape; the domain immediately inserts confirmation without ensuring candidates exist or checking supported years. A direct call can confirm 2036, and a future year containing one manual row can appear confirmed without its statutory calendar. **Fix:** enforce supported-year and complete-generation checks inside `confirmHolidayYear`, atomically with confirmation. Test direct action calls independently of UI visibility.

15. **medium — 04.2-05-PLAN.md, Task 1: Eager ±1-year loading breaks valid boundary-year calculations.** Any calculation within 2025 unnecessarily requests unsupported 2024; any within 2035 requests unsupported 2036—even `n=0`. Also, `|n|≤250` does not guarantee the result stays within adjacent years when manual holidays reduce available business days. **Fix:** load years as traversal reaches them and fail only when the actual calculation crosses unsupported coverage. Test both table boundaries and unusually dense holiday calendars.

16. **medium — 04.2-07-PLAN.md, Task 2: The initial 2026 calendar cannot be completed through the authorized workflow.** Election dates are manual-only, but September 2026 deployment prohibits adding June 3, 2026. Historical business-day calculations therefore omit that holiday permanently through normal administration. **Fix:** add a reviewed initial-calendar import before enabling calculations, while retaining the future-only restriction for subsequent interactive edits.

17. **medium — 04.2-08-PLAN.md, Task 2: SMTP-disabled processing consumes the daily send allowance.** `markPendingEmailSkipped` sets `email_attempted_at`, and claiming excludes anyone with any attempt today. Enabling all four SMTP variables later that day prevents even newly created notifications from being emailed, despite no email having been attempted. **Fix:** exclude `skipped_no_smtp` from the daily-attempt guard or maintain a distinct bundle claim. Test disabled tick → enable SMTP → new notification on the same day.

18. **medium — 04.2-09-PLAN.md, Tasks 1–2: The required SMTP-unconfigured failure banner cannot render as specified.** `email.kind="unconfigured"` carries no failure field, but the system-status page must derive B2 from `status.email.failure`. Its E2E explicitly expects B2 while the email row remains “미설정.” **Fix:** return the latest email-attempt outcome independently of current SMTP configuration, and use that shared result for both banner locations.

19. **medium — 04.2-06-PLAN.md, Task 1: The badge can stay stale throughout client navigation.** Counting in `(app)/layout.tsx` assumes layouts rerender on navigation; the installed Next.js documentation explicitly says shared layouts are reused. The proposed E2E creates notifications before login, so it misses the failure. **Fix:** refresh the count on navigation through a small authenticated client boundary. Test an already-open session, insert a notification, navigate via `Link`, and verify the badge changes.

20. **medium — 04.2-06-PLAN.md, Tasks 1 and 3: Inbox concurrency tests miss two real races.** Offset pagination duplicates or skips rows when new notifications arrive between pages. Separately, `created_at DEFAULT now()` reflects transaction start: a tick started before `openedAt` but committed afterward can be marked read despite being absent from the opening snapshot. **Fix:** use keyset pagination and a server-side opening operation that atomically marks the rows visible to that operation. Test insertion between pages and a tick transaction spanning inbox opening.

**Verdict: Request changes—the plans currently permit incorrect business calendars, silently lost email, and unsafe migration consolidation.**
