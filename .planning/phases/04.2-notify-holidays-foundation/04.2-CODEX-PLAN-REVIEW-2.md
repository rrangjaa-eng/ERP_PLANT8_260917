New high/medium findings:

1. **High — P10 T3; P13 T1–T3: A newer run can hide an interrupted attempt before it ever becomes visible.**  
   `findLastEmailOutcome` selects only the newest run with `email_claimed > 0`. Run A can crash at 09:00, then run B successfully send another recipient’s email at 09:01. At 09:11, A qualifies as unknown but is no longer selected. Its permanently suppressed message may never produce a warning.  
   **Fix:** query unresolved aged claims independently of the latest run’s outcome. Retain their visibility until explicitly reconciled. Test interrupted A → successful B → advance beyond ten minutes.

2. **High — P10 T2–T3; P13 T1: SMTP uncertainty is still reported as definite failure.**  
   Every rejected `send()` becomes `failed`. If the server accepts DATA but its final acknowledgement is lost, the promise can reject although delivery occurred. The UI then incorrectly says “알림함으로만 전달됨.” The new unknown mechanism handles process/database interruptions but misses this transport outcome. [RFC 5321 §4.5.3.2.6](https://www.rfc-editor.org/rfc/rfc5321.html#section-4.5.3.2.6) describes this ambiguity.  
   **Fix:** distinguish confirmed rejection from indeterminate delivery in the sender contract and ledger. Keep both non-retryable automatically. Test server acceptance followed by connection loss before acknowledgement.

3. **Medium — P01 T2; P10 T2–T3: `incompleteRecipientIds` is stale across overlapping email phases.**  
   Tick A finishes inbox insertion and blocks sending to B. Tick B then inserts only part of C’s bundle and excludes C. When tick A resumes, its older exclusion list does not contain C, so it can claim C’s partial bundle. The remainder is deferred despite the promised “complete bundle before sending” rule.  
   **Fix:** persist recipient readiness or a processing generation and check it atomically when claiming. Alternatively, restrict each email phase to a durable eligible set established during its inbox transaction. Add this overlapping-tick test.

4. **High — P06 T3; P12 T1–T2: Concurrent recomputation can leave extra substitute holidays.**  
   Transactions provide rollback, but there is no shared year lock. Start with manual holidays on October 4 and 5 and the substitute on October 6. One transaction deletes October 5 and regenerates a substitute there; another deletes October 4 while its substitute-deletion statement waits. Under READ COMMITTED, that waiting DELETE can miss the newly inserted October 5 row; the second recomputation inserts October 4, leaving **both substitutes**. Sequential insertion-order tests cannot detect this.  
   **Fix:** serialize generation and all mutations/recomputation for the affected calendar scope using the same transaction lock. Add a barrier-controlled concurrent-delete test asserting the exact final date set.

5. **Medium — P06 T3; P12 T1–T2: Cross-year substitutes contradict the recomputation scope.**  
   P12 assumes Christmas substitutes always remain in December. Its own unrestricted future manual holidays invalidate that assumption: blocking December 27–31, 2027 pushes the Christmas substitute into January 2028. Editing that January date recomputes only 2028; deleting substitutes by calendar year also cannot reliably identify the originating 2027 obligation.  
   **Fix:** track substitute origin and recompute affected origin years, including preceding-year spillovers. Test December blockers → January substitute → January blocker insertion/deletion.

6. **Medium — P10 T2–T3; P04 T1: The execution-budget proof is false.**  
   `socketTimeout` is an **idle timeout**, not a total send deadline; traffic can keep a send alive longer than 20 seconds. DNS time and pre-email evaluation/database work are also omitted from `120 + 40 < 180`. A fake clock advancing between immediately completed sends proves only loop stopping. [Nodemailer’s timeout definitions](https://nodemailer.com/smtp#connection-options) confirm the distinction.  
   **Fix:** define an end-to-end request budget, bound database waits, and enforce a cancellable wall-clock send deadline. Record deadline ambiguity as unknown. Test a transport that makes progress without finishing.

7. **Medium — P03 T1; P06 T3; P12 T1–T2: The transaction API cannot compile as specified.**  
   P03 calls `tx.execute`; holiday deletion needs `tx.delete`. The actual [`DbOrTx`](/home/user/ERP_PLANT8_260917/db/client.ts:48) contains only `insert`, `update`, and `select`. Prerequisite 04-32 explicitly says not to widen it; P01’s local `NotifyTx` does not repair these other callers.  
   **Fix:** explicitly plan a shared transaction type exposing the required operations and update `withTransaction` and repository signatures together. Include those files in ownership/dependencies.

8. **Medium — P14 T1–T2: The migration manifest and restoration baseline can disagree.**  
   Step ① classifies branch-only paths against the current `origin/main`; step ② then fetches a newer main. A snapshot newly added upstream can consequently remain in the deletion list and be removed immediately after restoration. The final diff guard catches the damage but leaves regeneration blocked. The rehearsal does not advance main between those steps.  
   **Fix:** fetch first, pin the selected main SHA, and use that SHA for manifest generation, merge, restoration, comparisons, and upgrade testing.

9. **Medium — P11 T2; P10 T2–T3: Revised behavior makes existing acceptance tests impossible as written.**  
   P11 induces confirmation failure by deleting statutory rows before confirmation—but confirmation now calls `ensureHolidayCandidates`, recreating them. Separately, P01 T1 requires newly inserted rows to remain `pending`; P10 changes the default SMTP-disabled tick to `skipped_no_smtp` while requiring that earlier test to remain green.  
   **Fix:** induce the confirmation error through a deterministic request failure or controlled database barrier, and explicitly revise earlier tick expectations when integrating the email phase.

10. **Medium — P06 T1: A required verification artifact belongs to a parallel plan.**  
    P06 runs `test/unit/db/migration-journal.test.ts`, whose designated creator is P05. Both are wave 2, and P06 depends only on P01/P02. Execution order can therefore produce “No test files found” or depend on another worker’s unfinished file.  
    **Fix:** create the shared guard in P01, or add the dependency and move P06 to a later wave.

11. **Medium — P01 T1; P07 T1–T2: Keyset cursors lack a timestamp-precision contract.**  
    PostgreSQL `timestamp DEFAULT now()` can contain microseconds, while the normal Drizzle Date mapping loses sub-millisecond precision. A page ending at `…00.123456` can return a cursor of `…00.123`; the next-page comparison then skips remaining rows at the original timestamp. A large single tick can produce exactly that boundary.  
    **Fix:** preserve exact database timestamps in opaque cursors, or explicitly use millisecond precision in storage and serialization. Test more than 50 rows sharing a timestamp with nonzero microseconds through the actual action serialization path.

12. **Medium — P12 T2–T3: The plan knowingly requires a false deletion confirmation.**  
    It mandates “이 날은 다시 영업일이 됩니다” even when deleting the manual holiday restores a substitute on the same date. It also retains the claim that only the deleted row changes, although recomputation can move other rows. Recording an open question does not resolve the contradictory acceptance criteria.  
    **Fix:** settle the copy before implementation—use neutral deletion wording or describe the calculated changes—and update the UI contract and E2E expectations together.

**Verdict: Request changes—the revision substantially improves the plan, but email uncertainty visibility, concurrent calendar recomputation, and executable migration/test contracts still block approval.**
