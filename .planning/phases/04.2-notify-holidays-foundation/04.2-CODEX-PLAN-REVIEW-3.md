   The email transaction reads the latest incomplete list under an **email-only** lock. Before its subsequent selection/update, an inbox transaction can commit C’s partial rows and `{C}`. Under READ COMMITTED, the later statement can see those rows while using the previously read list. Persisting both pieces atomically does not make separate reader statements atomic. The proposed test commits tick B *before* A starts its next claim, missing this window.  
   **Concrete fix:** synchronize claims with inbox commits using the shared tick lock, or select readiness and exact claimable IDs from one statement snapshot and update only those IDs. Add a barrier after readiness is read, then commit partial C before claiming.

2. **Medium — Cross-year generation can silently discard a substitute obligation belonging to another origin year.**  
   **Evidence:** [04.2-02-PLAN.md:100](/home/user/ERP_PLANT8_260917/.planning/phases/04.2-notify-holidays-foundation/04.2-02-PLAN.md:100), T3; [04.2-06-PLAN.md:116](/home/user/ERP_PLANT8_260917/.planning/phases/04.2-notify-holidays-foundation/04.2-06-PLAN.md:116), T1; [04.2-06-PLAN.md:117](/home/user/ERP_PLANT8_260917/.planning/phases/04.2-notify-holidays-foundation/04.2-06-PLAN.md:117), T3.  
   Spillover searches now account for the next year’s statutory dates, but neither generation nor recomputation supplies substitutes belonging to another origin year as occupied dates. With sufficient manual blockers, two origin-year calculations can choose the same substitute date. `ON CONFLICT (date) DO NOTHING` then silently drops one obligation while generation is marked complete. Calendar locking serializes this incorrect calculation; it does not resolve the collision.  
   **Concrete fix:** allocate substitutes across affected origin years in chronological order using a shared occupied-date set, and recompute downstream allocations when an earlier one moves. Test both generation orders and blocker insertion/deletion where a spillover reaches another origin year’s substitute.
