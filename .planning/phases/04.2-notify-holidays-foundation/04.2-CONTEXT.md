## Implementation Decisions

> 이 페이즈의 결정은 모두 Phase 7 논의(2026-09-24, `.planning/phases/07-schedule-notify-audit/07-CONTEXT.md`)에서 이미 확정됐다. 새로 묻지 않고 04.2 몫만 옮겨 왔다. 참조가 끊기지 않도록 결정 번호는 D-7xx 원번호를 그대로 쓴다. 이 페이즈에서 새로 결정할 일이 생기면 D-7xx와 겹치지 않게 **D-42xx**를 쓴다.

### 이미 확정된 입력 (다시 묻지 않음 — 출처가 정본)
- **공휴일 표:** 관공서의 공휴일에 관한 규정 제2·3조(음력 변환·대체공휴일)로 후보를 규칙 생성 → 관리자가 검토·확정, 임시공휴일·선거일만 수동 추가. 대상 2026·2027, 이후 매년 자동 생성. 영업일 = 월~금 중 공휴일 아닌 날 — `docs/inputs/phase-07-schedule-notify.md` §1, ADMN-11
- **한 표 원칙:** 지급일·결재 마감·알림은 같은 공휴일 표와 같은 파생 날짜를 읽는다(260907 「알림만 목요일 고정」 버그 재발 방지). 이 페이즈는 표·영업일 함수와 알림 tick까지 만들고, 지급일·마감이 이 함수를 쓰는 일은 Phase 7이다 — 입력 §1
- **알림 발송:** 하루 1번 오전 9시(KST), Cloud Scheduler → `/internal/notify-tick` 단일 엔드포인트, 채널 = 앱 알림함 + 이메일, `notification_log` 유니크 제약(INSERT … ON CONFLICT DO NOTHING), advisory lock으로 동시 실행 방지, Google OIDC ID 토큰 검증(audience = 서비스 URL, 이메일 = 스케줄러 서비스 계정, 실패 401 + 로그), 건수 상한(설정) 배치 + `{sent, skipped, remaining}` 응답, 남은 건은 다음 tick이 잇는다. 큐 없음 — 입력 §4, NOTI-04, ROADMAP 04.2 기준 4
- **조건 종류 틀:** 알림 조건 종류는 코드에 등록하는 틀로 두고, 이 페이즈는 **테스트 전용 조건 종류** 하나로 tick을 증명한다. 실제 조건 종류·기본 규칙은 Phase 7(NOTI-03) — ROADMAP 04.2 기준 4
- **이메일:** 회사 Google 계정 SMTP, 환경 변수 4개(`SMTP_HOST`·`SMTP_USER`·`SMTP_PASSWORD`·`SMTP_FROM`, `lib/env.ts` 72~75행에 선택값으로 정의만 있음), 발송 실패는 알림함 + 관리자 배너에 남는다 — 입력 §8, NOTI-02
- **배포:** 스케줄러 잡·서비스 계정은 `scripts/deploy.sh`가 만들고, OIDC 검증을 끄는 환경 변수가 있으면 배포가 거부된다(Issue 6). 관리자 시스템 상태 화면에 마지막 tick 시각·결과가 더해진다(18A) — ROADMAP 04.2 기준 4

### 공휴일 미확정 연도 (Phase 7 D-705 중 04.2 몫)
- **D-705 (앞부분):** **다음 해 공휴일이 아직 확정 전이면 규칙으로 만든 후보 표로 계산하고, 관리자에게 확정 요청 배너를 띄운다.** 통합 테스트: 다음 해 미확정 → 관리자 배너. (뒷부분 「확정 시 그 해 자동 계산 지급일 다시 파생, 사람이 직접 적은 지급 예정일은 건드리지 않음」은 지급일이 생기는 Phase 7 몫이다.)

### 발송 방식
- **D-706:** **이메일은 사람마다 하루 한 통으로 묶는다.** 그날 tick에서 그 사람에게 생긴 알림을 한 통에 모아 보낸다. 알림함에는 건별로 남는다. 중복 방지(`notification_log`)는 건 단위 그대로다 — **Reversibility:** costly — 발송 단위(사람 × 날짜)가 발송 실패 기록·재시도·일 한도 계산의 단위가 된다
- **D-709 (뒷부분):** **주말·공휴일에는 발송하지 않고 다음 영업일 9시 tick에서 보낸다. tick 자체가 비영업일이면 아무것도 보내지 않고 `{sent: 0}`으로 끝난다.** 영업일 판정은 이 페이즈의 공휴일 표·영업일 함수를 쓴다. (앞부분 「N일 셈법은 조건 종류마다 다르다 — 결재 대기·지급 임박은 영업일, 나머지는 달력일, 조건 종류가 자기 단위를 가진다」는 실제 조건 종류가 생기는 Phase 7 몫이다. 단, 이 페이즈가 만드는 조건 종류 등록 틀은 조건 종류가 자기 날짜 단위를 가질 수 있는 모양이어야 한다.)

### 이메일 설정 (입력 §10 미정 7-B)
- **D-711:** **SMTP 확인이 안 끝났어도 진행한다.** 알림함부터 만들고, 이메일 채널은 SMTP 환경 변수 4개가 모두 채워지면 켜지는 구조로 둔다(= 기능 플래그는 환경 변수 채움 여부). SMTP 값이 없으면 이메일 채널은 관리자 시스템 상태에 「미설정」으로 보이고, 알림은 알림함으로만 간다. 발송 주소·인증 방식(앱 비밀번호 vs Workspace 릴레이)·일 한도는 사용자가 Workspace 관리자에게 확인할 미정 항목으로 남는다 — 이 결정은 그 값을 정하지 않는다. 테스트는 가짜 SMTP(어댑터 교체)로 한다: 한 사람에게 3건 → 메일 1통·알림함 3건, SMTP 값 없음 → 메일 0통·시스템 상태 「미설정」, 발송 예외 → 알림함 실패 기록과 관리자 배너

### 행동 로그 — 계정 잠금·해제
- **D-712:** **계정 잠금과 잠금 해제를 행동 로그에 남긴다**(사용자 결정 2026-09-24, 스레드 「Phase 1~3 재검증」; Phase 1 성공 기준 2의 미이행분). 지금은 서버 JSON 로그에만 남는다(`domain/auth/hooks.ts` 116행 `auth.lockout`, `domain/auth/accounts.ts` 105행 `auth.unlock`), `domain/action-log/record.ts`의 `CORE_ACTION_TYPES`에 잠금·해제 종류가 없다. 설계 주의: 잠금은 로그인 전에 일어나 `recordAction`에 넘길 로그인한 행위자가 없다 — 행위자 표현(시스템 행위자 + 대상 이메일 등)은 계획이 정한다. 해제는 관리자 행위자가 있다. `recordAction` 호출은 Phase 4 플랜 04-32가 바꾸는 시그니처(tx 전달)에 맞춘다. 통합 테스트: 로그인 N회 실패 → 잠금 행동 로그 1건, 관리자 해제 → 해제 행동 로그 1건. 상세는 `.planning/phases/01-deploy-skeleton-login/01-VERIFICATION.md`(초안 PR #44, 브랜치 `claude/project-thread-pajnzt`)

### 계획이 정할 것 (ROADMAP 04.2 — 사용자에게 다시 묻지 않고 계획이 근거와 함께 정한다)
- REQUIREMENTS 추적표의 ADMN-11·NOTI-01·NOTI-02·NOTI-04 네 줄을 Phase 7 → Phase 04.2로 옮기는 일
- Phase 4(0011~0016)·04.1(0017부터 쓸 수 있음)과 겹치지 않는 마이그레이션 번호, `db/migrations/meta/_journal.json` 충돌을 푸는 방식
- `notification_log` 유니크 키가 Phase 7 독촉(D-707·D-708: 회차·받는 사람)을 막지 않는 모양
- 건수 상한과 사람별 하루 한 통 묶음(D-706)을 함께 지키는 방식 — 상한을 넘긴 건을 언제 보내는지 포함
- 공휴일 후보를 매년 만드는 계기(tick·배포·관리자 화면 진입 등)
- `/internal/notify-tick` 경로가 Cloud Run 엣지에서 살아남는지(`/healthz`는 엣지가 먹어서 헬스 체크를 `/api/health`로 옮긴 전례)
- Workspace SMTP 릴레이의 앱 비밀번호·발송 한도 확인(ROADMAP 기준 3) — 값은 사용자 몫(D-711), 계획은 확인 경로와 미설정 상태의 동작만 정한다

### Claude's Discretion
- 음력 변환 데이터는 외부 API 키 없이 쓸 수 있는 방식(코드 내장 표 등)을 연구 단계가 고른다
- 알림함 읽음 처리 방식·보관 기간, 묶음 메일의 모양(제목·본문 구성), 발송 실패 재시도 횟수는 계획이 정한다
- 잠금 행동 로그의 행위자 표현(D-712)
