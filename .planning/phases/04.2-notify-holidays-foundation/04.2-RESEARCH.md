## Summary

Phase 04.2 builds five independent-but-coupled pieces on top of Phase 3's settings registry / action log / admin system status: (1) a rule-generated Korean holiday table with admin review, (2) a pure business-day domain function everything else reads, (3) an in-app notification inbox with unread badge, (4) a single `/internal/notify-tick` endpoint that Cloud Scheduler calls once a day, dedup'd via a `notification_log` unique constraint and serialized via a Postgres advisory lock, fanning out to the inbox and to one bundled email per person per day, and (5) two new action-log entries (account lockout / unlock) closing a Phase 1 gap.

The single highest-risk technical finding is **not** about holiday math — it is that this repo's Drizzle migration runner (`drizzle-orm@0.45.2`) does not track "which migrations have been applied" as a set; it tracks only the **single latest applied timestamp** and applies any journal entry whose `when` exceeds it. Because Phase 4, Phase 04.1, and Phase 04.2 are three branches generating migrations in parallel and merging in an unknown order, a naive "reserve number range 0020+" plan is unsafe: a migration generated *early* (small `when`) but merged *late* — after a database has already applied a *later-generated* migration from a sibling phase — will be **silently skipped forever**, not rejected, not logged as an error. The coordinating Phase 04.1 planning session independently found the same defect and proposed a shared guard test + regenerate-before-merge protocol; this research confirms that finding against the installed package source and folds it in as the primary recommendation (see Pitfall 1 and Code Examples).

**Primary recommendation:** Don't hand-number 04.2's migrations. Use `pnpm db:generate` normally, add (or reuse, if 04.1 lands first) `test/unit/db/migration-journal.test.ts` as a CI guard, and make "rebase onto main, delete own migration artifacts, regenerate" the last task before merging the migration-bearing plan — this is safer than reserving 0020+ and is what actually prevents silent data-loss in staging.

**Package legitimacy note on `nodemailer`:** the seam's automated verdict (below) says `SUS` with reason `too-new`, but that reading is an artifact — it compares against the *latest patch release* date (2026-09-14), not the package's actual first-publish date. `npm view nodemailer time.created` returns **2011-01-21** [VERIFIED: npm registry] — nodemailer is one of the oldest, most widely used Node SMTP clients (current major 10.0.10). Treat this one as `OK` on manually-verified evidence, not the raw seam verdict. This package is still tagged `[ASSUMED]` name-provenance-wise per the protocol (discovered via training knowledge, not Context7/official docs) and needs a `checkpoint:human-verify` task before install regardless of the manual override, per CLAUDE.md's "new dependency = reason + approval" rule.

**No-new-dependency alternative:** hand-write a minimal SMTP client using `node:tls`/`node:net` (SMTP is a simple line protocol; Workspace SMTP needs `AUTH LOGIN` + STARTTLS on port 587). Cost: real, non-trivial protocol code (STARTTLS upgrade, base64 AUTH LOGIN, RFC 5322 message formatting, error-code parsing) that becomes this project's problem to maintain and secure — this is squarely the "don't hand-roll" pattern this project's own conventions flag. Recommend `nodemailer` and get explicit approval; if declined, budget significantly more plan time for the hand-rolled client and its tests.

## Architecture Patterns

### System Architecture Diagram

```
Cloud Scheduler (cron: 09:00 Asia/Seoul, daily)
   │  POST /internal/notify-tick
   │  Authorization: Bearer <OIDC ID token>  (aud = service URL, iss = accounts.google.com)
   ▼
app/internal/notify-tick/route.ts  ── verify token (google-auth-library OAuth2Client.verifyIdToken)
   │  reject (401 + log) if: missing token / bad audience / email != scheduler SA
   ▼
domain/notify/tick.ts  run(viewer=SYSTEM_VIEWER)
   │
```

### Pattern 4: Advisory lock — `pg_try_advisory_xact_lock` inside `db.transaction()`, not a session-level lock
**What:** No advisory-lock usage exists anywhere in this repo yet (`grep -rn "advisory"` returns nothing) — this is new. `db.execute(sql...)` is the established pattern for raw SQL not expressible in the query builder [VERIFIED: repositories/health.ts:7 `db.execute(sql`select 1`)`; repositories/system-status.ts:12,19].
**Why transaction-scoped, not session-scoped:** Cloud Run + `pg.Pool` pooling means a "session" (physical connection) can be silently returned to the pool and reused by an unrelated request if you don't release the lock explicitly (`pg_advisory_lock`/`pg_advisory_unlock` pairing is easy to leak on an unhandled exception). `pg_try_advisory_xact_lock` auto-releases at transaction COMMIT or ROLLBACK regardless of how the transaction ends, which is safer for a serverless/pooled environment.
**Example (sketch):**
```typescript
// domain/notify/tick.ts
import { sql } from "drizzle-orm";
import { db } from "@/db/client"; // domain importing db directly violates the boundaries ESLint rule
// (domain -> [domain, repositories, lib] only) — this must go through a small
// repositories/notify-lock.ts wrapper, same shape as lib/db-transaction.ts's withTransaction().

export async function runTick(): Promise<TickResult> {
  return withTransaction(async (tx) => {
    const [{ locked }] = await tx.execute<{ locked: boolean }>(
      sql`select pg_try_advisory_xact_lock(hashtext('notify-tick')) as locked`,
    );
    if (!locked) return { sent: 0, skipped: 0, remaining: 0, locked: true };
    // ... evaluate conditions, insert notification_log rows, fan out email ...
  });
}
```
**Caveat:** `lib/db-transaction.ts`'s exported `DbOrTx` type is deliberately narrowed to `Pick<typeof db, "insert" | "update" | "select">` [VERIFIED: db/client.ts:48 `export type DbOrTx = Pick<typeof db, "insert" | "update" | "select">;`] — it does not include `execute`. The tick's own repository function needs either its own wider type or to call `db.execute`/`tx.execute` directly rather than going through the shared `DbOrTx` alias; this is a real typing decision the plan must make explicitly, not copy blindly from `document-counters.ts`'s pattern.

### Anti-Patterns to Avoid
- **Building a notification queue table:** CONTEXT.md explicitly locks "큐 없음" — the tick re-evaluates live conditions every call; "remaining" items are simply conditions that are *still true* next tick, not rows sitting in a queue waiting to be popped. Do not add a `notification_queue` table.
- **Hand-numbering migration files/journal entries to "reserve" 0020+:** see Pitfall 1 — this does not prevent the actual failure mode and creates a false sense of safety.
- **Treating a failed email send as blocking the notification_log unique constraint:** the inbox item (channel: app) must still be created and readable even if the email channel fails — email delivery status is a separate column/flag on the same row, not a gate on whether the row gets inserted at all (D-711's own test spec: "발송 예외 → 알림함 실패 기록과 관리자 배너" implies the inbox side already succeeded).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|--------------|-----|
| SMTP protocol (STARTTLS, AUTH LOGIN, MIME) | Custom `node:tls` SMTP client | `nodemailer` (pending approval) | Protocol edge cases (charset encoding, line-length folding, auth mechanism negotiation) are exactly the "hand-rolled and later regretted" category |
| OIDC ID-token verification (JWT signature, JWKS rotation, audience/issuer checks) | Manual JWT decode + Google public-key fetch | `google-auth-library`'s `OAuth2Client.verifyIdToken` (already installed) | Google rotates its signing keys; a hand-rolled verifier either hardcodes keys (breaks on rotation) or reimplements JWKS caching — the library already does both correctly |
| Lunar→solar calendar conversion for all cases | Full lunisolar calendar algorithm | Bounded embedded table (3 dates/year, from KASI data) | Only 3 lunar-based holidays exist in the regulation; a full algorithm is solving a much bigger problem than this phase needs |
| Concurrent-tick protection | Application-level mutex / Redis lock | Postgres `pg_try_advisory_xact_lock` | Database is already the shared coordination point; no new infrastructure (Redis) needed for a once-a-day, single-endpoint lock |

**Key insight:** every "don't hand-roll" item above already has a project-approved or trivially-approvable answer that avoids adding *infrastructure* (no Redis, no queue) while still avoiding hand-rolled *protocol* code (SMTP, JWT/OIDC) — the phase's only genuinely new dependency is `nodemailer`.

## Common Pitfalls

### Pitfall 1: Migration-journal "reserve a number range" plan does not prevent silent migration loss
**What goes wrong:** An early planning draft proposed reserving number ranges per phase (e.g. Phase 4: 0011–0016, Phase 04.1: 0017–0019, 04.2: 0020+). This looks safe but is not, because of how the installed migrator actually decides what to apply.
**Why it happens — verified mechanism:**
- `pnpm db:generate` (`drizzle-kit@0.31.10`) computes the next migration's `idx` as `journal.entries[journal.entries.length - 1].idx + 1` — i.e., **the last array entry in the locally checked-out `_journal.json`**, not a scan of existing `.sql` filenames or numeric tags [VERIFIED: `node_modules/.pnpm/drizzle-kit@0.31.10.../drizzle-kit/bin.cjs:32926-32927` — `const lastEntryInJournal = journal.entries[journal.entries.length - 1]; const idx = typeof lastEntryInJournal === "undefined" ? 0 : lastEntryInJournal.idx + 1;`]. Running `db:generate` today, before Phase 4's 0011–0016 exist on `main`, produces `0011_*.sql` regardless of the reserved range — a direct numeric collision waiting to happen at merge time.
- At apply time, `drizzle-orm/pg-core/dialect.js`'s `migrate()` reads the **single most recent** applied migration (`select ... order by created_at desc limit 1`) *once*, then iterates the journal's migrations **in array order**, applying any whose `folderMillis` (= the journal entry's `when` field, a real wall-clock timestamp assigned at `db:generate` time) is strictly greater than that one recorded value [VERIFIED: `node_modules/.pnpm/drizzle-orm@0.45.2.../drizzle-orm/pg-core/dialect.js:44-72`, specifically lines 56-62: `const dbMigrations = await session.all(sql\`select id, hash, created_at from ... order by created_at desc limit 1\`); const lastDbMigration = dbMigrations[0]; ... for await (const migration of migrations) { if (!lastDbMigration || Number(lastDbMigration.created_at) < migration.folderMillis) { /* apply */ } }`]. There is **no hash-set membership check** — only this one timestamp comparison.
- Consequence: if a branch's migration is generated *early* (small `when`) but sits unmerged while a sibling phase's migration — generated *later* (larger `when`) — merges and deploys first (this repo auto-migrates on every merge to `main`: `git push(main) → ... → migrate Job` [VERIFIED: docs/ARCHITECTURE.md §6 pipeline diagram, lines ~217-224]), then when the early-generated branch finally merges, its `when` is now **less than** the DB's recorded max `created_at`. The migrator's loop condition is false for that migration — it is **silently skipped**, no error, no log line beyond the normal "0 new migrations" case. The application code that depends on that migration's table will then 500 in staging with no obvious cause. Reserving a numeric range does nothing to prevent this — the failure is keyed on `when` (generation wall-clock time), not on the filename's number.
**How to avoid — shared protocol (confirmed independently by the Phase 04.1 planning session, cross-checked here against the same source lines):**
1. Generate normally with `pnpm db:generate` — no hand-editing of `idx`/`tag` values, no manual renumbering to "claim" 0020.
2. Add a guard unit test, path **`test/unit/db/migration-journal.test.ts`** (shared name — if Phase 04.1 lands it first, 04.2 reuses the same file and does not duplicate), asserting: `idx` values are exactly `0..N-1` with no gaps and no duplicates, each `tag` prefix is the zero-padded `idx`, and `when` values are strictly increasing by array position. This makes a bad merge fail CI loudly instead of failing silently in staging.
3. As the **last task** before merging the plan that carries the migration: merge `origin/main` (merge only — no rebase or history rewrite, per 04.2-14 D-4215), delete the branch's own draft migration `.sql` file, its `meta/*_snapshot.json`, and its `_journal.json` entry, then re-run `pnpm db:generate` against the now-current `main`. This produces a fresh `when` (close to actual merge time) and a correct `idx` continuing from whatever already merged — resolving both the numbering collision and the stale-timestamp hazard in one step, with no manual arithmetic.
4. No numeric range is reserved for any phase. Each phase runs `pnpm db:generate` on its own branch and gets whatever `idx` its local `_journal.json` produces; the only rule that matters is step 3 (regenerate-at-merge-time against a fetched, pinned `origin/main` SHA) plus the shared `test/unit/db/migration-journal.test.ts` guard, which is what actually fixes the final `idx`/`when` values.
**Warning signs:** a migration merges cleanly, CI (which runs against a fresh test DB, always starting from `created_at` unset) passes, but staging (which has an existing `created_at` high-water mark from whatever merged most recently) never shows the new table. CI passing is not sufficient evidence this class of bug is absent, because a fresh test DB has no prior high-water mark to collide with — **the guard test in step 2 is the only automated check that catches it before staging.**

### Pitfall 2: Action-log's three-array rule applies to lockout/unlock too
**What goes wrong:** adding `"account_lock"`/`"account_unlock"` to `CORE_ACTION_TYPES` without also updating `ACTION_TYPE_LABELS` and (if they should be un-disableable, which locks/unlocks — a security-relevant event — almost certainly should be) `ALWAYS_ON_ACTION_TYPES` leaves the UI showing a raw snake_case token, or lets the event be silently disabled via the settings registry.
**Why it happens:** exactly the failure mode the code's own comment warns about — "04-RESEARCH.md Pitfall 2 — 하나만 고치면 조용히 어긋난다" [VERIFIED: domain/action-log/record.ts comment at CORE_ACTION_TYPES definition, lines 20-22].
**How to avoid:** one plan task touches all three arrays together (`CORE_ACTION_TYPES`, `ACTION_TYPE_LABELS`, and — recommend — add both new types to `ALWAYS_ON_ACTION_TYPES` since a lockout event is a security signal, not an optional audit nicety) plus `test/integration/leak-scan.test.ts`'s registry side-effect imports if a new DTO is introduced for the notification/holiday screens.
**Recommended actor design for D-712's pre-login lockout event:** reuse `SYSTEM_VIEWER` (already exists: `{ id: "system", roleId: SYSADMIN_ROLE_ID }` [VERIFIED: domain/viewer.ts]) as the `recordAction` caller — `recordAction` already special-cases `viewer.id === SYSTEM_VIEWER.id` to write `actorId: null` [VERIFIED: domain/action-log/record.ts, `recordAction` body], which is the correct representation for "no logged-in actor did this." The locked-out account's email goes in `entry.detail` (e.g. `{ email }`) since `entity`/`entityId` are reserved for the polymorphic document/entity reference convention (Pattern 2 above) and a pre-existing user record may not even be the right target (the email is attempted, not necessarily a valid account). Call site: `domain/auth/hooks.ts`'s `after` hook, right next to the existing `log.info("auth.lockout", ...)` call [VERIFIED: domain/auth/hooks.ts — the `if (isLocked(count, threshold))` branch inside `after`]. Unlock already has a real admin `Viewer` available in `unlockAccount(viewer, email)` [VERIFIED: domain/auth/accounts.ts `unlockAccount`] — no new actor problem there, just add the `recordAction` call using the tx-aware signature (Pitfall 4 below).

### Pitfall 3: `recordAction`'s transaction signature is a moving target — match Phase 4's 04-32 shape, don't invent your own
**What goes wrong:** `main`'s `recordAction`/`appendActionLog` do not currently take a `tx` parameter — writes always go through the module-level `db` [VERIFIED: domain/action-log/record.ts on `main`, no `tx` field on `RecordActionDeps`; repositories/action-log.ts on `main`, `appendActionLog(viewer, entry): Promise<ActionLogRow>` with no third parameter]. Phase 4's in-flight branch (`origin/claude/gsd-progress-e1nzgu`, plan 04-32) adds an optional `tx?: DbOrTx` to both, threaded through so a caller inside a locked transaction can log in the same transaction [VERIFIED: `git show origin/claude/gsd-progress-e1nzgu:domain/action-log/record.ts` — `RecordActionDeps.tx?: DbOrTx`, `recordAction`'s `appendActionLog(viewer, {...}, deps?.tx)` call, and `git show origin/claude/gsd-progress-e1nzgu:repositories/action-log.ts` — `appendActionLog(viewer, entry, tx?: DbOrTx): Promise<ActionLogRow>` with `(tx ?? db).insert(...)`].
**Why it matters here:** 04.2's advisory-lock tick runs inside `db.transaction()` (Pattern 4) and, if it ever calls `recordAction` from inside that transaction (e.g., to log holiday confirmation or a tick-triggered event), must pass `deps: { tx }` — using the plain (no-tx) call from inside a locked transaction would open a second pool connection and could deadlock against the advisory lock held by the outer transaction.
**How to avoid:** whichever of Phase 4 or 04.2 merges to `main` second must rebase onto the merged shape of `record.ts`/`repositories/action-log.ts` (same class of hazard as the migration journal, but for a shared source file rather than a shared data file) — this is explicitly called out as a shared-registry merge risk in the Phase Boundary section of 04.2-CONTEXT.md. Do not re-derive an independent tx-threading design; match 04-32's shape exactly so whichever branch lands second is a clean rebase, not a redesign.

### Pitfall 4: Confirming this year's holiday table late in the year breaks last year's already-derived dates
**What goes wrong (forward-compat, not this phase's own bug, but a design trap 04.2's function shape can create for Phase 7):** if `isBusinessDay`/`addBusinessDays` implicitly regenerate candidates every call instead of reading confirmed rows first, a mid-year rule change (e.g., a newly-announced temporary holiday, 임시공휴일) could retroactively change *past* business-day calculations that already had consequences (a payment already marked "on time" against the old calendar). D-705's own text is explicit that only forward-looking derived dates should reflow on confirmation, not backdated ones — that's Phase 7's job, but 04.2's `business-day.ts` function shape needs to make "read the confirmed table for date X" the only code path other domains call, with candidate-generation strictly a separate, admin/tick-triggered side effect, never inlined into the read path in a way that could silently write.
**How to avoid:** `ensureHolidayCandidates(year)` (write path, admin-screen-page-load or tick-triggered) and `isBusinessDay(date)` / `addBusinessDays(date, n)` (pure read path, reads whatever rows exist — confirmed or candidate — for that date) must be two separate exported functions, never one function that generates-then-reads inline. This is a design note for the plan's function signatures, not a verified defect.

### Yearly holiday-candidate generation trigger — lazy, idempotent, no dedicated cron
```typescript
// domain/holidays/candidates.ts (sketch — design recommendation, no in-repo precedent)
export async function ensureHolidayCandidates(viewer: Viewer, year: number): Promise<void> {
  const existing = await findHolidaysForYear(viewer, year);
  if (existing.length > 0) return; // idempotent — already generated (confirmed or candidate)
  const candidates = generateCandidates(year); // pure, rule-based (제2·3조 + embedded lunar table)

```
Call this from **both** the tick (needs the current year's table to answer `isBusinessDay`) and the admin holiday screen's server-side data load (so an admin visiting the screen for the first time in a new year sees candidates immediately, without waiting for tomorrow's 9am tick). ### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|------------------------|
| Forged/replayed OIDC token calling `/internal/notify-tick` to trigger spam-notification floods or DoS the SMTP quota | Spoofing / Denial of Service | `google-auth-library` verifies signature + audience + expiry; additionally check `payload.email` equals the exact expected Scheduler service-account email (not just "any valid Google-signed token") — a valid-but-wrong-audience token from a different Google Cloud project must not pass |
| `scripts/deploy.sh` deploying with OIDC verification accidentally disabled via an env var | Tampering / Elevation of Privilege | CONTEXT.md already locks this: "OIDC 검증을 끄는 환경 변수가 있으면 배포가 거부된다" — the plan must implement `deploy.sh` refusing to deploy if that flag is set, mirroring the existing pattern where `deploy.sh` already refuses on pool-rule violations (`exit 3`) [VERIFIED: test/integration/migrate-runner.test.ts shows the existing exit-code-based refusal pattern for `deploy.pool_rule_violation`] |
| Advisory lock never released due to a crashed connection, wedging the tick forever | Denial of Service | `pg_try_advisory_xact_lock` (transaction-scoped, not session-scoped) auto-releases on any transaction end (commit, rollback, or connection close by Postgres itself) — do not use the session-scoped `pg_advisory_lock`/`pg_advisory_unlock` pair, which requires explicit unlock and can leak on unhandled exceptions in a pooled environment |
| Notification content leaking cross-recipient (e.g., a bundled email accidentally including another person's items) | Information Disclosure | the "group by recipient_id, one email per group" step must partition strictly on `recipient_id` before composing — a unit test asserting no email body contains another recipient's `entity_id` is cheap insurance, recommend adding it |
