## S1 — 알림함 + 안 읽은 알림 배지 (NOTI-01)

§7-12 계약(읽음/안 읽음 인셋, 「내 차례」와의 경계, 진입점, 배지는 안 읽은 수 하나만 셈, 다섯 상태)은 **그대로 따른다.** 아래는 §7-12가 비워 둔 칸이다.

### S1-a. 배지: 상단 바 사용자 트리거 (PC·폰 공통)

진입점이 메뉴 안(§6-0 (a))에 있다. 그래서 메뉴를 열지 않아도 보이는 자리는 사용자 트리거 하나뿐이다.

```
PC   │▓PLANT8   프로젝트 지출결의 법인카드 결재 손익      ⌘K   박서연 [3]▓│
폰   │▓PLANT8                              박서연 [3]  ≡▓│
```

- 모양은 §7-5 상태 태그와 같다. `--fs-xs` 600, `1px solid currentColor`, 패딩 `1px 6px`, radius 0, 배경 없음, `tabular-nums`. 글자색은 `--bar-fg`다. 이름과의 간격은 `--s-2`(8px)다.
- 안 읽은 알림이 **0이면 배지를 렌더하지 않는다**(`0`을 쓰지 않는다). 1~99는 숫자 그대로, 100 이상은 `99+`다.
- 접근성: 배지 글자는 `aria-hidden="true"`다. 트리거 안에 시각적으로 숨긴 글자(`.sr-only`)로 ` · 안 읽은 알림 {N}건`을 넣는다. **N은 실제 수다** — 보이는 글자가 `99+`여도 134건이면 `134건`이다. 그러면 트리거의 접근 가능 이름은 「박서연 · 안 읽은 알림 134건」이 된다. 0이면 이 글자도 없다.
- 폰에서 트리거는 지금처럼 최소 44×44다. 배지 때문에 트리거가 이름 줄 밖으로 넘치면 이름을 말줄임한다. 배지는 자르지 않는다.
- **하단 탭(「내 차례 N」, 「더보기」)에는 배지를 달지 않는다.** §7-12 E④에 따라 건수를 세는 자리를 나누어 쓴다.
- 갱신: 실시간 갱신·폴링은 없다. 첫 값은 레이아웃이 서버에서 세고, 경로가 바뀔 때마다 클라이언트 경계 `UnreadCountProvider`가 안 읽은 수를 다시 받는다(D-4219 — 레이아웃은 클라이언트 이동에서 다시 렌더되지 않는다). 다시 받는 동안 표시는 없고 이전 값이 남는다. 다시 받기가 실패하면 이전 값을 유지한다. 알림은 하루 한 번 09:00 tick으로만 생긴다. 알림함을 열어 읽음 처리한 직후에는 같은 화면에서 배지가 사라져야 한다(읽음 액션 뒤 같은 경계가 다시 받는다). E2E 「배지 1 → 열람 → 배지 0」이 이 동작을 확인한다.

### S1-b. 메뉴 항목: 「알림함 N」

- `role-menu.ts`의 `accountGroup` **맨 앞**에 `{ kind: "link", label: "알림함", href: "/notifications" }`을 넣는다. 두 표면이 이 순서를 같이 쓴다.
  - PC 사용자 메뉴: `관리`(권한 있을 때) · `알림함 3` · `내 정보` · `로그아웃`
  - 폰 「더보기」 시트의 「계정」 그룹: `알림함 3` · `내 정보` · `설정` · `로그아웃`
- 건수는 BottomTabs의 `내 차례 3`과 같은 방식으로 라벨 뒤에 공백 하나를 두고 붙인다: `알림함 3`. 0이면 `알림함`이다. 100 이상은 `알림함 99+`다.
- 행 모양·높이·포커스(전체 폭 목록 행의 안쪽 링)는 기존 메뉴 행 그대로다. 아이콘은 없다.

### S1-c. 알림함 화면 `/notifications`

로그인한 모든 사용자가 쓴다. 템플릿은 §6-1 목록이다. 「내 차례」 블록은 없고, 필터 줄도 없다.

```
PC / 폰 공통 (칸이 둘뿐이라 폰에서도 칸을 접지 않는다)
│ 알림함                                         │ ← PageHeader, 부제 없음
╞════════════════════════════════════════════════╡
│    내용                                   시각 │ ← 머리글 --fs-sm --muted 600, 아래 1px --line-strong
├────────────────────────────────────────────────┤
│ 09-24                                          │ ← 그룹 머리글(날짜)
┃ 아이오닉9 무대설치 지출결의 — 증빙 14일 경과     09:00 │ ← 안 읽음: 왼쪽 인셋 2px --line-strong
┃ 한빛무대예술 지급 예정일 D-1                   09:00 │
│ 09-23                                          │
│ 테스트 알림 · T-0001                     09:00 │ ← 읽음: 인셋 없음
│   이메일 발송 실패                              │ ← 보조 줄 --fs-sm --muted
│ …                                              │
│ 더 보기 50건                                    │ ← 3차 버튼(§6-1)
```

- 표: 읽기용 `<table>` + 시각적으로 숨긴 `<caption>알림함</caption>`(§10). 칸은 **내용**(문자, 왼쪽 정렬, 줄바꿈 허용)과 **시각**(`HH:MM`, 오른쪽 정렬, `tabular-nums`, nowrap) 둘이다. 둘 다 P1이다. 폰에서도 칸을 접지 않는다(P1은 최대 3칸, §7-3).
- 그룹 머리글 행은 받은 날짜로 묶는다. 올해 날짜는 `09-24`, 다른 해는 `2025-12-30`이다(§2-4). 최신이 위다. 모양은 §7-3 그룹 머리글 행 규칙 그대로다(`--fs-sm --muted` 600, 위 12px, 아래 1px `--line-strong`). 마크업: 날짜마다 `<tbody>` 하나, 그 첫 행에 `<th scope="rowgroup" colSpan={2}>`(행 묶음의 머리글이다. `colgroup`이 아니다).
- **안 읽은 행:** 첫 칸에 `box-shadow: inset 2px 0 0 var(--line-strong)`을 준다(§7-12 E①의 「좌측 인셋 선」, §4-3의 인셋 선 허용 목록에 한 줄 더한다). 첫 칸 안에 시각적으로 숨긴 글자 `안 읽음 · `를 넣는다. §10 「색은 의미의 유일한 매체가 아니다」를 지키기 위해서다. 글자 굵기는 바꾸지 않는다(400).
- **이메일 발송 실패 기록(NOTI-02 「알림함에 남는다」):** 이메일 발송이 실패한 행에만 내용 칸 안 두 번째 줄로 `이메일 발송 실패`를 쓴다(`--fs-sm --muted`, 외화 2행과 같은 모양). 받는 사람이 할 일은 없어서 `--danger`가 아니고 다음 한 수도 없다. 이메일이 미설정이거나 발송에 성공하면 아무것도 쓰지 않는다. 결과 불명 행(`unknown`·`sending`)에는 아무것도 쓰지 않는다(받는 사람이 할 일이 없다).
- 행은 링크가 아니다. 이 페이즈의 조건 종류는 테스트용 하나뿐이다. 행을 관련 문서로 잇는 일은 실제 조건 종류가 생기는 Phase 7이 정한다. 다음 한 수 버튼은 두지 않는다(§7-12 E②).
- 목록 길이: 처음 50건이고, 그 아래에 3차 `더 보기 50건`을 둔다(§6-1, 페이지네이션 없음). 보관 기간(계획이 정한다)이 지난 알림은 목록에서 조용히 빠진다. 보관 기간은 화면에 적지 않는다(§8-5 안내 문구 없음).
- **`더 보기 50건`의 상태:**
  - 요청 중: 이미 보이는 행은 그대로 두고 버튼만 비활성이다(§7-1 대기 규칙).
  - 성공: 새 행이 아래에 붙는다. 더 있으면 버튼이 남는다(포커스는 버튼에 남는다). 마지막 쪽이면 버튼이 사라지고 **포커스는 새로 붙은 첫 행**으로 간다(버튼이 사라져 포커스를 잃지 않게).
  - 실패: 이미 보이는 행은 그대로이고, 버튼 자리에 `--fs-sm --danger` `불러오지 못했습니다` + 3차 `다시 시도`를 쓴다. `다시 시도`는 같은 커서로 다시 요청한다.
- 1차 버튼은 없다. 「모두 읽음」 버튼도 없다(아래 읽음 처리 참고).

### S1-d. 읽음 처리 (CONTEXT 「Claude's Discretion」, 여기서 정한다)

- **알림함 화면을 열면 그 사람의 안 읽은 알림이 모두 읽음이 된다.** 행마다 읽음 버튼을 두지 않는다. 「모두 읽음」 버튼도 두지 않는다.
- 이번 방문 동안에는 **연 순간에 안 읽음이었던 행에 인셋 선이 남는다.** 무엇이 새로 왔는지 보이게 하기 위해서다. 다음 방문이나 새로고침 때 선이 조용히 사라진다(§7-12 SUCCESS 「인셋 선이 조용히 사라지는 것으로 반영」). 방문 중에 `더 보기 50건`으로 불러온 행도 같은 기준(연 시점의 안 읽음 여부)으로 표시한다.
- 배지는 읽음 처리 직후 0이 된다(S1-a 갱신 규칙).
- 읽음 처리 액션이 실패해도 **화면에 오류를 띄우지 않는다.** 목록은 그대로 보이고 배지는 남는다. 다음 방문 때 다시 읽음 처리한다. 서버 로그에는 남긴다. 이유: 읽음 상태는 부수 정보이고, §7-12 SUCCESS·PARTIAL이 「해당 없음」이다.

|---|---|
| LOADING | §7-12: 목록 자리에 `--surface` 뼈대 행 3개. 반짝임과 스피너는 없다. 300ms 안에 끝나면 아무것도 보이지 않는다 |
| EMPTY | §7-12: `--muted` 한 줄 `알림이 없습니다`. 다음 한 수는 없다(DECISIONS 2026-09-20, `ListEmpty`에서 `action` 생략). 머리글은 렌더하지 않는다 |

## S2 — 공휴일 관리 `/admin/holidays` (ADMN-11)

SYSTEM.md에 정본이 없다. 새 템플릿을 만들지 않고, **§6-1 목록 + §6-1 관리자 마스터 등록 토글(`?new=1`, D-39) + §7-15 폼 + §7-3 폰 칸 접기**로 조립한다. 본보기는 `admin/corp-cards/page.tsx`다.

### S2-a. 진입점

- 메뉴 키는 `admin.holidays`(새, `domain/permissions/menus.ts`의 MENUS)다. 경로는 `/admin/holidays`다.
- 「관리」 인덱스(§6-10) **「마스터」 그룹 끝**에 라벨 `공휴일`로 넣는다: `사람 · 거래처 · 법인카드 마스터 · 코드표 · 공휴일`. 공휴일 표는 코드표처럼 날짜 행을 등록하고 관리하는 참조 데이터이고, 목록 + 등록 폼 모양도 마스터 화면과 같다. `role-menu.ts`의 `ADMIN_MENUS`와 SYSTEM.md §6-10 표를 **같은 변경에서** 고친다(단위 테스트가 두 쪽을 원소 단위로 대조한다).
- 권한: view가 없는 계급은 이 화면이 404다(D-17). view만 있고 write가 없으면 확정 버튼, 공휴일 추가 링크, 삭제가 **렌더되지 않는다**(비활성이 아니라 버튼 자체가 없다. 03-UI-SPEC과 같은 결).

- **화면 순서:** PageHeader → (폼, `?new=1`일 때만) → 필터 줄 → 연도 상태 줄 → (삭제 결과 줄, 삭제 직후에만) → 표. 폼 위치는 corp-cards 선례와 같다.
- **필터 줄**은 컨테이너 폭이다(표 위, §3). 왼쪽은 연도 목록이다. 공휴일 행이 있는 모든 연도를 오름차순으로 보인다. 화면을 열 때 올해와 다음 해의 후보는 이미 만들어져 있다(RESEARCH의 lazy `ensureHolidayCandidates`). 현재 연도는 링크가 아닌 `--fg` 글자 + `aria-current="page"`이고, 나머지는 3차 링크(`?year=2026`)다. 오른쪽은 3차 링크 `공휴일 추가`(`?year=…&new=1`)이고 폼이 열려 있으면 숨긴다. 줄 사이 간격은 `--s-4`, 위아래는 `--s-3`이다.
- **기본 연도**(`?year` 없음): 올해와 다음 해 중 확정 전인 가장 이른 해, 둘 다 확정이면 올해다.
- **연도 상태 줄**은 §7-3 (가) 「잠김」 한 줄과 같은 모양이다. 표 바로 위, `--fs-sm --muted`다. 상태 낱말은 `StatusTag variant="text"`로 쓴다.
  - 확정 전: `후보`(`--muted`) ` · 공휴일 {N}일`. 같은 줄 끝에 1차 `{연도}년 공휴일 확정`을 둔다. 폰에서는 줄 아래로 내려가 전폭이 된다(보이는 높이 40, 누르는 영역 44×44 이상).
  - 확정: `확정`(`--success`) ` · {YYYY-MM-DD HH:MM} {확정한 사람 이름} · 공휴일 {N}일`. 버튼은 없다.
  - N은 그 해 공휴일 행 수이고 수동 추가분을 포함한다. 「공휴일」을 붙여 날짜(「15일」)로 읽히지 않게 한다.
- **1차 버튼은 화면에 하나만 둔다(§7-1, SYSTEM.md §7-1 위계 표 「1차 1개」):** 폼이 열려 있으면(`?new=1`) 확정 버튼을 **렌더하지 않는다.** 그동안 1차는 폼의 `공휴일 추가`다. 연도 상태 줄의 글자는 남는다. 삭제에는 확인 단계가 없으므로(S2-f) 1차 버튼이 둘이 되는 순간이 없다.

### S2-c. 표

| 칸 | 내용 | 정렬 | 폰 우선순위 |
|---|---|---|---|
| 날짜 | `MM-DD`(연도는 필터가 말한다, §2-4). `tabular-nums`, nowrap. 모든 값이 같은 폭이라 정렬 방향으로 생기는 차이가 없다 | 왼쪽 | **P1** |
| 요일 | `월`~`일` 한 글자 | 왼쪽 | P2 |
| 이름 | 규칙 이름(`설날`, `설날 연휴`, `추석`, `개천절`…) 또는 관리자가 적은 이름. 대체공휴일은 원래 공휴일 이름을 쓴다(`개천절`). 대체라는 사실은 「구분」이 말한다 | 왼쪽, 줄바꿈 허용 | **P1** |
| 구분 | `법정 공휴일` · `대체공휴일` · `임시공휴일` · `선거일`. 글자만 쓰고 색·태그는 없다 | 왼쪽 | P2 |
| 동작 | 3차 `삭제`. **수동으로 넣은(임시공휴일·선거일) 행 가운데 날짜가 오늘보다 뒤인 행만.** 그 밖의 행은 칸이 비어 있다(§7-14 「이미 적용된 행은 동작 칸이 비어 있다」와 같은 원칙). write 권한이 없으면 칸 자체가 없다 | 왼쪽 | **P1** |

- 날짜 오름차순이고 그룹 머리글과 합계 행은 없다. 한 해가 15~20행이라 페이지를 나누지 않는다.
- 편집 셀이 없으므로 `role="grid"`가 아니라 `<table>` + `<caption className="sr-only">{연도}년 공휴일</caption>`이다. 머리글은 흰 바탕이다(§7-3 (가)).
- 규칙으로 만든 행(법정 공휴일·대체공휴일)은 **고치거나 지울 수 없다.** 검토란 목록을 보고 확정하는 것이다. 규칙 결과가 틀렸다면 고칠 곳은 코드 안 음력 표와 규칙이다. 이것을 관리자 화면에서 덮어쓰게 하지 않는다(아래 가정 U-3).

**폰 375px (§7-3 칸 접기):** P1은 날짜 · 이름 · 동작이다(문자 1 + 숫자 1 + 행동 1). P2는 각 행 아래 접힌 줄 하나로 들어간다. 모양은 `--fs-sm --muted`, 라벨 없이 `요일 · 구분`(예: `화 · 대체공휴일`)이다. 가로 스크롤과 카드 전환은 없다. 행을 눌러도 시트가 열리지 않는다(보일 정보가 접힌 줄에 이미 다 있다).

### S2-d. 공휴일 추가 폼 (`?new=1`, §7-15)

- `Form`(single-column 720, `noValidate`). 폰에서는 라벨이 위로 가고 칸은 전폭이다. `?new=1`로 열리면 **날짜 칸에 포커스를 둔다**(키보드로 바로 입력한다).

| 라벨 | 컨트롤 | 폭 | 규칙 |
|---|---|---|---|
| 날짜 | `TextField type="date"`, 자리표시자 없음. `min` = KST 내일, `max` = `{LUNAR_TABLE_LAST_YEAR}-12-31`(지금 `2035-12-31`). 선례 `admin/people/person-form.tsx` | 짧은 칸 280 | 내일 이후이고 음력 표 안의 해여야 한다. `noValidate`라 `min`·`max`는 제출을 막지 않고 키보드로는 범위 밖 값을 적을 수 있다. 마지막 관문은 서버의 칸 오류(카피 계약)다. 표시 형식은 브라우저 로캘을 따른다(네이티브 입력) |
| 종류 | `Select`: `임시공휴일`(기본 선택) · `선거일`. 빈 옵션 없음 | select 200 | 이 둘만 수동으로 넣을 수 있다(ADMN-11). 두 종류는 대체일 계산에서 같고 구분 글자만 다르다 |
| 이름 | `TextField`, 자리표시자 없음(형식 예가 없는 칸, §7-2) | 긴 칸 480 | 비어 있으면 안 된다 |

- `Form.Actions`: 1차 `공휴일 추가`. 오른쪽 끝 2차 `취소`는 `?year=…`로 돌아가는 링크다.
- 막힘(UX-06, §7-15 PARTIAL): 필수 칸(날짜·이름)이 비면 1차는 비활성이다. 바로 옆에 이유와 다음 한 수를 둔다. 예: `추가할 수 없음 — 날짜 · 이름 2칸 · 날짜 적기`. 이유 뒤의 다음 한 수(`날짜 적기` 등)는 **3차 버튼**이고, 누르면 첫 빈 칸으로 포커스를 옮긴다(§7-1 「이유 텍스트 + 다음 한 수 3차 버튼」). 1차 버튼의 `aria-describedby`가 이유 줄을 가리킨다(§7-15). 필수 표시 `*`는 쓰지 않는다. 막 연 빈 폼에도 이 줄은 보인다(§7-1 규칙). 포커스가 날짜 칸에 있어 바로 입력하면 된다.
- 제출 중: `공휴일 추가…`. 폼의 다른 버튼도 비활성이다. 300ms가 넘으면 상단 2px 진행 바를 띄운다(§7-1).
- 서버 검증 오류는 해당 칸 아래 `Form.Error`(`원인 · 다음 행동`)에 쓴다. 입력값은 지우지 않는다. 문구는 아래 카피 계약에 있다(음력 표 밖 해 포함).
- 성공(§7-15 SUCCESS, 화면이 바뀌는 폼): `?year={추가한 날짜의 연도}`로 이동하고 폼이 닫힌다. 새 행이 표에 들어간다. 토스트 `공휴일 추가 · 2027-06-03 추가됨`(4초).

### S2-e. 확정 (`{연도}년 공휴일 확정`)

- 확인 모달은 띄우지 않는다. §7-8 모달은 삭제·반려·덮어쓰기 같은 위험 행동을 확인할 때만 쓰는데, 확정은 파괴적인 행동이 아니고 이 화면의 주 행동이다.
- 제출 중: 라벨 `2027년 공휴일 확정…`, 비활성.
- 성공(화면 그대로, §7-7 SUCCESS 「행동한 자리」): 버튼이 사라진다. 연도 상태 줄이 `확정 · 2026-09-24 14:02 김관리 · 공휴일 15일`로 바뀐다. 토스트는 띄우지 않는다(화면 이동이 없다, §7-6). 같은 요청으로 D-705 배너 조건이 풀린다.
- 실패: 원래 라벨로 돌아오고 바로 옆에 `--fs-sm --danger` `확정하지 못했습니다 · 다시 시도`를 쓴다(§7-1 비활성 이유와 같은 자리).
- 동시 확정(두 관리자): 확정은 멱등이다. 뒤에 누른 사람도 성공 모양을 보고, 줄에는 먼저 확정한 사람과 시각이 남는다.
- 확정을 되돌리는 기능은 없다(아래 가정 U-2). 04.2에서 확정은 계산된 값을 바꾸지 않고 확정 기록과 B1 배너 해제만 하며, 확정 뒤에도 수동 행 추가·삭제는 된다. 그래서 확인 단계도 두지 않는다. 확정이 지급일을 다시 파생하게 되는 Phase 7에서 확인이나 되돌리기를 다시 본다.

### S2-f. 삭제 (수동으로 넣은 미래 행만) — 확인 대신 되돌리기

```
│ 후보 · 공휴일 15일                            [2027년 공휴일 확정]  │
│ 2027-06-03 제9회 전국동시지방선거 삭제됨  되돌리기                 │ ← --fs-sm --muted + 3차, role="status"
╞══════════════════════════════════════════════════════════════════╡
│ 날짜    요일  이름                      구분          동작       │
```

- **확인 단계가 없다.** 3차 `삭제`를 누르면 바로 지운다(CLAUDE.md §7 「확인 대신 되돌리기, 확인은 되돌릴 수 없는 일에만」). 같은 값으로 다시 넣으면 원래대로 돌아오는 일이라 되돌릴 수 있다.
- 대기 중: 그 행의 `삭제`가 `삭제…`로 바뀌고 비활성이다. 다른 행의 `삭제`는 그대로다.
- 성공: 화면을 서버에서 다시 그린다. 지운 행이 사라지고 재계산으로 바뀐 대체공휴일 행이 함께 보인다. 연도 상태 줄의 N은 다시 그린 그 해 행 수다. 토스트는 없다(화면 이동이 없는 행동, SYSTEM.md §7-6 토스트 규칙).
- 결과 줄: 연도 상태 줄과 표 사이에 한 줄 `{YYYY-MM-DD} {이름} 삭제됨` + 3차 `되돌리기`를 둔다(`--fs-sm --muted`, 간격 `--s-2`, `role="status"`). 포커스는 `되돌리기`로 간다(지운 행의 `삭제`가 사라지므로).
  - 줄은 하나뿐이다. 다른 행을 지우면 그 행의 줄로 바뀐다.
  - 시간이 지나도 사라지지 않는다. 연도를 바꾸거나, 공휴일 추가 폼을 열거나, 화면을 떠나면 사라진다.
- `되돌리기`: 지운 행과 **같은 날짜·이름·종류로 다시 추가한다.** 추가와 같은 경로(행 + 대체공휴일 재계산 + `holiday_change` op `add` 로그, 한 트랜잭션)다.
  - 대기 중: `되돌리기…`, 비활성.
  - 성공: 결과 줄이 사라지고 서버에서 다시 그린 표에 행이 돌아온다(옮겨졌던 대체공휴일도 제자리로). 포커스는 돌아온 행의 `삭제`로 간다. 토스트는 없다.
  - 실패(연결·서버): 결과 줄 글자가 `--danger` `되돌리지 못했습니다 · 다시 시도`로 바뀌고 `되돌리기`가 남는다.
  - 거절(그사이 그 날짜가 오늘 이전이 됐거나 다른 공휴일이 들어섰다): 결과 줄이 `--danger` `되돌리지 못했습니다 · {원인}`으로 바뀌고 `되돌리기`는 사라진다. 원인은 칸 오류 문구의 앞부분이다(카피 계약).
- 삭제 실패: 행은 그대로이고 그 행 동작 칸의 `삭제` 옆에 `--fs-sm --danger` `삭제하지 못했습니다 · 다시 시도`를 쓴다. `삭제`를 다시 누르면 된다.
- D-4209: 보관함이 아니라 바로 지우고 원래 값은 `holiday_change` 로그에 남긴다. 문구는 보관함을 말하지 않는다.
- 폰 375px: 결과 줄은 줄바꿈되어 가로 스크롤이 없다. `삭제`와 `되돌리기`의 누르는 영역은 44×44 이상이다.

## S3 — 관리자 배너 둘 (D-705, NOTI-02)

§7-11 규칙 그대로다: 화면 제목 **위**, 전역이 아니다, **한 화면에 최대 1개**, 닫기 버튼이 없다, 조건이 사라질 때까지 남는다. 배너 안의 다음 한 수는 3차 링크 하나다.

### 배너 둘

| 배너 | 등급 | 보이는 조건 | 사라지는 조건 | 누구에게 |
|---|---|---|---|---|
| B1 공휴일 확정 요청 | 안내 `Banner kind="info"`(`role="status"`) | 올해 또는 다음 해 가운데 확정 전인 해가 있다. 문구에는 그중 가장 이른 해를 쓴다 | 그 해를 확정한다. 남은 해가 미확정이면 그 해로 넘어간다(U-4) | `admin.holidays` **write** 권한이 있는 사람(행동할 수 있는 사람만) |
| B2 이메일 발송 실패 | 경고 `Banner kind="warning"`(`role="alert"`) | 이메일 발송을 시도한 **마지막 알림 발송(tick)**에서 실패가 1건 이상이다. 또는 결과 불명 묶음(`unknown` 행 · 선점 뒤 10분 지난 `sending` 행)이 선점 뒤 7일 안에 하나라도 있다(D-4217). 지금의 SMTP 설정과 무관하다 | 실패 부분은 그다음 이메일 발송 tick에 실패가 0건이면 빠진다. 재시도는 없으므로(RESEARCH OQ3) 「미해결 실패 전체」를 조건으로 삼지 않는다. 그렇게 하면 배너가 영원히 남는다. 결과 불명 부분은 선점 뒤 7일이 지나면 조용히 빠진다. 확인 컨트롤은 두지 않는다 | `admin.system-status` **view** 권한이 있는 사람 |

### 어느 화면에 띄우나

| 화면 | 배너 자리 하나에 들어가는 것 (위가 우선) |
|---|---|
| `/admin` 「관리」 인덱스 | ① B2 이메일 발송 실패(경고) → ② B1 공휴일 확정 요청(안내). 관리자 화면들의 입구라서 두 조건을 모두 받는다 |
| `/admin/system-status` | ① 기존 DB 커넥션 한도(경고) → ② B2 이메일 발송 실패(경고). B2가 밀려나도 아래 「이메일」 줄에 실패·결과 불명 꼬리가 항상 보인다. SMTP가 지금 미설정이어도 보인다(S4) |
| `/admin/holidays` | 배너 없음. 연도 상태 줄과 1차 확정 버튼이 같은 일을 한다(한 정보를 두 번 보이지 않는다) |
| 그 밖의 화면(첫 화면 `/` 포함) | 없음(아래 가정 U-5) |

우선순위 규칙: **경고가 안내보다 앞선다. 같은 등급이면 그 화면이 원래 가진 조건이 먼저다.** 이 규칙은 §7-11 D② 「최대 1개」를 기계적으로 지키기 위한 것이다. 밀려난 배너는 앞선 조건이 풀리면 나타난다.

## S4 — 시스템 상태 추가 줄 (18A, D-711)

§6-8의 `dl` 골격 그대로다. 라벨은 `--fs-sm --muted` 600, 폭 96(PC)/84(폰), 행 사이 점선이다. 기존 세 줄(배포 버전 · DB 커넥션 · 마지막 백업) **아래에** 두 줄을 더한다.

| 라벨 | 값 |
|---|---|
| `알림 발송` | 정상: `2026-09-24 09:00 · 알림 12건 · 중복 건너뜀 3건 · 남음 0건`. 비영업일 tick: `2026-09-26 09:00 · 비영업일 · 보내지 않음`. 기록 없음: `기록 없음 — 첫 알림 발송 전`(기존 `백업 없음 — 첫 자동 백업 전`과 같은 모양). 조회 실패: `StatusTag kind="muted"` `확인 불가` |
| `이메일` | **설정 부분 + 결과 꼬리**를 따로 만든다. 설정 부분: SMTP 환경 변수 4개 중 하나라도 비었으면 `StatusTag kind="muted"` `미설정`(D-711. 태그는 기존 `확인 불가`와 같은 자리·모양), 설정됨이면 `사용 중 · {SMTP_FROM 주소}`. 결과 꼬리(설정과 무관하게 붙는다): 이메일을 시도한 마지막 tick에 실패가 있으면 ` · 실패 {F}건 ({YYYY-MM-DD HH:MM})`, 결과 불명이 있으면 이어서 ` · 결과 불명 {U}건 ({가장 이른 결과 불명 시각})`. 예: `미설정 · 실패 3건 (2026-09-24 09:00)`. 발송 결과 조회가 실패하면 꼬리 자리에 ` · ` + `확인 불가` 태그. 비밀번호·호스트·사용자는 보이지 않는다 |

- `--danger` 글자는 `실패 {F}건` 하나뿐이다. 결과 불명 꼬리는 본문 색이다(받았는지 모를 뿐 실패가 아니다).
- 숫자와 시각은 `tabular-nums`다. 건수는 `12건`처럼 붙여 쓴다(§2-4). 상대 시간은 쓰지 않는다.
- advisory lock을 잡지 못해 곧바로 끝난 tick은 「마지막 tick」 기록을 덮어쓰지 않는다. 그래서 화면에 「다른 실행 중」 같은 상태는 없다. 기록 방식은 계획이 정한다.
- 다섯 상태는 §6-8 그대로다. 새 두 줄은 PARTIAL(`확인 불가`)에 합류한다.

## S5 — 계정 잠금 문구 · 행동 로그 라벨 (D-712)

- **잠금 문구:** 「15분」을 설정 `auth.lockout.window_minutes`의 값으로 바꾼다. 나머지 글자는 그대로 둔다(작게 바꾸는 일이라 문장 구조를 §8 형식으로 다시 쓰지 않는다):
  `로그인 시도가 너무 많습니다. {N}분 뒤 다시 시도하거나 관리자에게 문의하세요.`
  - N은 `lockoutConfig()`가 읽는 값과 **같은 출처**다. 잠금은 창 안의 실패가 창 밖으로 밀려나면 풀린다. 그래서 N분은 가장 긴 대기 시간이고 문구로 맞다.
  - 구현 주의(UI 계약에 영향): `app/(auth)/login/login-error.ts`는 지금 이 문구를 `===`로 정확히 대조한다. 숫자가 바뀌면 대조가 깨지므로 고정 접두어·접미어 대조나 별도 코드로 판정해야 한다. 그러지 않으면 잠금 문구가 일반 오류로 떨어진다. `locked-message.ts`는 계속 import 없는 잎 모듈이어야 한다(클라이언트 번들 제약). 문구를 만드는 함수는 숫자만 인자로 받는다.
  - 남은 시간(몇 분 남았는지)은 여전히 보이지 않는다. 기존 정보 최소화 원칙을 따른다.
- **행동 로그 라벨** (`ACTION_TYPE_LABELS`): `account_lock` → `계정 잠금`, `account_unlock` → `잠금 해제`. 행동 로그 화면은 바꾸지 않는다. 잠금은 행위자가 시스템이라 행위자 칸이 기존 규칙대로 `—`로 보인다. 대상 이메일은 기존처럼 상세 칸의 `detail`에 보인다.

## SYSTEM.md 수정 제안 (이 페이즈 계획에 「SYSTEM.md 반영」 작업으로 넣는다. 이 문서는 SYSTEM.md를 직접 고치지 않는다)

이것은 **이탈(divergence)이 아니다.** 모두 SYSTEM.md가 비워 두었거나 늘어나도록 설계한 자리를 채우는 것이다. CLAUDE.md 「시스템을 벗어나야 하면 DECISIONS.md에 이유 기록 후 SYSTEM.md를 고친다」에 따라 DECISIONS.md 항목 하나(「Phase 04.2 알림함·공휴일 UI 계약」, 위 U-1~U-10 요약)와 함께 반영한다.

1. **§6-10 표:** 「마스터」에 `공휴일` 추가. 절 제목의 「관리자 화면 10개」를 「11개」로. `role-menu.ts` `ADMIN_MENUS`와 같은 커밋에서 고친다(단위 테스트 대조).
2. **§7-12:** 제목의 「구현은 Phase 7」을 「구현은 Phase 04.2」로 고친다(ROADMAP 04.2가 요구한 표기 수정). S1-a(배지 자리·모양·`99+`·실제 수 스크린 리더 이름·경로 이동 때 다시 받기), S1-b(메뉴 순서), S1-c(인셋 색 `--line-strong`, 이메일 실패 보조 줄, 날짜 `<tbody>` rowgroup 머리글, 50건 더 보기와 그 상태), S1-d(열면 모두 읽음)를 계약에 더한다.
3. **§4-3:** 인셋 선 허용 목록에 `inset 2px 0 0 --line-strong`(알림함 안 읽은 행)을 더한다.
4. **§6-8:** 세 항목을 다섯 항목으로 늘린다(`알림 발송`, `이메일`). `이메일` 값은 설정 부분과 결과 꼬리(실패·결과 불명)를 따로 만든다는 것을 적는다. 배너가 둘 겹칠 때 DB 커넥션이 먼저라는 것을 적는다.
5. **§7-11:** 예시에 B1·B2(결과 불명 변형 포함)를 더한다. 우선순위 규칙 「경고 > 안내, 같은 등급이면 그 화면의 조건이 먼저」와 「관리」 인덱스가 여러 관리자 조건을 받는 자리라는 것을 적는다.
6. **§6-0 (a):** 사용자 메뉴가 `관리 · 알림함 N · 내 정보 · 로그아웃`이 되고 트리거에 배지가 붙는다는 것을 적는다.
7. **§6 레이아웃 목록:** 공휴일 화면은 새 템플릿이 아니다. §6-1 + §7-15 조립이라는 한 줄과 S2-b 와이어프레임을 §6-10 아래 참고로 둘지는 SYSTEM.md 담당 스레드가 정한다.
8. **§7-8 또는 §6-1(목록 행 삭제):** 같은 값으로 다시 넣을 수 있는 행의 삭제는 확인 없이 지우고, 표 위 결과 줄 `{대상} 삭제됨` + 3차 `되돌리기`를 둔다(화면 이동이 없어 토스트가 아니다, §7-6). 두 단계 인라인 확인(D-25)은 되돌릴 수 없는 삭제에 남긴다.
