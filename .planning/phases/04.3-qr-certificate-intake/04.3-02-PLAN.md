②-b **당첨자 UNIQUE를 지연 가능으로 — custom 마이그레이션(codex final3 A1 · C2):** drizzle-kit은 이 절을 내지 못한다(objective의 확인 셋). ② 바로 뒤에 `pnpm db:generate --custom --name cert_winners_unique_deferrable` — drizzle-kit이 다음 번호의 빈 SQL · 직전과 같은 스냅샷 · journal 항목을 만든다(번호는 그대로 쓴다, 예약 번호 범위 없음). 빈 SQL에 적는 것: 머리 `SET LOCAL lock_timeout` · `statement_timeout` 두 줄(0010과 같게) → 제약 `cert_winners_event_id_name_phone_unique` DROP → 같은 이름 · 같은 세 칸의 UNIQUE INDEX 생성 → `ADD CONSTRAINT cert_winners_event_id_name_phone_unique UNIQUE USING INDEX cert_winners_event_id_name_phone_unique DEFERRABLE INITIALLY IMMEDIATE`(문장 사이 `--> statement-breakpoint`). 칸을 괄호로 적는 `ADD CONSTRAINT … UNIQUE (…) DEFERRABLE` 형태는 squawk 2.65.0(`.squawk.toml`)이 `constraint-missing-not-valid` · `disallowed-unique-constraint` 두 경고로 막고, `USING INDEX` 형태는 0건이다(계획 시점 실측). Postgres 16의 `ALTER CONSTRAINT`는 UNIQUE의 지연 여부를 바꾸지 못하므로 DROP → 다시 걸기다 — 표가 같은 `migrate()` 트랜잭션에서 방금 생긴 빈 표라 잠금 부담이 없다. 제약 이름 · 칸이 스냅샷과 같으므로 이후 `pnpm db:generate`가 이 제약을 다시 건드리지 않는다. `INITIALLY IMMEDIATE`인 이유: 04.3-04 삽입 · 04.3-12 파기 등 다른 쓰기는 지금처럼 문장마다 검사하고, 04.3-10 일괄 저장만 `SET CONSTRAINTS`로 커밋 때 검사한다. 이 제약을 ON CONFLICT 중재자로 쓰는 INSERT는 04.3 계획 전부에 없다(grep 확인 — `onConflict`는 04.3-09의 권한 표뿐).
