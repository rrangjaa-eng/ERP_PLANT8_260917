<objective>

  - `_ensure_wrapped_data_key <base> <seed_bytes>`(예 `app-data-key-v1 32`) — 인코딩 계약(codex #1)은 「KMS 평문 = 평문 시크릿과 같은 base64 텍스트 · 감싼 시크릿 = KMS 암호문의 한 줄 base64」다. 순서:
    1. 감싼 시크릿 `secret_name "${base}-wrapped" "$ENV"`가 없으면 만든다. ENABLED 버전이 있으면 2~4(감싸기)를 건너뛰고 끝난다 — 권한 · 라벨은 이 함수가 아니라 5가 매번 보장한다(왕복 확인은 처음 감쌀 때 한 번 — 이후 드리프트는 기동 때 `loadDataKeys`가 막는다).
    2. 평문 원천: 평문 시크릿(`secret_name "$base" "$ENV"`)에 ENABLED 버전이 있으면 `gcloud secrets versions access latest`의 출력(**그 값 그대로** — 새 키를 만들지 않는다), 없으면 `openssl rand -base64 "$seed_bytes"`의 출력. 어느 쪽이든 base64 텍스트를 풀지 않고 그대로 파이프로 `gcloud kms encrypt --plaintext-file=- --ciphertext-file=-`에 넘기고 `openssl base64 -A`로 한 줄 base64로 만든다. 이 한 줄(KMS 암호문 — 비밀이 아니다)만 셸 변수에 둔다. 평문은 변수 · 임시 파일에 두지 않는다.
    3. `_verify_wrapped_data_key <그 한 줄> <base> <seed_bytes>` — 한 줄을 `openssl base64 -d -A` → `gcloud kms decrypt --ciphertext-file=- --plaintext-file=-` → 공백 제거 → `openssl base64 -d -A`로 푼 바이트 수가 `seed_bytes`인지, 평문 시크릿에서 옮기는 경우에는 같은 방식으로 푼 원래 키와 `openssl dgst -sha256` 해시가 같은지 본다(모두 파이프, 비교하는 것은 해시 · 바이트 수뿐). 어긋나면 `STAGE`를 남기고 실패로 끝난다 — 4와 서비스 배포가 일어나지 않는다.
    4. 확인이 통과하면 감쌀 때 읽은 주 버전 숫자를 **먼저** 그 시크릿 라벨 `kms-key-version`으로 남기고(`gcloud secrets update … --update-labels` — v2 확인의 근거), 그다음 한 줄을 감싼 시크릿의 새 버전으로 더한다(`--data-file=-`). 라벨이 버전보다 앞이라 라벨 없는 버전이 생기지 않는다 — 버전 추가가 실패하면 다음 실행이 다시 감싸 라벨을 덮어쓴다. 권한은 여기서 걸지 않는다(5).
  - `_ensure_wrapped_data_key_access <base>`(codex final C4 — 키 만들기와 분리, `scripts/deploy.sh` `_ensure_secret`이 버전 유무와 무관하게 끝에서 `secretAccessor`를 다시 거는 것과 같은 방식): 5. 런타임 서비스 계정에 감싼 시크릿 `secretAccessor`를 매 실행 다시 바인딩하고(멱등), 감싼 시크릿에 ENABLED 버전이 있는데 라벨 `kms-key-version`이 비어 있으면 지금 주 버전 숫자로 채운다(이전 실행이 버전 추가와 라벨 사이에서 멈췄거나 이 순서 전의 코드로 만든 경우 — 그사이 소유자가 새 주 버전을 만들었다면 라벨이 새 버전을 가리켜 `--add-data-key-v2`가 한 번 더 멈추고 소유자 단계를 요구하는 쪽으로 틀린다. v2를 v1과 같은 KMS 버전으로 감싸는 쪽으로는 틀리지 않는다). `ensure_secrets`는 v1에 이 함수를 매번 부르고, 감싼 v2 시크릿에 ENABLED 버전이 있으면 플래그와 무관하게 v2에도 부른다(`deploy_service`가 v2를 붙이는 조건과 같다) — 둘 다 `_ensure_wrapped_data_key` 호출 뒤, `deploy_service` 앞.
  - `ensure_secrets`에서 평문 데이터 키를 새로 만드는 줄을 `_ensure_wrapped_data_key app-data-key-v1 32` 호출로 바꾸고, `main()`에서 `ensure_kms_key`를 `ensure_secrets` 앞에 둔다.
  - `deploy_service`: `secrets`의 평문 데이터 키 연결을 `APP_DATA_KEY_v1_WRAPPED=<감싼 시크릿>:latest`로 바꾸고 `env_vars`에 `APP_DATA_KEY_KMS_KEY=projects/${PROJECT}/locations/${REGION}/keyRings/$(kms_keyring "$ENV")/cryptoKeys/$(kms_key)`.
  - 회전용 v2를 서비스에 먼저(codex C1): `parse_args`에 `--add-data-key-v2`(→ `ADD_DATA_KEY_V2=1`)와 `usage` 한 줄. `ensure_secrets`는 그 값이 1이면 v1 다음에, 감싼 v2 시크릿에 ENABLED 버전이 **아직 없을 때만** 지금 주 버전(`gcloud kms keys describe … --format='value(primary.name)'`의 마지막 조각)을 감싼 v1 시크릿의 라벨 `kms-key-version`과 견준다 — 같거나 라벨이 없으면 `STAGE`를 남기고 한 줄 `KMS 키에 새 주 버전이 필요합니다 — 소유자 계정으로 OPERATIONS §9 회전 (0) 단계를 먼저 실행하세요`로 0이 아닌 코드로 끝난다(v2 감싸기 · 서비스 배포 없음). 다르면 `_ensure_wrapped_data_key app-data-key-v2 32`를 부른다. 버전을 만드는 명령은 `deploy.sh`에 두지 않는다(오케스트레이터 결정 — 버전 만들기는 소유자 몫)(같은 함수 — 평문 v2 시크릿이 있으면 그 값을, 없으면 새 32바이트를 감싸고 같은 왕복 확인). `deploy_service`는 플래그가 아니라 **존재**로 판단한다 — 감싼 v2 시크릿(`secret_name app-data-key-v2-wrapped "$ENV"`)에 ENABLED 버전이 있으면(`_ensure_secret`과 같은 `versions list --filter='state:ENABLED'` 확인) `secrets`에 `,APP_DATA_KEY_v2_WRAPPED=<그 시크릿>:latest`를 더한다. 그래서 한 번 만든 v2는 이후 배포마다 붙고, v2가 없는 환경은 지금과 같다. `main()` 순서상 v2 감싸기(`ensure_secrets`)가 `deploy_service`보다 앞이다.
  - 평문 시크릿을 지우거나 끄는 명령을 넣지 않는다(되돌릴 길을 남긴다 — 런북). 평문 버전 파기와 런타임 서비스 계정의 평문 시크릿 `secretAccessor` 바인딩 제거도 런북의 운영자 단계다(⑥ — AX-2). 그리고 `ensure_secrets`는 평문 데이터 키 시크릿(`app-data-key-v1` · `app-data-key-v2`)에 `_ensure_secret`을 더는 부르지 않는다 — 부르면 운영자가 뗀 `secretAccessor`를 배포마다 다시 걸고, 평문 버전을 파기한 뒤에는 새 평문 키를 만든다.
