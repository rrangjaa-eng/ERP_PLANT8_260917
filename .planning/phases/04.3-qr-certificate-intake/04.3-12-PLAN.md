<objective>
**As a** 경영관리(개인정보 보관 책임자), **I want to** 보존 기간이 지난 확인증의 개인정보와 제출하지 않은 당첨자 명단이 정해진 날에 확실히 지워지기를 바란다, **so that** 세무 기록(건수 · 연결)은 남기면서 법이 허용한 기간보다 오래 개인정보를 들고 있지 않는다.

ROADMAP Goal 줄은 사용자 이야기 형식이 아니다 — Goal의 「보존 기간 뒤 파기를 지킨다」(기준 4)에서 이야기를 끌어냈다.

CONTEXT 「파기 시점 = 제출한 해 종료 + 법정 신고기한 + 보존 기간(설정, 기본 5년) · 이름 · 전화 · 주민등록번호 · 주소 · 서명 이미지를 지우고 줄은 남긴다 · DB 먼저, 파일 나중 · 보관함 예외」를 구현한다. CONTEXT 재량 둘(파기 실행 방식 · 서명 저장 위치)은 04.3-05(비공개 버킷)와 이 플랜(사람이 실행하는 Cloud Run Job)으로 정했고, 재량 「제출하지 않은 명단의 파기 시점」은 30일 상수로 정해 설계 `/cso`에 넘긴다.

**결정(재량, 설계 `/cso`가 다시 본다):** ① 기한 = (제출 KST 연도 + 1 + 보존 연수)-03-01 00:00 KST — 기타소득 지급명세서 제출기한(다음 해 2월 말) 다음 날부터 보존 기간을 센다. ② 보존 연수는 확인증의 `retention_years`(04.3-02 — 확인 때 묶인 `offered_retention_years`를 제출이 복사) — 파기는 설정을 읽지 않는다. ③ 파일 삭제 대기는 새 칸 없이 파기된 줄(`purged_at` 있음)에 남은 `signature_key`로 표시한다 — 삭제가 끝나면 비운다(스키마 변경 없음). ④ 미제출 명단은 행사가 닫힌 뒤 30일. ⑤ 실행은 Cloud Scheduler 없이 사람이 Job을 실행한다 — 이 저장소에 스케줄러가 아직 없고, 기한이 연 1회(3월 1일)라 월 1회 실행으로 늦어도 한 달 안에 지워진다. ⑥ 실행 기록은 끌 수 없는 새 핵심 로그 종류 `cert_purge`(라벨 `확인증 파기`) — 공유 등록부라 세 배열에 항목만 더한다. 이 로그는 칸 비우기와 한 트랜잭션(C6 — 04.3-07의 `appendCertActionLogTx`, 04-32가 오면 `recordAction(…, tx)`로 바꾸는 후속)이라 detail은 트랜잭션 안에서 아는 개수(`submissions` · `winners` · `filesQueued`)뿐이고, 커밋 뒤 파일 삭제 결과(`filesDeleted` · `filesPending` · `orphansDeleted`)는 반환값과 서버 로그 `purge_certs.done`에 남는다. ⑦ 고아 서명(C3): 04.3-02가 제출 전 업로드 의도 행을 넣고 제출 트랜잭션에서 지우므로, 24시간 넘게 남은 의도 행은 저장되지 않은 업로드다 — 파기 적용 실행이 객체를 지우고 행을 지운다. ⑧ 리포지토리는 저장소 규칙대로 viewer 첫 인자이고 domain이 `SYSTEM_VIEWER`를 넘긴다(codex #19).
