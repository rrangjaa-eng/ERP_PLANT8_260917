**받는 대상:**
- **D-1101:** 확인증은 경품(현물) 수령자에게만 받는다. 수령자 화면은 SYSTEM §6-5 그대로이며 계좌·지급액 칸이 없다. 현금 개인 지급(사업소득·현금 기타소득)은 확인증 없이 기존 지출결의·거래처 흐름(Phase 5·6)으로 처리한다. — Reversibility: costly

**링크와 수령자 찾기:**
- **D-1102:** QR 링크는 행사(경품 지출결의)당 하나이고 여러 명이 같이 쓴다. 한 사람은 한 번만 제출할 수 있고, 제출하면 그 사람 자리만 닫힌다. 링크 전체는 만료 시간(기본 72시간)이 지나거나, 등록된 당첨자가 모두 제출하거나, 담당자가 닫으면 닫힌다. — Reversibility: costly
- **D-1103:** 담당자가 당첨자 목록(이름·전화번호·경품명·수량·현장/택배)을 미리 넣고, 수령자는 QR로 들어와 목록에서 자기 이름을 고른 뒤 전화번호 뒤 4자리로 확인한다(260907 방식). 확인이 끝나야 §6-5 입력 폼이 열린다. 현장/택배는 사람마다 정한다. — Reversibility: costly

**지출결의 연결 (Phase 11 몫 — 참고):**
- **D-1104:** 행사 QR은 경품 지출결의 화면에서 만들고, 제출된 확인증은 그 지출결의에 자동으로 붙는다. 이 페이즈는 그 연결이 붙을 자리(연결 어댑터)와 플래그가 꺼진 동안 쓰는 내부 행사 화면만 만든다

**세금 (Phase 11 몫 — 참고):**

**제출 후 정정:**

## Summary

이 페이즈는 코드베이스에 이미 있는 세 가지 성숙한 패턴(Phase 3의 앱단 암호화+마스킹 해제+행동 로그, Phase 3의 이력형/단순 설정 레지스트리, Phase 1의 계정 잠금 순수 함수)을 그대로 재사용해서 외부인이 로그인 없이 접근하는 새로운 요청 경로 하나를 얹는 일이다. 재사용 가능한 부분은 HIGH 확신으로 문서화했다 — `lib/crypto.ts`의 `encrypt/decrypt`, `domain/vendors/index.ts`의 `revealAccountNumber`(마스킹 해제 = 노출 판정 → `recordAction` → `decrypt` 순서) 패턴을 주민등록번호에 그대로 적용하면 된다.

가장 중요한 발견은 이 페이즈가 기존 아키텍처의 암묵적 전제 두 가지를 깬다는 것이다. 첫째, **모든 Server Action은 `authedActionClient`(세션 필수)만 쓸 수 있다**는 ESLint 규칙(`eslint/rules/require-action-client.mjs`)이 하드코딩돼 있다 — 로그인 없는 외부 제출 액션을 넣으려면 `lib/actions/client.ts`에 세션을 요구하지 않는 새 클라이언트(`publicActionClient`)를 추가하고 `eslint.config.mjs`의 룰 옵션에 그 이름을 더해야 한다. 둘째, **이 저장소 어디에도 물리 `DELETE` 문이 없다**(`domain/archive/index.ts`의 명시적 불변식: "물리 삭제 문장은 이 리포 어디에도 넣지 않는다") — 확인증 파기(CERT-02)는 그래서 행을 지우는 게 아니라 PII 컬럼만 `UPDATE ... SET name = NULL, ...`로 비우는 방식이어야 하고, 이는 `ARCHITECTURE.md`가 이미 못박은 방향과도 일치한다.

QR 생성과 서명 이미지 저장(GCS)은 이 저장소에 선례가 전혀 없다(Phase 6도 아직 구현 전). 정해진 스택: QR은 `qrcode`(+ `@types/qrcode`, 사용자 승인 2026-09-24 09:51), GCS는 새 패키지 없이 이미 있는 `google-auth-library`로 GCS JSON API를 REST로 부르는 어댑터 하나(`@google-cloud/storage`는 쓰지 않는다 — `COVERAGE.md`). 마이그레이션 번호는 예약하지 않는다: drizzle-kit 스냅샷은 `id`/`prevId` 해시 체인으로 연결되고(실측: `0010_snapshot.json`) `migrate()`는 마지막 적용분보다 `when`이 새로운 항목만 적용하므로, 브랜치에서는 `pnpm db:generate`가 준 번호를 쓰고 머지 직전에 `db/migrations/`를 origin/main 그대로 복원한 뒤 이 페이즈 것만 다시 만들어 main 마지막 + 1로 둔다(아래 Pitfall 4).

**Primary recommendation:** 기존 패턴(암호화·설정 레지스트리·행동 로그·잠금 순수 함수)을 그대로 복제하고, 새로 필요한 두 가지(공개 액션 클라이언트, PII 파기 스크립트)만 신중히 설계한다. QR은 승인된 `qrcode` 하나, 서명 이미지는 기존 `google-auth-library` + GCS REST 어댑터로 간다(새 의존성은 `qrcode` · `@types/qrcode`뿐).

### Pattern 1: 공개(비인증) Server Action 클라이언트 신설

**What:** `lib/actions/client.ts`는 지금 `authedActionClient` 하나만 있고, `getSession()`이 없으면 무조건 `UserFacingError("로그인이 필요합니다.")`를 던진다[VERIFIED: lib/actions/client.ts, 이 세션에서 직접 Read]. 외부 수령자 액션(이름 선택·뒤 4자리 확인·제출)은 세션이 아예 없다.

**When to use:** `app/c/[token]/actions.ts`처럼 로그인하지 않은 외부인이 호출하는 Server Action 전부.

**Example (기존 파일 패턴을 따른 신규 export):**
```typescript
// lib/actions/client.ts — 기존 파일에 추가
// authedActionClient와 같은 payload 크기 검사는 그대로 두되 getSession()을
// 호출하지 않는다. 권한 경계는 세션이 아니라 액션 인자로 받는 token이며,
// 토큰 검증(만료·잠금·1회 제출)은 domain/certs/intake.ts가 담당한다.
export const publicActionClient = actionClient.use(async ({ next, clientInput }) => {
  const sizeCheck = checkPayloadSize(clientInput);
  if (!sizeCheck.ok) {
    throw new UserFacingError(sizeCheck.reason);
  }
  return next({ ctx: {} });
});
```

**필수 동반 변경 — `eslint.config.mjs`:**
```javascript
// 기존: "plant8/require-action-client": "error"
// 변경 후 (require-action-client.mjs가 옵션으로 clients 배열을 받는다 —
// eslint/rules/require-action-client.mjs:1, 47-58에서 확인됨):
"plant8/require-action-client": ["error", { clients: ["authedActionClient", "publicActionClient"] }],
```
[VERIFIED: eslint/rules/require-action-client.mjs:1,47-58 — `const DEFAULT_CLIENTS = ["authedActionClient"];`와 `schema: [{ type: "object", properties: { clients: { type: "array", items: { type: "string" } } } }]`, 이 세션에서 직접 Read] — 이 변경 없이는 `/c/[token]/actions.ts`가 `publicActionClient`를 쓰는 순간 린트가 실패한다(현재 기본값은 `authedActionClient`만 허용).

**Anti-pattern:** `authedActionClient`를 억지로 통과시키려고 익명 세션을 만들거나 `getSession()`을 우회하는 보조 로그인을 만들지 않는다 — CONTEXT.md의 "외부 경로는 앱 세션 로직과 분리된 별도 인증 경로"라는 명시적 결정과 어긋난다.

### Pattern 2: 토큰 기반 외부 경로는 `proxy.ts`(옛 middleware)를 거치지 않는다

**What:** `proxy.ts`의 `matcher`는 `["/api/auth/:path*"]` 하나뿐이다[VERIFIED: proxy.ts, 이 세션에서 직접 Read]. `/c/[token]` 라우트는 이 matcher에 안 걸리므로 `clientIp` 헤더 주입·CSRF 이중 제출 같은 기존 미들웨어 로직이 전혀 적용되지 않는다. Next.js 16 공식 문서도 "Server Function은 별도 라우트가 아니라 그 라우트로 가는 POST 요청으로 처리되므로, matcher가 그 경로를 빼면 Server Function 호출도 함께 빠진다"고 명시한다[CITED: node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md:249-251, 이 세션에서 직접 Read].

**When to use:** `/c/[token]` 설계 시 "요청 위조 방지"나 "속도 제한"을 proxy.ts에 기대지 말고 도메인 로직(뒤 4자리 5회 실패 → 3분 잠금, 사람당 1회 제출, 토큰 만료)에 전부 넣는다.

**Anti-pattern:** `proxy.ts`의 matcher를 `/c/:token*`까지 넓혀서 인증 미들웨어를 태우려는 시도 — CONTEXT.md의 Integration Points가 이미 "기존 세션 재사용 금지"로 명시했고, `/api/auth/*` 전용으로 좁혀 둔 이유(Eng Issue 1, x-client-ip 위조 방지)와 무관한 확장이라 boundary를 흐린다.

### Pattern 3: PII 암호화·마스킹 해제 재사용(주민등록번호 = 계좌번호와 같은 틀)

**What:** `domain/vendors/index.ts`의 `revealAccountNumber`는 "노출 판정(`visible`) → `recordAction('mask_reveal')` 먼저 기록 → `decrypt()`" 순서를 강제한다. 기록이 실패하면 평문을 돌려주지 않는다는 주석이 명시적이다[VERIFIED: domain/vendors/index.ts:368-393, 이 세션에서 직접 Read. 코드 인용: `// 통과하면 먼저 recordAction으로 기록하고 그 다음에 복호화한다(기록이 실패하면 평문을 돌려주지 않는다`].

**When to use:** 주민등록번호 전체 보기(경영관리 전용) 기능은 이 함수를 그대로 복제한다 — 정보 노출표에 새 항목(예: `cert.rrn_unmasked`)을 등록하고, `visible(viewer, 'cert.rrn_unmasked')` → `recordAction(viewer, {actionType: 'mask_reveal', entity: 'cert_submission', entityId})` → `decrypt(row.rrnEncrypted)` 순서를 그대로 따른다.

**Example:**
```typescript
// domain/certs/review.ts (신규, domain/vendors/index.ts:376-393 패턴 복제)
export async function revealRrn(
  viewer: Viewer,
  submissionId: string,
  deps?: Partial<{ visible: typeof defaultVisible; recordAction: typeof defaultRecordAction }>,
): Promise<string> {
  const visibleFn = deps?.visible ?? defaultVisible;
  if (!(await visibleFn(viewer, "cert.rrn_unmasked"))) {
    throw new ForbiddenError("주민등록번호 전체 보기 권한이 없습니다.");
  }
  const row = await repoFindSubmissionById(viewer, submissionId);
  if (!row?.rrnEncrypted) return "";
  const recordAction = deps?.recordAction ?? defaultRecordAction;
  await recordAction(viewer, { actionType: "mask_reveal", entity: "cert_submission", entityId: submissionId });
  return decrypt(row.rrnEncrypted);
}
```

**Anti-pattern:** RRN 복호화 결과를 `console.log`/`log.warn` 등 `lib/log.ts`에 넘기지 않는다 — `lib/crypto.ts` 헤더 주석이 이미 이 규칙을 명시한다[VERIFIED: lib/crypto.ts:1-3, `인자와 반환값을 lib/log.ts에 절대 넘기지 않는다`].

### Pattern 4: 설정 레지스트리에 확인증 탭 키 등록

**What:** `domain/settings/keys.ts`는 `SettingDef<T>` 객체를 `SETTING_DEFS` 배열 하나에 모으는 단일 정본이다. `kind: "simple"`(비이력형)과 `"historized"`(이력형) 두 종류가 있고, 등록되지 않은 키는 화면에 안 뜨며, 등록됐지만 서버가 안 읽으면 미사용 키 검출 테스트가 실패한다[VERIFIED: domain/settings/registry.ts, domain/settings/keys.ts, 이 세션에서 직접 Read].

**When to use:** 이 페이즈가 등록해야 할 키(전부 `kind: "simple"`, 이력이 필요 없는 운영 파라미터):
- `cert.link.expire_hours` (기본 72)
- `cert.verify.max_attempts` (기본 5)
- `cert.verify.lock_minutes` (기본 3)
- `cert.retention.years` (기본 5)
- `cert.enabled` (기본 `false` — CONTEXT 「기능 플래그」, boolean. **환경 게이트 `CERT_FEATURE_ALLOWED`가 `true`일 때만 `SETTING_DEFS`에 실린다** — 규약 C1, 04.3-02)

**Example (기존 `AUTH_LOCKOUT_THRESHOLD` 패턴 복제):**
```typescript
// domain/settings/keys.ts에 추가
export const CERT_VERIFY_MAX_ATTEMPTS: SettingDef<number> = {
  key: "cert.verify.max_attempts",
  kind: "simple",
  schema: z.coerce.number().int().min(1),
  label: "전화번호 확인 실패 허용 횟수",
  hint: "이 횟수만큼 틀리면 그 사람의 확인을 잠급니다.",
  namespace: "확인증",
  default: 5,
};
```
`cert.enabled`는 `admin.settings` 쓰기 권한으로 게이트되는 `setSettingValue`를 그대로 쓴다. 다만 설정 하나만으로는 켜지지 않는다(규약 C1, 04.3-02): 기능은 환경 변수 `CERT_FEATURE_ALLOWED`가 `true`이고 **그리고** `cert.enabled`가 켜졌을 때만 열리고, 환경 게이트가 꺼져 있으면 `cert.enabled` 줄은 설정 화면에 없고 설정 저장 액션이 등록되지 않은 키로 거부한다. 프로덕션 배포는 Phase 11 전까지 이 환경 변수를 두지 않는다 — CONTEXT 「두 감사를 통과해도 Phase 11의 경품 지출결의 연결이 끝나기 전에는 켜지 않는다」를 관리자 클릭 한 번이 깨지 못하게 한다.

**Anti-pattern:** 프로덕션 활성화를 설정 토글 하나에만 맡기지 않는다 — 설정 화면은 등록된 키를 전부 보이고 저장하므로(`app/(app)/admin/settings/page.tsx` 37행 · `actions.ts` 26행) 관리자 한 명이 Phase 11 전에 켤 수 있다. 환경 게이트(재배포가 필요)를 앞에 둔다.

### Pattern 5: 잠금 판정 순수 함수 재사용(전화번호 뒤 4자리 5회 실패 → 3분 잠금)

**What:** `domain/auth/lockout.ts`는 `windowStart(now, windowMinutes)`·`isLocked(openFailures, threshold)` 두 순수 함수 + 설정 레지스트리 조회로 이루어져 있고, DB 접근은 별도 리포지토리(`repositories/login-attempts.ts`)가 담당한다[VERIFIED: domain/auth/lockout.ts, 이 세션에서 직접 Read]. 이 페이즈의 "뒤 4자리 5회 틀리면 3분 잠금"은 **IP 기반이 아니라 당첨자 슬롯(winner row) 기반**이어야 한다 — `/c/[token]` 라우트가 `proxy.ts`를 거치지 않아 신뢰할 수 있는 클라이언트 IP 헤더가 없기 때문이다(Pattern 2).

**When to use:** `cert_winners` 테이블에 `failed_attempts int default 0`, `locked_until timestamptz` 컬럼을 두고, `verifyLast4(winnerId, last4)`가 이 두 컬럼을 갱신한다. `windowStart`/`isLocked` 스타일의 순수 함수를 그대로 복제해 단위 테스트로 고정한다.

**Anti-pattern:** `login_attempts` 테이블(이메일 로그인 전용)을 재사용하지 않는다 — 스키마가 이메일 기준이고, `proxy.ts`의 `x-client-ip` 신뢰 경로에 묶여 있어 이 외부 경로에 그대로 쓰면 잘못된 IP 신뢰 가정을 끌고 들어온다.

### Anti-Patterns to Avoid

- **`authedActionClient`를 외부 라우트에 억지로 통과시키기:** 세션 자체가 없다는 사실을 우회하면 안 된다(Pattern 1).
- **파기를 `DELETE FROM`으로 구현:** 이 저장소는 물리 삭제 문장이 0건이라는 불변식을 가지고 있다(아래 Pitfall 1). `UPDATE ... SET col = NULL`만 쓴다.
- **Cloud Scheduler 인프라를 이 페이즈에서 새로 짓기:** `infra/`에는 아직 Cloud Scheduler 정의가 없고(Phase 04.2가 아직 병합 전)[VERIFIED: `find infra -iname "*scheduler*"` 결과 없음, 이 세션에서 실행], `ARCHITECTURE.md`도 파기를 "배치(수동 실행 스크립트, 큐 아님)"로 명시한다[CITED: .planning/research/ARCHITECTURE.md:346]. `scripts/rotate-key.ts`와 같은 단발 스크립트로 시작하고, Phase 04.2의 tick 인프라가 병합된 뒤 필요하면 얹는 편이 과설계를 피한다.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| QR 코드 인코딩(Reed-Solomon 오류 정정, 마스크 패턴) | 자체 QR 인코더 | `qrcode`(신규 의존성, 사용자 승인 2026-09-24) | 표준 준수·오류 정정 로직이 복잡해 직접 구현은 명백한 hand-roll 금지 대상 |
| AES-256-GCM 암호화 | 새 암호화 유틸 | 기존 `lib/crypto.ts`의 `encrypt/decrypt` | 이미 Phase 3이 만들었고 키 버전 접두어·fail-closed·키 회전 스크립트까지 갖춰져 있다. 새로 만들면 두 개의 암호화 경로가 생겨 회전·감사가 어긋난다 |
| 주민등록번호 형식 검증(성별 코드·2020-10 이전 검증번호 알고리즘) | 커스텀 정규식만 | 순수 함수로 새로 작성하되(선례 없음) 단위 테스트로 전 자릿수 규칙 고정 | 이 저장소에 선례가 없어 "만들지 마라"가 아니라 "신중히 만들고 테스트로 고정하라"에 해당 — CONTEXT.md가 이미 규칙을 확정했다(형식·실제 날짜·성별 코드·2020-10 이전 발급분 검증번호) |
| 계정 잠금/속도 제한 로직 | 새 미들웨어 | `domain/auth/lockout.ts` 스타일의 순수 함수 복제(윈도우 기반이 아니라 시도 횟수 카운터가 더 맞다 — 260907 규칙은 "5회 틀리면 3분 잠금"으로 슬라이딩 윈도우가 아니다) | 검증된 fail-closed 패턴 재사용 |

**Key insight:** 이 페이즈에서 "만들지 말아야 할 것"은 대부분 이미 이 저장소 안에 있다. 진짜 신규는 QR 인코딩(`qrcode`)과 GCS 호출뿐이고, GCS는 새 SDK 없이 이미 있는 `google-auth-library`로 REST 세 호출(insert · get · delete)만 부른다.

## Common Pitfalls

### Pitfall 1: 파기(CERT-02)를 물리 삭제로 구현
**What goes wrong:** "PII를 지운다"는 요구사항을 문자 그대로 `DELETE FROM cert_submissions WHERE ...`로 구현하면, 이 저장소의 명시적 아키텍처 불변식(물리 삭제 문장 0건)을 깨고, 세무 기록으로 남겨야 하는 "건수·금액·연결"까지 함께 사라진다.
**Why it happens:** 일반적인 "개인정보 파기 = 행 삭제"라는 직관과, D-1107/D-1108이 요구하는 "줄(건수·금액·연결)은 세무 기록으로 남긴다"는 요구가 상충하는 것처럼 보이기 때문.
**How to avoid:** `domain/archive/index.ts`의 명시적 주석("물리 삭제 문장은 이 리포 어디에도 넣지 않는다")[VERIFIED: domain/archive/index.ts:16, 이 세션에서 직접 Read]과 `ARCHITECTURE.md`의 지침("`resident_registration_number` 컬럼만 NULL 처리")[CITED: .planning/research/ARCHITECTURE.md:346]을 그대로 따라 PII 컬럼만 `UPDATE ... SET name = NULL, phone = NULL, rrn_encrypted = NULL, address = NULL, signature_gcs_key = NULL`로 비운다. 서명 이미지 파일은 DB 갱신 뒤 GCS에서 별도 삭제(DB 먼저 → 파일 나중, 260907 3-18 규칙과 동일).
**Warning signs:** 계획이나 코드에 `DELETE FROM cert_submissions`가 등장하면 즉시 재검토.

### Pitfall 2: 공개 액션에서 `authedActionClient`의 payload 크기 검사만 빌리고 세션 체크까지 같이 딸려온다
**What goes wrong:** `authedActionClient`를 그대로 import해서 쓰면 `getSession()`이 없어 항상 "로그인이 필요합니다" 에러가 난다.
**Why it happens:** 기존 액션 파일을 복사-붙여넣기하면서 클라이언트 선택을 놓친다.
**How to avoid:** Pattern 1의 `publicActionClient`를 신설하고, `eslint.config.mjs`의 룰 옵션도 함께 바꾼다(둘 다 안 하면 린트가 새 클라이언트 사용을 거부한다).
**Warning signs:** E2E 테스트에서 외부 제출 흐름이 "로그인이 필요합니다"로 실패.

### Pitfall 3: 뒤 4자리 확인 잠금을 IP 기준으로 설계
**What goes wrong:** `/c/[token]` 경로가 `proxy.ts`를 거치지 않으므로 `x-client-ip` 신뢰 헤더가 없다(Pattern 2). IP 기준 잠금을 시도하면 위조 가능한 헤더에 의존하게 되고, 여러 명이 같은 사내 공유 QR을 스캔하는 정상 시나리오(같은 행사장 와이파이/NAT)에서 한 사람 실수로 전체가 잠기는 오탐도 생긴다.
**Why it happens:** 기존 로그인 잠금(`domain/auth/lockout.ts`)이 IP 기준이라 착각하고 그대로 옮긴다 — 실제로는 이메일(계정) 기준이지 IP 기준이 아니다.
**How to avoid:** 잠금은 `cert_winners` 행(그 사람의 슬롯) 단위로 건다 — 260907 원문도 "본인확인은 전화번호 뒤 4자리, 5회 틀리면 3분 잠금, 사람마다 1회만 제출 가능"[CITED: .planning/research/ERP260907-CONTEXT.md:151]으로 사람(슬롯) 기준이다.
**Warning signs:** 스키마에 `failed_attempts`가 IP 컬럼에 걸려 있거나 `cert_events`(행사) 단위로만 잠금이 걸림(한 사람 실수로 행사 전체가 잠긴다).

### Pitfall 4: 마이그레이션 번호를 지금 확정하고 파일명만 병합 시 바꾸면 된다고 가정
**What goes wrong:** drizzle-kit 스냅샷은 파일명 숫자가 아니라 `id`/`prevId` UUID 체인으로 이력을 추적한다[VERIFIED: db/migrations/meta/0010_snapshot.json — `"id": "d90fe79f-d8be-4bff-aefe-ce9f3dfb410c"`, `"prevId": "08b127a8-5005-454c-908a-dde21d8fa85d"`, 이 세션에서 직접 Read]. 04.3·Phase 4·04.1·04.2가 각자 브랜치에서 같은 tip(현재 main·Phase4 브랜치 모두 `0010`)을 기준으로 `drizzle-kit generate`를 돌리면, 여러 브랜치의 새 스냅샷이 전부 같은 `prevId`(0010의 `id`)를 가리키게 된다. 파일 번호만 바꾼다고 이 체인 충돌이 풀리지 않는다. 게다가 `migrate()`는 마지막으로 적용된 항목보다 `when`이 새로운 항목만 적용하므로(`node_modules/drizzle-orm/pg-core/dialect.js` 57~62행 · `scripts/migrate-runner.ts` 54행) 나중에 머지된 옛 `when`의 마이그레이션은 스테이징·프로덕션에서 조용히 건너뛴다 — 번호를 미리 나눠 갖는 방식으로는 막을 수 없다.
**Why it happens:** SQL 마이그레이션은 파일명 순서로만 적용된다는 오해(Rails/Django류 도구와 달리 drizzle-kit은 스냅샷 diff 기반).
**How to avoid:** 번호를 예약하지 않는다. 브랜치에서는 `pnpm db:generate`가 준 번호를 그대로 쓰고 손으로 바꾸지 않는다. **머지 직전에** origin/main을 머지(리베이스 · 강제 푸시 없음)한 뒤 `db/migrations/`(SQL · `meta/*_snapshot.json` · `meta/_journal.json`)를 origin/main과 정확히 같게 되돌려 놓고(main의 파일은 하나도 지우거나 고치지 않는다 — 같은 경로의 이 페이즈 파일은 main 내용으로 덮이고, main에 없는 파일만 지운다), 이 페이즈 마이그레이션만 `pnpm db:generate --name cert_intake`로 다시 만들어 main 마지막 번호 + 1 · main보다 새로운 `when` · main 마지막 스냅샷 `id`를 `prevId`로 갖게 한다. 확인은 개발 DB `erp`가 아닌 **별도의 빈 DB**에 마이그레이션 전체를 0번부터 적용해서 한다. 공용 가드 `test/unit/db/migration-journal.test.ts`(idx 연속 · tag = idx · `when` 엄격 증가)가 어긋남을 잡는다(절차: 04.3-02 ② · 04.3-13 Task 1).
**Warning signs:** `drizzle-kit`이 스냅샷 히스토리 불일치 오류를 내거나, `_journal.json` 병합 충돌이 남.

### Pitfall 5: RRN 이외의 PII(전화번호)를 평문 저장하면서 아무 검토 없이 넘어감
**What goes wrong:** CONTEXT.md의 "이미 확정된 입력"은 주민등록번호 암호화만 명시한다. 당첨자 명단의 전화번호(담당자가 미리 입력)와 수령자가 제출 폼에 다시 적는 연락처는 암호화 대상으로 결정된 바가 없다 — 그대로 평문 저장하면 설계 `/cso`에서 지적받을 가능성이 있다.
**Why it happens:** "확정된 결정에 없으면 평문이 기본"이라는 가정.
**How to avoid:** 계획에 이 항목을 Open Question으로 명시하고 설계 `/cso`(D-1107) 때 확정한다. 최소한 `phone_last4`(확인용, 이미 노출되는 정보)는 평문이어도 되지만, 전체 전화번호를 암호화할지는 `/cso` 판단에 맡긴다.
**Warning signs:** 설계 `/cso`가 "행사당 공유 링크의 노출 범위"를 볼 때 전화번호 평문 저장이 함께 지적될 가능성.

## Open Questions

1. **당첨자 명단 전화번호·수령자 연락처를 암호화해야 하는가? (RESOLVED — 설계 `/cso`로 명시적으로 미룸)**
   - **결정:** 이 페이즈 계획은 CONTEXT가 암호화 대상으로 정한 주민등록번호만 `lib/crypto.ts`로 암호화하고, 당첨자 전화번호 · 수령자 연락처 · 주소는 평문으로 두되 경영관리만 열람(04.3-07) · 공개 DTO에서 제외(04.3-02 허용 목록) · 파기 대상(04.3-12)으로 묶는다. 암호화 여부는 D-1107의 설계 `/cso`가 첫 항목으로 정한다 — 04.3-07 위협 T-04.3-15(accept, 「설계 `/cso`가 정한다」)와 04.3-13 Task 3 ② 「`/cso` 열린 질문」 목록에 올라 있다. `/cso`가 암호화를 요구하면 04.3-02 스키마 · 04.3-07 리포지토리를 그 결정대로 고친다
   - What we know: CONTEXT.md는 주민등록번호만 암호화 대상으로 명시. 거래처 계좌번호(마스터 데이터)는 암호화하지만 거래처 담당자 이름·사업자번호는 평문이다 — 이 저장소의 기존 경계는 "계좌/RRN=암호화, 그 외 PII=평문"으로 보인다.
   - What's unclear: 전화번호가 "그 외 PII"에 포함되는지, 아니면 CONTEXT.md가 놓친 항목인지.
   - Recommendation: 계획 게이트 뒤 설계 `/cso`(D-1107)의 첫 항목으로 명시적으로 묻는다.

2. **서명 이미지 GCS 업로드를 서버 액션 직접 쓰기로 할지, Phase 6의 서명 URL 패턴을 미리 도입할지? (RESOLVED — 서버 직접 쓰기, `google-auth-library` REST)**
   - **결정:** 서버 액션이 받은 PNG를 서버가 저장소 포트(`lib/storage/signature-store.ts`, 04.3-02 — 개발·테스트는 로컬 드라이버)로 쓰고, 스테이징·프로덕션 드라이버는 이미 있는 `google-auth-library`로 GCS JSON API REST(objects insert · get · delete)를 부르는 어댑터 하나다(04.3-05). `@google-cloud/storage`는 쓰지 않고, 브라우저가 버킷에 닿는 서명 URL은 만들지 않는다(`COVERAGE.md`의 signed URL OPT-OUT — Phase 6 몫). 업로드 뒤 DB 저장 전에 죽어 생기는 고아 객체는 업로드 의도 표 `cert_signature_uploads`(규약 C3, 04.3-02)와 파기 Job(04.3-12)이 닫는다
   - What we know: 서명 이미지는 작고(수십 KB), action payload 한도(256KB) 안에 들어온다. Phase 6은 아직 구현 전이라 GCS 서명 URL 패턴이 이 저장소에 선례가 없다.
   - What's unclear: Phase 6이 구현될 때 이 페이즈의 GCS 경로(`repositories/cert-files.ts`)와 중복 코드가 생길지, 아니면 재사용 가능한 형태로 지금 뽑을 수 있는지.
   - Recommendation: 이 페이즈는 서버 액션 직접 쓰기로 최소 구현하고, Phase 6 계획 때 공용 `lib/gcs.ts` 같은 공유 모듈로의 리팩터를 검토하는 메모를 남긴다(지금 억지로 공유 모듈을 만들지 않는다 — 과설계 방지).

3. **`cert.production_enabled` 플래그를 이 페이즈에서 등록만 하고 실제 라우트 가드에 반영하는 주체는 누구인가? (RESOLVED — 04.3-02의 규약 C1)**
   - **결정:** 플래그 이름은 `cert.enabled`(기본 꺼짐)이고, 기능은 환경 변수 `CERT_FEATURE_ALLOWED`가 `true`이고 **그리고** `cert.enabled`가 켜졌을 때만 열린다(`isCertFeatureEnabled()`, 04.3-02). 환경 게이트가 꺼져 있으면 설정 화면에 그 줄이 없고 저장 액션이 거부한다 — 프로덕션 배포는 Phase 11 전까지 환경 변수를 두지 않는다. 라우트 가드의 주인은 이 페이즈의 **모든 플랜**이다: 확인증 페이지 · 라우트 핸들러(`/print/certs/[id]` 포함) · 서버 액션(공개 · 내부)은 첫 줄에서 공유 가드 `assertCertFeatureEnabled()`(`lib/certs/feature-guard.ts`, 04.3-02)를 부르고, 라우트나 액션을 더하는 플랜은 페이지를 거치지 않는 직접 호출 테스트로 가드를 증명한다. 로컬 E2E · 통합 테스트만 환경 게이트를 켠다
   - What we know: ROADMAP은 "두 감사를 통과해도 Phase 11의 연결이 끝나기 전에는 켜지 않는다"고 명시 — 이 페이즈는 플래그를 만들고 기본값 `false`로 두되, 라우트(`/c/[token]`, 내부 행사 화면)가 이 플래그를 읽어 꺼져 있으면 접근을 막아야 하는지, 아니면 플래그는 Phase 11이 최종 게이트로만 쓰고 이 페이즈는 개발/스테이징에서 항상 켜 두고 테스트하는지가 불명확.
   - What's unclear: "프로덕션에서 꺼져 있다"는 표현이 환경별(개발=on, 프로덕션=off) 분기를 뜻하는지, 아니면 설정값 자체가 리전 무관하게 `false`이고 배포 환경마다 사람이 다르게 설정하는지.
   - Recommendation: 계획에서 라우트 가드(`isEventExpired`처럼 `getSettingValue(CERT_PRODUCTION_ENABLED)`를 확인해 꺼져 있으면 404)를 명시적으로 태스크화한다.

### Known Threat Patterns for {외부 토큰 링크 + PII}

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| 토큰 추측/열거(같은 행사 링크를 무작위 추측) | Spoofing | 충분한 엔트로피(128비트+) 랜덤 토큰, 순차 ID 미사용(UUID나 `randomBytes(32).toString('base64url')`) |
| 뒤 4자리 무차별 대입 | Spoofing | Pattern 5(사람 슬롯당 5회 실패 → 3분 잠금), 전화번호 뒤 4자리는 경우의 수가 10,000개뿐이라 잠금이 필수 — 이 잠금 없이는 사실상 무의미한 보호 |
| 같은 QR을 공유해 타인이 다른 사람 자리를 제출(D-1102의 "여러 명이 같이 쓴다"는 특성 자체가 위협 표면) | Tampering/Repudiation | "사람마다 1회 제출"을 서버 측 유니크 제약(`cert_winners.submitted_at IS NOT NULL` 체크 또는 unique submission FK)으로 강제, 목록에 보이는 이름 가림(Claude's Discretion 항목)으로 타인이 어떤 이름을 골라 사칭하기 어렵게 |
| 열람 로그 우회(코드 추가 경로에서 `recordAction` 호출을 빠뜨림) | Repudiation | Pattern 3처럼 "먼저 기록, 그다음 복호화" 순서를 강제하는 단일 함수(`revealRrn`)만 노출하고, 다른 경로에서 `decrypt()`를 직접 호출하지 않는다(코드 리뷰·`/cso` 체크리스트 항목) |
| 직원의 주민등록번호 임의 수정(D-1106의 위협 표면, `/cso`가 특히 지목) | Tampering | 정정은 전체 보기 권한 보유자만, 행동 로그에 어느 칸을 고쳤는지 남기되 평문 RRN은 로그에 담지 않음(Pattern 3 anti-pattern과 동일 원칙) |
| 파기 스크립트 오작동으로 세무 기록(건수·금액)까지 삭제 | Tampering/DoS(가용성 상실) | Pitfall 1 — PII 컬럼만 NULL, 행 자체·금액·연결 컬럼은 보존. 스크립트는 dry-run 모드 필수(`scripts/rotate-key.ts` 관례 확인 후 계획에서 dry-run 플래그 설계) |
