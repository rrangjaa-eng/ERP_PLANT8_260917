## Phase Boundary

관리자가 GitHub Actions 워크플로 하나로 최신 Cloud SQL 자동 백업을 임시 인스턴스에 복원해 확인하고 지우며, 그 결과가 관리자 시스템 상태 화면의 「복원 리허설」 항목에 보인다. 복원 절차(워크플로 실행법과 실제 사고 때 수동 복원)를 `docs/OPERATIONS.md`에 적고, 이 페이즈 안에서 리허설을 실제로 한 번 성공시킨다. 사람 목록(`/admin/people`)에 「첫 로그인 전」·「임시 비밀번호 사용 중」 표시를 더한다. 요구사항: OPS-03 (`.planning/ROADMAP.md` Phase 04.4 기준 1~5).

이 페이즈는 Phase 8(전환)에서 Phase 4 원장(견적 줄·프로젝트·번호 카운터)과 Phase 5~7 업무 표에 기대지 않는 코드 두 가지를 떼어 낸 것이다(2026-09-24 사용자 결정). 결정 번호는 Phase 8 논의의 D8-xx를 그대로 쓴다. 이 파일만 읽으면 계획할 수 있게 필요한 결정을 옮겨 두었다 — `08-CONTEXT.md`를 다시 읽을 필요가 없다.

**Phase 8에 남은 것:** demo 행 삭제 워크플로·전환 표시·전환 시각 저장(D8-05), 번호 카운터 26001 초기화(D8-09), 연습용 마스터 보관(D8-06), 전환일·경계 업무·인트라넷 공지(D8-01~D8-04), `docs/OPERATIONS.md` 전환일 체크리스트, 실제 직원 계정 발급(MIG-04)과 마스터 수기 입력(MIG-05). 체크리스트의 「복원 리허설 결과 확인」「전 직원 로그인 상태 확인」 단계는 이 페이즈가 만든 워크플로·상태 화면·표시를 읽는다.

범위 밖: demo 행 삭제·번호 카운터(Phase 8), 전환일 체크리스트(Phase 8), 정기(분기 등) 복원 리허설 스케줄(Deferred), 비밀번호 변경 강제(D-08로 하지 않음).

## Implementation Decisions

결정 번호는 Phase 8 논의(`08-CONTEXT.md`, PR #47)의 번호를 그대로 쓴다. 이 페이즈 몫은 D8-07(표시 부분)·D8-08이다.

### 이미 확정된 입력 (다시 묻지 않음 — 출처가 정본)
- Cloud SQL 자동 백업이 켜져 있다(`scripts/deploy.sh` 200행 부근 `--backup --backup-start-time=18:00 --retained-backups-count=7`, Phase 1 D-06). 상태 화면 「마지막 백업」은 Cloud SQL Admin API(`lib/gcp/cloud-sql-admin.ts` `getLastBackup`, `backupRuns.list`)로 화면 로드 시 조회하고 캐시하지 않으며, 조회할 수 없으면 「확인 불가」다 — D-18
- 운영 작업은 화면 버튼이 아니라 `workflow_dispatch` 워크플로 + 같은 컨테이너 이미지의 Cloud Run Job(WIF)이다. 본보기는 `.github/workflows/account.yml`(`gcloud run jobs execute … --wait`) — OPERATIONS §7. 세션은 gcloud를 직접 쓰지 않는다
- 인스턴스 이름: 스테이징 `plant8-staging-db`, 프로덕션 `plant8-prod-db`(OPERATIONS §1). 운영 DB에는 공인 IP가 없다(`--no-assign-ip`, Cloud SQL 커넥터 + IAM 인증)
- 배포 서비스 계정은 `roles/cloudsql.admin`이다(`scripts/bootstrap-gcp.sh` 119행) — 잘못된 대상을 고르면 운영 인스턴스를 덮어쓸 수 있다
- 비용 상한: 두 환경 합계 $30 안팎(D-06, OPERATIONS §2)
- 초기 비밀번호로 로그인해도 변경을 강제하지 않고 내 계정 화면 배너로 안내한다(`users.password_is_temporary`, `db/schema/auth.ts` 24행) — Phase 1 D-08. 발급은 `/admin/people` 등록 폼이 초기 비밀번호를 한 번 보여 주고(Phase 3), 재발급은 `account.yml` `reset`(OPERATIONS §7)
- 사람이 운영 DB에 직접 명령하지 않는다(CLAUDE.md 금지 규칙)

### 백업·복원 리허설
- **D8-08:** **복원 리허설은 GitHub Actions 워크플로(WIF)가 최신 자동 백업을 임시 Cloud SQL 인스턴스로 복원해 확인하고, 임시 인스턴스를 지운 뒤 결과를 기록한다.** 운영 DB는 건드리지 않는다 — 복원 대상 인스턴스 이름은 워크플로가 만들고 운영 인스턴스 이름과 같으면 거부한다(배포 계정이 `roles/cloudsql.admin`이라 잘못된 대상이면 운영을 덮어쓸 수 있다). 운영 DB에 공인 IP가 없으므로 복원본 확인은 GitHub 러너가 아니라 사설망에 닿는 곳(Cloud Run Job 등)에서 한다. 확인 항목은 최소한 마이그레이션 버전 일치와 핵심 표가 읽히고 비어 있지 않은지이며, 운영 현재 행 수와 직접 비교하지 않는다(백업 뒤 입력으로 차이가 나는 게 정상). 정확한 목록은 계획에서 정한다. 결과(일시·백업 id·성공/실패·소요 시간)는 관리자 시스템 상태 화면의 「복원 리허설」 항목으로 보인다. 전환 전 1회가 필수이고, 필요하면 같은 워크플로를 다시 돌릴 수 있다. 복원 절차 문서(OPS-03)는 이 워크플로 실행법과 실제 사고 시 수동 복원(PITR 포함 여부는 계획에서)을 함께 적는다. 임시 인스턴스 비용은 D-06 예산 안에서 수십 분 수준이어야 한다.

### 계정·로그인 확인
- **D8-07:** **사람 목록(`/admin/people`)에 「첫 로그인 전」·「임시 비밀번호 사용 중」 표시를 더한다.** Phase 8 체크리스트의 「전 직원 로그인 확인」은 이 표시로 한다. D-08(변경 강제 없음)은 유지한다. 표시는 SYSTEM.md의 기존 배지·표 규약을 쓴다. (같은 결정의 운영 규칙 — 전환일까지 비밀번호를 안 바꾼 사람이 있어도 전환하고 그 사람은 전환 뒤 재발급한다, ROADMAP Phase 8 기준 2 문구를 「목표이지 전환 조건이 아니다」로 맞춘다 — 는 Phase 8 몫이다.)

### 분리로 생긴 조정 (2026-09-24, 이 PR)
- 리허설은 이 페이즈 안에서 한 번 실제로 성공시킨다(OPS-03 「1회」). 프로덕션 인스턴스가 그때 없거나 비어 있으면 스테이징으로 증명한다 — 어느 환경에서 돌릴지는 계획에서 정한다. 결과 기록에는 원본 인스턴스(스테이징/프로덕션)가 들어가야 한다: Phase 8 기준 5가 전환 전에 **프로덕션 원본** 성공 기록을 요구하고, 스테이징 기록은 그 조건을 채우지 않는다
- 복원본 확인 항목은 계획 시점 main의 스키마로 정한다. Phase 4 원장 표는 아직 main에 없을 수 있으므로 특정 업무 표에 의존하지 않는 항목(마이그레이션 버전, `users`·설정·권한 같은 Phase 1~3 표)으로 시작하고, 표 목록을 한 곳에 두어 나중 페이즈가 더할 수 있게 한다
- 04.2도 같은 상태 화면에 「마지막 tick」·「이메일 미설정」을 더한다. 두 페이즈는 `domain/system-status`·`app/(app)/admin/system-status/page.tsx`에 항목을 더하기만 하고 서로의 항목을 고치지 않는다
- 사람 목록은 이미 느리다(issue #56: `listPeople` → `toPersonDto`가 사람마다 팀·계급·프로젝트를 따로 조회, 개발 서버 189명 3.5초). 표시를 위해 사람별 쿼리를 더하지 않는다 — 목록 조회(`repositories/users.ts` `listUsers`)의 칸을 쓴다
- 지금 `PersonDto`(`domain/people/index.ts` 43행, `PERSON_DTO_SPEC` 56행)에는 `passwordIsTemporary`가 없다. 두 표시를 DTO에 더하면 `PERSON_DTO_SPEC`의 정보 노출 매핑과 누수 스캔이 함께 바뀐다
- 관리자 재발급(`account.yml reset`, `domain/auth/accounts.ts` 89~91행)은 세션을 지우고 `password_is_temporary`를 다시 켠다 — 「임시 비밀번호 사용 중」이 다시 보인다. D8-07의 「전환 뒤 재발급」이 이 경로다
- `docs/OPERATIONS.md`는 지금 248줄이고 300줄 상한(`test/unit/docs-limits.test.ts`)이 있다. 04.2·04.3과 Phase 8 체크리스트도 이 파일에 절을 더하므로 남은 약 50줄을 나눠 쓴다 — 복원 절차는 짧게 쓰거나 계획에서 다른 문서로 나누는 방법을 정한다
- REQUIREMENTS의 OPS-06(상태 화면 「복원 리허설」 항목)은 Phase 1 Complete로 표시되어 있지만 그 항목은 아직 화면에 없다(`app/(app)/admin/system-status/page.tsx`는 배포 버전·DB 커넥션·마지막 백업만). 이 페이즈가 그 항목을 만든다 — 계획 단계에서 추적표 비고로 남긴다
- 마이그레이션 번호는 Phase 4(0011~0016)와 병렬 페이즈(04.1~04.3, 각자 계획 단계에서 정한다 — 04.3-CONTEXT 73행)와 겹치지 않게 계획 단계에서 정한다. 번호는 `pnpm db:generate`가 journal 다음 인덱스로 매기므로 손으로 붙이지 않는다. 머지 직전에 main을 합치고 자기 마이그레이션을 지운 뒤 `pnpm db:generate`를 다시 돌린다 — drizzle `migrate()`는 journal `when`이 마지막 적용보다 늦은 마이그레이션만 적용한다. 병렬 페이즈가 journal 순서 검사 테스트를 먼저 main에 넣었으면 그것을 따른다

### Claude's Discretion
- 복원 리허설 결과를 어디에 기록할지(운영 DB 한 줄을 Cloud Run Job으로 쓰기 대 GCS 파일) — 사람이 운영 DB에 직접 명령하지 않는다는 금지 규칙을 지킨다
- 「첫 로그인 전」을 기록할 칸의 형태(예: 첫 로그인 시각 또는 마지막 로그인 시각)와 재발급 뒤 다시 「첫 로그인 전」으로 볼지. `sessions` 행은 로그아웃·관리자 재발급(`domain/auth/accounts.ts` 89행)·「모든 세션 로그아웃」(`revokeAllSessions`, `domain/auth/password.ts` 97~103행) 때 지워지므로(`deleteUserSessions`) 판정 근거로 쓰지 않는다. 이미 로그인한 기존 계정(스테이징 검증 계정 등)을 새 칸 도입 때 어떻게 채울지
- 임시 인스턴스 이름 규칙(원본 이름 + 접미사·실행 id 등)과 실패·중단 때 남은 임시 인스턴스를 치우는 방식
- 복원 시 PITR까지 절차에 넣을지
