# 04.4 UI-SPEC 독립 디자인 교차 리뷰 (Opus, Codex 대체)

대상: `.planning/phases/04.4-restore-rehearsal-and-login-status/04.4-UI-SPEC.md` (+ PLAN의 UI 부분은 스펙 인용 범위에서 확인)
기준: docs/design/SYSTEM.md · tokens.css · CLAUDE.md §7. 잠긴 결정 「따로 두고 감지」(D8-07/D8-08)는 다루지 않음.

## 1. 정보 계층
- 참고 — 실패가 「확인 불가」보다 덜 두드러짐 (UI-SPEC.md:98,103,132). 「확인 불가」는 테두리 태그인데 「실패」는 일반 글자. 실패 쪽이 더 급한데 위계가 거꾸로다. 형제 「마지막 백업」 행과 맞춘 선택이라 막는 문제는 아님. 해결: 다음 시스템 개정 때 KvList 값의 상태 낱말(성공/실패)만 StatusTag variant="text"로 두는 규칙을 검토.
- 참고 — 원본 인스턴스 세그먼트는 그 화면에서 항상 같은 값 (UI-SPEC.md:136). 감사 흔적으로 남기는 것은 괜찮지만 2순위 위치(결과 바로 뒤)라 일시보다 먼저 읽힌다. 해결: 일시를 원본 앞으로 옮기거나 그대로 둔다(경미).

## 2. 빠진 상태
- 참고 — 오래된 성공(stale). 마지막 성공이 몇 달 전이어도 「성공」으로 보인다. 정기 리허설·경보는 Deferred라 범위 밖이지만, 일시가 이미 보이니 판단 재료는 있다. 해결: Deferred 항목에 "경과일 표시"를 남긴다.
- 로딩/빈/오류/부분/잠김/보관됨/노출 꺼짐 상태는 모두 정의됨 (UI-SPEC.md:112-114, 164-166, UI Considerations 표). 누락 없음.

## 3. 사용자 여정
- 참고 — 「전 직원 로그인 확인」(D8-07)을 하려면 관리자가 목록 전체를 훑어야 한다. 시스템이 셀 수 있는 값(첫 로그인 전 N명)을 사람이 센다 — §7 "계산할 수 있는 것은 묻지 않는다". 해결: 이번 페이즈 범위를 넓히지 않는다면, 후속으로 배지 있는 사람을 목록 위로 정렬하거나 개수 한 줄을 두는 것을 백로그에 남긴다. 새 기능이라 이번엔 막는 문제 아님.
- 실패 → 「실행 기록」 링크 → Actions 로그로 다음 행동이 이어짐. 끊김 없음.

## 4. 토큰 준수
- 새 색·서체·radius 없음. --muted/--accent, --fs-xs/sm/base, --lh-table/head/body, --s-1/3/5, --cell-pad-*, --touch-min 모두 기존 토큰. 위반 0건.

## 5. 구현자가 헷갈릴 부분
- 참고 — 스펙 본문이 리비전 이력·정정·근거로 너무 길다(줄 15 한 줄에 8차 리비전 서술). 구현자가 "규칙"과 "이력"을 구분하기 어렵다. 해결: 실행 전 요약 표(문구 표 :123-132, 배지 표 :157-162, 반응형 표)만 읽으면 되도록 PLAN에 인용하면 충분. 내용 모순은 찾지 못함.
- 참고 — 방어적 렌더 두 개(run_url NULL 실패 행 :130, NULL+false 배지 :162)는 "발생 경로 없음"이라 명시돼 있어 테스트를 쓸지 헷갈릴 수 있다. 해결: 단위 테스트 1건씩만(렌더 생략 확인) 두면 된다.
