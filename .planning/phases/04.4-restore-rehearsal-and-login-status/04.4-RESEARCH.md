**백업·복원 리허설**
- **D8-08:** 복원 리허설은 GitHub Actions 워크플로(WIF)가 최신 자동 백업을 임시 Cloud SQL 인스턴스로 복원해 확인하고, 임시 인스턴스를 지운 뒤 결과를 기록한다. 운영 DB는 건드리지 않는다 — 복원 대상 인스턴스 이름은 워크플로가 만들고 운영 인스턴스 이름과 같으면 거부한다. 운영 DB에 공인 IP가 없으므로 복원본 확인은 GitHub 러너가 아니라 사설망에 닿는 곳(Cloud Run Job 등)에서 한다. 확인 항목은 최소한 마이그레이션 버전 일치와 핵심 표가 읽히고 비어 있지 않은지이며, 운영 현재 행 수와 직접 비교하지 않는다. 정확한 목록은 계획에서 정한다. 결과(일시·백업 id·성공/실패·소요 시간)는 관리자 시스템 상태 화면의 「복원 리허설」 항목으로 보인다. 전환 전 1회가 필수이고, 필요하면 같은 워크플로를 다시 돌릴 수 있다. 복원 절차 문서(OPS-03)는 이 워크플로 실행법과 실제 사고 시 수동 복원(PITR 포함 여부는 계획에서)을 함께 적는다. 임시 인스턴스 비용은 D-06 예산 안에서 수십 분 수준이어야 한다.

**계정·로그인 확인**

## Summary

이 페이즈는 서로 독립적인 두 산출물을 만든다: (1) GitHub Actions `workflow_dispatch` + Cloud Run Job으로 최신 자동 백업을 임시 Cloud SQL 인스턴스에 복원·확인·삭제하는 워크플로와 그 결과를 관리자 상태 화면에 보이는 배선, (2) 사람 목록에 "첫 로그인 전"·"임시 비밀번호 사용 중" 두 표시를 더하는 것. 두 산출물 모두 **새 npm 패키지가 필요 없다** — Cloud SQL 연결(`@google-cloud/cloud-sql-connector`)·Admin API 클라이언트(`@googleapis/sqladmin`)·Drizzle·better-auth가 이미 의존성에 있다.

복원 워크플로는 `account.yml`과 같은 뼈대(WIF `google-github-actions/auth` → `gha-deployer` SA, `infra/names.sh` source)를 쓰되, 공인 IP가 없는 인스턴스를 GitHub 러너가 직접 열 수 없으므로 두 단계로 나뉜다: ① GitHub 러너가 직접 `gcloud sql` 명령(인스턴스 생성·백업 복원·삭제)을 실행한다 — 이 명령들은 Cloud SQL Admin API 호출이라 VPC 접근이 필요 없다(`bootstrap-gcp.sh`의 `gha-deployer`는 `roles/cloudsql.admin`을 이미 갖고 있다). ② 복원된 인스턴스의 **데이터**를 읽는 확인 단계만 VPC 안에 있는 Cloud Run Job으로 위임한다 — `db/client.ts`가 이미 `CLOUD_SQL_CONNECTION_NAME` 환경변수 하나로 커넥터를 초기화하므로, 이미 배포된 Job(또는 새로 만드는 전용 Job)을 `gcloud run jobs execute JOB --update-env-vars=CLOUD_SQL_CONNECTION_NAME=<임시 인스턴스 연결명>,...`으로 이번 1회 실행에만 다른 인스턴스를 가리키게 할 수 있다(공식 문서로 확인: 실행 시점 오버라이드는 job 정의 자체를 바꾸지 않는다).

결과 기록은 **운영 DB 한 줄 + Cloud Run Job**을 권한다(GCS 파일 대신) — 이유는 아래 "Claude's Discretion 판단" 절에 있다. 「첫 로그인 전」은 better-auth의 `after` 훅(`domain/auth/hooks.ts` 85~118행, 이미 로그인 성공 시점에 실행된다)에 한 줄을 더해 `users.first_login_at`을 최초 1회만 채우는 방식을 권한다 — 사람 목록 조회에 쿼리를 더하지 않는다(이미 `listUsers`가 읽는 `users` 행에 칼럼만 늘어난다).

**Primary recommendation:** 리허설 결과는 새 테이블(`restore_rehearsals`, 마이그레이션 하나)에 Cloud Run Job이 쓰고 상태 화면이 그 최신 행을 읽게 하라. 확인 대상 표는 `domain/ops/restore-check-tables.ts`에 배열 레지스트리로 두어 이 페이즈는 Phase 1~3 표(users·roles·permission_matrix·visibility_matrix·code_items·org_units/teams·settings_simple/historized·vendors)만 채우고 뒤 페이즈가 항목을 더하게 하라. 「첫 로그인 전」은 `users.first_login_at timestamp` nullable 칼럼 + better-auth `after` 훅에서 `if (!user.firstLoginAt) update`로 구현하라.

| 운영 DB 한 줄(신규 테이블) | GCS 객체(JSON 파일) | GCS는 이 저장소에 전례가 없다(`@google-cloud/storage` 신규 의존성, 버킷 생성·IAM 바인딩·수명주기 정책 필요) — 새 인프라 자원 하나가 늘고 D-06 비용에 항목이 추가된다. DB 한 줄은 이미 있는 커넥션·마이그레이션·백업 대상에 얹힌다(그 DB 자체가 백업된다는 이점도 있다) |
| Cloud Run Job이 확인+기록 둘 다 겸함 | GitHub Actions Job Summary만 남기고 DB에 안 씀 | 상태 화면(D-18, 캐시 없이 매 로드 조회)이 요구하는 "화면에서 확인"을 만족하지 못한다 — Actions 로그는 관리자가 반복해서 보는 화면이 아니다 |
| `gcloud sql instances clone`(+ PITR 타임스탬프) | `gcloud sql backups restore` | clone은 원본 인스턴스가 켜져 있어야 하고 원본에 약간의 부하를 준다는 보고가 있다(정확한 오버헤드는 미검증). 이 프로젝트는 "최신 자동 백업"을 검증하는 것이 목적이라 백업 ID 기반 `backups restore`가 요구사항(D8-08 "최신 자동 백업")과 더 직접적으로 대응한다 |

**Installation:** 해당 없음 — 새 패키지 설치가 필요 없다.

**버전 확인:** `@google-cloud/cloud-sql-connector`·`@googleapis/sqladmin`는 `package.json`에 이미 고정된 버전으로 존재함을 직접 읽어 확인했다(신규 설치가 아니므로 레지스트리 재조회 불필요).

## Package Legitimacy Audit

**이 페이즈는 새 외부 패키지를 설치하지 않는다.** 필요한 GCP 클라이언트·ORM·인증 라이브러리가 모두 이미 `package.json`에 있다(위 Standard Stack 표, `[VERIFIED: package.json:38-42]`). 따라서 패키지 정당성 감사 게이트는 해당 없음 — 표는 생략한다.

**만약 계획 단계에서 "최신 SUCCESSFUL 백업 id 조회"를 CLI(`gcloud`)가 아니라 코드에서 하기로 정하면**, `@googleapis/sqladmin`의 `backupRuns.list`를 재사용하면 되므로 그 경우에도 새 패키지는 없다.

### Pattern 1: 실행 시점 인스턴스 오버라이드 (Cloud Run Job)

**What:** 이미 배포된(또는 전용) Cloud Run Job을 매번 다른 Cloud SQL 인스턴스에 연결하려면 `gcloud run jobs execute`의 `--update-env-vars`로 그 실행 1회만 환경변수를 덮어쓴다. Job 정의(스펙) 자체는 바뀌지 않는다.
**When to use:** 임시 복원 인스턴스처럼 이름이 실행마다 달라지는 대상을 확인할 때.
**Example:**
```bash
# Source: https://docs.cloud.google.com/sdk/gcloud/reference/beta/run/jobs/execute (WebSearch로 확인, 2026-09)
gcloud run jobs execute plant8-staging-restore-verify \
  --region "$REGION" --project "$PROJECT" \
  --update-env-vars="CLOUD_SQL_CONNECTION_NAME=${TEMP_CONN_NAME}" \
  --wait
```
[CITED: docs.cloud.google.com/sdk/gcloud/reference/beta/run/jobs/execute — "You can override the arguments, environment variables, number of tasks, and task timeout... The parameters you specify affect only this execution and not subsequent ones, because the underlying job definition remains unchanged."]

**주의 — 미검증 세부사항([ASSUMED], Open Question 2 참고):** `db/client.ts`가 커넥터 라이브러리(`@google-cloud/cloud-sql-connector`)로 접속하므로 이론상 `CLOUD_SQL_CONNECTION_NAME` 환경변수만 바꾸면 되고 `--set-cloudsql-instances`(Cloud Run 자체의 Unix 소켓 사이드카) 재설정은 필요 없어 보인다 — 커넥터가 Admin API로 직접 mTLS 접속을 맺기 때문이다. 그러나 `deploy.sh`는 이 Job들에 `--set-cloudsql-instances="$CONN_NAME"`도 같이 붙이고 있어(305~322행), 이 플래그가 정말 불필요한 중복인지 아니면 커넥터가 우회하지 못하는 어떤 네트워크 경로에 필요한지는 이 저장소 코드만으로는 확정할 수 없다. **계획은 첫 실제 리허설 실행에서 이 가정이 맞는지 직접 확인하는 단계를 넣어야 한다**(예: 전용 `restore-verify` Job을 새로 만들어 `--set-cloudsql-instances` 없이 배포하고, 실행 시 `--update-env-vars`만으로 임시 인스턴스에 붙는지 스테이징에서 실측).

### Pattern 2: 이름 충돌 가드 (되돌릴 수 없는 대상 보호)

**What:** 복원 대상 인스턴스 이름이 운영 인스턴스 이름과 같으면 어떤 gcloud 명령도 실행하기 전에 중단한다.
**When to use:** `scripts/deploy.sh`가 이미 이런 가드를 여러 곳에 두고 있다(`require_prod_image`, `require_clean_tree`) — STAGE 변수 + 조기 `exit`.
**Example:**
```bash
# 참고 패턴: scripts/deploy.sh require_prod_image() (141~151행)와 같은 형태
TEMP_INSTANCE="plant8-${ENV_SHORT}-restore-$(date +%s)"
for guarded in plant8-staging-db plant8-prod-db; do
  if [ "$TEMP_INSTANCE" = "$guarded" ]; then
    echo "NameGuardViolation: generated target equals a real instance name ($guarded)" >&2
    exit 1
  fi
done
```
타임스탬프/실행 id를 접미사로 쓰면 이 충돌은 사실상 발생하지 않지만(Claude's Discretion 항목), **가드 자체는 값을 신뢰하지 않고 항상 실행**해야 한다(D8-08 요구사항 원문 — "이름이 같으면 거부").

### Pattern 3: 결과 조회는 화면 로드 시 직접(D-18)

**What:** `getLastBackup`와 같은 결 — 캐시 없이 화면 로드마다 조회하고, 조회 실패는 "확인 불가"로 구분해 렌더한다.
**When to use:** `getSystemStatus`에 필드를 추가할 때 그대로 재사용.
**Example:**
```typescript
// Source: domain/system-status/index.ts:61-77 (실제 파일, 같은 try/catch 패턴 재사용)
let restoreRehearsal: SystemStatus["restoreRehearsal"];
try {
  restoreRehearsal = await getLastRestoreRehearsalFn(viewer);
} catch (e) {
  log.warn("status.restore_rehearsal_unavailable", { message: e instanceof Error ? e.message : String(e) });

}
```

### Anti-Patterns to Avoid

- **워크플로 입력을 `run:` 블록에 `${{ inputs.x }}`로 직접 문자열 삽입**: 이미 `account.yml`이 `env:` 매핑 후 `$INPUT_X`로만 읽는 안전한 패턴을 쓴다(43~57행) — 새 워크플로도 동일하게, 절대 `${{ inputs.* }}`를 `run:` 셸 문자열에 직접 넣지 않는다(GitHub Actions script injection 방지, 아래 Security Domain 참고)
- **사람 목록에 사람별 쿼리 추가**: `toPersonDto`가 이미 사람마다 `teamAtDate`·`findRoleById`를 부른다(issue #56, 189명 3.5초 실측 — CONTEXT.md 43행). 새 표시는 `UserRow`(즉 `listUsers`가 이미 한 번에 가져오는 행)의 칼럼이어야 한다 — `toPersonDto` 안에 새 조회를 넣지 않는다
- **`sessions` 행 존재로 "로그인한 적 있음"을 판정**: `revokeAllSessions`(재발급·전체 로그아웃)가 세션을 지운다(`domain/auth/password.ts` 97~103행, `domain/auth/accounts.ts` 89행) — 세션이 없다고 "첫 로그인 전"으로 보면 재발급 후 정상 로그인한 사람도 틀리게 표시된다. 반드시 `users` 표에 별도 칼럼(`first_login_at`)을 둔다
- **restore_rehearsals 결과를 `domain/action-log`에 기록**: 행동 로그(`CORE_ACTION_TYPES`)는 "사람이 앱 안에서 한 행동"의 감사 기록이고 `restore`라는 액션 타입은 이미 ADMN-12 보관함 복원(archive 재복원)에 쓰이고 있다(`domain/action-log/record.ts` 25행) — 이름이 같다고 이 값을 재사용하면 의미가 섞인다. 복원 리허설은 CI/CD가 하는 인프라 작업이라 `log.info("restore_rehearsal.*", …)` 구조화 로그 + 전용 테이블로 남긴다

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| 최신 성공 백업 찾기 | 백업 목록을 받아 직접 날짜 파싱·정렬 | `gcloud sql backups list --filter="status=SUCCESSFUL" --sort-by=~startTime --limit=1` (서버 사이드 필터·정렬) [CITED: WebSearch 요약, docs.cloud.google.com/sdk/gcloud/reference/sql/backups/list] | 클라이언트 정렬은 페이지네이션·타임존 버그의 흔한 원인 |
| 임시 인스턴스 정리(실패 시 잔존 방지) | 커스텀 정리 스크립트를 별도 스케줄로 | 워크플로 안에서 `trap`/`always()` 스텝으로 삭제를 보장(GitHub Actions `if: always()` 스텝 또는 bash `trap ... EXIT`) — `deploy.sh`가 `smoke_failed()`에서 이미 "실패해도 정리/롤백은 반드시"라는 원칙을 쓴다 | 별도 스케줄은 그 자체로 또 다른 실패 지점이고 비용이 계속 샌다(D-06) |
| Cloud SQL 커넥션 문자열 조립 | 직접 `postgres://user:pass@host:port/db` 조립 | `@google-cloud/cloud-sql-connector`의 `Connector.getOptions()` — 이미 `db/client.ts`가 이 방식으로 IAM 인증·mTLS·인증서 갱신을 처리한다 | 직접 조립하면 IAM 토큰 갱신·mTLS 인증서 관리를 다시 구현해야 한다 |

**Key insight:** 이 페이즈에서 "직접 만들 것"은 사실상 얇은 접착 코드(recording CLI, registry 배열, KvList 행 하나, DTO 필드 두 개)뿐이다 — GCP 쪽 무거운 로직(백업 조회·복원·커넥션)은 전부 기존 gcloud 명령/기존 npm 패키지가 이미 한다. 새로 발명해야 할 로직은 "이름 가드"와 "확인 표 레지스트리를 순회하며 실패를 모으는 것" 정도다.

## Common Pitfalls

### Pitfall 1: 복원 대상 인스턴스는 미리 존재해야 한다 (신규 인스턴스도 create 필요)
**What goes wrong:** `gcloud sql backups restore BACKUP_ID --restore-instance=TEMP`만 실행하면 "instance not found" 오류가 난다.
**Why it happens:** `restore` 명령은 **기존 인스턴스에 백업 내용을 덮어쓰는** 동작이다 — 새 인스턴스를 만들어 주지 않는다. `--restore-instance`가 "새 이름 또는 기존 이름"으로 문서화돼 있지만, 실제로는 *먼저 `gcloud sql instances create`로 빈 인스턴스를 만든 뒤* restore해야 한다는 것이 통용되는 절차다.
**How to avoid:** 워크플로 순서를 반드시 `instances create` → `backups restore`로 둔다. `deploy.sh`의 `ensure_sql_instance()`(186~218행)와 같은 플래그(`--no-assign-ip --network=... --database-flags=cloudsql.iam_authentication=on --database-version=POSTGRES_16`)로 임시 인스턴스를 만들되, `--backup`(자동 백업)·`--deletion-protection`은 임시 인스턴스에는 굳이 켜지 않는다(비용·삭제 편의).
**Warning signs:** `restore` 스텝이 "NOT_FOUND"로 실패.
[CITED: WebSearch 요약, docs.cloud.google.com/sql/docs/postgres/backup-recovery/restoring — "TARGET_INSTANCE_NAME 매개변수는 새 또는 기존 대상 인스턴스의 이름일 수 있다"는 문구와 실제 커뮤니티 절차(oneuptime.com 블로그 등)가 모두 "먼저 인스턴스를 만든다" 순서를 전제한다. 이 지점은 GCP 공식 페이지 원문을 직접 열어보지 못해(도구 접근 차단) 완전히 확정하지 못했다 — Open Question 1 참고]

### Pitfall 2: PITR은 자동 백업과 별개 설정이며 이 프로젝트는 켜져 있지 않다
**What goes wrong:** "복원 절차에 PITR도 넣자"고 계획했다가 실제로는 특정 시각으로 복원할 수 없다는 것을 실행 중에 발견한다.
**Why it happens:** Point-in-time recovery는 자동 백업(`--backup`)과 별개로 WAL 아카이빙/바이너리 로그 보존을 켜야 한다. `scripts/deploy.sh`의 `ensure_sql_instance()`(195~202행)가 실제로 인스턴스를 만드는 명령을 확인한 결과:
```
--storage-type=HDD --storage-size="$DB_STORAGE_GB" \
--storage-auto-increase --storage-auto-increase-limit="$DB_STORAGE_LIMIT_GB" \
--availability-type=ZONAL --backup --backup-start-time=18:00 --retained-backups-count=7 \
--no-assign-ip --network="projects/$PROJECT/global/networks/$NETWORK" \
--database-flags=cloudsql.iam_authentication=on --deletion-protection
```
[VERIFIED: scripts/deploy.sh:195-202] — `--enable-point-in-time-recovery`(또는 동등 플래그)가 **없다**. 이 인용은 이 저장소 인스턴스 생성 명령의 전체 플래그 목록이며, PITR 관련 플래그가 없다는 것은 존재하는 플래그 목록으로 확인 가능한 사실이다(부재 증거이지만, 이 경우는 "이 프로젝트의 생성 명령에 무엇이 있는가"라는 완전한 목록에 대한 긍정 확인이다).

**Warning signs:** 없음(사고가 나기 전까지는 드러나지 않는 종류의 갭 — 그래서 문서화가 중요하다).

### Pitfall 3: IAM DB 사용자가 복원 후에도 존재하는지는 실제로 확인해야 한다
**What goes wrong:** 복원본에 접속하려는데 `DB_IAM_USER`(`plant8-{env}-runtime@{project}.iam`) 역할이 없어서 커넥터가 인증 실패한다.
**Why it happens:** IAM 데이터베이스 인증 사용자는 Postgres 카탈로그(`pg_roles`)에 실제 role로 존재하므로 물리적 백업/복원에 포함될 가능성이 높지만, WebSearch로 찾은 공식 문서는 이를 명시적으로 확정하지 않았다("복원은 원본의 설정·DB·사용자를 가져와 대상에 설정한다"는 요약만 확인됨, 상세 IAM 사용자 언급 없음).
**How to avoid:** 확인 Job이 접속에 실패하면 "확인 불가/실패"로 기록하고, 계획에는 첫 실행에서 이 가정을 검증하는 단계를 넣는다. 만약 IAM 사용자가 없다면, 복원 직후 `gcloud sql users create "$iam_user" --instance="$TEMP" --type=cloud_iam_service_account`(deploy.sh의 `ensure_sql_db_users` 230~235행과 동일 명령)를 한 번 더 실행해 보정한다 — 멱등하므로 안전하다.
**Warning signs:** 확인 Job 실행이 인증 오류(`PERMISSION_DENIED` 또는 Postgres `28000`)로 실패.

### Pitfall 4: `docs/OPERATIONS.md` 300줄 상한과 04.2·04.3·Phase 8의 경합
**What goes wrong:** 복원 절차를 자세히 쓰다가 `test/unit/docs-limits.test.ts`의 300줄 검사에 걸린다.
**Why it happens:** 파일이 이미 248줄이고(`[VERIFIED: wc -l docs/OPERATIONS.md → 248]`), 04.2·04.3·Phase 8도 같은 파일에 절을 더한다(CONTEXT.md 46행).
**How to avoid:** 새 절은 짧게 — 워크플로 실행법(3~5줄), 결과 읽는 법(2~3줄), 수동 복원 절차 요지(핵심 명령만, PITR 비활성 한 줄 고지), 자동 백업 확인법(이미 §2에 일부 있음, 중복 없이 참조만). 목표 15~20줄 이내로 잡는다. 상세 절차(모든 gcloud 플래그)는 워크플로 파일(`restore-rehearsal.yml`) 자체의 주석에 두고 OPERATIONS.md는 "무엇을·어디서" 수준으로만 적는다(§4 배포 런북이 이미 이런 밀도로 쓰여 있다).
**Warning signs:** `pnpm test:unit`의 `docs-limits.test.ts` 실패.

### Pitfall 5: `pnpm db:generate`가 매기는 번호는 로컬 journal 상태에 의존한다 — 04.4 브랜치 작업 중 계속 재확인 필요
**What goes wrong:** 계획에서 "0030"으로 고정해 두고 실제 실행 때 다른 번호가 나온다.
**Why it happens:** `drizzle-kit generate`는 `db/migrations/meta/_journal.json`의 마지막 `idx`+1을 다음 파일에 매긴다(로컬에서 직접 확인: `_journal.json`은 현재 idx 0~10, 11개 항목 — `[VERIFIED: db/migrations/meta/_journal.json, entries 배열 길이 11, 마지막 idx=10, tag="0010_revenue_entries"]`). 병렬 브랜치(04.1~04.3)가 먼저 머지되면 그 브랜치들의 마이그레이션이 main에 들어와 다음 idx가 올라간다.
**How to avoid:** 좌표 조정 문서(사용자 제공 제약)가 이미 04.4의 목표 범위를 0030~0034로 지정했다 — 계획 단계에서는 이 범위를 "목표"로만 적고, 실제 파일 이름은 `pnpm db:generate` 실행 시점에 로컬 journal이 매기는 그대로 받아들인다. 머지 직전 규칙(merge main → delete own migration → `pnpm db:generate` 재실행)을 계획의 마지막 Task로 명시한다. 04.1이 만들기로 한 `test/unit/db/migration-journal.test.ts`(idx 연속·tag=idx·when 증가 검사)가 main에 있으면 그 테스트를 그대로 통과시키는 것으로 검증한다 — 없으면 이 페이즈가 그 경로에 만든다(CONTEXT.md 지시 그대로).
**Warning signs:** `migration-journal` 테스트 실패, 또는 `pnpm db:generate` 결과 파일 이름이 계획 문서와 다름(정상 — 계획을 갱신).

## Open Questions

1. **`gcloud sql backups restore`가 정말 대상 인스턴스를 먼저 만들어야 하는가, 아니면 명령 자체가 생성까지 하는가?**
   - What we know: 공식 문서 페이지(`docs.cloud.google.com/sql/docs/postgres/backup-recovery/restoring`, `.../sdk/gcloud/reference/sql/backups/restore`)에 직접 접근이 이 세션에서 프록시로 차단됐다(`EGRESS_BLOCKED`). WebSearch 스니펫은 "새 또는 기존 인스턴스 이름"이라는 문구와 "기존 인스턴스면 먼저 존재해야 한다"는 커뮤니티 절차를 동시에 보여줘 애매하다.
   - What's unclear: "새 인스턴스 이름"을 주면 명령이 인스턴스를 만들어 주는지, 아니면 항상 사전 생성이 필요한지.
   - Recommendation: 계획에 두 경로를 다 넣지 말고, 첫 실제 실행(스테이징, 성공 기준 2가 요구하는 "실제로 한 번 성공")에서 `instances create` 선행 스텝을 기본값으로 두고 실행 로그로 확정한다 — 틀려도(즉 create가 불필요해도) 멱등하게 스킵되므로 안전한 쪽으로 설계돼 있다.

2. **Cloud Run Job 실행 시 `--update-env-vars`만으로 다른 Cloud SQL 인스턴스에 붙을 수 있는가(A2)?**
   - What we know: 공식 문서는 실행 오버라이드가 "arguments, environment variables, number of tasks, task timeout"에 적용된다고만 말하고 Cloud SQL 첨부(`--set-cloudsql-instances`)는 언급하지 않는다. `db/client.ts`는 커넥터 라이브러리로 접속하므로 이론상 Cloud Run의 소켓 사이드카와 무관하게 동작할 수 있다.
   - What's unclear: `deploy.sh`가 실제로 `--set-cloudsql-instances`를 왜 같이 붙이는지(방어적 중복인지 필수인지) 이 저장소 커밋 이력·주석에 설명이 없다.
   - Recommendation: 계획의 첫 Task로 "전용 `restore-verify` Job을 `--set-cloudsql-instances` 없이 배포해 스테이징의 기존 인스턴스에 `--update-env-vars`로 붙는지"를 먼저 검증하는 저위험 스파이크를 넣는다(임시 인스턴스 없이도 검증 가능 — 기존 `plant8-staging-db`를 대상으로 시험).

3. **REQUIREMENTS.md 추적표의 OPS-03 갱신을 이 페이즈 계획이 직접 수행할지, Phase 8이 마지막에 정리할지?**
   - What we know: CONTEXT.md·ROADMAP.md는 이미 04.4를 OPS-03의 정본으로 취급한다. REQUIREMENTS.md 자체(`2026-09-23` 갱신본)는 아직 `Phase 8`로 남아 있다.
   - What's unclear: 다른 병렬 페이즈(04.1~04.3)도 같은 추적표 파일을 동시에 편집 중일 수 있어 머지 충돌 위험이 있다.
   - Recommendation: 계획의 마지막 Task로 이 한 줄만 바꾸는 작은 diff를 넣고, 병렬 브랜치 머지 순서와 무관하게 재적용 가능하도록 커밋을 분리해 둔다.
