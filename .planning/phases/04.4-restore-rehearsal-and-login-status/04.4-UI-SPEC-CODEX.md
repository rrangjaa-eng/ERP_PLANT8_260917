## 2차 검토 원문

1. **Major — Backfill still mislabels previously logged-in users as 「첫 로그인 전」.**  
   **Evidence:** [UI-SPEC.md:160](/home/user/ERP_PLANT8_260917/.planning/phases/04.4-restore-rehearsal-and-login-status/04.4-UI-SPEC.md:160) leaves `first_login_at=NULL` whenever login logs are absent and the password is temporary. But [record.ts:127](/home/user/ERP_PLANT8_260917/domain/action-log/record.ts:127) permits disabling login logs. A successful login without changing the temporary password therefore produces this exact combination. Successful attempts are independently recorded at [hooks.ts:94](/home/user/ERP_PLANT8_260917/domain/auth/hooks.ts:94). The prospective fix at spec line 162 does not repair these existing accounts.  
   **Fix:** Backfill from the earliest trustworthy successful event across `action_log` and `login_attempts`, matching the latter to the account’s verified identity. Define handling for legacy accounts whose history cannot be established; absent optional logs alone must not establish “never logged in.”

2. **Major — Multiple rehearsal failures have no deterministic displayed stage.**  
   **Evidence:** [UI-SPEC.md:115](/home/user/ERP_PLANT8_260917/.planning/phases/04.4-restore-rehearsal-and-login-status/04.4-UI-SPEC.md:115) requires exactly one failure stage, while [line 131](/home/user/ERP_PLANT8_260917/.planning/phases/04.4-restore-rehearsal-and-login-status/04.4-UI-SPEC.md:131) requires cleanup even after another failure. Verification and cleanup can therefore both fail. Neither the copy contract nor `failed_stage` schema defines which wins, potentially concealing an undeleted temporary instance behind 「실패 · 검증」.  
   **Fix:** Define precedence explicitly: cleanup failure → `정리`; otherwise restoration failure → `복원`; otherwise verification failure → `검증`. Preserve all underlying failures in the execution log and add the combined-failure case to the rendering contract.

3. **Major — The phone fix does not provide a SYSTEM-compliant layout for the new badges.**  
   **Evidence:** [UI-SPEC.md:169](/home/user/ERP_PLANT8_260917/.planning/phases/04.4-restore-rehearsal-and-login-status/04.4-UI-SPEC.md:169) explicitly retains six phone columns; line 171 only stacks the badges. The existing [page.tsx:74](/home/user/ERP_PLANT8_260917/app/(app)/admin/people/page.tsx:74) renders all six headers, while [StatusTag.module.css:8](/home/user/ERP_PLANT8_260917/ui/status-tag/StatusTag.module.css:8) prevents the newly added long badge from wrapping. Stacking reduces the pair’s width but leaves that minimum width in the six-column table. Calling the underlying gap out of scope does not resolve this contract’s phone behavior.  
   **Fix:** Specify P1/P2/P3 placement for this list, including where both badges and the detail action remain accessible. Require the longest badge combination to fit at 360px and at 200% zoom without horizontal scrolling.

## 3차 검토 원문

1. **Major — Google sign-in never clears 「첫 로그인 전」.**  
   [04.4-UI-SPEC.md:171](/home/user/ERP_PLANT8_260917/.planning/phases/04.4-restore-rehearsal-and-login-status/04.4-UI-SPEC.md:171) mandates recording inside the existing success branch, but [hooks.ts:86](/home/user/ERP_PLANT8_260917/domain/auth/hooks.ts:86) returns immediately for every route except `/sign-in/email`. Consequently, a newly issued account can successfully sign in through Google repeatedly while retaining the first-login badge. Both prescribed backfill sources also originate in this email-only hook.
   
   **Fix:** Require the conditional first-login update for successful session creation through every enabled provider. Add a Google-login acceptance case, and document that the current backfill sources cannot establish historical Google-only logins.

2. **Major — The new phone fold loses accessible field relationships.**  
   [04.4-UI-SPEC.md:190](/home/user/ERP_PLANT8_260917/.planning/phases/04.4-restore-rehearsal-and-login-status/04.4-UI-SPEC.md:190) hides the email/rank/team headers and cells, then presents their unlabelled values in a separate spanning row. It defines no accessible association with those field names or the person. The existing name cell is an ordinary `<td>` ([people/page.tsx:85](/home/user/ERP_PLANT8_260917/app/(app)/admin/people/page.tsx:85)), so it supplies no row-header relationship either. The visual fold therefore discards the original table relationships for screen-reader navigation.
   
   **Fix:** Explicitly require accessible person and field labels for the folded values, using a person row-header ID and screen-reader-only field labels or equivalent associations. Keep the folded content exposed to assistive technology; the reference component’s no-row-tap branch uses `aria-hidden="true"` ([Table.tsx:336](/home/user/ERP_PLANT8_260917/ui/table/Table.tsx:336)), which must not be copied here. Include phone screen-reader verification.
