## Spacing Scale

이 프로젝트의 실제 토큰(`docs/design/tokens.css`, 4px 기본 단위 — 템플릿의 8pt 기본값이 아니라 이 값이 정본이다). 이 페이즈는 **새 간격 값을 만들지 않는다** — 기존 `KvList`·표 CSS가 이미 쓰는 값을 그대로 재사용한다.

| Token | Value | 이 페이즈에서 재사용하는 곳 |
|-------|-------|---------------------------|
| `--s-1` | 4px | 안 씀(참고용 전체 목록) |
| `--s-3` | 12px | `KvList` 라벨-값 grid gap(`.kv { gap: 0 var(--s-3); }`, 기존, 변경 없음) |
| `--s-4` | 16px | 안 씀 |
| `--s-5` | 20px | PC 컨테이너 좌우 패딩(셸, 변경 없음) |
| `--touch-min` | 44px | 폰 표 행 최소 높이(`--row-min` 폰값) — 사람 목록 표에 배지가 늘어도 행 높이 계산 방식(내용 기준, 최소 44px)은 그대로 |

**정정(#24 검증)**: `KvList`의 `dt`/`dd` 세로 패딩은 토큰이 아니라 **리터럴 값**이다(`ui/kv-list/KvList.module.css` 확인: `dt { padding: 7px 0; }`, `dd { padding: 6px 0; }`) — `--s-2`(8px)로 잘못 표기했던 이전 판을 정정한다. 이 리터럴은 02-02 결정("간격 리터럴은 stylelint 금지 대상에서 제외 — 색·서체·radius 셋만 금지")이 이미 허용한 기존 값이고, 이 페이즈는 그 값을 바꾸지 않는다.

Exceptions (SYSTEM.md §3에 이미 정의된 값을 이 페이즈가 재사용을 통해 **상속**만 한다 — 새로 만든 예외가 아니다): `12px`(`--s-3`, KvList 라벨-값 grid gap) · `20px`(`--s-5`, PC 컨테이너 좌우 패딩) · `44px`(`--touch-min`, 폰 표 행 최소 높이) · KvList `dt`/`dd` 리터럴 패딩 `7px`/`6px`(위 정정 참고) · 표 셀 패딩 `6px 8px`(PC) · `10px 8px`(폰)(SYSTEM.md §3 "표 셀 패딩" 원문 그대로, 사람 목록 `<table>`이 이미 씀).

## Color

이 페이즈는 **새 색을 하나도 만들지 않는다.** 기존 의미 토큰 중 **둘만** 쓴다:
- `--muted` — 네 배지(확인 불가·보관됨·첫 로그인 전·임시 비밀번호 사용 중) 전부
- `--accent` — **실패한 리허설에만** 나타나는 GitHub Actions 실행 링크 하나. **스타일은 `app/(app)/admin/people/people.module.css`의 `.detailLink`(「상세」 링크)와 완전히 동일하게 재사용한다**: `--fs-sm`, `font-weight: var(--fw-medium)`(600), `color: var(--accent)`, `text-decoration: underline`, `text-underline-offset: var(--underline-offset)` — 폰(<700px)에서는 같은 파일의 `.detailLink` 미디어 쿼리처럼 `min-width`/`min-height: var(--touch-min)`(44px)로 히트 영역을 키운다(짧은 링크 텍스트라 패딩이 아니라 히트 영역만 키우는 처리). §1-3 규칙 ①의 "행동 링크"가 이 3차 링크 전반을 가리킨다는 것은 이미 앱 전체의 모든 3차 버튼·링크가 `--accent`를 쓰는 기존 관행으로 확인된다 — 새 사용처를 여는 것이 아니라 이미 있는 자리(같은 파일의 같은 스타일)를 재사용하는 것. **탭 동작**: 같은 탭에서 연다(`target="_blank"` 없음) — SYSTEM.md §9(아이콘 절)는 "외부 링크(external-link)"를 아이콘으로 표시할 수 있는 자리로만 언급하고 탭 동작을 규정하지 않으며, 이 저장소 어디에도 `target="_blank"` 선례가 없다(`grep -rn 'target="_blank"' **/*.tsx` → 매치 없음, 확인함). §6-6의 "새 탭"은 인쇄 라우트 전용 규칙이라 이 링크에는 적용되지 않는다 — 그래서 기본값(같은 탭)을 따른다

`--danger`/`--success`는 쓰지 않는다(아래 근거).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--bg` `#FFFFFF` | 두 화면 배경 — 변경 없음 |
| Secondary (30%) | `--surface` `#F3F7F5` / `--g-100` `#DCE8E4` | 표 hover(`--surface`, 기존)·표 머리글(`--g-100`, 기존, 사람 목록은 읽기용이라 흰 바탕 유지) — 변경 없음 |
| Accent (10%) | `--accent` `#005446` | **실패 리허설에만** 나타나는 「실행 기록」 링크 한 곳(§7-1 3차 링크, §1-3 규칙 ①) — 그 외 이 페이즈 화면 어디에도 쓰지 않는다. 1차 버튼·포커스 링·「내 차례」·현재 위치는 이 페이즈 범위에 없다 |
| Destructive | `--danger` `#9B1C1C` | **이 페이즈는 사용하지 않는다** — 「실패」는 색이 아니라 단어("실패")+단계(`복원`/`검증`/`정리`)+링크로 표현한다(아래 근거) |
| 이 페이즈가 실제로 쓰는 색 | `--muted` `#4E5D59` | 「확인 불가」·「보관됨」·「첫 로그인 전」·「임시 비밀번호 사용 중」 StatusTag(§7-5 의미 목록의 "대기·미착수·임시" — "임시"가 "임시 비밀번호"와, "미착수"가 "첫 로그인 전"과 직접 대응) |

Accent reserved for: 실패한 복원 리허설 행의 GitHub Actions 실행 링크 한 곳뿐(§1-3의 5군데 중 ①에 해당, 새로 넓히지 않는다).

**근거 — 왜 성공/실패에 `--success`/`--danger`를 쓰지 않는가:** 기존 「마지막 백업」행(`app/(app)/admin/system-status/page.tsx` 60~71행)이 이미 같은 종류의 성공/실패 정보를 **색 없는 일반 텍스트**로 렌더한다(`{status.backup.status} · {status.backup.endTime}` — `StatusTag`를 쓰는 것은 "확인 불가" 하나뿐, D-18). 「복원 리허설」 행은 같은 KvList의 같은 성격의 값이므로 같은 처리를 따른다 — 다른 행만 색을 넣으면 §11 "새 색 사용처 §1-3의 5군데 안" 검증과 무관하게 시각적 일관성이 깨진다(같은 화면 안에서 성공/실패 표시 방식이 행마다 다르면 사용자가 규칙을 배울 수 없다).

| Error state | 「복원 리허설」 **필드 자체**의 조회 실패(연결·권한·표 없음·파싱 등 종류 불문): `확인 불가`(`StatusTag kind="muted"`, 기본 `variant="tag"` — D-18과 동일 패턴). **검증(#22)**: `system-status`·`people` 두 라우트에는 전용 `loading.tsx`/`error.tsx`가 없다(`find app -iname loading.tsx -o -iname error.tsx` 결과: `app/(app)/projects/{loading,error}.tsx`와 공유 `app/(app)/error.tsx`뿐 — 이 두 라우트는 없음). 도메인 함수가 catch 없이 throw하면 공유 경계 `app/(app)/error.tsx`로 떨어지고, 그 실제 문구는 제목 `문제가 생겼습니다` + 본문 `화면을 불러오지 못했습니다` + `다시 시도`다(파일 확인함) — SYSTEM.md §6-8이 적은 `상태를 불러오지 못했습니다 · 다시 시도`는 화면 자체의 인라인 처리를 가정하지만 그 인라인 처리는 코드에 없다(기존 갭, 이 페이즈가 만들지도 고치지도 않는다). **그래서 이 페이즈가 추가하는 「복원 리허설」 조회 함수는 반드시 자기 안에서 try/catch해 위 `확인 불가`로 흡수해야 한다** — 밖으로 throw하면 SYSTEM.md가 그리는 문구가 아니라 공유 경계의 다른 문구가 뜬다(기존 `db`·`backup` 필드가 이미 이렇게 자체 처리한다, 같은 패턴을 따른다) |
| Destructive confirmation | **해당 없음.** 이 페이즈가 다루는 두 화면(`system-status`·`people` 표시 부분)에는 삭제·반려 같은 위험 행동이 없다. 복원 리허설의 실제 파괴적 동작(임시 인스턴스 생성·삭제)은 GitHub Actions `workflow_dispatch` 확인 화면에서 일어나며 이 시스템의 SYSTEM.md 컴포넌트 규칙 대상이 아니다 |

### 복원 리허설 값 행 — 필드 순서와 정확한 문구

**필드 순서**: 왼쪽부터 **결과(+실패 시 단계) · 원본 인스턴스 · 일시 · 백업 id · 소요 시간**, 그리고 **실패일 때만 맨 끝에** GitHub Actions 실행 링크가 붙는다(§8-3 "원인 · 다음 행동" 순서 — 원인(단계)이 앞, 다음 행동(실행 기록 확인)이 맨 뒤). 원본 인스턴스·일시는 항상 있고, 백업 id·소요 시간은 값이 없으면 그 세그먼트 전체를 생략한다(구분자 `·`도 함께 생략 — 빈 자리·플레이스홀더 없음, #7).

**결과의 정의(#6)**: `성공` = 복원 완료 **AND** 모든 확인 항목 통과 **AND** 임시 인스턴스 삭제 성공. 셋 중 하나라도 실패하면 `실패`이고, 바로 뒤에 실패한 단계 **하나**(`복원` / `검증` / `정리` — 세 단어 중 하나만, 새 상태를 늘리지 않는다)가 붙는다. **여러 단계가 함께 실패했을 때의 표시 단계(Codex 2차 #2)**: 우선순위는 **`정리` > `복원` > `검증`**이다 — 정리(임시 인스턴스 삭제)가 실패했으면 다른 실패가 있어도 항상 `정리`를 보인다(지워지지 않은 임시 인스턴스는 비용이 계속 나가는 남은 자원이라 절대 가려지면 안 된다). 정리가 성공했으면 복원 실패가 `복원`, 그것도 아니면 `검증`. 표시되지 않은 나머지 실패는 모두 GitHub Actions 실행 로그에 남아 있고 같은 행의 「실행 기록」 링크로 간다 — 화면에 단계를 둘 이상 나열하지 않는다. 실패 행의 맨 끝에는 GitHub Actions 실행으로 가는 **일반 링크**(`실행 기록`, 3차 링크이지 버튼이 아니다 — #13, 스타일은 위 Color 절)가 붙는다. 링크 대상은 `https://github.com/{owner}/{repo}/actions/runs/{run id}`.

| 상태 | 문구 예시 |
|---|---|
| 성공 | `성공 · 스테이징 · 2026-09-24 03:14 · 백업 1758684000000 · 12분` |
| 성공, 1분 미만 소요 | `성공 · 스테이징 · 2026-09-24 03:14 · 백업 1758684000000 · 1분 미만` |
| 실패(검증 단계) | `실패 · 검증 · 스테이징 · 2026-09-24 03:14 · 백업 1758684000000 · 4분 · 실행 기록` |
| 실패(복원 단계, 백업 id를 아직 못 구함) | `실패 · 복원 · 스테이징 · 2026-09-24 03:14 · 4분 · 실행 기록` |
| 실패(검증 실패 + 정리 실패 동시 — 우선순위로 `정리`) | `실패 · 정리 · 스테이징 · 2026-09-24 03:14 · 백업 1758684000000 · 9분 · 실행 기록`(검증 실패는 「실행 기록」의 Actions 로그에서 본다) |
| 기록 없음(쿼리 성공, 0행) | `리허설 기록 없음 — 첫 리허설 전` |
| 조회 실패(쿼리 자체 에러) | `StatusTag kind="muted"` → `확인 불가` |

- **일시가 가리키는 순간**: 리허설의 **종료(결과 기록) 시각**이다 — CONTEXT.md 워크플로 8단계(임시 인스턴스 확인·삭제가 끝난 뒤 `restore_rehearsals`에 결과를 쓰는 순간)의 타임스탬프이지, 워크플로 시작 시각이나 백업 자체의 생성 시각이 아니다(#12 — 백업 생성 시각은 별도로 보이지 않는다: 워크플로가 항상 "그 시점의 최신 성공 백업"을 복원하므로 백업 id 자체가 그 백업을 특정하고, 생성 시각을 따로 보일 필요가 없다).
- **저장·표시(#11)**: DB에는 `timestamptz`(UTC 순간)로 저장한다. 화면에는 `Asia/Seoul`(KST)로 변환해 24시간 표기로 렌더하고, **날짜 부분은 반드시 ISO `YYYY-MM-DD`**여야 한다(`YYYY-MM-DD HH:MM`, §2-4 날짜·시각 형식을 공백으로 이어붙임) — `toLocaleDateString`류의 로캘 포맷(`"2026. 9. 24."` 같은)을 그대로 쓰지 않는다. **검증 및 인용 정정**: 이 저장소에 날짜/시각 포맷 공유 헬퍼가 없다(`find lib -iname "*date*" -o -iname "*time*"` → 빈 결과). 유일한 선례인 `domain/quotes/lines.ts:455-460`은 **시각만**(`toLocaleTimeString("ko-KR", { hour: "2-digit", minute: "2-digit", hour12: false, timeZone: "Asia/Seoul" })`, `HH:MM`만 만든다) 다루고 날짜 부분은 만들지 않는다 — 이전 판이 이 선례를 "`Intl.DateTimeFormat`로 날짜+시각을 함께 포맷한다"처럼 잘못 인용했으므로 정정한다. **날짜까지 함께 ISO로 만들려면** `Intl.DateTimeFormat("en-CA", { timeZone: "Asia/Seoul", year: "numeric", month: "2-digit", day: "2-digit", hour: "2-digit", minute: "2-digit", hour12: false }).formatToParts(date)`처럼 `formatToParts`로 연·월·일·시·분을 따로 뽑아 `YYYY-MM-DD HH:MM`으로 직접 조립하는 쪽을 권한다(`en-CA` 로캘이 연-월-일 순서를 주지만, 파츠를 직접 조립하는 편이 로캘 문자열 형식에 기대지 않아 더 안전하다) — 새 컴포넌트·새 공유 모듈을 만드는 것은 계획 단계의 선택이지 이 스펙이 강제하지 않는다(04.2의 "마지막 tick" 표시와 공유할지는 계획 단계 판단). **참고(기존 갭, 이 페이즈 범위 밖)**: 현재 「마지막 백업」 행(`lib/gcp/cloud-sql-admin.ts` `getLastBackup`)은 GCP Admin API가 반환한 raw UTC ISO 문자열을 변환 없이 그대로 넘긴다 — KST로 포맷되지 않는다. 「복원 리허설」은 이 페이즈가 처음 쓰는 값이므로 기록 시점부터 KST로 표시한다(「마지막 백업」을 고치는 것은 이 페이즈의 일이 아니다).
- **원본 인스턴스와 환경 분리(#3/#4)**: `스테이징` 또는 `프로덕션`(CONTEXT.md 원문 용어 그대로, 다른 표기 금지). 결과는 **그 화면이 속한 환경 자신의 DB**에만 기록된다 — 스테이징 Cloud Run 서비스는 `plant8-staging-db`에만, 프로덕션 Cloud Run 서비스는 `plant8-prod-db`에만 연결되도록 배포 시점에 고정된다(`scripts/deploy.sh`, RESEARCH.md 아키텍처 다이어그램 8단계 "이번엔 운영 자신의 CLOUD_SQL_CONNECTION_NAME"). 두 인스턴스는 완전히 분리된 Cloud SQL이므로 **프로덕션 상태 화면에 스테이징 리허설 결과가 나타나는 경로 자체가 없다** — 스테이징 성공이 프로덕션 증거로 오인될 수 없다(Phase 8 기준 5의 "전환 전 프로덕션 원본 성공 기록" 요구를 이 화면 자체의 위치가 보장한다). 값으로 원본 인스턴스를 보이는 것은 그래서 교차 확인이 아니라 감사 흔적(어느 인스턴스를 대상으로 리허설했는지)이다. 여러 기록 중 표시할 1건은 **종료 시각(일시) 내림차순 최신 1건**, 동시각이면 **id 내림차순**으로 고른다(계획 단계에서 id 타입이 삽입 순서를 보장하는지 확인 필요 — UUID라면 별도 정렬 키가 있어야 한다는 뜻이고, 이 스펙은 그 확정을 계획 단계에 맡긴다).
- 백업 id: `백업 ` + GCP 원본 숫자 id(쉼표 없음 — 수량이 아니라 식별자이므로 §2-4 "숫자 형식"이 아니라 §2-4 "문서 번호" 규칙("서버 서식 그대로, 모노 아님, tabular-nums")과 같은 성격으로 취급). 값이 없으면 세그먼트 생략(#7).
- 소요 시간(#25): **종료 시각 − 시작 시각**. 60초 미만이면 `1분 미만`, 그 외에는 초 단위를 버리고 정수 분만 남긴다(`N분`, `§2-4` "건수: 숫자+단위 붙여쓰기"와 같은 형태). 시작·종료 시각 중 하나라도 기록되지 않았으면 이 세그먼트를 생략한다(#7).
- **PARTIAL·진행 중 상태 없음(#5)**: 이 행은 **가장 최근에 기록된 결과 하나**만 보여준다. 워크플로가 지금 실행 중이어도 이 화면은 그 사실을 보여주지 않는다(D-18, 폴링·실시간 갱신 없음 — Outside Review Dispositions #10 참고). 기록 단계(`restore_rehearsals` insert)는 성공이든 실패든 **항상 실행되고**(CONTEXT.md 워크플로 8단계, 결과값을 성공/실패 인자로 받아 쓴다), 정리 단계(임시 인스턴스 삭제)도 결과와 무관하게 항상 실행된다(D8-08 "확인이 실패해도 임시 인스턴스는 지워진다"). 기록 단계 자체에 도달하지 못할 만큼 이른 실패(예: WIF 인증 실패)는 이 화면에 전혀 나타나지 않고 GitHub Actions 로그에만 남는다 — `docs/OPERATIONS.md`가 이 경계를 문서화해야 한다(계획 Task, 이미 §6-8 문서 Task 절이 다루는 문서 갱신과 함께 처리).

**계획 단계 필수 요구사항 — 리허설 기록의 데이터 항목**: 위 문구를 렌더하는 데 필요한 최소 칼럼은 다음과 같다(`restore_rehearsals` 테이블 또는 동등한 저장소, 정확한 스키마는 계획 단계에서 정한다):

| 항목 | 타입 | Nullable | 비고 |
|---|---|---|---|
| 원본 환경(source) | enum(`staging` \| `production`) | 아니오 | 값에 따라 화면 표시가 `스테이징`/`프로덕션`으로 갈린다 |
| 결과(result) | boolean(성공/실패) | 아니오 | |
| 실패 단계(failed_stage) | enum(`복원` \| `검증` \| `정리`) | **예**(`result=성공`이면 항상 NULL) | 실패일 때만 값이 있다. 여러 단계가 실패했으면 **하나만** 저장한다 — 우선순위 `정리` > `복원` > `검증`(위 "결과의 정의"). 워크플로의 기록 단계가 이 우선순위로 값을 골라 쓰고, 화면은 저장된 값을 그대로 보인다(화면에서 재계산하지 않는다). 나머지 실패는 Actions 실행 로그에만 남는다 |

| 종료 시각(finished_at) | `timestamptz` | 아니오 | 위 "일시"가 가리키는 값, 소요 시간 계산의 기준 |
| GitHub Actions 실행 식별자(run id 또는 repo+run id) | string | **예**(`result=성공`이면 표시하지 않으므로 NULL이어도 무방) | 실패 시 「실행 기록」 링크 URL 조립에 쓴다 |

### 사람 목록 배지 조합 규칙

| `first_login_at` | `password_is_temporary` | 「상태」 칸 렌더 |
|---|---|---|
| NOT NULL(로그인한 적 있음) | false | `—` |
| NOT NULL | true | `임시 비밀번호 사용 중`(단독 — 로그인은 했으나 아직 비밀번호를 안 바꿨거나, 관리자 재발급 뒤) |
| NULL(첫 로그인 전) | true | `첫 로그인 전 · 임시 비밀번호 사용 중`(둘 다 `StatusTag kind="muted" variant="text"`, `·`로 연결 — 앱 전체의 기존 구분자 관행. 신규 발급 직후의 정상 경로) |
| NULL | false | `첫 로그인 전`(단독) — **백필 직후에는 사실상 나오지 않는다**: 아래 "백필 규칙"이 이미 이 경우(로그인 로그 없음 + `password_is_temporary=false`)를 마이그레이션 시각으로 채워 `NOT NULL`로 만들기 때문이다. 그래도 이 행을 표에 남기는 이유는 **방어적 렌더 규칙**으로서다 — 백필 이후 어떤 경로로든(수동 DB 정정, 향후 기능 변경 등) 이 조합이 실제로 생기더라도 특수 케이스 코드 없이 두 칼럼을 독립적으로 읽는 것만으로 안전하게 렌더되게 하기 위함이다 |

**보관됨 처리(#17)**는 위 네 조합과 독립된 우선순위 규칙이다: `StatusTag kind="muted" variant="text"` → `보관됨`(기존 그대로) — **위 네 조합의 배지는 전부 억제한다.** 보관된 사람은 로그인하지 않으므로 로그인 상태 표시가 의미가 없다(이 스펙에서 확정, CONTEXT.md에 명시 없음 — 가정 표시). 이 억제는 표시 이상의 의미도 있다: 보관된 사람은 애초에 Phase 8 전환 체크리스트의 「전 직원 로그인 확인」 범위 밖이다(퇴사·비활성 계정이므로) — D8-07은 활성 직원만 다룬다.

**정보 노출 매핑(#9, 인용 정정)**: `PersonDto`의 필드는 세 정보 항목에 나뉘어 매핑돼 있다(`PERSON_DTO_SPEC`, `domain/people/index.ts:56-67`, 확인함) — `id`·`name`·`email`·`roleId`·`archivedAt`은 `person.value`(`domain/permissions/info-items.ts:24`, 라벨 "사람 정보", `staffDefault: true`), `roleName`은 `role.value`, `currentTeamId`·`currentTeamName`은 `team.value`다. 새로 추가하는 `firstLoginAt`·`passwordIsTemporary` 두 필드는 사람 자신의 계정 사실이지 계급·팀 정보가 아니므로 **`person.value`에 매핑한다**(`id`·`archivedAt`과 같은 자리) — 새 정보 항목을 만들지 않는다(둘 다 로그인 계정의 구조적 사실이지 `pnl.amount`류의 "새 기능 민감 정보"가 아니다). 계급이 `person.value`를 보지 못하면(노출표에서 꺼진 계급) `project()`가 그 계급의 DTO에서 **필드 자체를 제거한다**(`null`/`false`가 아니라 필드 부재 — `domain/revenue`가 이미 쓰는 동작과 동일). 이때 배지는 **렌더하지 않는다**(생략) — `null`/`false`처럼 "값이 있는데 비어 있다"로 취급하지 않는다. 그 계급은 이미 이름·이메일도 안 보이므로 배지가 없는 것이 자연스럽다 — 세 번째 "알 수 없음" 상태를 만들지 않는다.

**계획 단계 필수 요구사항 — 백필 규칙(Codex 2차 #1 반영)**: 이 칼럼을 추가하는 마이그레이션은 기존 사용자의 `first_login_at`을 아래 순서로 채운다.
1. **두 로그인 기록 중 더 이른 시각**: (가) 그 사용자의 가장 이른 `action_log` 행 중 `action_type = 'login'`인 것(`CORE_ACTION_TYPES`의 `"login"`, `domain/action-log/record.ts:11` — 기록 지점 `domain/auth/hooks.ts:106`), (나) `login_attempts`에서 `success = true`이고 `email`이 사용자의 이메일과 **대소문자 무관하게** 일치하는 가장 이른 행의 `attempted_at` — 둘 중 존재하는 것들의 최솟값. (나)가 필요한 이유: `"login"` action_log 행은 `action_log.optional_types` 설정으로 꺼질 수 있어(`domain/action-log/record.ts:127`) 로그인한 사람도 행이 없을 수 있지만, `domain/auth/hooks.ts:94`의 `recordAttempt(SYSTEM_VIEWER, { email, success, ip, attemptedAt })`는 설정과 무관하게 **모든** 로그인 시도를 `login_attempts`에 남긴다. **확인한 스키마**(`db/schema/login-attempts.ts`): `id uuid` · `email text NOT NULL` · `success boolean NOT NULL` · `ip text` · `attempted_at timestamp NOT NULL`(tz 없는 `timestamp` — `first_login_at`의 `timestamptz`로 옮길 때 기록 시와 같은 기준으로 해석하도록 계획 단계가 확인한다) · `resolved_at` · `resolved_reason`, 인덱스 `(email, attempted_at)`. 기록되는 `email`은 이미 소문자다(`getBodyEmail`이 `toLowerCase()`, `domain/auth/hooks.ts:20`) — 그래서 비교는 `lower(users.email) = login_attempts.email`로 충분하다. `action_log` 쪽은 정리(prune)가 행을 지우지 않고 `pruned_at`만 표시하므로(`db/migrations/0008_action_log_prune.sql`) `pruned_at`으로 거르지 않는다.
2. 위 둘 다 없고 `password_is_temporary = false`이면 **마이그레이션 실행 시각**(임시 비밀번호를 바꾸려면 이미 로그인했어야 하므로, 기록이 없다는 것은 "첫 로그인 전"이라는 뜻이 아니다).
3. 그 밖에는 `NULL`(→ 위 표의 「첫 로그인 전」).

이 규칙은 위 표의 네 조합이 실제로 나타나는 근거이므로, `gsd-planner`는 이 백필을 마이그레이션 Task에 명시적으로 포함해야 한다.

**가정 — 남는 오표시(정직하게 명시)**: `login_attempts`는 앱 코드 어디에서도 삭제되지 않는다(확인: `repositories/login-attempts.ts`는 insert·update뿐, 저장소 전체에 `delete(loginAttempts)`·`DELETE FROM login_attempts`·보존 기간 정리 없음 — 테스트의 `TRUNCATE`만 있다). 그래도 다음 경우 실제로 로그인한 적 있는 사람이 **다음 로그인 전까지** 「첫 로그인 전」으로 보일 수 있다: ① 로그인 이력이 DB에서 수동으로 지워진 경우, ② 로그인이 `login_attempts` 도입(`db/migrations/0001_login_attempts.sql`) 이전에만 있었던 경우, ③ 로그인한 뒤 관리자가 그 사람의 이메일을 바꿔 과거 행의 `email`과 일치하지 않는 경우 — 셋 다 아직 임시 비밀번호인 사람에게만 해당한다(비밀번호를 바꾼 사람은 2번 규칙으로 채워진다). 다음 로그인 때 `first_login_at`이 채워지므로 스스로 해소된다 — 이 페이즈는 이를 위한 별도 처리를 두지 않는다. **④ Google 로그인 이력은 백필로 확정할 수 없다(Codex 3차 #1)**: 두 기록원 모두 이메일 로그인 경로에서만 쓰인다 — `domain/auth/hooks.ts:86`의 `after` 훅이 `/sign-in/email`이 아닌 경로에서 곧바로 `return`하므로, `AUTH_PROVIDER=google`(`lib/auth.ts:73-82`, AUTH-04 전환)로 로그인한 기록은 `action_log`에도 `login_attempts`에도 남지 않는다. 오늘은 배포가 `AUTH_PROVIDER=email`로 고정돼 있어(`scripts/deploy.sh:440`) 그런 이력이 존재하지 않으므로 실제 오표시는 없다 — 백필 이후의 Google 로그인은 아래 기록 지점(세션 생성 훅)이 잡는다.

**기록 지점과 설정 무관성(#1/#2, Codex 3차 #1로 기록 지점 정정)**: `first_login_at`은 **로그인 방식과 무관하게, 세션이 만들어진 순간**에 최초 1회만(값이 `NULL`일 때만) 채운다. **기록 지점은 `domain/auth/hooks.ts` `after` 훅이 아니다** — 그 훅은 86행에서 `/sign-in/email`이 아닌 모든 경로에 `return`하므로, 거기에 두면 `AUTH_PROVIDER=google`(`lib/auth.ts:73-82`)로 로그인한 사람은 영원히 「첫 로그인 전」으로 남는다. **계획 단계 필수 요구사항**: 설치된 better-auth 1.7.5(`node_modules/better-auth/package.json`)의 `betterAuth({ databaseHooks: { session: { create: { after } } } })` — 타입 선언 `@better-auth/core@1.7.5` `dist/types/init-options.d.mts:1263`(`databaseHooks?:`), `:1322-1324`(`after?: (session: Session & Record<string, unknown>, context: GenericEndpointContext | null) => Promise<void>`, "Hook that is called after a session is created") — 를 `lib/auth.ts`에 등록해 이것을 **유일한 기록 지점**으로 삼는다. 모든 세션 생성(이메일 로그인·소셜 콜백)이 이 한 곳을 지나고, 이 저장소에는 다른 세션 생성 경로가 없다(확인: `lib/auth.ts`에 `plugins` 없음 — 대리 로그인 등 없음, `disableSignUp: true`로 가입 후 자동 로그인 없음, 앱 코드에 `createSession(` 직접 호출 없음). 훅은 `session.userId`로 `first_login_at IS NULL`인 행만 갱신하는 조건부 UPDATE 한 번을 한다(동시 로그인 둘이 겹쳐도 먼저 쓴 값이 남는다). 비밀번호 변경이 다른 세션을 끊으며 새 세션을 만드는 경우에도 이 훅이 돌지만 그 사람은 이미 값이 있어 no-op이다. **검증 결과**: `"login"`은 `ALWAYS_ON_ACTION_TYPES`(`domain/action-log/record.ts:65-72`)에 **없다** — 즉 `action_log.optional_types` 설정(`domain/settings/keys.ts:46-54`, 기본값은 켜짐)으로 **끌 수 있는 종류**다(`domain/action-log/record.ts:127-131`이 꺼져 있으면 `appendActionLog` 자체를 건너뛴다). **`first_login_at` 갱신은 이 설정과 무관하게 항상 실행돼야 한다** — `recordAction("login")` 호출이 설정에 의해 조용히 no-op 되더라도, `first_login_at` 갱신은 위 세션 생성 훅에서 따로 실행되므로 `recordAction`의 성공·스킵 여부에 기대지 않는다. 로그아웃·비밀번호 변경·비밀번호 재설정·관리자 재발급 중 어느 것도 이 값을 지우지 않는다(1회성 필드).

**수용 조건 — 이메일 외 로그인 방식(Codex 3차 #1)**: 테스트 환경에서는 Google이 켜지지 않으므로 **단위 테스트**로 확인한다 — 세션 생성 훅 처리 함수를 직접 호출해 ① 이메일 경로가 아닌 컨텍스트(예: `path: "/callback/google"`, 그리고 `context: null`)로 만들어진 세션에서도 `first_login_at`이 `NULL`인 사용자는 값이 채워지고, ② 이미 값이 있는 사용자는 두 번째 호출에서 값이 바뀌지 않으며, ③ `action_log.optional_types`에서 `"login"`을 끈 상태에서도 ①이 그대로 성립함을 단언한다. 이메일 로그인 경로의 통합 테스트(로그인 → 「첫 로그인 전」 사라짐)는 기존 계획대로 둔다.

**가정(재확인 필요, RESEARCH.md Discretion 항목을 이 화면 계약이 성립하도록 명시적으로 확정한다):**
1. **재발급 뒤 표시(#16)**: 관리자 재발급(`account.yml reset`)은 `password_is_temporary`만 다시 참으로 켜고 `first_login_at`은 그대로 둔다(RESEARCH.md 코드 예시 `setFirstLoginAtIfUnset`의 "최초 1회만" 전제와 일치). 재발급 뒤 「첫 로그인 전」이 다시 보이는지는 **오직 `first_login_at`이 여전히 `NULL`인지에 달려 있다** — 재발급 자체가 이 배지를 되살리는 스위치가 아니다. 이미 한 번이라도 로그인한 적 있는 사람은 재발급 후에도 `NULL`이 아니므로 「임시 비밀번호 사용 중」만 다시 보이고(위 표 두 번째 행), 한 번도 로그인한 적 없는 사람에게 재발급이 일어나는 경우(예: 발급 직후 정정)에는 `NULL`이 그대로이므로 두 배지가 계속 보인다(위 표 세 번째 행) — RESEARCH.md 통합 테스트 시나리오("관리자 재발급 → 「임시 비밀번호」 다시 표시")는 전자(이미 로그인한 사람)를 전제한다.

- **검증 조건 — 폰 폭 접근성 트리(Codex 3차 #2, 완료 판정)**: 같은 독립 DOM 감사가 폭 360px에서 접근성 트리(설치된 Playwright 1.63의 `locator.ariaSnapshot()` 또는 `getByRole`/접근 가능한 이름 조회 — 1.63에는 `page.accessibility`가 없다, 스크린샷 금지)를 실측해 단언한다: ① 각 사람 행의 이름이 `rowheader` 역할로 노출된다, ② 접힌 줄의 값이 트리에 있고(`aria-hidden` 조상 없음) 접근 가능한 텍스트가 `이메일 …`·`계급 …`·`현재 소속 …`처럼 필드 라벨을 포함한다, ③ 접힌 줄 셀이 `headers`로 그 행의 이름 머리글에 연결된다, ④ PC 폭 1280px에서는 접힌 줄이 트리에 없어 같은 값이 한 번만 노출된다.

이 페이즈의 반응형 지점은 위 칸 접기와 다음 둘이다:

1. **「상태」 칸의 두 배지**: PC(≥700px)에서는 `·`로 이어 한 줄. **폰(<700px)에서는 `·`로 잇지 않고 세로로 쌓는다**(배지마다 자기 줄, 배지 사이 세로 간격 `gap: var(--s-1)`(4px) — `tokens.css`에 `--s-1: 4px`가 이미 있음을 확인했다, 새 값 아님) — 좁은 셀에 `첫 로그인 전 · 임시 비밀번호 사용 중`을 한 줄로 구겨 넣지 않기 위함. `StatusTag` 자체는 이미 `white-space: nowrap`(각 배지 텍스트는 줄바꿈되지 않는다)이라, 감싸는 요소 하나의 CSS(폰 전용 미디어 쿼리에서 `display:flex; flex-direction:column; gap:var(--s-1)`)만으로 충분하다 — 새 컴포넌트를 만들지 않는다.
2. **복원 리허설 값의 백업 id**: §2-4 "모든 숫자 칸은 tabular-nums, white-space: nowrap"을 그대로 따른다 — 긴 숫자 문자열 중간에서 줄바꿈되지 않는다(`dd` 문자열 전체는 여러 줄로 접힐 수 있지만, 백업 id 숫자 부분만 별도로 `white-space: nowrap`을 걸어 중간에서 끊기지 않게 한다). GitHub Actions 실행 id는 화면에 **보이는 텍스트가 아니다**(링크 텍스트는 `실행 기록`이고 id는 `href` 안에만 있다) — 그래서 nowrap·tabular-nums 대상이 아니다(이전 판의 오류 정정).
