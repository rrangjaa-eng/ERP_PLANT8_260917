## Phase Boundary

관리자가 코드 없이 텍스트/숫자/날짜/선택 4종 입력 칸을 정의·수정·보관·복원하는 관리 화면을 만든다. 이 페이즈에서 관리 화면이 칸을 받는 대상은 거래처 하나이고, 프로젝트·견적 줄 대상은 Phase 10이 켠다(아래 「분리로 생긴 조정」). 추가한 칸은 정보 노출표에 자동으로 올라와 관리자가 계급별로 끈다. 칸 정의 저장 구조(`label`·`archived_at` 등)와 보관 규칙, 노출표의 두 출처 합치기, 칸별 노출 판정을 여기서 만들고, Phase 3부터 칸 정의를 읽는 거래처 입력 화면으로 끝까지 확인한다. 범위 정본은 `.planning/ROADMAP.md` Phase 04.5 기준 1~5다.

이 페이즈는 Phase 10(팀 손익·연간 목표·인센티브·화면 항목 추가)에서 Phase 4 폼 코드와 Phase 9 손익에 기대지 않는 부분을 떼어 낸 것이다(2026-09-24 사용자 결정). 결정 번호는 Phase 10 논의의 D10-xx를 그대로 쓴다. 이 파일만 읽으면 계획할 수 있게 필요한 결정을 옮겨 두었다 — `10-CONTEXT.md`를 다시 읽을 필요가 없다.

**요구사항:** ID로 옮긴 것은 없다. ADMN-07(「관리자가 … 칸을 추가하면 입력·목록·검색·내보내기에 반영된다」)은 사용자에게 보이는 결과가 폼·목록·검색·내보내기 반영에서 끝나고, 프로젝트·견적 줄 쪽 반영이 Phase 4 폼 코드에 기대므로 Phase 10에 남겼다. 이 페이즈는 ADMN-07의 기반(관리 화면·저장 구조·보관·노출표 등록)이다. 로드맵 요구사항 합계는 86 그대로이고 중복이 없다.

**왜 Phase 9 뒤를 기다리지 않는가:** `10-CONTEXT.md`의 「착수 시점: Phase 9 뒤」는 팀 손익·목표·인센티브 때문이다 — 그 셋은 Phase 9의 effectiveCost 식·연도 귀속 설정·전환 뒤 실입력 데이터를 공유한다. 커스텀 필드 관리는 그중 어느 것도 읽지 않는다. 필요한 것은 Phase 3에 이미 있는 `field_definitions` 표·zod 조립 검증·정보 노출표·보관함·행동 로그·누수 스캔이고, 끝까지 확인할 입력 화면(거래처)도 Phase 3 것이다. 그래서 Phase 4와 나란히 진행할 수 있다.

**Phase 10에 남은 것:** 팀 손익(PNL-07, D10-01~D10-03), 연간 목표(GOAL-01·GOAL-03, D10-04~D10-08), 인센티브(GOAL-02, D10-09~D10-11), 그리고 ADMN-07의 폼 반영 — 관리 화면의 프로젝트·견적 줄 대상을 켜고, 이 페이즈가 만든 칸을 프로젝트·견적 줄의 폼·목록·검색·Excel과 거래처 목록·검색·Excel에 붙이는 일, 칸별 노출 판정과 저장 때 값 보존 규칙을 프로젝트·견적 줄 DTO·저장 경로와 Excel에 적용하는 일, 정렬용 표현식 인덱스(Issue 13), 커스텀 칸의 목록 검색 방식.

범위 밖: 프로젝트·견적 줄 폼·목록·검색·Excel(Phase 10, Phase 4 코드), 거래처 목록·검색·Excel 반영(Phase 10), 필드 타입 변경(Phase 3 규약상 금지 — 새 칸을 만든다).

## Implementation Decisions

결정 번호는 Phase 10 논의(`10-CONTEXT.md`, PR #43)의 번호를 그대로 쓴다. 이 페이즈 몫은 D10-12·D10-13과 「화면 항목 추가」에 걸린 Claude's Discretion이다.

### 이미 확정된 입력 (다시 묻지 않음 — 출처가 정본)
- `custom_fields` JSONB 컬럼 + `field_definitions` 표 규약(ROADMAP Phase 3 절 트레일링 문단, 하드 제약 7): 서버 액션이 저장 전에 `field_definitions`에서 zod 스키마를 조립해 검증하고(미등록 키·타입 불일치 거부, `.strict()`), GIN 인덱스는 표 생성 마이그레이션에 포함, 정렬용 표현식 인덱스는 실측 후에만(Issue 13), **필드 타입 변경은 금지**(새 필드로). `docs/ARCHITECTURE.md` §4-5
- 업무 행(거래처 등)에 들어가는 칸 값의 검증은 새 검증 코드 없이 `domain/custom-fields/build-schema.ts` `buildCustomFieldsSchema(defs)`를 쓴다(ROADMAP Phase 10 기준 4). 이 함수는 값을 검증할 뿐 칸 정의(대상·이름·타입·선택지·필수·순서) 저장 요청을 검증하지 않으므로, 관리 화면의 정의 저장 액션은 보통의 액션 입력 스키마를 둔다
- 타입 변경 금지는 리포지토리 수준에서 강제된다: `repositories/field-definitions.ts` `updateFieldDefinition`이 `type`을 받지 않는다
- 보관함 규약(Phase 3): 삭제 대신 `archived_at`, 보관함에서 복원
- 정보 노출표 규약(Phase 3): 판정은 `visible()`·`project(viewer, dto)` 출구, 누수 스캔은 런타임 등록 레지스트리(D-38)
- 관리자 화면은 권한표 판정(`can(viewer, …)`)을 지나고, 없으면 404

### 화면 항목 추가 (커스텀 필드 관리)
- **D10-12:** **칸 삭제는 보관이다.** 보관한 칸은 입력·목록·검색·내보내기에서 숨고, 이미 입력된 값은 JSONB에 남아 복원하면 다시 보인다(Phase 3 보관함 규약).
- **D10-13:** **추가한 칸은 정보 노출표에 자동 등록된다.** 기본값은 전 계급 보임이고, 관리자가 계급별로 끌 수 있다. 지금 `domain/permissions/info-items.ts`의 `INFO_ITEMS`는 코드 상수 목록이므로, 노출표 열이 이 상수 + `field_definitions`(보관 제외) 두 출처를 합치도록 바뀐다. 누수 스캔도 커스텀 필드 항목을 포함한다. — **Reversibility:** costly — 노출표 격자·`visible()`·누수 스캔 생성기가 동적 항목을 전제하게 된다.

### 분리로 생긴 조정 (2026-09-24, 이 PR)
- **관리 화면의 대상은 거래처 하나로 켠다(/review 반영).** 프로젝트·견적 줄 칸을 이 페이즈에서 만들 수 있게 하면 두 가지가 깨진다: `domain/projects/index.ts`(85행 부근)와 `domain/quotes/lines.ts`(485행)가 이미 모든 칸 정의로 `{}`까지 검증하는데 Phase 4 폼은 커스텀 칸을 보내지 않으므로(Phase 4 브랜치의 `project-form.tsx`에도 없다) 필수 칸 하나로 프로젝트·견적 줄 저장이 전부 막히고, 두 DTO가 `customFields`를 `project.value` 한 항목으로 통째로 내보내(`domain/projects/index.ts` 74행, `domain/quotes/lines.ts` 138행) 노출표 스위치가 아무것도 가리지 못한다. 대상 목록을 한 곳(상수)에 두고 Phase 10이 폼·DTO를 붙이면서 프로젝트·견적 줄을 더한다
- 끝까지 확인은 거래처 입력 화면으로 한다. `app/(app)/admin/vendors/vendor-form.tsx`가 이미 `field_definitions`의 거래처 칸을 그리고, `domain/vendors/index.ts` `validatedCustomFields`(160행)가 저장 전에 검증한다. 이 경로에 보관 제외·값 보존·칸별 노출만 더하면 기준 4를 증명할 수 있다
- `listFieldDefinitions(viewer, entity)`(`repositories/field-definitions.ts` 9행)는 `domain/projects/index.ts`(30행)·`domain/quotes/lines.ts`(27행)도 부른다. 이 둘은 Phase 4 코드이므로 **호출 모양을 바꾸지 않는다.** 보관 제외가 필요하면 새 함수나 선택 인자로 더하거나, 기존 함수의 결과가 보관한 칸의 기존 값을 계속 통과시키도록 한다 — 보관 칸을 그냥 빼면 두 가지가 깨진다: 폼이 그 키를 보내지 않은 채 저장하면 `customFields`가 통째로 바뀌어(`domain/vendors/index.ts` 317~318행, 보낸 값으로 교체) 보관 칸의 값이 사라지고, 기존 값을 그대로 다시 보내는 경로에서는 `.strict()`가 미등록 키로 거부한다. 둘 다 D10-12(값이 남는다)와 어긋나고, 후자는 Phase 4 화면의 저장을 깨뜨린다. 방식은 계획에서 정한다
- 보이지 않는 칸의 값도 지킨다: 거래처 폼은 그리는 칸만 보내고(`vendor-form.tsx` 124행) 갱신은 `customFields`를 통째로 바꾸므로(`domain/vendors/index.ts` 317~318행), 노출표에서 칸이 꺼진 계급이 거래처를 고치면 그 칸 값이 지워진다. 보관한 칸과 같은 규칙으로 저장된 값에서 되살린다. 보관한 선택지도 같다 — `build-schema.ts` 29행이 선택지로 `z.enum`을 만들어 보관한 선택지 값이 든 행을 다시 저장하면 거부되므로, 기존 값은 통과시키고 새 입력에서만 숨긴다
- 거래처 DTO는 지금 `customFields` 전체를 정보 항목 `vendor.value` 하나로 묶는다(`domain/vendors/index.ts` 59행 `{ key: "customFields", from: "customFields", infoItem: "vendor.value" }`). 프로젝트 DTO도 같은 결(`project.value`, `domain/projects/index.ts` 74행)이다. D10-13의 칸별 판정은 이 한 덩어리를 칸마다 나눠야 한다 — 이 페이즈는 거래처 DTO에서 만들고, 프로젝트·견적 줄 DTO 적용은 Phase 10에 남긴다
- `project()` 출구와 DTO 등록부는 Phase 4 브랜치(`claude/gsd-progress-e1nzgu`)에서 04-32로 이미 바뀌었고(SUMMARY 있음) main에는 아직 없다(`518ad0f`: `project()` 호출당 정보 항목 한 번 조회·`projectMany`·all-of; `domain/permissions/project.ts`·`dto-registry.ts`·`test/integration/leak-scan.test.ts`). 동적 항목을 판정에 넣는 설계는 그 브랜치의 모양을 읽고 정하며, 04-32가 main에 들어오기 전이면 충돌이 적은 방식(항목 출처를 늘리는 함수 하나 등)을 고른다. 04-32 자체를 이 페이즈에서 구현하지 않는다
- 노출표 항목 출처가 코드 상수 하나라는 전제는 여러 곳에 있다: `domain/permissions/matrix.ts` `visibilityColumns()`(130행), `app/(app)/admin/visibility/actions.ts` `infoItemKeys`(14행, 저장 시 허용 키 검사), `domain/seed/index.ts`(166행, 노출표 기본 행 시드), `test/integration/leak-scan.test.ts`(117·164행, `INFO_ITEMS` 등록 검사). 네 곳 모두 두 출처를 보게 된다. 시드는 Phase 4 04-20도 고친다. 04-20은 기획 PM 등의 기본값을 `insertVisibilityIfAbsent`(없을 때만 쓰기, `repositories/permissions.ts`)로 바꾸지만 시스템 관리자의 전 메뉴·전 항목 루프는 배포마다 계속 덮어쓴다(04-20-PLAN 43·166행). 커스텀 항목은 그 경로에 싣지 않는다 — 배포 시드가 관리자가 끈 커스텀 항목을 다시 켜면 D10-13의 계급별 끄기가 무의미해진다
- 새 칸의 기본값 「전 계급 보임」은 `visible()`의 「행이 없으면 숨김」(`domain/permissions/visible.ts` 21행) 규칙을 바꾸지 않고, 칸을 만들 때 모든 계급의 행을 없을 때만 쓰는 방식으로 지킨다. 나중에 만든 계급(04-20 시드가 팀장·본부 책임자·대표 계급의 노출표 기본값을 넣는다)도 기존 커스텀 항목 행을 받아야 한다 — 계급 생성 때 채울지, 판정 때 커스텀 항목은 기본 보임으로 볼지는 계획에서 정한다
- Phase 4 미완성 플랜이 고치는 파일 중 이 페이즈가 닿는 것: `app/(app)/admin/vendors/vendor-form.tsx`(04-25), `domain/permissions/menus.ts`(04-13·04-20, 관리 화면 메뉴 키), `repositories/permissions.ts`(04-20), `domain/archive/index.ts`(04-07·04-12, 보관함 화면에서 복원한다면). 모두 항목만 더하고, 머지 직전에 main을 합쳐 다시 확인한다
- 커스텀 칸의 노출표 항목 키는 기존 항목(`vendor.value` 등)과 겹치지 않는 형태로 정한다(예: 대상 표 + 칸 키). 보관한 칸의 노출표 행은 지우지 않고 숨긴다 — 복원하면 이전 계급별 설정이 그대로 돌아온다
- 마이그레이션 번호는 Phase 4(0011~0016)와 병렬 페이즈(04.1~04.4, 각자 계획 단계에서 정한다)와 겹치지 않게 계획 단계에서 정한다. 번호는 `pnpm db:generate`가 journal 다음 인덱스로 매기므로 손으로 붙이지 않는다. 머지 직전에 main을 합치고 자기 마이그레이션을 지운 뒤 `pnpm db:generate`를 다시 돌린다 — drizzle `migrate()`는 journal `when`이 마지막 적용보다 늦은 마이그레이션만 적용한다. 병렬 페이즈가 journal 순서 검사 테스트를 먼저 main에 넣었으면 그것을 따른다

### Claude's Discretion (Phase 10 논의에서 옮김)
- 커스텀 필드 표시 이름: `field_definitions`에 `label`(한글 이름) 칼럼이 없다. 관리자는 이름을 적고 `key`는 자동 생성하는 방향 — 새 마이그레이션(`label`·`archived_at`)은 계획이 정한다.
- 필수 칸을 나중에 추가했을 때 기존 행: 새로 만들거나 고칠 때만 요구하고 기존 빈칸은 허용.
- 선택형 칸의 선택지 삭제: 선택지도 보관(새 입력에서 숨김, 기존 값은 그대로 표시).
- 커스텀 칸의 화면 위치: 폼은 기본 칸 아래 묶음, 폰은 P3(접힘). 견적 줄 표의 오른쪽 끝 열은 Phase 10 몫. 관리 화면과 거래처 폼 쪽은 UI 계약(`/gsd-ui-phase 04.5`)에서 확정.
- 관리 화면의 경로·모양(대상 표 고르기 — 지금은 거래처 하나, 칸 목록, 추가·수정 폼, 보관·복원). 설정 레지스트리 자동 화면과 같은 틀로 충분한지, 보관함 화면(`app/(app)/admin/archive`)에서 복원할지 관리 화면 안에서 할지.
