# Phase 04.5: 화면 항목 관리 - Research

**Researched:** 2026-09-24
**Domain:** 관리자 CRUD 화면(커스텀 필드 정의) + 기존 권한/노출표 메커니즘 확장(동적 열)
**Confidence:** MEDIUM — 재사용할 메커니즘(권한 4함수·보관함·`build-schema.ts`·누수 스캔)은 전부 코드로 확인했다(HIGH). 다만 "정적 레지스트리 + `keyof Dto` 정적 타입" 위에 "런타임에 생기는 커스텀 항목"을 얹는 설계는 이 리포에 선례가 없어(신규 문제) 이 문서의 권고안은 판단(judgment)이며 계획 단계 확인이 필요하다(MEDIUM/LOW로 표시).

## Summary

이 페이즈는 새 라이브러리를 들이지 않는다 — 전부 Phase 3가 이미 세운 메커니즘(권한 4함수, `field_definitions`/`buildCustomFieldsSchema`, 보관함(`domain/archive`), 행동 로그, 누수 스캔 생성기)을 확장하는 작업이다. 핵심 난제는 두 가지다.

1. **정적 레지스트리에 동적 항목을 얹기.** `INFO_ITEMS`(`domain/permissions/info-items.ts`)·`DTO_REGISTRY`(`dto-registry.ts`)·`ACTION_REGISTRY`(`lib/actions/registry.ts`)는 전부 모듈 로드 시점에 채워지는 **정적** 배열이고, 누수 스캔(`test/integration/leak-scan.test.ts`)은 이 정적 배열을 순회해 테스트 케이스를 만든다. `field_definitions`가 만드는 노출표 항목(`cf.vendor.<key>`)은 **DB에 있는 런타임 데이터**라 이 정적 배열에 미리 넣을 수 없다. `domain/permissions/project()`의 `DtoSpec.fields`도 `key: keyof Dto & string`로 컴파일 타임에 고정돼 있어 거래처 하나당 커스텀 필드 개수만큼 필드를 동적으로 낳는 투영과 근본적으로 안 맞는다. 이 문서는 **기존 파일을 건드리지 않고 별도 보조 함수로 우회**하는 안(아래 아키텍처 절)을 권고한다 — `project.ts`·`dto-registry.ts`는 Phase 4 브랜치의 04-32가 이미 바꿔놓은 파일이라(§04-32 절 참고) 여기서 타입을 다시 바꾸면 병합 충돌 위험이 크다.
2. **보관한 칸·선택지·안 보이는 칸의 값을 잃지 않으면서 `.strict()` 검증을 유지하기.** `buildCustomFieldsSchema`는 `field_definitions`가 돌려주는 정의 목록으로만 zod 스키마를 만든다 — 보관된 필드/선택지를 그 목록에서 빼면 기존 값이 든 행을 다시 저장할 때 `.strict()`가 거부한다. 반대로 항상 포함하면 새 입력 화면에도 보관된 선택지가 다시 나타난다. "검증용 정의 목록"과 "입력 화면용 정의 목록"을 분리해야 한다(아래 Pitfall 2).

프로젝트·견적 줄 도메인(`domain/projects`, `domain/quotes/lines`)이 부르는 `listFieldDefinitions(viewer, entity)`의 시그니처·반환 모양은 절대 건드리지 않는다 — 이 함수는 Phase 3 계약대로 **entity의 전체 정의**(보관 포함)를 그대로 돌려주고, "보관 제외" 필요는 새 함수(`listActiveFieldDefinitions` 등)를 추가해 해결한다.

**Primary recommendation:** `field_definitions`에 `label`(text, not null)·`archivedAt`/`archivedBy`(roles/vendors와 같은 패턴)를 추가하고, `field_definitions`를 `ARCHIVABLE_TABLES`(`repositories/archive.ts`)에 등록해 기존 보관함 도메인 함수(`archive()`/`restore()`)를 그대로 재사용한다. 노출표 열은 `INFO_ITEMS` 정적 배열과 DB의 "보관 제외 field_definitions"를 **런타임에 합치는 함수**(`visibilityColumns()` 안, async화)로 만들고, DTO 투영은 `project()`를 바꾸지 않은 채 거래처 DTO 쪽에서 커스텀 필드 전용 보조 투영 함수를 별도로 호출해 병합한다. 누수 스캔은 정적 `DTO_REGISTRY`/`INFO_ITEMS` 축과 별개로, DB의 활성 `field_definitions`를 조회해 케이스를 만드는 새 `describe` 블록을 하나 더한다.

### Locked Decisions (04.5-CONTEXT.md에서 그대로 옮김)

- **D10-12: 칸 삭제는 보관이다.** 보관한 칸은 입력·목록·검색·내보내기에서 숨고, 이미 입력된 값은 JSONB에 남아 복원하면 다시 보인다.
- **D10-13: 추가한 칸은 정보 노출표에 자동 등록된다.** 기본값은 전 계급 보임이고, 관리자가 계급별로 끌 수 있다. `INFO_ITEMS`(코드 상수) + `field_definitions`(보관 제외) 두 출처를 합친다. 누수 스캔도 커스텀 필드 항목을 포함한다. — Reversibility: costly.
- **관리 화면의 대상은 거래처 하나로 켠다.** 프로젝트·견적 줄 칸은 이 페이즈에서 만들 수 없다(Phase 10이 켠다). 대상 목록은 한 곳(상수)에 두어 Phase 10이 추가한다.
- 끝까지 확인은 거래처 입력 화면(`app/(app)/admin/vendors/vendor-form.tsx`)으로 한다.
- `listFieldDefinitions(viewer, entity)`의 호출 모양을 바꾸지 않는다(Phase 4 코드가 부른다). 보관 제외가 필요하면 새 함수/선택 인자로 더한다.
- 보이지 않는 칸의 값도 지킨다 — 폼이 보내지 않은 키는 저장된 값에서 되살린다. 보관한 선택지도 기존 값은 통과, 새 입력에서만 숨긴다.
- 거래처 DTO의 `customFields` 전체를 하나의 `vendor.value` 항목으로 묶는 현재 구조를 칸별 판정으로 나눈다 — 이 페이즈는 거래처 DTO에서 만들고, 프로젝트·견적 줄 DTO 적용은 Phase 10.
- `project()` 출구·DTO 레지스트리는 Phase 4 브랜치(04-32, main에 아직 없음)의 모양을 읽고 계획하되, 04-32 자체는 이 페이즈에서 구현하지 않는다.
- 노출표 항목 출처가 코드 상수 하나라는 전제가 있는 네 곳 — `matrix.ts` `visibilityColumns()`, `admin/visibility/actions.ts` `infoItemKeys`, `domain/seed/index.ts`(시드는 손대지 않음 — 커스텀 항목은 배포 시드 경로에 싣지 않는다), `leak-scan.test.ts` — 를 두 출처를 보도록 고친다(시드 제외).
- 새 칸 기본값 "전 계급 보임"은 `visible()`의 "행 없으면 숨김" 규칙을 바꾸지 않고, 칸 생성 시 모든 계급 행을 없을 때만 쓰는 방식(insert-if-absent)으로 지킨다. 나중에 만든 계급도 기존 커스텀 항목 행을 받아야 한다.
- 공유 파일(Phase 4 미완성 플랜이 고치는 파일)은 항목만 더한다: `domain/action-log/record.ts`·`domain/permissions/info-items.ts`·`domain/permissions/menus.ts`·`domain/seed/index.ts`·`test/integration/leak-scan.test.ts`·마이그레이션 journal, `app/(app)/admin/vendors/vendor-form.tsx`, `domain/archive/index.ts`, `repositories/permissions.ts`.
- 커스텀 칸 노출표 항목 키는 기존 항목(`vendor.value` 등)과 겹치지 않는 형태(예: 대상 표 + 칸 키). 보관한 칸의 노출표 행은 지우지 않고 숨긴다.
- 마이그레이션 번호는 계획 단계에서 겹치지 않게 정하되(대략 0035~0039 구간이 비어있을 것으로 예상, §마이그레이션 절 참고) 실제 번호는 `pnpm db:generate`가 매긴다 — 손으로 붙이지 않는다. 머지 직전에 main을 합치고 자기 마이그레이션을 지운 뒤 다시 `pnpm db:generate`.

### Pattern 1: 보관함 재사용(ARCHIVABLE_TABLES 등록)

**What:** `field_definitions`를 `repositories/archive.ts`의 `ARCHIVABLE_TABLES` 배열에 한 항목으로 등록하면 `domain/archive.archive()`/`restore()`가 행동 로그 기록까지 포함해 그대로 동작한다.
**When to use:** 이 페이즈의 "삭제=보관"(D10-12) 요구사항 전체.
**Example:**
```typescript
// Source: repositories/archive.ts:55-179(실측, vendor 항목 패턴을 그대로 복제)
{
  entity: "field_definition",
  label: "화면 항목",
  async setArchived(viewer, id, value) {
    await setFieldDefinitionArchived(viewer, id, value); // 신규 repo 함수, vendors.setVendorArchived와 동일 패턴
  },
  async findById(viewer, id) {
    return findFieldDefinitionById(viewer, id); // 기존 함수 재사용
  },

}
```
**주의:** `domain/archive.archive()`가 요구하는 최소 행 모양은 `{ archivedAt: Date | null; isSeed?: boolean }`(`repositories/archive.ts:27` [VERIFIED: repositories/archive.ts:27] — `export type ArchivableRow = { archivedAt: Date | null; isSeed?: boolean };`)이므로 `field_definitions` 행에 `archivedAt` 컬럼만 있으면 충분하다.

### Pattern 2: DTO 투영은 `project()`를 바꾸지 않고 보조 함수로 병합

**What:** `VENDOR_DTO_SPEC.fields`에서 `customFields` 항목(`infoItem: "vendor.value"`)을 제거하고, `domain/vendors/index.ts`가 `project()` 결과에 별도 계산한 커스텀 필드 객체를 병합한다.
**When to use:** 칸별(D10-13) 노출 판정이 필요한 모든 지점(`listVendors`·`searchVendors`·`createVendor`·`updateVendor` 반환값).
**Example:**
```typescript
// 신규 — domain/custom-fields/admin.ts 또는 domain/vendors/index.ts 로컬 함수
async function projectCustomFields(
  viewer: Viewer,
  entity: string,
  raw: Record<string, unknown>,
  activeDefs: FieldDefinitionDto[], // 보관 제외
): Promise<Record<string, unknown>> {
  const result: Record<string, unknown> = {};
  for (const def of activeDefs) {
    if (!(await visible(viewer, `cf.${entity}.${def.key}`))) continue;
    if (def.key in raw) result[def.key] = raw[def.key];
  }
  return result;
}

// 호출부
const base = await project(viewer, row, VENDOR_DTO_SPEC); // customFields 필드 없는 스펙
const customFields = await projectCustomFields(viewer, "vendor", row.customFields, activeDefs);
return { ...base, customFields } as VendorDto;
```
**왜 `project()`/`DtoSpec`를 안 바꾸는가:** `project.ts`·`dto-registry.ts`는 Phase 4 브랜치(`claude/gsd-progress-e1nzgu`)의 04-32가 이미 `projectMany`·`InfoItemRef`(all-of 목록) 지원을 추가해놓은 상태다(§04-32 절) — main엔 아직 없다. 여기서 타입을 다시 고치면 04-32가 main에 들어올 때 충돌한다. 보조 함수로 우회하면 두 브랜치 모두 `project.ts`/`dto-registry.ts`를 건드리지 않아 병합이 항목 추가(vendor 쪽 domain 파일)로만 끝난다.

### Pattern 3: 노출표 두 출처 합치기(async화)

**What:** `domain/permissions/matrix.ts`의 `visibilityColumns()`를 async로 바꿔 `INFO_ITEMS` 정적 배열 + DB의 활성 `field_definitions`(현재는 vendor 엔티티만)를 합친 `GridColumn[]`을 돌려준다.
**Example:**
```typescript
// domain/permissions/matrix.ts:130 부근 수정 방향(실측: 현재 sync 함수, INFO_ITEMS만 사용)
async function visibilityColumns(): Promise<GridColumn[]> {
  const staticCols = INFO_ITEMS.map((item) => ({ id: item.key, label: item.label }));
  const dynamicCols: GridColumn[] = [];
  for (const { entity, label } of CUSTOM_FIELD_ENTITIES) {
    const defs = await listActiveFieldDefinitions(SYSTEM_VIEWER, entity); // 보관 제외
    dynamicCols.push(
      ...defs.map((def) => ({ id: `cf.${entity}.${def.key}`, label: def.label, group: label })),
    );
  }
  return [...staticCols, ...dynamicCols];
}
```
**연쇄 변경:** `readVisibilityGrid`가 이미 async라 `await visibilityColumns()`로 호출부만 고치면 된다(`domain/permissions/matrix.ts:151` [VERIFIED: domain/permissions/matrix.ts:149-153] — 원문: `return { roles: roleRows.map(...), columns: visibilityColumns(), values };`).

### Anti-Patterns to Avoid

- **`INFO_ITEMS`를 async 함수로 바꾸지 않는다** — `matrix.ts`·`admin/visibility/actions.ts`·`test/integration/leak-scan.test.ts`·향후 Phase 10 코드까지 전부 동기 배열로 이 상수를 읽는다. 정적 배열은 정적으로 두고, "두 출처 합치기"는 합치는 지점(위 Pattern 3)에서만 한다.
- **배포 시드(`domain/seed/index.ts` `seedMasterData`)에 커스텀 항목을 얹지 않는다** — 시스템 관리자 루프는 배포마다 전 메뉴·전 항목을 다시 켠다(04-20-PLAN 43·166행 [CITED: 04.5-CONTEXT.md:47]). 커스텀 항목이 이 루프를 타면 관리자가 노출표에서 끈 커스텀 칸이 재배포마다 되살아나 D10-13이 무의미해진다.
- **`buildCustomFieldsSchema`에 새 검증 로직을 추가하지 않는다** — 보관/선택지 문제는 "이 함수에 넘기는 `defs` 배열을 어떻게 구성하는가"로 푼다(호출부 책임), 함수 내부 로직은 그대로 둔다(ROADMAP 명시: "새 검증 코드 없음").

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| 삭제→보관, 복원 | 새 archived 플래그·복원 API | `domain/archive.archive()`/`restore()` + `ARCHIVABLE_TABLES` 항목 등록 | 행동 로그·권한 게이트·멱등성 이미 구현됨(§Pattern 1) |
| 필드 값 타입 검증 | 커스텀 field-level validator | `buildCustomFieldsSchema(defs)` | Phase 3 정본, `.strict()`로 미등록 키 방어 |
| 노출 판정 | 역할별 if문 | `visible(viewer, infoItem)` | `can()`과 완전 독립, 행 없으면 기본 거부 |
| 행동 로그 | 커스텀 감사 로그 테이블 | `recordAction(viewer, {...})` | `CORE_ACTION_TYPES`에 이미 `document_create`/`document_update`/`archive`/`restore`/`permission_change` 존재 — 새 종류 불필요 |
| 관리 화면 CRUD 뼈대 | 새 폼 프레임워크 | `app/(app)/admin/vendors` 패턴(page.tsx+form.tsx+actions.ts+actions.registry.ts) 복제 | 기존 SYSTEM.md §6-3 폼 템플릿·`useAction` 훅 관례가 이미 있다 |

**Key insight:** 이 페이즈의 "새로 만드는 것"은 딱 셋이다 — (1) `field_definitions`에 `label`/`archivedAt`/`archivedBy` 컬럼, (2) 커스텀 필드 CRUD 관리 화면 한 벌, (3) 노출표/DTO/누수 스캔이 "정적+동적" 두 출처를 보게 하는 병합 지점 3~4곳. 나머지는 전부 기존 함수 호출이다.

## Key 자동 생성 (Claude's Discretion — 권고)

리포 전체에 한글→ASCII 슬러그화(로마자 변환) 라이브러리나 선례가 없다(`grep -rln "slug\|romaniz"` 결과 0건 [VERIFIED: 코드베이스 grep, 이번 세션]). `code_items` 표(코드표)도 `value`(코드)를 관리자가 직접 입력하지 `label`(한글)에서 자동 유도하지 않는다(`db/schema/code-tables.ts:16-19` [VERIFIED: db/schema/code-tables.ts:16-19] — `tableKey`·`value`·`label` 세 컬럼이 나란히 있고 파생 로직이 없다).

**권고:** `key`를 라벨에서 "유도"하지 말고 **완전히 별도로 생성**한다 — 예: `` `cf_${randomUUID().slice(0, 8)}` ``. `field_definitions.id`도 이미 이런 식으로 생성되는 것이 관례다(`test/integration/custom-fields.test.ts:22` [VERIFIED: test/integration/custom-fields.test.ts:22] — `id: \`fd-${randomUUID()}\``). 근거:
1. 한글 로마자 변환은 새 의존성이 필요하거나(예: `hangul-romanization`, 미검증 패키지) 자체 구현 시 다의어·중복·특수문자 엣지 케이스가 많다 — CLAUDE.md "Simplicity First"에 어긋난다.
2. `key`는 화면에 노출되지 않는다(JSONB 프로퍼티명일 뿐, 사람이 보는 것은 `label`) — 읽기 좋을 필요가 없다.
3. `(entity, key)` unique 제약과 충돌할 확률이 사실상 0에 가깝다(uuid 8자리).

이 권고는 **[ASSUMED]** — ROADMAP·CONTEXT 어디에도 "키를 어떻게 만들지" 구체적 규정이 없고(Claude's Discretion 항목으로 명시적으로 열려 있음), 계획 단계에서 사용자 확인이 필요하다.

## Common Pitfalls

### Pitfall 1: `field_definitions`에 기존 행이 있는 상태에서 `label NOT NULL` 컬럼 추가

**What goes wrong:** `ALTER TABLE field_definitions ADD COLUMN label text NOT NULL`은 테이블에 기존 행이 있고 DEFAULT가 없으면 Postgres가 즉시 거부한다.
**Why it happens:** `test/integration/custom-fields.test.ts`가 이미 `insertFieldDefinition`으로 행을 만든다 — 로컬/CI 테스트 DB에는 매 테스트 실행마다 새 행이 생기고(정리되는지는 확인 필요), 스테이징에도 Phase 3/4 실행 중 필드 정의가 생겼을 수 있다.
**How to avoid:** 마이그레이션에서 `ADD COLUMN label text NOT NULL DEFAULT ''` 로 추가하거나(임시 기본값), `ADD COLUMN label text` → `UPDATE field_definitions SET label = key WHERE label IS NULL` → `ALTER COLUMN label SET NOT NULL` 세 문장으로 백필한 뒤 NOT NULL을 건다. `.squawk.toml`의 `excluded_rules`에 이미 `"adding-required-field"`가 있어([VERIFIED: .squawk.toml:12-18]) 린트는 통과하지만 **Postgres 자체의 NOT NULL 제약 위반은 별개 문제**이므로 반드시 백필 순서를 지킨다.
**Warning signs:** 로컬 `pnpm db:dev` 위에서 마이그레이션 적용 시 `null value in column "label" violates not-null constraint`.

### Pitfall 2: 보관된 선택지가 있는 select 필드를 z.enum이 거부

**What goes wrong:** `baseSchemaFor`의 select 분기(`domain/custom-fields/build-schema.ts:28-29` [VERIFIED: domain/custom-fields/build-schema.ts:28-29] — `case "select": return z.enum((def.options ?? []) as [string, ...string[]]);`)는 `def.options`에 있는 값만 허용한다. 관리자가 선택지 "B"를 보관(삭제)하면 그 즉시 "B" 값이 든 기존 거래처 행을 재저장할 때 `.strict()` 스키마가 "B"를 거부한다.
**Why it happens:** `options` 컬럼이 지금은 단순 `string[]`이고 "활성" 상태와 "보관" 상태를 구분할 자리가 없다.
**How to avoid:** `options` JSONB 구조를 `{ active: string[]; archived: string[] }` 또는 병렬 컬럼(예: `archivedOptions: string[]`)으로 확장한다. **검증용**(`buildCustomFieldsSchema`에 넘기는 `FieldDef.options`)은 `[...active, ...archived]`(전체 합집합)로 만들어 기존 값이 통과하게 하고, **입력 화면용**(select 태그의 `<option>` 목록)은 `active`만 넘긴다. `buildCustomFieldsSchema` 함수 자체는 손대지 않는다 — 호출부가 넘기는 `options` 배열의 구성만 바꾼다.
**Warning signs:** 통합 테스트 "보관한 선택지 값이 든 행을 다시 저장해도 거부되지 않는다"가 실패하면 이 지점이다.

### Pitfall 3: 나중에 required가 된 필드가 기존 행의 저장을 막는다

**What goes wrong:** `buildCustomFieldsSchema`에서 `required: true`인 필드는 `.optional()`로 감싸지 않는다(`build-schema.ts:37` [VERIFIED: domain/custom-fields/build-schema.ts:37] — `shape[def.key] = def.required === true ? base : base.optional();`). `.strict()` 객체에서 이 키는 **반드시 존재**해야 한다. `number`/`date`/`select` 타입이면 `z.coerce.number()`/`z.coerce.date()`/`z.enum()`이 빈 문자열(`""`)을 유효값으로 받아주지 않는다 — 빈 문자열은 `NaN`/`Invalid Date`/열거값 밖으로 실패한다. 반면 `text` 타입은 `z.string()`이 `""`도 통과시켜(길이 제약 없음) 문제가 드러나지 않는다.
**Why it happens:** 필드를 나중에 필수로 바꾸면, 그 필드가 생기기 전에 만들어진 거래처 행은 그 키에 값이 없다. `vendor-form.tsx`는 필수 필드는 값이 비어 있어도 항상 키를 보낸다(`vendor-form.tsx:97-102` [VERIFIED: app/(app)/admin/vendors/vendor-form.tsx:97-102] — `if (raw === "" && !def.required) continue;` → required면 빈 문자열도 그대로 `customFields[def.key] = raw`로 보낸다). number/date/select 타입에서 이 빈 문자열이 그대로 서버 검증에 걸린다.
**How to avoid:** 이 요구사항("기존 빈칸은 허용, 새로 만들거나 고칠 때만 요구")은 **필드 단위 required가 아니라 "이 값을 실제로 바꾸려는 시도인가"** 기준으로 판정해야 한다. 계획에서 택할 방향 예시(둘 중 하나, 또는 계획이 정하는 세 번째 방안):
  (a) `validatedCustomFields`가 update 시 기존 행(`existing.customFields`)을 받아, 신규 payload 값이 빈 문자열이고 기존 값도 없으면 그 키를 **payload에서 제거한 뒤** 검증한다(즉 required 강제를 우회하되 다른 값 변경은 그대로 검증). create 시(기존 행 없음)에는 그대로 required 강제.
  (b) `vendor-form.tsx`가 "값이 비어 있고 편집 모드에서 기존 저장값도 없는" required 필드는 애초에 payload에서 제외한다(위 Pitfall과 같은 조건을 폼 레이어에서 미리 처리) — 서버 검증 로직은 안 바꾸지만 방어가 얕아진다(강제 로직이 클라이언트에만 있음).
계획 단계에서 (a)를 권고한다 — 서버 쪽에 방어가 남는다. **이 필드는 [ASSUMED] 권고이며 계획에서 명시적으로 확정해야 한다.**
**Warning signs:** "필수 칸 추가 후 기존 거래처의 다른 필드 수정 저장 시 실패" 통합 테스트.

### Pitfall 4: `infoItemKeys` 정적 Set이 커스텀 항목 키를 거부

**What goes wrong:** `setVisibilityCellAction`의 zod 스키마가 `infoItem`을 `INFO_ITEMS`에서 만든 정적 `Set`으로만 검증한다(`app/(app)/admin/visibility/actions.ts:14,20` [VERIFIED: app/(app)/admin/visibility/actions.ts:14,20] — `const infoItemKeys = new Set(INFO_ITEMS.map((item) => item.key));` / `.refine((value) => infoItemKeys.has(value), ...)`). 관리자가 노출표에서 커스텀 항목(`cf.vendor.<key>`)을 토글해도 이 액션이 "알 수 없는 정보 항목입니다"로 거부한다.
**Why it happens:** `INFO_ITEMS`는 모듈 로드 시 고정되는 배열이라 런타임에 생기는 커스텀 항목을 담을 수 없다.
**How to avoid:** `roleId` 필드가 이미 쓰는 패턴(같은 파일, DB를 직접 비동기로 확인하는 `.refine(async ...)`)을 그대로 따라 `infoItem` 검증도 비동기 DB 확인으로 바꾼다 — `INFO_ITEMS.has(value) || (활성 field_definitions에서 cf.<entity>.<key> 형태로 일치)`.
**Warning signs:** E2E "노출표에서 커스텀 칸을 끈다" 시나리오가 서버 오류로 실패.

`visibility_matrix`에는 같은 패턴의 `insertVisibilityIfAbsent`가 **main에는 아직 없다**(`upsertVisibility`만 있음, [VERIFIED: repositories/permissions.ts:100-117] — `onConflictDoUpdate`뿐). Phase 4 브랜치의 04-20 플랜이 이 함수를 `repositories/permissions.ts`에 추가할 예정이다("없을 때만 넣는 권한·노출 시드 함수", [CITED: 04-20-PLAN.md:69-70, 브랜치 claude/gsd-progress-e1nzgu]). **이 페이즈 실행 시점에 main에 이미 있으면 재사용하고, 없으면 같은 이름·시그니처로 이 페이즈가 직접 추가한다** — CONTEXT.md가 명시("04-20의 `insertVisibilityIfAbsent`가 main에 있으면 그것을 쓴다"). 두 플랜이 같은 함수를 동시에 정의하면 머지 시 충돌하므로, 계획에 "실행 직전 main 재확인" 체크포인트를 넣는다.

용도가 다르다는 점도 유의: 04-20의 함수는 **배포 시드**(새 계급이 생겼을 때 그 계급의 기본 권한 행을 채움)가 부르고, 04.5는 **필드 생성 시점**(관리자가 커스텀 필드를 만들 때 모든 기존 계급에 대해 `visible=true` 행을 채움)에 부른다 — 함수 자체는 공유해도 호출 지점은 다르다.
