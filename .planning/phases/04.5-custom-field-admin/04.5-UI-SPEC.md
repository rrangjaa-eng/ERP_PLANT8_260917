## Spacing Scale

Declared values (from `docs/design/tokens.css`, 4px 단위 — 템플릿 기본 6단계 중 `xl`·`3xl`는 이 시스템에 없고, 이 시스템에만 있는 두 단계(`--s-3`·`--s-5`)를 더한다):

| Token | Value | Usage |
|-------|-------|-------|
| `--s-1` | 4px | 폼 라벨-입력 세로 간격 |
| `--s-2` | 8px | 셀 상하 패딩(PC) |
| `--s-3` | 12px | 셀 좌우 패딩, 그룹 머리글 위 여백 |
| `--s-4` | 16px | 폼 항목 사이, 표 셀 패딩(폰) |
| `--s-5` | 20px | PC 컨테이너 좌우 패딩 |
| `--s-6` | 24px | 폼 묶음 사이(예: 커스텀 필드 섹션과 기본 칸 사이), 섹션 위 여백 |
| `--s-8` | 32px | 레이아웃 큰 간격(이 페이즈에서 드묾) |
| `--s-12` | 48px | 최대 섹션 간격 |

Exceptions: 템플릿의 `3xl`(64px)에 해당하는 토큰이 시스템에 없다 — 이 프로젝트의 최대 간격은 `--s-12`(48px)다. 새 값을 만들지 않는다(`DECISIONS.md` 절차 없이는 금지).

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px(`--fs-base`, 폰 15px) | 400 | 1.6(`--lh-body`), 표 셀은 1.5(`--lh-table`) |
| Label | 12px(`--fs-sm`) | 600 | 1.5 |
| Heading | 18px(`--fs-lg`) | 700 | 1.4 |
| Display | 사용 안 함 | — | — |

이 페이즈는 관리자 마스터 화면·폼·체크박스 매트릭스뿐이라 `--fs-2xl`(32px, 손익 대시보드 KPI 전용)과 `--fs-xl`(24px, 대시보드/인쇄/외부 수령자 전용)을 쓰지 않는다. 한 화면에 섞는 크기는 최대 4단계(`--fs-xs`·`--fs-sm`·`--fs-base`·`--fs-lg`)를 넘지 않는다(§2-2).

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--bg` `#FFFFFF` | 화면 바탕 전체 |
| Secondary (30%) | `--surface` `#F3F7F5` / `--g-50` `#EBF2F0` / `--g-100` `#DCE8E4` | 목록 행 hover(`--surface`), 표 머리글·매트릭스 머리글(`--g-100`) |
| Accent (10%) | `--accent`(`--g-700` `#005446`) | 아래 「Accent reserved for」만 |
| Destructive | `--danger`(`#9B1C1C`) | 오류 셀·검증 실패 문구·틀린 칸 테두리. **붉은 버튼은 없다** — 보관(삭제)은 색이 아니라 `DeleteToArchive`의 2단계 확인으로 구분한다(§1-3 규칙 3, §7-1) |

Accent reserved for(이 페이즈에서 실제로 쓰는 자리만, §1-3의 5곳 중 해당분):
- **1차 버튼 배경** — 「화면 항목 추가」·「화면 항목 수정」 제출 버튼
- **포커스 링** — 모든 입력·버튼·링크·체크박스의 `:focus-visible`

해당 없음(이 페이즈의 화면들이 쓰지 않는 나머지 3곳): 내 차례 태그·행동 링크(이 화면들은 「내 차례」 대상이 아님), 편집 중 셀·행(엑셀식 그리드 편집이 아님), 현재 위치 내비게이션 밑줄(상단 바 1차 메뉴가 아니라 「관리」 인덱스 하위 화면).

- 새 선택지 추가는 그 자리에서 목록에 항목을 더하는 **클라이언트 상태 조작**이고(아직 저장 안 됨), 폼 제출 시 그 시점의 활성 선택지 배열을 함께 보낸다. 기존(저장된) 선택지의 「보관」 버튼은 **즉시 그 옵션을 활성 목록에서 지역적으로 제거**하고 제출 시 반영한다(별도 서버 호출 없음 — 필드 정의 갱신 액션 하나가 label·required·sortOrder·options를 한 번에 저장한다, `updateFieldDefinition`이 `type`만 못 받을 뿐 나머지는 갱신 가능하다는 04.5-RESEARCH.md 계약과 일치)

### 화면 3 — 거래처 폼의 커스텀 칸 (`/admin/vendors`, 기존 화면 확장)

`vendor-form.tsx`는 이미 `fieldDefs.map`으로 커스텀 칸을 그린다(03-06). 이 페이즈가 새로 정하는 것은 **묶음 경계**와 **보관/비노출 칸의 값 보존 표시**뿐이다 — 입력 하나하나의 렌더는 바꾸지 않는다.

```
│ 이름 · 사업자 번호 · 기본 증빙 종류 · 계좌 은행 · 예금주 · 계좌번호 │ ← 기존 기본 칸(변경 없음)
├──────────────────────────────────────────────────────────┤ ← 1px --line + --s-6(§7-15 「묶음 사이」) — 신설
│ 담당자 연락처  [________________]                            │ ← fieldDefs.map, 활성 정의만(보관 제외)
│ 갱신일        [__________]                                  │
╞══════════════════════════════════════════════════════════╡
│ [거래처 등록/수정]  ...                                취소  │
```

- 커스텀 칸 라벨은 `def.key`가 아니라 **`def.label`**을 쓴다(이 페이즈가 `label` 컬럼을 추가하므로 `vendor-form.tsx`의 기존 `<label htmlFor={id}>{def.key}</label>`를 `{def.label}`로 고친다 — 사람이 보는 이름이 키가 아니라 이름이어야 한다는 것이 D10-12/13의 전제)
- 위 기본 칸 묶음과 커스텀 칸 묶음 사이에 **1px 선 구분**을 새로 넣는다(§7-15 Form 「묶음 사이 `--s-6` + `1px --line`」 — 지금 코드에는 이 구분선이 없다, 신설 지점). 구분선 위에 텍스트 라벨(「추가 항목」 등)을 붙이지 않는다 — §6-3 실물의 증빙/결재선 묶음도 텍스트 헤더 없이 선만으로 나뉜다
- 보관된 칸: 폼에 **렌더되지 않는다**(입력·목록·검색·내보내기에서 숨는다는 D10-12 그대로). 저장 시 그 칸의 기존 값은 서버가 되살리므로(§Pitfall 3/보관 규칙, 04.5-RESEARCH.md) 화면에는 아무 흔적도 남기지 않는다 — 「숨겨진 값이 있습니다」 같은 안내를 붙이지 않는다(§8 규칙 5, 값이 조용히 보존되는 것이 계약이지 사용자에게 알릴 일이 아니다)
- 계급별로 끈 칸(정보 노출표에서 `visible=false`): 서버가 애초에 그 `fieldDefs` 배열에 포함하지 않는다(§7-3 「칸 수 가변」과 같은 원칙 — 클라이언트에서 숨기지 않는다). 빠진 칸의 폭은 다른 칸이 흡수하지 않는다(폼은 세로 목록이라 §7-3의 가로 폭 흡수 규칙이 해당 없음 — 그 칸의 자리가 그냥 없다)
- 선택형(select) 칸에서 저장된 값이 **보관된 선택지**인 경우: 네이티브 `<select>`에 활성 선택지 + 현재 값(보관된 선택지 1개, `disabled`)을 함께 렌더한다 — 표시는 되지만(현재 값을 사람이 알아야 하므로) 다시 고를 수는 없다. 라벨은 `{value} (보관됨)`. 새로 값을 바꾸면(활성 선택지 중 하나를 고르면) 그 보관 선택지는 다시 나타나지 않는다
- 폰: 이 화면은 이미 §6-3 폼 화면 폰 규칙(라벨이 위로, 전폭)을 따른다 — 커스텀 칸도 같은 규칙, 별도 P1/P2/P3 접기 없음(그건 §7-3 **표**의 규칙이고 이 화면은 폼이다)
- 다섯 상태: 위 UI Considerations 표(E4)와 동일

- 다섯 상태: 기존 §7-13 「다섯 상태」 표 그대로(변경 없음) — 이 페이즈가 여는 것은 열 개수뿐, 상태 계약은 손대지 않는다

4. **목록·복원은 vendors/code-tables 패턴을 그대로 물려받는다 — 보관 행에 인라인 「복원」을 두지 않는다.** vendors·code-tables 실측 코드(`vendor.archivedAt ? null : (...)`)가 이미 이 원칙이다: 보관 즉시 그 행의 동작 칸이 빈다. 복원은 `/admin/archive`(범용 보관함 화면)에서 한다 — 04.5-RESEARCH.md Open Question 1이 열어 둔 자리를 **기존 선례를 따라 화면 안에 별도 복원 UI를 만들지 않는 쪽**으로 닫는다(코드 재사용 목적은 `ARCHIVABLE_TABLES` 등록만으로 달성되고, `archive()`/`restore()`를 굳이 두 화면에서 다시 배선하지 않는다).
5. **필수(required) 열/필드는 `StatusTag`가 아니라 평문으로 표시한다.** §7-5 상태 태그는 닫힌 어휘(막힘·오늘·결재·대기·승인·반려·편집 중·진행·현재·완료(정산)·미수주·취소·보관됨·비활성·숨김)를 갖는 컴포넌트다. 「필수」는 상태가 아니라 정적 속성이라 그 어휘를 늘리지 않고 §2-4 「값이 없으면 —」 규칙만으로 표시한다.
6. **선택지 편집 = 추가 + 보관뿐, 이름 변경 UI 없음.** 저장된 선택지 문자열은 그 자체가 JSONB 저장값이라(`db/schema/field-definitions.ts`) 이름을 바꾸면 이미 저장된 거래처 값과 문자열이 어긋난다(04.5-RESEARCH.md Pitfall 2). 이름 변경을 허용하려면 선택지가 `{id, label}` 쌍으로 바뀌어야 하는데 이는 스키마 변경이라 이 페이즈의 「새 검증 코드 없음」·「스키마는 label/archivedAt만 추가」 잠금과 충돌한다 — 제외.
7. **선택지 「보관」에 개별 「복원」 버튼을 두지 않는다.** 필드 전체 보관·복원(항목 4)과 달리 선택지 단위 복원은 요구사항 어디에도 명시되지 않았고(Claude's Discretion 항목이 「선택지 삭제는 보관(숨김)」까지만 말한다), 필요해지면 필드를 통째로 보관·복원하는 것으로 우회할 수 있어 지금 만들지 않는다(YAGNI).
8. **거래처 폼의 기본 칸 ↔ 커스텀 칸 사이에 1px 구분선을 신설한다(코드 변경 지점으로 명시).** CONTEXT.md의 「폼은 기본 칸 아래 묶음」을 §7-15 Form 컴포넌트의 기존 「묶음 사이 `--s-6` + `1px --line`」 계약으로 정확히 대응시켰다 — 새 시각 언어를 만들지 않고 이미 있는 계약을 적용만 한다.
9. **보관된 select 선택지가 현재 값일 때 `disabled` 옵션 + `(보관됨)` 접미사로 표시한다.** 04.5-RESEARCH.md Pitfall 2의 「검증용 목록엔 포함, 화면엔 active만」 권고를 select 렌더 수준까지 구체화했다 — 현재 값을 안 보이게 하면 사용자가 「내가 뭘 골랐었지」를 알 수 없고, 그냥 보이게(비-disabled) 하면 새 입력에서 다시 선택 가능해져 D10-12(「새 입력에서 숨김」)를 어긴다.
10. **정보 노출표 커스텀 열이 위조된 키를 받을 때의 오류 문구는 기존 문구를 재사용한다.** 04.5-RESEARCH.md Pitfall 4는 검증 로직(정적 Set → 비동기 확인)만 바꾸라고 하지 문구를 바꾸라고 하지 않는다 — 새 카피를 만들지 않는다.
11. **폰의 목록 P1/P2/P3 배정(이름·상태-또는-동작·타입 / 필수·정렬·선택지)은 vendors·code-tables에 선례가 없어 §7-3 일반 규칙(P1 최대 3열, 문자+숫자+상태-또는-행동)만으로 직접 배정했다.** 동작(수정·보관)이 이미 있는 행은 상태 열 대신 동작을 P1에 넣는다(vendors 폰 실측 패턴 — 목록 행에 상태와 동작이 공존할 때 우선순위를 매긴 06-01·06-04 선례가 이 문서 범위 밖이라, 이 배정은 계획 단계에서 vendors 폰 뷰 실측과 대조 확인이 필요할 수 있다).
