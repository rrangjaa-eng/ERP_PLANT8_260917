# Phase 04.6 — 공통 실행 규칙 (모든 04.6 플랜이 `<context>`로 읽는다)

> 플랜마다 되풀이하지 않으려고 한 곳에 둔 실행 규칙이다. 플랜의 `<action>`·`<acceptance_criteria>`가 「공통 §n」으로 가리킨다. 계약의 출처는 `04.6-UI-SPEC.md`(승인) · CHECKLIST §1 · ROADMAP SC 1~13이다.

## §1 웨이브 시작 의식 (세션 하나 = 웨이브 하나 — 같은 웨이브의 플랜은 한 세션에서 나란히)

1. 어떤 작업보다 먼저 `git fetch -q origin main && git merge --no-edit origin/main`(머지 커밋 — force push 금지). 충돌이면 멈추고 사용자에게 알린다.
2. 04.3(PR #88)·04.5 머지 여부를 `git log --oneline origin/main | grep -E "#88\)|04\.3|04\.5"` · `git ls-tree -d origin/main -- "app/(app)/certs"` · `git ls-tree origin/main -- "app/(app)/admin/field-definitions/page.tsx"`로 확인해 SUMMARY에 적는다. 순서는 사용자 결정(2026-09-30): 04.3 머지 → 04.5 실행 → 04.6 실행.
3. (04.6-02 뒤 웨이브) main에서 새로 들어온 CSS·TSX가 새 규칙에 걸리면 `node scripts/design/mark-legacy.mjs --add`로 그 파일에만 이관 전 표시를 넣어 머지 정리 커밋에 담는다(표시를 넣은 파일 목록을 SUMMARY에). 웨이브 ⑤(04.6-26~30) 이후에 표시가 새로 생기면 표시 0 단언이 설 수 없으므로 멈추고 `/gsd-plan-phase 04.6 --gaps`를 제안한다.
4. 푸시 전에도 1을 다시 한다.

## §2 실행 규율

- 화면 파일(`app/`·`ui/`의 .tsx·.css, `docs/design/`)을 고치기 전에 Skill `design-gate`를 호출하고, 플랜마다 점검표 `docs/design/checks/<실행일>-04.6-NN-<작업>.md`를 만든다. 「화면:」 줄에는 이 플랜이 고친 폴더를 하나씩(`app/`·`ui/` 통째 금지). 모든 항목 `[x]` + 근거 한 줄.
- 코드 태스크는 먼저 Skill `test-driven-development`(RED를 실제로 확인 → GREEN → 리팩터). 테스트·빌드·린트 실패는 코드를 만지기 전에 Skill `systematic-debugging`. 커밋과 「완료」 전에 Skill `verification-before-completion`. 서브에이전트에 맡기면 세 스킬과 `model`을 프롬프트에 적는다.
- 공유 테스트 DB·E2E 서버·`next build`는 `flock /tmp/plant8-erp-test.lock` 접두(환경 변수는 `sh -c '…'` 안). E2E 판정은 `CI=true`(프로덕션 빌드). 로컬은 건드린 화면의 스펙만 — 전체 E2E는 ready PR의 CI 한 번.
- 새 의존성 0(예외: 04.6-26에서 UQ-5 B가 사람 승인됐을 때만). `any` 금지. 요청 밖 리팩터 금지 — 지우는 것은 자기 변경으로 쓸모없어진 것만.
- Next.js 16은 학습 데이터와 다르다 — 링크·라우터를 만지면 `node_modules/next/dist/docs/01-app/03-api-reference/02-components/link.md`(「scroll」·「Scrolling to an id」)와 `04-functions/use-router.md`를 먼저 읽는다.
- 커밋 제목은 영어 접두어(docs:/feat:/fix:/test:/chore:) + 짧은 요약, 본문 한국어. 한 커밋 한 의도.
- `.planning/`은 GSD 도구로만(`gsd-phase` 등).
- 묶음: 페이즈 브랜치 하나(draft PR)에 웨이브를 쌓는다. 위험 경로 변경(`.github/workflows/` 04.6-03 · `.claude/` 04.6-30)은 `origin/main`에서 갈라진 별도 브랜치·별도 PR이고 사용자가 직접 머지한다(세션 머지 금지 — 훅이 막는다).

## §3 이관 전 표시(래칫) — 중앙 목록 파일 없음

같은 웨이브의 여러 플랜이 한 목록 파일을 고치면 파일 겹침이 되므로, 아직 옮기지 않은 파일은 **그 파일 맨 위 한 줄**로 표시한다(04.6-02가 형식·생성 스크립트·래칫 테스트를 만든다).

| 종류 | 표시(파일 첫 줄) | 래칫 테스트 |
|---|---|---|
| CSS 새 규칙 | `/* stylelint-disable unit-disallowed-list, declaration-property-value-allowed-list, declaration-property-value-disallowed-list -- 04.6 스킨 A 이관 전 */` | `test/unit/stylelint-config.test.ts` |
| TSX 직접 그리기 | `/* eslint-disable no-restricted-syntax -- 04.6 스킨 A 이관 전 */` | `test/unit/eslint-restrictions.test.ts` |
| 화면 틀 | `// 04.6 스킨 A 이관 전: 화면 틀` | `test/unit/ui/screen-frames.test.ts` |

- 래칫: 표시가 있는데 표시를 떼도 위반이 0건인 파일이 있으면 테스트가 실패한다(옮겼으면 표시를 떼라). 04.6-28이 「표시 0」을 단언한다.
- 플랜은 **자기 `files_modified`에 있는 파일의 표시만** 뗀다.
- 스크립트: `node scripts/design/mark-legacy.mjs --add`(새 규칙에 걸리는 파일에만 표시 추가) · `--list`(표시 파일 목록과 개수) · `--audit <경로…>`(공통 §4 마무리 조건 위반을 줄 단위로 출력, 위반이 있으면 종료 코드 1).

## §4 화면·컴포넌트 마무리 조건 (화면 플랜의 수용 기준 — `--audit`가 기계로 확인)

`node scripts/design/mark-legacy.mjs --audit <이 플랜의 폴더·파일…>`이 아무 줄도 출력하지 않고 종료 코드 0이다. 확인 항목: (a) 이관 전 표시 0 · (b) `@/ui/page-header/PageHeader` 직접 import 0 · (c) `StatusTag`에 `kind` 0(`status` 낱말만) · (d) CSS에 옛 토큰 이름(`--bg` `--surface` `--fg` `--muted` `--faint` `--line` `--line-ui` `--line-strong` `--line-w-strong` `--radius` `--shadow` `--modal-w` `--bar` `--fs-*` `--danger`·`--warning`·`--success`(+`-weak`) `--scrim` `--row-min`)과 원시 토큰 직접 참조 0 · (e) `app/**`에 `<table>`·`<dialog>` 0 · (f) 패널을 여는 링크에 해시 0.
그 밖에(사람·E2E가 확인): 패널 여는 링크는 `next/link` + `scroll={false}` · 숫자는 `Num` · 행 행동은 `RowActions` · 목록 부제 설명문 삭제(UI-SPEC Copywriting — 그 밖의 문구는 바꾸지 않는다) · 권한 분기(`canWrite` 등)·`actions.ts`는 그대로.

## §5 E2E 기대 규칙 · 스펙 소유

- 이 플랜이 바꾼 것의 계산 값을 재는 스펙을 `grep -rlnE "getComputedStyle|toHaveCSS|tokenAsColor|tokenValue|tokenNumber|getPropertyValue" test/e2e`로 찾아 `CI=true`로 돌리고, **스킨·배치가 의도해 바꾼 값만** UI-SPEC 값으로 갱신한다. 단언을 지우거나 느슨하게 하지 않는다(바꾼 줄 · 옛 값 → 새 값 · 근거를 SUMMARY 표로).
- 옛 토큰 **이름** 문자열은 옛 이름이 남아 있는 동안 바꾸지 않는다(04.6-27이 한 번에).
- 스펙 파일의 소유자는 그 웨이브에서 그 파일을 `files_modified`에 적은 플랜이다. 같은 웨이브의 **다른 플랜 소유** 파일은 고치지 않는다 — SUMMARY 「넘김」에 적는다. 어느 같은 웨이브 플랜도 소유하지 않은 파일을 고쳐야 하면 고치고 SUMMARY 「목록 밖 수정」에 적는다.

## §6 옆 패널 쓰는 법 (04.6-04가 만든 API — 화면 플랜 공통)

RSC `page.tsx`가 `searchParams`로 판정해(기존 규칙: `editId`가 `new`를 이김 · 보관된 `editId`는 등록 모드 · 쓰기 권한 없으면 패널 없음) `ListScreen panel={… ? <SidePanel title="{대상} 등록|수정" closeHref={목록 URL}> <폼/> </SidePanel> : null}`. 폼은 `PanelForm`(1차 라벨 = 기존 문구 · 행동 줄 「취소 Esc → 1차」 · Ctrl+Enter · 성공 처리 = UQ-8 답 하나). 연속 입력용 `formRef.reset()` 같은 화면별 성공 코드는 `PanelForm`이 대신하므로 중복만 지운다. 폼 `id`는 유지(셀렉터 변경 최소). 제어 형태(`onClose`)는 상태로 여닫는 시트(결재 시트)만.

## §7 독립 DOM 감사 (화면 플랜마다)

실행자가 아닌 별도 Sonnet 에이전트가 `CI=true` 프로덕션 빌드에서 이 플랜의 화면(PC 1280 · 폰 390 · 320, 패널이 있으면 열린 상태 포함)의 DOM을 실측한다 — 틀 제목 크기·1차 버튼 하나·부제 없음·표 면(r8 · 1px)·행동 링크 간격·패널 폭/위치/모서리/가림막·행동 줄 순서·포커스·대비. 스크린샷 육안 판정 금지. 지적을 고친 뒤 해당 스펙만 다시 돌린다.
