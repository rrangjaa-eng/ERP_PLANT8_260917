## Summary

이 페이즈는 새 라이브러리가 필요 없다. 필요한 도구(stylelint 17.15.0, eslint 9.39.5 `no-restricted-syntax`, Playwright 1.63.0 `toHaveScreenshot`, @axe-core/playwright 4.13.0, vitest 5.0.1)가 모두 설치돼 있고, 요구된 lint 계약은 **기존 규칙만으로** 구현된다(로컬 플러그인 불필요). 핵심 위험은 기술이 아니라 **이행 마찰**이다: (1) 옛 토큰 이름을 런타임에서 읽는 테스트가 24개 파일 70줄, CSS 텍스트를 정규식으로 단언하는 단위 테스트가 다수, SYSTEM.md 문구를 단언하는 테스트가 수십 개 — 토큰·문서를 바꾸는 웨이브가 이 테스트를 같은 커밋에서 옮겨야 한다. (2) 공유 `erp_test`와 병렬 스펙 때문에 목록 화면 사진이 비결정적이다. (3) 04.3(PR #88, 이미 실행됨)이 `ui/button`·`ui/input`·`ui/table`·`SYSTEM.md`·`DECISIONS.md`·`playwright.config.ts`를 건드려 04.6과 겹친다.

옆 패널은 저장소에 이미 있는 **네이티브 `<dialog>.showModal()` 패턴**(`ConfirmDialog`·`MoreSheet`·`RowSheet`)으로 만드는 것이 맞다(포커스 트랩·Esc·뒤쪽 비활성 제공). Next 16 공식 가이드가 검색 파라미터 기반 다이얼로그 + `router.replace('?', { scroll: false })`를 권장하므로 UI-SPEC의 토글 URL 유지가 공식 패턴과 일치한다. 현재 「목록이 밀리는」 원인은 폼이 문서 흐름 안에 있는 것과 `…#vendor-form` 해시 이동이다 — 패널은 `position: fixed` 최상위 레이어이고 링크에서 해시를 제거하면 된다.

시각 회귀 기준 사진은 **CI(ubuntu-latest, Playwright 1.63 번들 Chromium 153)에서 만들어야 한다** — 이 클라우드 세션의 Chromium은 141이라 픽셀이 다르다. CI에서 사진을 꺼내려면 `ci.yml` e2e 잡의 아티팩트 스텝(152–157행)에 `test-results/`를 더해야 하고(현재 CI 리포터는 html이 아니라 `playwright-report/`가 비어 있다), 이는 위험 경로(`.github/workflows/`) → **별도 PR, 사용자 직접 머지**.

**Primary recommendation:** 기존 stylelint 규칙(`unit-disallowed-list` · `declaration-property-value-allowed-list` · `overrides`)과 eslint `no-restricted-syntax`만으로 기계 검사를 만들고, 「아직 못 옮긴 파일」 목록은 `stylelint.legacy.mjs`/eslint `ignores` 배열 하나로 웨이브마다 줄이며(단위 테스트가 비어 있어야 통과), 옆 패널은 네이티브 `<dialog>` + `?new=`·`?editId=` 토글 + `Link scroll={false}`로 구현하고, 시각 회귀는 **전용 Playwright 프로젝트를 다른 스펙보다 먼저** 직렬 실행해 결정성을 확보한다.

```
        │         (네이티브: 뒤 문서 inert · Esc=cancel · 포커스 트랩 · ::backdrop = --scrim-panel)
        ├─ PanelForm → 기존 Server Action (useAction)
        │     ├─ 성공: router.replace(listHref, {scroll:false}) → RSC가 패널 없이 재렌더 → unmount → 포커스 복귀
        │     └─ 실패: 패널 유지 · 칸 아래 「원인 · 다음 행동」 · 값 보존
        └─ 닫기(Esc·x·취소): onRequestClose(dirty 가드 가능) → router.replace(listHref,{scroll:false})
```

### Pattern 1: stylelint — 범위별 규칙 조립 + 마지막에 legacy 해제
**What:** 규칙 객체를 범위(`base`/`ui`/`app`/`print`)별 함수로 만들고 `overrides`에 넣되, **`overrides`는 규칙 옵션을 통째로 교체**(깊은 병합 아님)하므로 범위마다 전체 맵을 다시 적는다. 「아직 못 옮긴 파일」 해제 override는 **맨 마지막**에 둔다(앞에 두면 뒤의 `app/**` override가 다시 켜 버린다 — 이 연구의 실측에서 15건이 다시 살아났다).
**When to use:** SC 1·6·7 전부.
**실측 근거(이 세션에서 실행):**
- 임시 규칙(아래 「측정」)을 현 저장소 CSS 47개에 돌리면 **45개 파일 317건**(`declaration-property-value-allowed-list` 269 + `unit-disallowed-list` 48). 깨끗한 파일은 `ui/form-alert/FormAlert.module.css`·`app/(auth)/login/login-form.module.css` 둘뿐. 269건 중 `font-size` 231건(=`--fs-*`→`--text-*` 이름 변경), `border-radius` 14, `padding` ~13, `margin` 5+, `box-shadow` 4, `z-index` 1 등. 날 px 선언 실질 원인: `width/height:1px; margin:-1px`(sr-only 5곳 중복 — `globals.css`·`action-log`·`archive`·`PermissionGrid`), `7px 0`·`6px 0`·`9px 0`·`13px 0`(+`margin:-13px 0`) 패딩, `top:-80px`, `padding-bottom:72px`, `grid-template-columns: 84px 1fr`, `height: 38px/44px/32px`, `min-width:160px`, `Form`의 칸 폭 200/280/480, `translateY(4px)` 등.
- `stylelint.lint({ code, config, configBasedir, codeFilename })` API에서 `overrides`가 경로로 적용됨 — `ui/` 통과 · `app/`에서 제목 크기 1건 경고 · legacy 경로 0건 [VERIFIED: 스크래치 스크립트 실행 결과 `ui/button… 0 / app/(app)/… 1 / ui/next-turn… 0`]. 즉 경로별 규칙을 단위 테스트에서 `codeFilename`으로 직접 검증할 수 있다.
- 전체 `pnpm exec stylelint …` 실행 시간 약 0.9초 → 작업 커밋마다 돌려도 싸다.

### Pattern 2: 네이티브 `<dialog>` 옆 패널
**What:** `SidePanel`(client)이 마운트되면 `dialog.showModal()`을 부른다(가드: `if (!dialog.open)` — `ConfirmDialog`와 같은 StrictMode 안전 패턴). URL이 패널 없는 상태로 돌아가면 서버가 패널을 렌더하지 않아 언마운트된다(`dialog` 요소가 DOM에서 사라지며 최상위 레이어도 해제).
**When to use:** 패널 대상 폼 전부(SC 3). 견적 줄에는 쓰지 않는다.
**Example:** 아래 「Code Examples」.

### Pattern 3: 이행용 「쇠퇴 목록」 래칫
**What:** stylelint는 `stylelint.legacy.mjs`, eslint는 `ignores` 배열(`eslint/restrictions.mjs`의 `LEGACY_TABLE_FILES`)로 「아직 위반이 허용된 파일」을 명시한다. 단위 테스트가 (a) 목록의 모든 파일이 실재하고 (b) **목록에 있으면서 위반이 없는 파일이 없고**(래칫 — 옮긴 파일을 목록에서 안 지우면 실패) (c) 페이즈 끝에 길이 0이어야 통과시킨다. (b)는 stylelint API로 해당 파일을 legacy override 없이 돌려 확인한다.
**글롭 함정(실측):** `(app)`·`[id]` 같은 경로가 micromatch 글롭에서 리터럴이 아니다 — `app/(app)/projects/**`라고 쓰면 **조용히 매칭되지 않아**(규칙이 계속 켜져 있음) 웨이브 ①에서 예상 밖 lint 폭발이 난다. 해결: 경로를 `p.replace(/[()[\]]/g, "[$&]")`로 이스케이프(`app/[(]app[)]/projects/[[]id[]]/…`) [VERIFIED: 스크래치 실행 — 이스케이프 시 `projects.module.css:0 · [id]/project-detail.module.css:0`, 미이스케이프 시 6·8건 그대로]. eslint `ignores`는 `app/(app)/…` 리터럴이 그대로 동작한다 [VERIFIED: 스크래치 실행 — `app/(app)/admin/vendors/page.tsx` 무시됨].

### Anti-Patterns to Avoid
- **`--bar` 같은 옛 이름을 정규식 치환으로 지우기:** `--bar-fg`·`--bar-muted`·`--bar-leaf`·`--bar-h`를 깨뜨린다. `--line`은 `--line-w`·`--line-ui`·`--line-strong`, `--surface`는 `--surface-*`, `--radius`는 `--radius-*`, `--shadow`는 `--shadow-*`와 접두가 겹친다. 치환은 `var\(--name(?![\w-])` 형태(뒤에 `[\w-]` 불가)로만, 그리고 이름→이름 매핑 표를 테스트로 고정(`--fs-sm`→`--text-aux` 같은 의미 변환은 기계 치환 금지).
- **`:modal` 없이 「`[inert]` 안 요소 제외」만 구현:** 네이티브 `showModal()`의 뒤쪽 비활성은 `[inert]` 속성이 아니다. 원칙 점검의 보임 판정은 `el.closest("[inert]") || (modal && !modal.contains(el))`로 써야 한다(아래 §design-principles).
- **모듈 CSS에서 원시 토큰 직접 사용:** 현재도 `var(--g-100/--g-50/--g-700/--g-950)` 11곳(5파일: `Table`·`TopBar`·`PermissionGrid`·`project-detail`·`reserves`)이 있다 — 2단 계약 위반이므로 전용 금지 규칙으로 막는다.

## Common Pitfalls

### Pitfall 1: 「옛 이름 삭제」가 런타임 테스트를 조용히 깨뜨림
**What goes wrong:** `getComputedStyle(...).getPropertyValue("--fg")`는 미정의 토큰에 빈 문자열을 돌려주고, 비교 대상도 빈 값이 되어 **어긋난 채 통과하거나** `toBe` 실패로 터진다.
**How to avoid:** 웨이브 ① tokens.css에서는 옛 이름을 **유지**(역할 이름을 더하기만), 옛 이름 삭제는 웨이브 ④ 마지막 커밋에서 테스트 이관과 함께. 삭제 전 `rg -n "var\(--(bg|surface|fg|muted|faint|line|line-ui|line-strong|line-w-strong|radius|shadow|modal-w|bar|fs-[\w]+|danger|warning|success|scrim|row-min)(?![\w-])" app ui test docs/design/SYSTEM.md`가 0건이어야 한다. UI-SPEC의 삭제 목록에는 `--fs-*`·`--danger/--warning/--success`·`--row-min`·`--scrim`·`--touch-min`이 없다 — `--fs-*`→`--text-*`, `--danger…`→`--status-*`, `--scrim`→`--scrim-dialog/panel`, `--row-min`→`--row-h` 대응을 플래너가 삭제 표에 명시해야 한다(UI-SPEC 공백).
**Warning signs:** e2e에서 `rgb(…)` 기대 문자열이 빈 값으로 비교됨.

### Pitfall 2: 공유 DB 때문에 목록 사진이 비결정적
**What goes wrong:** `desktop` 프로젝트는 스펙 파일을 워커 여러 개로 병렬 실행하고 모두 같은 `erp_test`를 쓴다(`tests.md`). `/projects`·`/admin/vendors`·`/approvals` 사진에 다른 스펙이 방금 만든 행(`e2e-…` 무작위 이름)이 섞인다. `mobile-*.spec.ts`는 `mobile-375` 프로젝트에서 **desktop이 모두 끝난 뒤** 돌아 DB가 더 오염돼 있다.
**Why it happens:** DB는 `globalSetup`(`resetTestSchema`)이 **실행 시작 때 한 번** 비운다 [VERIFIED: `test/e2e/global-setup.ts` `DROP SCHEMA … public CASCADE`].
**How to avoid:** 전용 Playwright 프로젝트(`visual`)를 만들어 `workers: 1`, **`desktop`·`mobile-375`가 `dependencies: ["visual"]`로 그 뒤에 돌게** 한다(= 시각 스펙이 시드만 있는 깨끗한 DB에서 먼저 실행). 스펙이 만드는 행은 고정 이름 픽스처로. 기준 사진 파일명이 `mobile-*.spec.ts` 패턴에 걸리지 않게 **UI-SPEC의 `mobile-visual.spec.ts` 이름은 피한다**(`playwright.config.ts:45 const MOBILE_SPEC_PATTERN = "mobile-*.spec.ts";`가 잡아 `mobile-375`로 가 버림) — 예: `visual-390.spec.ts`. 대가: `visual`이 빨가면 나머지가 「did not run」(기존 mobile·settings 직렬화와 같은 성격). 완화: 시각 스펙은 별도 잡이 아니라 같은 e2e 잡에 두되 flake 여지를 줄이려 `retries`는 쓰지 않고 마스크로 해결.
**Warning signs:** 같은 커밋 재실행에서 행 수가 다른 diff.

### Pitfall 3: 로컬에서 만든 기준 사진이 CI에서 전부 실패
**What goes wrong:** 사진 이름에 `-linux`만 붙어 플랫폼이 같아 보이지만 브라우저 빌드가 다르다. **이 세션 Chromium = 141.0.7390.37**(`/opt/pw-browsers/chromium --version`), **CI가 설치하는 Playwright 1.63 번들 = 153.0.8010.12**(`playwright-core/browsers.json` `chromium rev=1243 ver=153.0.8010.12`) [VERIFIED: 두 명령 실행 결과]. 글리프 래스터·서브픽셀이 다르다.
**How to avoid:** 기준 사진은 **CI e2e 잡에서 만들어** 받는다(아래 「CI 워크플로 PR」). 로컬은 스펙 실행·마스크·타이밍 검증용으로만.

### Pitfall 4: CI가 실패 사진을 아무것도 올리지 않음
**What goes wrong:** CI 리포터가 `[["github"],["dot"]]`라 `playwright-report/`(HTML)가 생기지 않는데, 실패 업로드 스텝은 그 경로만 올린다 [VERIFIED: `playwright.config.ts:53` `reporter: process.env.CI ? [["github"], ["dot"]] : "list"` · `ci.yml:152-157` `path: playwright-report/`]. 전후 diff PNG는 `test-results/` 아래에 있다.
**How to avoid:** 워크플로 PR에서 같은 스텝의 `path:`를 `playwright-report/` + `test-results/` 두 줄로(아티팩트 이름 `playwright-report-${{ matrix.shard }}`는 `ci-guard.test.ts:168`이 단언하므로 유지).

### Pitfall 5: `design-principles.ts`의 CSS 모듈 클래스명 셀렉터가 컴포넌트 이관 뒤 공허해짐
**What goes wrong:** 스냅샷이 `[class*="PageHeader-module__"][class*="__subtitle"]`와 `[class*="Button-module__"][class*="__primary"]`로 부제·1차 버튼을 센다 [VERIFIED: `design-principles.spec.ts:25`·`:40`]. `PageHeader`가 `ListScreen`/`DetailScreen`으로 흡수되면 부제 셀렉터가 **아무것도 못 찾아 경고 0건으로 통과**한다(막는 모드가 공허해짐).
**How to avoid:** `data-ui="screen-subtitle"`·`data-ui="primary-button"` 같은 안정 훅을 컴포넌트가 달고 스펙은 그것을 읽게 바꾼다. 카나리 E2E 하나: `/admin/vendors`에서 `primaryButtons === 1`, `/projects/[id]`에서 `subtitle !== null`을 단언(셀렉터가 죽으면 즉시 실패).

### Pitfall 6: 패널 폼이 「연속 등록」 동작을 바꿈
**What goes wrong:** 현재 등록 폼 다수가 성공 시 `formRef.current?.reset()`만 하고 **열린 채 유지**(연속 입력): `card-form.tsx:44`, `code-item-form.tsx:35`, `org-client.tsx:150·153`, `roles-client.tsx:110`, `vendor-form.tsx`(create: reset + 중복 N건 안내 유지). UI-SPEC은 「성공 → 패널 닫힘」이다. 거래처는 성공 뒤 「같은 이름 N건」(`duplicateCount`) 안내가 패널과 함께 사라질 자리가 없다.
**How to avoid:** 폼별 성공 표시 위치를 플랜에서 명시(토스트/결과 줄). 사용자에게 「연속 등록 유지 여부」가 UQ 밖의 새 결정인지 확인 요청 → Open Question O-2. 관련 E2E가 연속 등록에 기대는지 확인 필요.

### Pitfall 7: 링크가 전체 새로고침이라 스크롤이 튐
**What goes wrong:** 지금 패널 진입 링크 일부가 `next/link`가 아니라 `<a href>`다: `holidays/page.tsx:92·101`(`<a className={styles.addLink} href="…&new=1">`), `ListEmpty.tsx:38`(`<a href={action.href}>`), `vendors/page.tsx`의 필터 토글 `<a href="?includeHidden=…">`. 전체 새로고침이면 스크롤이 맨 위로 가고 포커스가 사라진다. 그리고 해시(`…#vendor-form`·`#org-unit-form`·`#team-form`·`#role-form`)가 Next의 해시 스크롤을 일으킨다 [CITED: `link.md` 687–702행 「Scrolling to an id」].
**How to avoid:** 패널을 여는 모든 링크는 `next/link` + `scroll={false}`, 해시 제거. `RowAction`/`EmptyState`/`ListScreen.primaryAction`이 이 규칙을 컴포넌트 안에 고정(호출부가 고르지 못하게).

### Pitfall 8: 네이티브 `showModal()`의 첫 포커스는 「첫 입력」이 아니다
**What goes wrong:** `dialog.showModal()`은 DOM 순서상 첫 포커스 가능 요소(머리의 닫기 x)에 포커스한다. UI-SPEC은 「열리면 첫 입력」.
**How to avoid:** 마운트 효과에서 `dialog.querySelector("input,select,textarea")?.focus()`(`ConfirmDialog`가 이미 같은 방식 — `evidenceRef…querySelector(...).focus()`). 닫기 x는 `tabIndex`를 건드리지 말고 DOM 순서만 머리 뒤에 둬도 된다.

### Pitfall 9: `display: flex`가 닫힌 `<dialog>`를 보이게 함
**What goes wrong:** 작성자 CSS `display:flex`가 UA의 `dialog:not([open]){display:none}`을 이긴다. **How to avoid:** `ConfirmDialog.module.css`처럼 `.panel[open]{display:flex}` 로만 선언. 그리고 UA 기본(`margin:auto; max-width/max-height`)을 `margin:0; inset:0 0 0 auto; max-width:100vw; max-height:none; height:100dvh`로 해제.

### Pitfall 10: 기존 E2E가 옛 폼 배치를 단언
**What goes wrong:** `single-column.spec.ts:124–153`은 `#org-unit-form`·`#role-form` 등이 「720px 이하, `main h1`과 같은 x」라고 단언 — 패널 폼(480, 오른쪽 끝)은 위반. `admin-master-list-first.spec.ts`는 「등록」 **링크**가 스크롤 없이 보이고 누르면 폼이 열린다고 단언(링크 역할 유지되면 통과, 폼 위치 단언은 패널로). `people.spec.ts:181–189`는 머리글 아래 2px, `page-chrome.spec.ts:36·157·166·186`은 본문 14·제목 18/700·부제 12·404 제목 32px, `notify-inbox.spec.ts:362–372`는 그룹 머리글 위 12px·아래 1px, `mobile-people.spec.ts:112–119`는 접힌 줄 선 두께, `admin-people-detail-link.spec.ts:45`는 12px.
**How to avoid:** 웨이브마다 「기대 깨짐 목록」(D-39 URL 토글을 만지는 스펙 23개 — `admin-master-list-first`·`admin-nav`·`code-tables(-write-gate)`·`corp-cards`·`design-principles`·`holidays`·`master-edit`·`mobile-320-no-overflow`·`mobile-admin-master-list-first`·`mobile-code-tables`·`mobile-holidays`·`mobile-projects-error`·`number-format`·`org`·`project-copy`·`project-lifecycle`·`project-register`·`projects-list`·`revenue-section`·`roles`·`single-column`·`vendor-edit`·`vendors`)을 그 웨이브의 플랜에 선언하고 `CI=true`로 해당 스펙만 재실행. 폼 `id`(`vendor-form`·`org-unit-form`·`role-form`)는 패널에서도 유지해 셀렉터 변경을 줄인다.

### Pitfall 11: 패널 안에서 「입력 버리기」 확인(중첩 모달)
`project-form.tsx`는 `ConfirmDialog`(「입력 버리기」)를 폼 안에서 연다(`:408`). 네이티브 모달은 스택되며 Esc는 맨 위 것만 닫는다 — 패널의 `cancel` 핸들러가 dirty일 때는 `preventDefault` 후 확인 모달을 열어야 한다(`SidePanel`에 `onRequestClose` 훅 제공). 가림막 클릭은 UI-SPEC 기본값대로 「바뀐 칸 없을 때만」.

### Pitfall 12: 원칙 점검에 `/dev/components`를 넣으면 구조적으로 실패
모음 페이지는 1차 버튼을 여러 개 **일부러** 보여 준다(버튼 3위계 × 상태) → 「주 버튼 하나」 위반이 본질. 원칙 점검 대상에서는 제외하고(`a11y`·`visual`·대비에는 포함) 제외 사실을 스펙 주석에 기록한다. UI-SPEC은 「원칙의 대상에 넣는다」고 적었으나 이 충돌을 놓친 것으로 보인다 → Open Question O-3(사용자 결정 아님, 플래너가 정리).

### Pitfall 13: 기준 CSS의 `row-reverse` 재현 금지
행동 줄 DOM·Tab·시각 순서가 같아야 한다(UI-SPEC). `flex-direction: row-reverse`·`order`로 시각만 뒤집으면 axe가 아닌 DOM 감사에서 걸린다 — 오른쪽 정렬은 `justify-content: flex-end`로.

### Pitfall 14: 코드 블록 `--bar` 포커스 예외(04.2)
`TopBar.module.css`는 전역 `:focus-visible`(`--focus`=g-700)이 딥그린 바(g-900) 위에서 안 보여 `.markLink`·`.navLink`·`.userTrigger`를 `outline: var(--focus-w) solid var(--bar-fg)`로 덮는다(49–51·79–81·153–155행). 역할 이름으로 옮길 때 이 예외를 **전용 역할 토큰**(`--focus-on-bar` → `--bar-fg`)으로 명시해 유지하고, 하단 탭·사용자 메뉴 항목(바 밖 흰 면, `--focus`)과 구분한다. 「`--bar` 삭제」가 `--bar-fg`까지 지우지 않도록(위 Anti-Pattern).
