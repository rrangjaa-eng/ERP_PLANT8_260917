## Summary

06.1은 05(지출결의 · `files` 업로드 경로)와 06(지급 · 증빙 확인 · 카드 사용 · 구매 요청) **위에** 「주인 없는 증빙 → 공개 → 고르기 → 대사」 층을 얹는다. 실측 결과 **05-04 `files`·`upload_intents`, 06의 `corp_card_usages`·`purchase_requests`·`expense_evidence_reviews`는 아직 어느 브랜치에도 코드가 없다** — 05 브랜치에는 05-01·02·03·14만 SUMMARY가 있고 `db/schema/expenses.ts`까지만 섰다 `[VERIFIED: git ls-tree origin/claude/phase-05-execute-pxok9w]`. 그래서 이 리서치는 05·06 **계획 문서**의 이름(`lockExpenseForUpdate`, `countActiveByOwner`, `expenseCostBasis`, `evidenceGateInputs`, `splitCardTotal`, `cards.proxy` 등)을 기준으로 연결점을 적었고, 플랜마다 「선행 의존 재확인(⓪)」이 필요하다.

**엑셀 라이브러리가 저장소에 하나도 없다** `[VERIFIED: package.json]`. 견본 다섯이 전부 OLE2/BIFF8 .xls라 **xlsx 전용 라이브러리(exceljs · read-excel-file)로는 못 읽는다** — 사실상 SheetJS뿐이다. npm 레지스트리의 `xlsx`는 0.18.5(2022-03-24)에서 멈췄고 알려진 취약점(CVE-2024-22363 ReDoS, 0.20.2 미만)이 있다. 공식 배포는 `cdn.sheetjs.com` tarball인데 **이 세션 환경에서는 그 도메인이 막혀 있다**(403). npm의 `@e965/xlsx@0.20.3`(SheetJS 0.20.3 재배포)는 이 환경에서 설치되고 **견본 다섯을 Node에서 실제로 읽었다**(머리줄 위치 · 줄 수 실측, 아래 표). 새 의존성은 사용자 승인이 필요하다 — 플랜 맨 앞에 승인 확인 지점을 둔다.

데이터 모델은 **`files`를 넓히지 말고 새 표 두 개(증빙 기록 + 붙임 이력)와 등록 묶음 표 하나**를 권한다. `files`는 「저장소에 바이트가 있는 첨부」(`object_key` · `sha256` NOT NULL)이고, 엑셀 한 줄 증빙에는 바이트가 없다 — 억지로 넓히면 NOT NULL 셋을 풀어야 하고 05·06의 「살아 있는 파일」 판정 전부가 흔들린다. 행 범위(D-6108)는 **기존 `Scope` 유니온을 넓히지 말고** 같은 파일(`scope-for.ts`)에 증빙 전용 판정을 더한다 — 기존 리포지토리 9곳이 `rows === "none"`만 보고 나머지를 전부 「all」로 읽기 때문에, 유니온에 셋째 값을 넣으면 **타입 검사를 통과한 채 조용히 전 행이 열린다**(Pitfall 3).

**Primary recommendation:** 서버 액션 한 번 = 파일 하나(1MB 상한 안)로 서버가 SheetJS 배열 모드로 읽고 → 서식 규칙(순수 함수) → 전부-아니면-전무 검증 → `dedupe_key` UNIQUE로 `ON CONFLICT DO NOTHING` 등록 → 같은 화면 목록에서 키보드로 공개/붙이기. 원본 파일은 **저장하지 않는다**(비씨·롯데 원본에 카드 전체 번호, 비씨에 결제 계좌번호가 평문으로 있다).

### 서식 공통 규칙 (실측 + 서식 명세 기반)

1. **형식은 바이트로 판별**: `D0 CF 11 E0 A1 B1 1A E1` = CFB(BIFF8) · `50 4B 03 04` = xlsx · 앞 1KB에 `<html`/`<table` = HTML 표 → **거절**(짐작 읽기 금지) `[CITED: 807 명세 §0, 37-44행]`. 견본 다섯 전부 CFB `[VERIFIED: magic d0cf11e0a1b11ae1]`.
2. **배열 모드만**: `header: 1` — 홈택스 `상호` 중복, 객체 키 오염 회피 `[CITED: old-samples.md:57]`.
3. **문자열 숫자 정규화**: 비씨는 모든 칸이 공백 패딩 문자열, 롯데 금액은 쉼표 문자열, 신한·홈택스는 숫자 — 서식 규칙이 칸마다 `trim` + 쉼표 제거 후 정수 원으로.
4. **날짜는 한국 날짜 문자열 그대로**(`YYYY-MM-DD`로 정규화) — `Date`로 바꾸지 않는다(시간대 하루 밀림 방지, `lib/dates.ts` `seoulToday` 관례).
5. **카드 번호는 뒤 4자리만 남기고 나머지는 버린다** — 원본 파일도 저장하지 않는다(Security).
6. **취소**: 신한 = 음수 / 롯데 = `취소일자` 채움 또는 음수 / 비씨 = 표기 미확인 → 음수이거나 `금액SIGN코드`가 공백이 아니면 「확인 필요」 표시 `[CITED: 807 명세 §8 ②]` / 홈택스 = `합계금액 < 0`(분류 `수정세금계산서`), 원거래 연결은 `비고` 글월 안 `당초 승인번호 (…)` 뿐 `[CITED: 807 명세 §4 「취소·수정」]`.
7. **홈택스 검산**: 3줄 총계와 읽은 줄 합이 다르면 파일 거절(추론 — 전부-아니면-전무의 무결성 검사로 쓰기 좋다). 대표 품목 칸(26~33)은 금액으로 쓰지 않는다 `[CITED: 807 명세 §4 「가장 큰 함정」]`.

### Pattern 1: 데이터 모델 — `files`를 넓히지 않고 새 표 셋 (D-6107)

**왜 새 표인가(추론, 근거 실측):** 05-04 `files`는 `object_key` NOT NULL UNIQUE · `sha256` NOT NULL CHECK 64자 · `size_bytes > 0` · `owner_id` NOT NULL `[CITED: 05-04-PLAN.md:175]` — 「저장소에 바이트가 있는 첨부」다. 엑셀 한 줄 증빙은 바이트가 없고 승인번호 · 금액 · 사업자번호 · 카드가 본체다. `files`를 넓히면 NOT NULL 넷을 풀어야 하고, 05·06이 쓰는 「살아 있는 행 = `removed_at IS NULL AND voided_at IS NULL`」 판정과 `checkEvidenceUpload` 중복 검사 · 고아 청소(06-11)가 바이트 없는 행을 만나게 된다. D-6107의 「기존 증빙 행 이관」도 새 표면 필요 없다(이관할 행이 0 — 06.1 이전에는 이런 증빙이 없다).

### Pattern 2: 서식 규칙 = 순수 함수 하나 (D-6103)

**What:** `detect(sheets) → { format, sheetIndex, headerRow } | refused` 와 서식마다 `read(sheet, ctx) → { rows, errors, checksum }`. 서식 목록은 배열 하나에 등록 — 새 카드사 = 파일 하나 + 등록 한 줄. 현금영수증 · 계산서 규칙은 견본이 올 때까지 **등록하지 않는다**(판별이 「아는 서식 아님」으로 거절 = fail closed).

```typescript
// 판별 낱말은 견본 실측값이다 — 07 서식 표의 값과 같아야 한다.
// [VERIFIED: 견본 머리글 — 신한 "이용일시"·"이용카드" / 비씨 "수신정보구분코드"·"금액SIGN코드" /
//  롯데 "청구예정일"·"하위가맹점명" / 홈택스 시트 "세금계산서"·"품목", A="작성일자" B="승인번호", 띠 "매입 전자(수정) 세금계산서 목록조회"]
type FormatKey = "card-shinhan" | "card-bc" | "card-lotte" | "hometax-tax-invoice"; // 계산서·현금영수증은 견본 뒤에 더한다
```

### Pattern 3: 전부-아니면-전무 + 중복 건너뛰기 (:83 · Discretion)

- **검증은 트랜잭션 밖에서 먼저**(줄 번호 · 까닭을 다 모으려고) → 오류 0이면 한 트랜잭션에서 INSERT. 옛 구현도 같은 순서 `[CITED: 907 receipts.ts:3880-3960 주석 「먼저 전 줄을 잰다 · 트랜잭션 밖」]`. 오류 문구는 앞 5줄 + 「외 n줄」 `[CITED: 907 bulkBlockedWhy :3916]` — 문구는 이 저장소 명사형 규약으로 다시 쓴다.
- **「형식 오류」 = 파일 거절**: 모르는 서식 · 필수 칸 없음 · 날짜/금액 못 읽은 줄 · 홈택스 총계 불일치 · 줄 수 상한 초과.
- **「이미 등록」 = 건너뜀(오류 아님)**: `INSERT … ON CONFLICT (dedupe_key) DO NOTHING RETURNING id` — 동시 두 업로드도 DB가 가른다.
- **dedupe 키 — 승인번호만으로는 안 된다**(실측): 신한 · 롯데 견본 모두 **취소가 원거래와 같은 승인번호**를 쓴다(같은 번호 2줄 1쌍씩) `[VERIFIED: probe2 dupApprovalKeys 1 · negativeRows 1]`, 카드 승인번호는 8자리라 카드사 · 기간을 넘어 겹칠 수 있다(추론). 권장 키:
  - 홈택스: `hometax|{승인번호 26자}`(파일 안 전부 유일 `[VERIFIED: probe3 uniqueApproval = rows]`)
  - 카드: `{format}|{끝4}|{승인번호}|{사용일}|{부호 있는 합계}` · 승인번호가 비거나 `00000000`이면 `{format}|{끝4}|{이용일시(시각 포함)}|{가맹점}|{부호 있는 합계}`(서식 명세 ⑧-③과 같은 결 `[CITED: 807 명세 §8 ③]`)
  - 현금영수증: 견본 뒤 확정 `[ASSUMED]`
- 「이미 등록 n건」 + 파일 sha256이 기존 묶음과 같으면 「같은 파일」로 결과에 표시(추론 — 겹치는 기간 재업로드가 잦을 것이라는 CONTEXT 추정과 맞음).
- **완전 상쇄 쌍**(원거래 + 같은 값 취소): 옛 기본은 등록에서 제외 `[CITED: old-samples.md:65 markOffsetPairs]`. 06.1 권장: 등록하되 `canceled` 표시 + 공개 · 고르기 · 대사 후보에서 뺀다(감사 흔적 유지). 부분 취소(+4,000 / −18 꼴)는 둘 다 일반 증빙 `[CITED: 907 receiptImport.ts:455-462 주석]`. — 플래너 판단(A7).

### Pattern 4: 행 범위 — `Scope`를 넓히지 말고 증빙 전용 판정을 같은 파일에 (D-6108)

**현재 계약** `[VERIFIED: domain/permissions/scope-for.ts:11]`:
```typescript
export type Scope = { rows: "all" | "none"; includeArchived: boolean };
```
엔티티 → 메뉴 표 `ENTITY_MENUS`(`code_items`·`org_unit`·`team`·`user`·`corp_card`·`vendor`·`holiday`·`project`·`quote_line`) `[VERIFIED: scope-for.ts:20-33]`.

**왜 넓히면 안 되나(실측):** 기존 리포지토리 9곳 이상이 `if (opts.scope.rows === "none") return [];` 한 줄만 보고 나머지를 전 행으로 처리한다 `[VERIFIED: repositories/users.ts:41 · projects.ts:243,307 · org-units.ts:11 · vendors.ts:14,33 · corp-cards.ts:14 · code-tables.ts:17 · teams.ts:11]`, `domain/reserves/index.ts:302,678,719`는 `rows === "all"`로 분기한다. `rows`에 `"team"`을 넣으면 타입 검사가 통과한 채 **전 행 노출**이 된다.

**권장:** `scope-for.ts`에 증빙 전용 함수를 하나 더한다(같은 파일 = 판정 단일 지점 유지, 기존 `scopeFor` 계약 불변).
```typescript
// 제안 — 새 함수 이름 · 메뉴 키는 사용자 승인 대상.
export type EvidenceScope =
  | { rows: "all" }                                               // 등록 권한자(경영관리)
  | { rows: "published"; teamId: string | null; orgUnitId: string | null } // 공개된 것만, 오늘 소속 기준
  | { rows: "none" };
```
- 리포지토리는 `switch (scope.rows)`에 `never` 검사로 세 갈래를 다 다룬다(빠진 갈래 = 타입 오류).
- 소속은 오늘(서울) 발령 기준 — `findMembershipAtDate` `[VERIFIED: repositories/team-memberships.ts:11]` · `teams.org_unit_id` `[VERIFIED: db/schema/org.ts:28-30]`. 발령 이력이 없으면 team null → 팀 공개 · 본부 공개 모두 안 보임(임의 기본 팀으로 떨어지지 않는 관례 `[VERIFIED: domain/projects/status.ts:83-85]`).
- **붙은 증빙은 풀(pool)에서 빠진다** — 풀 목록은 「공개 + 살아 있는 붙임 없음」. 붙은 뒤에는 **문서의 행 판정**(`canSeeExpense` 등)으로만 보인다.
- 누수 스캔: 새 DTO는 `registerDto`로 등록하면 DTO × 계급 케이스가 자동 생성된다 `[VERIFIED: domain/permissions/dto-registry.ts:1-6]` — `test/integration/leak-scan.test.ts` 맨 위 import 목록에 `import "@/domain/evidence-records";`를 더한다(05-04가 같은 방식 `[CITED: 05-04-PLAN.md:189]`). **누수 스캔은 정보 항목(칸) 축만 본다 — 행 축은 새 통합 테스트가 필요하다**(아래 Validation).

### Pattern 6: 카드 대사 (:83 · :67)

```
카드 줄(서식이 카드사를 정함, 끝4, 승인번호, 사용일, 부호 있는 합계)
 ├─ 카드 찾기: corp_cards(issuer, number_last4) — UNIQUE(issuer, last4) [VERIFIED: db/schema/corp-cards.ts:31]
 │     ⚠ issuer는 자유 입력 칸 [VERIFIED: app/(app)/admin/corp-cards/card-form.tsx:71-77 TextField "발급사"]
 │       → 끝4로 후보를 찾고 서식별 별칭(신한/비씨·BC/롯데)이 issuer 문자열에 들어 있나로 가른다.
 │         0건 또는 2건 이상 = 「카드 미등록」 표시(줄은 등록, 대사 안 함)
 ├─ 1단계: 승인번호 같은 카드 사용 건(카드 사용에 승인번호 칸을 더해야 함 — 06-05 표에 없다)
 ├─ 2단계: 같은 카드 · 사용일 같음 · 합계 같음 · 아직 증빙 없음 → 정확히 1건이면 자동 연결
 │         (2건 이상이면 3단계로 — 자동으로 고르지 않는다)
 └─ 3단계: 사람이 고름 — 공개된 카드 줄을 작성자가 풀에서 골라 자기 카드 사용에 붙인다(= 2차 붙이기)
           · 경영관리는 짝 없는 줄 목록에서 대리 등록(06-09 `cards.proxy` 경로, 카드·날짜·합계·가맹점 미리 채움) → 그 건에 연결
```
- **「파일이 이긴다」(:67)**: 3단계로 사람이 고른 카드 사용의 `corp_card_id`가 파일의 카드와 다르면 파일 카드로 바꾸고 전·후를 남긴다. 연결 시 카드 사용에 승인번호를 적어 다음 재업로드 때 1단계로 잡힌다.
- **합계가 다를 때(3단계에서만 생김)**: 증빙 금액은 파일 값(D-6106). 카드 사용의 `total`까지 파일 값으로 덮을지는 열린 질문(Open Q3) — 권장: 덮고 전·후를 끌 수 없는 기록으로 남긴다(한 거래에 숫자 하나).
- 롯데 날짜 칸은 `매입일자`(가맹점 매입 접수일)라 실제 사용일과 하루 이상 다를 수 있다 `[ASSUMED]` — 2단계는 정확 일치만 자동, ±n일은 3단계 후보로만 보인다(추론).
- 점수 정렬(고르기 화면): 옛 가중치 종류 4 · 사업자번호 2 · 금액 1 `[VERIFIED: 907 app/src/domain/receiptMatch.ts:60]` — 사업자번호는 숫자만 비교, 빈 값끼리는 같다고 세지 않음. 이 저장소에서 다시 쓴다(복사 금지).

### Pattern 7: 거래처 자동 생성 (:81)

- 대상: **서식이 정한다**(추론 권장) — 홈택스 세금계산서 · 계산서 · 현금영수증 서식만. 카드 서식은 가맹점 사업자번호가 있어도(비씨 · 롯데) 만들지 않는다(옛 구현도 카드 전표에는 안 켰다 `[CITED: old-samples.md:70]`). 증빙 종류 코드표에 새 속성(`creates_vendor`)을 더하는 길도 있으나 새 이름 · 새 칸이라 사용자 승인이 필요하다.
- 열쇠: 사업자번호 **숫자 10자리**. 현재 `vendors.business_no`는 입력 그대로의 text이고 UNIQUE · 정규화 칸이 없다 `[VERIFIED: db/schema/vendors.ts:15]` · 거래처 폼이 자유 입력 `[VERIFIED: app/(app)/admin/vendors/vendor-form.tsx:209]` → 하이픈 있는 값과 없는 값이 섞일 수 있다. 조회는 `regexp_replace(business_no, '\D', '', 'g') = $digits`(또는 생성 칸 + 인덱스 — 스키마 변경, 위험 경로).
- 경합: 같은 사업자번호를 두 업로드가 동시에 만들 수 있다 → `pg_advisory_xact_lock(hashtextextended('vendor_business_no:' || digits, 0))` — 저장소 선례 `[VERIFIED: repositories/settings.ts:189 pg_advisory_xact_lock(hashtextextended(${"approval_route_step:" + step}, 0))]`. UNIQUE 인덱스는 기존 데이터에 중복이 있으면 마이그레이션이 실패하므로 권하지 않는다(추론).
- 보관됨 → 되살림: 보관함 복원은 `domain/archive` `restore`가 정본 `[VERIFIED: domain/archive/index.ts:100-123]` — 트랜잭션 안에서 부를 수 있게 `tx`를 받는 리포지토리 함수가 필요할 수 있다(⓪ 확인). 숨김(`hidden`)과 보관(`archived_at`)은 다르다 — 숨김 거래처는 그대로 쓴다(추론).
- 이름 다름: 「알림만」 = **등록 결과 줄에 표시**(옛 구현도 응답의 `nameDiffers`로 화면에 보였다 `[CITED: 907 receipts.ts:3205-3260]`). 알림함(NOTI) 알림은 만들지 않는다(추론 — Phase 7 소관 · 사용자 확인 A11).
- 권한: 경영관리가 `admin.vendors` write가 없어도 등록의 부수 효과로 거래처가 생긴다(옛 구현 동일). 행동 로그 `document_create` entity `vendor`. → `/cso` 점검 항목.

### Pattern 8: 금액 (D-6106)

| 서식 | 공급가 | 세액 | 합계 |
|---|---|---|---|
| 홈택스 세금계산서 | 파일 `공급가액` | 파일 `세액` | 파일 `합계금액` |
| 홈택스 계산서 | 파일(견본 뒤 확정) | 0 `[ASSUMED]` | 파일 |
| 비씨 · 롯데 | `diffKrw(합계, 파일 부가세)` | 파일 `부가세`(`0` = 면세, 덮어쓰지 않음 `[CITED: 807 명세 §2 ㉡]`) | 파일 |
| 신한(세액 칸 없음) | `grossFromTotal(합계, tax.vat.rate, 단위, 방식)` (D-6106 문구 그대로) | `diffKrw(합계, 공급가)` | 파일 |

- `grossFromTotal(totalKrw, vatRate, unit, method)` `[VERIFIED: domain/money/index.ts:202-205]` · `round()`는 `Math.round` 사용 `[VERIFIED: domain/money/index.ts:35-49]` → **음수 합계에 그대로 부르면 원거래와 정확히 반대가 안 될 수 있다**(JS `Math.round(-2.5) = -2`). 취소 줄은 `−grossFromTotal(|합계|)`로 셈한다(Pitfall 6).
- **D-6106 vs 비씨 · 롯데**: D-6106은 「카드 금액은 합계로 읽고 공급가는 `grossFromTotal()`」이라고 적었지만 같은 결정의 첫 문장은 「파일에서 읽은 공급가·세액·합계가 증빙 금액」이다. 비씨 견본에 세액 `0`(상품권 · 면세) 줄이 4개 있다 `[VERIFIED: xlrd 비씨 2~5줄 부가세 "0"]` — `grossFromTotal`을 쓰면 없는 세금이 생긴다. **권장: 세액 칸이 있는 서식은 파일 세액, 없는 서식(신한)만 `grossFromTotal`** — 사용자 확인(Open Q2).
- 시드의 카드 전표 세금 규칙은 `ruleKind: "none"`이다 `[VERIFIED: domain/seed/index.ts:90 { value: "card_receipt", label: "카드 전표", … taxRule: { ruleKind: "none" } }]` — 06-05 `splitCardTotal`은 `none`이면 공급가 = 합계 `[CITED: 06-05-PLAN.md:230]`. 신한 줄에 D-6106(역산)과 06-05(규칙 따름) 중 무엇을 쓸지 같은 Open Q2에서 묻는다.
- 금액 고침(경영관리): 증빙 행 version 낙관적 잠금 + 전·후 기록. **`document_update`는 설정으로 끌 수 있다**(`ALWAYS_ON_ACTION_TYPES`에 없음) `[VERIFIED: domain/action-log/record.ts:85-100]` → 「전·후 값이 남는다」를 보장하려면 끌 수 없는 기록이 필요하다(Pitfall 8).
- 결재 중 문서에 붙은 증빙의 금액은 고치지 못하게 막는다(:79 재계산 금지와 같은 결 — 추론).

### Anti-Patterns to Avoid
- **브라우저에서 읽은 줄을 서버가 그대로 믿기** — 금액 · 카드가 조작 가능. 서버가 다시 읽는다.
- **원본 엑셀 저장** — 비씨 · 롯데에 카드 전체 번호, 비씨에 결제 계좌번호 평문(Security).
- **승인번호 하나로 중복 판정** — 취소가 원거래로 뭉개진다(Pattern 3).
- **`Scope.rows` 유니온 확장** — 기존 리포지토리가 전 행을 연다(Pattern 4).
- **증빙 종류 라벨 문자열로 분기** — 라벨은 관리자가 바꾼다. 코드값(`tax_invoice` 등)이나 서식 키로 분기.
- **카드 issuer 정확 일치** — 자유 입력이라 「신한카드」/「신한」/「기업은행(BC)」이 섞인다.

## Common Pitfalls

### Pitfall 1: 취소 줄이 원거래로 뭉개짐
**What goes wrong:** 승인번호만 열쇠로 쓰면 두 번째 줄(취소)이 「이미 등록」으로 버려져 비용이 취소 전 금액으로 남는다.
**Why:** 신한 · 롯데 견본 모두 같은 승인번호 2줄 1쌍(원거래 + 취소/부분 취소) `[VERIFIED: probe2]`.
**How to avoid:** dedupe 키에 부호 있는 합계 · 날짜 · 끝4를 넣는다(Pattern 3).
**Warning signs:** 단위 테스트 「같은 승인번호 + 음수 금액 → 둘 다 등록」이 없으면 잡히지 않는다.

### Pitfall 2: 비씨 `합계` 줄 · `00000000` 승인번호
**What goes wrong:** 합계 줄이 증빙 한 건으로 등록되거나, `00000000`끼리 다른 거래가 한 키로 뭉친다.
**Why:** 비씨 끝 줄 첫 칸 `합      계` · 승인번호 빈칸 · 휴대폰 안내 400원 줄의 승인번호 `00000000` `[VERIFIED: probe2 blankApproval 1 · zeroApproval 1]`.
**How to avoid:** 첫 칸 공백 제거 = `합계` 또는 승인번호 빈 줄은 요약으로 건너뜀(비씨만) · `isRealApproval`처럼 1~9 숫자가 하나라도 있어야 승인번호로 인정 `[CITED: 907 receiptImport.ts:332]`.

### Pitfall 3: 행 범위 유니온 확장이 전 행을 연다
Pattern 4 참조. **Warning signs:** `Scope` 타입 diff에 새 값이 보이면 멈춘다.

### Pitfall 4: 서버 액션 본문 1MB 상한
**What goes wrong:** 여러 파일을 한 요청에 담으면 1MB를 넘어 실패.
**Why:** Server Action 기본 본문 상한 1MB(multipart 머리 포함) `[CITED: node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/serverActions.md 「bodySizeLimit」]` · `next.config.ts`에 `serverActions` 설정 없음 `[VERIFIED: next.config.ts]`.
**How to avoid:** **파일 하나 = 액션 한 번**(파일 단위 전부-아니면-전무와도 맞는다). 실측 크기: 견본 23~51KB, 홈택스 6개월치 417,792B `[CITED: old-samples.md:40]` — 1MB 안. 상한을 올리지 않는다(올리면 `next.config.ts` 변경 · 보안 검토).

### Pitfall 5: 카드 issuer 자유 입력
Pattern 6 참조. 특히 비씨 카드는 은행이 발급(견본 `결제계좌은행명` = 기업은행 계열)이라 관리자가 issuer에 은행 이름을 적었을 수 있다 `[ASSUMED]` — 사용자 확인(A4).

### Pitfall 6: 음수 반올림 비대칭
`Math.round`는 .5에서 +∞ 쪽으로 간다 → `grossFromTotal(-x)` ≠ `-grossFromTotal(x)`일 수 있다. 취소는 절댓값으로 셈하고 부호를 붙인다. 단위 테스트: 원거래 + 완전 취소의 공급가 합 = 0.

### Pitfall 7: 05-09 결재 중 규칙과 :79의 충돌
**What goes wrong:** 05-09는 「결재 중 기안자가 증빙을 더하고 마지막 아닌 파일을 지울 수 있다」 `[CITED: 05-09-PLAN.md:52]`인데, 06.1이 이어받은 :79는 「결재 중에는 아무도 못 뗀다 · 붙이기는 경영관리만」이다.
**How to avoid:** 06.1 범위(등록된 증빙 붙임)에는 :79를 적용하고, 파일(05-09) 규칙을 바꿀지는 **사용자에게 묻는다**(Open Q1). 조용히 05-09 동작을 바꾸지 않는다.

### Pitfall 8: 「전·후 값이 남는다」·「뗀 기록」이 행동 로그 설정에 기대면 사라진다
`document_update`는 관리자가 끌 수 있다 `[VERIFIED: domain/action-log/record.ts:85-100 — ALWAYS_ON 목록에 없음]`. 뗀 기록은 붙임 이력 행이 보존한다(Pattern 1). 금액 고침 전·후는 ⒜ 증빙 행 옆 이력 칸/표 또는 ⒝ 끌 수 없는 새 행동 종류(새 이름 — `cert_correct` 선례 `[VERIFIED: record.ts:39-40,96-97]`) 중 하나 — 사용자 결정(새 이름).

### Pitfall 9: 「증빙 있음」 판정이 여러 곳에 흩어짐
Pattern 1의 `hasEvidence` 참조. 06의 게이트 다섯 곳 중 하나만 고치면 「목록 한 줄로 증빙 완료」(D-6104·6105)가 일부 경로에서만 통한다.

### Pitfall 10: 계산서(면세) 목록 견본도 없다
현금영수증만 대기라고 적혀 있지만, 세금계산서 목록에는 면세 계산서가 없다(실측) — **계산서 읽기도 견본이 필요하다**. 확인 지점을 계산서 · 현금영수증 둘 앞에 둔다.

### Pitfall 11: 폭이 넓은 표 · 320px
경영관리 목록은 열이 많다(날짜 · 서식 · 거래처/가맹점 · 금액 셋 · 공개 · 붙은 문서 · 카드). 320px 가로 넘침 E2E가 이미 있다(`test/e2e/mobile-320-no-overflow.spec.ts` — frontend.md 언급) — 새 화면도 그 스펙에 넣는다.

## Code Examples

### 바이트 판별 (순수)
```typescript
// 머리 8바이트 — 견본 다섯 전부 d0cf11e0a1b11ae1 [VERIFIED: 이 세션 실측]
// xlsx 50 4b 03 04 · HTML 판별 규칙 [CITED: 807 들여오기-서식-명세.md §0]
export type Sniff = "cfb" | "xlsx" | "html" | "unknown";
export function sniff(bytes: Uint8Array): Sniff {
  const cfb = [0xd0, 0xcf, 0x11, 0xe0, 0xa1, 0xb1, 0x1a, 0xe1];
  if (cfb.every((b, i) => bytes[i] === b)) return "cfb";
  if (bytes[0] === 0x50 && bytes[1] === 0x4b && bytes[2] === 0x03 && bytes[3] === 0x04) return "xlsx";
  const head = new TextDecoder("utf-8", { fatal: false }).decode(bytes.subarray(0, 1024)).toLowerCase();
  if (head.trimStart().startsWith("<") || head.includes("<html") || head.includes("<table")) return "html";
  return "unknown";
}
```

### SheetJS 읽기 (서버, 배열 모드)
```typescript
// 옵션은 이 세션에서 견본 다섯을 읽은 그대로 [VERIFIED: probe.mjs]
import * as XLSX from "xlsx"; // 안 B면 "@e965/xlsx" — 승인 뒤 확정
export type Cell = string | number | boolean | null;
export function readSheets(bytes: Uint8Array): { name: string; rows: Cell[][] }[] {
  const wb = XLSX.read(bytes, { type: "array", dense: true, cellFormula: false, cellHTML: false });
  return wb.SheetNames.map((name) => ({
    name,
    rows: XLSX.utils.sheet_to_json<Cell[]>(wb.Sheets[name], { header: 1, raw: true, defval: null, blankrows: true }),
  }));
}
```

## Open Questions

1. **결재 중 증빙 규칙 충돌(:79 vs 05-09)**
   - What we know: 05-09는 결재 중 기안자의 파일 추가 · 마지막 아닌 삭제를 연다 `[CITED: 05-09-PLAN.md:52]`. 06.1 CONTEXT는 :79(아무도 못 뗌, 붙이기는 경영관리만)를 「이미 확정」으로 적었다.
   - What's unclear: :79가 파일(05)까지 덮는지, 등록된 증빙 붙임에만 적용되는지.
   - Recommendation: 06.1은 등록 증빙 붙임에 :79 적용. 05-09 파일 규칙 변경 여부는 사용자 카드로 묻는다(05가 이미 만들어졌으면 되돌리는 값이 크다).
2. **카드 공급가 계산(D-6106 vs 파일 세액 · 06-05 규칙)**
   - Recommendation: 세액 칸 있는 비씨 · 롯데는 파일 세액(면세 `0` 유지), 신한만 `grossFromTotal`. 신한에 카드 전표 규칙 `none`(공급가 = 합계)을 따를지 D-6106 문구대로 역산할지 사용자 확인.
3. **3단계 대사에서 합계가 다를 때 카드 사용 금액을 파일로 덮나**
   - Recommendation: 덮고 전·후를 끌 수 없는 기록으로(「파일이 이긴다」의 연장). 덮지 않으면 한 거래에 숫자 둘(사용 건 합계 · 증빙 합계)이 남아 Phase 9 effectiveCost가 고를 것이 늘어난다.
4. **증빙 금액이 비용이 되는 자리(06-06 A-608 칸 vs 붙은 증빙 합)**
   - What we know: 06-06은 「Phase 5 증빙 금액 칸」을 전제하는데 05 계획에 그 칸이 없다.
   - Recommendation: 06이 그 칸을 만든 뒤, 06.1은 「붙은 증빙 기록이 있으면 그 공급가 합이 증빙 금액(작성자 입력 칸은 읽기 전용)」 규칙을 `expenseCostBasis`에 더한다. 06이 칸을 안 만들었으면 06.1 ⓪에서 멈춘다.
5. **새 이름 승인 묶음**(CLAUDE.md 260907 잣대 ㉠ — 사용자 몫): 표 이름 셋, 메뉴 키 둘(`evidence` · `evidence.intake`), 정보 항목 둘, 상태 낱말 여섯, (선택) 끌 수 없는 행동 종류 하나, SheetJS 의존성. 한 카드에 묶어 묻는다.
6. **시드: `evidence` view를 기획 PM · 팀장에게 켤지**(회사 규칙 — 사용자 몫). 안 켜면 관리자가 권한표에서 켜기 전까지 2차 붙이기가 아무에게도 안 보인다.
