가장 큰 구조 사실 세 가지. ① `scopeFor`의 `Scope` 타입(`{rows:"all"|"none", includeArchived}`)은 프로젝트·견적뿐 아니라 사람·팀·본부·거래처·법인카드·코드표 리포지토리 9곳이 읽고(`.rows === "none"`), 도메인 곳곳이 `{ rows: "all", includeArchived: … }` 리터럴을 직접 만들어 넘긴다 — **타입을 넓히면 안 되고**(06.1-01 계획도 같은 이유로 `Scope` 불변을 못 박았다) 프로젝트·견적 줄용 서술자를 별도 타입으로 둔다. ② 프로젝트 행을 읽는 **원시 읽기 프리미티브(`repositories/projects.ts:findProjectById` 등)는 범위를 모르며 도메인이 20곳 넘게 직접 부른다** — 이 입구들(쓰기 포함)이 compare.md §3 표에서 빠져 있다. 「목록·상세만 거르는」 접근은 구멍이 남는다. ③ 지출결의 보임은 이미 **하나의 SQL 조건**(`repositories/expenses.ts:517-526 scopeCondition`)을 목록·합계·문서 하나가 같이 쓴다 — CONTEXT가 말한 「TS 모양과 SQL 모양 둘」이 아니라 한 모양이라 일관성 걱정은 줄지만, `ExpenseScope.company/teamIds` 필드를 읽는 `domain/payments/targets.ts:122-123`이 같이 바뀌어야 한다.

**Primary recommendation:** 위험 경로 PR(스키마·이행·SEED_ROLES·`scopeFor` 서술자·`projects.member` 키·역할 도메인 함수)을 먼저 사용자 머지로 세우고, 그 위에서 `repositories/row-scope.ts`의 **필수 인자(projectId 열) 번역기 하나**로 모든 입구를 배선한다. 입구 누락은 손으로 쓴 목록이 아니라 **리포지토리 소스를 스캔해 발견하는 구조 테스트**(260907이 `project:` 칸을 조용히 빠뜨린 구멍의 재발 방지)로 잡는다. 기존 테스트 중 PM·팀장 계급으로 타 팀 프로젝트를 읽는 것들(통합 79개 파일 중 27개가 프로젝트 읽기 함수 호출, E2E 48개가 `/projects` 접촉)은 별도 테스트 이행 태스크가 필요하다.

### Pattern 1: 서술자 타입 (제안 — 추정, 이름·모양은 플래너 재량)
**What:** `scopeFor`를 오버로드해 `"project"|"quote_line"`일 때만 서술자를, 나머지 엔티티는 기존 `Scope`를 돌려준다. `Scope`는 한 글자도 안 바꾼다(06.1-01이 `scope-for.ts`에 별도 `EvidenceScope`를 더하고 `Scope` 불변을 전제로 한다 — 같은 파일 병합 충돌 최소화).
```typescript
// domain/permissions/scope-for.ts (제안)
export const ROLE_VIEW_SCOPES = ["company", "org_unit", "team", "own"] as const; // D-6201
export type RoleViewScope = (typeof ROLE_VIEW_SCOPES)[number];

export type ProjectRowScope =
  | { rows: "none" }
  | { rows: "all"; includeArchived: boolean }
  | {
      rows: "limited";
      includeArchived: boolean;
      viewerId: string;
      by: { kind: "team"; teamId: string | null } | { kind: "org_unit"; orgUnitId: string | null } | { kind: "own" };
    };
```
**When to use:** 프로젝트·견적 줄 계열 입구 전부. `deps.can`·`deps.findRole`·`deps.findMembershipAtDate`·`deps.findTeamById` 주입 꼴은 기존 `scopeFor`/`loadActorTeamScope` 선례를 따른다(`N: domain/permissions/scope-for.ts:34-41`, `N: domain/projects/status.ts:69-84`).
**fail-closed:** 계급 없음 → `{rows:"none"}`; view_scope가 알려진 4값이 아님 → none(260907 `default: return '(false)'` `O: server/src/scope.ts:106-109`와 같은 태도); 팀/본부 null → `limited`이되 `by`의 id가 null이면 번역기가 「내 것 + 참여」만 남긴다(D-6207).
**주의:** `by`는 기본 구성요소만 담고 PM·참여 OR 조각은 번역기가 **항상** 더한다 — 호출부가 빠뜨릴 수 없게.

### Pattern 2: 번역기의 필수 인자 (260907 구멍 봉쇄)
```typescript
// repositories/row-scope.ts (제안 — 추정)
import { and, or, eq, exists, sql, type SQL, type AnyColumn } from "drizzle-orm";
import { projectMembers } from "@/db/schema";
import type { ProjectRowScope } from "@/domain/permissions/scope-for";

export type ProjectColumns = { projectId: AnyColumn | SQL; teamId: AnyColumn | SQL; pmUserId: AnyColumn | SQL };
// 260907은 ScopeColumns.project가 선택(O: server/src/scope.ts:35-41)이라 호출부가 안 주면 참여자 조각이 조용히 빠졌다.
// 여기서는 세 열이 모두 필수 — 타입 검사가 누락을 잡는다.
export function projectScopeCondition(scope: ProjectRowScope, cols: ProjectColumns): SQL {
  switch (scope.rows) {
    case "none": return sql`false`;
    case "all": return sql`true`;
    case "limited": {
      const mine = eq(cols.pmUserId as AnyColumn, scope.viewerId);
      const asMember = exists(/* select 1 from project_members pm where pm.project_id = cols.projectId and pm.user_id = viewerId and pm.archived_at is null */);
      const base = /* team: teamId = :teamId | org_unit: teamId IN (select id from teams where org_unit_id = :orgUnitId) | own: undefined */;
      return or(mine, asMember, base) ?? sql`false`;
    }
    default: { const unreachable: never = scope; void unreachable; return sql`false`; }
  }
}
```
위치 근거: `eslint.config.mjs:48`에서 `repositories`는 `["repositories","db","domain"]`을 import할 수 있어 `import type { ProjectRowScope } from "@/domain/permissions/scope-for"`가 합법이다(`repositories/projects.ts:6`이 이미 `Scope` 타입을 같은 방식으로 import) [VERIFIED: eslint.config.mjs:47-48, repositories/projects.ts:6]. `domain → db`는 허용 목록에 없다(`{ from: "domain", allow: ["domain","repositories","lib"] }` `eslint.config.mjs:47`) — domain은 SQL 조각을 만들 수 없다는 CONTEXT 가정이 맞다.

### Pattern 3: 단일 관문 `findVisibleProject`
읽기·쓰기 모두 `findProjectById`(원시)를 직접 부르는 도메인 호출이 많다(§Q4 M-표). 서술자를 넘겨 받는 `findProjectInScope(viewer, scope, id)` 리포지토리 함수 하나와 도메인 래퍼 `findVisibleProject(viewer, id)`를 두고, **원시 `findProjectById`는 이름을 바꿔(`findProjectByIdUnscoped`) 허용 목록 테스트로 호출부를 고정**한다(Q6). 잠금 안 호출(`lockProjectForWrite`)은 이미 「트랜잭션 전 가시성 판정 → 트랜잭션 안 잠금」 순서라 가시성 판정을 트랜잭션 앞에 두는 현재 구조를 유지한다(`N: domain/projects/ledger.ts:154-170`).

### Anti-Patterns to Avoid
- **`Scope.rows` 유니온에 셋째 값 추가:** 리포지토리 9곳(`repositories/{users,teams,org-units,vendors,corp-cards,code-tables}.ts`, `projects.ts:243,307`)이 `none`만 보고 나머지를 전 행으로 읽는다 [VERIFIED: grep `rows === "none"`].
- **화면·도메인에서 행을 걸러 범위를 대신:** 06.1-05도 같은 금지를 둔다. 서버 where에서만.
- **참여자 조각을 선택 인자로:** 260907 구멍(`O: server/src/scope.ts:36-41`; 호출 누락 `O: server/src/card-uses.ts:637`은 `creator: 'p.id'`만 주고 `project:`가 없다).
- **문자열 SQL 보간:** 260907의 `idOrNull` 보간(`O: server/src/scope.ts:44-48`)은 Drizzle에서 불필요하고 위험하다.

## Common Pitfalls

### Pitfall 1: 범위가 「입구」가 아니라 「프리미티브」에 있다
**What goes wrong:** 목록·상세만 거르면 `getCurrentQuoteRevision`·`listQuoteLines(revisionId)`·`lineCardSideFacts`·`prepareQuoteLineSave`·구매 요청의 `loadQuoteLineBasis`가 프로젝트 가시성을 묻지 않아 revision/line id만 알면 열린다(상세 페이지는 `findProject`가 404여도 서버 액션은 별도로 호출 가능 — `app/(app)/projects/actions.ts`의 `listRevisionLinesAction`·`saveProjectLedgerAction` 등).
**Why:** `domain/quotes/lines.ts`에는 `scopeFor` 호출이 0건이다(compare.md §3 #4의 「`scopeFor`=메뉴」는 틀림) [VERIFIED: grep]. 그 파일의 읽기는 호출 페이지가 `findProject`를 먼저 통과했다는 전제에 기대고 있다 [VERIFIED: app/(app)/projects/[id]/page.tsx:57-58 이후 호출].
**How to avoid:** §Q6 구조 테스트 + 읽기·쓰기 모두 `findVisibleProject`/서술자 필터 경유.
**Warning signs:** `repoFindProjectById`/`findProjectById`/`findQuoteRevisionById`/`findQuoteLineById`가 가시성 판정 없이 DTO를 돌려주는 도메인 함수.

### Pitfall 2: 기존 테스트가 PM·팀장으로 타 팀 프로젝트를 읽는다
**What goes wrong:** D-6203으로 PM·팀장이 `team` 범위가 되면, 다른 팀 프로젝트를 읽던 통합·E2E가 조용히 0행/404로 바뀐다. `createFixtureUser({ roleId, withTeam })`은 사용자마다 **새 본부·새 팀**을 만든다(`N: test/e2e/fixtures.ts:36-54`) — 서로 다른 픽스처 사용자는 서로 다른 팀이다.
**How to avoid:** 계획에 「테스트 이행」 태스크를 둔다: 뷰어를 담당 PM으로 만들거나(D-6205 ①로 보임) 시스템 관리자(company)로 바꾸거나 같은 팀에 발령. 규모(실측 grep): 통합 `role-pm|role-team-lead` 사용 79파일 중 프로젝트 읽기 함수도 부르는 파일 27개, E2E `/projects` 접촉 48스펙, `createFixtureUser({ roleId: "role-pm"…})` 69곳. 첫 PR(위험 경로) 직후 전체 통합을 한 번 돌려 붉은 목록을 얻는다(CI가 한 번 돈다 — CLAUDE.md §5).
**Warning signs:** `test/integration/projects-list.test.ts:107 ALL_SCOPE = { rows:"all", includeArchived:false }` 리터럴이 새 타입에 안 맞음(컴파일 오류로 즉시 드러남), `test/unit/domain/project-list-view.test.ts:155,530`의 `scope: () => Promise.resolve({rows:"all",…})` 스텁.

### Pitfall 3: `expenses.team` 두 번째 열쇠와 view_scope의 충돌
**What goes wrong:** 현재 팀 갈래는 `expenses` 보기 ∧ `expenses.team` 보기를 요구하고(`N: domain/expenses/access.ts:33,40`), 시드는 팀장에게만 `expenses.team`을 준다(`N: domain/seed/expenses.ts` ⑤). D-6203으로 PM도 `team`이 되는데 `expenses.team`이 없으면 팀 문서가 안 보인다 — D-6202(「보기 판정은 오직 view_scope」)와 모순. 통합 테스트가 이 동작을 직접 고정한다(`N: test/integration/expense-visibility.test.ts:126,150,187`).
**How to avoid:** Open Question 1에서 결정 후 반영. 권장은 §Open Questions 1.

### Pitfall 4: 이행과 시드가 서로 다른 값을 낸다
`seedRole`은 `onConflictDoNothing`(`N: repositories/roles.ts` seedRole)이라 **기존 DB의 시드 계급은 시드가 못 고치고 이행만 고친다**. 반대로 통합 테스트는 매 테스트 전 모든 표를 TRUNCATE한 뒤 `seedMasterData`로 계급을 다시 넣는다(`N: test/integration/setup.ts:27-37`) — 즉 **테스트의 view_scope는 오직 `SEED_ROLES`에서 온다**. 둘을 같은 상수에서 맞추는 단위 테스트가 필요하다(0013 주석 「새 DB(시드)와 기존 DB(마이그레이션)가 같은 값」을 계승, `N: domain/permissions/roles.ts:30`).

### Pitfall 5: 공유 enum으로 연차 결재선에 `project_team`이 새어 들어감
`APPROVAL_ROUTE_SCOPE_VALUES`(`N: domain/settings/keys.ts:518`)는 연차 4단·지출결의 4단 **여덟 개** 키가 같은 `z.enum`으로 쓴다 [VERIFIED: keys.ts:562,…,684,855,897,939,…]. 이 상수에 값을 더하면 연차 설정 화면 select에도 「행사 담당 팀」이 뜨고 저장된다. 별도 상수로 나눈다(§Q8).

### Pitfall 6: 참여자 후보에서 sysadmin 판정을 직책 코드 문자열로
260907은 `pe.position_code <> 'sys_admin'`(`O: server/src/projects.ts:3917-3918` 인근). 우리는 `users.roleId !== SYSADMIN_ROLE_ID`(`N: domain/permissions/roles.ts:38` `SYSADMIN_ROLE_ID = "role-sysadmin"`). 계급 이름·id 조건 분기 금지 규약(`domain/viewer.ts` 주석, `no-admin-boolean.test.ts`)은 「관리자 불리언」에 대한 것이고 계급 id 상수 비교는 선례가 있다(`domain/seed`, `SYSTEM_VIEWER`) — 단 후보 제외 목적이므로 권한 판정이 아님을 주석으로 남긴다(추정).

### Pitfall 7: 마이그레이션 문장 안의 `SET LOCAL` 타임아웃
이행 SQL 첫머리에 `SET LOCAL lock_timeout = '1s'; SET LOCAL statement_timeout = '5s';`를 둔다(0013·0025·0027 공통 선례) [VERIFIED: 0013_role_work_scope.sql, 0027_vendor_kind.sql].

### 번역기 단위 테스트 (DB 없이)
`PgDialect().sqlToQuery(cond)`로 SQL 문자열·파라미터를 단언 — 선례 없음(grep 0건)이라 새 패턴. 대안은 통합 테스트(실제 Postgres)이며 CLAUDE 규칙상 둘 다 허용. 번역기는 분기가 4갈래뿐이라 **통합 매트릭스가 주 증거**이고 단위는 보조(fail-closed `default`) 정도로 충분하다.

### Q1. 스키마·이행
- **roles.view_scope:** 위 §Code Examples SQL. 같은 변경에서 `SEED_ROLES`(`N: domain/permissions/roles.ts:30-36`)에 `viewScope`를 더하고 `seedRole`(`N: repositories/roles.ts`)이 그 칸을 넣게 한다. `insertRole` 기본값은 DB 기본 `'team'`.

- **drizzle-kit 규약:** `drizzle.config.ts`는 `casing: "snake_case"`, schema `./db/schema/*.ts`, out `./db/migrations` [VERIFIED: drizzle.config.ts]. 새 스키마 파일은 `db/schema/index.ts` 배럴에 export 한 줄을 더해야 통합 테스트 TRUNCATE(`test/integration/setup.ts:15-18`)와 `drizzle-kit`이 본다.
- **저널 가드:** `test/unit/db/migration-journal.test.ts` (a)~(f) 불변식(idx 연속, tag 접두, when 증가, sql·스냅숏 쌍, 고아 스냅숏 없음) [VERIFIED: 파일 읽음, 이번 세션 통과]. 06.1-01도 같은 저널·스냅숏을 건드리므로 **나중에 머지되는 쪽이 자기 마이그레이션·스냅숏을 지우고 재생성**(`.claude/rules/db.md`, CONTEXT 순서 항).
- **생성된 마이그레이션에 손으로 쓴 데이터 UPDATE가 허용되나:** 선례 다수 — 0013(`UPDATE roles …`), 0027(`UPDATE vendors … EXISTS`), 그 밖 0003·0009·0011·0012·0019·0023·0029에 `UPDATE/INSERT` [VERIFIED: grep].
