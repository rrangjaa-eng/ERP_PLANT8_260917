## Q2. 겹침 조회·잠금·트랜잭션·순서 (D-6307, D-6310, D-6311)

**SQL 모양(Drizzle)** — `repositories/leave-usage.ts:33-36`의 join을 그대로 따른다:
```ts
// repositories/leave-usage.ts (LIVE 상태 상수는 이 파일의 PENDING_STATUSES 옆에)
export async function listLiveLeaveInRange(viewer: Viewer, input: { drafterId: string; fiscalYear: number; startDate: string;
  endDate: string; documentKind: string; excludeId?: string }, tx?: DbOrTx): Promise<LiveLeaveRow[]> {
  void viewer;
  return (tx ?? db).select({ id: leaveRequests.id, kind: leaveRequests.kind, half: leaveRequests.half,
      startDate: leaveRequests.startDate, endDate: leaveRequests.endDate })
    .from(leaveRequests)
    .innerJoin(approvalInstances, and(eq(approvalInstances.documentKind, input.documentKind), eq(approvalInstances.documentId, leaveRequests.id)))
    .where(and(eq(leaveRequests.drafterId, input.drafterId), eq(leaveRequests.fiscalYear, input.fiscalYear),
      lte(leaveRequests.startDate, input.endDate), gte(leaveRequests.endDate, input.startDate),
      inArray(approvalInstances.status, ["submitted", "in_review", "approved"]),
      input.excludeId ? ne(leaveRequests.id, input.excludeId) : undefined))
```

**잠금 헬퍼 위치**: `repositories/leave-requests.ts`(쓰기 계열) — 선례 모양 그대로 [VERIFIED: repositories/settings.ts:189]:
`await tx.execute(sql\`select pg_advisory_xact_lock(hashtextextended(${"approval_route_step:" + step}, 0))\`);` → `lockLeaveDrafter(viewer, drafterId, tx)`는 `"leave:" + drafterId`. 같은 모양이 `login-attempts.ts:65`에도 있다. 잠금 대기는 `withTransaction`이 먼저 건 `SET LOCAL lock_timeout = '5s'`(lib/db-transaction.ts:46)에 걸려 55P03 → UserFacing `다른 저장이 끝나지 않음 · 잠시 뒤 다시 저장`(db-transaction.ts:16,22).

**tx 노출**: `withTransaction(fn: (tx: DbOrTx) => ...)`가 `db.transaction`의 tx를 그대로 넘긴다(db-transaction.ts:41-50). 제출은 `withTransaction(async (tx) => { insertLeaveRequest(..., tx) ...})`(index.ts:329-342), 다시 신청은 `resubmitDocument(viewer, prepared, {...}, tx)` 뒤 `updateLeaveRequestFields(..., tx)`(resubmit.ts:36-54). `DbOrTx = Pick<typeof db, "insert"|"update"|"select"|"delete"|"execute">`(db/client.ts:57)라 select·execute 둘 다 된다.

**READ COMMITTED에서 잠금 뒤 조회가 맞는 이유**: 잠금이 별도 문장이고 그 다음 문장이 새 스냅숏을 잡으며, 앞선 제출은 신청 행과 `approval_instances`를 같은 tx에서 커밋하므로(index.ts:330-344) 뒤 제출은 둘을 함께 본다.

**제출 tx 순서**: `lockLeaveDrafter` → `listLiveLeaveInRange({drafterId: viewer.id, fiscalYear: days.fiscalYear, ...})` → `findLeaveOverlap` → 있으면 `throw new LeaveValidationError([{field:"startDate", message}])` → `insertLeaveRequest` … (기존). `LeaveValidationError`는 `withTimeoutConversion`이 그대로 재던지고(isTxTimeoutError 거짓) drizzle이 롤백한다. 액션이 `instanceof LeaveValidationError`로 `{rejected:{errors}}` 변환(actions.ts:35-37).

**다시 신청 tx 순서 — 추천: 잠금(`leave.drafterId`) → `resubmitDocument` → 겹침(자기 제외) → `updateLeaveRequestFields`.**

- `repositories/`·`domain/leave/`·`app/(app)/leave/`·`test/`만 건드린다. `db/`·`domain/permissions/`·`domain/approvals/` 수정 없음(결재 상태는 읽기만).

## Architecture Patterns

```
입력(폼/액션) ─▶ assertLeaveWrite ─▶ loadLeaveHolidays(startDate, range)   [tx 밖; 범위 밖 해/표 밖 해 → 빈 집합]
                     │                         │
                     ▼                         ▼
        countLeaveQuarters(input, range, holidays)  ── 실패 ─▶ LeaveValidationError(칸 오류)
                     │ ok
        (제출) prepareSubmission ─▶ withTransaction(tx):
                     │   lockLeaveDrafter(tx) ─▶ [다시 신청이면 resubmitDocument(tx)]
                     │   ─▶ listLiveLeaveInRange(tx, 자기 제외) ─▶ findLeaveOverlap(순수, holidays)
                     │        겹침 ─▶ throw LeaveValidationError(startDate) ─▶ 롤백 ─▶ {rejected:{errors}}
                     │   ─▶ insertLeaveRequest / updateLeaveRequestFields ─▶ …(기존)
        (미리보기) 같은 holidays ─▶ previewLeaveBalance(deps.holidays) + listLiveLeaveInRange(잠금 없음) ─▶ {offDays, overlap, …}
```
권장 파일: `domain/leave/days.ts`(+인자·`NO_HOLIDAYS`·`LEAVE_KIND_WORDS`), `domain/leave/overlap.ts`(순수), `domain/leave/guard.ts`(서버: 로더·`assertNoLeaveOverlap`·`previewLeaveOverlap`), `repositories/leave-usage.ts`(+조회), `repositories/leave-requests.ts`(+잠금).

### Anti-Patterns
- 겹침 조회에 전역 `db` 사용(풀 교착). 기간 구간(start~end)만으로 비교(주말·휴일에서만 접해도 막힘, D-6308 위반). `half`만 보고 예외 판정(반반차 오전+오후가 통과). `days.ts`에 `loadHolidayLookup`·DB 모듈 import(클라이언트 번들 깨짐). 사전 판정 없이 범위 밖 해마다 달력 잠금 트랜잭션 개설.

## Don't Hand-Roll
| 문제 | 만들지 말 것 | 쓸 것 |
|---|---|---|
| 영업일 판정 | 주말+집합 직접 검사 | `isBusinessDay(date, lookup)` (business-day.ts:55) |
| 휴일 표 조회·후보 생성 | 직접 SELECT | `loadHolidayLookup([year])` (calendar.ts:20) |
| 기안자 직렬화 | 재시도 루프·유일 제약 | `pg_advisory_xact_lock(hashtextextended(…,0))` (settings.ts:189 선례) |
| 날짜 형식 검증 | 새 정규식 | `days.ts` 기존 `parseDate`/형식 오류 경로 |
| 겹침 오류 전달 | 새 오류 타입·새 액션 반환형 | `LeaveValidationError` + `rejected.errors`(index.ts:61-65, actions.ts:27-29) |

## Common Pitfalls
1. **풀 교착**: 겹침 조회를 `db`로 하면 `withTransaction` 연결을 잡은 채 풀에서 연결을 더 빌려 풀 5·동시 6건에서 대기(`approvals-concurrency.test.ts` 「풀 5에서 6건(CEO-2)」). 모든 tx 안 읽기는 `tx`. 휴일 조회는 tx 앞.
2. **다시 신청 자기 겹침**: 전이 먼저 순서에서 `excludeId` 누락 → 항상 거절. 회귀 테스트: 같은 날짜로 다시 신청 성공.
3. **범위 검사 순서**: 9999년 입력은 휴일 조회보다 `연도 범위 밖` 오류가 먼저(leave-permission.test.ts:81-96). 로더가 범위 밖이면 빈 집합을 주고 `countLeaveQuarters`가 범위 오류를 낸다.
4. **미리보기 이중 조회**: 액션이 `previewLeaveBalance`에 `deps.holidays`를 넘기지 않으면 휴일 읽기가 두 배.
5. **TRUNCATE로 휴일 표도 비워짐**(setup.ts) — 통합 테스트 첫 제출이 후보 생성 잠금 트랜잭션을 한 번 탄다(기능상 무해, 시간만 약간).
6. **저장값 소급 금지**: 이미 저장된 행의 `days_quarters`를 다시 세는 코드를 넣지 않는다(D-6305). 겹침 판정에만 현재 표로 전개.
7. **단위 테스트 목**: `actions.ts`에 새 DB 모듈 import → 두 단위 테스트 import 실패. 목 추가.
