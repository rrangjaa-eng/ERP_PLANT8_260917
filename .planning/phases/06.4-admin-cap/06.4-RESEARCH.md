## Summary

**마이그레이션도 새 패키지도 없다.** 변경은 (1) 순수 비교 모듈 `grant-ceiling.ts`(계급 권한 집합의 부분집합 + 범위 순위) (2) 권한 집합·재직 관리자 수·점유 팀 조회·advisory 잠금 리포지토리 함수 (3) 쓰기 진입점 7곳을 **트랜잭션으로 감싸 잠금 → 재조회 → 판정 → 쓰기 → 로그** 순서로 바꾸는 배선 (4) `DOMAIN_RESTORERS.user`(+ 범용 `archive()`의 `user` 분기) (5) 화면 셋(계급 select 걸러내기·비활성, 조직 화면 중복 태그, 복원 거부 토스트)이다. 판정 코드의 99%는 `domain/`·`repositories/` 4계층 안이고 DB·화면은 얇다.

**가장 큰 발견 다섯.**
1. **현재 쓰기 진입점은 거의 다 트랜잭션이 아니다.** `registerPerson`·`changePersonRole`·`archivePerson`·`assignTeam`·`setPermissionCell` 모두 전역 `db`로 한 문장씩 쓰고 `recordAction`은 따로 부른다(`domain/people/index.ts:330-333`, `domain/org/index.ts:261-265`, `matrix.ts:114-127`, `repositories/users.ts:57-76`가 `tx` 인자 없음). 락을 쓰려면 리포지토리 함수 4개에 `tx` 인자를 더하고 도메인 함수를 `withTransaction`으로 감싸야 한다 — D-6408의 숨은 비용.
2. **D-6404의 「최신 발령(미래 포함)」 정의는 `cancelFutureAssignment`로 구멍이 난다**(미래 발령을 취소하면 사람이 이전 팀으로 되돌아가 보유자가 늘어난다)이고, 미래 발령이 도래하는 시점에도 쓰기가 없어 중복이 생길 수 있다. 「오늘 기준 팀 ∪ 모든 미래 발령 팀」을 **점유 팀 집합**으로 정의하면 시간 경과·취소에 닫힌다(권장, O1).
3. **계급 보관은 관리자 수를 줄이지 못한다.** `findPermission`도 `getSession`도 `roles.archived_at`을 보지 않아(`repositories/permissions.ts:12-31`, `lib/viewer.ts:34-67`) 보관된 계급의 사람은 권한을 그대로 갖는다. D-6403/성공 기준 2의 「계급 보관」 항목은 정의를 `can()` 실동작과 맞추면 공허해진다(O2).
4. **기존 테스트 일부가 마지막 관리자 가드에 걸린다**: `archived-session.test.ts:25-45`는 시스템 관리자 계급 사람 하나를 만들고 `archive(SYSTEM_VIEWER,"user",…)`로 보관한다 — 유일한 관리자다. **SYSTEM_VIEWER를 마지막 관리자 가드에서도 면제**해야 이 테스트(및 E2E `archived-session.spec.ts:25-30`)가 안 깨진다.
5. **design-E 시나리오 「`admin.people`만 켠 경영관리 → PM 지정 통과」는 그대로는 실패한다.** 새 계급은 권한 행이 0이고 PM은 `projects` 등 여러 칸을 가진다 → PM ⊄ 경영관리. 통합 테스트 픽스처는 위임받는 계급에 PM 칸을 **모두 포함**시켜야 한다(Pitfall 5).

**Primary recommendation:** 리스크 PR(A) = `grant-ceiling.ts` + 리포지토리 읽기·잠금 + `matrix.ts` 마지막 관리자 + 그 테스트, 일반 PR(B) = people·org·archive 배선 + 화면. 모든 쓰기 진입점은 `withTransaction` 안에서 **person → admin → team → division** 순서로 advisory 잠금을 잡고(같은 계층 안 키는 정렬), 잠금 뒤에 권한 집합·점유·관리자 수를 다시 읽어 판정한다. 점유 팀 집합 정의와 SYSTEM_VIEWER 면제 범위는 아침 확인 항목으로 올린다.

### Pattern 1: 잠금 → 재조회 → 판정 → 쓰기 → 로그 (한 트랜잭션)
**What:** 모든 쓰기가 같은 순서. 판정에 쓰는 읽기는 **잠금 뒤에** `tx`로 한다(READ COMMITTED에서 잠금을 얻은 뒤의 SELECT는 앞 트랜잭션이 커밋한 행을 본다). **When:** register·changeRole·archive·assignTeam·cancelFuture·resignation·setPermissionCell·restore.
**Example (선례: 06.3 기안자 잠금):**
```typescript
// Source: N: repositories/leave-requests.ts:40-43 (읽음) — 같은 모양으로 키만 다르게
export async function lockLeaveDrafter(viewer: Viewer, drafterId: string, tx: DbOrTx): Promise<void> {
  void viewer;
  await tx.execute(sql`select pg_advisory_xact_lock(hashtextextended(${"leave:" + drafterId}, 0))`);
}
// 새 함수: lockSeatKeys(viewer, keys: string[], tx) — keys를 호출 쪽이 계층 순서로 정렬해 넘기고 한 개씩 순서대로 잠근다.
// 키 문자열: "seat:person:" + userId · "seat:admin:last" · "seat:team:" + teamId · "seat:division:" + orgUnitId
```
`withTransaction`은 콜백 전에 `SET LOCAL lock_timeout = '5s'`를 내고 잠금 시간 초과를 `다른 저장이 끝나지 않음 · 잠시 뒤 다시 저장` UserFacingError로 바꾼다 [VERIFIED: N: lib/db-transaction.ts:12,16,41-46 — `SET LOCAL lock_timeout = '5s'`].

- 부분집합: `[...setR].every((k) => setActor.has(k))` (R, C 둘 다). 행위자가 `admin.permissions` 쓰기(`m:admin.permissions::write`)를 가지면 통과. 키에는 커스텀 칸 노출 `cf.<대상>.<키>`도 자연히 들어간다(노출표가 같은 표) [VERIFIED: N: repositories/permissions.ts:230-257 `customFieldInfoItem` + `visibilityMatrix` 한 표].
- 범위 순위(D-6401 기본값): `view_scope`는 `ROLE_VIEW_SCOPES = ["company", "org_unit", "team", "own"]`(앞이 넓음), `work_scope`는 `ROLE_WORK_SCOPES = ["team", "company"]`(뒤가 넓음) [VERIFIED: N: domain/permissions/roles.ts:25,29 — 위 두 줄 그대로]. 배열 순서를 믿지 말고 순위 상수를 grant-ceiling에 따로 둔다(두 배열의 방향이 반대다).
- 행위자 집합이 비어도(`roleId` null) 거부다 — `can()`이 roleId 없음을 거부하는 것과 같다(`domain/permissions/can.ts:22`).

### Pattern 3: 도메인 복원기
`DOMAIN_RESTORERS`(`domain/archive/index.ts:97-103`)는 `quote_line`·`reserve_entry`·`holiday` 세 항목. `restore()`는 `assertCanWrite`(`admin.archive` 쓰기) 뒤 `domainRestorer`가 있으면 통째로 위임한다(`:118-124`). `user` 항목은 `restoreUser(viewer, id, { recordAction })`: `admin.people` 쓰기 확인 → `withTransaction` → 잠금 → 보관 행 확인(없으면 거부 · 이미 활성이면 `{restored:false}`) → 계급 C 상한 → 재직 관리자(증가라 검사 없음) → 점유 팀 중복 → `setUserArchived(false, tx)` → `recordAction({actionType:"restore"})`.

### Anti-Patterns to Avoid
- **화면 select 걸러내기를 보안으로 믿기.** 걸러낸 목록은 UX이고 서버 액션이 진짜 관문이다(액션은 id만 받는다 — `changePersonRoleAction` `z.object({ userId, roleId })`).
- **잠금 전에 읽은 값으로 판정.** 점유 팀을 잠금 전에 읽고 그 키만 잠그면 그 사이 발령이 바뀐다 → person 잠금을 먼저 잡고 점유를 읽는다(Pitfall 3).
- **전역 `db`로 리포지토리 호출.** `withTransaction` 안에서 `tx`를 안 넘기면 풀 5에서 동시 호출이 교착한다(`approvals-concurrency.test.ts:27-40` 「풀 5에서 6건」 선례, CEO-2).
- **`domain/archive` ↔ `domain/people` 순환 import.** `domain/people/index.ts:10`이 `@/domain/archive`를 import하므로 archive가 `domain/people/index`를 import하면 순환. 새 파일(`restore.ts`·`admin-guard.ts`)이 `domain/people/index`를 import하지 않게 한다.

| 2 admin | `seat:admin:last` | 관리자 수를 줄일 수 있는 쓰기 전부(changeRole · archive · resignation · setPermissionCell) |
| 3 team | `seat:team:{teamId}` | 팀장 보유자를 늘릴 수 있는 쓰기 |
| 4 division | `seat:division:{orgUnitId}` | 본부 책임자 보유자를 늘릴 수 있는 쓰기 |

규칙: **항상 1→2→3→4 순서, 같은 계층에서는 id 정렬.** 이 규칙을 지키면 두 트랜잭션이 서로 반대 순서로 잠그는 교착이 없다. 5초 `lock_timeout`이 마지막 안전망이다.

**왜 person 잠금이 필요한가(D-6408이 안 적은 것):** 팀 키만 잠그면 「changePersonRole(X→팀장)이 X의 팀 T1을 점검·잠금」하는 동안 「assignTeam(X→T3)이 X는 아직 PM이라 점검을 건너뛰는」 경합이 남는다 — 커밋 뒤 X는 팀장이면서 T3(이미 팀장 Z 있음)에 있다. 둘 다 X의 person 키를 먼저 잡으면 직렬화되고, 늦은 쪽은 **잠금 뒤에 X의 최신 계급·점유를 재조회**하므로 올바르게 거부된다. `assignTeam`은 대상이 지금 팀장이 아니어도 항상 person 잠금을 잡아야 한다. 점유 팀을 읽는 시점은 person 잠금 **뒤**, team/division 잠금 **앞**이다(점유 집합이 잠금 키를 정하므로; person 잠금이 점유 변경을 막아 안정적이다).

**registerPerson는 사람이 아직 없다:** person 키 없이 도착 팀·본부 키만 잠근다. 같은 팀에 동시에 두 명을 팀장으로 등록하는 경합은 team 키로 직렬화된다. 단, 검사 통과 후 커밋·잠금 해제 → `createAccount` → `assignTeam` 사이에 다른 쓰기가 끼면 `assignTeam` 안의 재검사(위 person+team 잠금)가 두 번째로 거른다 — 이때 계정은 이미 생겨 있어 **보상 보관 경로**(`index.ts:249-262`)가 돈다(Pitfall 2). 완전 원자성은 포기(주석 `:200-206`이 이미 그렇게 정의), 부분 상태는 보상 보관 + 「발령 실패 · 계정은 발급됨」 문구.

**증명(성공 기준 5) — 선례 패턴 두 가지(`test/integration/leave-overlap.test.ts:145-197`):**
1. **결정적:** 홀더 트랜잭션이 `pg_advisory_xact_lock(hashtextextended(<같은 키 문자열>,0))`을 쥔 채 멈추고, `Promise.allSettled`로 경합 호출 둘을 띄워, `pg_locks`에서 `locktype='advisory' and not granted and objsubid=1 and classid/objid = hash 상·하위 32비트`가 **2**가 될 때까지 폴링(`waitingOn` 선례) → 홀더 해제 → 정확히 1건 성공 · 1건 거부 · 행 수 +1.
2. **스모크:** 잠금 없이 같은 입력 동시 2건 → 성공 1 · 거부 1.
시나리오: (a) 같은 팀에 동시에 두 명 팀장 지정 · (b) 마지막 관리자 둘이 서로를 동시에 강등 · (c) `changePersonRole(X→팀장)` ∥ `assignTeam(X→다른 팀)` · (d) `archive(A)` ∥ `setPermissionCell(관리자 계급 끄기)`. 풀 5에서 동시 호출이 교착하지 않는지(`expect(pool.options.max).toBe(5)`)도 한 케이스 포함 — 전역 `db`가 새면 여기서 걸린다.

**재직 관리자 수(요청 5)** — 재직 판정식 정본은 `repositories/org-snapshot.ts:41`:
`.where(and(isNull(users.archivedAt), or(isNull(users.resignationDate), gte(users.resignationDate, asOf))))` [VERIFIED: N: repositories/org-snapshot.ts:41 — 위 줄 그대로]. 같은 판정을 `repositories/users.ts`에 `countActiveAdmins(viewer, { asOf, excludeUserId?, excludeRoleId? }, tx)`로 둔다:
```sql
select count(*) from users u
where u.archived_at is null
  and (u.resignation_date is null or u.resignation_date >= :asOf)
  and u.id <> :excludeUserId                         -- 대상이 곧 바뀔 사람이면 제외
  and u.role_id <> :excludeRoleId                    -- 칸을 끌 계급의 사람 전부 제외

              where pm.role_id = u.role_id and pm.menu = 'admin.permissions' and pm.action = 'write' and pm.allowed)
```
「후 수 = 0」이면 거부한다: changeRole(대상이 지금 관리자이고 R이 관리자 계급이 아님) · archive · resignation · cell-off. `roles.archived_at`을 **조인하지 않는다**(`can()`의 실동작과 일치, O2).

**점유 팀·보유자 조회**(D-6404 + O1 권장 정의):
```sql
-- 점유 팀 = 오늘 기준 최신 발령 팀 ∪ 모든 미래 발령 팀
with latest_today as (
  select distinct on (user_id) user_id, team_id from team_memberships
  where effective_from <= :today order by user_id, effective_from desc),
future as (select user_id, team_id from team_memberships where effective_from > :today),
occ as (select * from latest_today union select * from future)
select u.id, u.name, occ.team_id, t.org_unit_id
from users u join occ on occ.user_id = u.id
join teams t on t.id = occ.team_id and t.archived_at is null
where u.role_id = :roleId and u.archived_at is null
  and (u.resignation_date is null or u.resignation_date >= :today)
  and u.id <> :excludeUserId
```
팀장 중복은 `t.id = :teamId`, 본부 책임자 중복은 `t.org_unit_id = :orgUnitId`(본부가 보관이면 제외 — `org-snapshot.ts:38-39`와 같이 보관 팀/본부는 점유 없음). 기존 `listOrgSnapshot`(`:20-45`)·`teamLeadCandidatesAtDate`(`team-memberships.ts`)는 asOf 단일 날짜라 이 질의에 재사용 불가(점유 집합은 다른 모양).

## Common Pitfalls

### Pitfall 1: `cancelFutureAssignment`가 보유자를 늘린다 (CONTEXT의 「대상 아님」 전제가 틀림)
**What goes wrong:** D-6404의 「최신 발령(미래 포함)」 정의에서 팀장 X(현재 T1, 미래 T2 예약)는 T2의 보유자이고 T1의 보유자가 **아니다**. 그 사이 Y를 T1 팀장으로 지정해도 막히지 않는다. X의 미래 발령을 취소하면 X의 최신 발령이 T1로 돌아가 T1에 팀장 둘.
**Why:** `cancelFutureAssignment`(`domain/org/index.ts:283-`)는 발령 행을 지울 뿐이라 「팀을 늘리지 않는다」가 맞지만 「보유자 집합」은 최신 발령 기준이라 되돌아온다. 같은 문제가 시간 경과에도 있다(오늘 기준 팀과 미래 팀 사이: 미래 발령이 도래하는 날 쓰기 없이 T2에 둘이 된다).
**How to avoid:** 점유 팀 = 「오늘 기준 최신 발령 팀 ∪ 모든 미래 발령 팀」(위 SQL). 이 정의에서는 취소가 점유를 줄이기만 하고(현재 팀은 이미 점유) 시간 경과는 점유를 안 바꾼다. 아침 확인(O1)이 CONTEXT 문자 그대로(최신 발령)를 고집하면 `cancelFutureAssignment`에 같은 잠금·점검을 더한다.
**Warning signs:** 통합 테스트 「미래 이동 예약 후 후임 지정 → 예약 취소」.

### Pitfall 2: 등록의 검사-생성 사이 창
**What goes wrong:** 검사를 `withTransaction`에서 끝내고 커밋한 뒤 `createAccount`(tx 밖)를 부르면 잠금이 이미 풀렸다.
**How to avoid:** 완전 원자성은 불가(주석 `index.ts:200-206`). `assignTeam`(내부에서 person+team 잠금·재검사)이 두 번째 그물이고, 거기서 거부되면 기존 보상 보관 경로가 돈다 — 문구 `발령 실패 · 계정은 발급됨 — 보관함에서 복원 후 발령 추가`(`:262-264`)가 그대로 나가 중복 사유가 안 보인다. 개선: `assignTeam` 실패가 `UserFacingError`(중복)면 보상 보관 뒤 **그 오류를 그대로 다시 던진다**(현재는 모든 오류를 삼킨다 `:249`). 검사 순서도 지킨다: 상한(R) → 중복 → `createAccount`.
**Warning signs:** `registerPerson` 단위 테스트에서 `createAccount` 스텁이 거부 케이스에 호출되면 안 된다(순서 단언).

### Pitfall 3: 점유 읽기와 잠금의 순서
**What goes wrong:** 점유를 잠금 전에 읽어 키를 정하면 그 사이 발령이 바뀌어 잠그지 않은 팀이 점유에 들어온다.
**How to avoid:** person 잠금 → 점유 읽기 → team/division 잠금 → (점유 변하지 않았음을 person 잠금이 보장) → 판정. 위 「동시성 설계」 표의 순서를 코드에 박고 순서 위반을 막는 단위 테스트(키 정렬 함수)를 둔다.

### Pitfall 4: SYSTEM_VIEWER가 마지막 관리자 가드에 걸림
**What goes wrong:** `archived-session.test.ts:25-45`(시스템 관리자 계급 사용자 1명 → `archive(SYSTEM_VIEWER,"user",…)`)와 E2E `archived-session.spec.ts:25-30`, `registerPerson` 보상 보관이 거부된다.
**How to avoid:** 마지막 관리자 가드는 `viewer.id === SYSTEM_VIEWER.id`면 건너뛴다(그 주체는 CLI·훅·Job·보상 — `domain/viewer.ts:13-14` 주석). 상한(D-6401)은 `can` 성질로 자동 통과, **점유 중복(D-6404)은 면제하지 않는다**(CONTEXT 문장 그대로 — 단 SYSTEM_VIEWER 호출 경로 `scripts/demo-data.ts:295`·`test/e2e/fixtures.ts`는 한 팀에 팀장 둘을 안 만드는지 확인: 데모 데이터는 `lead`(팀장)·`divisionHead`(본부 책임자)가 같은 `demo` 팀 하나씩이라 통과, 추정).

### Pitfall 5: 상한이 너무 엄격해 위임이 안 된다
**What goes wrong:** 새 커스텀 계급(경영관리)은 권한 행이 0이고 `admin.people` 쓰기만 켠 상태에서 PM을 지정하려 하면 PM ⊄ 경영관리라 거부된다(design-E.md:161의 「PM 지정 통과」가 그대로는 성립하지 않는다).
**How to avoid:** (a) 통합 테스트 픽스처에서 위임받는 계급에 PM의 allowed/visible/범위 칸을 **전부 포함**시킨다(`upsertPermission`/`upsertVisibility` 복사) — 시나리오는 「PM 지정 통과 / 시스템 관리자 계정 등록 거부 / 관리자 강등 거부」. (b) 운영 문서에 한 줄: 사람 등록을 위임하려면 위임 계급이 지정할 계급의 칸을 모두 가져야 한다(07 권한 검수 후보). (c) 걸러낸 select가 빈 목록이면 첫 옵션 `—`로 제출을 막고 이유는 `Form.Actions`(SYSTEM.md:1199).

### Pitfall 6: 계급 보관은 관리자 수를 안 줄인다 (O2)
**What goes wrong:** 「계급 보관이 관리자를 0으로」를 막겠다며 보관 가드를 만들면 정의(보관된 계급 제외)와 `can()` 실동작(보관된 계급도 권한 유지)이 어긋난다.
**How to avoid:** 관리자 수 정의에서 `roles.archived_at`을 안 본다. 성공 기준 2의 「계급 보관」은 「보관해도 관리자 수가 변하지 않는다 + 보관된 관리자 계급 사람도 계속 `admin.permissions` 쓰기를 한다」를 통합 테스트로 **문서화**한다. 사용자가 「보관된 계급은 권한이 사라져야 한다」를 원하면 별개 변경(`findPermission`이 `roles.archived_at`을 보게 — 위험 경로, 범위 밖).

### Pitfall 7: 퇴직일 시한폭탄
**What goes wrong:** 마지막 관리자에게 **미래** 퇴직일을 넣으면 오늘은 통과하고 그 날 이후 관리자 0이 된다. 쓰기가 없는 시간 경과는 가드로 못 막는다.
**How to avoid:** D-6403 기본값(오늘 **이전** 날짜 거부)에 더해, 후 수를 `asOf = 새 퇴직일의 다음 날`로 평가(다른 재직 관리자가 그 날에도 재직인지)하는 것이 가장 일관되다(O3). 최소안은 CONTEXT 기본값 그대로 + 테스트에 「미래 날짜는 허용되고 시간 경과는 못 막음」 명시. 퇴직일 해제(`null`)·관리자가 아닌 사람은 검사 안 함.

### Pitfall 8: 낡은 화면과 걸러낸 목록
상세 화면을 연 뒤 위임 계급의 권한 칸이 바뀌어도 select는 열 때 계산한 목록 그대로다. 서버가 저장 시점에 다시 판정하므로(거부 문구 `계급 지정 권한 없음`) 안전하다. 별도 처리 불필요 — 토스트/한 줄만 정확히.

```typescript
// 설계 골격 — 순수 함수. 값(메뉴·동작·범위)은 아래 검증 인용에서만 쓴다.
// [VERIFIED: N: domain/permissions/menus.ts:7] export const PERMISSION_ACTIONS = ["view", "write", "approve"] as const;
// [VERIFIED: N: domain/permissions/menus.ts:55] { key: "admin.permissions", label: "권한표" },
// [VERIFIED: N: domain/permissions/roles.ts:25,29] ROLE_WORK_SCOPES = ["team", "company"] · ROLE_VIEW_SCOPES = ["company", "org_unit", "team", "own"]
const VIEW_RANK = { own: 0, team: 1, org_unit: 2, company: 3 } as const;   // 클수록 넓다
const WORK_RANK = { team: 0, company: 1 } as const;
export function canGrantRole(actor: RoleSnapshot, role: RoleSnapshot): boolean {
  if (actor.keys.has("m:admin.permissions::write")) return true;        // admin.permissions 쓰기 보유자 통과
  for (const key of role.keys) if (!actor.keys.has(key)) return false;  // 메뉴×동작 + 노출 부분집합
  return VIEW_RANK[role.viewScope] <= VIEW_RANK[actor.viewScope] && WORK_RANK[role.workScope] <= WORK_RANK[actor.workScope];
}
// 도메인: assertCanGrant(tx, viewer, { roleId: R, currentRoleId: C }) → R·C 둘 다 canGrantRole 아니면 throw new RoleGrantForbiddenError("계급 지정 권한 없음")
```
