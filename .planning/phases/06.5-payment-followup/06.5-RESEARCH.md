## Summary

이번 조사의 핵심은 세 가지다. 첫째, **조정 줄(D-6502)은 막혀 있지 않다.** 조정 줄 삽입·보관은 `structuralEditability`에서 프로젝트 상태가 아니라 `canAdjust`만 보고(`domain/quotes/edit-scope.ts`), 새 차수가 열릴 때 조정 줄은 복사되지 않고 **옮겨진다**(`repositories/quote-lines.ts:339-` `moveAdjustmentLines`, 복사는 `COPYABLE_KINDS = ["quote", "out_of_quote"]` `:287`). 따라서 CONTEXT의 「확인 못 함」은 해소됐고, `quote_lines.source_expense_id`에 `archived_at IS NULL` 부분 유일 인덱스를 걸어도 복사 경로에서 깨지지 않는다. 다만 쓰는 쪽은 `project.line-edit` 규칙과 `quote.adjust` 검사를 **거치지 않는 저수준 경로**(리포지토리 `insertQuoteLineIfAbsent` · `updateQuoteLineIfVersionMatches` · `archiveQuoteLines`)로 짜야 하고, 지급 트랜잭션 안에서 **프로젝트 행 → 견적 줄 → 지출결의 행** 잠금 순서(N-3)를 지켜야 한다.

둘째, **8.8% 제거(D-6501)는 `withholding` 규칙 종류 자체를 지우는 일이 아니다.** 사업소득(3.3%)이 같은 종류를 쓰므로 지울 것은 `incomeType === "other"` 분기 · 기타소득 세율/면제 설정 키 · `other_income` 시드 규칙이고, 기타소득의 새 규칙은 `company_borne`(이미 `TAX_COMPANY_BORNE_RATE` 0.22 · `gross_up` 기본)이다. 새로 필요한 것은 「5만원 이하 면제」 한 가지뿐이고 `company_borne` 분기에는 면제 자리가 없다.

셋째, **차단 수준의 미해결이 둘 있다.** (a) 지출결의에 「직원 수취인」을 담는 칸이 지금 없다(`expenses`의 수취인 칸은 `vendor_id` 하나뿐, `vendors.kind`는 `client|supplier|both`). D-6504(직원 건도 같은 파일)·D-6507(직원 지급 건 같은 검사)은 이 칸이 있어야 의미가 있는데 D-6505는 `users` 칸만 말한다 — 플래너가 스키마 플랜에서 `expenses` 쪽 수취인 칸을 넣을지 사용자에게 물어야 한다. (b) 신한 양식 견본이 `.xls`였는데 D-6504는 xlsx로 잠갔다 — 은행이 `.xlsx` 업로드를 받는지 확인되지 않았다.

**Primary recommendation:** 스키마 플랜 **하나**(웨이브 0)를 맨 앞에 두어 `quote_lines.source_expense_id`(+`source_synced_version`) · `corp_card_usages.card_use_number`/`idempotency_key` · `purchase_requests.idempotency_key` · `users` 계좌 4칸 · (선택) `vendors` 예금주 CHECK · 코드표/시드 맞춤 데이터 마이그레이션을 한 번에 만들고(위험 경로, 사용자 머지), 그 위에 돈 플랜(D-6501/6502/6503/6504, Opus 실행자 + Opus 검토, `/review` + `/cso`)과 화면·테스트 정리 플랜을 얹는다. ### Pattern 1: 규칙 줄 쓰기는 리포지토리 저수준 함수로
**What:** 사람이 편집하는 경로(`writeQuoteLinesInTx` → `prepareQuoteLineSave` → `project.line-edit` 규칙)와 별개로, 시스템이 만드는 조정 줄은 `insertQuoteLineIfAbsent` / `updateQuoteLineIfVersionMatches` / `archiveQuoteLines`를 직접 부른다.
**When to use:** 지급 완료/취소 트랜잭션 안에서만.
**근거:** 조정 줄 삽입/보관 가능 여부는 프로젝트 상태가 아니라 `canAdjust`로만 갈린다 [VERIFIED: domain/quotes/edit-scope.ts `structuralEditability` — 이전 세션 확인, 줄 번호는 함수 이름으로 가리킨다]. 시스템 규칙 줄이므로 `quote.adjust` 재검사 안 함(D-6502).

### Pattern 2: 멱등 키 — 지출결의 선례를 그대로
`expenses.idempotency_key text unique`(`db/schema/expenses.ts:50`), 화면은 `useState(() => crypto.randomUUID())`(`app/(app)/expenses/[id]/expense-form.tsx:168`). 서버는 **잠금·한도 판정보다 앞에서** 키로 기존 행을 조회하고, 있고 같은 행위자면 그 행을 돌려준다. 없으면 `onConflictDoNothing` → 재조회로 경합을 닫는다 [VERIFIED: domain/expenses/index.ts createTeamExpenseDraft 주변, repositories/expenses.ts:31-45].

### Anti-Patterns to Avoid
- **`copyQuoteLines`가 새 칸을 복사하게 두기:** 이 함수는 `getTableColumns(quoteLines)`로 모든 칸을 옮긴다(`repositories/quote-lines.ts:324`). 조정 줄은 `COPYABLE_KINDS` 밖이라 오늘은 안전하지만, 연결 칸은 **조정 줄에만** 쓰고 다른 종류 줄에는 NULL이어야 한다(CHECK로 고정 권장).
- **플랫 문자열 비교로 손 편집 감지:** 금액·이름 비교 대신 `version` 대조(아래 Q2).
- **8.8% 분기를 남겨 두고 시드만 바꾸기:** 설정 키 · `TaxRates` 필드 · 테스트(`test/unit/settings/tax-rate-precision.test.ts`)가 참조한다.

## Q1. D-6501 기타소득 22% 역산 (8.8% 제거)

**8.8% 경로가 사는 곳 (이번 세션에 연 파일):**
- 시드 규칙: `domain/seed/index.ts:119-130` — `value: "other_income"`, `ruleKind: "withholding"`, `roundingUnit: 10`, `roundingMethod: "truncate"`, `minWithholdingAmount: 125000`, `basisDate: "payment_date"` [VERIFIED: domain/seed/index.ts:119-130].
- 계산 분기: `domain/money/tax.ts` `applyTaxRule`의 `withholding` 갈래 — `incomeType === "business"`면 사업소득 세율, 아니면 `TAX_WITHHOLDING_OTHER_INCOME_RATE`; `incomeType === "other"`이면 `TAX_WITHHOLDING_OTHER_INCOME_EXEMPT_THRESHOLD` 이하 면제 [VERIFIED: domain/money/tax.ts:92-117].
- `company_borne` 갈래: `TAX_COMPANY_BORNE_RATE`(기본 `0.22`) · `TAX_COMPANY_BORNE_METHOD`(`flat` | `gross_up`)로 `gross = supply / (1 - rate)`, `companyBorneKrw = round(gross - supply, unit, roundingMethod)`, `payableKrw: supplyKrw` [VERIFIED: domain/money/tax.ts:118-139, domain/settings/keys.ts TAX_COMPANY_BORNE_RATE `default: 0.22`]. **면제 자리가 없다.**
- 설정 정의: `TAX_WITHHOLDING_OTHER_INCOME_RATE` `key: "tax.withholding.other_income.rate"` `default: 0.088`, `TAX_WITHHOLDING_OTHER_INCOME_EXEMPT_THRESHOLD` `key: "tax.withholding.other_income.exempt_threshold"` `default: 125000` [VERIFIED: domain/settings/keys.ts:81-110].
- 배선: `TaxRates.withholdingOtherRate` · `withholdingOtherExemptThreshold` (`domain/money/tax.ts:159-193`), `domain/expenses/tax.ts:90`(`rateDefFor`), `domain/expenses/tax.ts` `incomeTypeFor`/`taxLineText`, 단위 시험 `test/unit/settings/tax-rate-precision.test.ts` (grep 결과 확인).

**권장 변경 (최소):**
1. 시드 `other_income`을 `ruleKind: "company_borne"`(`roundingUnit: 10`, `truncate` 유지, `minWithholdingAmount: 0`, `basisDate: "payment_date"`)로 바꾼다. `taxRule` 스키마(`domain/code-tables/tax-rule.ts`, strict)가 `company_borne`에서 필수로 요구하는 칸을 먼저 읽고 맞춘다(이번 세션 미확인 — 「추정」 `minWithholdingAmount` 등 공통 칸은 유지).
2. `applyTaxRule`의 `company_borne` 분기에 면제를 넣는다. 위치 권장: **분기 첫머리 `if (supplyKrw <= exemptThreshold) return …0`**, 기준은 새 historized 설정 키(예: `tax.company_borne.exempt_threshold`, 기본 `50000`)로 둔다 — 8.8% 쪽 면제와 같은 모양(기준일 = 지급일)이라 설정 화면에서 바꿀 수 있고 「코드에 숫자 박지 않는다」를 지킨다. **새 설정 키라 사용자 확인(3절 ㉠)이 필요할 수 있음** → Open Question 3. 대안: `taxRule` jsonb에 `exemptAtOrBelowKrw` 칸을 더하는 방식(코드표 안에서 끝남) — 설정 화면을 늘리지 않는 대신 strict 스키마 변경.

**(a) `test/e2e/cert-review.spec.ts:303` 「게이트 꺼짐 — 잡아 둔 세 액션을…」**
- 읽은 사실: `page.on("request")`로 서버 액션 POST를 `captured`에 모으고, `전체 보기` → `fill` → `가리기` → `전체 보기`(`toHaveValue` 한 번) → `fill` → `저장` 클릭 → `저장됨 · ` 글자 가시 → **즉시** `expect(captured).toHaveLength(3)` [VERIFIED: test/e2e/cert-review.spec.ts:303-326].
- 레이스 후보: `captured`는 `request` 이벤트(요청 **발송**) 기준이다. `저장됨 · ` 글자는 서버 응답 후 렌더라 저장 요청은 이미 잡혔다. 불안정한 쪽은 **둘째 `전체 보기`** 뒤 요청이 서버 액션을 한 번 더 부르는지(상태 복원인지)와, 저장 성공 직후 `router.refresh()`가 만드는 **RSC 요청이 서버 액션 판별(`isServerAction`)에 걸려 4번째로 잡히는 경우**다. 즉 건수 단언이 「타이밍」이 아니라 「부가 요청이 끼는 순간」에 따라 3 또는 4가 될 수 있다. 가장 의심: `toHaveLength(3)` 정확 일치.
- 수정 방향(원인 쪽): 건수 정확 일치를 **의미 단언**으로 바꾼다 — 캡처한 요청의 `next-action` 헤더(액션 id)로 「잡아 둔 세 액션 id 각각이 정확히 1회 이상 나감」을 단언하거나, `expect.poll(() => captured.length)`로 안정화 대기 뒤 id 집합을 비교. 테스트 본문만 고치며 앱 코드·마이그레이션 0. **먼저 CI 실패 로그에서 어느 단언이 터졌는지 확인**하는 단계를 태스크 첫 줄에 둔다(없으면 근거 없이 고치는 것 = 추측 수정이라 CLAUDE.md §5 위반).
- 약한 후보: 로그인 속도 제한 429(같은 IP 연속 로그인, 183-qa.md:44), 게이트 설정 전환의 서버 캐시(캐시 코드 못 찾음).

**(b) `test/e2e/project-period.spec.ts` (3) 둘째 기간 저장**
- 읽은 사실: `waitForSaveAction`은 「메서드 POST + `next-action` 헤더 존재」인 **아무** 응답이나 잡는다. 클릭 **직전**에 등록하고, 첫 저장 뒤 `진행` 태그와 `기간 … ~ …` 글자를 기다린 다음 `#period-open`을 눌러 둘째 저장을 보낸다 [VERIFIED: project-period.spec.ts:60-75, :168-200].
- 레이스 후보 1: 첫 저장 뒤 `router.refresh()`가 끝나기 전에 둘째 `#period-open`/`fill`/`일괄 저장 1` 클릭이 일어나 **낡은 클라이언트 version**으로 둘째 저장이 가서 `다른 사람이 먼저 기간을 바꿈`(충돌)이 난다. 글자 단언(`진행` 태그 · 기간 글자)이 서버 렌더 갱신 **전의 낙관적 클라이언트 상태**로도 통과할 수 있는 것이 핵심 의심.
- 후보 2: `waitForSaveAction`이 다른 서버 액션 POST(예: 뒤따르는 알림/세션 활동)를 먼저 잡아 DB 단언(`:196-197`)이 저장 전에 읽는다.
- 후보 3: `TODAY`가 모듈 로드 시 고정 — 자정(KST) 근처 CI 시각에서 「종료일이 어제」 계산이 하루 어긋남(`:17`).
- 수정 방향: (1) 둘째 저장 전에 **서버가 새 version을 렌더했다는 신호**(예: 화면에 반영된 버전 표식 또는 네트워크 idle 후 RSC 응답 대기 `page.waitForResponse` RSC 요청)를 기다린다, (2) `waitForSaveAction`에 URL/액션 식별(가능하면 응답 본문 또는 요청 `next-action` 값 고정)을 넣어 다른 액션 POST를 걸러낸다, (3) `TODAY`를 테스트 시작 시 `kstToday(new Date())`로 한 번 고정하되 자정 경계 케이스를 피하게 시각 주입. 어느 줄이 터지는지 CI 로그 확인이 선행.
- 프로젝트 기간 편집은 `ledger-save-flow.spec.ts:266-284` · `quote-edit-scope.spec.ts:478-492` · `quote-table.spec.ts:1695`도 거치므로 같은 헬퍼를 쓰면 공통 수정이 이득이다 — 단 이번 범위는 간헐 2건의 근본 수정이므로 헬퍼 공유화는 확장하지 않는다.

## Common Pitfalls

### Pitfall 1: 조정 줄을 지출결의 행 잠금 뒤에 쓰다가 교착
**What goes wrong:** 지급 완료가 지출결의 행을 먼저 잠그고 견적 줄을 나중에 잠그면, 견적 줄 편집(프로젝트 행 → 견적 줄 → 지출결의)과 교착한다.
**How to avoid:** 완료/취소 함수의 잠금 순서를 N-3으로 통일하고, 06-19 「기안 동시 6건」 꼴로 결정적 교착 시험을 쓴다(풀 크기 `pool.options.max` 단언).
**Warning signs:** 통합 시험이 간헐적으로 hookTimeout.

### Pitfall 2: 8.8% 키를 지우며 시험·설정 내보내기가 깨짐
`test/unit/settings/tax-rate-precision.test.ts`가 `TAX_WITHHOLDING_OTHER_INCOME_RATE`를 import하고, `TaxRates` 필드가 `applyTaxRule`/`taxRatesReader` 외 `domain/expenses/tax.ts`에도 쓰인다. 지울 때 `pnpm typecheck` + 해당 단위 시험을 먼저 돌린다. 설정 화면은 키가 SETTING_DEFS에서 빠져도 DB 행이 남는다 → Open Question 4.

### Pitfall 3: `copyQuoteLines`가 연결 칸을 복사
조정 줄은 복사 대상이 아니므로 오늘은 안전하지만, 나중에 종류 목록이 넓어지면 연결 칸이 복사돼 부분 유일 인덱스를 어긴다. CHECK(`source_expense_id IS NULL OR line_kind='adjustment'`)로 고정.

### Pitfall 4: 서버 액션 반환 안의 BOM/바이너리
CSV에서 BOM이 Flight 청크에 떨어졌다는 기록(`filter-bar.tsx` 주석). xlsx는 base64로 돌려주고 브라우저에서 디코딩해 `Blob`을 만든다 — 문자열 그대로 `Blob`에 넣으면 깨진다.

### Pitfall 5: `excel_export` 기록 순서
기록은 직렬화 **전**(`exportActionLog` 패턴). 파일을 만든 뒤 기록하면 기록 실패 시 파일이 이미 나간다.

### Pitfall 6: 로컬 dev 통과를 완료로 착각
`playwright.config.ts`가 CI에서만 프로덕션 빌드를 쓴다(CLAUDE.md §5). 화면/간헐 수정 완료는 `CI=true`로 확인.

### Pitfall 7: 통합 시험 동시 실행
테스트 DB(`erp_test`)가 하나라 병렬 실행 시 권한 거부·데드락. 항상 `flock` 아래에서 하나씩(`.claude/rules/tests.md`).

## Open Questions

1. **직원 수취인 표현 (차단 — D-6504 직원 건 · D-6507 직원 갈래)**
   - What we know: `expenses`의 수취인 칸은 `vendor_id` 하나, `vendors.kind`는 `client|supplier|both`. D-6505는 `users` 계좌 칸만 말한다.
   - What's unclear: 「직원 지급 건」을 지출결의에 어떻게 담나(`expenses.payee_user_id` 칸 추가? 거래처에 직원 거래처를 만들어 연결?). D29(직원 바로 고르기)는 gap-verdicts.md:84-87에서 「지출결의 쪽이 맡음」이라 했으나 해당 칸이 현 저장소에 없다.
   - Recommendation: 사용자에게 한 줄 질문(권장: `expenses.payee_user_id` nullable 칸을 스키마 플랜에 포함, `vendor_id`와 둘 중 하나 CHECK). 답이 「06.5 범위 밖」이면 D-6504/6507은 **거래처 지급만** 구현하고 users 계좌는 칸·입력 화면까지만 둔다.
   - 함께 올릴 확인: **경영관리 계급에 `admin.people` 보기를 켜야 한다**(시드는 `role-sysadmin`에게만 줌). 사용자가 권한 매트릭스에서 켠다.
2. **신한 업로드 파일 형식(.xls vs .xlsx)** — 견본은 `.xls`. D-6504 xlsx 잠금이므로 은행 수용 여부를 사용자가 실제 파일로 확인(1건). 안 되면 SheetJS `bookType`만 바꾸는 한 줄 변경.
