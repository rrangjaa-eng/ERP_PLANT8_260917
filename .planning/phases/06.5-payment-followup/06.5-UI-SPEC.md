`vendor-form.tsx`(옆 패널)의 칸에 서버 검사 오류를 단다. **저장 때 판정은 은행 · 계좌 · 예금주 칸을 새로 넣거나 바꾼 저장에만 적용된다**(`06.5-REVIEWS.md` DH-3 — 손대지 않은 기존 값은 막지 않는다). 아래 「적용 범위」 행이 정본이다. **필수 표시(`*`)를 두지 않는다**(SYSTEM §7-2 — 필수인데 비면 제출이 이유를 말한다).

| 항목 | 계약 |
|---|---|
| 적용 범위 (REVIEWS DH-3) | 이 표의 ① ② ③은 **은행 · 계좌번호 · 예금주 칸을 새로 넣거나 바꾼 저장에만** 돈다. 「새로 넣거나 바꿈」 = 제출한 `계좌 은행` · `예금주` 글자가 저장된 값과 다르거나, `새 계좌번호` 칸에 값이 있는 것. 셋 중 어느 칸도 손대지 않은 저장(이름 · 연락처 등 다른 칸만 고침)은 판정 0 — 저장된 기존 값이 옛 데이터라 풀리지 않거나 예금주가 비어 있어도 **막지 않는다**. 칸별로 따진다: ②는 **은행 칸을 새로 넣거나 바꾼 저장**에서만, ③은 **예금주 칸을 새로 넣거나 바꾼 저장**에서만, ①(예금주 필요)은 **은행 또는 계좌번호를 새로 넣거나 바꿔 은행 + 계좌번호 짝이 새로 만들어지는 저장**에서만 돈다. 옛 데이터는 V5 막힌 건 + 끝 링크로 잡힌다(아래 「기존 데이터」) |
| 조건 | ① 은행과 계좌번호가 **둘 다 있을 때**만 예금주 필요(옛 CHECK와 같은 조건 `O: db/schema/010_tables.sql:5440`). 수정 모드에서 `새 계좌번호`를 비우고 저장된 번호가 있으면 「번호 있음」으로 센다 ② **`계좌 은행` 칸을 새로 넣거나 바꿨으면 은행 코드로 풀리는지 본다**(번호 유무와 무관 — 풀리지 않는 이름은 어디에도 쓸 수 없다) ③ **예금주 칸을 새로 넣거나 바꿨으면 길이 · 글자를 본다**(V2 ③과 같은 함수). ②③은 V5 이체 파일과 **같은 규칙** — 저장 때와 파일 때의 판정이 갈라지지 않는다. 위 「적용 범위」 밖 저장에는 ①②③ 모두 돌지 않는다 |
| 칸 오류 | `예금주` `TextField`의 `error` prop → 입력 테두리 `--status-danger` 1px + 칸 아래 `--text-aux --status-danger` 한 줄: `예금주 없음 · 예금주 적기` / `예금주 길이 초과 · 예금주 줄이기` / `예금주 형식 오류 · 예금주 고치기`. `계좌 은행` 칸: `은행 코드 없음 · 은행 이름 고치기`. 입력값은 지우지 않는다. 오류가 뜨면 포커스를 첫 오류 칸으로 보낸다(`firstErrorId`) |
| 요약 | 기존 `fieldErrorsReason` 그대로: 등록 `등록할 수 없음 — {칸 이름} 1칸 · ` + 3차 `{칸} 고치기`, 수정은 `수정할 수 없음 — …`. 오류가 여러 칸이면 칸 순서대로 이어 붙고 3차는 첫 칸으로 간다 |
| 클라이언트 | 서버 검사가 정본이다. 클라이언트에서 미리 막지 않는다(제출 뒤 오류로 충분 — 사용자 결정 최소) |
| 기존 데이터 | 예금주 없이 계좌가 있거나 풀리지 않는 은행 이름을 가진 **옛 거래처는 저장을 막지 않는다** — 그 칸을 건드리지 않은 저장은 통과한다(REVIEWS DH-3). 옛 데이터는 V5 이체 파일이 같은 문구로 막은 건 + 행 아래 끝 링크(`/admin/vendors?editId=…`)로 잡힌다. 그 링크로 와서 은행 · 예금주를 고치는 저장이 곧 「바꾼 저장」이라 그때 이 오류가 같은 문구로 선다. 별도 안내 없음 |
| 범위 밖 | 은행 칸을 코드표 선택으로 바꾸는 일은 이 페이즈 밖(자유 텍스트 유지) |

### V4. 지출결의 제출 막힘 「지급처 계좌 없음」 (D-6507)

기존 제출 막힘 사슬(`firstExpenseSubmitBlock`, ①~⑨ 첫 막힘 하나)에 **단계 하나**를 더한다. 새 컴포넌트 없음 — `BlockLine`이 1차 옆에 이유를 그린다.

| 항목 | 계약 |
|---|---|
| 언제 | 지급 방식이 계좌이체이고 지급처(거래처 · 직원)에 쓸 수 있는 계좌가 없을 때. 현금 · 법인카드는 막지 않는다. 계좌 있음 = 은행 칸이 공백 아님 ∧ 계좌번호 있음 |
| 사슬 자리 | `쓰지 않는 지급 방식`(지급 방식 비활성) 단계 **바로 뒤** · `공급가액이 0` 앞. 거래처 · 지급 방식이 정해진 뒤에야 판정할 수 있어서다 |
| 문구 — 고칠 수 없는 사람 | `지급처 계좌 없음 · 계좌 등록은 경영관리` — 「원인 · 다음 행동」, 다음 한 수가 제출자(기안자)의 권한 밖이므로 **버튼을 세우지 않고 담당을 적는다**(SYSTEM §8 규칙 3). `target`은 null(3차 버튼 없음) |
| 문구 — 고칠 수 있는 사람 | 제출자가 고칠 권한을 가졌으면(거래처: 거래처 관리 쓰기 · 직원: 지급 처리 쓰기 ∧ 사람 상세 보기) 같은 원인 뒤에 **3차 링크 `계좌 등록`**(`지급처 계좌 없음 · ` + 링크). 거래처면 `/admin/vendors?editId={id}`, 직원이면 `/admin/people/{id}?editAccount=1`, **새 탭**(`target="_blank"` — 작성 중인 폼을 잃지 않는다). 담당 글자는 이때 쓰지 않는다 |
| 지급처 없음 | 지급처 자체가 비었으면 기존 ⑤ 단계 문구를 이름만 바꾼다: `지급처 없음 · 지급처 고르기`(3차가 `지급처 고르기` 대화상자를 연다) |
| 경고가 아니라 막기 | 1차 `지출결의 제출`은 `aria-disabled` + 이 문장이 `aria-describedby`로 붙는다(§10). 임시 저장 · 증빙 올리기는 막지 않는다 |
| 풀리는 길 | 지급 방식을 바꾸거나 지급처를 바꾸면 사슬이 다시 돌아 풀린다. 경영관리가 거래처 · 직원 계좌를 채우고 기안자가 문서를 다시 열면 풀린다 |
| 고를 때 미리 보임 | 지급 방식이 계좌이체일 때 V12 대화상자 후보 행 부제 끝에 ` · 계좌 없음`이 붙어(`--text-muted`) 고르기 전에 안다(M-6). 이미 제출 막힘 문장이 같은 사실을 기안자에게 알리므로 새 노출은 아니다 |
| 직원 지급 건 | 같은 문장 · 같은 자리(D-6505 칸이 비면 같은 단계가 막는다) |
| 줄 수 | 문장이 좁은 폭에서 두 줄이 되어도 고정 제출 줄 아래 여백(`.formBarSpacer` — 행동 줄 + 막힘 한 줄분)이 모자라지 않는지 **320에서 실측**한다(검증 계약). 모자라면 spacer를 막힘 줄 두 줄분으로 키운다(기존 CSS 변수 조정 — 새 토큰 0) |

### V10. `Form` 안 `KvList` 맨 앞 1px 선 (D-6514) — 시스템 부품 쪽 수정 (page 배치만)

SYSTEM §7-15 `Form`은 「묶음 사이 `--s-6` + `1px --border-row`」인데 실제 부품에는 그 선이 없다(`ui/form/Form.module.css`는 행동 줄 위 선뿐). 연차 신청 폼의 잔고 · 결재선 `KvList`가 비고 칸 바로 뒤에 간격만 있고 선이 없는 것이 그 결과다.

**전제 정정(H-7):** `.form { gap: var(--s-6) }`는 `Form layout="page"`만 참이다. `.panel { gap: 0 }`(`Form.module.css`)이고 `PanelForm`이 칸 묶음을 스크롤 래퍼(`.fields`)로 감싸 `dl`이 `.form`의 직계가 아니다 — 그래서 아래 규칙은 **page 배치 전용**이다. `Form layout="panel"` 안 `KvList`는 현재 호출 0곳이고 이번 범위 밖이다(생기면 그때 패널 변형을 별도 결정).

| 항목 | 계약 |
|---|---|
| 고치는 곳 | **`ui/form/Form.module.css`에 규칙 하나**: `.form`의 직계 `dl`(= `KvList`)이 첫 자식이 아니면 위에 `var(--line-w) solid var(--border-row)`(리터럴 `1px` 금지 — stylelint `unit-disallowed-list`), 선 아래 `--s-3`(선 위 `--s-6`은 `.form`의 `gap`이 이미 준다). `.panel`에는 걸지 않는다. `KvList.module.css`는 바꾸지 않는다 — 읽기 화면(`KvList`가 폼 밖에 서는 곳)이 영향을 받지 않는다 |

### V12. 지급처 고르기 — 직원 지급처 (D-6517)

지급처는 거래처 **또는** 직원이고 둘 다는 아니다. 지출결의 폼의 지급처 칸과 고르기 대화상자가 직원을 함께 다룬다. 새 컴포넌트 0 — 기존 `PickDialog`에 `noun: "지급처"` 한 값을 더하고 직원 행을 같은 목록에 섞는다(SP-65-5).

```
폼
│ 지급처   김OO                         바꾸기 │   ← Form.Field id="vendor" label "지급처"
│          직원 · 마케팅팀                    │   ← 값 아래 한 줄(13 muted): 직원이면 `직원 · {팀}`, 거래처면 기존 `기본 증빙 {종류}`
대화상자
│ 지급처 고르기                         ✕ │
│ 지급처 이름 검색 [____________________] │
│ 지급처 5                                 │
│ ○ 김OO                  직원 · 마케팅팀  │
│ ○ (주)스테이지원   기본 증빙 세금계산서 · 계좌 없음 │ ← 계좌이체 지급 방식일 때만 ` · 계좌 없음`
│ [취소 Esc]                  [이 지급처로] │
```

| 항목 | 계약 |
|---|---|
| 이름표 | **「거래처」→「지급처」**(결정 맥락 9, DH-1 A안): 지출결의 폼의 칸 라벨 `지급처` · 열기 버튼 `지급처 고르기`(비었을 때) / `바꾸기`(값이 있을 때) · 실패 `지급처 바꾸기 실패 · 다시 시도` · 문서 화면 라벨 `지급처`(`expense-document.tsx`) · 목록 열 머리글 `지급처`(`list-columns.ts`) · 지급 대상 표 열 머리글 `지급처`(`payment-targets-table.tsx`) · 제출 막힘 ⑤ `지급처 없음 · 지급처 고르기`. **거래처 자체를 뜻하는 곳은 그대로**: 거래처 관리 화면 · 거래처 폼 · 견적 표의 `거래처` 열 · V5 이유 `거래처 계좌 등록`. 용어표 한 줄 `지급처`(= 거래처 또는 직원)는 SP-65-4 |
| 후보 | 거래처 + **직원**. 직원 후보에서 **보관된 사람과 퇴사일이 오늘(KST) 이전인 사람은 뺀다**(`O: server/src/expenses.ts:2387-2392` `archived_at is null and left_date is null`). 한 검색어가 두 목록을 함께 거른다. 계좌 · 연락처는 싣지 않는다(직원 후보는 이름 · 팀만) |
| 대화상자 | 제목 `지급처 고르기`(비었을 때) / `지급처 바꾸기`(값이 있을 때) · 검색 이름 `지급처 이름 검색` · 1차 `이 지급처로` · noun `지급처` → 빈 목록 `조건에 맞는 지급처가 없습니다` / `고를 수 있는 지급처가 없습니다` · 고른 것 없음 `고른 지급처 없음`(모두 `pickEmptyText`가 만든다 — 새 문구 아님). 로딩 · 검색 0건 · 실패는 기존 `PickDialog` 문구 그대로 |
| 결과 머리 | `지급처 {N}` — N = 거래처 + 직원 후보 합. 기존 `거래처 {N}` 꼴과 같다. `거래처 {N} · 직원 {M}`처럼 종류별 건수를 풀어 쓰지 않는다(안내 문구에 가깝다) |
| 행 | 거래처 행은 지금 모양 그대로(제목 이름 · 부제 `기본 증빙 {종류}`). 직원 행은 제목 `{이름}` · 부제 `직원 · {팀}`(팀 없으면 `직원`) — 배지 · 새 색 없이 글자 `--text-aux --text-muted`. **지급 방식이 계좌이체인 문서에서만** 부제 끝에 ` · 계좌 없음`을 붙인다(계좌 유무만 — 평문 · 끝 4자리 노출 없음; V4 제출 막힘이 같은 사실을 이미 기안자에게 말한다) |
| 첫 저장 전 | **새 문서에서도 직원을 고를 수 있다**(EP1-9). 고른 값은 폼 상태 하나로 들고 있다가 **첫 저장에 함께 싣는다**(별도 저장 단계 없음) — 거래처를 고른 때와 같다. 폼은 `picked: { 거래처 } | { 직원 } | 없음` **한 상태**로 들어 다른 종류를 고르면 앞의 것이 사라지고 칸에는 언제나 이름 하나만 보인다. 직원을 고르면 증빙 종류를 건드리지 않는다(거래처 기본 증빙 종류 자동 채움은 거래처에만) |
| 저장된 문서 | 고르는 순간 서버가 바로 바꾼다(거래처는 기존 동작, 직원은 같은 모양의 새 동작) — 성공하면 칸 이름과 부제가 바뀌고 실패는 `지급처 바꾸기 실패 · 다시 시도` |
| 어느 문서에서 | **팀 비용 · 프로젝트 비용 모두**(결정 맥락 16) — 프로젝트 비용에서도 지급처 칸이 열린다. 문서의 지급처 칸이 정본이다: 이체 파일과 제출 막힘 판정은 모두 이 칸을 읽는다(견적 줄 문서의 줄 거래처는 기본값으로 채워질 뿐이다). 결재 뒤에는 지급처를 바꾸지 못한다(바꾸는 길은 제출 전에만 열려 있다 — 옛 `O: server/src/expenses.ts:4241-4243`) |
| 표시 위치 | 폼 · 문서: 칸 값 = 이름, 값 아래 한 줄로 종류를 말한다(거래처 `기본 증빙 {종류}` · 직원 `직원 · {팀}`). 목록 · 지급 대상 표 열: **이름만**(부제 없음 — 구별은 문서에서). 같은 이름의 거래처와 직원이 목록에서 구별되지 않는 것은 받아들인다 |
| 키보드 · 접근성 | `PickDialog` 기존 계약 그대로(`aria-live` 결과 머리 · 초점 가두기 · `Esc` 닫기). 직원 행도 같은 radio 행 |
| 다섯 상태 | LOADING: 기존 `PickDialog` 검색 중. EMPTY: noun 문구. ERROR: 기존 `failedLine`. SUCCESS: 대화상자 닫힘 + 칸 이름 갱신. PARTIAL: 두 목록 중 하나만 실패하면 전체를 실패로 본다(반쪽 목록을 보이지 않는다) |

### V14. 지급처 합산 이체 파일 · 소계 (D-6519)

**이체 파일은 지급처마다 한 줄**(이체액 합산)이다. 지급 대상 표는 이미 **지급 예정일 기준 그룹**(`groupBy={(row) => row.group}`)으로 나뉘어 있어 지급처 머리줄을 표에 넣으면 두 축의 그룹이 겹치고 「표 하나」가 깨진다(`O:`가 지급처 머리줄을 둔 `SalesPayments.tsx:596-621`은 예정일 그룹이 없는 표였다). 그래서:

**결정 — 표는 그대로 두고, 지급처 소계는 「고른 행」에 대해서만, 확정 직전 `지급 완료` 대화상자에 보인다.**

### V15. 받는 인원 — 경품 면제를 한 사람 몫마다 판정 (결정 맥락 4 · 카드 ①)

경품(기타소득, 회사 대납) 면제 한도(시가 50,000원 이하)는 **받는 사람 한 명 몫**으로 잰다. 지출결의 한 건에 여러 사람 몫이 들어 있으면(3만원 × 5명 = 15만원) 한 건 합계로 재면 면제를 잘못 잃는다(`06.5-REVIEWS.md` ND-1). 그래서 지출결의 폼에 **`받는 인원` 칸 하나**를 더하고 서버가 한 사람 몫 세전 금액(`공급가액 ÷ 받는 인원 ÷ 0.78` ≤ 50,000 — 카드 ① 10/13 23:29 KST · 카드 ⓪ 「세전 금액으로」 10/13 23:30 KST)으로 사람별 면제를 판정한다. 판정 · 계산은 서버(02), 화면은 칸 하나와 읽기 행 하나다. 새 컴포넌트 0 — 기존 `Form.Field` + 텍스트 입력 + `Form.Error`.

```
폼 (Form layout="page", 한 열)
│ 증빙 종류   [기타소득 ▾]                       │
│ 통화        [KRW ▾]                            │
│ 공급가액    [        150,000]                  │
│             회사 대납 세금 0 · 면제 기준 이하   │ ← 서버 계산 한 줄(기존 taxHint, 인원이 바뀌면 다시 계산)
│ 받는 인원   [5]                                 │ ← 증빙 종류의 세금 규칙이 회사 대납일 때만 선다
│ 분할 지급   …                                   │
│ …                                               │
│ 증빙        (첨부 영역)                          │ ← 증빙 묶음: 첨부 · 증빙일 · 선결제 · 사유
│ 증빙일      [2026-09-17]                        │   **`증빙 금액` 칸 없음**(D-6520 — 06-10 칸 삭제, 06.5-05)
```

폼의 금액 칸은 **공급가액 하나**다(D-6520). 06-10이 증빙 묶음에 둔 `증빙 금액` 칸과 그 오류(`숫자 아님 · 12,400,000처럼` · `증빙 금액 0 이하 · 금액 고치기` · EA-1 `부가세 포함 금액 · 공급가로 입력`)는 새 문서 · 작성 중 · 반려 폼 어디에도 없다. 증빙 묶음은 첨부 영역 · `증빙일` · 선결제 · 사유로 남고 그 칸들의 자리 · 모양은 06 그대로다. 선결제 묶음의 자리 단언은 `증빙일` 칸을 기준으로 잡는다. 공급가액에 부가세 포함 판정을 새로 걸지 않는다.

## 시스템 변경 제안 (계획의 첫 화면 태스크가 `DECISIONS.md` → `SYSTEM.md` 순서로 옮긴다 — 이 문서는 두 파일을 고치지 않는다)

### SP-65-1. §7-15 `Form` — `layout="page"` 폼 안 `KvList`는 묶음으로 취급해 위 `var(--line-w)` `--border-row`
구현은 `ui/form/Form.module.css` 한 규칙(V10). 이유: SYSTEM §7-15 · §3(`폼: 묶음 사이 24px + 1px 선`)가 이미 선을 요구하는데 부품에 없어 연차 신청 폼 4폭이 모두 어긋난다(06.3-03 design-review). **panel 배치는 `gap: 0`이고 스크롤 래퍼가 `dl`을 직계에서 떼므로 이번 범위 밖**이다. 화면 하나만의 선택지(`leave-form.tsx`에 `<hr>`)는 CLAUDE.md §6이 금지한다.

### SP-65-2. §6-1 목록 필터 줄 구성 한 줄
「필터 줄 = 검색 칸(있으면 맨 앞, Enter 제출) → 선택 칸들 → 2차 `파일 받기` 버튼(편집 폭에서만) → 결과 글자(줄이 모자라면 아래 줄), 오른쪽 끝에 1차」. 이유: V1 · V5가 이미 프로젝트 목록 · 행동 로그 · 지급 대상에서 따로 굳은 배치를 명문화한다. 새 부품 · 새 토큰 없음.

### SP-65-3. §7-20 `SidePanel` — 주소로 직접 연 패널의 닫힘 포커스
「열기 요소가 없으면(주소 직접 열기) 호출부가 `returnFocusTo?: () => HTMLElement | null`로 그 행의 열기 요소를 돌려주고, `null`이면 화면 제목으로 간다」. 이유: V9 L-1 — 카드만이 아니라 OI-9 재현 시 거래처 · 법인카드도 같은 규칙이다. 선택자 문자열 API는 행 링크 모양이 바뀌면 조용히 깨지므로 쓰지 않는다. 새 컴포넌트 아님.

### SP-65-4. §8 규칙 7 용어표 — `지급처`
용어 한 줄 추가: `지급처`(= 거래처 또는 직원; 지출결의 폼 · 문서 · 목록 · 지급 대상 · 고르기 대화상자 · 제출 막힘에 쓴다. 거래처 관리 화면 · 견적 표의 `거래처`는 그대로). 이유: V12 — 같은 칸에 직원 이름이 서는데 이름표가 「거래처」면 한 화면 안에서 낱말이 갈라진다(규칙 1 · 2 · 7). `DECISIONS.md`에 용어 변경으로 기록.

### SP-65-5. `Table` `selection` · `PickDialog` — 두 부품의 작은 API 확장
① `Table` 선택 표의 행 아래 줄: 막힘 줄(`blockedReason`)이 끝에 3차 글자 링크 하나를 가질 수 있게(`blockedLink?: (row) => { label; href; newTab } | null`)와 info 톤 정보 줄 하나(`noteReason?: (row) => string | null`, `--text-muted`)를 더한다 — 한 행 아래 줄은 하나(막힘 > 정보). V5의 링크 꼬리 · 담김 줄이 쓴다. ② `PickDialog`의 `noun`에 `"지급처"` 값을 더한다(`pickEmptyText`의 조사 규칙은 이미 `거래처`와 같은 쪽). 이유: 새 컴포넌트 없이 V5 · V12를 부품 규칙으로 흡수한다(화면 하나만의 예외 금지).

### SP-65-6. §6-3 「제출 뒤 문서 화면」 예시 글자 — D-6520 (개정 4판)
SYSTEM §6-3 「제출 뒤 문서 화면」 줄의 예시 두 곳을 바꾼다. 「지출결의: `증빙 확인` → `지급 완료` → 없음」은 「지출결의: `공급가액과 같음` → `지급 완료` → 없음」으로, 「① … (증빙 금액 → `증빙 확인`, …)」는 「(공급가액 고침 칸 → `공급가액 고쳐 확인`, …)」로 고친다. 규칙(1차 하나 · 칸이 1차의 입력이면 1차가 값과 행동을 함께 저장)은 그대로이고 예시 글자만 바뀐다. 이유: D-6520으로 `증빙 금액` 칸이 없어져 SYSTEM 예시가 화면과 갈린다. §8 규칙 7 용어표의 `증빙 확인`은 그대로다(확인하러 가는 행동 · 섹션 이름). 새 토큰 · 부품 0.
