# Phase 06.5 — UI Design Contract (06 후속 · 지급 파일 · 계좌 · 카드 번호 · 작은 결함)

> Visual and interaction contract. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **기준 = `docs/design/SYSTEM.md` · `docs/design/tokens.css` · `ui/` (로컬 작업 트리).** 이 문서는 새 색 · 서체 · radius · 그림자 · 간격 · 토큰을 **만들지 않는다(0개)**. 새 컴포넌트도 0개다 — 아래 11개 표면은 전부 기존 `ui/` 부품과 기존 화면 파일의 변경이다.

> 결정 번호는 `06.5-CONTEXT.md`의 D-6501~D-6516을 그대로 쓴다. 문구는 SYSTEM §8(명사형 · 「원인 · 다음 행동」 · 높임말 종결 금지)과 `.claude/rules/frontend.md` 「화면 사용성 원칙」(안내 문구 최소 · 사용자 결정 최소 · 주 버튼 하나 · 폼은 옆 패널)을 따른다.
> 이 페이즈는 **새 기능이 아니라 06 화면에 얹는 작은 변경 11건**이다. 새 문구는 아래 「Copywriting Contract」에 전부 모았다 — 거기 없는 문구는 만들지 않는다.

### V1. 지출결의 목록 검색칸 (D-6508)

```
PC ≥1024
│ 지출결의                                                                              │
│ 검색 [______________]  상태 [지급 대상 ▾] 팀 [전체 ▾] 증빙 [증빙 전체 ▾]   [지급 완료 5] │
│    합계 (지급 대상 · 3건)     지급 총액 12,400,000                                      │

폰 (<700)
│ 검색 [______________________________] │ ← 전폭, DOM 첫째
│ 상태 [진행 중 ▾]                       │
```

| 항목 | 계약 |
|---|---|
| 위치 · 순서 | 필터 줄 **맨 앞**(PC 왼쪽 끝 · 폰 맨 위 전폭). DOM 순서 = 시각 순서(SYSTEM §10) — CSS `order`로 바꾸지 않고 폰용 칸을 따로 그리지 않는다(칸 하나, `flex-wrap`이 폰에서 줄을 나눈다). 왜 맨 앞 — 경영관리가 통장 내역과 번호 · 지급처로 건을 맞출 때 가장 먼저 쓰는 도구(G20 근거) |
| 모양 | 라벨 `검색`(`--text-aux` `--text-muted`, 칸 위) + 텍스트 입력(`--control-h` PC · 폰 40, `1px --border-control`, `--text-body`). 기존 프로젝트 필터 검색 칸(`projects.module.css` `textInput`)과 같은 모양 · 폭 규칙 재사용. 자리표시자 없음(§7-2: 형식 예만, 설명 금지) |
| 제출 | **Enter 와 blur(값이 바뀐 때만)**. 타이핑 중 매 글자 제출 없음. 제출은 같은 GET 폼으로 `?q=` 를 싣고 `page`는 싣지 않는다(1쪽). 앞뒤 공백은 서버가 뗀다. 다른 select를 바꿔도 `q`는 남는다(같은 폼이라 함께 제출) |
| 검색 대상 | **화면에 보이는 문자 열만**: 번호 · 프로젝트 · 항목(내용) · 거래처 · 기안 — 보는 사람에게 서버가 빼는 열은 검색 대상에서도 뺀다(정보 노출표 — 숨은 열을 검색으로 추측하는 길 차단). 대상 목록을 화면에 적지 않는다(안내 문구 없음) |
| 합계 | 필터 전체 기준(§6-1) — 검색도 필터다. 합계 줄 제목은 그대로(`합계 ({보기} · {N}건)`), N과 금액이 검색 결과를 따른다. 검색어를 합계 줄에 되풀이하지 않는다(입력 칸이 이미 보인다) |
| 0건 | 문서는 있는데 검색 · 필터로 0건: 표 자리 `ListEmpty` — 메시지 `조건에 맞는 건이 없습니다`(S1이 이미 쓰는 문구) + 2차 `필터 지우기`(같은 보기로 `q` · 팀 · 증빙을 지운 주소). 문서가 아예 없을 때의 기존 EMPTY(`등록된 지출결의가 없습니다`)와 섞지 않는다 — `list.hasAny`가 가른다. **검색칸은 문서가 하나도 없으면 그리지 않는다**(기존 `list.hasAny` 규칙 — 거를 것이 없는 필터는 숨긴다) |

| 선택 · 입력 보존 | 지급 대상 보기의 고른 행 · 이체액 편집은 필터를 바꾸면 비운다(S1 기존 규칙)에 **검색도 포함**한다 |
| 키보드 | `Tab`으로 닿고 `Enter` 제출, `Esc` 동작 없음(브라우저 기본). 단축키 없음 |

`admin/people/[id]` 페이지(`DetailScreen`)에 **섹션 하나**를 더한다. 읽기는 섹션 안 `KvList`, 입력은 **옆 패널**(폼은 옆 패널 — SYSTEM §6-3 · §7-8; 입력칸 3개 + 체크 1개는 사람 상세의 입사일처럼 칸마다 blur 저장하면 「은행+계좌번호 → 예금주」가 중간 상태로 저장되므로 한 번에 저장하는 패널로 한다).

```
┌ 지급 계좌 ───────────────────────────────────────── ┐ ← DetailScreen.Section (위 1px --border-row)
│ 은행        신한                                    │
│ 예금주      김OO                                    │
│ 계좌번호    ****-**-1234   번호 보기                │ ← AccountNumberCell 모양(거래처와 같은 노출)
│ 계좌 바꾸기                                         │ ← 3차(없으면 `계좌 적기`)
└──────────────────────────────────────────────────── ┘
```

| 항목 | 계약 |
|---|---|
| 자리 | 계급 변경(`PersonRoleChange`)과 연차 섹션 사이가 아니라 **연차 섹션 아래 · 소속 발령 이력 위**(돈 칸은 가장 덜 쓰는 자리, 발령 이력 표는 전폭 표라 맨 아래 유지). `.single-column`(720) 안 |
| 노출 | **섹션 자체를 그리지 않는다**: 지급 계좌 권한이 없는 모든 사람(직원 본인 포함 — 자기 상세 · `/account` 어디에도 이 칸 없음). 권한이 없다는 사실을 문구로 알리지 않는다(거래처 계좌 `canReveal` 선례). 게이트 정의는 열린 항목 OI-1 |
| 읽기 목록 | `KvList` 3행: `은행` · `예금주` · `계좌번호`. 값이 없으면 `—`(SYSTEM §2-4). 계좌번호는 서버가 만든 마스킹 문자열(`{은행} ****-**-{뒤4}` 꼴이 아니라 거래처와 같은 `maskTail4` 결과) — 평문은 마스킹 해제 권한자가 `번호 보기`(3차)를 눌러야 보이고 `가리기`로 되돌린다. 해제 호출은 매번 기록되므로 `가리기`는 서버를 다시 부르지 않는다(거래처 `AccountNumberCell`과 같은 동작). 실패 줄 `번호 불러오기 실패 · 다시 시도`(기존 문구) |
| 3차 | 값이 하나도 없으면 `계좌 적기`, 하나라도 있으면 `계좌 바꾸기`. 누르면 같은 페이지 `?editAccount=1`(URL 토글, D-39) → 옆 패널. 폰에서도 보인다(권한자가 폰에서 고칠 수 있다 — 터치 `--touch-min` 44) |
| 패널 | `SidePanel` 제목 `지급 계좌 수정` · `PanelForm intent="edit"` · 1차 `계좌 저장`(+ `Ctrl+Enter`) · 2차 `취소 Esc`. 칸은 거래처 폼(`vendor-form.tsx`)과 **같은 이름 · 같은 순서**: `계좌 은행`(TextField) · `예금주`(TextField) · `새 계좌번호`(TextField, `autoComplete="off"`) + 아래 힌트 `현재 {마스킹}` 또는 `등록된 계좌번호 없음` + 체크 `계좌번호 지우기`(번호가 있을 때만). 새 필드 종류 0 |
| 검증 | 예금주 필수 = V3와 **같은 조건 · 같은 문구**(은행과 계좌번호가 둘 다 있으면 예금주 필요). 칸 오류는 칸 아래, 요약은 1차 옆(`PanelForm` `reason`) |
| 저장 뒤 | 패널이 닫히고 포커스는 연 요소(`계좌 바꾸기`)로 돌아간다(PanelForm 기존 동작). 토스트 없음. 섹션 값이 서버 값으로 바뀐다 |
| 다섯 상태 | LOADING: 페이지가 서버 렌더라 별도 뼈대 없음(`PersonDetail` 기존). EMPTY: `—` 3행 + `계좌 적기`. ERROR: 기존 `app/(app)/error.tsx`. SUCCESS: 패널 닫힘. PARTIAL: 일부 칸만 값이 있으면 있는 칸만 값, 나머지 `—` |

### V3. 거래처 폼 예금주 필수 오류 (D-6506)

`vendor-form.tsx`(옆 패널)의 `예금주` 칸에 서버 검사 오류를 단다. **필수 표시(`*`)를 두지 않는다**(SYSTEM §7-2 — 필수인데 비면 제출이 이유를 말한다).

| 항목 | 계약 |
|---|---|
| 조건 | 은행과 계좌번호가 **둘 다 있을 때**만 예금주 필요(옛 CHECK와 같은 조건). 수정 모드에서 `새 계좌번호`를 비우고 저장된 번호가 있으면 「번호 있음」으로 센다 |
| 칸 오류 | `예금주` `TextField`의 `error` prop → 입력 테두리 `--status-danger` 1px + 칸 아래 `--text-aux --status-danger` 한 줄 `예금주 없음 · 예금주 적기`. 입력값은 지우지 않는다. 오류가 뜨면 포커스를 `예금주` 칸으로 보낸다(`firstErrorId`) |
| 요약 | 기존 `fieldErrorsReason` 그대로: 등록 `등록할 수 없음 — 예금주 1칸 · ` + 3차 `예금주 고치기`, 수정은 `수정할 수 없음 — …`. 다른 칸 오류와 함께 있으면 칸 순서대로 이어 붙는다 |
| 클라이언트 | 서버 검사가 정본이다. 클라이언트에서 미리 막지 않는다(제출 뒤 오류로 충분 — 사용자 결정 최소) |
| 기존 데이터 | 예금주 없이 계좌가 있는 거래처는 수정 저장 때 이 오류를 처음 만난다 — 그때 예금주를 적게 하는 것이 의도. 별도 안내 없음 |

### V4. 지출결의 제출 막힘 「지급처 계좌 없음」 (D-6507)

기존 제출 막힘 사슬(`firstExpenseSubmitBlock`, ①~⑨ 첫 막힘 하나)에 **단계 하나**를 더한다. 새 컴포넌트 없음 — `BlockLine`이 1차 옆에 이유를 그린다.

| 항목 | 계약 |
|---|---|
| 언제 | 지급 방식이 계좌이체이고 지급처(거래처 · 직원)에 쓸 수 있는 계좌가 없을 때. 현금 · 법인카드는 막지 않는다 |
| 사슬 자리 | `쓰지 않는 지급 방식`(지급 방식 비활성) 단계 **바로 뒤** · `공급가액이 0` 앞. 거래처 · 지급 방식이 정해진 뒤에야 판정할 수 있어서다 |
| 문구 | `지급처 계좌 없음 · 계좌 등록은 경영관리` — 「원인 · 다음 행동」, 다음 한 수가 제출자(기안자)의 권한 밖이므로 **버튼을 세우지 않고 담당을 적는다**(SYSTEM §8 규칙 3). `target`은 null(3차 버튼 없음) |
| 경고가 아니라 막기 | 1차 `지출결의 제출`은 `aria-disabled` + 이 문장이 `aria-describedby`로 붙는다(§10). 임시 저장 · 증빙 올리기는 막지 않는다 |
| 풀리는 길 | 지급 방식을 바꾸거나 거래처를 바꾸면 사슬이 다시 돌아 풀린다. 경영관리가 거래처 · 직원 계좌를 채우고 기안자가 문서를 다시 열면 풀린다 |
| 직원 지급 건 | 같은 문장 · 같은 자리(D-6505 칸이 비면 같은 단계가 막는다) |

### V5. 지급 대상 「이체 파일 받기」 + 막힌 건 (D-6504, 신한 대량이체 xlsx)

`payment-targets-table.tsx`의 `filters` 슬롯에 2차 버튼 하나와 결과 글자를 더한다. **화면의 1차는 계속 `지급 완료 N` 하나다.**

```
│ 지출결의                                                                                       │
│ 검색 [____] 상태 [지급 대상 ▾] 팀 [전체 ▾] 증빙 [증빙 전체 ▾]  [이체 파일 받기]  14:05 이체 파일 5건 · 막힘 2건     [지급 완료 5 Ctrl+Enter] │
```

| 항목 | 계약 |
|---|---|
| 자리 | 필터 select들 **바로 뒤 · 결과 글자 앞**(`ExportButton`이 필터 줄에 선 선례와 같은 모양, 결과 글자는 1차와 떨어진 자리 — S1 M-2). 2차 `variant="secondary"` |

| 대상 | **지금 고른 행**(모든 쪽 — 선택은 쪽을 넘어 기억된다). 필터를 바꾸면 선택이 비므로 파일도 비운 상태에서 시작한다 |

| 누르면 | 확인 창 없음. 버튼이 `…` 진행 중(`pending`) → 응답이 오면 **브라우저 다운로드**(Blob, `ExportButton`과 같은 방식) + 결과 글자. 선택 · 이체액 편집 · 사유는 그대로 남는다(받은 뒤 `지급 완료 N`으로 이어 가는 흐름) |

| 막힌 건 | 파일에서 뺀 행은 **자리를 지키고** 행 아래 한 줄 `--text-aux --status-danger` 이유가 선다(S1 막힌 행 줄과 같은 모양). 파일 제외 사유일 뿐 **지급 게이트가 아니므로 선택은 그대로 남는다**(계좌 없이 다른 방법으로 지급하는 건이 `지급 완료 N`에 들어갈 수 있다 — S1 M-7). 이유 문구는 아래 Copywriting 「막힌 건 이유」 |
| 실패 | 서버 오류 · 응답 없음: 오류 토스트 `이체 파일 받기 · 실패 · 다시 시도`(닫을 때까지). 선택 · 편집은 그대로 |
| 노출 | 평문 계좌가 파일에 들어가므로 **마스킹 해제 권한이 있는 지급 권한자에게만 버튼을 그린다**. 없는 사람은 버튼 · 이유 글자 둘 다 없다(할 수 없는 일에는 문구를 더하지 않는다 — §8 규칙 5). 게이트 정의는 OI-2 |

### SP-65-1. §7-15 `Form` — 폼 안 `KvList`는 묶음으로 취급해 위 1px `--border-row`
구현은 `ui/form/Form.module.css` 한 규칙(V10). 이유: SYSTEM §7-15 · §3(`폼: 묶음 사이 24px + 1px 선`)가 이미 선을 요구하는데 부품에 없어 연차 신청 폼 4폭이 모두 어긋난다(06.3-03 design-review). 화면 하나만의 선택지(`leave-form.tsx`에 `<hr>`)는 CLAUDE.md §6이 금지한다.

### SP-65-2. §6-1 목록 필터 줄 구성 한 줄
「필터 줄 = 검색 칸(있으면 맨 앞) → 선택 칸들 → 2차 `파일 받기` 버튼(편집 폭에서만) → 결과 글자, 오른쪽 끝에 1차」. 이유: V1 · V5가 이미 프로젝트 목록 · 행동 로그 · 지급 대상에서 따로 굳은 배치를 명문화한다. 새 부품 · 새 토큰 없음.
