## 플래그된 가정

- **D-743(확정 — 아침 카드 10-4):** 「퇴직일 지나면」 = `resignationDate < 오늘(KST)` — 퇴직일 당일까지 로그인 가능. KST 오늘은 기존 `toKstDate(now)`(`domain/holidays/business-day.ts:30`)로, 비교는 `YYYY-MM-DD` 문자열끼리. 코드베이스의 다른 퇴직 경계(예: `domain/expenses/index.ts:230`의 `<=` — 결재 후보 판정)는 뜻이 달라 건드리지 않는다(A-P3-7).
- **FA-1(이 플랜 몫 — F1 해법, A-P2-5 · A-P2-6으로 확정):** 잠금 키는 기존 `lockLoginEmail`(`hashtextextended('login_attempts:' + email, 0)`) 하나만 쓴다 — 새 도우미 없음. 전역 db 읽기(`lockoutConfig` · `findUserByEmail`)는 트랜잭션 **전에** 끝낸다(eng E5).
  - before(`reserveLoginAttempt`): tx { `lockLoginEmail` → `countOpenFailures` → 임계 이상이면 아래 「잠금 기록 확인」 뒤 잠금 거부(403 `lockedMessage`) → 아니면 실패 행을 **미리** 기록 }.
  - after 실패(`settleLoginFailure`): tx { `lockLoginEmail` → 다시 세기(미리 기록한 행 포함 — `count+1` 셈 없음) → 임계 미만이면 끝(기존 401) → 임계 이상이면 「잠금 기록 확인」 → 응답을 잠금 문구 403으로(ISSUE-002) }.
  - after 성공: 기존대로 성공 행 기록 + 열린 실패 해소(미리 기록한 행 포함, 사유 `success`). 실패 이력 화면은 없다(읽는 곳은 `repositories/login-attempts.ts`뿐).
  - 「잠금 기록 확인」(공용 tx 함수 한 곳): 지금 열린 실패 중 가장 이른 시각 이후에 같은 이메일의 `account_lock`이 없을 때만 `account_lock` 한 행(`repositories/action-log.ts`에 tx 조회 하나 — `detail.email` · `occurred_at`). 「창 시작 이후」가 아니라 「열린 실패의 처음 이후」로 보는 이유: 관리자가 풀고 같은 창 안에서 다시 잠기면 새 행이 있어야 한다. before에서도 부르는 이유: after의 잠금 기록이 실패해 롤백돼도(행은 before에서 이미 커밋) 다음 시도가 잠금 기록을 채워 「잠겼는데 기록 0건」이 한 시도 이상 이어지지 않는다(D-712).
  - 기존 `recordLoginFailure(email, ip, deps)`는 서명 · 뜻(실패 행 기록 + 잠금 기록이 한 tx) 그대로 두고 내부만 공용 함수로 — 시험(`action-log.test.ts` · `account-cli.test.ts`)이 직접 부른다.
  - better-auth 훅 경로상 after가 응답을 403으로 바꾸지 못하거나 after가 돌지 않는 실패 갈래가 있으면 멈추고 SUMMARY에(systematic-debugging) — 우회 구현 금지.
  - 알려진 대가(부록 NA:421): 동시 시도 중 맞는 비밀번호도 다른 시도의 미리 기록 행 때문에 잠깐 「잠김」을 볼 수 있다(그 시도가 성공하면 곧 풀림) — SUMMARY 한 줄.
- 비밀번호 초기화의 잠금 해소 사유는 `admin_reset`(기존 `admin_unlock`과 구분) — `resolved_reason`은 CHECK 없는 text 칸(`db/schema/login-attempts.ts:15`)이라 `resolveOpenFailures`의 사유 유니언에 `"admin_reset"`만 더한다(스키마 변경 없음).
