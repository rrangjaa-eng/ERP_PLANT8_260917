### Recommended Project Structure
기존 구조 유지. 신규 파일은 시험(`test/unit/**`, `test/integration/**`, `test/e2e/**`)과 `docs/design/checks/<날짜>-<작업>.md`, 플랜의 「사람 확인 목록」 절뿐이다.

### Pattern 1: 도메인 순수 판정 + DTO (경과일·지급 문구)
**What:** 날짜·문구 판정은 도메인 순수 함수로 만들고 단위 시험을 먼저 쓴다. 화면은 DTO 필드만 그린다.
**When to use:** PD2 문구 분기, PD4 경과일(D-721 `domain/notify/kinds/orphan-evidence.ts`와 판정 공유).

### Pattern 2: 로그 종류 추가는 코드만
**What:** 새 종류는 `domain/action-log/record.ts`의 CORE 목록(~:55)·라벨(~:110)·ALWAYS_ON(~:159)과 `test/unit/action-log/record.test.ts`만 건드린다. 마이그레이션 없음 [VERIFIED 이전 조사: record.ts 구조 Read].
**Example (수정 대상 현재 모양):**
```typescript
// domain/evidence-records/amount.ts:214-221 (HEAD, 이전 Read) — 이미 로그를 남기지만 droppable 종류
//   document_update, detail: { change: "evidence_record_needs_check_clear", needsCheck: row.needsCheck }
// PX1은 이를 전용 always-on 종류로 승격하는 일이다.
```

### Pattern 3: 위험·돈 변경은 별도 PR/플랜
위험 경로(훅 정규식)는 플랜 분리 + 사용자 머지. 돈 경로는 `risk:` + Opus 실행자 + 독립 검토 1명 + `/cso`.

### Anti-Patterns to Avoid
- **존재하지 않는 파일 가정:** `domain/evidence-records/list.ts`는 없다(PE5). 로직은 `index.ts` `withAttachFacts`.
- **정렬 점수로 필터 대신하기:** C-92는 점수를 낮추는 게 아니라 후보 집합에서 빼야 한다.
- **문구만 바꾸는 척 하기:** PD2는 `EvidenceGateInput`에 완료 여부가 없어 문구 하나로 끝나지 않는다.
- **클라이언트 숨김만으로 C-91 끝내기:** 서버가 증빙 날짜를 쓰도록 `tax.ts` 쪽도 바꿔야 한다.

## Common Pitfalls

### P-1: 존재하지 않는 `domain/evidence-records/list.ts` (PE5, D-7105)
**What goes wrong:** 플랜이 이 파일을 열라고 적으면 첫 태스크에서 막힌다.
**How to avoid:** 위치는 `domain/evidence-records/index.ts`의 `withAttachFacts`(~:347-352). 이미 `actionBlockedReason`을 그리는 `evidence-table.tsx:796-826`을 재사용.
**Warning signs:** `Glob domain/evidence-records/list.ts` 0건.

### P-2: PE3 대상 코드를 `reconcile.ts:41-56`으로 잘못 짚음 (D-7104)
**What goes wrong:** 그 줄(`stepOneHit`/`stepTwoHit`)은 이미 `usedOn` 같음을 요구하는 자동 대사다. 사용일이 덮이지 않는 곳은 **수동·완화 붙임**(`isRelaxedHit` :174-177, `attachToCardUsage`, `applyFileWins`).
**How to avoid:** 덮기 로직은 `fileWinsPatch`/`applyFileWins`에 `usedOn`을 더하고, 부가세 분리(`cardOverwriteSplit`)가 새 사용일을 기준일로 쓰는지 시험으로 고정. `CHANGE_FIELD_LABELS`에 `usedOn`·`totalKrw` 추가.

### P-3: PD2는 문구 하나가 아니다 (D-7101)
**What goes wrong:** `action-row.ts:96`을 통째로 「증빙 없음 · 경영관리 등록」으로 바꾸면 **완료 전 프로젝트에서 기안자가 올릴 수 있는데도** 틀린 안내가 나간다.
**Why:** `EvidenceGateInput`에 완료 플래그가 없어 같은 줄이 두 상황을 못 가른다. 실제 판정은 `domain/evidence/index.ts:233`.
**How to avoid:** 입력 타입에 불리언(예: 기안자가 올릴 수 있는지)을 더해 `evidenceGateInputs`(`domain/evidence-reviews/index.ts:120-131`)에서 계산해 넘기고, 고정 시험(`payment-batch.test.ts:220,485-493`, `evidence-presence.test.ts:271`)을 두 갈래로 갱신. `action-row.ts`는 순수 함수로 유지.

### P-4: UI-SPEC의 「보는 사람 권한별 분기」 주장은 코드가 뒷받침하지 않음 (PD2)
**What goes wrong:** UI-SPEC가 경영관리에게는 `증빙 올리기`가 보인다고 쓰나, 문구의 유일한 원천은 `evidenceGateDecision`이고 지급 행은 `canPay` 사용자에게만 보인다. 분기 코드는 없다.
**How to avoid:** D-7101(고정 문구)을 따르고 UI-SPEC의 권한별 분기는 구현하지 않는다(필요하면 discuss에서 사용자 확인).

### P-5: PX1이 「로그 없음」이라는 전제는 틀림 (D-7115)
**What goes wrong:** 새로 로그를 만들면 `amount.ts:214-221`의 기존 `document_update` 로그와 이중 기록된다.
**How to avoid:** 기존 호출을 **새 always-on 종류로 교체**하고 `record.test.ts`의 종류 목록·라벨 완결성 시험(`test/unit/action-registry-completeness.test.ts` 계열)을 갱신.

### P-6: PE7의 「격리 해제가 완료 신호」는 틀림
**What goes wrong:** `EVIDENCE_WIPE_SPECS` 등록은 증빙 표 삭제·단독 워커 때문이다. 해제하면 병렬 실행 중 다른 스펙의 데이터를 지운다.
**How to avoid:** W20의 완료 신호를 「`expect.soft` S8이 hard로 통과하고 `CI=true`에서 안정」으로 바꾸고 격리는 유지.

### P-7: PE8은 이미 절반이 있다
**What goes wrong:** 표시(붙은 원거래의 번호 링크·`취소 줄 등록됨 · 원거래 확인`)를 다시 만든다.
**How to avoid:** 남은 것만: 재시도, 로그를 `released` 여부와 무관하게 남기기, 결재 인스턴스 version 정책 결정(현재 의도적으로 안 올림 — 바꾸려면 근거를 DECISIONS에), 지급 뒤 처리. UI-SPEC U-16과 `COPY.draftOwner` 충돌은 discuss/UI 단계에서 확정.

### P-8: C-90은 스키마를 요구할 수 있다
**What goes wrong:** 「팀 없는 사람 갈래만 추가」로 시작하면 사람의 본부를 알 방법이 없다(`team_memberships`는 팀 전용). 설정의 본부(`readDivision`)로 대체하면 **팀 없는 모든 사용자**에게 본부 공개 증빙이 열린다.
**How to avoid:** Q1을 사용자에게 먼저 묻고, 결정 전에는 비권한부(C-80)만 진행.

### P-9: CONTEXT의 PR 겹침 범위가 넓다
**What goes wrong:** PF4·C-91에 불필요하게 #296 의존을 걸어 웨이브가 늦어진다.
**How to avoid:** `domain/expenses/index.ts`를 안 건드리면 의존 없음을 `depends_on` 근거로 적는다. 반대로 SYSTEM.md :843·:862(SP-71-1)는 #296 :845-852와 충돌할 가능성이 높아 그 PR 뒤에.

### P-10: S7 DELETE 목록이 CONTEXT보다 하나 많다
`repositories/privacy-session-activity.ts:46` (`db.delete(sessions)`)가 CONTEXT 7곳 밖이다. 허용 목록에 이유와 함께 넣거나 가드 시험이 첫 실행부터 실패한다.

### P-11: 화면 완료는 CI=true
로컬 dev 통과는 완료 신호가 아니다. `CI=true pnpm test:e2e test/e2e/<spec>`로만 판정. 이 환경에는 Playwright 브라우저가 없어(아래) 화면 판정은 CI 또는 브라우저 설치가 필요하다.
