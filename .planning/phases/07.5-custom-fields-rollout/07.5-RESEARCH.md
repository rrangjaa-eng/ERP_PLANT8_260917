## Summary

04.5의 기계(정의 저장·관리 화면·보관·노출표 자동 등록·칸별 판정·값 보존)는 이미 `entity` 문자열을 받는 모양이라 **대상 일반화 자체는 얕다** — 상수 한 줄과 `admin.ts`의 `FIELD_ENTITY` 한 곳, 거래처 전용으로 박힌 `readVendorFieldAccess` 한 곳이 전부다. 보관함·노출표 열·허용 키 검사·계급 생성 부여는 이미 `FIELD_DEFINITION_TARGETS`를 순회하므로 상수에 두 값을 더하면 따라온다. 스키마(`custom_fields` + GIN)도 이미 있어 **마이그레이션 0건**이다 (0048이 마지막, 0049/0050/0051은 07.3·07.2가 예약).

**CONTEXT가 짐작한 것보다 일이 큰 곳이 셋 있다.** (1) **프로젝트에는 기본 칸을 고치는 「수정」 경로가 아직 없다** — `updateProject`는 없고(`domain/projects/index.ts:78` 주석만), 기간·PO 금액·PO 번호는 `saveProjectLedger`(견적 표 `QuoteLedger`의 「정보 면」 고치기)로 저장한다. D-7505의 「수정 경로」는 07.2-17이 만드는 `saveProjectLedger.info`(`applyInfoChange`, `projects.version` 낙관적 잠금) 위에 얹는 일이므로 **07.2-17 뒤**다. `createProjectAction` 스키마(`app/(app)/projects/actions.ts:52-77`)에도 `customFields`가 없다. (2) **견적 줄 저장은 갱신 때 `custom_fields`를 쓰지 않는다** — 행 입력 zod(`quoteLineRowInputSchema`, lines.ts:703-740)에 `customFields` 키가 없어 값이 벗겨지고, 갱신 SQL(`repositories/quote-lines.ts:275-296`)의 `set` 목록에도 없다. 게다가 `lines.ts:1221`은 모든 줄에 `customFieldsSchema.parse(row.customFields ?? {})`를 걸어 **필수 칸이 하나만 생겨도 모든 줄 저장이 던진다**(D-7503이 막으려는 바로 그 상황). (3) **프로젝트 목록 DTO·목록 행에는 `customFields`가 아예 없다**(`PROJECT_LIST_DTO_SPEC` domain/projects/index.ts:206-226, `ProjectListRow` repositories/projects.ts) — 열을 그리려면 SQL select부터 더한다.

**D-7511에는 기록된 사용자 결정과 충돌하는 부분이 있다.** 260907 대조 노트에 2026-10-07 11:49 KST 「G6 목록 내려받기 = 증빙·거래처만」, 「프로젝트·견적 목록은 안 함」이 사용자 결정으로 남아 있다(`260907-full-inventory/decisions.md:8`, `gap-verdicts.md:58`). 2026-11-04 카드가 이를 뒤집는지는 답을 받아야 안다. 권장: **카드 답 전 기본값을 「새로 만듦」이 아니라 「거래처 CSV 열만 더하고 프로젝트 내보내기 플랜은 보류」로 두고 사용자에게 한 번 확인.**

**Primary recommendation:** 거래처 모양(`resolveCustomFieldsWrite` + `visibleCustomFieldKeys` + `pickVisibleCustomFields` + `readVendorFieldAccess`)을 `entity`·`valueInfoItem` 인자를 받는 한 벌로 일반화하고, `FIELD_DEFINITION_TARGETS`에 `project`·`quote_line`을 더하는 한 줄은 **맨 마지막 플랜**(폼·표·목록·노출 출구가 모두 들어온 뒤)에 둔다. 07.2와 안 겹치는 일(일반화·관리 화면 대상 고르기·공용 입력 컴포넌트·거래처 목록/검색/내보내기·프로젝트 등록 폼)을 앞 웨이브로, 견적 표·프로젝트 상세 정보 면·프로젝트 목록 SQL은 07.2-14/17 뒤로 보낸다.

### Pattern 1: 거래처 → 일반 접근 판정 (핵심 일반화)
**What:** `readVendorFieldAccess`(repositories/permissions.ts:235-265)는 `eq(fieldDefinitions.entity, VENDOR_TARGET)`·`"vendor.value"`가 박혀 있다. `entity`·`valueInfoItem`을 인자로 받는 `readCustomFieldAccess`로 올리고 vendor는 얇은 래퍼로 남긴다(거래처 테스트 무수정).
**주의(검증된 사실):** 프로젝트·견적 줄의 바깥 문은 둘 다 `project.value`다 — 견적 줄 DTO의 `customFields`도 `infoItem: "project.value"` ([VERIFIED: domain/quotes/lines.ts:253] `{ key: "customFields", from: "customFields", infoItem: "project.value" }`). 견적 줄 가시성은 **보는 사람 자신의 계급**(`viewer.roleId`)으로 판정한다 — 프로젝트별 계급이 없다(`projectLines(viewer, …)` lines.ts:~397).
**Example (vendor 패턴, 그대로 복제할 모양):**
```typescript
// Source: domain/vendors/index.ts:223-229 (VERIFIED, 이 세션에 읽음)
async function toVendorDto(viewer: Viewer, row: VendorRow, visibleKeys: ReadonlySet<string>): Promise<VendorDto> {
  const dto = (await project(viewer, row, VENDOR_DTO_SPEC)) as VendorDto;
  if (dto.customFields === undefined) return dto;
  return { ...dto, customFields: pickVisibleCustomFields(dto.customFields, visibleKeys) ?? {} };
}
```

### Pattern 2: DTO 레지스트리는 정적으로 둔다
`DTO_REGISTRY`의 `customFields`는 `project.value`로 **그대로 둔다**. 누수 스캔 DTO 축이 `INFO_ITEMS.some(item.key === infoItem)`을 요구하므로(leak-scan.test.ts:191-195) 레지스트리에 `cf.*`를 넣으면 깨진다. 칸별 판정은 거래처처럼 출구 뒤 거름 + **별도 동적 축 테스트**로 증명한다(leak-scan.test.ts:415-480 거래처 블록이 모델).

### Pattern 3: 견적 줄 칸 수정 권한 = `note`와 같게 (권장, [ASSUMED])
`QuoteLineField`(edit-scope.ts:16-25)에 `customFields`를 **더하지 않는다** — `FIELD_COLUMNS`·`CELL_LABELS`·`lineChangeView`·게이트 규칙(`domain/rules/register.ts:63`)·07.2-06이 같은 목록을 고치는 중이라 충돌·파급이 크다. 대신 추가 칸이 바뀐 줄은 기존 `gate(projectRow, LINE_EDIT_RULE, … fields: ["note"])`로 판정하고, 화면 셀 편집 가능성도 DTO의 `cellEditability.note`를 따른다(완료·정산 중 잠김, 조정 줄은 `projects.adjustment` 보유자만 — edit-scope.ts:35,53-72).

### Anti-Patterns to Avoid
- **`required` 필수 칸을 폼·표가 안 보내는 상태로 대상 켜기** — 기존 `validatedCustomFields`(projects/index.ts:153-166)와 lines.ts:1221은 viewer가 못 보는 칸·보관 칸까지 **모든 정의**로 검증한다. 일반화 후에는 입력 칸(보이는 활성 칸)만 판정.
- **검색에 `custom_fields::text ilike`** — 숨은 칸 값·키 이름이 맞는다.
- **`DTO_REGISTRY`에 동적 `cf.*` 등록.**
- **`QUOTE_LINE_FIELDS`에 `customFields` 추가**(위 Pattern 3).
- **행동 로그 `detail`에 추가 칸 값 싣기** — `lineChangeView`(lines.ts:916)·`buildChanges`는 값을 로그로 옮긴다. 노출표가 꺼진 칸 값이 `action_log.detail` 권한자에게 새므로 값 대신 바뀐 칸 수/키만 기록하거나 아예 제외 [ASSUMED 설계 권고].

## 3. 쓰기 경로

### 3-1 프로젝트 등록 (겹침 없음)
- `validatedCustomFields`(projects/index.ts:153-166, 호출 :646)는 **모든 정의**(보관·못 보는 칸 포함)로 `buildCustomFieldsSchema(...).parse(input ?? {})` — 필수 칸이 하나 생기면 등록이 막힘. `resolveCustomFieldsWrite({mode:"create", inputDefs, knownKeys, stored:{}, submitted})`로 교체하고 입력 칸 집합은 `readCustomFieldAccess(viewer, viewer.roleId, {entity:"project", valueInfoItem:"project.value"})`. 프로젝트 등록은 번호 부여 tx(:665 `withTransaction`) 전에 검증하므로 vendor의 「잠금 뒤 tx 읽기」(T-04.5-44)와 달리 풀 호출이 허용되는 자리 — 단 거래처처럼 tx 안에서 읽어도 된다(tx 인자 지원).
- `createProjectAction` 스키마(actions.ts:52-77)와 호출(:82-92)에 `customFields: z.record(z.string(), z.unknown()).optional()` + `CustomFieldsInvalidError`→`returnValidationErrors(…, { customFields: {key:{_errors:[…]}} })` (vendors/actions.ts:102-104,127 선례).

## 5. 검색

현재: 프로젝트 `ilike(projects.name)`·`number`·`vendors.name` [VERIFIED: repositories/projects.ts:170-173] — 사용자 입력을 `%…%`에 그대로 넣어 `%`·`_` 이스케이프가 없다(기존 동작, 이번 범위 밖 — 새 절에는 거래처처럼 `likeContains` 이스케이프를 쓴다. repositories/vendors.ts:21-23). 거래처 `nameQuery`는 정규화 이름 + 선택적 사업자번호 숫자(vendors.ts:28-37).

**권장 SQL 꼴:** domain이 viewer 기준으로 **검색 대상 text 키 집합**을 계산(`활성 ∧ type==="text" ∧ cf.<entity>.<key> 보임 ∧ 바깥 문(`project.value`/`vendor.value`) 보임`)해 filter에 `customTextKeys: string[]`로 넘기고, repo는 키마다
`or(…, sql`${projects.customFields} ->> ${key} ilike ${pattern}`)`를 더한다(키는 매개변수 바인딩). 같은 `projectFilterConditions`를 쓰는 목록·집계(합계 줄)가 자동으로 같은 행을 본다(T-04-28 주석: 둘이 어긋나면 합계 정보 노출).
- **바깥 문을 반드시 포함** — vendor DTO는 `vendor.value`가 꺼지면 `customFields`가 통째로 사라지는데(`dto.customFields === undefined`) 검색 키 집합이 칸별 문만 보면 「보이지 않는 값으로 행이 걸리는」 누수(검색 결과로 존재·내용 추정)가 생긴다. `vendorInputFieldKeys`가 이미 두 문의 AND를 쓴다(vendors/index.ts:337-339) — 같은 규칙.
- **select 거르개:** `sql`${projects.customFields} @> ${JSON.stringify({[key]: value})}::jsonb``. 값은 해당 칸의 **활성 또는 보관 선택지** 중 하나로 서버가 검증(임의 값 거부는 필수 아님이나 URL 위조 시 빈 결과일 뿐). 보이지 않는 칸·보관 칸의 `cf_<key>` 파라미터는 무시.
- **인덱스(실측, 이 세션 로컬 Postgres temp 테이블 5만 행 + GIN, 롤백):** `->> 'cf_a' ilike '%v123%'` → `Seq Scan`, `custom_fields::text ilike` → `Seq Scan`, `custom_fields @> '{"cf_b":"3"}'` → `Bitmap Index Scan on t_gin` [VERIFIED: psql EXPLAIN]. 즉 GIN은 select 거르개(`@>`)만 돕고 텍스트 키워드 검색은 못 돕는다. 프로젝트는 연 수백~수천 건 규모라 순차 스캔이 허용 범위 — **Issue 13 규칙대로 표현식 인덱스는 만들지 않고**, 검증 단계에서 대표 규모 `EXPLAIN ANALYZE`로 기록만(필요하면 위험 경로 별도 PR).
- **빈 키 집합이면 or 절을 더하지 않는다**(기존 검색 동작 그대로 — 추가 칸 0개인 화면은 SQL도 불변).
- 거래처 검색은 `vendorListQuery`(vendors/index.ts:~246)가 만든 필터에 같은 `customTextKeys`를 더한다. 자동완성 `searchVendors`(이름 정규화 점수)에는 넣지 않는다(용도 다름).
- 대소문자: `ilike`가 처리. 한글 NFC: 저장 텍스트는 `z.string()` 그대로(정규화 안 함) — 검색어를 NFC로 맞춰도 NFD로 입력된 옛 값과는 안 맞을 수 있음(드문 엣지, 문서화만).

## Common Pitfalls

### Pitfall 1: 대상 켜기 순서 (D-7503)
**What goes wrong:** 상수를 먼저 늘리고 관리자가 필수 칸을 만들면 프로젝트 등록·모든 견적 줄 저장이 막힌다(위 §3-3 lines.ts:1221 · §3-1).
**How to avoid:** 상수 변경을 마지막 플랜에. 앞 플랜은 `insertFieldDefinition`+`insertVisibilityIfAbsent`로 심은 정의로 테스트. 마지막 플랜에서 「필수 칸이 있어도 기존 프로젝트 등록·줄 저장이 성공한다(보이는 입력 칸만 판정)」 회귀 테스트.

### Pitfall 2: 검색으로 숨은 칸 값 누수
**What goes wrong:** 검색 키 집합이 칸별 노출만 보고 바깥 문(`project.value`/`vendor.value`)을 안 보면, DTO에선 칸이 안 보이는데 검색에는 걸린다.
**How to avoid:** 키 집합 = 활성 ∧ type text ∧ 칸별 보임 ∧ 바깥 문 보임. 통합 테스트: 끈 계급이 그 값으로 검색해 0건.

### Pitfall 3: 견적 줄 갱신이 custom_fields를 안 쓰고 zod가 벗긴다
**What goes wrong:** UI만 만들면 저장이 조용히 성공하지만 값이 안 남는다(신규 줄만 남음).
**How to avoid:** §3-3의 ①~④를 한 플랜에서. 통합 테스트: 기존 줄 추가 칸 수정 → 저장 → 재조회에 값, `version` 증가, 숨은 키 값 보존.

### Pitfall 4: 노출표 열 이름 충돌
같은 이름의 칸이 거래처·프로젝트·견적 줄에 있으면 격자 열이 구분 안 됨 — `visibility.ts` `customFieldColumns` 라벨에 대상 이름을 붙인다(§1).

### Pitfall 5: 날짜·숫자 모양
`z.coerce.date()` 관대함(§3-4). 폼은 항상 `YYYY-MM-DD`, 표 셀은 엄격 검사, 저장값은 ISO — 읽을 때 `slice(0,10)`. 목록·CSV 열에도 같은 변환.

### Pitfall 6: 공유 E2E DB 오염
추가 칸이 전 계급 보임이면 동시에 도는 다른 스펙의 폼·표 열 수·Tab 순서가 흔들린다. 픽스처의 `onlyRoleId` 설계(fixtures.ts:96-137)를 유지해 전용 계급에만 보임 행을 주고, `afterAll`에서 `archiveE2EFieldDefinitions(PREFIX)`(custom-field-visibility.spec.ts:19-21 선례).

### Pitfall 7: SYSTEM_VIEWER·시드 스크립트
`SYSTEM_VIEWER`는 `roleId: SYSADMIN_ROLE_ID`(domain/viewer.ts)이지만 `cf.*` 보임 행이 칸 생성 때만 생기므로 `insertFieldDefinition`만으로 심은 정의는 입력 칸에서 빠져 값이 조용히 버려진다(테스트에서 흔한 실수). 테스트 픽스처 헬퍼에 「정의 + 보임 행」 쌍 생성을 둔다.

### Pitfall 8: 폰 접힘 vs 읽기
D-7504 「폰 P3」는 폰에서 아예 안 보인다. 현장에서 폰으로 장소·비고를 확인할 수 있어야 하면 P2(접힌 줄)이고 `summary`가 필요 — UI-SPEC 결정.
