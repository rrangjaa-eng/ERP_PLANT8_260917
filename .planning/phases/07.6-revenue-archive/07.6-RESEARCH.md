## Summary

**읽기 쪽은 거의 다 이미 거른다 — 빠진 곳은 정확히 하나다.** `repositories/revenue-entries.ts:15-22` `listRevenueEntriesByProject`가 `archived_at`을 거르지 않는다 (260907 REPORT.md:70 「잠재 결함」 확인). 이 함수가 `listRevenue`(매출 칸 줄 · 합계 · 잔액, domain/revenue/index.ts:233)와 `numberEntryChanges`(로그 순번, :529)를 먹이므로, 줄을 지우는 순간 매출 칸 표와 합계가 지운 줄을 계속 센다. 반면 같은 `listRevenue` 안의 수금 지연은 거른 목록(`listCollectionRows` :41)을 읽어 화면 잔액과 수금 지연이 서로 어긋난다. 거기에 쓰기 쪽 결함이 하나 더 있다: `updateRevenueEntryIfVersionMatches`(:148-179)의 WHERE에 `archived_at is null`이 없어 낡은 화면이 보관된 줄을 고칠 수 있다. 나머지 읽는 곳(프로젝트 목록 발행 합계 · 정산 전 점검 · 수금 지연 알림 후보 · 수금 지연 행 · 계산서 파일 목록)은 이미 `isNull(archivedAt)`이다. **CONTEXT D-7606의 `repositories/notify-sources.ts`는 revenue_entries를 읽지 않는다** — 수금 지연 알림은 `repositories/revenue-entries.ts:49-70`을 `domain/notify/kinds/collection-overdue.ts:10,27`이 부른다.

**쓰기 경로는 지금 없다.** `saveRevenueInTx`(:550-583)는 insert · update만 한다 — 화면에 줄 삭제도 없고(`revenue-section.tsx`에 remove 없음), 서버가 조용히 무시하거나 거부하는 삭제 입력도 없다. 일괄 저장(`saveProjectLedger`)은 dirty 줄만 보내고 `archivedLineIds` 같은 필드는 견적 줄(`domain/quotes/lines.ts:693`)에만 있다. 가장 가까운 선례는 같은 화면 폴더의 **참여자 떼기**(`app/(app)/projects/[id]/members-section.tsx` + `domain/projects/members.ts:304-330`): 행 `삭제`(RowAction danger) → 확인 없이 보관 → 표 위 결과 줄 + 3차 `되돌리기`, 서버는 프로젝트 행을 `FOR UPDATE`로 잠근 뒤 판정, 되돌리기는 **10분 창**. 매출 줄 지우기는 이 꼴을 그대로 따른다.

**마이그레이션은 필요 없다** (칸 · 색인 · 제약 모두 확인). 연결 관계는 둘뿐이다: `revenue_issue_requests.issued_entry_id`(FK, 한 줄에 요청 하나, `issued`는 되돌릴 수 없는 종착 상태)와 계산서 파일(`files.owner_kind='revenue_entry'`, 소프트 참조). 발행 요청에 이어진 발행 줄은 지우면 요청이 「발행됨」인 채 보관된 줄을 가리키는 막다른 상태가 되므로 **막기(PU22 꼴)를 권한다** — 단 사용자 확인 필요(Q1).

**Primary recommendation:** (1) `listRevenueEntriesByProject`와 `updateRevenueEntryIfVersionMatches`에 `archived_at is null`을 먼저 넣고(줄 지우기 전에도 안전한 선행 수정), (2) 별도 모듈 `domain/revenue/archive.ts`에 `archiveRevenueEntry` / `undoRevenueArchive` / `restoreRevenueEntry`를 두어 **프로젝트 행 잠금 → 줄 조건부 UPDATE(version) → 같은 tx 행동 로그** 순서로 구현하고, (3) `ARCHIVABLE_TABLES` + `DOMAIN_RESTORERS`에 `revenue_entry`를 등록하고, (4) 화면은 members-section 꼴(행 행동 열 `삭제` + 표 위 결과 줄 `되돌리기`, 로컬 상태에서 그 줄만 빼고 합계만 서버 값으로 갱신)로, (5) 입금일 미래 막기는 `prepareEntries` 칸 오류(기존 거부 봉투)로 — 이 순서의 플랜 1~2개.

### Pattern 1: 잠금 순서 (프로젝트 → 줄)
**What:** 원장 합성 저장이 프로젝트 행을 먼저 잠그고 줄을 쓴다 (ledger.ts:228 → :437). 지우기 · 되돌리기 · 보관함 복원도 같은 순서.
**Example (골격, 선례 members.ts `inLockedProject` + reserves `restoreReserve`):**
```typescript
// Source: domain/projects/members.ts:inLockedProject · domain/reserves/index.ts:restoreReserve (이 리포)
return withTransaction(async (tx) => {
  const project = await lockProjectForWrite(viewer, projectId, tx);
  if (!project || project.archivedAt !== null) throw new ProjectNotFoundError("존재하지 않는 프로젝트");
  await deps?.afterLock?.();                       // 테스트 경합 훅 (reserves 선례)
  const entry = await findRevenueEntryById(viewer, entryId, tx);
  if (!entry || entry.projectId !== projectId) throw new UserFacingError("줄을 찾을 수 없음 · 새로 고침");
  /* 연결 막기 · 활성 목록 순번 · 조건부 UPDATE(version, archived_at IS NULL) · 0행이면 충돌 문구 */
  await recordAction(viewer, { actionType: "archive", entity: "revenue_entry", entityId: projectId, detail: { entryId, lineChanges } }, { tx });
});
```

### Pattern 2: `ARCHIVABLE_TABLES` 등록 (reserve_entry 꼴)
`setArchived`는 도메인 경로 전용이라 거부(`Promise.reject(new Error("매출 줄 보관 · 복원은 domain/revenue로만"))`, holiday 선례 repositories/archive.ts:254-256), `isProtected() { return true }`, `findById`는 `findRevenueEntryById`, `listArchived`는 프로젝트 번호를 join해 `{ entity:"revenue_entry", label:"매출 줄", id, name, archivedAt, archivedBy, projectId }`.

### Anti-Patterns to Avoid
- **일괄 저장(`saveRevenueInTx`)에 삭제 지시를 싣기:** 로컬 표시와 서버 보관이 어긋나고 D-7602 · 보관함과 안 맞는다 (§2).
- **`findRevenueEntryById`에 보관 필터 넣기:** 재전송 거부 · 계산서 `closed` 판정이 깨진다 (R4).
- **응답으로 `entriesFromDto` 전체 교체:** 다른 줄의 저장 전 편집을 잃는다 (§7).
- **계급 이름으로 판정:** 금지 (D-7604) — `can()` + 행 범위만.
- **범용 `archive()`로 매출 줄 보관:** 잠금 · 버전 · 연결 막기를 건너뛴다 → `isProtected() true`.

## Common Pitfalls

### Pitfall 1: R1 필터를 안 넣고 줄을 지우기 시작
**What goes wrong:** 줄을 지워도 매출 칸 표에 그대로 있고 합계 · 잔액이 줄지 않는다 (수금 지연 배지만 사라져 서로 모순).
**How to avoid:** R1 · R6 수정을 **첫 태스크**로, 통합 시험 「보관된 줄은 `listRevenue` 줄 · 합계 · 잔액 · 로그 순번에서 빠진다」를 그 태스크의 RED로.
**Warning signs:** `listRevenue.issuedEntries.length`가 지운 뒤에도 그대로.

### Pitfall 2: 로그 순번이 화면과 어긋남
**What goes wrong:** `numberEntryChanges`(:527-537)는 같은 tx로 `listRevenueEntriesByProject`를 읽어 화면 표 순서와 같다고 가정한다. 보관 줄이 목록에 끼면 순번이 한 칸씩 밀린다. **How to avoid:** R1 필터가 해결. 지우기 로그의 `no`는 **지우기 전** 활성 목록 위치.

### Pitfall 3: 낡은 화면이 보관된 줄을 고치거나 지우기 직후 저장
**What goes wrong:** R6 미수정 시 `updateRevenueEntryIfVersionMatches`가 보관 줄을 갱신. 또 일괄 저장이 지운 줄(dirty)을 version으로 보내면 version이 +1 되어 있어 충돌로 거부된다 — 이것이 의도한 안전망이지만 문구가 `다른 사람이 먼저 이 줄을 바꿈 · 덮어쓰기 / 그 값으로`라 혼란 → 보관된 줄은 `줄을 찾을 수 없음 · 새로 고침`으로 분기 (§1 R6).

### Pitfall 4: 구조 스캔 시험이 새 함수를 몰라 붉어짐
**What goes wrong:** `test/unit/row-scope-disposition.test.ts`는 도메인에서 `findProjectInScope`/`listRevenueEntriesByProject` 같은 프리미티브를 부르는 (파일, 함수, 프리미티브) 집합을 처분표로 고정한다 (revenue 항목 :132-134, :169) — 새 `domain/revenue/archive.ts`와 `repositories/revenue-entries.ts`의 프로젝트 join 읽기(`listArchivedRevenueEntryNames`)는 처분표에 줄을 더해야 한다. `action-registry-completeness`(새 액션 등록 빠짐), `error-copy-noun-style`(새 문구), `archive-revalidate`(`await (archive|deleteHoliday|restoreHoliday)\(` 정규식 — 새 보관 액션이 `revalidatePath("/admin/archive")`를 하는지 이 시험 확장), `leak-scan`(DTO 추가 시) 동일. **How to avoid:** 플랜의 `files`에 해당 시험을 넣고 실행 중 하나씩 실행해 본다.

### Pitfall 5: 일괄 저장 · 버림 되돌리기가 지운 줄을 되살림
`undoDiscard`(quote-table.tsx:1716~)의 병합이 지운 줄의 옛 편집을 다시 얹을 수 있다. 지운 뒤 서버 version이 달라 저장 때 충돌로 막히지만, 화면에 지운 줄이 다시 나타나면 혼란 → 병합에서 서버가 모르는(보관된) 줄 id 제외 또는 시험 고정. `dirtyStorage`(로컬 복원 보관본)에 지운 줄 편집이 남는지도 확인.

### Pitfall 6: 되돌리기 권한이 사실상 영구
10분 창 없이 `archived_by = 나`만 보면 지운 사람이 영원히 되살릴 수 있어 「보관함은 시스템 관리자만」(260907) 규칙과 어긋난다. 창 길이는 사용자 결정 필요 (A1).

### Pitfall 7: 연결된 발행 줄을 지워 요청이 막다른 상태로
Q1. 막지 않으면 `revenue_issue_requests`가 `issued`인 채 보관된 줄을 가리킨다 (R11 leftJoin이 보관 줄의 날짜 · 금액을 계속 보인다).

### Pitfall 8: 로그 종류가 설정으로 꺼짐
`archive`/`restore`는 `ALWAYS_ON`이 아니다 — 끄면 D-7605 「모두 남김」이 설정에 달린다 (Q4).
