## P1 설계 — 같은 문장 재평가 (잠금 방식 기각)

**고른 방식:** `belowThreshold` 모드의 UPDATE WHERE에 상관 하위 질의를 더한다 — 「이 제출의 경품(`cert_prizes.id = cert_submissions.prize_id`)의 `unit_value_krw` ≤ (50,000 정수) ÷ `cert_submissions.quantity`」(정수 나눗셈 — `certRrnPurgeTarget`의 `Math.floor(50000 / quantity)`와 같은 판정, 곱하지 않아 bigint 넘침도 없음; `quantity ≥ 1` · `unit_value_krw ≥ 1`은 DB 제약 `cert_submissions_quantity_check` · `cert_prizes_unit_value_krw_check`). 기준값은 `domain/certs/prize-value.ts`의 `CERT_RRN_EXEMPT_PRIZE_VALUE_KRW`를 import한다(repositories → domain import는 경계 규칙상 허용 · 선례 `repositories/action-log.ts`). `rrnCleared`는 이미 `RETURNING` 행 수라 실제 지운 수와 저절로 같다.

**READ COMMITTED에서의 동작(경합 분석):**
- (가) 가액 편집이 파기 UPDATE 문장 시작 **전에** 커밋 → 문장 스냅숏이 새 가액을 본다 → 50,000 넘으면 지우지 않는다. **지적의 경로가 이것이다**(후보를 읽은 뒤 ~ 갱신 전 커밋).
- (나) 가액 편집이 문장 시작 **뒤에** 커밋(또는 아직 미커밋) → 가액 편집은 제출 행을 잠그지 않아 파기는 기다리지 않고 스냅숏의 옛 가액으로 판정해 지운다. 직렬 순서 「파기 → 가액 편집」과 같다 — Job이 몇 ms 먼저 돈 것과 구별되지 않고, 결정 「실행 시점 가액 × 수량」 규칙 그대로다. **받아들인다**(남는 위험 — 위협 표 T-261002-3c1-03).
- (다) 수량 정정이 제출 행을 갱신하고 미커밋 → 파기 UPDATE는 그 행 잠금을 기다린다 → 정정 커밋 뒤 PostgreSQL이 새 행 버전으로 WHERE 전체를 다시 평가(EvalPlanQual — 상관 하위 질의가 새 `quantity`로 다시 돈다, `cert_prizes`는 문장 스냅숏) → 60,000이면 지우지 않는다. 정정이 롤백되면 옛 행으로 판정. 정정이 문장 시작 전에 커밋됐으면 스냅숏이 새 수량을 본다.
- (라) 파기가 먼저 그 행을 갱신 → `version + 1`이라 정정은 옛 버전으로 충돌(04.3-17 REVIEW 확인한 것 3 — 기존 동작).
- 잠금: 새 잠금 없음. 파기 트랜잭션은 여전히 제출 행만 잠그고(`clearClosedEventIpHashes` · 보존 기한 · 이 갱신) 경품 표는 잠금 없이 읽는다 → 행사 → 제출 순서와 순환 없음 유지.

**기각한 대안 — 행사 잠금으로 직렬화:** 같은 트랜잭션의 IP 가명 · 보존 기한 UPDATE가 제출 행을 먼저 잡으므로, 행사 잠금을 그 뒤에 잡으면 제출 → 행사 순서가 생겨 수량 정정 · 수령자 제출(행사 → 제출)과 교착할 수 있다. 피하려면 트랜잭션 맨 앞에서 후보 행사 전부를 정렬해 잠가야 하고, 그동안 수령자 제출 · 경품 편집이 모두 멈춘다. 얻는 것은 (나)의 직렬 순서 차이뿐이라 더 복잡하고 덜 안전하다.
