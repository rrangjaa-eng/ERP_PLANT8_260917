## 확인한 것

1. **P1 SQL 판정 = domain 규칙: PASS.**
   - WHERE는 `unit_value_krw <= 50000::integer / cert_submissions.quantity`다. quantity는 `NOT NULL` · `CHECK (quantity >= 1)`(`db/schema/cert-submissions.ts:23 · :52`)라 0으로 나누거나 NULL이 될 수 없다.
   - 양수 정수 나눗셈(PG 버림)은 `Math.floor(50000 / q)`와 같고, 비교도 둘 다 `≤`다(`domain/certs/prize-value.ts:16`). 정수 v에 대해 `v ≤ ⌊50000/q⌋ ⇔ v·q ≤ 50000`이므로 「가액 × 수량 ≤ 50,000」과 같은 판정이다. `bigint ≤ integer` 비교라 형 문제도 없다.
   - `prize_id`는 `NOT NULL` + FK이고, 제출이 있는 경품 줄은 지우지 못한다(N5 a). 경품 행이 없으면 하위 질의가 0행이라 `EXISTS`가 거짓이고, 그 줄은 비우지 않는다(안전 쪽).
   - 기준값은 `CERT_RRN_EXEMPT_PRIZE_VALUE_KRW`를 import한다. repositories → domain import는 eslint boundaries가 허용한다(`repositories` allow `domain`, `action-log` · `projects` · `roles` 선례).
   - purge · exclude 모드의 guard는 그대로 `isNull(purgedAt)`이다(삼항의 다른 갈래). `rrnCleared`는 RETURNING 행 수라 실제로 비운 수와 같고, cert_purge 로그 `detail.rrnCleared`와도 같다.
2. **회귀 테스트가 결함을 잡는다(변이 확인): PASS.**
   - ① `git show efe70c7b^:repositories/cert-purge.ts`로 수정을 빼면 새 테스트 2건이 실패한다. 순차 재평가는 `expected 5 to be 2`, 경합은 `expected 2 to be 1`이다.
   - ② `lte` → `lt`로 바꾸면 순차 테스트가 `expected 1 to be 2`로 실패한다. 16,666 × 3 경계가 `≤`/`<`를 가른다.
   - 순차 테스트는 `clearSubmissionPersonalFields`에 16,667 × 3 줄을 포함한 id를 직접 넘긴다. 그래서 domain 필터 없이 **SQL 자체가** 그 줄을 남기는지 본다.

3. **경합 테스트가 의도한 인터리빙을 만든다: PASS.**
   - 시드 행사는 `expiresAt` 2100 · `closedAt` null이라 `clearClosedEventIpHashes`가 닿지 않는다. 보존 기한 대상도 없어 purge 모드는 id 0으로 일찍 끝난다(SQL 없음). 그래서 정정 트랜잭션이 잡은 제출 행을 기다리는 문장은 **belowThreshold UPDATE 하나뿐**이다.
   - 정정은 `lockEventRow` → `updateSubmissionIfVersion`(행 잠금) → 로그 주입에서 멈춘다. 파기는 그 전에 후보(수량 1)를 읽고 UPDATE에서 기다린다. `waitForLockWaiter`가 이 대기를 확인한 뒤에야 정정을 푼다.
   - 통합 프로젝트는 `fileParallelism: false`라 다른 파일의 잠금 대기가 섞이지 않는다.
   - 대안 수정(트랜잭션 안에서 따로 SELECT로 다시 판정)이었다면 정정 커밋 전 스냅숏을 보고 그 줄을 비워 이 테스트가 실패한다. 즉 「문장 안 재평가」를 구별해 잡는다.
4. **READ COMMITTED · EPQ 분석: PASS.**
   - `EXPLAIN`을 보면 EXISTS가 끌어올려져 `Nested Loop`(제출 PK 인덱스 → `cert_prizes_pkey`, Filter `unit_value_krw <= 50000 / cert_submissions.quantity`)가 된다.
   - 잠긴 행이 커밋되어 바뀌면 EPQ는 대상 행만 최신판으로 바꿔 조건을 다시 본다. 이때 `cert_prizes`는 잠금 없는 비대상 관계라 처음 조인한 튜플(문장 스냅숏 판)을 TID로 다시 가져온다(ROW_MARK_REFERENCE). 그 결과는 다음 셋이다.
     - 수량 정정(제출 행 갱신)은 대기 뒤 새 수량으로 재판정한다.
     - 가액 편집이 문장 시작 전에 커밋됐으면 새 값으로 판정한다.
     - 가액 편집이 문장 시작 뒤에 커밋되면 옛 값으로 판정한다. 이것이 받아들인 위험 T-261002-3c1-03이다.
   - 커밋 메시지 · 주석의 서술과 같다. T-03은 「파기 → 편집」 직렬 순서(예: 4월 2일에 가액 인상)와 결과가 같아 새 위험을 더하지 않는다. 가액 편집 쪽 로직은 주민번호 상태에 따라 갈리지 않으므로(`events.ts` 표시용 `purgeTargetCount`뿐) 쓰기 비뚤어짐도 없다.
   - 정정은 `prize_id`를 바꾸지 않는다(`correctSubmission` patch에 없음).
5. **잠금 순서 · 교착: PASS.**
   - 파기는 여전히 행사 행을 잠그지 않고 제출 행만 갱신한다. 경품 표는 잠금 없이 읽는다. 행사 → 제출 순서를 쓰는 쓰기(정정 · 대조 제외)와 순환이 없다.
   - 새 조건은 이미 잠그던 행의 부분집합만 통과시키므로 새 잠금이 없다. 잠그는 행은 같거나 줄어든다.
   - 성능: 후보 하나당 PK 인덱스 조회 한 번이다. `inArray` 대량 id는 기존 구조 그대로다.
6. **P2-1 `requestKeyFor`: PASS.**
   - 클라이언트 정규화(NFC + 앞뒤 공백)가 서버 `requestQr`(`events.ts:476` `normalize("NFC").trim()`)와 같다. 당첨일은 `<input type="date">`의 `YYYY-MM-DD` 그대로다.

   - 「같은 키 · 다른 내용」은 이제 클라이언트에서 만들어지지 않는다. 서버는 키가 같으면 칸 검증 전에 기존 행사를 ok로 돌려주므로, 이 불변식이 토스트(`sentName`)와 실제 행사를 일치시킨다.
   - invalid · contactMissing 뒤 같은 내용 재전송은 같은 키다. 서버에 행이 없으므로 정상 처리된다.
   - 패널을 열 때 키를 비우는 것은 수정 전과 같은 동작이다(닫았다 열면 새 요청).
   - 부작용은 사용자가 받아들인 「고쳐 보냈는데 첫 신청이 커밋됨 → 행사 둘」뿐이다.
