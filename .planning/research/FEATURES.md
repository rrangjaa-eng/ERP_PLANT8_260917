# Feature Research

**Domain:** 소규모 대행사용 사내 ERP — 프로젝트 회계 + 지출결의/전자결재 + 손익 가시화 (Korean SME agency internal system)
**Researched:** 2026-09-17
**Confidence:** MEDIUM-HIGH (내부 감사 자료는 HIGH, 시장 비교는 WebSearch 기반 MEDIUM)

## Feature Landscape

이 시스템은 "제품을 파는" SaaS가 아니라 PLANT8 한 회사(10→30명)만 쓰는 사내 도구다. 그래서 "경쟁 제품 대비 차별화"보다 "이 회사의 핵심 가치(기획본부와 경영관리가 같은 숫자를 보고, 그 계산을 기획본부가 납득한다)에 직결되는가"가 우선순위 기준이다. 비교 대상은 경리나라·자비스(중소기업 경리 SaaS), 플렉스(HR/전자결재), 더존 iCUBE(소규모용 ERP), 모두싸인류 전자서명, ERPNext/Odoo(오픈소스 ERP) — 이들은 전자결재·증빙 관리·기본 회계는 표준 기능으로 갖췄지만, **원가 3단 우선순위(증빙>승인액>견적)로 드릴다운 가능한 프로젝트별 손익**과 **코드 없이 결재선·권한·정보 노출을 바꾸는 관리 화면**은 범용 제품엔 없다 — 이 둘이 이 프로젝트의 진짜 차별점이고, 나머지는 전부 "있으면 당연한 것"이거나 "만들지 말아야 할 것"이다.

세 번의 실패(260807, 260907, plant8-erp-rebuild)가 공통으로 남긴 교훈: 기능이 부족해서가 아니라 **범위가 너무 커서**(메뉴 5→15~16개, 화면 8→36~54개, 표 10→68~70개) 무너졌다. 아래 Anti-Features 절은 그 실패에서 실제로 추가됐다가 뒤집히거나 미완으로 남은 기능(구매요청 분리, 매출·수금·리저브 전체 대장, 정산 스냅샷, 조건부 결재 분기)을 이름을 대서 다시 만들지 말라고 못 박는다.

### Differentiators (Competitive Advantage)

### Anti-Features (Commonly Requested, Often Problematic)

"있으면 좋아 보이지만" 이 회사 규모·이 팀 구성(비개발자 1인 유지보수)에선 만들지 말아야 할 기능이다. 대부분 260807/260907에서 실제로 시도했다가 뒤집히거나 미완으로 남았다.

| Feature | Why Requested | Why Problematic | Alternative |
|---------|---------------|------------------|-------------|

## Feature Dependencies

```
[프로젝트 등록]
    └──requires──> (없음, 최상위 엔티티)

[견적 줄 원장] ──requires──> [프로젝트 등록]

[지출결의] ──requires──> [견적 줄 원장]  (프로젝트 비용 줄에 연결)
    └──requires──> [결재 라우팅 설정] (계급×단계 매핑이 있어야 결재가 성립)
    └──requires──> [사람·계급·팀 마스터] (결재자 지정의 전제)

[법인카드 사용 등록] ──requires──> [견적 줄 원장] (매칭 대상)
    └──enhances──> [지출결의] (경량 지출결의로 취급, Anti-Feature 참고)

[증빙 첨부] ──requires──> [지출결의] 또는 [법인카드 사용 등록] (연결 대상 존재)
    └──enhances──> [프로젝트 손익] (원가 우선순위 최상단 값 제공)

[프로젝트 손익] ──requires──> [견적 줄 원장] + [지출결의 승인 상태] + [증빙 첨부]
    └──requires──> [매출 기준·연도 귀속 설정] (분모·귀속 연도 결정)
    └──enhances──> [계산식 화면 노출] (같은 설정을 화면에 노출해야 신뢰 성립)

[팀 손익] ──requires──> [프로젝트 손익] (팀 소속 프로젝트 합산)
    └──requires──> [수주 실패 비용 입력] (프로젝트 없이 팀 이름 지출 허용 구조)
    └──requires──> [팀 직접 관리비 입력] (동일 구조)

[연간 팀 목표·인센티브] ──requires──> [팀 손익] (달성률 분모)
    └──requires──> [정보 노출표] (인센티브 금액은 대표·경영관리만)

[정보 노출표] ──requires──> [권한표(계급×메뉴×동작)] (별도 축이지만 같은 계급 마스터 공유)

[결재 라우팅 설정 화면] ──requires──> [사람·계급·팀 마스터]
    └──enhances──> [지출결의] (설정 변경이 즉시 결재 흐름에 반영)

[관리자 정의 커스텀 필드] ──enhances──> [프로젝트 등록] + [견적 줄 원장] + [거래처 마스터]
    └──conflicts──> [빠른 v1 출시] (설계 난이도가 높아 v1 범위에 넣으면 일정 위험)

[알림] ──requires──> [지출결의 상태] + [결재 상태] + [증빙 첨부 상태] (감시 대상 이벤트 존재)

[기타소득 확인증 현장 수집] ──requires──> [외부 토큰 링크 인증] (로그인 없는 접근 경로)
    └──conflicts──> [일반 사용자 인증 체계] (완전히 별도 트랙, 재사용 시도 금지)

[연차 신청·승인] ──requires──> [사람·계급·팀 마스터] + [결재 라우팅]
    (다른 손익/견적 기능과는 낮은 결합 — 병행 개발 가능)

[데이터 이전] ──requires──> [코드표/마스터 스키마 확정] (거래처·직원·카드·분류가 먼저 있어야 트랜잭션 데이터 이전 가능)
    └──conflicts──> [지속 미러링] (일회 이전만, PROJECT.md 확정 결정)
```

### Dependency Notes

- **[지출결의]가 [결재 라우팅 설정]을 요구한다:** 결재선이 코드가 아니라 데이터이므로, 지출결의 기능을 켜기 전에 최소한의 계급×단계 매핑(기본 4단)이 시드 데이터로 존재해야 한다. 순서가 바뀌면 "결재할 사람이 없는 지출결의"가 생긴다.
- **[프로젝트 손익]이 세 가지(견적/지출결의/증빙)를 동시에 요구한다:** 이 세 소스가 모두 존재해야 "가장 굳은 값" 우선순위 로직이 의미를 갖는다. 하나라도 빠진 채 손익 화면을 먼저 만들면 항상 예상값만 보이는 반쪽 기능이 된다 — 반드시 이 셋이 먼저 안정화된 뒤 손익을 얹는다.
- **[팀 손익]이 [프로젝트 손익]을 요구한다:** 팀 손익은 프로젝트 손익의 합산 위에 수주 실패 비용·관리비를 더하는 구조이므로, 프로젝트 손익 계산이 검증되기 전에는 팀 손익 숫자를 신뢰할 수 없다. 로드맵상 반드시 뒤 단계.
- **[정보 노출표]와 [권한표]는 같은 계급 마스터를 공유하지만 별도 축이다:** 권한표(메뉴×동작)를 먼저 만들고 정보 노출표(정보 항목 단위)를 그 위에 얹는 순서가 안전하다 — 반대로 하면 화면 접근 권한 없이 정보 노출만 관리하는 모순이 생긴다.
- **[기타소득 확인증]은 일반 인증 체계와 conflicts:** 외부 인력은 계정이 없으므로 토큰 기반 1회성 링크로 완전히 분리된 인증 경로가 필요하다. 기존 로그인 세션 로직을 재사용하려 하면 보안 경계가 흐려진다(PII 유출 위험) — 별도로 설계해야 한다.
- **[관리자 정의 커스텀 필드]는 빠른 v1 출시와 conflicts:** 스키마 진화 전략(EAV, JSONB 컬럼, 동적 마이그레이션 등)은 선택지마다 트레이드오프가 크고 아키텍처 리서치가 필요한 영역(PROJECT.md에 Pending으로 명시)이다. v1 범위에 넣으면 다른 모든 기능이 이 결정에 발이 묶인다 — 커스텀 필드는 4종 고정 타입으로 범위를 좁히고 별도 단계로 늦춘다.
- **[데이터 이전]은 지속 미러링과 conflicts:** PROJECT.md가 이미 확정한 결정이지만, 설계상 이관 스크립트가 "몇 번이든 재실행 가능(멱등)"해야 한다는 것과 "인트라넷을 계속 읽어와 동기화"하는 것은 서로 다른 기술적 방향이다 — 후자를 시도하면 전환 시점이 흐려지고 이중 입력 문제가 재발한다.

## MVP Definition

세 번의 실패가 전부 "범위 과다"였다는 것을 감안해, MVP는 **인트라넷 4기능을 그대로 대체하고 이중 입력을 없애는 것**으로 최대한 좁힌다. 손익·목표·확인증 같은 신규 가치 기능은 이 위에 얹는 다음 단계로 미룬다 — PROJECT.md의 Active 요구사항 안에서의 순서이지, 제품 범위를 줄이는 것은 아니다.

### Launch With (v1)

인트라넷 전환의 최소 요건 — 없으면 직원이 인트라넷을 계속 쓰게 된다.

- [ ] 프로젝트 등록·목록·상세 — 인트라넷 대체의 진입점
- [ ] 견적 줄 원장(서버 계산 차익) — 인트라넷의 핵심 버그(브라우저 계산)를 없애는 것 자체가 신뢰 회복의 시작
- [ ] 지출결의 + 4단 결재(설정 가능, 빈 자리 건너뜀) — "돈이 나가려면 결재를 거친다"는 회사의 유일한 강제 규율
- [ ] 법인카드 사용 등록 + 견적 줄 매칭 — 이중 계산 방지가 이미 검증된 요구
- [ ] 마스터 코드표(거래처·클라이언트·직원·법인카드·분류) — 자동완성 없이는 입력 저항이 큼
- [ ] 데이터 이전(멱등, 행수 검증) — 전환의 전제조건, 이게 없으면 아무것도 시작 못 함
- [ ] 관리 화면 최소셋(사람·계급·팀, 권한표, 결재 단계·담당 설정, 코드표 관리) — 이관 직후부터 사람이 늘 수 있으므로 동시 필요
- [ ] 로그인(이메일+비밀번호) — 인트라넷 평문 비밀번호를 이전하지 않는다는 결정과 직결

### Add After Validation (v1.x)

v1이 실제로 매일 쓰이기 시작하면(로그인 세션·지출결의 건수가 인트라넷 수준을 회복하면) 추가한다.

- [ ] 증빙 첨부 + 필수 규칙 on/off — 지급 규율 강화 트리거: v1 결재 흐름이 안정된 뒤
- [ ] 프로젝트 손익(3단 원가 우선순위 + 드릴다운 + 계산식 노출) — 트리거: 견적·지출결의·증빙 세 소스가 모두 실데이터로 쌓인 뒤 (Dependency 참고)
- [ ] 정보 노출표(계급×정보 항목) — 트리거: 손익처럼 민감한 신규 정보가 생기는 시점과 함께
- [ ] 마감·기한 알림(인앱+이메일) — 트리거: 지출결의 습관이 아직 정착 안 됐다는 신호(누락·지연 빈발) 확인 후
- [ ] 연차 신청·승인·잔여 — 다른 기능과 결합도 낮아 병렬 개발 가능, 사용자 만족도를 빠르게 올리는 카드
- [ ] 관리자 정의 커스텀 필드(4종 고정 타입) — 트리거: 실제로 "이 칸이 없어서 못 쓴다"는 요청이 나온 뒤(선제적으로 만들지 않는다)

### Future Consideration (v2+)

핵심 가치 검증 후, 또는 PROJECT.md가 이미 Out of Scope로 확정한 항목.

- [ ] 팀 손익(수주 실패 비용 + 관리비) + 연간 목표·인센티브 — 프로젝트 손익 신뢰가 먼저 검증돼야 팀 단위 숫자를 믿을 수 있음
- [ ] 기타소득 확인증 현장 수집(외부 링크, PII) — 별도 인증 경로·보안 감사가 필요해 다른 모든 기능과 독립적으로 늦춰도 무방
- [ ] 설정 JSON 내보내기·가져오기 — 설정 항목 수가 늘어난 뒤에야 가치가 생김
- [ ] Google 로그인(회사 GCP 전환 시) — 회사 GCP 이식이라는 별도 이벤트에 종속
- [ ] 카카오톡·슬랙 알림 — PROJECT.md 확정 v2
- [ ] 완전한 매출·계산서·수금 대장, 홈택스 연동, 정산 스냅샷, 대결, 조건부 결재, OCR, 네이티브 앱, 리포트 빌더 — Anti-Feature 절 참고, 이번 마일스톤 범위에서 의도적으로 배제
