# Pitfalls Research

**Domain:** 사내 ERP(프로젝트·지출결의·법인카드·손익·연차) — 10~30인 대행사, 비개발자 1인 + Claude Code 운영, Cloud Run + 관리형 Postgres
**Researched:** 2026-09-17
**Confidence:** MEDIUM-HIGH (도메인 실패 패턴은 저장소 감사로 HIGH, GCP 비용·한국 개인정보법·인코딩 항목은 공식 문서·법령 기반 웹 검색으로 MEDIUM)

이 문서는 `docs/research/repo-audit-260917.md`(인트라넷 1개 + 실패한 ERP 시도 2개의 실측 감사)와 `.planning/PROJECT.md`를 1차 근거로 삼는다. 세 리포 비교에서 드러난 패턴은 일반론이 아니라 **이 회사에서 이미 세 번 벌어진 일**이므로 가장 높은 확신도로 다룬다.

## Critical Pitfalls

### Pitfall 1: 네 번째 과잉설계 (Over-engineering by a solo builder + AI agent)

**What goes wrong:**
설계·화면·표·테스트가 실제 사용자 수(10~30명)와 실제 업무량(월 지급요청 ~80건, 견적 줄 ~130건)에 비해 10배 이상 커진다. `260907`은 11일간 519커밋·28.5만 줄·6,543개 테스트·설정 키 136개를 만들었지만 운영 DB가 없고 사용자가 0명이었다. `260807`은 31일간 1,326커밋·34.9만 줄·54개 화면을 만들었지만 "정한 것을 지키는 장치가 없어"(규칙 284개 중 사람이 지키는 것 30개, 설정 65개 중 서버가 실제로 읽는 것 6개) 폐기됐다. AI 코딩 에이전트는 "더 만들 수 있다"는 신호에 브레이크가 없고, 커밋 승인이 쉬우니 하루 100커밋 이상도 찍는다.

**Why it happens:**
- 비개발자 오너가 "이것도 있으면 좋겠다"고 말하면 Claude Code는 거절 없이 구현한다 — 범위 크리프의 병목이 사라진다.
- 화면·설정·테스트를 "많이 만드는 것"이 진행처럼 보이지만, 실사용자 검증 없이는 그게 완료 신호가 아니다.
- 설정 가능성을 늘릴수록 "이것도 설정으로 빼자"가 반복되어 설정 자체가 새 기능이 된다(§Pitfall 2).
- 실패 리포 두 개 모두 게시판·구매요청·리저브 등 인트라넷에 없던 새 업무 영역까지 처음부터 동시에 만들었다(인트라넷 메뉴 5개 vs ERP 메뉴 15~16개).

**How to avoid:**
- 이번 계획은 **인트라넷 4기능 대체를 1차 마일스톤으로 고정**하고, 손익·증빙·연차·목표는 그 위에 얇게 얹는다(PROJECT.md가 이미 이렇게 스코프를 잘라뒀다 — 로드맵이 이 경계를 다시 넓히지 않는다).
- 각 페이즈 시작 전에 "이 페이즈가 없으면 지금 인트라넷보다 못한가?"로 검증. 아니라면 다음 마일스톤으로 민다(구매요청·발주 폰입력·카카오톡 알림은 이미 Out of Scope로 명시됨).
- 커밋/일·화면 수·설정 키 수에 상한 신호를 두고, 한 페이즈가 인트라넷 전체 규모(15,650줄, 표 10개)를 넘기면 멈추고 재검토한다.
- **"완료"의 정의를 실사용자 로그인·데이터 입력으로 못박는다.** 테스트 통과·커밋 수가 아니라 실제로 10명이 이걸로 이번 주 지급요청을 올렸는가로 판정.
- 페이즈마다 "이번에 안 만든 것" 목록을 명시적으로 남긴다(260907/260807은 이게 없어서 범위가 조용히 불어났다).

**Warning signs:**
- 한 페이즈 계획의 파일/테이블/화면 수가 인트라넷 대응 기능 대비 3배 이상.
- "설정으로 빼자"는 결정이 하루에 여러 번 나옴.
- 실사용자 없이 테스트 스위트만 커짐(테스트 500개 넘어가는데 운영 DB에 사람 데이터가 없음).
- 하루 커밋 수가 두 자리를 넘김(260807은 하루 최대 356커밋).
- 인수인계 문서/미결 대장이 코드보다 빨리 커짐(260907은 문서 15.9만 줄로 코드의 절반 크기).

**Phase to address:**
setup (스코프 고정 및 "완료" 기준 문서화) — 전 페이즈에 걸쳐 게이트로 반복 점검.

### Pitfall 2: 설정 지옥 — 아무도 안 읽는 설정, 서버가 안 읽는 설정

**What goes wrong:**
"코드 수정 없이 조정 가능"이 목표이다 보니 권한·결재선·규칙 on/off·알림 시점·수식·코드표·커스텀필드까지 전부 설정 테이블로 뺀다. 화면에 설정 키가 있는데 서버가 실제로 그 값을 읽지 않는(하드코딩된 채 남은) 경우가 생긴다. `260807`은 정확히 이 이유로 폐기됐다 — 설정 65개 중 서버가 실제로 읽는 것은 6개뿐이었고, 새 권한을 켰는데도 반영 안 된 사고가 6회 있었다.

**Why it happens:**
설정 화면을 만드는 것과 서버 로직이 그 값을 매번 참조하도록 배선하는 것은 별개 작업인데, 전자만 하고 후자를 빠뜨리기 쉽다. 특히 Claude Code에게 "설정 화면 추가"를 시키면 설정 CRUD는 완벽히 만들지만, 기존 로직 여러 곳에 흩어진 하드코딩된 상수를 전부 그 설정으로 교체했는지는 별도로 확인해야 한다.

**How to avoid:**
- PROJECT.md에 이미 명시된 요구사항을 그대로 지킨다: "화면에 있는 설정 키는 서버가 반드시 읽는다(테스트로 강제)". 설정 키 하나당 최소 1개의 통합 테스트로 "설정값을 바꾸면 동작이 바뀐다"를 확인한다(단위 테스트가 설정을 우회하고 상수를 직접 넣는 방식이면 무효).
- 설정 테이블에 `last_read_at`/참조 카운터 같은 감사 컬럼을 두거나, 코드 그렙(`grep`)으로 "설정 키 문자열이 서버 코드에서 최소 1곳 이상 읽힌다"를 CI에서 강제.
- 설정 항목 수 자체를 계획 단계에서 상한(예: 1차 마일스톤 30개 이하)으로 못박는다 — 260907의 136개는 과했다.
- 설정 화면 하나 추가할 때마다 "이게 없으면 지금 당장 문제가 생기는가"를 되묻는다. 결재 단계 수·규칙 on/off·수식·알림 시점처럼 회사가 이미 "바뀔 것"이라고 말한 것만 설정으로 뺀다.

**Warning signs:**
- 설정 화면에 값이 있는데 바꿔도 동작이 안 바뀜(수동 QA에서 흔히 놓침).
- 설정 테이블 컬럼 수가 늘어나는 속도가 실제 업무 요구보다 빠름.
- "일단 설정으로 빼놓고 나중에 연결하자"는 결정이 남아있음(TODO로 남으면 영원히 안 됨).

**Phase to address:**
admin-config — 설정 CRUD를 만드는 페이즈 자체에 "서버가 읽는지 테스트로 검증"을 완료 조건으로 포함.

### Pitfall 3: 권한(RBAC)×메뉴×정보노출 행렬이 조합 폭발하며 새는 정보

**What goes wrong:**
계급×메뉴×동작(보기/쓰기/승인) + 계급×정보항목(손익·팀비용·목표·인센티브) 두 겹의 행렬은 계급이 5종이어도 메뉴·정보항목이 늘어날 때마다 조합이 곱으로 늘어난다. 화면(UI)에서는 숨겼지만 API 응답·엑셀 내보내기·검색 자동완성·전역 검색에는 그대로 노출되는 사고가 가장 흔하다 — 화면 컴포넌트 하나만 막고 데이터 레이어를 안 막았기 때문이다.

**Why it happens:**
프런트엔드에서 "이 필드는 안 보여준다"는 조건부 렌더링으로 처리하기 쉬운데, API가 이미 전체 필드를 내려보내고 있으면 브라우저 개발자도구나 `/api` 직접 호출로 새는 것을 놓친다. 엑셀 내보내기·자동완성(Ajax)·PDF 생성처럼 화면 렌더링 경로 밖에서 별도로 데이터를 조회하는 기능은 권한 체크가 통째로 빠지기 쉽다(인트라넷의 `Ajax.php` 자동완성도 원래 권한 체크가 없었다).

**How to avoid:**
- 필드 단위 가시성 체크를 **API 응답 직렬화 레이어 한 곳**에서 강제한다(뷰마다 개별 구현 금지). 신규 API·내보내기·자동완성을 추가할 때 이 레이어를 거치지 않으면 리뷰에서 반려.
- "계급×메뉴×동작"과 "계급×정보항목"을 분리된 두 테이블로 유지하되, 정보항목 마스터에 API 필드명을 직접 매핑해 코드와 설정이 어긋나지 않게 한다.
- 자동 테스트: 각 역할(대표/경영관리/본부책임자/팀장/기획PM)로 로그인해 손익·팀비용·인센티브 API를 직접 호출하는 회귀 테스트를 최소 1세트 둔다(화면 테스트만으로는 이 누락을 못 잡는다).
- 신규 기능(손익·목표·인센티브)의 기본값은 "기획본부에 안 보임"으로 시작하고, 보여줄 항목만 화이트리스트로 연다(PROJECT.md 요구사항과 일치).

**Warning signs:**
- 엑셀 내보내기나 PDF에 화면에서는 안 보이는 필드가 포함됨.
- 검색/자동완성 결과에 권한 밖 거래처·프로젝트 금액이 노출.
- 새 API 엔드포인트 추가 시 권한 체크 코드가 복사되지 않고 "일단 열어두고 나중에" 상태로 배포됨.

**Phase to address:**
data-model & auth (권한 모델 설계) — admin-config에서 UI가 붙을 때 재검증.

### Pitfall 4: 결재선(approval route) 편집이 진행 중 문서를 깨뜨림

**What goes wrong:**
결재 단계·담당자를 설정 화면에서 바꿀 수 있게 만들면, 이미 2단계까지 승인된 지출결의 건이 새 결재선(예: 5단으로 변경, 혹은 담당 계급 변경)으로 재계산되면서 승인 이력이 붕 뜨거나, 다음 승인자가 사라지거나(빈 자리), 이미 지나간 단계가 다시 대기 상태로 돌아가는 사고가 난다.

**Why it happens:**
결재선을 "현재 설정값을 실시간 참조"하는 방식으로 구현하면 과거 문서까지 영향을 받는다. 결재선은 문서 발행 시점에 스냅샷으로 고정돼야 하는데, 설정 테이블을 그대로 조인해서 매번 계산하면 이 구분이 사라진다.

**How to avoid:**
- 지출결의(문서)가 생성되는 시점에 그 시점의 결재선 정의를 **문서에 스냅샷으로 복사**해 저장한다(`route_steps`를 문서별로 고정 — 260907/260807 스키마의 `approval_routes/route_steps` 설계 의도와 일치, 실행 시 반드시 스냅샷 방식으로 구현).
- 결재선 설정을 변경해도 "이미 발행된 문서"는 영향받지 않고, "새로 발행되는 문서"부터 적용됨을 명시적으로 테스트한다.
- 빈 자리 건너뜀(예: 본부 책임자 공석) 로직은 문서 생성 시점에 고정된 담당자 스냅샷을 기준으로 계산하고, 이후 인사이동으로 재계산되지 않게 한다. 대신 위임(delegation) 기능을 별도로 둔다.
- 결재선 설정 변경 화면에 "진행 중인 문서 N건에는 영향 없음"을 명시해 관리자가 착각하지 않게 한다.

**Warning signs:**
- 결재선 설정을 바꾼 직후 진행 중이던 결재함 건이 사라지거나 단계가 초기화됨.
- "관리팀이 팀장 건너뛰기"처럼 인트라넷에서 이미 관찰된 편법(승인 없이 통과)이 새 시스템에서도 설정 실수로 재현됨.

**Phase to address:**
core-ledger (지출결의+결재 구현 페이즈) — 결재선 스냅샷 여부를 설계 리뷰에서 명시적으로 확인.

### Pitfall 5: 계산식·귀속기준 설정 변경이 과거 손익 숫자를 소급으로 바꿔버림

**What goes wrong:**
매출 인식 기준(세금계산서 발행액/계약 금액/입금액)과 연도 귀속 날짜(발행일/종료일/입금일)를 설정에서 바꿀 수 있게 만들면, 과거에 이미 "확정"됐던 프로젝트 손익·팀 손익·연간 목표 달성률·인센티브가 설정 변경 한 번에 전부 재계산되어 달라진다. 팀장이 이미 확인한 "작년 우리 팀 목표 120% 달성"이 규칙을 바꾼 뒤 95%로 내려가면 신뢰가 완전히 무너진다 — 이는 인트라넷의 "차익 불일치 66줄" 문제(계산 로직이 언제 저장됐는지 불명확)를 손익 전체 규모로 재현하는 것이다.

**Why it happens:**
손익 계산식을 "항상 실시간으로 최신 설정값으로 재계산"하는 방식(뷰/쿼리로 매번 계산)이 가장 구현하기 쉽지만, 이게 바로 소급 변경을 낳는다. 회사는 "설정으로 바꿀 수 있어야 기획본부가 납득한다"고 했지, "과거 숫자도 매번 바뀌어도 된다"고 하지 않았다.

**How to avoid:**
- 손익·목표 달성·인센티브 숫자는 **정산(마감) 시점에 스냅샷으로 확정**하고(PROJECT.md의 `settlement_records` 개념과 일치), 확정된 이후에는 설정이 바뀌어도 재계산하지 않는다. 진행 중(마감 전) 프로젝트만 최신 설정으로 재계산되는 "예상치"로 표시해 이 구분을 화면에서도 명확히 한다.
- 설정(계산식·귀속기준)이 바뀌면 "이 변경은 이 날짜 이후 마감되는 건부터 적용됩니다"를 강제하고, 변경 이력(누가 언제 무엇을 왜 바꿨는지)을 감사 로그로 남긴다.
- 연도 귀속 기준을 연중에 바꾸는 것은 원칙적으로 막거나(회계연도 경계에서만 허용), 바꾸면 그 사실과 영향받는 프로젝트 목록을 관리자에게 미리 보여준 뒤 확인받는 확인 절차를 둔다.
- 계산식은 화면에 노출(PROJECT.md 요구사항)하되, "이 숫자가 계산된 시점의 계산식 버전"도 같이 보여줘 소급 논란이 생기면 즉시 대조 가능하게 한다.

**Warning signs:**
- 어제 확인했던 팀 손익/달성률이 오늘 설정 변경 없이도 다른 값으로 보임(재계산 트리거를 못 찾음).
- 설정 변경 이력이 없어 "언제 왜 바뀌었는지" 답을 못함.
- 인센티브 지급 확정 후에도 숫자가 화면상 계속 움직임.

**Phase to address:**
P&L (손익 계산 페이즈) — 스냅샷/확정 시점 설계를 반드시 포함. admin-config에서 계산식 편집 UI를 만들 때 "적용 시점" 규칙을 강제.

### Pitfall 6: 새 손익 숫자를 기획본부가 납득하지 못함 (신뢰 붕괴)

**What goes wrong:**
새 시스템의 손익이 인트라넷/현재 관행과 다르게 나오면(이미 예견된 상황 — PROJECT.md: "새 시스템의 손익이 인트라넷 숫자와 달라져도 기획본부가 그 계산을 납득해야 한다"), 기획본부는 "숫자가 틀렸다"고 판단하고 시스템을 신뢰하지 않는다. 이는 기능 결함이 아니라 **설명 가능성(explainability) 부재**가 원인인 경우가 대부분이다.

**Why it happens:**
현재도 기획본부와 경영관리가 같은 프로젝트를 다른 숫자로 본다(PM은 발주 뒤 몰아서 입력, 경영관리는 그때 처음 봄). 원인 데이터가 다른데 결과만 다르다고 하면 논쟁이 "누구 숫자가 맞냐" 싸움이 된다. 근거 줄로 못 내려가면 검증할 방법이 없어 감정 싸움으로 번진다.

**How to avoid:**
- PROJECT.md에 이미 명시된 원칙 — "모든 숫자는 근거 줄까지 내려가 볼 수 있고 계산식은 설정 화면에 드러나 있다" — 을 손익 화면의 **1차 완료 기준**으로 삼는다. 손익 합계 숫자를 클릭하면 반드시 어떤 견적 줄/지출결의/증빙에서 왔는지 드릴다운되는지를 UAT 항목으로 못박는다.
- 인트라넷과 다른 이유를 자동으로 설명하는 화면을 둔다: "인트라넷 기준 vs 새 기준" 나란히 비교, 차이가 나는 원인(비용 우선순위: 증빙>지출결의>견적 실행가, 부가세 포함 여부, 매출 인식 시점)을 항목별로 표시.
- 전환 초기(병행 기간)에는 옛 인트라넷 숫자와 새 시스템 숫자를 나란히 보여주는 대조 리포트를 만들어, 기획본부가 차이의 원인을 스스로 짚어낼 수 있게 한다. 차이가 나면 "왜"를 기획본부에 먼저 보여주고 합의 후 새 숫자를 공식화한다.
- 손익 관련 설정(비용 우선순위, 매출 인식 기준, 연도 귀속)을 확정하기 전, 기획본부·경영관리 양쪽에게 실제 프로젝트 표본으로 시범 계산해 보여주고 서명받는 절차를 페이즈 계획에 넣는다.

**Warning signs:**
- 손익 화면 배포 후 "이 숫자 왜 이래요?"라는 문의가 반복되는데 답할 근거 화면이 없음.
- 기획본부가 여전히 자체 엑셀로 손익을 따로 계산함(시스템 숫자를 안 씀).
- 드릴다운이 최종 구현에서 빠지고 "나중에"로 미뤄짐.

**Phase to address:**
P&L — 드릴다운·계산식 노출·구버전 대조를 핵심 완료조건(UAT)으로 포함. setup 단계에서 기획본부·경영관리 합의 프로세스를 계획.

### Pitfall 7: 이중 계산 — 법인카드 사용과 지출결의가 같은 비용을 두 번 셈

**What goes wrong:**
인트라넷에서 법인카드 사용(`CARD_USED`, 433건)과 견적 줄(`QUOTATION_LINE`)은 1:1로 연결되어 있었다(433:433). 새 시스템에서 법인카드 사용 등록과 지출결의(지급요청)를 각각 독립적으로 비용 집계에 반영하면, 카드로 결제한 같은 비용이 지출결의로도 올라와 손익에서 두 번 차감된다. PROJECT.md 요구사항에 "법인카드 사용 등록, 견적 줄과 연결, 이중 계산 없음"이 명시된 것 자체가 이 리스크를 인지하고 있다는 신호다.

**Why it happens:**
법인카드 지출은 보통 사후 등록(카드사 명세서 기반)이고 지출결의는 사전 승인 흐름이라, 같은 견적 줄에 두 경로가 동시에/순차로 입력될 수 있다. 견적 줄 하나에 "비용 발생 경로"를 하나로 강제하지 않으면 검증 로직에서 막을 방법이 없다.

**How to avoid:**
- 견적 줄(비용 항목) 하나당 "확정 비용의 출처"는 **정확히 하나**만 허용(증빙 > 지출결의 승인액 > 견적 실행가 우선순위와 동일한 원칙을 지급 방식에도 적용). 법인카드로 결제됐다고 표시된 줄은 지출결의 대상에서 자동 제외하거나, 지출결의 등록 시 "이미 법인카드로 처리됨" 경고와 함께 차단.
- DB 제약(unique 제약 또는 상태 머신)으로 "같은 견적 줄에 지출결의 승인 완료 + 법인카드 사용 등록"이 동시에 존재할 수 없게 강제 — 애플리케이션 로직만으로는 놓치기 쉽다.
- 마이그레이션 시점에 기존 433:433 연결을 그대로 이관해, 신규 데이터 모델에서도 "법인카드 사용 = 항상 특정 견적 줄에 연결"이라는 불변식을 처음부터 강제한다.

**Warning signs:**
- 프로젝트 손익 검증 시 총비용이 지출결의 합계 + 법인카드 합계로 단순 더해짐(연결 여부 무시).
- 특정 견적 줄에 지출결의 승인 이력과 법인카드 사용 이력이 둘 다 존재.

**Phase to address:**
core-ledger — 법인카드·지출결의 스키마 설계 시 상호배타 제약을 필수 요구사항으로.

### Pitfall 8: 데이터 마이그레이션 — 인코딩·NULL 날짜·고아 행·ID 충돌·타임존을 놓침

**What goes wrong:**
MySQL(CodeIgniter, AWS RDS)에서 Postgres(Cloud SQL)로 이관할 때 흔히 놓치는 것들이 이 프로젝트에 구체적으로 존재한다: 인트라넷 `db_backup_260915.sql`은 한글 데이터가 대부분이라 EUC-KR/UTF-8 인코딩 불일치 시 한글이 깨진다(모지바케). 고아 견적 줄이 이미 5건 확인됐다(프로젝트 삭제 시 하위 미삭제). 등록시각이 전부 NULL인 컬럼도 있다(`QUOTATION_LINE`). 세션·로그 타임스탬프가 KST인지 UTC인지 애매한 상태로 Postgres `timestamptz`에 잘못 넣으면 9시간 밀린 시각이 저장된다. 434~464건 규모라 작아 보이지만, "표별 행수 일치"만 검증하면 인코딩 깨짐이나 시각 밀림은 행수가 같아도 안 잡힌다.

**Why it happens:**
MySQL 덤프가 실제로 EUC-KR인지 UTF-8인지는 `SHOW CREATE TABLE`이나 컬럼 collation을 봐야 확실히 알 수 있는데, CodeIgniter 3 기본 설정과 실제 DB 컬럼 collation이 다를 수 있다(설정과 실제가 어긋나는 것은 이 회사에서 반복된 패턴 — Pitfall 2와 동형). 타임존은 애플리케이션이 `date()` 계열 함수로 서버 로컬시간을 문자열로 저장했을 가능성이 높고, 이 경우 원본에 타임존 정보가 아예 없다.

**How to avoid:**
- 이관 스크립트 실행 전, 실제 컬럼 collation과 바이트 시퀀스를 샘플 검사(한글 이름·주소가 포함된 행 몇 개를 직접 열어 원본 인코딩을 확인)해 문서화. 변환은 명시적 디코드(EUC-KR로 읽기)→인코드(UTF-8/UTF-8MB4로 쓰기)로 하고, 바이트를 그대로 복사하지 않는다.
- KST/UTC: 원본에 타임존 표시가 없다면 "이 서버는 항상 KST였다"고 명시적으로 가정해 이관 시 `+09:00`을 붙여 `timestamptz`로 저장. 이 가정을 이관 문서에 기록해 나중에 재현 가능하게 한다.
- NULL/빈 날짜: 필수 날짜 컬럼에 NULL이 있으면 이관을 막지 말고 "고쳐지지 않은 값"으로 플래그만 남기고 통과시킨다(PROJECT.md: "불일치는 고치지 않고 표시" 원칙과 일치). 화면에서 관리자가 나중에 채우게 한다.
- 고아 행: 참조 무결성이 깨진 행(고아 견적 줄 5건 등)은 이관 시 자동 연결 시도하지 않고 별도 "미해결" 목록으로 분리해 사람이 검토·결정.
- ID: MySQL auto_increment ID를 그대로 Postgres 시퀀스로 옮기되, 신규 채번과 충돌하지 않도록 이관 후 시퀀스 시작값을 `max(id)+1`로 명시적으로 재설정.
- 행수 일치 검증에 더해 **체크섬/샘플 대조 검증**을 추가한다: 한글 필드 일부를 원본과 이관 후 직접 비교(육안 또는 정규식으로 깨진 문자 패턴 탐지), 날짜 필드는 최소/최대/분포를 원본과 대조.
- 이관 스크립트는 멱등(이미 PROJECT.md 요구사항)하게 만들어 리허설을 여러 번 반복하고, 문제를 고칠 때마다 처음부터 재실행해 결과가 같은지 확인한다.

**Warning signs:**
- 이관 후 한글 이름/거래처명 일부가 물음표나 깨진 기호로 보임.
- 특정 시간대(예: 새벽 3~5시)에 등록된 것으로 보이는 데이터가 비정상적으로 많음(UTC/KST 혼동 신호).
- 행수는 맞는데 합계 금액(예: `QUOTATION_LINE` 견적가 합)이 원본과 다름.

**Phase to address:**
migration — 리허설 단계에서 인코딩·타임존·고아행 검증을 표별 행수 검증과 별도 체크리스트로 명시.

### Pitfall 9: 평문 비밀번호 이관 + 병행 기간 규율 붕괴로 컷오버가 흐지부지됨

**What goes wrong:**
인트라넷은 비밀번호를 평문 비교로 저장한다(`models/Login_m.php:205`). 이를 그대로(또는 단순 해시만 씌워) 새 시스템에 이관하면 평문이었던 값이 어떤 경로로든 로그·백업에 남아있을 위험이 이어진다. 또한 "이관 후 인트라넷은 조회만" 원칙이 실제로는 코드로 강제되지 않으면(권한 체크가 아니라 "부탁"에 의존하면), 직원들이 급하면 예전 화면에 입력해버려 두 시스템 데이터가 다시 갈라진다 — 실제로 감사 보고서에 "9-01 화면 긁기 이후 2주간 프로젝트 8·견적 줄 68건이 늘었다"는 기록이 있어, 절체 시점이 하루라도 늦어지면 계속 갈라진다는 게 이미 실증됐다.

**Why it happens:**
비밀번호는 "일단 로그인만 되게" 급하게 이관하고 나중에 고치자는 유혹이 크다. 병행 기간 쓰기 차단은 애플리케이션 코드(라우트 disable)가 아니라 "쓰지 말라고 공지"로 끝내기 쉽다.

**How to avoid:**
- 평문 비밀번호는 **이관하지 않는다**(PROJECT.md에 이미 명시). 전 직원 계정을 임시 비밀번호로 새로 발급하고 첫 로그인 시 강제 변경시키거나, 이메일로 비밀번호 재설정 링크를 발송한다.
- 인트라넷 쓰기 차단은 애플리케이션 레벨에서 실제로 막는다: 컷오버 시점에 인트라넷의 `write/insert/update/del` 계열 라우트를 서버에서 비활성화(읽기 전용 DB 계정으로 전환하거나 라우트 자체를 막음)해 "공지"가 아니라 기술적으로 강제한다.
- 컷오버 날짜를 명확히 정하고, 그 날짜 이후 인트라넷에서 발견되는 신규 데이터는 "새 시스템에 수동으로 다시 입력해야 하는 예외"로 취급해 직원들에게 컷오버의 실질적 비용을 알린다(리허설 반복으로 이 창을 최소화).
- 리허설은 최소 2회 이상: 1회차는 스크립트 검증용, 마지막 리허설은 실제 컷오버 절차(공지→인트라넷 차단→이관→검증→새 시스템 오픈)를 시간까지 재서 실전처럼 수행.

**Warning signs:**
- 이관 스크립트에 비밀번호 컬럼을 그대로 복사하는 코드가 남아있음.
- 컷오버 이후에도 인트라�트 로그인 세션이 계속 생성됨(`ci_sessions` 증가).
- "직원들에게 공지했다"가 유일한 차단 수단.

**Phase to address:**
migration — 컷오버 절차 설계에 "인트라넷 쓰기 강제 차단"과 "비밀번호 재발급 플로우"를 필수 항목으로.

### Pitfall 10: 주민등록번호·계좌번호 등 개인정보 처리가 법을 어김

**What goes wrong:**
기타소득 확인증 기능은 외부 인력이 휴대폰에서 주민등록번호를 직접 입력·제출하는 흐름이다. 개인정보보호법 제24조의2는 주민등록번호를 "법령에 구체적 근거가 있거나 급박한 생명·신체·재산 이익을 위해 명백히 필요한 경우"에만 수집하도록 제한하고, 수집 시 암호화(DB 양방향 암호화) 저장을 의무화한다. 위반(미암호화) 시 3천만원 이하 과태료다. 인트라넷 백업 리포에는 이미 계좌번호 732건이 평문으로 존재한다는 감사 기록이 있다 — 같은 습관이 새 시스템에서 반복될 위험이 크다.

**Why it happens:**
소득세법상 기타소득 지급명세서 작성에는 주민등록번호(또는 대체 식별번호) 수집이 법적 근거가 있어 "수집 자체는 가능"하다고 착각하고, 그 뒤 암호화·접근 로그·보존기간 관리까지는 챙기지 않은 채 일반 텍스트 컬럼에 저장하는 경우가 흔하다. 비개발자 1인 개발 환경에서는 KMS 연동, 컬럼 암호화, 접근 로그 별도 테이블까지 챙기는 게 후순위로 밀리기 쉽다.

**How to avoid:**
- 주민등록번호는 저장 시점에 애플리케이션 레벨 암호화(예: AES-256, 키는 Cloud KMS 또는 Secret Manager 관리, DB 컬럼에는 암호문만) 적용. 평문 컬럼을 아예 만들지 않는다.
- 계좌번호도 동일 원칙 — 완전 평문 저장 대신 암호화하거나 최소한 마스킹된 형태로만 화면에 노출(전체 조회는 권한자만, 조회 자체를 감사 로그에 남김).
- 확인증 데이터는 접근 권한을 대표·경영관리로 극도로 제한(PROJECT.md에 이미 "보안 감사 뒤 확정"으로 명시돼 있음 — `/cso` 실행을 이 기능 배포 전 필수 게이트로 고정).
- 보존기간을 명시(예: 세법상 보관 의무 기간 경과 후 파기 절차를 스케줄링하거나 최소한 수동 파기 체크리스트).
- 접근 로그(누가 언제 주민등록번호/계좌번호를 조회했는지)를 감사 로그 테이블에 남긴다.
- 외부 인력이 로그인 없이 접근하는 링크(`/g/:token` 방식)는 토큰 만료·1회성·전송 채널(SMS/카톡 링크 노출) 보안을 별도로 검토한다.

**Warning signs:**
- 주민등록번호/계좌번호 컬럼이 `varchar`로 평문 저장되어 있음.
- 확인증 데이터를 기획PM 등 넓은 권한군이 열람 가능.
- 외부 제출 링크에 만료 시간이 없음.

**Phase to address:**
hardening (보안 감사, `/cso`) — 단, 스키마 설계는 data-model 단계에서부터 암호화 컬럼으로 시작해야 나중에 마이그레이션 없이 안전.

### Pitfall 11: Cloud Run 콜드스타트 + Cloud SQL 커넥션 폭증, 그리고 "스케일-투-제로인데 비싸다"는 착각

**What goes wrong:**
Cloud Run은 스케일-투-제로가 가능하지만 **Cloud SQL은 자동으로 멈추지 않는다** — 인스턴스가 켜져 있는 한 초 단위로 과금되고, 가장 작은 shared-core 티어(db-f1-micro급)도 월 8~10달러 기본 요금에 퍼블릭 IP를 쓰면 유휴 시간에도 추가로 월 9.57달러 정도가 붙는다. 여기에 PostgreSQL은 연결마다 프로세스를 새로 띄우므로, Cloud Run이 트래픽 급증 시 여러 인스턴스로 동시에 스케일 아웃하면 각 인스턴스가 커넥션 풀을 새로 만들면서 Cloud SQL의 `max_connections`를 순식간에 소진할 수 있다. "월 운영 비용 최소, 스케일-투-제로"라는 목표(PROJECT.md)를 DB 계층까지 그대로 기대하면 예상과 다른 청구서를 받는다.

**Why it happens:**
Cloud Run의 스케일-투-제로 개념을 DB에도 그대로 적용될 거라 오해하기 쉽다. 또한 로컬 개발/저부하 환경에서는 커넥션 문제가 드러나지 않다가, 실제 10~30명이 동시에 쓰는 순간(예: 월말 마감 몰림) 갑자기 연결 오류가 난다.

**How to avoid:**
- Cloud SQL은 상시 켜두는 비용을 전제로 예산을 잡되, 사용하지 않는 야간·주말에 인스턴스를 스케줄로 정지(Cloud Scheduler + Admin API)하는 것을 검토해 실질 비용을 줄인다(단, 정지·재기동 지연을 감안).
- Cloud Run 서비스의 `max-instances`를 낮게(예: 2~5) 제한하고, 인스턴스당 DB 커넥션 풀 크기를 작게(예: 3~5) 설정해 `max-instances × pool-size < Postgres max_connections`를 항상 만족시킨다.
- Cloud SQL Auth Proxy(또는 언어별 커넥터)를 사용해 연결을 안정화하고, 필요하면 Cloud SQL의 Managed Connection Pooling(관리형 풀링)을 검토한다.
- 스택 리서치(STACK.md)에서 Cloud Run+Cloud SQL 대비 Neon/Supabase 등 서버리스 Postgres(진짜 스케일-투-제로, 유휴 시 과금 없음) 대안을 비용 관점에서 비교하도록 요청한다 — PROJECT.md도 "리서치가 더 싸고 단순한 대안을 권하면 검토"라고 이미 열어뒀다.
- 로깅 비용(Cloud Logging은 일정 용량 이상 과금)도 초기부터 로그 레벨·보존기간을 설정해 방치되지 않게 한다.

**Warning signs:**
- 매달 청구서에 DB 항목이 예상(스케일-투-제로 기대)과 다르게 고정비로 찍힘.
- 월말 마감 시점에 "connection refused" 또는 "too many connections" 오류 급증.
- 개발 중에는 문제없다가 동시 사용자 10명대에서 오류가 남.

**Phase to address:**
setup (인프라 스택 결정, STACK.md와 연동) — core-ledger 이후 부하 테스트로 재검증.

### Pitfall 12: 관리 화면이 오너 본인에게도 복잡해져 결국 코드로 다시 손댐

**What goes wrong:**
"코드 수정 없이 운영"이 목표인데, 권한표·정보노출표·결재선 편집·수식 편집 화면 자체가 UX적으로 복잡해지면(체크박스 격자, 여러 단계 탭) 오너가 결국 "이거 그냥 DB 직접 고칠게" 또는 "Claude Code한테 코드로 고쳐달라고 할게"로 돌아간다. 그러면 설정 화면은 장식이 되고, 코드와 실제 운영 상태가 다시 벌어진다(260807/260907이 "규칙을 지키는 장치 없음"으로 실패한 것과 같은 패턴이 관리 화면 단계에서 재현).

**Why it happens:**
권한×메뉴×동작 행렬을 그대로 체크박스 표로 만들면 계급 5개×메뉴 10개 이상×동작 3개=150칸이 넘는 격자가 나온다. 비개발자 1인 사용자에게 이건 사실상 못 쓰는 화면이다.

**How to avoid:**
- 권한 화면은 "역할별 프리셋 + 예외만 조정" 구조로 설계한다(계급 5종의 기본 프리셋을 미리 채워두고, 예외적으로 바꿀 항목만 펼쳐서 수정).
- 관리 화면도 `docs/design/SYSTEM.md` 기준을 그대로 따르되(CLAUDE.md 규칙), 특히 관리 화면은 "이걸 만든 사람이 6개월 뒤에도 설명 없이 쓸 수 있는가"를 UAT 기준으로 삼는다.
- 화면 입력 항목 추가(커스텀 필드), 결재선 편집처럼 구조적으로 복잡한 기능은 먼저 종이/스케치로 오너에게 직접 시연해 "이 정도면 스스로 쓸 수 있다"는 확인을 받은 뒤 구현한다.
- 설정 변경의 "되돌리기"(이전 값으로 복원) 버튼을 기본 제공해, 오너가 실수해도 코드로 돌아가지 않고 화면에서 복구 가능하게 한다.

**Warning signs:**
- 오너가 설정 화면을 열지 않고 "이거 그냥 고쳐줘"라고 요청하는 빈도가 늘어남.
- 권한표 체크박스 격자가 스크롤이 여러 화면 넘어감.
- 설정 JSON 내보내기/가져오기 기능이 "화면 대신 직접 편집"용으로 쓰이기 시작함.

**Phase to address:**
admin-config — 프리셋 기반 UX를 설계 단계에서부터 반영. UAT는 실제 오너가 조작해보는 세션으로 진행.

### Pitfall 13: 커스텀 필드(관리자 정의 입력 항목)가 검증·성능·마이그레이션을 계속 어렵게 만듦

**What goes wrong:**
관리자가 프로젝트·견적 줄·거래처 등에 칸(텍스트·숫자·날짜·선택)을 자유롭게 추가하는 기능은 EAV(Entity-Attribute-Value) 패턴이나 JSONB 컬럼으로 구현되기 쉬운데, 두 방식 모두 타입 검증(숫자 칸에 문자가 들어감), 필수/선택 강제, 목록 정렬·검색 성능, 그리고 향후 이관·백업 시 스키마가 불명확해지는 문제를 만든다. PROJECT.md는 이미 이 항목을 "구조적 결정 — 아키텍처 리서치에서 방식 확정, Pending"으로 표시해뒀다.

**Why it happens:**
"필드를 자유롭게 추가"라는 요구를 가장 쉽게 만족시키는 방법(JSONB 컬럼 하나에 다 넣기)이 가장 유연하지만, 그 유연함이 그대로 검증 부재·인덱스 부재로 이어진다.

**How to avoid:**
- 커스텀 필드는 타입별로 제한된 선택지(텍스트/숫자/날짜/단일선택)만 허용하고, 저장 시 서버가 타입을 검증(숫자 칸에 문자열이 들어가면 저장 거부)한다.
- 목록·검색에 자주 쓰일 것으로 예상되면 JSONB + GIN 인덱스, 아니면 단순 조회만 지원하는 것으로 범위를 좁혀 처음부터 "검색 가능"을 약속하지 않는다.
- 커스텀 필드 개수에 실질적 상한(예: 엔티티당 10개)을 두어 무한정 늘어나는 것을 방지.
- 마이그레이션(이관) 스크립트가 커스텀 필드 스키마 변화에 영향받지 않도록, 핵심 고정 필드와 커스텀 필드 저장소를 명확히 분리한다.

**Warning signs:**
- 커스텀 필드에 잘못된 타입 값이 저장되어 화면에서 계산/정렬 오류 발생.
- 목록 화면이 커스텀 필드가 늘어날수록 느려짐.
- 커스텀 필드가 실제로는 3~5개 안팎만 쓰이는데 구현은 완전 범용 EAV로 과설계됨(Pitfall 1의 축소판).

**Phase to address:**
admin-config — 아키텍처 리서치(ARCHITECTURE.md)에서 방식을 확정한 뒤 구현. data-model 단계에서 스키마 분리를 미리 반영.

### Pitfall 14: AI 에이전트(Claude Code) 특유의 유지보수 드리프트

**What goes wrong:**
비개발자 1인 + Claude Code 조합에서는 (1) 컨벤션이 세션마다 조금씩 달라지고, (2) 테스트가 "통과는 하지만 실제 동작을 검증하지 않는" 형태(모킹 과다, 스냅샷 테스트 남발)로 쌓이고, (3) 타입 안전성을 포기한 `any`가 조용히 늘어나고, (4) "이 라이브러리가 편할 것 같다"는 이유로 의존성이 계속 추가된다. 260907은 `any` 29건, 260807도 `any` 29건이 이미 확인됐다 — "any 금지"라는 CLAUDE.md 규칙이 있어도 실행 중 새어나간다는 실증이다.

**Why it happens:**
검토자가 없는 1인 개발 환경에서는 Claude Code가 스스로 자기 코드를 리뷰하는 구조라, 컨벤션 위반이나 타입 회피를 잡아낼 두 번째 시선이 없다. 세션이 끊기고 새로 시작할 때마다 이전 세션의 암묵적 규칙(변수명 패턴, 에러 처리 방식)을 다시 추론해야 해서 조금씩 달라진다.

**How to avoid:**
- CLAUDE.md의 "any 금지"를 린트 규칙(`no-explicit-any` 등)으로 CI에 강제해, 사람이 매번 검토하지 않아도 기계가 막게 한다.
- 새 의존성 추가는 "이유 한 줄 + 승인"을 커밋 메시지 규칙으로 강제(CLAUDE.md에 이미 명시) — 이걸 훅(pre-commit)으로 자동 점검(예: `package.json` diff가 있으면 커밋 메시지에 이유가 있는지 체크).
- 테스트는 "행동을 검증하는가"를 기준으로 리뷰한다: 실제 DB/HTTP 요청 없이 모킹만으로 통과하는 테스트 비중이 높아지면 경고. 핵심 흐름(로그인→지출결의→결재→손익 반영)은 최소한 통합 테스트로 실제 동작을 확인.
- 세션 종료 시 컨벤션을 코드가 아니라 문서(CLAUDE.md, ARCHITECTURE.md)에 반영해 다음 세션이 그대로 이어받게 한다. 단, CLAUDE.md 자체는 자주 바뀌면 캐시가 깨지므로(이미 프로젝트 규칙에 명시) 컨벤션 변경은 세션 끝에 몰아서 반영.
- `/gsd-code-review`, `/review` 같은 코드 리뷰 게이트를 페이즈마다 실제로 통과시키고 건너뛰지 않는다(이미 워크플로에 있음 — 실행되는지가 관건).

**Warning signs:**
- `any` 사용 건수가 페이즈마다 늘어남(0에서 시작해 조용히 증가).
- 테스트는 늘어나는데 실사용 버그가 줄지 않음(테스트가 실제 결함을 못 잡는다는 신호).
- 같은 종류의 코드(예: 폼 검증)가 파일마다 다른 패턴으로 작성됨.
- `package.json` 의존성 수가 기능 대비 빠르게 늘어남.

**Phase to address:**
전 페이즈 공통 — hardening 단계에서 `any`/미검증 테스트/의존성 전수 점검을 한 번 더 수행.

## Performance Traps

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|-----------------|
| 손익 드릴다운을 매번 전체 조인으로 계산 | 손익 화면 로딩 느림 | 정산 시점 스냅샷 테이블 + 필요 시에만 상세 조인 | 프로젝트 수백 건 이상 누적 시 |

| Cloud Run 콜드스타트 시 DB 커넥션 초기화 지연 | 첫 요청 응답이 느림/타임아웃 | 최소 인스턴스 1개 유지(비용과 트레이드오프) 또는 커넥션 풀 워밍 | 사용자가 몰리는 마감 시점(월말) |

## UX Pitfalls

| Pitfall | User Impact | Better Approach |
|---------|-------------|-------------------|
| 역할별 첫 화면(랜딩)이 없어 로그인 후 뭘 해야 할지 모름 | 기획PM은 지출결의 대기, 팀장은 결재 대기, 대표는 손익 요약이 필요한데 다 같은 대시보드를 봄 | 역할별 첫 화면 지정: 기획PM→내 진행 프로젝트/미입력 지출결의, 팀장→결재 대기함, 대표→전체 손익 요약 |
| 마감 기한이 임박해야만 알림 | 습관 형성 실패(부차 목적인 "지출 규칙 습관화" 무산) | 여유 있는 사전 알림 + 임박 알림 이중화(PROJECT.md 요구사항과 일치) |

| 관리 화면 진입 경로가 숨겨져 있어 오너도 못 찾음 | 설정을 아예 안 씀 → 코드로 회귀(Pitfall 12) | 관리자 메뉴를 항상 눈에 띄는 고정 위치에 |

## "Looks Done But Isn't" Checklist

- [ ] **결재 완료**: 승인 완료 버튼이 동작해도, 되돌아가기(반려)·위임·빈 자리 건너뜀 케이스까지 실제 데이터로 확인했는가.
- [ ] **손익 계산**: 합계 숫자가 보여도, 근거 줄 드릴다운과 계산식 노출 화면까지 연결됐는가(Pitfall 6).
- [ ] **권한/정보노출**: 화면에서 숨겨졌어도, 같은 데이터를 내려주는 API/엑셀 내보내기/자동완성도 확인했는가(Pitfall 3).
- [ ] **설정 화면**: 값을 바꿔도, 서버 로직이 실제로 그 값을 읽는지 통합 테스트로 확인했는가(Pitfall 2).
- [ ] **데이터 이관**: 표별 행수가 맞아도, 한글 인코딩·시각·금액 합계까지 샘플 대조했는가(Pitfall 8).
- [ ] **보안 감사**: `/cso`가 "통과"했다고 해도, 주민등록번호/계좌번호 저장 방식·CSRF·세션 정책을 구체적으로 확인했는가(Pitfall 10, 11의 SecurityMistakes).
- [ ] **백업**: 백업 스케줄이 설정돼 있어도, 실제로 복원해본 적이 있는가(단순히 "백업 자동" 요구사항 충족만으로는 부족).
- [ ] **알림**: 알림이 발송돼도, 중복 발송 방지와 발송 실패 시 재시도/가시성이 있는가.

## Recovery Strategies

| Pitfall | Recovery Cost | Recovery Steps |
|---------|-----------------|-----------------|
| 결재선 편집으로 진행 중 문서가 깨짐 (Pitfall 4) | MEDIUM | 감사 로그로 변경 전 상태 복원, 영향받은 문서 목록을 추출해 수동으로 재확인·재승인 |
| 손익 숫자 소급 변경으로 신뢰 붕괴 (Pitfall 5) | HIGH | 설정 변경 이력에서 "이전 계산식 버전"을 되살려 과거 확정 숫자를 재현·공개, 이후 스냅샷 방식으로 긴급 전환 |
| 이관 후 인코딩 깨짐 발견 (Pitfall 8) | LOW~MEDIUM | 원본 덤프가 남아있으므로(멱등 스크립트) 재이관 실행, 깨진 컬럼만 원본에서 재변환 |
| 병행 기간 인트라넷에 데이터가 계속 쌓임 (Pitfall 9) | LOW | 컷오버 시점 이후의 인트라넷 신규 행만 다시 추출해 새 시스템에 수동/스크립트 재입력 |
| 관리 화면이 안 쓰이고 코드로 회귀 (Pitfall 12) | MEDIUM | 실제 사용 로그를 봐서 안 쓰이는 설정 화면을 프리셋 중심으로 재설계, 오너와 직접 세션으로 재검증 |
| `any`/미검증 테스트 누적 (Pitfall 14) | MEDIUM | 페이즈 사이 정기 청소 페이즈(hardening)를 두고 린트 강제 + 핵심 플로우 통합 테스트로 교체 |

## Pitfall-to-Phase Mapping

| Pitfall | Prevention Phase | Verification |
|---------|--------------------|----------------|
| 1. 과잉설계 재발 | setup | 스코프 문서에 "이번에 안 만드는 것" 명시, 페이즈 규모가 인트라넷 대응 기능의 3배를 넘지 않음 |
| 2. 설정 지옥 | admin-config | 설정 키마다 "서버가 읽는다" 통합 테스트 존재 여부 |
| 3. 권한×정보노출 누수 | data-model & auth | 역할별 API 직접 호출 회귀 테스트 통과 |
| 4. 결재선 편집이 진행 문서 파괴 | core-ledger | 결재선 변경 후 진행 중 문서 상태 불변 테스트 |
| 5. 계산식 변경이 과거 숫자 소급 변경 | P&L | 정산 확정 후 설정 변경 시 확정 숫자 불변 테스트 |
| 6. 손익 신뢰 붕괴 | P&L | 드릴다운·구버전 대조 화면이 UAT 항목에 포함 |
| 7. 법인카드/지출결의 이중계산 | core-ledger | 동일 견적 줄에 두 출처 동시 존재 불가 제약 테스트 |
| 8. 이관 인코딩/타임존/고아행 | migration | 행수 검증 외 샘플 대조·합계 대조 체크리스트 통과 |
| 9. 평문 비밀번호/병행 규율 붕괴 | migration | 컷오버 후 인트라넷 쓰기 라우트 비활성 확인, 비밀번호 컬럼 이관 안 됨 확인 |
| 10. 개인정보(주민번호/계좌) 법 위반 | hardening (`/cso`) | 암호화 컬럼·접근 로그·보존기간 존재 확인 |
| 11. Cloud Run/Cloud SQL 비용·커넥션 | setup, hardening | 부하 테스트로 커넥션 한도 초과 없음 확인, 월 청구서 검토 |
| 12. 관리 화면 복잡도로 코드 회귀 | admin-config | 오너 본인이 직접 조작하는 UAT 세션 통과 |
| 13. 커스텀 필드 검증/성능 | admin-config (설계는 data-model) | 잘못된 타입 저장 차단 테스트, 목록 성능 확인 |
| 14. AI 에이전트 유지보수 드리프트 | 전 페이즈 + hardening | 린트(`no-explicit-any`) CI 강제, 정기 코드 리뷰 게이트 실제 실행 |
