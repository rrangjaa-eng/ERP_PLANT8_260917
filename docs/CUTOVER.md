## 3. 전환일

전환 시각 앞뒤 입력은 멈춘다. 도구가 거부하면 이유대로 한다: `confirm_mismatch`(사이에 입력) → 5번부터, `backup_not_fresh`(백업이 3시간보다 오래됨) → 4번부터, `already_cut_over` → 다시 돌리지 않고 §4로 간다.

| 단계 | 누가 | 증거 |
|---|---|---|
| 1 델타 재승격 — §2 (c′) 뒤에 main에 들어온 마이그레이션 · 코드가 있으면 §1 (b)~(e) 반복. 없으면 건너뛰고 운영 `cutover.yml` 읽기 전용 실행으로 Job · 건수만 본다 | 사용자 | 실행 링크 또는 「델타 없음」 한 줄 |
| 2 점검 시간 공지 — 전환 시각 앞뒤 입력 멈춤(§6 점검 시작 문안) | 관리자 | 공지 시각 |

| 8 연습용 마스터 **보관** — 기존 보관함 · `bank_transfer`는 제외 | 관리자 | 각 마스터 화면 기본 목록에 실제 쓰는 행만 있고 `/admin/archive`에 보인다 |

| (9 아래) 전환 뒤 늦게 온 비용(인트라넷에서 끝난 프로젝트)도 이 길로 그 프로젝트를 새 시스템에 등록해 올린다 | 관리자 | 건별 등록 기록 |

## 5. 되돌릴 수 없는 문

| 문 | 직전에 할 것 |
|---|---|
| 첫 승격 — 9/18로 못 돌아간다. 수동 백업이 유일한 복원점이고 PITR이 꺼져 있으면 더 그렇다 | §1 (c) 수동 백업 SUCCESSFUL |
| apply — 지운 행은 백업 복원으로만 돌아온다(복원은 [`RESTORE.md`](RESTORE.md) §3) | §3 4번 수동 백업 · 5번 dry-run 확인 문자열 |
| 전환 뒤 첫 번호 — 재사용하지 않는다 | 번호 서식 · 시작값 확인 |
| 운영 시크릿 버전 삭제 — 하지 않는다 | 필요하면 새 버전을 더하기만 한다 |
| `bank_transfer` 지급 방식 값 — 보관 · 개명하지 않는다 | 마스터 정리에서 제외 |

전환 뒤 막힘 — 지급 · 결재가 막히면 기본은 앞으로 고치기다. 급한 지급은 은행 사이트에서 직접 한다. 인트라넷 입력 재개는 사용자만 정한다(백업 복원은 전환 뒤 입력을 잃는다).

## 6. 공지 문안

**연습 안내**(계정 발급 때 필수): 전환일 전 입력은 연습용이고 전환일에 모두 지워짐 · 실제 결재는 인트라넷 · 영수증 원본은 인트라넷 절차대로 · 연차 조정 · 증빙 일괄 등록은 연습 금지.

**결재 마감 공지**(전환 3영업일 전): 인트라넷 결재 · 지급 대기는 전환 전날까지 끝낸다. 결재된 건의 지급도 인트라넷 기록대로 마무리한다. 못 끝낸 건만 전환 뒤 새 시스템에 다시 올린다.

**점검 시작 공지**(전환일): 점검 시각을 적는다. 그 사이 입력을 멈춘다. 끝나면 다시 알린다.

**전환 공지**: 접속 주소는 운영 `status.url` 실측값.
- 전환일부터 새 시스템만 쓴다. 인트라넷은 조회만 한다.
- 예외 하나: 전환 전 결재된 건의 지급 처리 기록(경영관리).
- 법인카드는 사용일 기준 — 전환일 전 사용분은 인트라넷에서 마감한다.
- 2026년 업무는 인트라넷에만 있고 새 시스템 프로젝트 번호는 27001부터다.
- 인트라넷에서 끝난 프로젝트에 늦게 온 비용도 새 시스템에 그 프로젝트를 등록해 올린다.
