# 공휴일 되돌리기 = 복원 · 보관함 공휴일 — 점검표
화면: app/(app)/admin/holidays/, app/(app)/admin/archive/
기준: BRIEF.md · frontend.md 화면 사용성 원칙 · CHECKLIST.md §1 · SYSTEM.md §7-6 · §7-7

지금 화면(고치기 전): 공휴일 삭제는 행을 지우고, 결과 줄 「되돌리기」는 같은 값으로 addHolidayAction을 다시 부른다(새 id). 보관함에는 공휴일이 없다. 보관함 복원 실패는 원인 없이 `복원 · 실패 · 다시 시도` 하나.
고칠 계획: 결과 줄 문구 · 버튼 · 배치는 그대로(A-6), 되돌리기가 같은 행을 복원(restoreHolidayAction). 보관함에 「공휴일」 행이 생기고, 복원 거부는 원인(「 · 」 앞부분)을 실은 오류 토스트.

## 원칙
- [x] 안내 문구: 화면의 모든 설명문을 셌다. 남긴 것은 오류·되돌릴 수 없는 일·잠김뿐이고 명사형 한 줄이다 — 근거: 새 문구는 거부 원인 둘뿐(`오늘·지난 날짜 · 복원 불가` · `이미 공휴일(이름) · 복원 불가`, 명사형). 화면엔 「 · 」 앞부분만 결과 줄(`되돌리기 실패 · …`)·토스트(`복원 · 실패 · …`)에 실린다. 설명문 추가 0
- [x] 결정 최소: 알 수 있는 값은 기본값으로 채웠고, 시스템이 계산할 것을 묻지 않는다 — 근거: 되돌리기 · 복원은 입력 없이 한 번 누름. 대체일 재배치는 restoreHoliday가 재계산(사용자에게 묻지 않음)
- [x] 할 수 없는 선택지는 숨기거나 비활성화했다 — 근거: 거부된 되돌리기는 버튼을 치운다(retry 거짓, undoFailure 단위 테스트). 보관함에서 복원할 수 없는 공휴일 행(지난 날짜 · 공휴일 쓰기 권한 없음)은 「복원」 대신 「—」(독립 검토 지적 반영 — listArchive restorable 통합 테스트 · holidays.spec 「복원」 버튼 0개 단언). 같은 날짜 공휴일 충돌은 그때그때 바뀌는 상태라 원인 토스트로 둔다
- [x] 주 버튼 하나: 이 화면의 다음 행동이 주 버튼 하나로 보인다 — 근거: 버튼 추가 0. 공휴일 화면 1차 버튼 수 1(holidays.spec 「primaryCount = 1」 단언 그대로 통과), 되돌리기 · 복원은 3차 그대로
- [x] 위험한 동작(삭제 등)은 떨어뜨려 두고 위험 색이다 — 근거: 삭제가 되돌릴 수 있는 보관이 됐다 — 확인 창 없이 되돌리기(§7 「확인 창 대신 되돌리기」). 배치 · 색 변경 없음
- [x] 같은 말을 두 번 하지 않는다(라벨과 칸 안 글자, 태그와 줄 등) — 근거: 보관함 행은 종류 칸 「공휴일」 + 이름 칸 `{날짜} {이름}` — 종류를 이름에 다시 쓰지 않는다
- [x] 빈 화면은 설명보다 첫 행동 버튼이 먼저다 — 근거: 빈 화면 변경 없음(보관함 EMPTY 예외 · DECISIONS 2026-09-20 그대로)
- [x] 키보드만으로 끝난다(표는 엑셀 키 구성) — 근거: 결과 줄 되돌리기는 autoFocus 그대로, 복원된 행의 삭제 버튼이 포커스를 받는다(holidays.spec 「toBeFocused」 단언 통과). 보관함 복원은 기존 Button
- [x] 같은 종류의 행동은 같은 모양이다(링크·버튼 섞지 않음) — 근거: 되돌리기 · 복원 모두 기존 3차 Button. 실패 표기는 기존 결과 줄 · 토스트(tone error) 재사용
