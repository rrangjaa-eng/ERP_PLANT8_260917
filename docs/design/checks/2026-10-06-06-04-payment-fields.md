지금 화면(착수 전, 06-03 뼈대): 지급 전 섹션은 `지급 예정일 · 지급 방식` 두 읽기 행뿐이라 지급 총액 · 이체액이 보이지 않는다. 1차 `지급 완료`는 오늘 · 이체액 = 지급 총액으로만 보낸다. 지급 총액이 바뀐 거부 뒤 다시 읽지 않아 같은 거부가 되풀이된다(06-03 검토 P2-1).

## 원칙
- [x] 안내 문구: 화면의 모든 설명문을 셌다. 남긴 것은 오류·되돌릴 수 없는 일·잠김뿐이고 명사형 한 줄이다 — 근거: 새 글자는 칸 오류(「Error — 이체액 칸」 셋 · 「Error — 차이 사유 칸」 · 05 DATE_FORMAT_ERROR)와 서버 계산 힌트 `지급 총액 N · 차이 ±N`뿐(UI-SPEC Copywriting 원문 그대로 — action-row.ts 상수). 설명문 · 도움말 0 · Task 2: 막힘 이유 셋(`증빙 없음 · 기안자 {이름}` · `{방식} · {종류} 짝 아님 · 짝 설정은 관리자` · `지급 총액 볼 권한 없음 · 노출 설정은 관리자`)은 행동 줄 이유 자리(`block`) 한 줄, 예정일 힌트 `지급 총액 {전} → {후}`는 서버 두 값이 다를 때만(같으면 없음)
- [x] 결정 최소: 알 수 있는 값은 기본값으로 채웠고, 시스템이 계산할 것을 묻지 않는다 — 근거: 지급일 기본 오늘(KST — 서버가 정함), 이체액 기본 = 서버 지급 총액이고 안 고친 동안 지급일을 바꿔 지급 총액이 바뀌면 칸이 새 값을 따른다. 지급 총액 · 차이 · 공급가 역산은 서버(`previewPayable` · `decidePayable`)만 셈한다 — 화면은 칸 값과 서버 지급 총액을 비교만(차이 사유 칸을 세울지) · Task 2: 예정일 칸은 지금 값으로 채워 열리고, dirty 판정 · 1차 전환은 서버와 같은 순수 함수 `scheduleDirtyBar`(action-row.ts)가 정한다
- [x] 할 수 없는 선택지는 숨기거나 비활성화했다 — 근거: 칸은 1차가 `지급 완료`(P4 지급 권한자)일 때만 선다. 차이 사유 칸은 이체액 ≠ 지급 총액일 때만. 지급 권한 없는 사람 · 대표는 칸 · 버튼 0(06-03 E2E 「대표 — 이 페이즈 버튼 0」 그대로 녹색) · Task 2: 3차 `지급 예정일 바꾸기`는 지급 전 지급 권한자(1차 `지급 완료` 행)에게만 — 지급 뒤 · 권한 없음 · 대표는 값만. 증빙 없음(P3) · 짝 아님 · 금액 볼 권한 없음은 `지급 완료` aria-disabled + 이유(Button disabledReason — 숨기지 않고 왜 막혔는지 보인다, UI-SPEC P3 행). Ctrl+Enter도 막힌 1차를 부르지 않는다(E2E 「증빙 없음 막힘」 — 지급 기록 0)
- [x] 주 버튼 하나: 이 화면의 다음 행동이 주 버튼 하나로 보인다 — 근거: 칸 옆 저장 버튼 · `Form.Actions` 없음(§7-15 「Form.Actions 없는 단일 칸 폼」) — 지급일 · 이체액 · 차이 사유는 행동 줄 1차 `지급 완료` 하나가 함께 보낸다(SP-3 ①) · Task 2: 예정일 칸에도 저장 버튼 없음 — dirty인 동안 1차 자리가 `예정일 저장 Ctrl+Enter` 하나로 바뀌고 `지급 완료`는 그 자리에 없다(E2E 「지급 예정일 제자리 저장」 toHaveCount(0))
- [x] 위험한 동작(삭제 등)은 떨어뜨려 두고 위험 색이다 — 근거: Task 1 · 2 범위에 위험 동작 없음(예정일 저장은 되돌릴 수 있는 날짜 편집 — 확인 모달 없음, UI-SPEC 「제자리 편집」). 지급 취소(2차 · 확인 모달)는 Task 3에서 이 점검표를 다시 확인한다
- [x] 같은 말을 두 번 하지 않는다(라벨과 칸 안 글자, 태그와 줄 등) — 근거: 이체액 라벨은 지급 방식 이름 하나(계좌이체 `이체액` · 법인카드 `카드 결제액` · 현금 `현금 지급액`), 힌트는 차이가 있을 때만(같으면 줄 없음 — `지급 총액과 같음` 없음). 지급 뒤 읽기 줄은 지급일 · 2행 처리한 사람 / 이체액 · 2행 `지급 총액 · 차이 · 공급가 역산`(차이 0이면 차이 묶음 없음)
- [x] 빈 화면은 설명보다 첫 행동 버튼이 먼저다 — 근거: 빈 화면 상태 없음(섹션은 결재 통과 문서에만). 값 없음은 `—`
- [x] 키보드만으로 끝난다(표는 엑셀 키 구성) — 근거: 칸의 `Enter`는 제출을 막고(제자리 칸 §7-15), 1차는 Ctrl+Enter(06-03 그대로). 칸 오류가 서면 그 칸으로 포커스(E2E 「차이 사유」 toBeFocused) · Task 2: 예정일 칸 `Enter` 제출 막음 · `Esc` 서버 값으로 되돌리고 닫음 → 포커스 3차 버튼 · `Ctrl+Enter` = 그때 보이는 1차, 저장 뒤 포커스는 돌아온 1차(E2E toBeFocused 둘)
- [x] 같은 종류의 행동은 같은 모양이다(링크·버튼 섞지 않음) — 근거: 새 버튼 없음. 칸은 05 지출결의 폼과 같은 `expense.module.css` textInput · numeric · date 입력과 `ui/form` Form.Field · Form.Hint · Form.Error · Task 2: 3차 `지급 예정일 바꾸기`는 05 지출결의 폼 `바꾸기`와 같은 `valueRow` + `fill` + Button tertiary, 예정일 칸은 지급일 칸과 같은 Form.Field width="short"(`--field-w-short`) · date 입력
