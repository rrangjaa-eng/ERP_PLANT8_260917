## 지금 화면 기준으로 어긋난 것(고치기 전)
- (Task 1 · V5) 지급 대상에서 고른 계좌이체 건을 은행에 올릴 파일로 받는 길이 없다 — 경영관리가 계좌 · 금액을 손으로 옮겨 적는다(옛 CSV도 막힘 판정 · 기록 없음).
- (Task 2 · V5) 파일에 못 담는 건(현금 · 계좌 없음 · 은행 이름 오류 등)을 화면이 말하지 않고, 이미 받은 건인지 알 길이 없다(이중 이체 위험).
- (Task 3 · V14) `지급 완료` 확인 창에 같은 지급처로 가는 여러 건의 합이 보이지 않는다.

## 원칙
- [x] 안내 문구: 화면의 모든 설명문을 셌다. 남긴 것은 오류·되돌릴 수 없는 일·잠김뿐이고 명사형 한 줄이다 — 근거: (Task 1) 더한 글자는 버튼 이름 `이체 파일 받기` · 비활성 이유 `고른 건 없음`(1차와 같은 글자 · info 톤) · 결과 글자 `{HH:mm} 이체 파일 {N}건`(기존 결과 글자 자리 · aria-live) · 실패 토스트 `이체 파일 받기 · 실패 · 다시 시도` — 설명문 0.
- [x] 결정 최소: 알 수 있는 값은 기본값으로 채웠고, 시스템이 계산할 것을 묻지 않는다 — 근거: (Task 1) 확인 창 없음 — 지금 고른 행(모든 쪽)과 표의 이체액 편집값을 그대로 보내고, 은행 코드 · 계좌 · 금액 글자 · 파일 이름은 서버가 만든다.
- [x] 할 수 없는 선택지는 숨기거나 비활성화했다 — 근거: (Task 1) 고정 게이트(지급 쓰기 ∧ 계좌 해제 ∧ 금액 보임)가 거짓이거나 1024 미만이면 버튼 · 이유 둘 다 DOM에 없다(page.tsx canExportBankTransferFile → prop). 고른 건 0이면 aria-disabled + 이유(E2E 「고른 건 0」).
- [x] 주 버튼 하나: 이 화면의 다음 행동이 주 버튼 하나로 보인다 — 근거: 1차는 `지급 완료 N` 그대로, `이체 파일 받기`는 2차(variant="secondary").
- [x] 위험한 동작(삭제 등)은 떨어뜨려 두고 위험 색이다 — 근거: 해당 없음 — 파일 받기는 되돌릴 수 있는 읽기 동작(UI-SPEC Destructive confirmation).
- [x] 같은 말을 두 번 하지 않는다(라벨과 칸 안 글자, 태그와 줄 등) — 근거: 결과 글자는 일괄 지급 결과와 같은 한 자리(가장 마지막 동작만 — 파일 요청 때 지급 결과를, 지급 확인 때 파일 결과를 지운다). 고른 건 0 이유는 UI-SPEC V5 「비활성」 행대로 버튼마다 선다(같은 reasonId 공유는 선택 사항).
- [x] 빈 화면은 설명보다 첫 행동 버튼이 먼저다 — 근거: 해당 없음 — 빈 화면 변경 0(빈 목록에서도 필터 줄은 그대로).
