## 지금 화면 기준으로 어긋난 것(고치기 전)
- 단건 지급 섹션 `지급일` 날짜 칸에 `max`가 없어 달력에서 내일 이후를 고를 수 있고, 미래 날짜로 미리보기 · 지급 완료가 그대로 통과해 돈이 안 나간 날로 지급 기록이 선다(D-6518).
- `지급 예정일` 칸은 미래가 맞는 자리 — 바꾸지 않는다(V13 「대상」).

## 원칙
- [x] 안내 문구: 화면의 모든 설명문을 셌다. 남긴 것은 오류·되돌릴 수 없는 일·잠김뿐이고 명사형 한 줄이다 — 근거: 새 글자는 오류 한 줄 `미래 지급일 · 오늘까지 날짜 고르기`(UI-SPEC V13 확정 문구 · 「원인 · 다음 행동」)뿐. 칸 위 · 옆 안내 0 — `max`가 달력에서 미래를 못 고르게 한다(행동으로 유도).
- [x] 결정 최소: 알 수 있는 값은 기본값으로 채웠고, 시스템이 계산할 것을 묻지 않는다 — 근거: 기본값 = 서버 KST 오늘(view.payDate) 그대로 · `max`도 같은 서버 값(브라우저 시계 없음). E2E `toHaveValue(today)` · `toHaveAttribute("max", today)`.
- [x] 할 수 없는 선택지는 숨기거나 비활성화했다 — 근거: 날짜 고르기에서 오늘 뒤 날짜가 비활성(`max`). 손으로 친 값은 서버 미리보기가 칸 오류로 막는다(클라이언트 선비교 없음 — V13 「밤새 연 화면」).
- [x] 주 버튼 하나: 이 화면의 다음 행동이 주 버튼 하나로 보인다 — 근거: 1차 `지급 완료` 그대로 · 새 버튼 0.
- [x] 위험한 동작(삭제 등)은 떨어뜨려 두고 위험 색이다 — 근거: 해당 없음 — 위험 동작 변경 0.
- [x] 같은 말을 두 번 하지 않는다(라벨과 칸 안 글자, 태그와 줄 등) — 근거: 오류는 칸 아래 `Form.Error` 한 자리(기존 날짜 형식 오류와 같은 자리) — 행동 줄 왼쪽에 다시 쓰지 않는다(서버 거절도 validationErrors.payDate → showFieldErrors 길).
- [x] 빈 화면은 설명보다 첫 행동 버튼이 먼저다 — 근거: 해당 없음 — 빈 화면 변경 0.
- [x] 키보드만으로 끝난다(표는 엑셀 키 구성) — 근거: 날짜 칸 키 처리(Enter 제출 막음) 그대로 · 1차를 누르면 거절 뒤 포커스가 지급일 칸으로 간다(E2E `toBeFocused`).
- [x] 같은 종류의 행동은 같은 모양이다(링크·버튼 섞지 않음) — 근거: 버튼 · 링크 변경 0.
