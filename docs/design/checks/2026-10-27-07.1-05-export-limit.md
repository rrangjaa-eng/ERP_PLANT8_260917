# 파일 받기 5,000건 상한 — 점검표
화면: app/(app)/expenses/evidence/, app/(app)/admin/action-log/
기준: BRIEF.md · frontend.md 화면 사용성 원칙 · CHECKLIST.md §1 · SYSTEM.md §7-1(버튼 비활성 이유 · DR-10 · DR-11) · 07.1-UI-SPEC W13

지금 화면(main 0309438c): 증빙 목록 `파일 받기`와 행동 로그 `Excel 내보내기`는 결과가 아무리 커도 활성이고, 큰 결과를 받으려다 서버가 오래 붙잡힌다. 거래처 `파일 받기`만 5,000곳 상한 + 비활성 + 이유 한 줄이 있다.
계획: 두 단추를 거래처와 같은 꼴(ui/button `disabledReason` · `reasonTone="info"`)로 — 건수가 5,000을 넘으면 `aria-disabled` + 옆에 이유 한 줄(`aria-describedby`), 서버도 같은 수로 거부. 증빙 이유 `5,000건 넘음 · 필터나 검색으로 줄이기`, 행동 로그 이유 `5,000건 넘음 · 기간이나 필터로 줄이기`. 단추 글자 · 위치 · 위계(2차) 불변.

## 원칙
- [x] 안내 문구: 화면의 모든 설명문을 셌다. 남긴 것은 오류·되돌릴 수 없는 일·잠김뿐이고 명사형 한 줄이다 — 근거: 새 글자는 5,000건을 넘을 때만 나오는 잠김 이유 한 줄 둘(명사형 · 허용 ① 막힘의 까닭)뿐이고, 5,000건 이하에는 새 글자가 없다. E2E W13이 5,001건에서 이유 줄 글자 일치 · 5,000건에서 이유 줄 0을 잰다
- [x] 결정 최소: 알 수 있는 값은 기본값으로 채웠고, 시스템이 계산할 것을 묻지 않는다 — 근거: 건수는 서버가 목록과 같은 집합으로 센 수(증빙 `list.total.count` · 행동 로그 `rows.length`)를 그대로 써서 사용자가 고르거나 세는 것이 없다. 상한 5,000은 거래처와 같은 상수(코드 값 — 새 설정 0)
- [x] 할 수 없는 선택지는 숨기거나 비활성화했다 — 근거: 받을 수 없는 5,001건 이상에서 단추를 `aria-disabled="true"`로 비활성(네이티브 disabled 아님 · DR-11)하고 까닭을 단추 옆에 둔다. 0건 증빙의 기존 비활성(빈 결과 줄 가리킴)은 우선순위를 그대로 지킨다
- [x] 주 버튼 하나: 이 화면의 다음 행동이 주 버튼 하나로 보인다 — 근거: 두 단추 모두 기존 2차(`secondary`)이고 1차 버튼을 더하거나 옮기지 않았다. 기존 E2E(evidence-list-audit ① 1차 DOM 수)가 새 prop 뒤에도 통과
- [x] 위험한 동작(삭제 등)은 떨어뜨려 두고 위험 색이다 — 근거: 위험 동작을 더하거나 옮기지 않았다(행동 로그 `정리` 단추 자리 · 모양 그대로, 그 건수 `pruneCount`는 건드리지 않음)
- [x] 같은 말을 두 번 하지 않는다(라벨과 칸 안 글자, 태그와 줄 등) — 근거: 이유 줄은 단추당 하나(`Button`의 `disabledReason` 한 곳)이고 증빙 0건에는 이유 줄을 더하지 않아 빈 결과 줄과 같은 말을 두 번 하지 않는다(`tooMany`는 0건이 아닐 때만)
- [x] 빈 화면은 설명보다 첫 행동 버튼이 먼저다 — 근거: 빈 화면 갈래를 바꾸지 않았다
- [x] 키보드만으로 끝난다(표는 엑셀 키 구성) — 근거: 비활성도 `aria-disabled`라 Tab 순서에 남고 포커스되며 이유가 `aria-describedby`로 읽힌다(Button 기존 계약 · DR-11). 표 키 구성은 건드리지 않았다
- [x] 같은 종류의 행동은 같은 모양이다(링크·버튼 섞지 않음) — 근거: 증빙 · 행동 로그 · 거래처 세 파일 받기 단추가 같은 2차 `Button` + `disabledReason`(info 색) 꼴로 맞춰졌다. 새 행동 0
