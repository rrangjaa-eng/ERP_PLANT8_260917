## 원칙
- [x] 안내 문구: 화면의 모든 설명문을 셌다. 남긴 것은 오류·되돌릴 수 없는 일·잠김뿐이고 명사형 한 줄이다 — 근거: 요청 화면은 막힘 한 줄(`새 희망일 없음 · 날짜 고르기` / `사유 없음 · 사유 적기`)과 서버 거부 글자뿐. 상세의 처리 줄 aux 둘(`희망 사유` · `변경 사유`)은 판단 재료(값)이고 설명문이 아니다. 거절 창은 `거절 메모 없음 · 메모 적기` 한 줄. 토스트는 결과 명사형(`변경 요청 · 경영관리 확인 대기` · `변경 승인 · 지급 예정일 MM-DD` · `되돌리기 실패 · {원인}`)
- [x] 결정 최소: 알 수 있는 값은 기본값으로 채웠고, 시스템이 계산할 것을 묻지 않는다 — 근거: `현재 희망일`은 읽기로 보이고 `새 희망일` 최솟값은 내일(min) · 영업일 판정은 서버. 승인은 확인 창 없이 즉시 + 토스트 `되돌리기`(확인 창 대신 되돌리기). 지급 예정일은 승인이 새 희망일로 바로 쓴다(따로 고르지 않는다)
- [x] 할 수 없는 선택지는 숨기거나 비활성화했다 — 근거: 입구 `변경 요청`은 기안자 · 최종 승인 · 미종결 · 미지급 · 이체 파일 밖 · 대기 없음일 때만 DOM에 선다(그 밖 DOM 0 — E2E에서 대표 · 팀장 0 실측). 처리 줄은 `지급 예정일 바꾸기`(expenses.payments write) 권한자에게만. 대기 중이면 `변경 요청` 대신 `요청 철회`. 제출 · 거절 1차는 칸이 비면 aria-disabled + 막힘 한 줄
- [x] 주 버튼 하나: 이 화면의 다음 행동이 주 버튼 하나로 보인다 — 근거: 요청 화면 1차 `변경 요청 Ctrl+Enter` 하나 + 2차 `취소`. 상세 줄 안 행동은 모두 3차(상세의 1차는 기존 결재 · 지급 행동 그대로). 거절 창 1차 `요청 거절` 하나
- [x] 위험한 동작(삭제 등)은 떨어뜨려 두고 위험 색이다 — 근거: 이번 화면에 삭제 · 되돌릴 수 없는 동작이 없다. 거절은 메모 필수 확인 창으로 한 단계 떨어뜨렸고, 상태 글자 `거절`은 danger(DC-1)
- [x] 같은 말을 두 번 하지 않는다(라벨과 칸 안 글자, 태그와 줄 등) — 근거: 대기 줄은 StatusTag `변경 요청 중` + 날짜만(문장 반복 없음). 이력 표 상태 열은 글자 태그 하나, 요청 · 처리 열은 이름 · 시각 + 보조 줄. 지급 대상 행 아래 줄은 `희망 지급일 변경 요청 MM-DD` 한 줄(이체 파일 줄이 있으면 그 줄 우선 — 한 줄만)
- [x] 빈 화면은 설명보다 첫 행동 버튼이 먼저다 — 근거: 요청이 한 번도 없으면 이력 표 DOM 0(빈 표 · 설명 없음). 요청 화면은 빈 칸 + 포커스가 첫 칸(`새 희망일` autoFocus — E2E toBeFocused 실측)
- [x] 키보드만으로 끝난다(표는 엑셀 키 구성) — 근거: 요청 화면 Tab 순서 날짜 → 사유 → 1차 · `Ctrl+Enter` 제출 · `Esc` 취소(입력 있으면 「입력 버리기」 확인, DR1). 날짜 칸의 `Enter`는 제출로 가지 않는다(§7-15). 거절 창 `Ctrl+Enter`. 처리 줄 버튼 · 토스트 `되돌리기`는 Tab으로 닿는 button
- [x] 같은 종류의 행동은 같은 모양이다(링크·버튼 섞지 않음) — 근거: 이동(`변경 요청` → 요청 화면)은 3차 모양 Link, 그 자리에서 실행하는 것(`요청 철회` · `요청 승인` · `요청 거절` · `되돌리기`)은 3차 Button — 기존 `지급 예정일` 줄의 3차 링크 · 버튼 구분과 같다
