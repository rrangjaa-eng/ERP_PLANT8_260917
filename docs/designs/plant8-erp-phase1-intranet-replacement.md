## Problem Statement

PLANT8은 약 10명(30명까지 성장 예정)의 BTL 광고·마케팅 대행사다. 전 직원이 PHP 인트라넷으로 프로젝트·견적·지급요청·법인카드를 매일 처리하지만, 기획본부와 경영관리본부가 프로젝트 하나의 돈을 같은 숫자로 보지 못한다.

사용자의 말 그대로:

- 목적: "프로젝트의 수익율과 수익금액 보기, 증빙과 지출결의서 등의 연결, 현장에서 기타소득 확인증 수집, 기획본부의 업무와 경영관리 본부에서 업무 연결이 안되는 불편함"
- 근본 원인: "기획본부 pm이 구두나 전화로 발주하고 진행한 내용을 나중에 한번에 몰아서 입력하기 때문에 프로젝트 진행 과정을 알 수가 없어. 경영관리와 기획본부에서 보는 매출과 비용의 관점도 달라."
- 맹점: "기획본부에서 본인들이 입력하는 만큼만 프로젝트 비용이라고 인식하고 실제 나가는 비용에 대한 경각심이 없고 … 지출결의나 구매 요청을 몰아서 하거나 갑자기 하기 때문에 자금 관리에도 어려움이 생길 수 있다"
- 크게 만든 이유: "기존 인트라넷이 기능이 너무 없어. 경영관리쪽에서 기획본부의 업무를 파악할 수 있는 동선이 없었다"
- 부차 목적: "기획본부 사람들에게 업무 가이드와 체계를 익숙하게 만들고 싶어"

한 문장으로: **발주하는 순간 "나갈 돈"이 기록되지 않아서, 기획은 실제 비용을 모르고 경영관리는 자금 흐름을 모른다.** 손익 화면이 없어서가 아니라 입력이 늦어서 손익이 틀리고 늦다.

## Demand Evidence

- 전 직원 10명이 오류 많은 인트라넷을 그래도 매일 쓴다. 2026년 1~9월 데이터(`db_backup_260915.sql` 집계): 프로젝트 125건, 견적 줄 1,379행, 지급요청 464건(요청자 11명), 법인카드 사용 433건(작성자 10명), 로그인 세션 7월 한 달 1,453회.
- 인트라넷의 강제력이 곧 채택 지렛대다: 돈이 나가려면 견적 줄 → 지급요청 → 3단 결재를 거쳐야 한다. 사람들은 시스템이 좋아서가 아니라 지급 경로라서 쓴다.
- 사용자는 처음에 "다른 사람이 원한다는 증거는 없다"고 했으나, 인트라넷 사용 자체가 그 증거다. 새 시스템이 인트라넷의 지급 경로를 그대로 이어받으면 수요는 자동으로 따라온다.
- 반대 증거도 있다: ERP 시도 #1(`260807`)·#2(`260907`)는 41일간 1,845커밋, 63만 줄, 1만 3천 개 테스트를 만들었으나 사용자 0, 운영 데이터 0. 시도 #0(`plant8-erp-rebuild`)은 "20명이 쓸 것에 비해 너무 크다"로 폐기. 세 번의 실패 원인은 수요가 아니라 범위와 "다 만든 뒤 옮긴다"였다.

**ERP #2** (`260907`, 진행 중이던 것): TypeScript, React 19 + Vite, Hono 4 on Node 22, Postgres(Cloud SQL), Cloud Run. 메뉴 16, 화면 36(틀 6종 위), 표 70, `/api` 236개, 테스트 약 6,500개, guards 43, CI 5, Claude 훅 11, CSS 토큰 124. 디자인 시스템과 인쇄물 양식 있음. 미결 54건, 인트라넷 이관 파이프라인 `server/도구/이관/` 미완(E4). 문서 md 888파일 15만 9천 줄, `00_이어하기-지시문.md` 1MB. 사용자 판정: "기능은 어느 정도 괜찮은 거 같은데 너무 정리가 안 되어있고 특히 시스템 디자인이 처음 보는 사람들이 알아보기 어렵게 구성되어있어."

**사람의 동선**: 기획본부 PM이 전화·구두로 발주 → 행사 진행 → 나중에 몰아서 견적 줄·지급요청 입력 → 경영관리는 그때 처음 금액을 봄 → 지출결의가 한꺼번에 몰림 → 자금 계획 불가 → 프로젝트 손익은 끝나고도 불명확.

## Target User & Narrowest Wedge

세 사람이 모두 아프다고 답했고(대표·경영관리 담당자·기획본부 PM), 데이터의 출발점은 PM이다.

- **기획본부 PM** (입력자): 발주 순간에 폰에서 30초 안에 "어느 프로젝트에, 어느 거래처에, 얼마, 언제 지급"을 남길 수 있어야 한다. 이 기록이 곧 지출결의 초안이 되어 PM 자신의 일이 줄어야 입력이 지속된다.
- **경영관리 담당자** (감시자): 프로젝트별 예정 지출과 예정 지급일을 보고 이번 달·다음 달 나갈 돈을 미리 안다. 증빙 없는 지출결의를 쫓아다니지 않는다.
- **대표** (판단자): 프로젝트 상세 상단의 네 숫자(견적 / 예정 지출 / 실제 지출 / 손익)로 다음 견적·수주를 판단한다.

사용자는 좁은 조각(스트랭글러, 손익 화면만) 대신 **260907 기능 전부 + 규칙을 1차에 포함**하기로 세 번 확인했다. 그래서 "가장 좁은 조각"은 범위가 아니라 **순서**다: 인트라넷 4기능 동등 + 이전 → 발주 시점 예정 지출 + 진행 현황 → 나머지 기능 정리 + 규칙. 9/30에 뒤쪽이 덜 다듬어져도 앞쪽은 실데이터로 돌아가야 한다.

## Constraints

- **일정**: 2026-09-30 직원 데모(13일). 데모에서 의견을 받고 절체 날짜를 정한다.
- **인력**: 사용자 1인 + Claude Code. 검토자 없음. 회사에 개발자가 없고 사용자는 취미 개발자다. 따라서 **운영은 코드 수정 없이** 관리 화면과 설정으로 되어야 하고, 코드는 한 사람이 Claude Code로 고칠 수 있을 만큼 단순해야 한다. 큐·마이크로서비스·영리한 추상화 금지.
- **호스팅**: 개인 Google 계정의 Cloud Run + Cloud SQL(Postgres)에서 먼저 이전·실행해 보고, 회사 Google Cloud로 옮겨 공개한다. 프로젝트 ID를 코드에 박지 않고, 배포와 이전을 스크립트 한 번으로 재현할 수 있어야 한다. 회사 도메인 Google 로그인은 개인 계정에서 검증할 수 없다.
- **공존**: 절체 전까지 인트라넷은 그대로 쓴다. 직원에게 같은 것을 두 번 입력시키지 않는다.
- **비용**: 구독·라이선스 도구 없음. "비용이 들지 않고 현재 회사에 알맞은 시스템"이 목적.
- **개인정보**: 기타소득 확인증(주민등록번호), 계좌번호, 고객사 행사 참가자 DB가 관련된다. `/cso` 보안 감사 필수. 인트라넷 백업 리포에 직원 비밀번호 평문·계좌 732건·RDS 비밀번호가 들어 있다(값은 이 문서에 싣지 않음).
- **디자인**: 프로젝트 `DESIGN.md` 절차가 우선한다. `docs/design/SYSTEM.md`가 없으면 화면을 만들지 않고 §1(브리프)→§2(발산)→§3(수렴)을 먼저 한다. 이 세션에서는 목업을 만들지 않았다.
- **규모**: 10명 → 30명. 동시 사용자 수십 명 수준이라 성능보다 이식성과 단순함이 우선.

## Premises

사용자가 확인한 9개. 3번과 8번은 제안(축소)을 사용자가 근거를 들어 거부하고 확정했다.

1. **핵심 가치**: 기획본부와 경영관리본부가 프로젝트마다 같은 숫자(견적, 예정 지출, 실제 지출, 손익)를 본다. 이게 안 되면 나머지 기능은 의미 없다.
2. **근본 원인은 입력 시점**: PM이 발주 후 몰아서 입력한다. 1차에 "발주 시점 예정 지출 기록"(발주됨 상태 + 예정 금액 + 예정 지급일)을 넣고, 이 입력은 PM 자신에게 이득이 있어야 한다.
3. **260907 기능 전부를 가져오되 분류표대로 다룬다**: 보완·수정·대체 항목은 1차에 완성하고, 보류 항목(매출·수금·리저브)은 코드는 유지하되 메뉴에서 숨긴다. 9/30까지 신규 구현은 넷(발주 흐름, 증빙 풀, 권한 2축, 설정 6묶음)뿐이고 나머지는 정리·재디자인 + 이전이다. 순서는 인트라넷 4기능 → 예정 지출·진행 현황 → 나머지 정리·규칙. (제안: 5화면으로 못 박고 나머지 숨김. 사용자 거부: "기능이 너무 없어서 크게 만든 거고, 기능은 괜찮은데 정리와 디자인이 문제". 이후 "가볍고 단순하면서도 효율적으로" 요청에 따라 아래 분류표로 합의) 단, 권한 2축·설정 6묶음·증빙 풀·발주 흐름은 260907에 없던 **신규 구현**이며, 체크포인트 규칙에 따라 9/30 이후로 밀릴 수 있다.
4. **260907을 가져와서 깎는다**: 새로 짓지 않는다. `260917`은 260907의 정리본이다. 사용자 요청: "260907을 가져오되 여기에 사용된 코드들을 더 깔끔하게 정리되게".
5. **9/30 데모는 실데이터로**: 인트라넷 2,849행이 이전된 상태여야 의견이 나온다. 이전이 첫 작업이다.
6. **절체 전 이중 입력 없음**: 데모 뒤 절체 날짜를 정하고 그때까지 인트라넷은 그대로 쓴다.
7. **회사 GCP로 옮길 수 있게**: 프로젝트 ID 미고정, 재현 가능한 배포, 이전 스크립트 재실행 가능.
8. **규칙(결재선·증빙 필수 등)도 1차에 넣는다**: 단 데모 반응에 따라 조정할 수 있게 설정으로 켜고 끌 수 있게 한다(260907의 `settings`·`money_rules` 재사용).
9. **화면 기준은 하나**: "처음 보는 직원이 설명 없이 자기 일을 찾는다." `DESIGN.md` 절차로 `SYSTEM.md`를 먼저 확정하고 260907의 틀 6종(AppShell, List, Form, Detail, Dashboard, Phone)과 토큰 124개를 교체해 36화면을 한 번에 바꾼다. 화면을 하나씩 고치지 않는다.

### 용어 정의

- **견적**: 프로젝트의 견적 줄 합계(클라이언트에 제시한 금액).
- **예정 지출**: "발주됨" 상태이면서 종결되지 않았고, 연결된 지출결의가 있더라도 아직 대표 승인 완료되지 않은 금액의 합.
- **발주 연결**: 새 시스템 소유 표 `order_links(order_id, expense_ref, closed_at)`. 절체 전에는 지출결의가 인트라넷에 있어 자동 연결이 불가하므로 PM 또는 경영관리가 발주를 미러된 지출결의에 수동 연결하거나 "종결"한다. **연결된 발주는 그 지출결의가 대표 승인 완료되는 순간 예정에서 빠져 실제로 들어간다**(그 전까지는 예정에 남는다). 종결된 발주는 즉시 예정에서 빠진다. 예정 지급일이 지났는데 미연결인 발주는 경영관리 첫 화면에 목록으로 뜬다. 절체 뒤에는 초안 자동 생성이 연결을 만든다.
- **실제 지출**: 대표 승인까지 완료된 지출결의 + `CARD_USED`(법인카드 사용)의 합. 인트라넷 `pay_status=법카사용`인 견적 줄 행은 `CARD_USED`와 연결만 하고 합산에서 제외한다(이중 계산 방지).
- **손익** = 견적 − (예정 지출 + 실제 지출). 연결된 발주는 지출결의가 대표 승인 완료되는 순간 예정에서 실제로 옮겨 간다. 같은 지출이 두 곳에 동시에 있는 구간도, 어디에도 없는 구간도 없다.
- **시연 데이터**: 데모용 행은 `source='demo'`로 시드한다. 규칙(초안 자동 생성, 알림 1·3·4)은 전역 설정이지만 `source='intranet'`(미러) 행에는 적용하지 않고 `source='erp'`·`'demo'` 행에만 적용한다. 절체 때 `source='demo'` 행은 전부 삭제한다.
- **수익률** = 손익 ÷ 견적. 진행 중 프로젝트도 같은 식으로 실시간 계산.
- **발주됨**: PM이 거래처에 진행을 확정한 순간의 기록(프로젝트, 거래처, 예정 금액, 예정 지급일). 인트라넷 `pay_status`에 없던 상태.
- **실데이터로 동작**: 화면별로 다르다. 프로젝트·견적·지출결의·법인카드 = 미러된 인트라넷 데이터 **읽기**. 결재함 = `source='demo'` 시드 행에서만 쓰기(미러 행은 읽기 전용). 발주 폰 입력 = 실제 쓰기(새 시스템 소유). 연차·증빙 풀 = 새 시스템 소유 쓰기.
- **미러링**: 절체 전까지 인트라넷 DB를 하루 1회 이상 새 DB로 복사하는 것. 미러 행은 인트라넷이 소유하고 새 시스템은 읽기만 한다.

## Cross-Model Perspective

Claude 서브에이전트(이 대화를 보지 않고 요약만 읽음)의 냉정한 읽기. Codex CLI는 이 PC에 없어 대체했다.

- **스틸맨**: 인트라넷은 "돈이 나가려면 여기에 적어야 한다"는 강제력으로 매일 쓰이는 원장이고, 260907은 그 원장에 없는 것(틀·토큰·guards·결재선·증빙·손익)을 이미 갖춰 놓았다. 가장 강한 버전은 인트라넷의 지급 경로를 260907 골격 위로 옮기고 입력 시점을 발주 순간으로 하나만 앞당겨, 두 본부가 프로젝트마다 네 숫자를 같은 화면에서 보는 것.
- **가장 많이 드러내는 문장**: 맹점 문장. "입력하는 만큼만 = 비용"은 비용의 진실 출처가 PM 입력뿐이라는 뜻이라 바꿀 것은 화면 수가 아니라 입력 순간이고, "몰아서·갑자기"는 경영관리의 고통이 금액이 아니라 **시점**이라는 뜻이라 필요한 데이터는 예정 금액 + **예정 지급일**이다. 인트라넷 `pay_status` 다섯 값은 전부 사후 상태이고 "발주됨"이 없다. 세 번의 재구현에서 이 상태 하나가 폰 첫 화면이 된 적이 없다.
- **틀렸다고 본 전제**: 3번. 시도 #0·#1·#2가 같은 이유로 실패했고 4기능짜리 인트라넷이 월 1,453세션이라는 데이터는 "틀이 갖춰져야 쓴다"의 정반대를 말한다. 9/30에 측정 가능한 예측 셋: 이전 실데이터가 1행 이상 붙는 화면 8장 이하, 직원 10명이 "내일 아침 처음 열 화면"으로 적는 화면 5종 이하, 미결 54건 중 닫힌 수 20 미만. 셋 중 둘이 맞으면 나머지 28화면 정리에 쓴 날은 아무도 안 여는 화면에 쓴 것이다.
- **48시간 프로토타입**: 이관(E4 완성, 멱등·재실행 가능, 행수 일치 검증, 차익 불일치 66줄은 표시만) → 화면 4장 실데이터(프로젝트·견적·지출결의+결재함·법인카드, 기존 틀 그대로, 나머지 메뉴는 숨김) → 예정 지출 폰 화면 1장(`purchase_requests` 재사용, 강제는 설정 off 기본) → 프로젝트 상세 네 숫자 + 프로젝트 ID 파라미터화 배포.
- **종합**: 두 시선(진행자 + 서브에이전트)이 독립적으로 3번을 가리켰다. 사용자는 유지를 택했다. 서브에이전트의 예측 셋은 데모 당일 측정해 성공 기준에 넣는다. 서브에이전트가 건너뛰자고 한 SYSTEM.md 확정·틀 교체는 사용자가 명시한 문제("디자인이 처음 보는 사람이 알아보기 어렵다")라 유지한다. 이관 10시간 추정은 근거 없음, 순서만 맞다.

## Recommended Approach

**A + C.** A만이 13일을 지키고, C가 데모를 살아 있는 것으로 만들며 이관 재실행을 강제한다. 사용자 선택.

**정리 원칙** (사용자 요청 "더 깔끔하게 정리"에 대한 경계):
- 정리는 동작을 바꾸지 않는다. 기존 테스트가 정리의 판정 기준이다. 테스트가 깨지면 정리가 아니라 변경이다. 권한 2축·설정 6묶음 재구조와 발주 흐름·증빙 풀은 처음부터 **변경**으로 분류하고, 관련 테스트는 새 구조로 다시 쓴다.
- 리포 밖으로 보낼 것: `00_이어하기-지시문.md`(1MB), `docs/` 중 결정 기록(`90_결정-기록.md`)과 목적(`00_목적.md`) 외의 회의록·점검·인수인계. 별도 보관 폴더나 별도 리포로 옮기고 링크만 남긴다.
- 상태의 단일 출처를 GSD `.planning/`으로 옮긴다. 인수인계 문서 방식은 끝낸다.
- guards 43개는 "데모를 지키는 것"만 남긴다(`screen-hardcoded-style`, `screen-four-states` 등 화면 일관성 guards는 유지, 라운드·에이전트 운영용 훅은 제거).
- 폴더는 처음 보는 사람이 `app/` `server/` `db/` `docs/`에서 자기 일을 찾을 수 있게. `any` 29개 제거, 죽은 라우트·화면은 메뉴 사용 여부로 판정해 제거.
- 정리 작업은 이전·틀 교체·예정 지출보다 뒤에 둔다. 정리가 데모를 밀어내면 안 된다.

**순서** (9/30까지, 뒤가 덜 돼도 앞은 실데이터로 돌아가게):
1. 260907 → 260917 가져오기, CI·테스트 초록 확인, 개인 GCP에 Cloud SQL·Cloud Run 배포 스크립트(프로젝트 ID·리전·DB 접속을 환경 변수로). **로그인**: 개인 GCP 단계는 이메일 + 초기 비밀번호 발급(인트라넷 평문 비밀번호는 이전하지 않음). 회사 GCP에서 Google 로그인으로 바꾸는 건 배포 단위 설정이라 화면 설정이 아니라 환경 변수 `AUTH_PROVIDER`로 둔다.
2. **이관 + 미러링**: `fone_project`→`projects`, `QUOTATION_LINE`→`quotes`/`quote_items`, `QUOTATION_PAYMENT`(승인 상태 포함)→`expenses`/`statuses`, `CARD_USED`→법인카드 사용, `fone_partners`/`fone_client`→`vendors`, `fone_member`→`people`, `REPORT_CATEGORY1/2`→`code_lists`, `fone_project`의 담당자 컬럼→`projects.owner_id`(미러 소유). 담당자가 비어 있으면 팀장이 데모 전 `projects.owner_override`(새 시스템 소유 컬럼)에 지정하고, 권한 판정은 `owner_override`가 있으면 그것을, 없으면 `owner_id`를 쓴다.
   - 경로: 인트라넷 서버에서 `mysqldump` → Cloud Storage → Cloud Run Job이 적재. RDS 직접 연결은 회사 GCP 이후.
   - 멱등·재실행 가능. `intranet_id_map`(원본 표·ID ↔ 새 ID) 매핑표를 두고, 원본에서 사라진 ID는 soft-delete.
   - 미러가 소유하는 컬럼과 새 시스템이 쓰는 컬럼을 분리한다. 새 시스템이 만든 행은 `source='erp'`로 미러 대상에서 제외. 미러 행에 새 시스템이 덧붙이는 값(미사용 표시, 역할·팀, 첨부, `owner_override`, `order_links`)은 별도 컬럼·표에 둔다.
   - 검증: 행수 일치(원본 전체, 고아 견적 줄 5 포함) + 프로젝트별 견적 줄 합계 대 인트라넷 차익. 고아·불일치 66줄은 고치지 않고 `flag` 컬럼으로 표시만. 검증 실패 시 트랜잭션 롤백, 직전 성공본 유지, 실패는 관리 화면 배너로 표시(알림은 7단계라 이 시점엔 없음).
   - 계좌번호 컬럼은 `/cso` 완료 전까지 미러링 제외.
   - **역할·팀은 이 단계에서**: `people.role`(관리자/대표/경영관리/팀장/기획)과 `people.team` 컬럼, 열람 범위 판정(대표·경영관리 전체 / 팀장 자기 팀 / PM 자기 프로젝트)을 넣는다. 초기값은 `fone_member`와 인트라넷의 지정 팀장 5명에서. 역할 관리 화면과 260907 다층 권한 구조 제거는 8단계.

9. 코드 정리(정리 원칙대로), 미결 54건 중 데모를 막는 것만. "막는 것" = 역할별 데모 시나리오 중 하나라도 진행 불가하게 하는 것.

### 권한 2축

사용자의 목적: "초기에 erp시스템을 설치하고 코드를 다시 수정하는 일이 없도록". 회사에 개발자가 없다.

- **역할** = 권한 묶음. 기본 5개: 관리자(사용자 본인), 대표, 경영관리, 팀장, 기획(PM). 관리 화면에서 역할 × 메뉴 × 동작(보기/쓰기/승인) 체크박스. 역할은 표(데이터)라 개수 제한 없음.
- **팀** = 열람 범위. 팀장은 자기 팀, 대표·경영관리는 전체, PM은 자기 프로젝트.
- 사람에게 붙는 건 역할 하나 + 팀 하나. 입사자 추가 = 사람 등록 → 역할·팀 선택. 코드 수정 0.

### 설정 6묶음 (전부 서버가 읽는 것만)

1. **회사**: 상호, 사업자번호, 주소, 로고, 도장 (견적서 PDF에 들어감)
2. **코드표**: 견적 대분류·소분류(인트라넷 16/113 이전), 증빙 종류, 지급 방식, 프로젝트 상태
3. **돈 규칙**: 기타소득 원천징수율, 부가세율, 반올림, 금액 표기
4. **결재와 규칙**: 단계 수와 단계별 역할, 금액 구간별 결재선(예: 100만 원 이하는 팀장까지), `rules.order.due_date_required`(발주 예정 지급일 필수), `rules.expense.draft_from_order`(지출결의 초안 자동 생성, 절체 전 off), `rules.expense.receipt_required`(증빙 필수)
5. **알림**: 규칙 1~4 각각의 on/off, 대상 역할, 시점(일수), 채널
6. **화면**: 역할별 첫 화면, 메뉴 켜기·끄기(보류 기능은 여기서 켬), 회사 휴일

배포 단위 값(`AUTH_PROVIDER`, DB 접속, 프로젝트 ID, 리전)은 설정이 아니라 환경 변수다. 화면 설정에 두지 않는다.

원칙: **화면에 있는 설정 키는 서버 코드에서 반드시 읽힌다.** 설정 키를 레지스트리 한 곳(`server/src/settings/registry.ts` 같은 단일 파일)에 등록하면 설정 화면이 자동 생성된다. 판정 테스트: 레지스트리의 각 키 문자열이 `server/` 안에 `settings.get('<key>')` 리터럴로 최소 한 번 등장하는지 grep. 동적 키(`settings.get(prefix + name)`) 금지. 첫 설치는 시드 스크립트(회사 정보·코드표·역할 기본값)로, 이후는 설정 전체 JSON 내보내기·가져오기(회사 GCP 이식 시 재입력 없음). 설치 마법사는 두지 않는다(설치는 개인·회사 두 번뿐). 260907 설정 136개는 6묶음에 들어가는 것만 남긴다.

**나중에 늘어나면** (사용자 질문 "나중에 설정에서 조절하고 싶은 게 생기거나 역할이 더 늘어나면"):

- 없던 동작(예: 프로젝트 종류별로 결재선을 다르게): 어떤 시스템이든 코드가 필요하다. 레지스트리 구조 덕에 "키 등록 → 서버에서 읽기 → 테스트"의 작은 변경이 되고, Claude Code로 한 시간 단위 일이다. 데모 뒤 요청이 쌓이면 GSD 페이즈 하나로 묶는다.

## The Assignment

코드를 만지기 전에, **기획본부 PM 한 명이 실제로 발주하는 순간(전화나 구두로 거래처에 "진행하세요"라고 하는 그때)에 옆에 앉아서, 그 사람이 폰으로 30초 안에 남길 수 있는 항목이 정확히 무엇인지 적어 오세요.** 프로젝트 이름? 거래처? 금액은 확정인지 대략인지? 지급일은 아는지? 다섯 항목을 넘으면 입력을 안 합니다. 그리고 경영관리 담당자에게 한 가지만 물어보세요.
