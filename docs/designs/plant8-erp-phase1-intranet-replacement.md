## Problem Statement

PLANT8은 약 10명(30명까지 성장 예정)의 BTL 광고·마케팅 대행사다. 전 직원이 PHP 인트라넷으로 프로젝트·견적·지급요청·법인카드를 매일 처리하지만, 기획본부와 경영관리본부가 프로젝트 하나의 돈을 같은 숫자로 보지 못한다.

사용자의 말 그대로:

- 목적: "프로젝트의 수익율과 수익금액 보기, 증빙과 지출결의서 등의 연결, 현장에서 기타소득 확인증 수집, 기획본부의 업무와 경영관리 본부에서 업무 연결이 안되는 불편함"
- 근본 원인: "기획본부 pm이 구두나 전화로 발주하고 진행한 내용을 나중에 한번에 몰아서 입력하기 때문에 프로젝트 진행 과정을 알 수가 없어. 경영관리와 기획본부에서 보는 매출과 비용의 관점도 달라."
- 맹점: "기획본부에서 본인들이 입력하는 만큼만 프로젝트 비용이라고 인식하고 실제 나가는 비용에 대한 경각심이 없고 … 지출결의나 구매 요청을 몰아서 하거나 갑자기 하기 때문에 자금 관리에도 어려움이 생길 수 있다"
- 크게 만든 이유: "기존 인트라넷이 기능이 너무 없어. 경영관리쪽에서 기획본부의 업무를 파악할 수 있는 동선이 없었다"
- 부차 목적: "기획본부 사람들에게 업무 가이드와 체계를 익숙하게 만들고 싶어"

한 문장으로: **발주하는 순간 "나갈 돈"이 기록되지 않아서, 기획은 실제 비용을 모르고 경영관리는 자금 흐름을 모른다.** 손익 화면이 없어서가 아니라 입력이 늦어서 손익이 틀리고 늦다.

## Demand Evidence

- 전 직원 10명이 오류 많은 인트라넷을 그래도 매일 쓴다. 2026년 1~9월 데이터(`db_backup_260915.sql` 집계): 프로젝트 125건, 견적 줄 1,379행, 지급요청 464건(요청자 11명), 법인카드 사용 433건(작성자 10명), 로그인 세션 7월 한 달 1,453회.
- 인트라넷의 강제력이 곧 채택 지렛대다: 돈이 나가려면 견적 줄 → 지급요청 → 3단 결재를 거쳐야 한다. 사람들은 시스템이 좋아서가 아니라 지급 경로라서 쓴다.
- 사용자는 처음에 "다른 사람이 원한다는 증거는 없다"고 했으나, 인트라넷 사용 자체가 그 증거다. 새 시스템이 인트라넷의 지급 경로를 그대로 이어받으면 수요는 자동으로 따라온다.
- 반대 증거도 있다: ERP 시도 #1(`260807`)·#2(`260907`)는 41일간 1,845커밋, 63만 줄, 1만 3천 개 테스트를 만들었으나 사용자 0, 운영 데이터 0. 시도 #0(`plant8-erp-rebuild`)은 "20명이 쓸 것에 비해 너무 크다"로 폐기. 세 번의 실패 원인은 수요가 아니라 범위와 "다 만든 뒤 옮긴다"였다.

**ERP #2** (`260907`, 진행 중이던 것): TypeScript, React 19 + Vite, Hono 4 on Node 22, Postgres(Cloud SQL), Cloud Run. 메뉴 16, 화면 36(틀 6종 위), 표 70, `/api` 236개, 테스트 약 6,500개, guards 43, CI 5, Claude 훅 11, CSS 토큰 124. 디자인 시스템과 인쇄물 양식 있음. 미결 54건, 인트라넷 이관 파이프라인 `server/도구/이관/` 미완(E4). 문서 md 888파일 15만 9천 줄, `00_이어하기-지시문.md` 1MB. 사용자 판정: "기능은 어느 정도 괜찮은 거 같은데 너무 정리가 안 되어있고 특히 시스템 디자인이 처음 보는 사람들이 알아보기 어렵게 구성되어있어."

**사람의 동선**: 기획본부 PM이 전화·구두로 발주 → 행사 진행 → 나중에 몰아서 견적 줄·지급요청 입력 → 경영관리는 그때 처음 금액을 봄 → 지출결의가 한꺼번에 몰림 → 자금 계획 불가 → 프로젝트 손익은 끝나고도 불명확.

## Target User & Narrowest Wedge

세 사람이 모두 아프다고 답했고(대표·경영관리 담당자·기획본부 PM), 데이터의 출발점은 PM이다.

- **기획본부 PM** (입력자): 거래처에 "진행하세요" 한 직후 폰에서 견적 실행 탭의 줄을 골라 "발주됨"으로 표시한다. 거래처는 자동완성, 금액은 몰라도 되고("미정"), 예정 지급일은 기본값이 채워진다. 행사가 끝나고 네고로 확정되면 같은 줄에 확정 금액을 적고 지출결의를 올린다. 두 번 적지 않는다. 클라이언트 요구로 바뀌면 그 줄을 고치거나 취소한다(이력 남음).
- **경영관리 담당자** (감시자): 프로젝트별 발주됨 줄의 예상 실행가와 예정 지급일을 보고 이번 달·다음 달 나갈 돈을 미리 안다. 증빙 없는 지출결의를 쫓아다니지 않는다.
- **대표·팀장** (판단자): 프로젝트 상세 상단의 네 숫자(견적 / 예상 실행가 합 / 확정 실행가 / 수익금액·수익률)로 다음 견적·수주를 판단한다. 대표는 전체, 팀장은 자기 팀.

사용자는 좁은 조각(스트랭글러, 손익 화면만) 대신 **260907 기능 전부 + 규칙을 1차에 포함**하기로 세 번 확인했다. 그래서 "가장 좁은 조각"은 범위가 아니라 **순서**다: 인트라넷 4기능 동등 + 이전 → 발주 시점 예정 지출 + 진행 현황 → 나머지 기능 정리 + 규칙. 9/30에 뒤쪽이 덜 다듬어져도 앞쪽은 실데이터로 돌아가야 한다.

## Constraints

- **일정**: 2026-09-30 직원 데모(13일). 데모에서 의견을 받고 절체 날짜를 정한다.
- **인력**: 사용자 1인 + Claude Code. 검토자 없음. 회사에 개발자가 없고 사용자는 취미 개발자다. 따라서 **운영은 코드 수정 없이** 관리 화면과 설정으로 되어야 하고, 코드는 한 사람이 Claude Code로 고칠 수 있을 만큼 단순해야 한다. 큐·마이크로서비스·영리한 추상화 금지.
- **호스팅**: 개인 Google 계정의 Cloud Run + Cloud SQL(Postgres)에서 먼저 이전·실행해 보고, 회사 Google Cloud로 옮겨 공개한다. 프로젝트 ID를 코드에 박지 않고, 배포와 이전을 스크립트 한 번으로 재현할 수 있어야 한다. 회사 도메인 Google 로그인은 개인 계정에서 검증할 수 없다.
- **공존**: 절체 전까지 인트라넷은 그대로 쓴다. 직원에게 같은 것을 두 번 입력시키지 않는다.
- **비용**: 구독·라이선스 도구 없음. "비용이 들지 않고 현재 회사에 알맞은 시스템"이 목적.
- **개인정보**: 기타소득 확인증(주민등록번호), 계좌번호, 고객사 행사 참가자 DB가 관련된다. `/cso` 보안 감사 필수. 인트라넷 백업 리포에 직원 비밀번호 평문·계좌 732건·RDS 비밀번호가 들어 있다(값은 이 문서에 싣지 않음).
- **디자인**: 프로젝트 `DESIGN.md` 절차가 우선한다. `docs/design/SYSTEM.md`가 없으면 화면을 만들지 않고 §1(브리프)→§2(발산)→§3(수렴)을 먼저 한다. 이 세션에서는 목업을 만들지 않았다.
- **규모**: 10명 → 30명. 동시 사용자 수십 명 수준이라 성능보다 이식성과 단순함이 우선.

## Premises

사용자가 확인한 9개. 3번과 8번은 제안(축소)을 사용자가 근거를 들어 거부하고 확정했다.

1. **핵심 가치**: 기획본부와 경영관리본부가 프로젝트마다 같은 숫자(견적, 예정 지출, 실제 지출, 손익)를 본다. 이게 안 되면 나머지 기능은 의미 없다.
2. **근본 원인은 입력 시점**: PM이 발주 후 몰아서 입력한다. 260907 실측으로도 협력사가 채워진 견적 줄은 5.7%뿐이다. 1차에 견적 실행 탭의 줄 단위 **"발주됨" 상태**(발주 시각·담당·예정 지급일, 예상 실행가는 빈칸·"미정" 허용)를 넣고, 폰에서 그 목록을 고치게 한다. 새 표를 만들지 않는다(260907 원칙 "프로젝트 비용은 견적 줄에서만", 08-10). 이 입력은 PM 자신에게 이득이 있어야 한다: 네고 뒤 확정 금액을 같은 줄에 적으면 그게 곧 지출결의가 되어 다시 적지 않는다.
3. **260907 기능 전부를 가져오되 분류표대로 다룬다**: 보완·수정·대체 항목은 1차에 완성하고, 보류 항목(매출·수금·리저브)은 코드는 유지하되 메뉴에서 숨긴다. 9/30까지 신규 구현은 셋(견적 줄 "발주됨" 상태 + 폰 목록 화면, 권한 단순화, 설정 분류 + 레지스트리 테스트)뿐이고 나머지는 정리·재디자인 + 이전이다. 증빙 풀은 260907에 이미 있어 신규가 아니다. 순서는 인트라넷 4기능 → 예정 지출·진행 현황 → 나머지 정리·규칙. (제안: 5화면으로 못 박고 나머지 숨김. 사용자 거부: "기능이 너무 없어서 크게 만든 거고, 기능은 괜찮은데 정리와 디자인이 문제". 이후 "가볍고 단순하면서도 효율적으로" 요청에 따라 아래 분류표로 합의) 단, 권한 단순화·설정 분류·발주됨 상태는 260907에 없던 **신규 구현**이며, 체크포인트 규칙에 따라 9/30 이후로 밀릴 수 있다.
4. **260907을 가져와서 깎는다**: 새로 짓지 않는다. `260917`은 260907의 정리본이다. 사용자 요청: "260907을 가져오되 여기에 사용된 코드들을 더 깔끔하게 정리되게".
5. **9/30 데모는 실데이터로**: 인트라넷 2,849행이 이전된 상태여야 의견이 나온다. 이전이 첫 작업이다.
6. **절체 전 이중 입력 없음**: 데모 뒤 절체 날짜를 정하고 그때까지 인트라넷은 그대로 쓴다.
7. **회사 GCP로 옮길 수 있게**: 프로젝트 ID 미고정, 재현 가능한 배포, 이전 스크립트 재실행 가능.
8. **규칙(결재선·증빙 필수 등)도 1차에 넣는다**: 단 데모 반응에 따라 조정할 수 있게 설정으로 켜고 끌 수 있게 한다(260907의 `settings`·`money_rules`·`formulas` 재사용). 금액에 따라 결재를 건너뛰는 규칙은 만들지 않는다(사용자 결정 08-27·09-12, `09_권한-기준선.md` 결정 4).
9. **화면 기준은 하나**: "처음 보는 직원이 설명 없이 자기 일을 찾는다." `DESIGN.md` 절차로 `SYSTEM.md`를 먼저 확정하고 260907의 틀 6종(AppShell, List, Form, Detail, Dashboard, Phone)과 토큰 124개를 교체해 36화면을 한 번에 바꾼다. 화면을 하나씩 고치지 않는다.

### 용어 정의

용어와 식은 260907 정본(`docs/03_용어.md`, `docs/06_업무/08_손익-합계.md`, `server/src/profit.ts`, `formulas` 표)을 따른다. 모든 금액은 공급가액이다(부가세는 원가가 아니다).

- **견적**: 프로젝트의 견적 줄 합계(클라이언트에 제시한 금액, 공급가). 완료 전 손익의 분모(진행 중 = 상세 견적 합, 없으면 사전견적).
- **매출**: 붙은 계산서 전부(종료일 기준). 완료 프로젝트의 손익 분모.
- **실행가**: 견적 줄의 `cost_amount`. 지출결의·구매 요청이 붙기 전에는 **예상**, 지출결의 제출 순간 잠겨 **확정**이 된다(`is_cost_locked`, 08-10). "지금 실행가 = 확정된 줄은 확정값, 아직인 줄은 예상값". 실제 값의 우선순위는 뷰 `quote_item_costs`가 정한다: 증빙 > 지출결의·구매 요청 > 견적.
- **발주됨**: 견적 실행 탭의 줄에 얹는 상태. PM이 거래처에 "진행하세요" 한 순간 그 줄을 발주됨으로 표시한다(발주 시각·담당·예정 지급일 `scheduled_payment_date`). 예상 실행가는 있으면 그대로, 없으면 빈칸 + "미정" 딱지. 취소는 삭제가 아니라 취소 표시. 변경은 줄 이력으로 남는다. 인트라넷 `pay_status`에도 260907에도 없던 상태.
- **예상 실행가 합(예정 지출)**: 발주됨이면서 아직 잠기지 않은 줄의 예상 실행가 합. "미정" 줄은 0으로 세되 건수를 따로 보여 준다. 네고 뒤 PM이 같은 줄에 확정 금액을 적고 지출결의를 올리면 그 순간 잠겨 확정 실행가로 옮겨 간다.
- **확정 실행가**: 잠긴 줄의 실행가(지출결의 금액·구매 요청 `confirmed_amount`·대신 낸 원천징수·조정 줄). 지출결의는 PM이 상신하는 금액이 그 순간 실행가로 굳고 경영관리는 증빙으로 부가세만 덮는다. 구매 요청은 경영관리가 증빙대로 `confirmed_amount`를 적는다.
- **수익금액** = 매출 − 실행가(진행 중이면 견적 − 지금 실행가). **수익률** = 수익금액 ÷ 매출(진행 중이면 ÷ 견적). 소수 0쪽 버림. 식은 `formulas` 표 키 `profit.line.amount`·`profit.line.rate`가 덮는다(09-14).
- **네 숫자**(프로젝트 상세 상단): 견적 / 예상 실행가 합(발주됨) / 확정 실행가 / 수익금액·수익률. 예상과 확정은 같은 줄이 한 번에 한쪽에만 든다(잠김 여부로 갈림).
- **정산**: 완료 수락 순간 `settlement_records`에 찍고 안 움직인다. 확정 뒤 변동은 `money.settled_adjust=show` 표시만.
- **법인카드 이중 계산 방지**: 인트라넷 `pay_status=법카사용` 견적 줄은 `CARD_USED`와 연결만 하고, 이관 뒤에는 260907 구매 요청(`paid_by_requester=true`)으로 옮겨 실행가에 한 번만 든다.
- **시연 데이터**: 데모용 행은 `source='demo'`로 시드한다. 규칙(지출결의 초안, 알림 1·3·4)은 전역 설정이지만 `source='intranet'`(미러) 행에는 적용하지 않고 `source='erp'`·`'demo'` 행에만 적용한다. 절체 때 `source='demo'` 행은 전부 삭제한다.
- **실데이터로 동작**: 화면별로 다르다. 프로젝트·견적·지출결의·법인카드 = 미러된 인트라넷 데이터 **읽기**. 결재함 = `source='demo'` 시드 행에서만 쓰기(미러 행은 읽기 전용). 발주 폰 입력 = 실제 쓰기(새 시스템 소유). 연차·증빙 풀 = 새 시스템 소유 쓰기.
- **미러링**: 절체 전까지 인트라넷 DB를 하루 1회 이상 새 DB로 복사하는 것. 미러 행은 인트라넷이 소유하고 새 시스템은 읽기만 한다.

## Recommended Approach

**A + C.** A만이 13일을 지키고, C가 데모를 살아 있는 것으로 만들며 이관 재실행을 강제한다. 사용자 선택.

**정리 원칙** (사용자 요청 "더 깔끔하게 정리"에 대한 경계):
- 정리는 동작을 바꾸지 않는다. 기존 테스트가 정리의 판정 기준이다. 테스트가 깨지면 정리가 아니라 변경이다. 권한 단순화·설정 분류와 견적 줄 발주됨 상태는 처음부터 **변경**으로 분류하고, 관련 테스트는 새 구조로 다시 쓴다.
- 리포 밖으로 보낼 것: `00_이어하기-지시문.md`(1MB), `docs/` 중 결정 기록(`90_결정-기록.md`)과 목적(`00_목적.md`) 외의 회의록·점검·인수인계. 별도 보관 폴더나 별도 리포로 옮기고 링크만 남긴다.
- 상태의 단일 출처를 GSD `.planning/`으로 옮긴다. 인수인계 문서 방식은 끝낸다.
- guards 43개는 "데모를 지키는 것"만 남긴다(`screen-hardcoded-style`, `screen-four-states` 등 화면 일관성 guards는 유지, 라운드·에이전트 운영용 훅은 제거).
- 폴더는 처음 보는 사람이 `app/` `server/` `db/` `docs/`에서 자기 일을 찾을 수 있게. `any` 29개 제거, 죽은 라우트·화면은 메뉴 사용 여부로 판정해 제거.
- 정리 작업은 이전·틀 교체·예정 지출보다 뒤에 둔다. 정리가 데모를 밀어내면 안 된다.

## 260907 문서 대조 (2026-09-17 저녁, 본문에 반영됨)

근거: `docs/research/erp260907-money-flow.md`, `docs/research/erp260907-design-conflicts.md`(결정 기록은 최신부터). 아래 항목은 본문(전제·용어 정의·분류표·권한·설정·알림·순서·런북·성공 기준)에 반영했다. 기록으로 남긴다.

1. **발주는 새 표가 아니라 견적 실행 탭 위에 얹는다.** 260907 원칙 "프로젝트 비용은 견적 줄에서만"(08-10). 실행가 `quote_items.cost_amount`가 예상이자 확정이고, 진행 중 손익에 예상값이 이미 든다("지금 실행가"). 협력사 발주 문서·미확정 상태는 없고, 실측으로 협력사가 채워진 줄은 5.7%뿐이다(같은 입력 지연). 따라서 "발주 목록" = 견적 실행 탭의 줄 목록이며, 추가할 것은 줄 단위 `발주됨/취소` 상태 + 발주 시각·담당 + 예정 지급일(`scheduled_payment_date` 기존 칸) + 변경 이력 + 폰 화면뿐이다. `order_links`·별도 발주 표는 만들지 않는다. 예정 지출 = 발주됨이면서 잠기지 않은 줄의 예상 실행가 합. 금액 미정이면 실행가 빈칸 허용 + "미정" 딱지.
2. **금액 구간별 결재선은 이미 금지된 결정이다.** 08-27·09-12 "금액에 따라 결재 없이 처리하는 것이 없다", 조건은 업무 갈래만. 설정 4묶음에서 금액 구간을 뺀다. 결재 기본값은 260907의 4단(제출자→팀장→본부 책임자→경영관리 책임자→대표, 빈 자리 건너뜀). 인트라넷 3단은 이관 매핑에서만 쓴다.
3. **손익 식은 260907 것을 따른다.** 수익금액 = 매출 − 실행가, 수익률 = 수익금액 ÷ 매출(공급가). 분모는 완료 = 매출, 진행 = 상세 견적 합(없으면 사전견적). 식은 `formulas` 표가 정한다. 이 문서의 "견적 − (예정 + 실제), ÷ 견적"은 폐기하고 용어 정의를 고친다. 실제 지출 우선순위는 뷰 `quote_item_costs`(증빙 > 지출결의 > 견적)가 이미 정의한다.
4. **권한은 계급 5(`ceo`·`head`·`team_lead`·`staff`·`sys_admin`) + 직책 층이 기준선**(`docs/09_설계/09_권한-기준선.md`). 이 문서의 "역할 5 + 팀"은 계급 5와 거의 같다. 새 구조를 만들지 않고 기준선 문서를 출발점으로 직책 층을 단순화할지만 정한다.
5. **알림은 앱 안 19갈래가 이미 있고, 알림함 화면 대신 서랍을 키우기로 했다(09-17).** 4규칙은 새 갈래 추가로 다룬다. 규칙 4(미증빙 7일)는 "증빙이 먼저다" 규칙 때문에 성립하지 않으므로 "선결제 14일 초과"로 바꾼다. "실행가 필요"는 알림이 아니라 배지(08-30).
6. **증빙 흐름은 260907이 이미 사용자 말과 같다.** 경영관리 등록·공개 → 건에 붙임, 떼면 예상으로 되돌아감. 분류표의 증빙 "보완"은 유지하고 새 흐름을 만들지 않는다.
7. **구매 요청은 법인카드·온라인구매 전용이고 결재 없음(09-16).** "구매 요청 → 발주로 대체"는 틀렸다. 구매 요청은 그대로 두고, 협력사 발주는 1번의 실행 탭 상태로 처리한다. 진입점은 09-17 기준 4곳으로 확인됐다.
8. **260907 업무 규칙 유지**: 지급 기한 작성일 + 60일, 그 전 마지막 금요일, 목요일 14시 컷오프, 마감은 지급일의 전 영업일(공휴일이면 당겨짐), 선결제 사유 필수·14일, 부가세는 원가 아님(견적·매출·실행가 전부 공급가), 원천징수는 계산식 해석기(`server/src/formula.ts`, eval 금지), 완료 잠금 하나로 지난 기간 잠금 대신, 완료 수락 시 정산 스냅샷 불변(`settlement_records`), 번호 서식(프로젝트 `26001`, 견적 `26001-1차`, 지출결의 `26001-0001` 전사 통합 순번, 구매 요청 `26001-C0001`), 영업일 = 월~금 + 공휴일 자동 생성, 모든 시각 KST, "지우지 않는다"(보관함 이동, 확인증만 5년 뒤 파기), 지출결의만 0/음수 별도 제약(09-08).
9. **설정은 이미 `formulas`·`money_rules`(날짜별 값)와 항목 문서(`docs/07_설정-항목.md`)가 있다.** 6묶음은 "새 구조"가 아니라 133개를 묶는 분류로 낮추고, 레지스트리 테스트만 추가한다.
