## 1. 증빙 종류 코드표 (7종 시드)

사용자 결정: REQUIREMENTS EXP-15의 예시 7종을 그대로 시드한다.

| 증빙 종류 | 세금 규칙 | 세율 | 기준일 | 비고 |
|---|---|---|---|---|
| 세금계산서 | 부가세 가산 | 10% | 증빙일 (없으면 작성일) | 가장 흔한 종류 |
| 계산서 (면세) | 없음 | — | — | 면세 재화·용역 |
| 카드 전표 | 부가세 가산 | 10% | 증빙일 (없으면 작성일) | |
| 현금영수증 | 부가세 가산 | 10% | 증빙일 (없으면 작성일) | |
| 기타소득 | 원천징수 (수령자 부담) | **기타소득금액 × 22%** | 지급일 (없으면 지급 예정일) | 면제: 기타소득금액 5만원 이하 |
| 사업소득 | 원천징수 (수령자 부담) | 3.3% | 지급일 (없으면 지급 예정일) | |
| 해외 인보이스 | 없음 | — | — | 외화(USD) 건이 여기 붙는다 |

**세금 규칙 4종** (ROADMAP Phase 3 기준 5): 없음 / 부가세 가산율 / 원천징수율 + 면제 기준(수령자 부담) / 원천징수 회사 대납. 7종 시드는 앞의 3종을 쓰고, 네 번째(회사 대납)는 아래 2의 경품 건에서 쓴다.

**종류마다 갖는 칸**: 세금 규칙 · 세율 · 절사 단위(1원/10원) · 절사 방식(절사/반올림/올림) · 최소 징수액 · 적용 기준일 종류. 값은 `phase-03-masters.md` §5-2·5-3.

**미정 — 필요경비율 칸**: 기타소득 22%가 기타소득금액 기준이므로 증빙 종류마다 필요경비율(60% / 0% / 그 외)을 둘 칸이 필요하다. 현재 코드표 설계에 그 칸이 없다. Phase 3 계획에서 더할지 정한다 (`phase-03-masters.md` §10의 3-E와 같은 항목).

**거래처 기본 증빙 종류**: 거래처 마스터마다 기본값을 두어 지출결의·카드 사용 등록 때 자동으로 채워진다(MAST-01). 사람은 바꿀 수 있다.

## 2. 회사 대납 원천징수 (경품 등)

| 항목 | 값 | 출처 |
|---|---|---|
| 계산 방식 | **gross-up (역산)** | 문답 |
| 뜻 | 수령자가 약속한 금액을 그대로 받고, 세금은 회사가 더 부담한다 | 문답 |
| 손익 처리 | 회사가 대납한 세금은 **그 줄의 프로젝트(또는 팀) 비용에 더해진다** | 확정 (EXP-15, PROJECT.md) |
| 기준일 | 지급일 (미지급이면 지급 예정일) | 확정 시드 |

**예**: 경품 100만원을 주기로 했다면 수령자는 100만원을 받고, 회사가 원천징수세액을 얹어 신고한다. 단순 비율 방식(100만원에서 세금을 떼어 수령자가 덜 받는 방식)이 아니다.

계산은 `domain/money.applyTaxRule()` 한 곳에서만 한다(Issue 8). Phase 5·6은 이 함수를 부르기만 한다.

## 8. 구매 요청

| 항목 | 값 | 출처 |
|---|---|---|
| 결재 | **없음** | 확정 (EXP-10) |
| 문을 가르는 방식 | **견적 줄의 협력사가 설정된 이름이면 구매 요청만, 그 밖이면 지출결의만.** 사람이 고르지 않는다 | 문답 |
| 그 이름 | **'온라인구매'** (설정 키) | 문답 |
| 흐름 | 직원 신청 → **경영관리 담당자 1명**이 법인카드로 구매 → 구매 완료 처리 → 카드 사용 건으로 연결 | 문답 |
| 상태 | 신청 / 구매 완료 / 취소 | 확정 (EXP-10) |
| 번호 부여 | **생성 시** (`26001-C0001`) | 확정 (ADMN-09) |
| 견제 | 요청자 ≠ 결제자 + 증빙으로 확정 비용 사후 확인 | 파생 |

**미정 — 경영관리 부재 시**: 경영관리본부가 1명이라 그 사람이 자리를 비우면 구매 요청·지급·증빙 처리가 멈춘다. 260907은 이걸 "대표 대행(위임이 아니라 대표 본인 권한 사용, 행동 로그에 대표 이름으로 남김)"으로 풀었다. 현 요구사항에는 없다. **사용자가 Phase 6 계획 때 정한다.**
