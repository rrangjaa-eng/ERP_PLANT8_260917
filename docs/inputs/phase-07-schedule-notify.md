## 4. 알림 발송

| 항목 | 값 | 출처 |
|---|---|---|
| 횟수·시각 | **하루 1번 · 오전 9시** | 문답 |
| 동작 | Cloud Scheduler가 `/internal/notify-tick` 단일 엔드포인트 호출 | 확정 (NOTI-04) |
| 채널 | 앱 안 알림함 + 이메일 | 확정 (NOTI-01·02) |
| 중복 방지 | `notification_log` 유니크 제약 (INSERT … ON CONFLICT DO NOTHING) | 확정 (NOTI-04) |
| 동시 실행 방지 | advisory lock | 확정 (ROADMAP Phase 7 기준 4) |

**하루 1번을 고른 이유**: 메일이 하루에 여러 번 오면 직원이 안 보게 된다. tick 호출이 적을수록 비용도 적다.

## 6. 기본 알림 규칙 4개 (시드)

| # | 규칙 | 조건 | 받는 사람 | 상태 |
|---|---|---|---|---|
| 1 | 프로젝트 종료 후 지출결의 없음 | 종료일 **+7일**, 그 프로젝트에 지출결의 0건 | **담당 PM** | 문답 |
| 2 | 지급 예정일 임박 | **미정** | **미정** | — |
| 3 | 결재 대기 초과 | 그 단계에서 **3일** 경과 | **그 단계 결재자** | 문답 |
| 4 | 증빙 미첨부 | **지급 완료 +7일**, 증빙 0건 | **기안자** | 문답 |

**규칙 2가 미정인 이유**: 사용자가 나중에 정하기로 했다. Phase 7 계획 때 며칠 전인지와 받는 사람(경영관리만 / 경영관리 + 기안자)을 정한다. 시드 없이 화면에서 만들어도 되지만, 기본 규칙 4개는 시드로 제공한다는 것이 요구사항(NOTI-03)이므로 Phase 7 전에는 값이 필요하다.

**규칙 4와 선결제 독촉의 관계**: 선결제 건은 별도로 14일 독촉 규칙이 붙는다(`phase-06-payment.md` §6). 규칙 4는 "지급은 끝났는데 증빙이 안 붙은" 건을 잡는 것이라 역할이 겹치지 않는다.

**Phase 6에서 미룬 알림 2개도 여기서 붙는다**
- 선결제 14일 증빙 독촉
- 경영관리 대리 등록 시 담당 PM 알림

## 7. 알림 규칙 구조 (확정 — 다시 묻지 않음)

조건 종류는 **코드에 등록**되고, 규칙은 그 조건 종류 × 파라미터의 인스턴스다(NOTI-03).

| 파라미터 | 고를 수 있는 값 |
|---|---|
| 대상 문서 | 지출결의 · 구매 요청 · 결재 · 증빙 · 프로젝트 · 연차 |
| 조건 | 상태 + 기준일로부터 N일 전/후, 교차 문서 조건 |
| N일 | 숫자 |
| 받는 사람 | 계급 · 담당자 · 팀장 |
| 채널 | 알림함 · 이메일 |

관리자는 **등록된 조건 종류로 새 규칙을 만든다**. 조건 종류 자체를 늘리려면 코드가 필요하다.

## 9. 전 메뉴 권한 검수 (Phase 7 끝)

입력값이 아니라 작업이다. Phase 3에서 미룬 것을 여기서 끝낸다.

- 누수 스캔 생성기가 Phase 3~7의 모든 액션 · DTO 타입 · Excel 내보내기 함수를 덮는다
- 정보 노출표에 매핑되지 않은 DTO가 0이어야 한다
- 계급별 기본값 표와 핵심 행동 종류 목록을 전 메뉴 기준으로 확정한다
- Playwright 계급별 노출 스모크(역할 4종이 같은 화면에서 보는 것/못 보는 것)가 CI에 있다
