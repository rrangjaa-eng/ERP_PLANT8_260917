## 2. 구매 요청 (`purchase_requests`)

- **뜻**: 「법인카드로 살 것을 요청하는 문서다. 온라인 구매물이 주로 여기 든다. 결재를 타지 않는다」(`06_구매요청.md:12`). 「법인카드 사용(K)」(현장 결제 사실 기록)도 같은 표(`paid_by_requester=true`).
- **칸**(`010_tables.sql:2011`): `project_id`·`quote_item_id`(행사 비용이면 필수, `project_needs_quote_item` 제약)·`requested_by`·`status_code`·`item_name`·`quantity`·**`requested_amount NOT NULL, >0`**·`is_prize`·`purchase_place`·`vendor_id`·`handled_by/at`·`card_paid_date`·`receipt_id`·`confirmed_amount`·`cancel_reason`(취소 시 필수)·`product_url`·`detail`·`receipt_waived*`·`number(26001-C0001)`·`paid_by_requester`·`pursuit_item_id`(수주 비용)·`card_id`·`card_user_id`·`card_mismatch`.
- **상태**(`purchase_statuses`, `is_open`/`is_confirmed` 딱지): 「`receipted`가 따로 있는 까닭 — 요청 금액은 확정 실행가가 아니다. 경영관리가 증빙을 붙이고 증빙대로 실행가를 적어야 확정된다」. `receipted_needs_both` 제약: 증빙(또는 면제)+`confirmed_amount` 둘 다.
- **금액 필수?** 예. `requested_amount NOT NULL` + `amount_positive`. 견적 실행 탭에서 올리면 「견적 실행가(공급가)+부가세=합계」를 자동으로 채움(09-16 물음17·18㉠). 금액 없이 「말로 발주」한 상태를 담을 자리 없음.
- **변경·취소**: 취소는 경영관리가 어디서든 사유와 함께; 요청자는 「취소 요청」(알림 `purchase_cancel_request`). 「증빙등록까지 간 건을 취소하면 붙였던 전표가 자동으로 떨어져 「주인 없음」으로 돌아가고 확정 실행가도 함께 비워진다」(08-24 M-27). 금액 변경은 「요청 금액 ≠ 확정 실행가」를 전제로 경영관리가 `confirmed_amount`로 덮는 구조; 요청자가 요청 금액을 나중에 고치는 규칙은 **문서에 없음**(서식 「고치기」만 존재, `PurchasesForm.tsx` 머리주석 언급).
- **「진입점 0곳」 내력**(결정 기록 `5442`, 09-16): 08-10 「견적 줄에서 구매 요청」 약속 → **08-24 사용자 확정으로 뒤집힘**(단추 걷고 「지출결의 창으로만」) → 09-03 그 지출결의 법인카드 갈래도 걷힘 → **09-15 결정 ⑤ 실측**: 「`createPurchase`를 부르는 화면이 지출결의·견적 어느 쪽에도 없었다 … 결제 전 구매 요청을 올릴 자리가 그동안 통째로 없었다」 → 09-16 사용자 「견적줄에서 바로 구매요청으로 이동하는 게 없잖아!!!」 → R-20(PR #17)·견적 실행 탭 손 신설 → 09-17 S-03 「「진입점 0곳」은 낡았다 — 지금 네 곳이다」. 즉 **일부러 미룬 것도, 미결로 남긴 것도 아니라 뒤집힌 결정을 앞에서 읽고 멈춘 오독의 누적**이었다(「결정 기록은 맨 뒤부터 읽는다」 09-16).

## 4. 변경 이력

- `audit_log`(넣기만 · `old_value/new_value jsonb`·`changed_keys`·`reason`): 설정·삭제·되살림·결재 이력·권한·면제·완료 잠금 해제·조정 줄·증빙 뗌(`05_기본-정책.md` 2절). 보는 사람 `sys_admin`만.
- 견적은 **차수**로 판 관리: 「차수마다 견적 한 벌이 통째로 남으므로 이전 차수를 열면 그때 얼마로 잡았는지 알 수 있다」(08-10) · 「차수는 되돌릴 수 없다」 · 「재견적 — 지출결의·구매 요청이 붙은 줄은 그 건과 함께 새 차수로 옮겨 온다」(08-24).
- 지출결의: `reject_count`·`last_reject_reason`·`resubmit_note`·「반려 이력은 문서에 그대로 남는다」. 재상신은 새 회차(08-27).
- 프로젝트 상세 「변경 이력」 카드는 **2차 이월**(`02_프로젝트.md:503`, 미결 `프로젝트상세-2차`).
- **고객 요구 변경 중간 대응**: 명시 절은 **없음**. 기제만 있음 — 승인 뒤 내부 칸(협력사·실행가)은 계속 고침, 고객용 칸은 재견적(`03_견적.md` 「잠금이 칸에 따라 갈린다」); 「계약이 줄거나 늘면 차수를 새로 만들어 반영한다」(`13_성과-정산.md:104`); 확정 뒤 변동은 `show`.

## 7. 손익 정의

`docs/06_업무/08_손익-합계.md:9`: 「수익금액 = 매출 − 실행가 / 수익률 = 수익금액 ÷ 매출 … 매출도 실행가도 공급가액」. 실제 셈은 `server/src/profit.ts` `셈하기()`(245행) 한 자리, 프로젝트 목록·손익·홈이 같이 씀:

```ts
const 견적있음 = 견적합 > 0n;
const 어림바탕 = 견적있음 ? 견적합 : 사전견적;           // 09-01
const 남은몫 = 잠겼나 ? 0n : 어림바탕 > 매출 ? 어림바탕 - 매출 : 0n;
const 분모 = 매출 + 남은몫;                              // 완료=매출, 진행=매출+안 끊을 몫
const 매출로세나 = 남은몫 === 0n;                        // 「확정/예상」 딱지
```

실행가 재료 = `quote_item_costs` 뷰(`090_views.sql:416`): 지출결의는 **`status_code <> 'draft'`**(즉 결재 중도 든다), 구매 요청은 **`<> 'cancelled'`**(요청 단계도 `requested_amount`를 세율로 역산해 든다), 둘 다 없으면 `cost_amount`(예상). ⚠ `08_손익-합계.md:66`의 「지출결의서 금액 — 결재가 끝난 것」과 뷰(제출 이후 전부)가 어긋난다. **예상은 든다**(「지금 실행가」), 정산 기준(`settlement_records`)만 「예상 안 든다」(`13_성과-정산.md` 2절 표). 실비 반영은 `withActualCosts()`(658행). 식 자체는 `formulas` 키 `profit.line.amount`·`profit.line.rate`·`profit.actual.amount`가 덮는다(09-14).

## 8. 직접 답

**A. 구두 발주 · 금액 미확정** — 문서는 이 경우를 **다루지 않는다**. 견적 실행 탭의 예상 실행가(`cost_amount`)가 「나갈 것으로 본 돈」이고, 지출결의는 「증빙(또는 선결제 사유)이 있어야 올리는 지급 요청」이라 **금액이 정해지기 전에는 올릴 수 없다**. 구매 요청도 `requested_amount NOT NULL`이라 금액 없이 못 선다. 협력사 발주 문서·「발주함/미확정」 상태는 없음. 문서가 가장 가깝게 말하는 자리: 「「증빙이 없다」와 「금액이 안 정해졌다」는 다르다. 계약을 마치고 지출결의를 올렸는데 세금계산서만 다음 달에 오는 일이 흔하다」(`13_성과-정산.md:129`) — 즉 **협의 후 확정 금액으로 지출결의를 올리는 것**을 전제로 한다. 행사 뒤 협상 마무리 관행은 **문서에 없음**.

**B. 요구 변경(협력사 추가·취소·금액 변경)** — 기제는 있으나 설계 절은 없음. 추가: 「견적에 없던 지출이 생기면 견적에 줄을 먼저 더한다」, 승인 뒤에도 실행 탭 줄은 세우고 뺄 수 있음(09-14). 금액 변경: 지출결의 제출 전까지 예상 실행가 자유, 제출 뒤 잠김(반려·거두기·보관이면 풀림). 취소: 지출결의 거두기(첫 결재 전)·반려→draft·보관; 구매 요청 취소(전표 떨어짐·확정 비움). 고객 계약 변경은 새 차수(확정 줄 이어받음). 「클라이언트 요구 변경」이라는 말로 정리한 절은 **문서에 없음**.

**C. 실행가 채우는 시점·최종 금액 기록자** — 실행가는 **견적 실행 탭에서 고객 승인 뒤** PM이 채운다(견적 시점이 아니라 진행 단계 · `03_견적.md:34` 표 「실행: 진행 단계 — 지출결의·구매 요청을 올린다」). 최종 금액: 지출결의는 **PM이 상신하는 금액이 그 순간 실행가로 굳고**(제출 기준) 경영관리는 증빙으로 부가세만 덮음 · 실제 지급일 기록; 구매 요청은 **경영관리가 증빙대로 `confirmed_amount`**(PM은 증빙만 붙일 수 있고 실행가는 못 적음, 08-26·09-16). 「협의 마무리 뒤 PM이 최종 금액을 고쳐 적는」 단계는 **문서에 없음** — 제출 후에는 견적 줄 실행가를 고칠 길이 잠겨 있다.
